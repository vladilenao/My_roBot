## Context

Бот работает в бесконечном цикле, обрабатывая один фиксированный инструмент (`NGU6 future`) из конфигурации. Архитектура модульная: `config → api → data → indicators → signals → notifier → scheduler`. Основная точка расширения — `scheduler/runner.py`, который связывает все модули. Конфигурация хранится в `src/config.py` как набор констант уровня модуля.

## Goals / Non-Goals

**Goals:**
- Интерактивный ввод нескольких инструментов при старте приложения
- Валидация каждого инструмента через API до запуска основного цикла
- Обработка списка инструментов в основном цикле с привязкой сигналов к инструменту
- Обратная совместимость: `TICKER` и `INSTRUMENT_TYPE` остаются как fallback для тестов и одиночного запуска

**Non-Goals:**
- Сохранение списка инструментов между запусками ( persistent config)
- Горячее добавление/удаление инструментов во время работы
- GUI или веб-интерфейс для выбора

## Decisions

### Решение 1: Интерактивный ввод через `input()` в отдельном модуле

**Выбор**: Новый модуль `src/instruments/selector.py` с функцией `select_instruments()`, использующей стандартный `input()`.

**Альтернативы**:
- Аргументы командной строки (`argparse`) — отвергнуты: пользователь должен видеть ошибки валидации и повторно вводить тикер, что неудобно в CLI без интерактивности
- Конфигурационный файл — отвергнут: противоречит требованию интерактивного выбора при каждом запуске

**Обоснование**: `input()` обеспечивает простой цикл ввод→валидация→повтор, соответствует требованию.

### Решение 2: Формат ввода `ТИКЕР ТИП`

**Выбор**: Пользователь вводит строки вида `SBER share` или `NGU6 future`. Тип необязателен — при отсутствии система запрашивает его отдельно.

**Альтернативы**:
- Отдельные запросы для тикера и типа — отвергнуты:增加 количество шагов
- Формат `ТИКЕР:ТИП` — отвергнут: менее интуитивен

### Решение 3: Валидация до запуска цикла

**Выбор**: Все инструменты валидируются до начала бесконечного цикла. Невалидные инструменты отсеиваются, цикл запускается только с валидным списком.

**Альтернативы**:
- Ленивая валидация при обработке — отвергнута: пользователь хочет знать о проблемах до начала мониторинга
- Валидация + повторный запрос при ошибке в цикле — частично реализована: при ошибке `find_working_instrument` запрашивается замена до запуска

### Решение 4: Модификация `make_decision` вместо обёртки

**Выбор**: Добавить параметр `instrument_label` в `make_decision()` для включения идентификатора инструмента в сообщение.

**Альтернативы**:
- Обёртка-декоратор вокруг `make_decision` — отвергнута: избыточная сложность
- Форматирование в `runner.py` — отвергнута: нарушает单一 ответственность `generator.py`

### Решение 5: Последовательная обработка инструментов

**Выбор**: Инструменты обрабатываются последовательно в рамках одной итерации, не параллельно.

**Альтернативы**:
- Параллельная обработка (`threading`/`asyncio`) — отвергнута: избыточная сложность для начальной реализации, API может иметь rate limits

## Risks / Trade-offs

- **[Rate limits API]** → Последовательная обработка минимизирует нагрузку; количество инструментов ограничено ручным вводом
- **[Долгий старт]** → При большом количестве инструментов валидация может занять время; митигация: информативный прогресс-вывод
- **[Отсутствие persistent config]** → При каждом запуске нужно заново вводить инструменты; митигация: можно добавить позже через `--config` флаг
- **[Одиночный инструмент]** → Сценарий с одним инструментом должен работать так же хорошо, как и с несколькими
