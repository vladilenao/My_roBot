## MODIFIED Requirements

### Requirement: Компактный формат сигналов
Нормативный уровень: MUST.
Представление решения ДОЛЖНО определяться шаблоном канала, а не общим форматтером. Отображаемое решение ДОЛЖНО оформляться одной строкой: BUY — `🟢 ПОКУПКА (BUY) — Цена: X`, SELL — `🔴 ПРОДАЖА (SELL) — Цена: X`, отклонённое фильтром решение (`filtered_out=True`) — `❌ Отклонено фильтром.` без цены. Консоль НЕ ДОЛЖНА печатать отдельную строку чистого отсутствия сигнала: `decision` с `outcome=no_signal` и без признака отклонения фильтром учитывается в сводке тика.

Строка отображаемого решения ДОЛЖНА начинаться с маркера `● `; за ним ДОЛЖЕН следовать `<инструмент>`, к которому через один пробел добавляется блок `(<таймфрейм>)` при наличии заданного задаче таймфрейма. Блок времени бара `HH:MM` и блок стратегии `| <имя>` включаются только при наличии соответствующих значений; блок `[<профиль>]` ДОЛЖЕН следовать за блоком стратегии и включается только при наличии значения профиля.

Значение `bar_time` решения ДОЛЖНО представлять момент ЗАКРЫТИЯ свечи последнего бара, а не момент её начала: момент начала бара в tz-naive UTC, сложенный с длительностью периода таймфрейма. Блок времени отображаемого решения ДОЛЖЕН применять сконфигурированное смещение от UTC в часах; при нулевом смещении выводится UTC-время закрытия без изменений. Московское время публикации сводки отсутствия сигналов определяется отдельным требованием и НЕ заменяет время бара в остальных решениях.

#### Scenario: Покупка
- **WHEN** решение имеет тип BUY, цену X, время закрытия бара 22:00, стратегию `macd_rsi_stoch`, профиль `raw`, а таймфрейм задачи `15m`
- **THEN** сообщение равно `● <инструмент> (15m) 22:00 | macd_rsi_stoch [raw] ➜ 🟢 ПОКУПКА (BUY) — Цена: X`

#### Scenario: Продажа
- **WHEN** решение имеет тип SELL, цену X, время закрытия бара 22:00, стратегию `macd_rsi_stoch`, профиль `basic_levels`, а таймфрейм задачи `1h`
- **THEN** сообщение равно `● <инструмент> (1h) 22:00 | macd_rsi_stoch [basic_levels] ➜ 🔴 ПРОДАЖА (SELL) — Цена: X`

#### Scenario: Нет сигнала
- **WHEN** консоль получает чистое решение об отсутствии сигнала внутри тика
- **THEN** индивидуальное сообщение `⏳ Нет сигнала.` не печатается; решение учитывается для сводки этого тика

#### Scenario: Отклонено фильтром
- **WHEN** решение доставляется с признаком `filtered_out=True`, в том числе со стороной HOLD
- **THEN** сообщение содержит статус `❌ Отклонено фильтром.` без цены и печатается сразу, а не учитывается как чистое отсутствие сигнала

#### Scenario: Нет профиля фильтрации
- **WHEN** профиль фильтрации не задан (пустое значение)
- **THEN** блок `[<профиль>]` в строке опускается

#### Scenario: Нет времени бара
- **WHEN** отображаемое решение не имеет `bar_time`
- **THEN** блок времени в строке опускается (нет `HH:MM`)

#### Scenario: Нет имени стратегии
- **WHEN** отображаемое решение не имеет имени стратегии
- **THEN** блок `| <имя>` в строке опускается

#### Scenario: Нет таймфрейма
- **WHEN** отображаемому решению не задан таймфрейм (пустое значение)
- **THEN** блок `(<таймфрейм>)` в строке опускается, маркер `● ` и `<инструмент>` выводятся без него

#### Scenario: Время в локальном поясе
- **WHEN** смещение часового пояса задано, например `+3` часа, а `bar_time` отображаемого решения равен `06:00` UTC
- **THEN** в сообщении блок времени выводится как `09:00`

#### Scenario: Нулевое смещение сохраняет UTC
- **WHEN** смещение часового пояса равно `0`, а `bar_time` отображаемого решения равен `06:00` UTC
- **THEN** блок времени выводится как `06:00`

### Requirement: Консольный канал доставки
Нормативный уровень: MUST.
Система ДОЛЖНА предоставлять консольный канал: доставка сообщения — вывод текста в stdout, сетевые вызовы отсутствуют. Канал ДОЛЖЕН по умолчанию принимать весь каталог пользовательских уведомлений и доставлять отображаемые уведомления синхронно, в вызывающем потоке. Пользовательские события вне настроенного набора ДОЛЖНЫ игнорироваться; служебные границы тика ДОЛЖНЫ приниматься независимо от этого набора и НЕ ДОЛЖНЫ иметь собственного пользовательского вывода. Чистые решения об отсутствии сигнала ДОЛЖНЫ обрабатываться согласно требованиям сводки тика, а не печататься индивидуально.

#### Scenario: Сообщение печатается
- **WHEN** консольный канал получает разрешённое пользовательское событие с текстовым представлением, отличное от чистого отсутствия сигнала
- **THEN** текст сообщения сразу выводится в stdout

#### Scenario: Событие неподдерживаемого типа пропускается
- **WHEN** пользовательское событие отсутствует в настроенном наборе уведомлений канала
- **THEN** событие игнорируется, вывода нет

#### Scenario: Граница тика не является сообщением
- **WHEN** консоль получает служебную границу начала или завершения тика
- **THEN** обрабатывается состояние тика без отдельной строки с именем границы или её идентификатором

### Requirement: Каталог типов событий
Нормативный уровень: MUST.
Каталог ДОЛЖЕН содержать 19 существующих типов пользовательских уведомлений и два служебных типа `tick_started` и `tick_finished`. Консоль по умолчанию принимает все пользовательские типы и обязательно получает границы тика; Telegram по умолчанию получает девять lifecycle-типов: `signal`, `trade_opened`, `position_added`, `stop_hit`, `target_hit`, `stop_moved`, `trade_closed`, `trade_cancelled`, `order_rejected`.

Отмена/отклонение заявки актуализируют карточку с учётом её текущего состояния, а не автоматически означают закрытие уже открытой позиции. Явно заданные пользователем наборы уведомлений ДОЛЖНЫ сохраняться без скрытого добавления отображаемых событий. Обязательная техническая доставка границ тика НЕ ДОЛЖНА включать отключённые уведомления или требовать изменения существующих списков `events`.

| `trade_cancelled` | ✓ | ✓ | подтверждённая отмена |
| `order_accepted` | ✓ | — | подтверждение заявки |
| `order_rejected` | ✓ | ✓ | подтверждённый отказ заявки |
| `protection_armed` | ✓ | — | подтверждение защиты |

#### Scenario: Состав по умолчанию
- **WHEN** наборы уведомлений не переопределены
- **THEN** консоль принимает 19 пользовательских типов и две служебные границы, Telegram — девять перечисленных lifecycle-типов без границ тика

#### Scenario: Отказ не попадает в Telegram
- **WHEN** сигнал не допущен
- **THEN** `rejected` идёт в консоль, Telegram не получает его и не создаёт карточку

#### Scenario: Явный список событий сохраняется
- **WHEN** пользователь оставил Telegram только `signal` и `trade_closed`
- **THEN** остальные типы не доставляются скрыто; доступные карточки и итоги работают без обязательного промежуточного поста

#### Scenario: Старый список консоли не требует миграции
- **WHEN** пользователь задал консоли `events = ["decision", "error"]` без границ тика
- **THEN** консоль получает обязательные границы и корректно завершает агрегацию; остальные пользовательские уведомления не включаются

### Requirement: Порт канала уведомлений
Нормативный уровень: MUST.
Абстракция канала ДОЛЖНА объявлять эффективный набор подписки и ДОЛЖНА иметь абстрактный метод обработки события. Создание экземпляра абстракции, как и создание наследника без переопределения метода обработки, ДОЛЖНО завершаться ошибкой. Эффективная подписка ДОЛЖНА объединять настроенные пользовательские уведомления и обязательные для канала служебные типы; проверка разрешения пользовательского вывода ДОЛЖНА сохранять настроенный фильтр.

#### Scenario: Канал фильтрует по типу
- **WHEN** канал подписан на ограниченный набор пользовательских уведомлений
- **THEN** пользовательские события других типов игнорируются, а обязательные служебные границы продолжают доставляться

#### Scenario: Абстрактный канал нельзя инстанцировать
- **WHEN** создаётся экземпляр абстрактного канала
- **THEN** выбрасывается ошибка

## ADDED Requirements

### Requirement: Консольная сводка отсутствия сигналов за тик
Нормативный уровень: MUST.
Консоль ДОЛЖНА учитывать разрешённые чистые решения об отсутствии сигнала между началом и завершением одного тика. Если тик завершён штатно, учтено хотя бы одно такое решение и внутри тика не напечатано ни одного другого уведомления, консоль ДОЛЖНА вывести ровно одну сводку вида `● HH:MM ➜ ⏳ Нет сигналов (N пар: <имена>)`. Слово «пара» ДОЛЖНО согласовываться с числом: `1 пара`, `2 пары`, `8 пар`, `11 пар`, `21 пара`.

N ДОЛЖНО соответствовать числу решений об отсутствии сигнала по обработанным привязкам «инструмент × стратегия» текущего тика; разные таймфреймы и профили учитываются отдельно. Имена инструментов ДОЛЖНЫ быть короткими пользовательскими именами, без повторений, в порядке первого появления. Неизвестное короткое имя ДОЛЖНО отображаться как `контракт не указан`, а не сырой биржевой код.

Любое действительно напечатанное внутри тика уведомление ДОЛЖНО подавлять сводку независимо от порядка его появления относительно HOLD. События вне пользовательского фильтра, служебные границы и события без текстового представления НЕ ДОЛЖНЫ считаться напечатанными. Отключение `decision` в пользовательском фильтре ДОЛЖНО также отключать сводку. Вне активного тика чистые решения об отсутствии сигнала НЕ ДОЛЖНЫ печататься индивидуально или накапливаться для следующего тика.

Состояние ДОЛЖНО очищаться после завершения, включая нештатное, и при начале следующего тика. Тик без учтённых решений НЕ ДОЛЖЕН создавать сводку «0 пар». Прерванный тик НЕ ДОЛЖЕН создавать сводку, сообщающую штатное отсутствие сигналов.

#### Scenario: Восемь решений по четырём инструментам
- **WHEN** штатный тик содержит только восемь разрешённых чистых HOLD по двум привязкам на каждый из инструментов `NG-9.26`, `GAZP`, `Si`, `RTS`, в этом порядке, и публикация сводки происходит в 10:15 по Москве
- **THEN** консоль выводит ровно `● 10:15 ➜ ⏳ Нет сигналов (8 пар: NG-9.26, GAZP, Si, RTS)`

#### Scenario: Разные таймфреймы и профили
- **WHEN** по GAZP обработаны три привязки одной стратегии: 5m/raw, 15m/raw и 15m/basic_levels, все дали чистый HOLD
- **THEN** сводка содержит `3 пары: GAZP`, имя инструмента указано один раз

#### Scenario: Сигнал появляется после HOLD
- **WHEN** в тике несколько чистых HOLD предшествуют разрешённому решению BUY
- **THEN** BUY печатается сразу в прежнем формате; отдельные HOLD и сводка не печатаются

#### Scenario: Торговое событие появляется до HOLD
- **WHEN** внутри тика напечатано уведомление об исполнении, после которого поступают чистые HOLD
- **THEN** в конце тика сводка не выводится

#### Scenario: Отклонение фильтром сохраняется
- **WHEN** внутри тика получены чистые HOLD и разрешённое решение с `filtered_out=True`
- **THEN** отклонение печатается сразу и подавляет сводку

#### Scenario: Сердцебиение или ошибка подавляют сводку
- **WHEN** внутри тика с чистыми HOLD напечатано разрешённое сердцебиение либо уведомление о сбое
- **THEN** сводка этого тика не выводится

#### Scenario: Непечатные события не подавляют сводку
- **WHEN** в штатном тике есть чистые HOLD и события, исключённые из фильтра или не имеющие текстового представления
- **THEN** непечатные события не мешают выводу одной сводки

#### Scenario: Решения отключены в настройках
- **WHEN** `decision` исключён из пользовательского списка уведомлений консоли
- **THEN** чистые HOLD и сводка не выводятся, служебные границы сами не создают сообщений

#### Scenario: Независимые последовательные тики
- **WHEN** первый тик содержит напечатанный сигнал, а второй штатный тик содержит только чистые HOLD
- **THEN** первый тик не получает сводку, а второй получает свою сводку с собственными количеством и именами

#### Scenario: Уведомление между тиками
- **WHEN** между завершением первого и началом второго тика напечатано торговое уведомление, а второй штатный тик содержит только чистые HOLD
- **THEN** уведомление печатается самостоятельно и не подавляет сводку второго тика

#### Scenario: Пустой или прерванный тик
- **WHEN** тик не содержит учтённых HOLD либо завершён нештатно после частичного анализа
- **THEN** сводка не выводится, состояние не переносится в следующий тик

#### Scenario: HOLD вне границ тика
- **WHEN** чистый HOLD доставлен при отсутствии активного тика
- **THEN** индивидуальная строка не печатается, решение не включается в будущую сводку

### Requirement: Московское время публикации сводки
Нормативный уровень: MUST.
Время `HH:MM` в консольной сводке ДОЛЖНО соответствовать фактическому моменту её публикации в московском часовом поясе UTC+3. Оно НЕ ДОЛЖНО зависеть от локального пояса компьютера, времени бара, настроенного смещения для обычных решений или источника исторического рыночного времени. Обычные уведомления ДОЛЖНЫ сохранять свои правила отображения времени бара.

#### Scenario: Публикация позже закрытия бара
- **WHEN** учтённые решения относятся к бару 07:00 UTC, а сводка публикуется в 07:15 UTC
- **THEN** время сводки равно `10:15`, а не `10:00`

#### Scenario: Компьютер в другом часовом поясе
- **WHEN** одинаковый момент публикации 07:15 UTC отображается на компьютерах в UTC, Москве и другом локальном поясе
- **THEN** время сводки во всех случаях равно `10:15`

#### Scenario: Исторический прогон
- **WHEN** обрабатывается исторический бар, а фактическая публикация сводки происходит в 07:15 UTC текущего дня
- **THEN** сводка содержит `10:15` текущего московского времени, не время исторического бара

#### Scenario: Переход через полночь
- **WHEN** сводка публикуется в 22:15 UTC
- **THEN** время сводки равно `01:15` по Москве
