## ADDED Requirements

### Requirement: Стоп-заявка у брокера
Нормативный уровень: MUST. У каждой открытой сделки контура на брокере ДОЛЖНА стоять у брокера ровно одна стоп-заявка `STOP_LOSS` со сроком «до отмены» (`GOOD_TILL_CANCEL`):

- на сторону выхода сделки;
- на объём, равный учтённому остатку минус объём заявок выхода контура в работе;
- по цене подтверждённого стопа, округлённой до шага цены в безопасную сторону: стоп продажи вверх, стоп покупки вниз.

Сумма стоп-заявок инструмента НЕ ДОЛЖНА превышать позицию того же знака на счёте по последнему снимку сверки. Если на счёте меньше, чем по журналу, объём срезается сначала у самых поздних сделок, иначе стоп перезакрыл бы позицию.

Исключения: у сделки ещё нет исполненного входа, объём выходит нулевым или контур сам выходит по стопу (стоп-задание). Заявки целей из объёма стопа НЕ ДОЛЖНЫ вычитаться: стоп стоит на весь остаток рядом с ними.

Стоп-заявки ДОЛЖНЫ храниться в таблице `broker_stop_orders` в `broker.sqlite3` контура. Строка пишется до `PostStopOrder` и хранит:

- ключ — UUID из `<trade>:bs:<номер постановки>`;
- сделку, инструмент, сторону, лоты, стоп-цену в пунктах;
- состояние (`sending`, `active`, `cancelling`, `cancelled`, `executed`, `expired`, `rejected`, `unknown`);
- номер стоп-заявки и номер порождённой заявки;
- причину и время.

Номер счёта в таблице НЕ ДОЛЖЕН храниться.

Хранитель стопа ДОЛЖЕН приводить стоп-заявку к желаемой на каждом обслуживании, после разбора очереди исполнений и перед сверкой. Если у живой стоп-заявки другой объём или цена, контур ДОЛЖЕН сначала снять её и дождаться подтверждения (`cancelled`, `executed` или `expired`) и только потом поставить новую. Две живые стоп-заявки одной сделки НЕ ДОЛЖНЫ существовать ни в какой момент. Пока у сделки есть непроведённые исполнения, хранитель НЕ ДОЛЖЕН менять её стоп-заявку.

Если за `stop_place_secs` секунд с появления желаемого стопа у сделки нет активной стоп-заявки:

- отказ брокера из-за закрытых торгов — постановка повторяется не чаще раза в минуту без выхода;
- иначе — выход из сделки циклом выхода требования «Выходы лимитными заявками» с причиной `stop-not-placed` и тревога `stop_failed` в канал.

`AddToTrade` у сделки, чья стоп-заявка не совпадает с желаемой, ДОЛЖЕН получать `REJECT stop-pending`.

#### Scenario: Стоп после входа
- **GIVEN** вход 10 лотов NG исполнен по 2.943, подтверждённый стоп 2.901
- **WHEN** очередь исполнений разобрана
- **THEN** у брокера одна стоп-заявка `STOP_LOSS` на продажу 10 лотов по 2.901 со сроком «до отмены», в карточке строка «стоп у брокера 2.901 · 10 лотов»

#### Scenario: Цель взята
- **GIVEN** у длинной сделки NG 2 лота стоп-заявка на 2 лота и заявка цели 1 на 1 лот
- **WHEN** цель 1 исполнилась
- **THEN** стоп-заявка на 2 лота снята, после подтверждения поставлена стоп-заявка на 1 лот, двух живых стоп-заявок не было ни в один момент, в карточке «стоп пересоздан на остаток 1»

#### Scenario: Перенос стопа
- **GIVEN** у сделки активная стоп-заявка по 2.901
- **WHEN** `TradeManager` выпустил `MoveStop` на 2.916
- **THEN** у брокера одна стоп-заявка по 2.916 на тот же объём

#### Scenario: Добор до пересоздания стопа
- **GIVEN** добор сделки исполнен, стоп-заявка на новый объём ещё не активна
- **WHEN** стратегия даёт следующий добор
- **THEN** он получает `REJECT stop-pending`

#### Scenario: Стоп не принят
- **GIVEN** вход исполнен, брокер отклоняет стоп-заявку по причине, не связанной с закрытыми торгами
- **WHEN** проходит `stop_place_secs`
- **THEN** сделка закрывается циклом выхода с причиной `stop-not-placed`, в канал уходит тревога «стоп не принят»

#### Scenario: Торги закрыты
- **GIVEN** брокер отклоняет стоп-заявку, потому что торги закрыты
- **WHEN** проходит `stop_place_secs`
- **THEN** выхода нет, постановка повторяется раз в минуту, условие стопа проверяет контур по минутам

### Requirement: Срабатывание стоп-заявки у брокера
Нормативный уровень: MUST. Отчёт стрима заявки, которой нет в журнале заявок (нет нашего ключа, номер незнаком), НЕ ДОЛЖЕН отбрасываться. Контур ДОЛЖЕН искать его стоп-заявку через `GetStopOrders` по `exchange_order_id`. Опрос `GetStopOrders` ДОЛЖЕН выполняться:

- при незнакомом отчёте;
- на каждой сверке, если у контура есть живые стоп-заявки.

Опросов — не больше 30 в минуту.

Если стоп-заявка найдена, контур ДОЛЖЕН:

- отметить её `executed`;
- завести строку журнала заявок вида `broker_stop` с номером порождённой заявки;
- провести каждую сделку биржи защитным исполнением с `command_id` вида `<trade>:pv:stop:<номер стоп-заявки>:<номер сделки биржи>`;
- снять заявки целей сделки;
- отправить в канал строку «стоп сработал у брокера».

Остаток, не исполненный рыночной заявкой за `exit_requote_secs`, ДОЛЖЕН добирать цикл выхода от последней цены. Незнакомый отчёт, не сопоставленный за 60 секунд, ДОЛЖЕН считаться чужим: его показывает сверщик. Сопоставление только по инструменту, стороне и объёму НЕ ДОЛЖНО делаться.

Стоп-заявка, которую брокер показал снятой или истёкшей без отмены контура, ДОЛЖНА закрываться в журнале. Хранитель стопа ставит новую.

Пока у сделки есть активная стоп-заявка на весь желаемый объём по желаемой цене, контур НЕ ДОЛЖЕН проверять условие стопа по минутам. Без неё (стоп ставится, пересоздаётся, отклонён из-за закрытых торгов) условие ДОЛЖЕН проверять контур по требованию «Выходы лимитными заявками».

#### Scenario: Стоп сработал у брокера
- **GIVEN** у длинной сделки NG 2 лота активная стоп-заявка по 2.812 и заявка цели на 1 лот
- **WHEN** песочница исполнила стоп-заявку, стрим принёс отчёт порождённой рыночной заявки без нашего ключа
- **THEN** стоп-заявка найдена по `exchange_order_id`, продажа 2 лотов проведена защитным выходом, заявка цели снята, сделка закрыта, в канале «стоп сработал у брокера», лишних заявок нет

#### Scenario: Минута через стоп при живом стопе у брокера
- **GIVEN** у сделки активная стоп-заявка на весь остаток
- **WHEN** закрытая минута ядра прошла через стоп, а отчёт брокера ещё не пришёл
- **THEN** контур своего выхода не начинает, выход приходит от стоп-заявки брокера

#### Scenario: Окно пересоздания
- **GIVEN** прежняя стоп-заявка снята, новая ещё не активна
- **WHEN** закрытая минута ядра прошла через стоп
- **THEN** контур выходит стоп-лимитом по циклу выхода, новая стоп-заявка не ставится

#### Scenario: Чужая заявка
- **GIVEN** стрим принёс отчёт заявки, которой нет ни в журнале, ни среди `exchange_order_id` наших стоп-заявок
- **WHEN** прошло 60 секунд
- **THEN** отчёт считается чужим, расхождение показывает сверка

### Requirement: Стоп-заявки после простоя
Нормативный уровень: MUST. До первого тика, после разбора журнала заявок и до сверки, контур ДОЛЖЕН:

1. сверить незавершённые строки стоп-заявок с `GetStopOrders` за период с самой ранней;
2. стоп-заявку, исполненную за простой, провести по требованию «Срабатывание стоп-заявки у брокера». Сделки берутся из `GetOrderState` по номеру биржи порождённой заявки, а без сделок — средняя по сумме заявки;
3. разобрать строки `unknown`;
4. привести стоп-заявки к желаемым: срезать объём, поставить недостающие, снять стоп-заявки сделок без остатка.

Потерянный ответ `PostStopOrder` (тайм-аут, обрыв, процесс упал в `sending`) ДОЛЖЕН переводить строку в `unknown`. Разбор:

- поиск среди активных стоп-заявок того же инструмента, стороны, объёма и стоп-цены, созданных не раньше чем за 5 секунд до отправки и не привязанных к другой строке;
- найдена одна — строка `active` с её номером;
- не найдена, а желаемое совпадает — `PostStopOrder` тем же ключом;
- не найдена, желаемого нет — `cancelled`;
- найдено больше одной — строка остаётся `unknown`, расхождение показывает сверка.

Потерянный ответ `CancelStopOrder` ДОЛЖЕН разбираться по статусу из `GetStopOrders`.

Штатный выход процесса, `kill` и `no_entries` ДОЛЖНЫ оставлять стоп-заявки у брокера.

#### Scenario: Стоп сработал, пока контур убит
- **GIVEN** у сделки NG активная стоп-заявка, процесс контура убит, за простой песочница исполнила стоп-заявку
- **WHEN** контур запущен снова
- **THEN** до первого тика сделка закрыта по сделкам порождённой заявки, заявки целей сняты, стоп-заявок нет, сверка `ok`

#### Scenario: Потерянный ответ на постановку
- **GIVEN** `PostStopOrder` ушёл, процесс упал до ответа, стоп-заявка у брокера активна
- **WHEN** контур запущен снова
- **THEN** стоп-заявка найдена по инструменту, стороне, объёму и цене, у брокера одна стоп-заявка

#### Scenario: Ручная продажа части за простой
- **GIVEN** у длинной сделки 10 лотов стоп-заявка на 10, процесс убит, командой песочницы продано 4 лота
- **WHEN** контур запущен снова
- **THEN** сверка показывает расхождение позиции тревогой, позиция по журналу не меняется, стоп-заявка срезана до 6 лотов — позиции на счёте

#### Scenario: Сделка открыта до обновления
- **GIVEN** сделка открыта сборкой без стоп-заявок, стопа у брокера нет
- **WHEN** контур поднялся на новой сборке
- **THEN** до первого тика у брокера поставлена стоп-заявка на остаток с причиной «рестарт»

## MODIFIED Requirements

### Requirement: Заявки контура на брокере
Нормативный уровень: MUST. `TInvestBroker` ДОЛЖЕН реализовывать `BrokerPort` и те методы, которые у `JournalBroker` вызывают `TradeManager` и сборка контура. Ответ `submit` ДОЛЖЕН быть немедленным:

- `ACK` — брокер принял заявку или её судьба неизвестна (причина `broker-unknown`);
- `REJECT` — отказ брокера (причина `broker:<код>`) или отказ проверки до отправки.

Исполнения, подтверждённые снятия и поздние отказы ДОЛЖНЫ приходить позже через `drain_addressed_events` и проводиться тем же `consume`.

| Команда | Действие у брокера |
|---|---|
| `OpenTrade`, `AddToTrade` (лимит) | `PostOrder` лимитная заявка по `limit_price`, ключ из `command_id`; `AddToTrade` при несовпадающей стоп-заявке сделки — `REJECT stop-pending` |
| `CloseTrade`, `ReduceTrade` без цели | цикл выхода по требованию «Выходы лимитными заявками» |
| `CancelEntry` | `CancelOrder` по каждому неисполненному входу сделки |
| `MoveStop` | новый стоп в представлении контура; стоп-заявку у брокера пересоздаёт хранитель стопа по требованию «Стоп-заявка у брокера» |

Ключ идемпотентности (`order_id` запроса) ДОЛЖЕН быть UUID, однозначно выведенным из `command_id`: тот же `command_id` даёт тот же ключ и после рестарта. Повторный `submit` команды, по ключу которой уже есть строка в журнале заявок, НЕ ДОЛЖЕН ставить новую заявку и ДОЛЖЕН отвечать её текущим состоянием.

`CANCEL` команды входа ДОЛЖЕН приходить только после подтверждения снятия брокером. Сделка биржи, пришедшая до подтверждения, ДОЛЖНА проводиться обычным исполнением. После частичного исполнения снимается остаток, а сделка продолжается с исполненным объёмом. Отказ брокера на вход ДОЛЖЕН отменять план без повторов.

#### Scenario: Вход принят и исполнен
- **GIVEN** привязка NG дала сигнал на покупку 2 лотов по 2,845
- **WHEN** команда входа доставлена брокеру, а затем пришли две сделки биржи по 1 лоту
- **THEN** `submit` отвечает `ACK` с номером заявки; журнал получает `PARTIAL` 1 лот и `FILL` 1 лот с ценами в пунктах; позиция 2 лота

#### Scenario: Повторная доставка той же команды
- **GIVEN** заявка входа отправлена, процесс упал до отметки outbox `SENT`
- **WHEN** после подъёма outbox снова отдаёт команду в `submit`
- **THEN** второй `PostOrder` не выполняется, у брокера одна заявка с этим ключом

#### Scenario: TTL входа
- **GIVEN** лимитный вход не исполнился за TTL таймфрейма
- **WHEN** `TradeManager` выпускает `CancelEntry` с `entry-timeout`
- **THEN** у брокера выполняется `CancelOrder`, `CANCEL` входа проводится только после подтверждения снятия

#### Scenario: Исполнение раньше отмены
- **GIVEN** по входу отправлен `CancelOrder`
- **WHEN** до подтверждения снятия пришла сделка биржи на 1 из 2 лотов, затем подтверждение
- **THEN** позиция 1 лот, вход завершён отменой остатка, сделка сопровождается дальше

#### Scenario: Отказ брокера на вход
- **WHEN** брокер отклонил лимитную заявку входа
- **THEN** план отменён, резерв освобождён, повторной заявки нет, в канале отказ с кодом брокера

### Requirement: Сверщик счёта
Нормативный уровень: MUST. Сверщик ДОЛЖЕН сравнивать по каждому инструменту, у которого есть что-то на счёте или в журнале контура:

- позицию в лотах (`GetPortfolio`) с суммой знаковых остатков открытых сделок журнала;
- активные заявки (`GetOrders`) с незавершёнными строками журнала заявок, у которых есть номер брокера;
- активные стоп-заявки (`GetStopOrders`) с активными строками `broker_stop_orders`.

Сверка ДОЛЖНА выполняться при старте, после разбора журнала заявок и до первого тика, и затем не реже раза в `reconcile_every_min` минут. Перед каждой сверкой ДОЛЖНА разбираться очередь исполнений. Перед каждой сверкой ДОЛЖЕН работать хранитель стопа: недостающую или несовпадающую по объёму свою стоп-заявку он исправляет сам, без тревоги. Инструмент, у которого есть заявка или стоп-заявка в `sending`, `unknown` или `cancelling`, непроведённое исполнение или незнакомый отчёт стрима моложе 60 секунд, в этой сверке НЕ ДОЛЖЕН сравниваться и ДОЛЖЕН попадать в отчёт отметкой `in_flight`. Чужая стоп-заявка на счёте — расхождение `stop_order`.

Инструмент с любым расхождением ДОЛЖЕН попадать в заморозку, инструмент без расхождений — выходить из неё. Заморозка ДОЛЖНА запрещать по инструменту новые входы и доборы с причиной «инструмент заморожен сверкой». Выходы, сокращения и стоп заморозка НЕ ДОЛЖНА трогать. При `orders = false` журнал пуст, поэтому любая позиция, заявка или стоп-заявка на счёте — расхождение «на счёте есть, в журнале нет».

Уведомления сверщика:

- при переходе из «совпадает» в «расхождение» и при каждом изменении состава расхождений — событие `broker_account` с `kind = reconcile_alarm`;
- при переходе в «совпадает» — `reconcile_cleared`;
- одинаковые подряд отчёты НЕ ДОЛЖНЫ уведомлять повторно.

Каждый отчёт ДОЛЖЕН сохраняться в `broker.sqlite3` (последние 100) и содержать:

- время;
- итог `ok` или `mismatch`;
- расхождения: инструмент коротким именем, что (`position`, `order`, `stop_order`), на счёте, по журналу;
- инструменты `in_flight`;
- замороженные инструменты.

Если счёт не прочитан (сеть, брокер), сверка ДОЛЖНА пропускаться с предупреждением в лог, `account_link = lost`, заморозки — оставаться как были. Третий подряд пропуск ДОЛЖЕН давать `reconcile_alarm` с причиной «счёт недоступен».

#### Scenario: Ручная покупка
- **GIVEN** песочница работает, расхождений нет
- **WHEN** командой `python -m src.sandbox buy NG 1` куплен 1 лот, и наступила сверка
- **THEN** отчёт `mismatch`: NG, `position`, на счёте на 1 больше, чем по журналу; NG заморожен; в канал «Песочница» уходит одна тревога

#### Scenario: Сделка контура совпадает
- **GIVEN** контур купил 2 лота NG, исполнение проведено
- **WHEN** наступила сверка
- **THEN** отчёт `ok`, NG не заморожен

#### Scenario: Исполнение ещё в пути
- **GIVEN** сделка биржи по входу NG пришла в стрим, но ещё не проведена
- **WHEN** наступила сверка
- **THEN** очередь разбирается до сравнения, а если исполнение всё равно не проведено, NG в отчёте `in_flight` и не заморожен

#### Scenario: Журнал не принял исполнение
- **GIVEN** исполнение брокера больше открытой позиции сделки, reducer его не принял
- **WHEN** наступила сверка
- **THEN** исполнение помечено «отвергнуто», инструмента нет в `in_flight`, отчёт `mismatch` с тревогой и заморозкой, позиция сделки у контура — по журналу

#### Scenario: Заморозка не мешает выходу
- **GIVEN** NG заморожен, у контура открытая позиция NG
- **WHEN** стратегия даёт сигнал на добор, а затем срабатывает стоп
- **THEN** добор отклонён с причиной «инструмент заморожен сверкой», выход по стопу выполнен

#### Scenario: Расхождение устранено
- **GIVEN** NG заморожен из-за ручной позиции
- **WHEN** позиция закрыта командой `sell NG 1`, и наступила сверка
- **THEN** отчёт `ok`, заморозки нет, в канал уходит `reconcile_cleared`

#### Scenario: Тревога не повторяется
- **GIVEN** расхождение по NG уже отправлено тревогой
- **WHEN** следующие сверки дают тот же состав расхождений
- **THEN** новых сообщений в канал нет, отчёты сохраняются

#### Scenario: После рестарта тревога на месте
- **GIVEN** NG заморожен, робот перезапущен
- **WHEN** контур песочницы поднялся и выполнил стартовую сверку
- **THEN** NG снова заморожен, `GET /api/v1/sandbox/reconcile` показывает расхождение, в канал уходит `started` и тревога

#### Scenario: Своя стоп-заявка
- **GIVEN** у контура открытая сделка NG и активная стоп-заявка на её остаток
- **WHEN** наступила сверка
- **THEN** отчёт `ok`, NG не заморожен

#### Scenario: Чужая стоп-заявка
- **GIVEN** командой песочницы или в обход контура поставлена стоп-заявка по NG
- **WHEN** наступила сверка
- **THEN** отчёт `mismatch`: NG, `stop_order`, на счёте на 1 больше, чем по журналу; NG заморожен, в канал уходит тревога

### Requirement: Выходы лимитными заявками
Нормативный уровень: MUST. Выходы контура ДОЛЖНЫ идти лимитными заявками. Рыночная заявка допускается только как аварийный выход после исчерпания перевыставлений.

**Цели.** После каждого исполнения входа или добора контур ДОЛЖЕН держать у брокера лимитную заявку на каждую неисполненную цель:

- по цене цели после пересчёта от средней;
- на объём цели по прежнему распределению;
- в сторону выхода.

Изменился объём или цена цели — заявка перевыставляется: сначала снимается старая, потом ставится новая. Каждая сделка биржи по заявке цели ДОЛЖНА проводиться отдельным защитным исполнением с `command_id` вида `<trade>:pv:tp:<target>:<номер сделки биржи>`. Если брокер снял заявку цели в конце дня без исполнения, контур ДОЛЖЕН поставить её заново после открытия торгов.

**Стоп.** Основной стоп сделки — стоп-заявка у брокера по требованию «Стоп-заявка у брокера». Пока у сделки нет активной стоп-заявки на весь желаемый объём по желаемой цене, контур ДОЛЖЕН проверять условие стопа по закрытым минутным свечам ядра по тем же правилам, что симулятор эмуляции: стоп важнее целей, гэп через стоп на открытии. При срабатывании контур ДОЛЖЕН:

1. снять заявки целей сделки;
2. поставить лимитную заявку на остаток, не занятый живыми заявками целей, по цене стопа с запасом `exit_offset_steps` шагов в сторону исполнения: продажа — стоп минус запас, покупка — стоп плюс запас;
3. если заявка не исполнилась целиком за `exit_requote_secs` секунд, снять её и поставить новую на весь текущий остаток по последней цене с тем же запасом;
4. после `exit_requote_attempts` перевыставлений выйти рыночной заявкой на остаток и отправить тревогу.

Каждая сделка биржи по заявке стопа проводится отдельным защитным исполнением с `command_id` вида `<trade>:pv:stop:<момент срабатывания>:<номер сделки биржи>`.

Условие стопа сделки ДОЛЖНО проверяться только по минутам, закрывшимся после её первого исполнения входа; минута входа проверяется. После рестарта граница прогона пропущенных минут ДОЛЖНА учитывать исполнения, проведённые при старте до первого тика. Стоп, пробитый за время простоя после входа, ДОЛЖЕН закрывать позицию.

**Сигнальные выходы и закрытие.** `CloseTrade` и `ReduceTrade` без цели ДОЛЖНЫ идти тем же циклом, от последней цены: лимит с запасом, перевыставление, аварийный рынок. Это сигнал стратегии, сессионная защита, экспирация, `close_all`.

- Перед `CloseTrade` снимаются заявки целей и стоп-заявка сделки; первая заявка выхода ставится только после подтверждения снятия стоп-заявки. Если стоп-заявка при снятии оказалась исполненной, выход ждёт её по правилу стопа.
- `ReduceTrade` на q лотов сначала уменьшает стоп-заявку сделки на q; заявка выхода ставится после снятия прежней стоп-заявки.
- `ReduceTrade` берёт сначала лоты, не занятые заявками целей, затем уменьшает заявку самой дальней цели.

**Объём.** Сумма лотов живых выходных заявок сделки НЕ ДОЛЖНА превышать её остаток. Стоп-заявка у брокера входит в эту сумму вместе с заявками выхода контура; заявки целей стоят рядом со стоп-заявкой на весь остаток и в сумму со стопом не входят. Кроме заявок целей, у сделки ДОЛЖНО быть не больше одной выходной заявки в работе. Сигнальный выход, пришедший при незавершённом стопе, ждёт его. Если после завершения остаток ноль, сигнальный выход получает `REJECT trade-not-open`.

Остаток для новой заявки выхода или цели ДОЛЖЕН считаться по исполнениям, уже учтённым сделкой. Пока у сделки есть непроведённые исполнения или заявка её выхода ждёт своих сделок, новая заявка выхода или цели НЕ ДОЛЖНА ставиться.

**Отказ брокера на выход** или заявку цели ДОЛЖЕН повторяться не чаще раза в минуту новым ключом, пока заявка не пройдёт или остаток не станет нулевым. О первом отказе в канал уходит тревога.

#### Scenario: Цель исполнена лимитом
- **GIVEN** вход 2 лота NG исполнен по 2,846, цель 1 — 1 лот по 2,911
- **WHEN** биржа исполнила заявку цели
- **THEN** в журнале выход 1 лота по 2,911, остаток 1 лот, заявок по рынку не было

#### Scenario: Стоп-лимит исполнен
- **GIVEN** длинная позиция NG 2 лота, стоп 2,812, активной стоп-заявки у брокера нет, `exit_offset_steps = 5`, шаг 0,001, у брокера заявки двух целей по 1 лоту
- **WHEN** закрытая минута ядра имеет low 2,810
- **THEN** заявки целей сняты, у брокера лимитная продажа 2 лотов по 2,807, после исполнения сделка закрыта, в канале «стоп исполнен»

#### Scenario: Рестарт после исполнения входа
- **GIVEN** вход Si исполнился в 16:40, процесс контура тут же убит, у прошлой сделки Si последнее исполнение в 08:32, минута 14:04 имеет low ниже стопа новой сделки
- **WHEN** контур запущен снова
- **THEN** стоп новой сделки по минутам до 16:40 не проверяется, сделка остаётся открытой

#### Scenario: Стоп пробит за время простоя
- **GIVEN** открытая сделка NG, процесс контура не работал 10 минут, в одну из них low ниже стопа
- **WHEN** контур запущен снова
- **THEN** стоп срабатывает по этой минуте, позиция закрывается стоп-лимитом

#### Scenario: Закрытие при стопе у брокера
- **GIVEN** у сделки NG 2 лота активная стоп-заявка на 2 лота
- **WHEN** приходит `CloseTrade` по сигналу стратегии
- **THEN** стоп-заявка снимается, и только после подтверждения ставится заявка выхода на 2 лота; в карточке «стоп снят перед выходом»

#### Scenario: Выход исполнился сразу
- **GIVEN** короткая позиция Si 10 лотов, сигнал частичного выхода на 1 лот
- **WHEN** заявка на 1 лот исполнилась в стриме до разбора очереди исполнений, и наступило следующее обслуживание
- **THEN** второй заявки на этот выход нет; после разбора очереди остаток 9 лотов

#### Scenario: Стоп-лимит не исполнился
- **GIVEN** стоп-лимит NG стоит по 2,807, рынок ушёл на 2,790
- **WHEN** проходит `exit_requote_secs` без исполнения
- **THEN** заявка снята, новая стоит от последней цены с запасом; после `exit_requote_attempts` перевыставлений остаток продаётся по рынку, в канал уходит тревога

#### Scenario: Цель снята в конце дня
- **GIVEN** у открытой сделки заявка цели не исполнилась до конца торгового дня, брокер её снял
- **WHEN** открылись торги следующего дня
- **THEN** контур ставит заявку цели заново, сделка не считается изменённой

#### Scenario: Выход вне торгов
- **GIVEN** стоп сработал на последней минуте сессии
- **WHEN** брокер отклонил заявку, потому что торги закрыты
- **THEN** в канал уходит тревога, выход повторяется не чаще раза в минуту и проходит после открытия торгов

### Requirement: Остановка контура на брокере с открытыми сделками
Нормативный уровень: MUST. Команды остановки контура «Песочница» ДОЛЖНЫ действовать на его сделки по правилам эмуляции:

- `no_entries` — неисполненные входы снимаются у брокера, открытые сделки сопровождаются до выхода;
- `close_all` — дополнительно каждая открытая сделка закрывается по требованию «Выходы лимитными заявками».

Процесс ДОЛЖЕН завершаться сам со `state = stopped`, когда у контура не осталось открытых сделок, незавершённых заявок и живых стоп-заявок. При `no_entries` стоп-заявки открытых сделок остаются у брокера до их выхода.

Снятие привязки ДОЛЖНО действовать так же, но только на сделки этой привязки:

- `no_entries` — привязка не открывает новых входов, сопровождает свои сделки и уходит из состава после последней;
- `close_all` — то же, плюс её сделки закрываются.

Последняя привязка инструмента уводит и инструмент.

Штатный выход по Ctrl+C, концу стандартного ввода или пульсу «остановлено» ДОЛЖЕН оставлять заявки входа и целей, стоп-заявки у брокера и позиции на счёте как есть. Сообщение `stopped` ДОЛЖНО называть число открытых позиций и число стоп-заявок у брокера (`broker_stops`).

#### Scenario: Остановка с закрытием
- **GIVEN** у контура открытая позиция NG и неисполненный вход SBER
- **WHEN** приходит `PUT /api/v1/sandbox/target` с `mode = close_all`
- **THEN** вход SBER снят у брокера, заявки целей и стоп-заявка NG сняты, позиция NG закрыта лимитной заявкой, контур завершается со `stopped`, на счёте позиций, заявок и стоп-заявок нет

#### Scenario: Снятие одной привязки
- **GIVEN** у привязок `future-ng-macd` и `future-ng-flat` по открытой сделке
- **WHEN** `future-ng-macd` снимается с `no_entries`
- **THEN** её сделка доводится до выхода, сделка `future-ng-flat` не затронута, после выхода `future-ng-macd` уходит из состава

#### Scenario: Остановка процесса со стопом у брокера
- **GIVEN** у контура открытая сделка NG с активной стоп-заявкой
- **WHEN** процесс завершается по Ctrl+C
- **THEN** стоп-заявка остаётся у брокера, `stopped` называет 1 открытую позицию и 1 стоп-заявку

### Requirement: Уведомления контура на брокере
Нормативный уровень: MUST. Контур ДОЛЖЕН публиковать события в свою шину и доставлять их Telegram-каналом с ботом из `telegram_bot_env` в канал из `telegram_channel_env`, с сохранением и досылкой по правилам `telegram-delivery-recovery` в своём `telegram_delivery.sqlite3`.

Канал контура ДОЛЖЕН получать:

- `broker_account`;
- `broker_order`;
- `order_accepted`;
- девять lifecycle-типов торговли своего контура: `signal`, `trade_opened`, `position_added`, `stop_hit`, `target_hit`, `stop_moved`, `trade_closed`, `trade_cancelled`, `order_rejected`.

Списки `[notifier.telegram] events` эмуляции на канал контура НЕ ДОЛЖНЫ влиять. Карточки сделок контура ДОЛЖНЫ строиться по правилам `telegram-trade-cards` с меткой контура «ПЕСОЧНИЦА» в заголовке. Строки `order_accepted` и `broker_order` ДОЛЖНЫ дописываться в корневую карточку своей сделки.

| `kind` `broker_account` | Содержание |
|---|---|
| `started` | вид контура, счёт …XXXX, рубли, `liquid_portfolio`, число позиций, заявок и стоп-заявок, число привязок, поколение, режим заявок |
| `reconcile_alarm` | расхождения по инструментам коротким именем, заморозка, подсказка «выровнять счёт и дождаться сверки» |
| `reconcile_cleared` | что расхождений нет, какие инструменты разморожены |
| `stopped` | причина выхода, число открытых позиций и стоп-заявок у брокера |

| `kind` `broker_order` | Содержание |
|---|---|
| `sent` | заявка отправлена: вход, добор, цель, стоп или выход, лимитная цена, лоты |
| `unknown` | ответ брокера потерян, заявка будет найдена по ключу |
| `found` | заявка найдена по ключу, её состояние |
| `resent` | по ключу пусто, заявка отправлена снова тем же ключом |
| `cancelling` | отмена отправлена брокеру |
| `requoted` | выход перевыставлен: номер попытки, новая цена |
| `exit_rejected` | брокер отклонил выход или заявку цели, причина, когда повтор (тревога) |
| `emergency_market` | выход по рынку после исчерпания перевыставлений (тревога) |
| `stop_placed` | стоп у брокера: цена, лоты, номер стоп-заявки; при пересоздании — новый объём и причина (цель, добор, сокращение, перенос, рестарт) |
| `stop_triggered` | стоп сработал у брокера, номер порождённой заявки |
| `stop_failed` | стоп не принят, причина, выход (тревога) |
| `stop_removed` | стоп снят перед выходом контура |

Постановка стоп-заявки без смены объёма и цены (повтор тем же ключом, рестарт) НЕ ДОЛЖНА публиковаться. Инструменты в сообщениях ДОЛЖНЫ называться коротким именем, номер заявки и стоп-заявки брокера — последними четырьмя символами. Номер счёта и ключ целиком в сообщениях НЕ ДОЛЖНЫ появляться.

#### Scenario: Старт в канале
- **GIVEN** на счёте песочницы 1 000 000 ₽, позиций нет, в составе две привязки
- **WHEN** контур прошёл допуск
- **THEN** в канал «Песочница» приходит сообщение о старте со счётом …09c3, 1 000 000 ₽, двумя привязками и режимом заявок

#### Scenario: Карточка сделки в песочнице
- **GIVEN** привязка NG дала сигнал, вход исполнен, затем сработала цель
- **WHEN** события доставлены
- **THEN** в канале «Песочница» одна корневая карточка «ПЕСОЧНИЦА NG», в ней строки «отправлено в Т-Инвест, лимит 2,845», «принято брокером, заявка …7f3a», «исполнено 2 из 2 по 2,846», затем выход по цели; в канале эмуляции этих строк нет
