## Context

- **После С3** (`add-tinvest-orders`, архив 06.11) `TInvestBroker` ведёт представление сделки (`TradeView`: подтверждённый стоп, остаток, исполненные цели) и журнал заявок `broker_orders` / `broker_executions` в `broker.sqlite3`.
  - Цели — дневные лимитные заявки (`kind = target`), их ставит `_ensure_targets` после открытия торгов.
  - Стоп — условие в `track_bar` по закрытой минуте ядра. При срабатывании `_start_stop` заводит `ExitJob(kind="stop")`, и цикл `_pump` ставит лимит с запасом, перевыставляет его, в конце идёт рынком.
  - `MoveStop` только меняет `confirmed_stop`.
  - Сверщик считает любую стоп-заявку на счёте расхождением.
- **Разведка С1 (29.10).**
  - `STOP_LOSS` на 1 лот NG со сроком `GOOD_TILL_CANCEL` принят и виден в `GetStopOrders`.
  - Он сработал: песочница выставила рыночную заявку, её номер — `StopOrder.exchange_order_id`. Стрим принёс «новая» с временным номером, затем «исполнена». `GetStopOrders` показал `EXECUTED`.
- **SDK 1.49.3.**
  - `PostStopOrderRequest.order_id` — ключ идемпотентности. `PostStopOrderResponse` возвращает `stop_order_id` и `order_request_id`.
  - У `StopOrder` поля с нашим ключом нет. `GetStopOrders` фильтрует по статусу и периоду.
  - `GetOrderState` принимает `ORDER_ID_TYPE_EXCHANGE`.
  - Стрима у стоп-заявок нет.
- **Решения владельца 08.11:**
  - стоп у брокера — `STOP_LOSS`;
  - цели — дневные лимиты, как на С3;
  - перед выходом контура стоп уменьшается на объём выхода, при полном выходе снимается.

## Goals / Non-Goals

**Goals:**

- У каждой открытой сделки контура на брокере — ровно одна стоп-заявка на весь остаток по цене подтверждённого стопа, если только контур в эту минуту сам не выходит.
- Позиция защищена, когда процесс контура не работает.
- После простоя журнал совпадает со счётом до первого тика, стоп-заявки — с остатками.
- Ни одной лишней заявки и ни одного перезакрытия по вине контура.

**Non-Goals:**

- Цели стоп-заявками (тейк-профит GTC) — отвергнуто 08.11.
- `STOP_LIMIT` и трейлинг-стоп брокера.
- Автоподъём упавшего контура ядром, свечи песочницы без эмуляции — отдельные задачи.
- Предохранители (С6), настоящие комиссии и отчёт против эмуляции (С7).
- Показ стопа у брокера в UI — в репозитории UI, после API 2.8.0.

## Decisions

### 1. Журнал стоп-заявок — отдельная таблица `broker_stop_orders`

Стоп-заявка у брокера — не заявка: у неё свой номер (`stop_order_id`), нет нашего ключа в ответах чтения, нет сделок. Сделки есть у рыночной заявки, которую она порождает. Поэтому стоп-заявки живут в своей таблице `broker.sqlite3`, а не строками `broker_orders`.

| Поле | Смысл |
|---|---|
| `key` | ключ идемпотентности, `order_key("<trade>:bs:<n>")`, `n` — номер постановки у сделки |
| `trade_id`, `instrument_uid`, `side` | сделка, инструмент, сторона выхода |
| `lots`, `stop_price` | объём и стоп-цена в пунктах |
| `state` | `sending`, `active`, `cancelling`, `cancelled`, `executed`, `expired`, `rejected`, `unknown` |
| `stop_order_id`, `exchange_order_id` | номер стоп-заявки и номер порождённой заявки |
| `reason` | вход, добор, цель, сокращение, перенос, рестарт, сверка |
| `created_at`, `sent_at`, `updated_at` | время |

Строка пишется до `PostStopOrder`, как у заявок С3. Порождённая рыночная заявка заводится строкой `broker_orders` вида `broker_stop` с номером брокера = `exchange_order_id` и `job` = задание выхода по стопу. Её сделки идут через существующие `broker_executions` и `consume`.

Существующий вид `stop` в `broker_orders` остаётся за запасным стоп-лимитом контура (решение 4).

### 2. Хранитель стопа

На каждом обслуживании (`service`) и после разбора очереди исполнений хранитель считает **желаемый стоп** каждой сделки:

- цена — `confirmed_stop`, округлённая до шага в безопасную сторону: стоп продажи вверх, стоп покупки вниз;
- объём — учтённый остаток минус объём заявок выхода контура в работе. Цели не вычитаются (решение 3).
- При нулевом объёме, при активном стоп-задании контура и у сделки без исполненного входа желаемого стопа нет.
- Сумма стопов инструмента не больше позиции того же знака на счёте по последнему снимку сверки. Если на счёте меньше (ручная продажа, потерянное исполнение), объём срезается сначала у самых поздних сделок. Иначе стоп перезакрыл бы позицию. Расхождение при этом показывает сверка.

Затем сравнивает желаемое с живой строкой журнала:

| Живая строка | Желаемое | Действие |
|---|---|---|
| нет | есть | `PostStopOrder` (`STOP_LOSS`, `GOOD_TILL_CANCEL`, сторона выхода, лоты, стоп-цена в пунктах) |
| `active`, совпадает | — | ничего |
| `active`, другой объём или цена | есть или нет | `CancelStopOrder` → `cancelling` |
| `sending`, `unknown`, `cancelling` | — | ждать разбора (решение 6) |

Новая стоп-заявка ставится только после того, как прежняя стала `cancelled`, `executed` или `expired`: короткое окно без стопа лучше двух стопов на один объём. Пока у сделки есть непроведённые исполнения, хранитель её не трогает, как заявки выхода С3.

**Срок постановки.** Отсчёт `stop_place_secs` начинается, когда у сделки появился желаемый стоп, а живой активной стоп-заявки нет. Если за это время стоп не стал `active`:

- брокер отклонил стоп из-за закрытых торгов (класс отказа «торги закрыты» по коду брокера, проверяется разведкой) — без выхода, повтор раз в минуту, запасное условие у контура (решение 4);
- иначе (другой отказ, нет ответа и поиск не нашёл) — `ExitJob(kind="stop")` на весь остаток с причиной `stop-not-placed` по циклу С3 и тревога `stop_failed`.

**Добор.** `AddToTrade` при несовпадающем стопе сделки получает `REJECT stop-pending`: следующий добор не допускается, пока стоп не пересоздан после предыдущего.

### 3. «Стоп раньше выхода контура»

- **`CloseTrade`** (сигнал, сессионная защита, экспирация, `close_all`, снятие привязки): задание выхода заводится сразу, но первая заявка выхода ставится, только когда стоп-заявка сделки снята (`cancelled`) или её не было. Если снятие не удалось, потому что стоп уже исполнен, выход ждёт стоп-задание, как сигнальный выход ждёт стоп на С3.
- **`ReduceTrade` на q лотов:** желаемый стоп уменьшается на q. Заявка выхода ставится после снятия прежней стоп-заявки, новая стоп-заявка на остаток минус q ставится параллельно. В любой момент стоп плюс выход ≤ остатку.
- **Заявки целей** в этот инвариант не входят: стоп стоит на весь остаток рядом с ними, это цена отсутствия OCO. После исполнения цели хранитель первым делом пересоздаёт стоп на новый остаток.

Ожидание снятия стопа добавляет к выходу одно обслуживание (обычно меньше секунды). Аварийный рынок цикла С3 остаётся последней ступенью.

### 4. Условие стопа у контура — запасное

`track_bar` проверяет условие стопа сделки, только если у неё нет стоп-заявки `active` на весь желаемый объём по желаемой цене. Например, в окне «снять → поставить», пока стоп не принят, при отказе из-за закрытых торгов. Сработало условие — прежний `_start_stop`, и хранитель желаемого стопа больше не держит. Если в этот момент стоп-заявка в `sending` или `unknown`, контур снимает её после разбора.

Почему не держать условие всегда: тогда при живом стопе у брокера вышли бы двое, и позиция ушла бы за ноль.

### 5. Срабатывание у брокера

1. Стрим приносит отчёт заявки, которой нет в журнале: нет нашего ключа и номер незнаком. Сейчас такой отчёт отбрасывается (`ingest` → `False`). Теперь он кладётся в «незнакомые» с временем.
2. На ближайшем обслуживании брокер опрашивает `GetStopOrders` (`STATUS_ALL`, с момента самой ранней живой стоп-заявки) и ищет нашу стоп-заявку с `exchange_order_id`, равным номеру отчёта.
3. Найдена:
   - строка стоп-заявки → `executed`;
   - заводится строка `broker_orders` вида `broker_stop` с номером брокера;
   - отчёт применяется к ней, сделки проводятся защитными исполнениями с `command_id` вида `<trade>:pv:stop:<stop_order_id>:<номер сделки биржи>`;
   - заявки целей сделки снимаются;
   - заводится `ExitJob(kind="stop", base=None)` с этой заявкой как текущей. Если рыночная заявка исполнилась не целиком за `exit_requote_secs`, остаток добирает цикл С3 от последней цены.
4. Не найдена — повтор опроса на следующих обслуживаниях. Через 60 с отчёт остаётся чужим: его покажет сверщик.

Кроме того, `GetStopOrders` опрашивается на каждой сверке, если у контура есть живые стоп-заявки. Так ловятся сработавшие стопы, отчёт которых потерялся при обрыве стрима, а также стопы, снятые или истёкшие у брокера (`cancelled` или `expired` без нашей отмены — хранитель поставит новую). Общий предел — 30 опросов в минуту, лишние откладываются.

Если `GetStopOrders` не показал `exchange_order_id`, а отчёт стрима один и совпадает по инструменту, стороне и объёму с нашей активной стоп-заявкой, сопоставления не делается. Ошибиться на чужой заявке опаснее, чем подождать.

### 6. «Неизвестно», рестарт и простой

**Потерянный ответ `PostStopOrder`** (тайм-аут, обрыв, падение процесса в `sending`) → `unknown`. Разбор:

1. `GetStopOrders` `ACTIVE`: ищем стоп-заявку того же инструмента, стороны, объёма и стоп-цены, созданную не раньше `sent_at − 5 с` и не привязанную к другой строке. Найдена — `active` с её номером.
2. Не найдена, сделка открыта и желаемое совпадает — `PostStopOrder` тем же ключом. Ответ «дубликат» ведёт к шагу 1 через 2 с. Что именно отвечает брокер на повтор ключа, проверяет П20.
3. Не найдена, желаемого нет — `cancelled` (не дошла).

**Потерянный ответ `CancelStopOrder`** → остаётся `cancelling`. Опрос `GetStopOrders` решает: `CANCELED` → `cancelled`, `EXECUTED` → срабатывание (решение 5), `ACTIVE` → повтор отмены.

**Подъём после простоя** идёт до первого тика, после разбора журнала заявок С3 и до сверки:

1. Все незавершённые строки стоп-заявок сверяются с `GetStopOrders` `ALL` с момента самой ранней.
2. `EXECUTED` за простой → `GetOrderState(ORDER_ID_TYPE_EXCHANGE, exchange_order_id)`. Сделки проводятся как в решении 5. Если сделок в ответе нет, работает правило средней по сумме заявки С3 (`fill_average`).
3. Строки `unknown` разбираются по правилу выше.
4. Хранитель приводит стопы к желаемому: срезает объём, ставит недостающие, снимает стоп-заявки закрытых сделок.

Только потом сверка и первый тик. Перезакрытие, которое уже случилось за простой, хранитель не исправляет: его показывает сверка тревогой и заморозкой.

### 7. Сверщик

`JournalView.stop_orders` — короткие имена инструментов по строкам стоп-заявок в `active` с номером. Инструмент со стоп-заявкой в `sending`, `unknown` или `cancelling` или с незнакомым отчётом стрима моложе 60 с попадает в `in_flight`. Перед сверкой работает хранитель. Сравнение остаётся по числу стоп-заявок на инструмент.

Недостающий или лишний по объёму стоп хранитель исправляет сам, и до тревоги дело не доходит. Чужая стоп-заявка или лишняя стоп-заявка без строки журнала — расхождение `stop_order` с тревогой и заморозкой входов.

### 8. Остановка

- `close_all`, снятие привязки с `close_all` — `CloseTrade` по решению 3: стоп и цели снимаются, потом выход. После закрытия у контура не остаётся ни заявок, ни стоп-заявок, процесс завершается `stopped`.
- `no_entries`, снятие привязки с `no_entries` — позиции доживают со стопом у брокера, хранитель продолжает работу.
- Ctrl+C, конец stdin, пульс «остановлено», `kill` — стоп-заявки остаются у брокера. `stopped` получает поле `broker_stops` — число активных стоп-заявок.
- Процесс завершается сам при `close_all`, только когда нет и живых строк стоп-заявок.

### 9. Уведомления

Новые `kind` события `broker_order`:

| `kind` | Строка карточки |
|---|---|
| `stop_placed` | «стоп у брокера 2.812 · 10 лотов, стоп-заявка …ab12»; при пересоздании — «стоп пересоздан на остаток 5 (цель 1)» |
| `stop_triggered` | «стоп сработал у брокера, заявка …91c» |
| `stop_failed` | «стоп не принят: <причина> — выход» (тревога) |
| `stop_removed` | «стоп снят перед выходом» |

`stop_placed` без смены объёма и цены (повтор после рестарта, постановка тем же ключом) не публикуется. Поле `order` у событий стоп-заявки — `broker_stop`, `broker_order` — последние 4 символа `stop_order_id`. `broker_account` `stopped` получает `broker_stops`.

### 10. API позиций

`…/positions` контура на брокере получает у позиции `broker_stop`:

- `null` у эмуляции и у сделки без стопа;
- иначе `{ "state": "active" | "placing" | "contour", "price", "lots", "order" }`:
  - `placing` — стоп-заявка ставится или пересоздаётся;
  - `contour` — у брокера стопа нет, условие держит контур (решение 4);
  - `order` — последние 4 символа номера.

Читается из `broker.sqlite3` контура только на чтение, рядом с журналом сделок. OpenAPI 2.8.0.

### 11. Разведка `probe-stops`

Отдельное действие, чтобы не менять 15 проверок `probe`: `python -m src.sandbox probe-stops [инструмент] [--stop-ticks N] [--stop-wait МИН]`. На 2 лотах:

| № | Проверка |
|---|---|
| П19 | `STOP_LOSS` на 2 лота с ключом принят. В подробности — `stop_price` из `GetStopOrders`: рубли или пункты |
| П20 | повтор `PostStopOrder` тем же ключом не создал вторую стоп-заявку. В подробности — ответ брокера |
| П21 | «снять → поставить»: `CancelStopOrder` → `CANCELED`, новая стоп-заявка на 1 лот с другим ключом активна |
| П22 | срабатывание: стрим принёс отчёт порождённой заявки. В подробности — есть ли `order_request_id`, совпадает ли номер с `exchange_order_id`, через сколько секунд после касания, сколько сделок |
| П23 | `GetOrderState` с `ORDER_ID_TYPE_EXCHANGE` находит порождённую заявку, есть ли сделки или только сумма |
| П24 | `CancelStopOrder` исполненной стоп-заявки: код ответа |

Уборка — как П15. Ответы записываются в `data/sandbox/probe-…/` и дополняют фейковый шлюз.

## Risks / Trade-offs

- **[Рынок на гэпе и тонком стакане]** → `STOP_LOSS` исполняется по рынку, в тонкую сессию (выходные, вечер) проскальзывание может быть заметным. Принято владельцем: гарантия выхода без контура важнее. Расхождение с эмуляцией покажет отчёт С7.
- **[Перезакрытие при цели без контура]** → Цель исполнилась, пока контур не работает, а стоп остался на прежний объём. Если цена затем дойдёт до стопа, позиция уйдёт за ноль. Окно — время простоя. Сверка после подъёма покажет тревогой, хранитель срежет стоп, если перезакрытия ещё не было.
- **[Окно без стопа]** → При каждом пересоздании (снять → поставить) стопа у брокера нет доли секунды–секунды. На это время работает запасное условие контура по минуте.
- **[Поиск по атрибутам]** → Если две сделки одного инструмента ставят одинаковые стопы одновременно, поиск по атрибутам может перепутать номера. Встречные сделки по семейству запрещены, одинаковые стоп и объём у двух сделок одного инструмента в одну секунду маловероятны. При сомнении (две подходящие) строка остаётся `unknown`, и сверщик покажет расхождение.
- **[Квоты]** → Каждое изменение остатка или стопа — снятие и постановка. `MoveStop` на 15m-таймфрейме — не чаще раза в бар на сделку. Опрос `GetStopOrders` ограничен 30 в минуту. Песочница — 200/мин, счёт — 50/мин: запас есть.
- **[Песочница исполняет стоп не как биржа]** → На Р2 первые срабатывания проверяются под присмотром.

## Migration Plan

1. Таблица `broker_stop_orders` создаётся миграцией схемы `broker.sqlite3` при старте.
2. Сделки, открытые до обновления, получают стоп у брокера при подъёме (решение 6, шаг 4) с причиной «рестарт».
3. Откат на сборку С3: стоп-заявки остаются у брокера, старая сверка покажет их расхождением. Перед откатом — `close_all` или снятие стоп-заявок командой песочницы.
