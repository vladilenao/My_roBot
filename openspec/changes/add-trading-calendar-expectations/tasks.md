Все пункты — будущая реализация после отдельного запроса apply. Эта ревизия изменяет только артефакты данного change: код, рабочие конфиги, тесты и БД не меняются, запросы к брокеру не выполняются.

Пометка «⟵ ingestion N.M» означает, что пункт выполняется после соответствующей задачи `reliable-live-candle-ingestion`. Пункты без пометки можно выполнять параллельно с ingestion. Тесты — только в `tests/unit/` (подкаталог `tests/unit/market_calendar/`) и в существующих разрешённых каталогах.

## 4. Интеграция с live-ingestion

- [ ] 4.1 Детектор ожидаемой последовательности и trailing gap использует перечисление ожидаемых баров и календарное evidence с версией (⟵ ingestion 5.1, 5.6). Неизвестная фаза → `unresolved` по правилам ingestion. Второй детектор не создаётся.
- [ ] 4.2 Кандидат publication deadline из `DueBar` с `candle_publication_timeout_by_tf` и базовым `candle_publication_timeout_secs` (⟵ ingestion 5.5, 7.7). Проверить, что deadline первого отсутствующего не скользит и не дублируется.
- [ ] 4.3 Заменить `_expected_live_open` и выбор пар `refresh_live` на `last_due`. Пара BREAK/CLOSED с разрешённым `last_due` не попадает в свежую очередь до `next_event`. При UNKNOWN опрос не сокращается (⟵ ingestion 2.1).
- [ ] 4.4 Recent reconciliation в BREAK/CLOSED — только до разрешения последних баров завершённой сессии, затем пауза до `next_event`. Recovery старых `unresolved` продолжается своим бюджетом (⟵ ingestion 5.7).
- [ ] 4.5 Календарное пробуждение планировщика по ближайшему `next_event` вместе с data-ready notify. Без торгового тика при отсутствии бара, без изменения UTC-сеток и виртуальных часов (⟵ ingestion 6.1).
- [ ] 4.6 Здоровье stream в BREAK/CLOSED: отсутствие свечей не объявляет соединение потерянным, подписки не снимаются, критерий здоровья — ping/ответы (⟵ ingestion 3.3).
- [ ] 4.7 Свечи вне биржевого расписания: приём в любой фазе, `received` сильнее `scheduled_closed`, диагностика «вне расписания».
