### Чем владеют изменения в работе

`reliable-live-candle-ingestion` владеет:
- единым owner;
- состояниями отсутствующих интервалов;
- нескользящим deadline;
- recovery-раундами;
- readiness/barrier;
- data-ready пробуждением;
- `market_data.candle_publication_timeout_secs`.

Этот change даёт им календарный вход и не создаёт параллельных механизмов.

`remove-mandatory-preflight-gap-scan` убирает предварительный подсчёт разрывов. Этот change не возвращает сплошное чтение и не вычисляет «ожидаемое число свечей» диапазона.

## Goals / Non-Goals

**Goals:**
- Один расчёт ожиданий с одинаковым смыслом в live, в истории и во всех потребителях.
- Фаза из четырёх значений, при которой неизвестность никогда не равна закрытию.
- Расписание по режиму торгов и торговой дате с версией и источником.
- Боевой режим без зависимости от эмулятора; исторический режим на снимке.
- Сокращение свечных запросов при закрытом рынке без остановки сопровождения.

**Non-Goals:** перечислены в `proposal.md`. Дополнительно:
- не менять поведение `JournalBroker` при клиринге;
- не трактовать `trading_status` как доказательство фазы;
- не синтезировать OHLCV.

## Decisions

### 1. Чистое ядро и тонкие источники

```text
ScheduleSource (сеть)          MarketCalendar (кэш + обслуживание)        expect() (чистая функция)
  BrokerScheduleSource  ─┐        ├─ calendar(uid, at) -> TradingCalendar ─┐
  EmulatorScheduleSource ┴──────► ├─ service(now)  [фоновая полоса]       ├──► CandleExpectation
                                  └─ expectation(uid, tf, now) ────────────┘
```

- Пакет `src/market_calendar/` (имя предварительное) содержит модель, правила ТФ и `expect()`: без сети, SQLite и часов. Новый модуль оправдан отсутствующим общим контрактом. Сейчас математика продублирована в `live_analysis.py` и `cache.py` и частично в `reconciliation.py`, а нужна ещё истории и preflight.
- `MarketCalendar.expectation()` только читает уже загруженный календарь. Если календаря нет, она возвращает `UNKNOWN` и регистрирует фоновую задачу загрузки. Это соответствует правилу ingestion «live-read APIs тика только читают».
- `service(now)` выполняет не более одного RPC за вызов. Вызов идёт через общий `RequestBudget` в вспомогательной полосе ingestion-owner, как сейчас `MarketDataReconciler.service_calendar`.
- `SessionCalendar` и загрузка расписания уходят из `MarketDataReconciler`: реконсилятор получает `MarketCalendar` как зависимость.

### 2. Модель

```python
class MarketPhase(Enum): TRADING, BREAK, CLOSED, UNKNOWN

@dataclass(frozen=True)
class SessionWindow:          # интервал одной торговой даты, UTC-naive
    start: datetime; end: datetime
    kind: Literal["continuous", "auction", "clearing", "intersession", "unknown"]
    raw_type: str             # исходная строка брокера или имя поля TradingDay

@dataclass(frozen=True)
class ScheduleRef:
    source: Literal["tbank", "emulator"]
    exchange: str             # код режима торгов (instrument.exchange)
    days: tuple[tuple[date, str], ...]   # (торговая дата, версия дня), использованные расчётом
    digest: str               # короткий хеш days, для отображения
    observed_at: datetime     # самое старое наблюдение среди days
    snapshot_generation: int | None
    stale: bool               # последняя попытка обновления не удалась, но применимость не истекла

@dataclass(frozen=True)
class DueBar:
    open: datetime; close: datetime
    publication_deadline: datetime       # close + publication_timeout(tf)
    rule_confirmed: bool

@dataclass(frozen=True)
class NextEvent:
    kind: Literal["bar_close", "session_open", "session_close", "break_start", "break_end",
                  "publication_deadline", "schedule_refresh"]
    at: datetime

@dataclass(frozen=True)
class CandleExpectation:
    instrument_uid: str; timeframe: str; now: datetime
    phase: MarketPhase; break_kind: str | None
    last_due: DueBar | None
    next_event: NextEvent | None
    schedule: ScheduleRef | None
    reason: str               # обязателен для UNKNOWN, неподтверждённого правила, конфликта
```

Внутренние сравнения ведутся в UTC-naive после конвертации aware-значения в UTC. Это согласуется с ingestion, требование «Раздельные временные факты».

### 3. Классификация интервалов и фазы

Окна строятся из `intervals[]`, если список непуст. Иначе — из именованных полей `TradingDay`:
- `premarket_*`;
- `opening_auction_*`;
- `start_time…end_time` за вычетом `clearing_*`;
- `closing_auction_*`;
- `evening_opening_auction_start_time`;
- `evening_*`.

Отображение типа в `kind` — версионируемая таблица. Её содержимое фиксируется контрактными тестами по реальным ответам (задача 1.2):

| `kind` | Примеры исходных типов (Проверить) | Фаза | Свечи |
|---|---|---|---|
| continuous | основная, вечерняя, утренняя сессия, сессия выходного дня, премаркет с непрерывными сделками | TRADING | ожидаются |
| auction | аукционы открытия/закрытия, дискретный аукцион | BREAK(auction) | не ожидаются; полученная принимается |
| clearing | `clearing_start…clearing_end`, клиринговые типы | BREAK(clearing) | не ожидаются |
| intersession | промежуток между окнами одной торговой даты | BREAK(intersession) | не ожидаются |
| unknown | любой нераспознанный тип | TRADING + `reason=unknown_interval_type` | ожидаются (консервативно) |

Фаза на момент `t`:
- **UNKNOWN** — расписание не применимо к дате `t` (раздел 6).
- **TRADING** — `t` внутри окна `continuous` или `unknown`.
- **BREAK** — `t` внутри окна `auction`/`clearing` или между окнами одной торговой даты, если до конца даты есть ещё окно.
- **CLOSED** — день не торговый (`is_trading_day=false`) или после последнего окна даты и до первого окна следующей применимой торговой даты.

Если следующая дата не покрыта применимым расписанием, фаза остаётся CLOSED. Поле `next_event` при этом пустое, а `reason` сообщает, что следующее открытие неизвестно. Закрытие текущей даты подтверждено, открытие — нет.

Решения:
- Правило «будни — торги, выходные — закрыто» не применяется нигде. Праздник в будний день, рабочая суббота и сессии выходного дня следуют только из расписания даты.
- Аукцион отнесён к BREAK по смыслу непрерывных свечей: в фазе сбора заявок минутные свечи не формируются. Возможная свеча в момент пересечения принимается как полученная. Без этого правила строгий 1m-барьер ingestion блокировал бы UID каждое утро.
- Неизвестный тип даёт TRADING, а не BREAK. Это может дать ложное `delayed`, но не скроет реальный сбой.

### 4. Правило свечи по ТФ

`CandleRule(source_profile, tf)` определяет границы бара и признак «бар должен существовать».

| ТФ | Границы | Бар ожидается, если | Статус правила |
|---|---|---|---|
| 1m, 5m, 15m, 30m, 1h | UTC-сетка `CandleScheduler` | `[open, close)` пересекается с окном `continuous`/`unknown` | подтверждено действующим кодом и ingestion 1.3 |
| 4h | UTC-сетка от 00:00 UTC (D4) | то же | подтверждено документом, нужен контрактный тест |
| 1d | календарный день брокера (не биржевой день фьючерса) | в днях есть окно `continuous` | **Проверить**: граница суток брокера (UTC или МСК) |
| 1w | календарная неделя брокера | в неделе есть торговое окно | **Проверить**: начало недели |
| 1M | календарный месяц | в месяце есть торговое окно | **Проверить** |

`last_due` — самый поздний ожидаемый бар с `close ≤ now`. Бар, содержащий конец сессии, закрывается по своей сетке, а не по концу сессии. Так уже работает `_expected_live_open`, и ingestion требует «не переносить на время последней сделки».

Если правило ТФ не подтверждено (`rule_confirmed=false`):
- расчёт `last_due` по сетке выполняется для ожидания и диагностики;
- `scheduled_closed` для этого ТФ не выдаётся, `idle` не публикуется;
- поведение совпадает с нынешним сеточным, плюс `reason`.

### 5. Publication deadline и следующее событие

`publication_deadline = last_due.close + publication_timeout(tf)`. Таймаут берётся из `market_data.candle_publication_timeout_by_tf[tf]`, а при отсутствии — из `market_data.candle_publication_timeout_secs` (ключ ingestion).

Календарь даёт только **кандидата**. Фиксация deadline первого отсутствующего интервала, его нескользящий характер и переходы `waiting → delayed → recovery` принадлежат ingestion: требование «Нескользящее ожидание отсутствующей свечи». `LivePairState.observe` уже фиксирует deadline при первом наблюдении.

`next_event` = ближайшее из:
- закрытие следующего ожидаемого бара этого ТФ;
- смена фазы (открытие, закрытие, начало и конец перерыва);
- publication deadline, если `last_due` ещё не получен;
- момент, когда истекает применимость расписания или требуется обновление.

При UNKNOWN `next_event` пуст, и пробуждение идёт по обычной cadence.

### 6. Применимость, версия и обновление

- **Ключ дня:** `(source, exchange, trading_date)`. `trading_date` — дата торгового дня в поясе площадки. Интерпретацию `TradingDay.date` фиксирует контрактный тест (задача 1.3), без сдвига на сутки.
- **Версия дня:** `sha256` канонического JSON исходного `TradingDay` (все поля, включая `intervals`, в UTC ISO). Новая версия добавляется, только если хеш изменился. Иначе обновляется `last_confirmed_at`. Старые версии хранятся для аудита и происхождения `interval_coverage`.
- **Применимость к дате D (live):**
  - используется последняя версия с `observed_at ≥ start(D) − schedule_max_age_secs`;
  - возраст отсчитывается от торговой даты, а не от `now`, поэтому прошедшая дата с вовремя наблюдённым расписанием остаётся доказательством навсегда;
  - будущая дата требует свежего наблюдения;
  - дата без применимой версии даёт UNKNOWN.
- **Флаг `stale`:** последняя попытка обновления не удалась и прошло больше `schedule_refresh_interval_secs`. Применимость при этом сохраняется; это только диагностика.
- **Обновление (live):**
  - на каждый `exchange`, а не на UID: окно `[today−1, today+schedule_horizon_days]`;
  - внеочередной запрос, когда `now` или запрошенная дата выходят за покрытие;
  - повторы при ошибке — через общий бюджет и retry-after;
  - ошибка не стирает уже применимые версии.
- **Связь UID → `exchange`:** хранится в БД с `observed_at` и обновляется редко. Смена `exchange` у UID — новая привязка, прежние даты используют прежнюю.
- **Сервис запросов:** TradingSchedules и `get_instrument_by` относятся к сервису инструментов (200/мин по D6). Бюджет учитывает это отдельно от свечного сервиса котировок.

### 7. Хранение в `market-data.sqlite3`

```sql
CREATE TABLE trading_schedule_days (
  source TEXT NOT NULL, exchange TEXT NOT NULL, trading_date TEXT NOT NULL,
  version TEXT NOT NULL, raw_json TEXT NOT NULL, is_trading_day INTEGER NOT NULL,
  observed_at TEXT NOT NULL, last_confirmed_at TEXT NOT NULL,
  schedule_change_id INTEGER NOT NULL UNIQUE,
  PRIMARY KEY (source, exchange, trading_date, version));
CREATE TABLE instrument_schedule_bindings (
  source TEXT NOT NULL, instrument_uid TEXT NOT NULL, exchange TEXT NOT NULL,
  observed_at TEXT NOT NULL, schedule_change_id INTEGER NOT NULL UNIQUE,
  PRIMARY KEY (source, instrument_uid, observed_at));
```

- `schedule_change_id` — монотонный счётчик ленты экспорта расписания (раздел 9), отдельный от `changes.change_id`.
- Миграция выполняется увеличением `SCHEMA_VERSION` **после** миграций ingestion, с сохранением существующих строк.
- Legacy-строки `source_observations(kind='trading_schedule')` не переносятся, потому что тип интервалов в них потерян. Они остаются для аудита, а первое обновление получает полный ответ.
- `trading_status` по-прежнему пишется в `source_observations` как объяснение.
- Ранее записанные `scheduled_closed` сохраняют своё evidence. Переоценка `unresolved` по новому применимому календарю идёт существующим `recheck`.

### 8. Источники по режимам

| | Боевой | Исторический |
|---|---|---|
| Источник | `instruments.trading_schedules(exchange, from, to)` | `GET /api/v1/trading-schedules?instrument_id=&from=&to=[&snapshot_generation=]` эмулятора |
| UID → exchange | `get_instrument_by(uid).instrument.exchange`, кэш в БД | привязка, экспортированная роботом и отданная эмулятором в ответе |
| Хранение | `market-data.sqlite3` | память прогона; версии использованных дней пишутся в отчёт |
| Применимость | правило max-age от торговой даты | наличие дня в снимке; max-age не применяется |
| Отказ | UNKNOWN, повтор по бюджету | UNKNOWN на прогон, прогон продолжается по прежним правилам |
| Брокер | да | никогда |

Предлагаемый контракт эмулятора (реализуется в его репозитории отдельным изменением):

```http
GET /api/v1/trading-schedules?instrument_id=<uid>&from=YYYY-MM-DD&to=YYYY-MM-DD&snapshot_generation=<n>
200 {"instrument_id": "...", "snapshot_generation": 42,
     "days": [{"trading_date": "2026-10-09", "exchange": "MOEX_EVENING_WEEKEND",
               "version": "<sha256>", "observed_at": "...", "provenance": "my_robot_export",
               "day": { ...исходный TradingDay... }}],
     "missing_dates": ["2026-10-10"]}
404 NOT_FOUND (маршрута нет)   → робот: «источник расписания не поддерживается», UNKNOWN
409/400 snapshot mismatch      → робот: ошибка подготовки прогона, как для свечей
```

- Версия дня вычисляется одинаково на обеих сторонах, по исходному `day`. Тогда версия, наблюдённая в live, совпадает с версией в истории.
- Если ответ вернул другой `snapshot_generation`, это ошибка контракта, а не UNKNOWN.
- Эмулятор может пополнять расписание и собственной загрузкой у брокера (`provenance=tbank_download`). Доступность прошлых дат в TradingSchedules — **Проверить**. Для робота важны только `provenance` и версия.

### 9. Экспорт эмулятору отдельной лентой

`/changes` и его виды не меняются: текущий импорт эмулятора отвергает неизвестный `kind`, а фильтрация остановила бы его курсор. Добавляется ресурс:

```http
GET /api/v1/market-data/trading-schedules?after_id=&limit=
  → {"producer_id", "next_after_id", "has_more",
     "items": [{"schedule_change_id", "kind": "schedule_day"|"instrument_binding", ...}]}
PUT /api/v1/market-data/consumers/{consumer_id}/trading-schedules-checkpoint
```

- Семантика повторов, ошибок курсора, `producer_id`, хранения неподтверждённого и авторизации совпадает с действующими требованиями `market-data-export`.
- Изменение OpenAPI аддитивное: появляется новый путь, существующие не меняются.
- `sync` эмулятора для выдачи `snapshot_generation` должен догнать обе ленты (задача на стороне эмулятора). Робот вправе считать расписание закреплённым только при эхо того же `snapshot_generation` в ответе расписания.

### 10. Интеграция с `reliable-live-candle-ingestion`

| Механизм ingestion (владелец) | Календарный вход этого change | Порядок |
|---|---|---|
| expected sequence и trailing gap (5.1) | перечисление ожидаемых баров `CandleRule × окна continuous`; `scheduled_closed` для BREAK/CLOSED только при подтверждённом правиле и применимом расписании | после 5.1 |
| `scheduled_closed`/unknown schedule/последний интервал сессии (5.6) | evidence `applicable_trading_schedule:<exchange>:<date>:<version>`; UNKNOWN → `unresolved` по их правилам | вместе с 5.6 |
| нескользящий deadline (5.5) | кандидат `DueBar.publication_deadline` с per-TF таймаутом | после 7.7 |
| recent reconciliation (5.7) | при CLOSED/BREAK сверка только до разрешения последних баров завершённой сессии, затем пауза до `next_event` | после 5.7 |
| calendar/deadline wakeup (6.1) | `next_event` пар; ближайшее событие будит планировщик | вместе с 6.1 |
| stream health: тихая сессия ≠ outage | фаза BREAK/CLOSED; здоровье по-прежнему по ping/ответам | после 3.3 |
| readiness/barrier (6.3) | не меняется; календарь лишь сообщает, какие интервалы ожидаемы | — |
| polling dispatch (`refresh_live`) | `last_due` вместо `_expected_live_open`; пара с разрешённым `last_due` в BREAK/CLOSED не ставится в свежую очередь | после 2.1 |
| `LivePairState`/`market_data_status` | `phase`, `next_event`, `schedule`; `session` сохраняет совместимые значения | после 8.3 |

Чего этот change не делает в зоне ingestion:
- не вводит второй deadline;
- не снимает `integrity_hold`/`parked` по календарю;
- не трактует `delayed` как no-trade;
- не меняет roster подписок;
- не отписывает stream при закрытии.

### 11. Потребители вне ingestion

- **Стартовая загрузка и прогрев:** `prepare_live_history(max_close=last_due.close)`. Если `last_due` уже получен, пара актуальна независимо от календарного возраста; это случай понедельника 03:00. Глубина прогрева по-прежнему по числу закрытых баров.
- **`LiveAnalysis.publish_status` и `current()`:** используют `CandleExpectation`. Дублирующий `expected_close` и подсчёт `missed` по `calendar.is_open` заменяются перечислением ожидаемых баров из `expect()`.
- **`entry_market`:** цена актуальна, если 1m `last_due` получен и не истёк его publication deadline при TRADING. Иначе — прежние причины недопуска. При BREAK/CLOSED вход не допускается («торговая сессия закрыта/перерыв»); при UNKNOWN действует прежнее сеточное правило с причиной. Окно актуальности торгового решения не расширяется.
- **История:**
  - `has_fresh_closed_bar` берёт `expected` из `last_due` календаря снимка; при UNKNOWN — прежняя сетка;
  - предпроверка правой границы при применимом расписании снимка сначала проверяет, что все ожидаемые бары между L и B вне торговых окон (доказанный плановый перерыв);
  - при UNKNOWN действует существующее правило L/R с формулировкой «наблюдаемый ограниченный разрыв»;
  - сплошного чтения диапазона нет.
- **`JournalBroker`:** продолжает использовать `CLEARING_TIMES`. Если окна клиринга из расписания на текущую дату расходятся с конфигом, пишется диагностическое предупреждение. Поведение не меняется.

### 12. Закрытый рынок и сокращение запросов

Пара в BREAK/CLOSED с полученным или разрешённым `last_due` и без незакрытых ожидаемых интервалов:
- не получает свежих GetCandles до `next_event`;
- recent reconciliation для неё приостанавливается;
- recovery старых `unresolved` продолжается своим бюджетом.

Подписки stream сохраняются, без churn control-запросов.

Продолжают работать по своей cadence:
- торговый поток;
- `JournalBroker.run_clearing_if_due`;
- TTL заявок и экспирации;
- обработка подтверждений;
- сердцебиение;
- `market_data_status`;
- обновление расписания.

При UNKNOWN свечной опрос не сокращается.

### 13. Профиль источника и свечи вне расписания

Профиль `UNSPECIFIED` может включать дилерские свечи выходного дня (**Проверить**). Поэтому:
- полученная завершённая свеча принимается в любой фазе — календарь никогда не отвергает данные;
- состояние `received` сильнее `scheduled_closed`;
- отсутствие свечи в CLOSED нормально;
- свеча, пришедшая в CLOSED, не меняет фазу, но отражается в диагностике как «свеча вне биржевого расписания».

Если проба подтвердит отдельное расписание дилерских торгов, применимым расписанием профиля станет объединение. Это технический вопрос, а не решение владельца.

## Risks / Trade-offs

- **[Словарь типов интервалов неизвестен]** → консервативное `unknown`=TRADING, контрактные тесты по сохранённым сырым ответам, диагностика нового типа. Минус — возможные ложные `delayed` до обновления таблицы.
- **[Сдвиг торговой даты из-за пояса]** → отдельный контрактный тест до включения `scheduled_closed`. Ошибка проявилась бы как ложный перерыв, поэтому тест блокирующий.
- **[Брокер меняет расписание задним числом или внутри дня]** → версии дня, обновление по cadence, применимость по max-age от торговой даты. Прошлые `scheduled_closed` сохраняют evidence версии.
- **[Аукцион как BREAK скрывает реальную сделку]** → полученная свеча всегда принимается. Ингест не объявляет её отсутствующей.
- **[Правила 1d/1w/1M не подтверждены]** → `rule_confirmed=false` не даёт календарного доказательства; поведение как сейчас.
- **[Исторический эмулятор без ресурса]** → UNKNOWN и прежние правила; прогон не ломается.
- **[Нагрузка RPC]** → запросы по `exchange`, а не по UID; cadence в часах. 23 UID обычно соответствуют нескольким режимам торгов — оценка, **Проверить** на реальном roster.
- **[Пересечение с ingestion в одних файлах]** → интеграционные задачи упорядочены после групп ingestion; чистое ядро и хранилище — отдельно.

## Migration Plan

Это план будущей реализации, а не действие данной ревизии.

1. Контрактные тесты SDK и сохранённые сырые ответы (без сети). Словарь типов, интерпретация `date`, правила 1d/1w/1M. Read-only проба брокера — только с отдельного разрешения владельца.
2. Чистое ядро и `expect()` с тестами на управляемых часах.
3. Таблицы расписания и миграция `SCHEMA_VERSION` после ingestion. `BrokerScheduleSource` и `MarketCalendar` в фоновой полосе. Порт провайдеров.
4. Перевод потребителей по таблице раздела 10, после соответствующих групп ingestion. Затем потребители раздела 11.
5. Лента экспорта расписания. Клиент эмулятора с толерантностью к 404. Изменение эмулятора в его репозитории.
6. Rollback: старые конфиги принимаются. Отключение календарного вывода `scheduled_closed` (`market_data.calendar_evidence=false`) возвращает поведение «расписание неизвестно» без удаления данных.

## Open Questions

Блокирующих решений владельца нет. Технические проверки (не выбор владельца):

1. Интерпретация `TradingDay.date` и граница торговой даты для каждого используемого `exchange`.
2. Полный словарь `TradingInterval.type` и соответствие именованным полям при пустом `intervals`.
3. Доступность прошлых дат в TradingSchedules (для эмулятора и переоценки старых `unresolved`).
4. Границы 1d/1w/1M у брокера для профиля `UNSPECIFIED`.
5. Включает ли `UNSPECIFIED` дилерские свечи выходного дня у выбранных инструментов и есть ли у них расписание.
6. Реальная задержка публикации по ТФ — для значений `candle_publication_timeout_by_tf` (совместно с ingestion 8.5).

Инженерные гипотезы настраиваемы и не являются SLA:
- `schedule_refresh_interval_secs = 3600`;
- `schedule_max_age_secs = 129600` (36 ч);
- `schedule_horizon_days = 7`.

## Acceptance Matrix

Все сценарии проверяются на управляемых часах и фиктивных источниках. Утверждения используют эффективные настройки.

| № | Сценарий | Результат |
|---|---|---|
| 1 | Запуск в понедельник 03:00 МСК, получены пятничные свечи до конца вечерней сессии, следующее окно 06:50 МСК | CLOSED; `last_due` = последний бар пятницы, получен → актуально; recovery и `delayed` нет; `next_event=session_open`; прогрев не ждёт новых баров |
| 2 | Клиринг 14:00–14:05 МСК | 1m внутри клиринга → BREAK(clearing), `scheduled_closed`; 15m/1h, перекрывающие клиринг и торги, остаются ожидаемыми |
