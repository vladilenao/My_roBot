## ADDED Requirements

### Requirement: Порт брокера контура на брокере
Нормативный уровень: MUST. Общий код контура на брокере ДОЛЖЕН работать с брокером только через порт `src/broker_contour/port.py`:

- `BrokerApi` — заявки, стоп-заявки, операции, цены, ГО, стрим заявок;
- `BrokerAccess` — правило счёта, факты допуска, снимок счёта, капитал, имена инструментов;
- `BrokerTraits` — свойства брокера.

Модули `broker`, `stops`, `fees`, `stream`, `process`, `admission`, `prices`, `orders`, `reconcile`, `guards`, `control`, `notify`, `fingerprint`, `store`, `bindings`, `port` НЕ ДОЛЖНЫ импортировать SDK брокера (`t_tech`, `grpc`) и `src.sandbox`, в том числе внутри функций. Код Т-Инвест ДОЛЖЕН лежать в пакете `src/broker_contour/tinvest/`.

Порт НЕ ДОЛЖЕН требовать от брокера:

- поиска заявки по ключу позже дня её постановки;
- комиссии в отчёте исполнения;
- ответа об объёме по обеспечению (`GetMaxLots`), если свойство `max_lots` выключено.

#### Scenario: Общий код без SDK
- **WHEN** тест разбирает импорты модулей общего кода
- **THEN** ни один из них не импортирует `t_tech`, `grpc` и `src.sandbox`

#### Scenario: Контракт порта на фейковом брокере
- **GIVEN** фейковый брокер с поведением Т-Инвест, реализующий `BrokerApi`
- **WHEN** контур проходит вход, цель, стоп у брокера, срабатывание стопа, рестарт и досверку
- **THEN** журнал заявок, журнал стоп-заявок и события исполнения те же, что с прежним `TInvestBroker`

### Requirement: Свойства брокера в адаптере
Нормативный уровень: MUST. Различия брокеров ДОЛЖНЫ задаваться свойствами адаптера `BrokerTraits`, а не условиями по номеру или виду контура:

- префикс номеров исполнений;
- суммы и стоп-цена в рублях за контракт;
- запрос объёма по обеспечению;
- период чтения ГО;
- досверка заявки по ключу или по номеру;
- поиск стоп-заявки с потерянным ответом по атрибутам или по ключу;
- источник настоящих комиссий.

У «Песочницы» и «Счёта» свойства ДОЛЖНЫ давать прежнее поведение:

- префикс `tinvest`;
- рублёвые суммы есть;
- `GetMaxLots` — только у «Счёта»;
- ГО раз в сутки;
- досверка по ключу, стоп-заявка — по атрибутам;
- комиссии из операций.

#### Scenario: Старая база не задваивает исполнения
- **GIVEN** `broker.sqlite3` и `trades.sqlite3` контура, записанные прежней версией, с исполнениями `tinvest:<сделка>` и `tinvest-order:<заявка>:<лоты>`
- **WHEN** контур стартует новой версией и брокер повторно присылает те же сделки
- **THEN** новых исполнений нет, журнал сделок не меняется, ждущие комиссии находятся по прежним номерам

#### Scenario: Объём по обеспечению только у «Счёта»
- **WHEN** песочница и «Счёт» входят в сделку
- **THEN** `GetMaxLots` спрашивает только «Счёт», как раньше

### Requirement: Описание контура на брокере
Нормативный уровень: MUST. Контур на брокере ДОЛЖЕН собираться по описанию: номер контура, вид, отпечаток брокера, профиль адаптера, заголовок карточек, переменные окружения токена и номера счёта. Процесс, надзиратель ядра и уведомления ДОЛЖНЫ брать номер и вид из описания. Новый экземпляр вида «счёт» ДОЛЖЕН добавляться новым описанием, без копии функций запуска.

Описания `sandbox` и `account` ДОЛЖНЫ сохранять прежние:

- номер и вид;
- папку `data/contours/<номер>/`;
- ключи `[contours.<номер>]`;
- пути API;
- отпечаток `broker` в `broker.sqlite3`;
- заголовки «ПЕСОЧНИЦА» и «СЧЁТ».

#### Scenario: Вид в статусе
- **WHEN** контур «Счёт» пишет `status.json`
- **THEN** `contour_id` и `kind` равны `account`, как раньше, и `kind` берётся из описания, а не из номера

#### Scenario: Порядок подъёма
- **WHEN** ядро поднимает контуры на брокере
- **THEN** первым «Счёт», затем песочница, как раньше
