## MODIFIED Requirements

### Requirement: Каталог типов событий
Нормативный уровень: MUST. Каталог ДОЛЖЕН содержать 19 существующих типов пользовательских уведомлений, типы `startup_analysis`, `market_data_status`, `broker_account` и `broker_order` и два служебных типа `tick_started` и `tick_finished`. Консоль по умолчанию ДОЛЖНА принимать все 23 пользовательских типа и обе служебные границы. Telegram по умолчанию ДОЛЖЕН получать девять lifecycle-типов: `signal`, `trade_opened`, `position_added`, `stop_hit`, `target_hit`, `stop_moved`, `trade_closed`, `trade_cancelled`, `order_rejected`; новые информационные типы доступны только при явной подписке. Канал Telegram контура на брокере ДОЛЖЕН получать `broker_account`, `broker_order`, `order_accepted` и девять lifecycle-типов своего контура всегда, независимо от списков `[notifier.telegram] events`; каналы эмуляции `broker_account` и `broker_order` по умолчанию НЕ ДОЛЖНЫ получать. Событие `broker_order` ДОЛЖНО нести `trade_id`, `kind` (`sent`, `unknown`, `found`, `resent`, `cancelling`, `exit_rejected`), контур, инструмент коротким именем, вид заявки, тип, лоты, цену в пунктах, последние четыре символа номера заявки брокера и причину.

Отмена/отклонение заявки актуализируют карточку с учётом текущего состояния и НЕ ДОЛЖНЫ автоматически означать закрытие уже открытой позиции. Явные наборы событий пользователя ДОЛЖНЫ сохраняться без скрытого добавления новых отображаемых событий. Служебные границы ДОЛЖНЫ доставляться технически независимо от пользовательских списков и НЕ ДОЛЖНЫ включать отключённые сообщения. Схемы новых событий ДОЛЖНЫ быть самодостаточными: каналы не запрашивают рынок или торговую базу для их отображения.

#### Scenario: Состав по умолчанию
- **WHEN** наборы событий не переопределены
- **THEN** консоль получает 23 пользовательских типа и две служебные границы, Telegram — девять lifecycle-типов

#### Scenario: Отказ не попадает в Telegram
- **WHEN** сигнал не допущен
- **THEN** rejected идёт в консоль, Telegram по умолчанию не создаёт карточку

#### Scenario: Явный список событий сохраняется
- **WHEN** пользователь оставил Telegram только signal и trade_closed
- **THEN** остальные типы, включая новые информационные, скрыто не доставляются

#### Scenario: Старый список консоли не требует миграции
- **WHEN** пользователь задал консоли events = ["decision", "error"]
- **THEN** обязательные границы продолжают доставляться, новые информационные типы автоматически не добавляются

#### Scenario: Информационный тип явно включён в Telegram
- **WHEN** пользователь включил startup_analysis или market_data_status в список Telegram
- **THEN** событие отображается информационным сообщением без создания торговой карточки или действия

#### Scenario: Событие контура на брокере
- **WHEN** контур «Песочница» публикует `broker_account` с `kind = reconcile_alarm`
- **THEN** сообщение уходит в канал контура «Песочница», канал эмуляции его не получает

#### Scenario: Заявка контура на брокере
- **WHEN** контур «Песочница» публикует `broker_order` с `kind = sent` по сделке NG
- **THEN** строка «отправлено в Т-Инвест» дописывается в карточку этой сделки в канале «Песочница», канал эмуляции её не получает
