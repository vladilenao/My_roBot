## ADDED Requirements

### Requirement: Торговля привязками в контуре на брокере
Нормативный уровень: MUST. При `[contours.sandbox] orders = true` процесс контура «Песочница» после допуска ДОЛЖЕН поднимать ту же торговую часть, что у эмуляции:

- свечи из ленты ядра;
- стратегии и фильтр;
- `TradeManager` с outbox в `trades.sqlite3` папки контура;
- карточки сделок.

Отличий три:

- стратегии — только привязки состава песочницы, каждая со своими стратегией, управлением, фильтром и таймфреймом;
- брокер — `TInvestBroker` поверх шлюза песочницы;
- капитал для допуска берётся со счёта (требование «Капитал контура на брокере»).

Эмуляция и история НЕ ДОЛЖНЫ менять поведение.

Спрос свечей инструментов своих привязок контур ДОЛЖЕН заявлять в ленте ядра под `contour_id = sandbox`. Инструмент привязки ДОЛЖЕН получать свечи, даже если эмуляция им не торгует.

Входы ДОЛЖНЫ идти только лимитными заявками. Команда входа или добора по рынку ДОЛЖНА получать `REJECT` с причиной `limit-entry-required` без обращения к брокеру.

#### Scenario: Одна привязка NG при эмуляции на всех стратегиях
- **GIVEN** эмуляция торгует NG всеми стратегиями, в составе песочницы одна привязка NG
- **WHEN** стратегия другой привязки NG даёт сигнал
- **THEN** сигнал виден в эмуляции, в песочнице сделки по нему нет

#### Scenario: Инструмента нет в эмуляции
- **GIVEN** эмуляция не торгует SBER, в песочницу добавлена привязка SBER
- **WHEN** контур заявил спрос
- **THEN** ядро грузит свечи SBER, стратегия привязки получает закрытые бары

### Requirement: Заявки контура на брокере
Нормативный уровень: MUST. `TInvestBroker` ДОЛЖЕН реализовывать `BrokerPort` и те методы, которые у `JournalBroker` вызывают `TradeManager` и сборка контура. Ответ `submit` ДОЛЖЕН быть немедленным:

- `ACK` — брокер принял заявку или её судьба неизвестна (причина `broker-unknown`);
- `REJECT` — отказ брокера (причина `broker:<код>`) или отказ проверки до отправки.

Исполнения, подтверждённые снятия и поздние отказы ДОЛЖНЫ приходить позже через `drain_addressed_events` и проводиться тем же `consume`.

| Команда | Действие у брокера |
|---|---|
| `OpenTrade`, `AddToTrade` (лимит) | `PostOrder` лимитная заявка по `limit_price`, ключ из `command_id` |
| `CloseTrade`, `ReduceTrade` без цели | `PostOrder` рыночная заявка на объём команды |
| `CancelEntry` | `CancelOrder` по каждому неисполненному входу сделки |
| `MoveStop` | новый стоп в представлении контура, без обращения к брокеру (до стоп-заявок у брокера) |

Ключ идемпотентности (`order_id` запроса) ДОЛЖЕН быть UUID, однозначно выведенным из `command_id`: тот же `command_id` даёт тот же ключ и после рестарта. Повторный `submit` команды, по ключу которой уже есть строка в журнале заявок, НЕ ДОЛЖЕН ставить новую заявку и ДОЛЖЕН отвечать её текущим состоянием.

`CANCEL` команды входа ДОЛЖЕН приходить только после подтверждения снятия брокером. Сделка биржи, пришедшая до подтверждения, ДОЛЖНА проводиться обычным исполнением. После частичного исполнения снимается остаток, а сделка продолжается с исполненным объёмом. Отказ брокера на вход ДОЛЖЕН отменять план без повторов.

#### Scenario: Вход принят и исполнен
- **GIVEN** привязка NG дала сигнал на покупку 2 лотов по 2,845
- **WHEN** команда входа доставлена брокеру, а затем пришли две сделки биржи по 1 лоту
- **THEN** `submit` отвечает `ACK` с номером заявки; журнал получает `PARTIAL` 1 лот и `FILL` 1 лот с ценами в пунктах; позиция 2 лота

#### Scenario: Повторная доставка той же команды
- **GIVEN** заявка входа отправлена, процесс упал до отметки outbox `SENT`
- **WHEN** после подъёма outbox снова отдаёт команду в `submit`
- **THEN** второй `PostOrder` не выполняется, у брокера одна заявка с этим ключом

#### Scenario: TTL входа
- **GIVEN** лимитный вход не исполнился за TTL таймфрейма
- **WHEN** `TradeManager` выпускает `CancelEntry` с `entry-timeout`
- **THEN** у брокера выполняется `CancelOrder`, `CANCEL` входа проводится только после подтверждения снятия

#### Scenario: Исполнение раньше отмены
- **GIVEN** по входу отправлен `CancelOrder`
- **WHEN** до подтверждения снятия пришла сделка биржи на 1 из 2 лотов, затем подтверждение
- **THEN** позиция 1 лот, вход завершён отменой остатка, сделка сопровождается дальше

#### Scenario: Отказ брокера на вход
- **WHEN** брокер отклонил лимитную заявку входа
- **THEN** план отменён, резерв освобождён, повторной заявки нет, в канале отказ с кодом брокера

### Requirement: Журнал заявок брокера
Нормативный уровень: MUST. Контур ДОЛЖЕН вести журнал заявок брокера в `broker.sqlite3` своей папки. Одна строка — одна заявка у брокера. Строка ДОЛЖНА записываться до вызова `PostOrder` и содержать:

- ключ, `command_id`, `trade_id`;
- вид — `entry`, `add`, `exit`, `stop`, `target`;
- инструмент, направление, тип заявки, лоты, цену в пунктах;
- состояние, номер заявки брокера, исполненные лоты, среднюю цену исполнения в пунктах;
- причину, число отправок, время создания, отправки и изменения.

Состояния: `sending`, `accepted`, `partial`, `filled`, `rejected`, `cancelling`, `cancelled`, `unknown`. Завершённые — `filled`, `rejected`, `cancelled`.

Каждая сделка биржи ДОЛЖНА записываться в журнал отдельной строкой с `execution_id = tinvest:<номер сделки биржи>` до проведения через `consume` и помечаться проведённой после него. Одна и та же сделка биржи НЕ ДОЛЖНА проводиться дважды, откуда бы она ни пришла: из стрима, из `GetOrderState` или после рестарта.

Полный номер счёта НЕ ДОЛЖЕН храниться в журнале заявок.

#### Scenario: Сделка пришла дважды
- **GIVEN** сделка биржи по входу пришла из стрима и проведена
- **WHEN** после переподключения стрима `GetOrderState` вернул ту же сделку в `stages`
- **THEN** объём позиции не меняется, новой строки исполнения нет

### Requirement: Исполнения из стрима
Нормативный уровень: MUST. Контур ДОЛЖЕН держать `OrderStateStream` по счёту робота в отдельном потоке. Поток ДОЛЖЕН:

- сопоставлять каждое событие со строкой журнала заявок по `order_request_id` и не опираться на временный `order_id` первого события;
- писать новые сделки биржи в журнал заявок и в очередь исполнений;
- обновлять состояние строки по статусу и `lots_executed`.

Событие по заявке без нашего ключа НЕ ДОЛЖНО попадать в очередь исполнений.

Поток стрима НЕ ДОЛЖЕН писать в `trades.sqlite3`. Очередь исполнений ДОЛЖНА разбираться главным потоком через `consume` не реже раза в `tick_poll_secs`, а не только на новой свече.

При обрыве стрим ДОЛЖЕН переподключаться с паузой 1, 2, 4… до 30 с. После переподключения каждая незавершённая строка журнала заявок ДОЛЖНА досверяться через `GetOrderState` по ключу. Пропущенные сделки берутся из `stages`.

#### Scenario: Временный номер заявки
- **GIVEN** стрим прислал событие с временным `order_id` и нашим `order_request_id`, затем событие с постоянным номером
- **WHEN** оба события обработаны
- **THEN** это одна строка журнала заявок, номер брокера — постоянный

#### Scenario: Обрыв стрима во время исполнения
- **GIVEN** вход отправлен, стрим оборвался
- **WHEN** вход исполнился, пока стрима не было, и стрим переподключился
- **THEN** исполнение найдено по ключу, проведено один раз, позиция совпадает со счётом

### Requirement: Восстановление заявки по ключу
Нормативный уровень: MUST. Заявка ДОЛЖНА становиться `unknown`, если:

- `PostOrder` закончился тайм-аутом, `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `INTERNAL` или обрывом соединения;
- при старте найдена строка в `sending`.

Контур НЕ ДОЛЖЕН отправлять такую заявку повторно, не спросив брокера. На ближайшей границе тика, а после старта до первого тика, контур ДОЛЖЕН выполнить `GetOrderState` с `ORDER_ID_TYPE_REQUEST` по ключу:

- найдена — состояние и сделки берутся из ответа;
- не найдена, а команда актуальна — `PostOrder` тем же ключом. Вход актуален, если сделка ждёт входа и TTL не истёк; выход — пока у сделки есть остаток;
- не найдена и вход устарел — вход завершается `CANCEL` с причиной `entry-undelivered`.

Ответ `INVALID_ARGUMENT` с кодом 30057 («дубликат») на `PostOrder` ДОЛЖЕН вести к поиску по ключу, а не к отказу.

Если шлюз исчерпал повторы при `RESOURCE_EXHAUSTED`, вход ДОЛЖЕН получать `REJECT` с причиной `rate-limited`, а выход — повторяться на следующем шаге.

Перед первым тиком после старта контур ДОЛЖЕН разобрать все незавершённые строки журнала заявок и провести через `consume` все непроведённые исполнения.

#### Scenario: Процесс убит между отправкой и исполнением
- **GIVEN** заявка входа отправлена, процесс контура убит до ответа
- **WHEN** ядро поднимает контур снова
- **THEN** до первого тика заявка найдена по ключу, второй заявки у брокера нет, исполнение, если было, проведено один раз

#### Scenario: Заявка не дошла
- **GIVEN** `PostOrder` входа закончился тайм-аутом
- **WHEN** поиск по ключу ничего не нашёл, TTL входа не истёк
- **THEN** заявка отправляется снова тем же ключом, у брокера одна заявка

#### Scenario: Дубликат ключа
- **WHEN** повторный `PostOrder` получил ошибку 30057
- **THEN** контур находит заявку по ключу и продолжает с её состоянием, отказа в журнале нет

### Requirement: Цены, лоты и ГО заявок
Нормативный уровень: MUST. Перед отправкой контур ДОЛЖЕН:

- округлять цену лимитной заявки до шага цены в безопасную сторону: покупка вниз, продажа вверх;
- отправлять её в пунктах;
- отправлять количество в лотах;
- отклонять заявку с ценой вне коридора инструмента причиной `price-out-of-band`, без запроса `PostOrder`.

Цены фьючерса от брокера (ответы заявок, сделки стрима, `stages`) приходят в рублях за контракт. Контур ДОЛЖЕН переводить их в пункты: `пункты = рубли × min_price_increment / min_price_increment_amount` из `GetFuturesMargin`, с округлением до шага. У акций цена в рублях за бумагу и есть цена в пунктах. Если брокер присылает объём сделки в штуках, а не в лотах, контур ДОЛЖЕН делить его на размер лота.

ГО на контракт ДОЛЖНО браться из `GetFuturesMargin` (`initial_margin_on_buy` или `initial_margin_on_sell`) при допуске инструмента и обновляться раз в сутки. Оно заменяет ГО карточки контракта у контура.

#### Scenario: Рубли в пункты
- **GIVEN** у NG шаг 0.001, стоимость шага 8,08664 ₽
- **WHEN** брокер прислал цену исполнения 22 731,55 ₽
- **THEN** в журнал сделок попадает цена 2.811

#### Scenario: Округление лимита
- **WHEN** план входа в покупку даёт цену 2.8457 при шаге 0.001
- **THEN** заявка уходит с ценой 2.845

### Requirement: Капитал контура на брокере
Нормативный уровень: MUST. Капиталом контура «Песочница» для допуска сделок ДОЛЖНЫ быть рубли на счёте из `GetPositions`. `liquid_portfolio` ДОЛЖЕН показываться рядом и НЕ ДОЛЖЕН влиять на допуск. Капитал ДОЛЖЕН читаться при старте, после каждого своего исполнения (на следующей границе тика) и при каждой сверке. Кандидаты одного тика ДОЛЖНЫ допускаться по одному снимку капитала.

Вход или добор ДОЛЖЕН допускаться по ГО, только если лоты × ГО на контракт не больше рублей на счёте за вычетом ГО неисполненных входов контура. Отказ ДОЛЖЕН публиковаться прежним событием ограничения бюджета с причиной «не хватает ГО».

Если капитал не прочитан, новые входы и доборы ДОЛЖНЫ отклоняться с причиной «счёт недоступен», а выходы и сокращения ДОЛЖНЫ работать.

Эмуляция ДОЛЖНА по-прежнему брать капитал из `initial_deposit`.

#### Scenario: Пополнение без правки конфига
- **GIVEN** на счёте 1 000 000 ₽
- **WHEN** командой песочницы счёт пополнен на 500 000 ₽, и прошла сверка
- **THEN** следующая сделка считается от 1 500 000 ₽

#### Scenario: Не хватает ГО
- **GIVEN** на счёте 5 000 ₽, ГО NG на покупку 6 228 ₽
- **WHEN** привязка NG дала сигнал на 1 лот
- **THEN** сделки нет, у сигнала причина «не хватает ГО», заявок к брокеру нет

### Requirement: Стоп и цели контуром до стоп-заявок у брокера
Нормативный уровень: MUST. Пока стоп-заявки у брокера не введены, контур ДОЛЖЕН определять срабатывание стопа и целей открытых сделок по закрытым минутным свечам ядра по тем же правилам, что симулятор эмуляции:

- стоп важнее целей;
- гэп через стоп на открытии;
- цели по порядку цены;
- объём цели по прежнему распределению.

При срабатывании контур ДОЛЖЕН ставить рыночную заявку на объём стопа (весь остаток) или цели. Её `command_id` строится в формате защитного закрытия симулятора (`<trade>:pv:stop:<bar>`, `<trade>:pv:tp:<target>:<bar>`).

Сделки биржи по защитной заявке ДОЛЖНЫ сводиться в одно исполнение `FILL` со средней ценой, когда заявка завершилась. Позиция в журнале меняется только по этому исполнению.

У одной сделки ДОЛЖНА быть не больше одной выходной заявки в работе. Сигнальный выход, пришедший при незавершённом защитном, ждёт его. Если после завершения остаток ноль, сигнальный выход получает `REJECT trade-not-open`.

Отказ брокера на выход ДОЛЖЕН повторяться не чаще раза в минуту новым ключом, пока выход не пройдёт или остаток не станет нулевым. О первом отказе в канал уходит тревога.

#### Scenario: Стоп по закрытой минуте
- **GIVEN** длинная позиция NG 2 лота, стоп 2,812
- **WHEN** закрытая минута ядра имеет low 2,810
- **THEN** контур ставит рыночную продажу 2 лотов, после исполнения сделка закрыта по цене брокера, в канале «стоп исполнен»

#### Scenario: Цель 1
- **GIVEN** позиция 2 лота, цель 1 — 1 лот по 2,911
- **WHEN** закрытая минута имеет high 2,915
- **THEN** контур продаёт 1 лот по рынку, остаток 1 лот, стоп контура ведёт остаток

#### Scenario: Выход вне торгов
- **GIVEN** стоп сработал на последней минуте сессии
- **WHEN** брокер отклонил рыночную заявку, потому что торги закрыты
- **THEN** в канал уходит тревога, выход повторяется не чаще раза в минуту и проходит после открытия торгов

### Requirement: Остановка контура на брокере с открытыми сделками
Нормативный уровень: MUST. Команды остановки контура «Песочница» ДОЛЖНЫ действовать на его сделки по правилам эмуляции:

- `no_entries` — неисполненные входы снимаются у брокера, открытые сделки сопровождаются до выхода;
- `close_all` — дополнительно каждая открытая сделка закрывается рыночной заявкой.

Процесс ДОЛЖЕН завершаться сам со `state = stopped`, когда у контура не осталось открытых сделок и незавершённых заявок.

Снятие привязки ДОЛЖНО действовать так же, но только на сделки этой привязки:

- `no_entries` — привязка не открывает новых входов, сопровождает свои сделки и уходит из состава после последней;
- `close_all` — то же, плюс её сделки закрываются.

Последняя привязка инструмента уводит и инструмент.

Штатный выход по Ctrl+C, концу stdin или пульсу «остановлено» ДОЛЖЕН оставлять заявки входа у брокера и позиции на счёте как есть. Сообщение `stopped` ДОЛЖНО называть число открытых позиций.

#### Scenario: Остановка с закрытием
- **GIVEN** у контура открытая позиция NG и неисполненный вход SBER
- **WHEN** приходит `PUT /api/v1/sandbox/target` с `mode = close_all`
- **THEN** вход SBER снят у брокера, позиция NG закрыта рыночной заявкой, контур завершается со `stopped`, на счёте позиций нет

#### Scenario: Снятие одной привязки
- **GIVEN** у привязок `future-ng-macd` и `future-ng-flat` по открытой сделке
- **WHEN** `future-ng-macd` снимается с `no_entries`
- **THEN** её сделка доводится до выхода, сделка `future-ng-flat` не затронута, после выхода `future-ng-macd` уходит из состава

## MODIFIED Requirements

### Requirement: Контур «Песочница» отдельным процессом
Нормативный уровень: MUST. Контур на брокере вида `sandbox` ДОЛЖЕН работать процессом `run.py --contour sandbox`, который запускает ядро. Папка контура — `data/contours/sandbox/`. В ней ДОЛЖНЫ лежать:

- блокировка `robot.pid`;
- лог `bot_debug.log`;
- `launch.json` — файл запуска от ядра;
- `status.json` — фактическое состояние;
- `broker.sqlite3` — отпечаток счёта, отчёты сверки и журнал заявок брокера;
- `trades.sqlite3` — журнал сделок торговой части (при `orders = true`);
- `telegram_delivery.sqlite3` — доставка в канал контура.

С брокером контур ДОЛЖЕН работать только через шлюз песочницы `src/sandbox` (адрес песочницы, токен `TINKOFF_SANDBOX_TOKEN`).

При `[contours.sandbox] orders = false` контур работает только на чтение, как на С2:

- НЕ ДОЛЖЕН отправлять заявки и стоп-заявки;
- НЕ ДОЛЖЕН читать свечи;
- НЕ ДОЛЖЕН заявлять спрос в ленте ядра.

При `orders = true` контур торгует по требованию «Торговля привязками в контуре на брокере». Стоп-заявки он НЕ ДОЛЖЕН отправлять до введения стоп-заявок у брокера.

`status.json` ДОЛЖЕН содержать поля, по которым ядро решает подхват (`pid`, `version`, `alive_at`, `exited_at`, `state`, `applied_generation`, `members`), а также:

- `orders_enabled` — режим заявок, `true` или `false`;
- `account` — номер счёта последними четырьмя символами;
- `capital` — `rub` и `liquid_portfolio`;
- `positions`, `orders`, `stop_orders` — что есть на счёте;
- `trades` — число открытых сделок журнала;
- `orders_in_flight` — число незавершённых заявок журнала заявок;
- `frozen` — замороженные инструменты;
- `last_reconcile_at`;
- `account_link` — `ok` или `lost`;
- `stream_link` — `ok` или `lost`;
- `reason` — причина отказа или выхода.

У каждого участника в `members` ДОЛЖНО быть состояние привязки: `warming`, `trading`, `draining`, `closing`, `rejected` (инструмент не определён) или `watching` (режим только чтения).

#### Scenario: Процесс песочницы
- **WHEN** ядро запускает контур «Песочница»
- **THEN** работает процесс `run.py --contour sandbox`, его лог и `status.json` лежат в `data/contours/sandbox/`, а процесс эмуляции, если он есть, работает дальше

#### Scenario: Только чтение
- **GIVEN** `orders = false`, контур «Песочница» работает со стартовым составом из двух привязок
- **WHEN** проходит любое число шагов
- **THEN** в записях вызовов шлюза нет `PostOrder`, `PostStopOrder`, `CancelOrder` и `CancelStopOrder`

#### Scenario: Без стоп-заявок
- **GIVEN** `orders = true`, у контура открытая сделка
- **WHEN** проходит любое число тиков
- **THEN** в записях вызовов шлюза нет `PostStopOrder`

### Requirement: Шаг контура на брокере
Нормативный уровень: MUST. При `orders = false` после допуска контур ДОЛЖЕН работать шагами раз в 10 секунд. При `orders = true` та же работа ДОЛЖНА выполняться на границах тика торговой части и не реже раза в 10 секунд, даже без новых свечей. По порядку:

1. пульс ядра: «остановлено» или пульс другой версии — штатный выход после шага, как у эмуляции; пульс старше `heartbeat_timeout_secs` — работа продолжается, `core_link = lost`, новые входы не допускаются;
2. целевое состояние из `core.sqlite3`: новое поколение применяется на этом шаге, `applied_generation` — его номер;
3. разбор заявок `unknown` и очереди исполнений;
4. капитал, если было своё исполнение;
5. сверка, если с прошлой сверки прошло не меньше `reconcile_every_min` минут;
6. запись `status.json` с `alive_at`.

При `orders = false` остановка (`no_entries` или `close_all`) ДОЛЖНА завершать процесс на шаге её применения, со `state = stopped`, и НЕ ДОЛЖНА трогать счёт. При `orders = true` остановка действует по требованию «Остановка контура на брокере с открытыми сделками».

#### Scenario: Добавили привязку
- **GIVEN** песочница работает, применено поколение 4
- **WHEN** команда добавляет привязку и пишет поколение 5
- **THEN** не позже чем через 10 секунд `status.json` показывает `applied_generation = 5` и привязку в `members`

#### Scenario: Остановка с закрытием
- **GIVEN** `orders = false`, на счёте песочницы ручная позиция NG
- **WHEN** приходит `PUT /api/v1/sandbox/target` с `mode = close_all`
- **THEN** процесс выходит на ближайшем шаге со `state = stopped`, позиция NG на счёте остаётся

### Requirement: Состав контура на брокере из привязок
Нормативный уровень: MUST. Участник состава контура «Песочница» ДОЛЖЕН быть привязкой — `id` из `[strategies.*]`. Состав ДОЛЖЕН храниться в `contour_members` `core.sqlite3` с ключом — `id` привязки и:

- карточкой привязки: инструмент, стратегия, управление, фильтр, таймфрейм;
- инструментом привязки, который ядро определяет по правилам запуска эмуляции: акция — по тикеру, фьючерс — действующий контракт семейства с запасом до экспирации;
- карточкой контракта от ядра.

Если инструмент привязки определить нельзя, ДОЛЖЕН следовать отказ `422 BINDINGS_REJECTED` с причиной, а состав НЕ ДОЛЖЕН меняться. `launch.json` контура ДОЛЖЕН нести привязки, их инструменты и карточки контрактов.

Состав ДОЛЖЕН меняться только командами API и НЕ ДОЛЖЕН задаваться в `robot.toml`. Состав эмуляции и состав песочницы НЕ ДОЛЖНЫ влиять друг на друга.

Привязка, добавленная на работающий контур, ДОЛЖНА начинать торговать на ближайшей границе тика после прогрева своего инструмента. Привязка, сохранённая без инструмента (С2), при запуске получает его заново. Если это не удалось, привязка помечается `rejected` с причиной, а остальные торгуют.

#### Scenario: Независимые составы
- **GIVEN** эмуляция торгует NG всеми стратегиями
- **WHEN** в песочницу добавлена одна привязка NG
- **THEN** состав эмуляции не меняется, `GET /api/v1/sandbox/bindings` отмечает эту привязку как торгующую в эмуляции и в песочнице

#### Scenario: Контракт привязки
- **GIVEN** у семейства NG действуют контракты NG-11.26 и NG-12.26, до экспирации NG-11.26 меньше `contract_expiry_block_days`
- **WHEN** в песочницу добавляется привязка NG
- **THEN** её инструмент — NG-12.26, как выбрала бы эмуляция

### Requirement: Сверщик счёта
Нормативный уровень: MUST. Сверщик ДОЛЖЕН сравнивать по каждому инструменту, у которого есть что-то на счёте или в журнале контура:

- позицию в лотах (`GetPortfolio`) с суммой знаковых остатков открытых сделок журнала;
- активные заявки (`GetOrders`) с незавершёнными строками журнала заявок, у которых есть номер брокера;
- активные стоп-заявки (`GetStopOrders`) с защитными заявками журнала. Пока стоп-заявки у брокера не введены, любая стоп-заявка на счёте — расхождение.

Сверка ДОЛЖНА выполняться при старте, после разбора журнала заявок и до первого тика, и затем не реже раза в `reconcile_every_min` минут. Перед каждой сверкой ДОЛЖНА разбираться очередь исполнений. Инструмент, у которого есть заявка в `sending`, `unknown` или `cancelling` или непроведённое исполнение, в этой сверке НЕ ДОЛЖЕН сравниваться и ДОЛЖЕН попадать в отчёт отметкой `in_flight`.

Инструмент с любым расхождением ДОЛЖЕН попадать в заморозку, инструмент без расхождений — выходить из неё. Заморозка ДОЛЖНА запрещать по инструменту новые входы и доборы с причиной «инструмент заморожен сверкой». Выходы, сокращения и стоп заморозка НЕ ДОЛЖНА трогать. При `orders = false` журнал пуст, поэтому любая позиция, заявка или стоп-заявка на счёте — расхождение «на счёте есть, в журнале нет».

Уведомления сверщика:

- при переходе из «совпадает» в «расхождение» и при каждом изменении состава расхождений — событие `broker_account` с `kind = reconcile_alarm`;
- при переходе в «совпадает» — `reconcile_cleared`;
- одинаковые подряд отчёты НЕ ДОЛЖНЫ уведомлять повторно.

Каждый отчёт ДОЛЖЕН сохраняться в `broker.sqlite3` (последние 100) и содержать:

- время;
- итог `ok` или `mismatch`;
- расхождения: инструмент коротким именем, что (`position`, `order`, `stop_order`), на счёте, по журналу;
- инструменты `in_flight`;
- замороженные инструменты.

Если счёт не прочитан (сеть, брокер), сверка ДОЛЖНА пропускаться с предупреждением в лог, `account_link = lost`, заморозки — оставаться как были. Третий подряд пропуск ДОЛЖЕН давать `reconcile_alarm` с причиной «счёт недоступен».

#### Scenario: Ручная покупка
- **GIVEN** песочница работает, расхождений нет
- **WHEN** командой `python -m src.sandbox buy NG 1` куплен 1 лот, и наступила сверка
- **THEN** отчёт `mismatch`: NG, `position`, на счёте на 1 больше, чем по журналу; NG заморожен; в канал «Песочница» уходит одна тревога

#### Scenario: Сделка контура совпадает
- **GIVEN** контур купил 2 лота NG, исполнение проведено
- **WHEN** наступила сверка
- **THEN** отчёт `ok`, NG не заморожен

#### Scenario: Исполнение ещё в пути
- **GIVEN** сделка биржи по входу NG пришла в стрим, но ещё не проведена
- **WHEN** наступила сверка
- **THEN** очередь разбирается до сравнения, а если исполнение всё равно не проведено, NG в отчёте `in_flight` и не заморожен

#### Scenario: Заморозка не мешает выходу
- **GIVEN** NG заморожен, у контура открытая позиция NG
- **WHEN** стратегия даёт сигнал на добор, а затем срабатывает стоп
- **THEN** добор отклонён с причиной «инструмент заморожен сверкой», выход по стопу выполнен

#### Scenario: Расхождение устранено
- **GIVEN** NG заморожен из-за ручной позиции
- **WHEN** позиция закрыта командой `sell NG 1`, и наступила сверка
- **THEN** отчёт `ok`, заморозки нет, в канал уходит `reconcile_cleared`

#### Scenario: Тревога не повторяется
- **GIVEN** расхождение по NG уже отправлено тревогой
- **WHEN** следующие сверки дают тот же состав расхождений
- **THEN** новых сообщений в канал нет, отчёты сохраняются

#### Scenario: После рестарта тревога на месте
- **GIVEN** NG заморожен, робот перезапущен
- **WHEN** контур песочницы поднялся и выполнил стартовую сверку
- **THEN** NG снова заморожен, `GET /api/v1/sandbox/reconcile` показывает расхождение, в канал уходит `started` и тревога

### Requirement: Уведомления контура на брокере
Нормативный уровень: MUST. Контур ДОЛЖЕН публиковать события в свою шину и доставлять их Telegram-каналом с ботом из `telegram_bot_env` в канал из `telegram_channel_env`, с сохранением и досылкой по правилам `telegram-delivery-recovery` в своём `telegram_delivery.sqlite3`.

Канал контура ДОЛЖЕН получать:

- `broker_account`;
- `broker_order`;
- `order_accepted`;
- девять lifecycle-типов торговли своего контура: `signal`, `trade_opened`, `position_added`, `stop_hit`, `target_hit`, `stop_moved`, `trade_closed`, `trade_cancelled`, `order_rejected`.

Списки `[notifier.telegram] events` эмуляции на канал контура НЕ ДОЛЖНЫ влиять. Карточки сделок контура ДОЛЖНЫ строиться по правилам `telegram-trade-cards` с меткой контура «ПЕСОЧНИЦА» в заголовке. Строки `order_accepted` и `broker_order` ДОЛЖНЫ дописываться в корневую карточку своей сделки.

| `kind` `broker_account` | Содержание |
|---|---|
| `started` | вид контура, счёт …XXXX, рубли, `liquid_portfolio`, число позиций, заявок и стоп-заявок, число привязок, поколение, режим заявок |
| `reconcile_alarm` | расхождения по инструментам коротким именем, заморозка, подсказка «выровнять счёт и дождаться сверки» |
| `reconcile_cleared` | что расхождений нет, какие инструменты разморожены |
| `stopped` | причина выхода, число открытых позиций |

| `kind` `broker_order` | Содержание |
|---|---|
| `sent` | заявка отправлена: вход, добор или выход, лимит с ценой или рынок, лоты |
| `unknown` | ответ брокера потерян, заявка будет найдена по ключу |
| `found` | заявка найдена по ключу, её состояние |
| `resent` | по ключу пусто, заявка отправлена снова тем же ключом |
| `cancelling` | отмена отправлена брокеру |
| `exit_rejected` | брокер отклонил выход, причина, когда повтор (тревога) |

Инструменты в сообщениях ДОЛЖНЫ называться коротким именем, номер заявки брокера — последними четырьмя символами. Номер счёта и ключ целиком в сообщениях НЕ ДОЛЖНЫ появляться.

#### Scenario: Старт в канале

- **WHEN** контур прошёл допуск
- **THEN** в канал «Песочница» приходит сообщение о старте со счётом …09c3, 1 000 000 ₽, двумя привязками и режимом заявок

#### Scenario: Карточка сделки в песочнице
- **GIVEN** привязка NG дала сигнал, вход исполнен, затем сработала цель
- **WHEN** события доставлены
- **THEN** в канале «Песочница» одна корневая карточка «ПЕСОЧНИЦА NG», в ней строки «отправлено в Т-Инвест, лимит 2,845», «принято брокером, заявка …7f3a», «исполнено 2 из 2 по 2,846», затем выход по цели; в канале эмуляции этих строк нет
