- [x] 3.7 Инцидент 02.11 (проверка 7.2, вход SiZ6 на 10 лотов исполнился одной сделкой): в `broker_executions` по заявке две записи по 10 лотов — исполнение по сумме заявки (`GetOrderState` через 0,05 с после `PostOrder`, сделок ещё нет) и следом сделка стрима; `lots_executed = 20`. Тик падал `execution order does not match command`: ACK и исполнения брокера несли в `order_id` номер заявки брокера, а у заявки журнала сделок id — команда. Сделка осталась `ENTRY_PENDING`, сверка заморозила Si. Исправление:
  - `order_id` событий брокера — id заявки журнала сделок (команда, у целей и стопа — `:pv:`-команда);
  - сделки стрима не ложатся поверх исполнения по сумме заявки: объём заявки не больше её лотов и итога брокера, лишнее с непроведённых исполнений помечается «перекрыто» (`consumed = 2`) — сначала заглушка, затем последние сделки;
  - та же проверка перед выдачей исполнений в `consume` выправляет журнал, записанный до правки;
  - тесты: обе гонки (стрим → `GetOrderState`, `GetOrderState` → стрим, с проведённой и непроведённой заглушкой), снятая после частичного исполнения заявка, база тестового робота после рестарта; сквозной тест с настоящими `Storage`, reducer и `TradeManager` (`test_tinvest_journal.py`).
- [x] 3.8 Инцидент 02.11 (Si, выходы): частичный выход на 1 лот и стоп на 8 лотов ушли по две заявки, брокер исполнил обе (стоп первой сделки — тоже 2 × 10). Выход исполнялся сразу, а `_pump` считал остаток по представлению сделки, которое меняется только при разборе очереди, и через 0,05–0,25 с ставил такую же заявку. Лишние исполнения reducer отверг (`reducing fill exceeds open position`, `filled quantity exceeds order quantity`), они навсегда остались непроведёнными, Si выпал из сверки как «в пути»: на счёте −2, в журнале −1, тревоги нет; брокер насчитал по сделке 0 лотов и отвечал на каждое закрытие `REJECT trade-not-open`. Исправление:
  - новая заявка выхода или цели не ставится, пока у сделки есть непроведённые исполнения или заявка выхода ждёт своих сделок;
  - отказ reducer'а по исполнению брокера на счёте: `TradeManager.consume` зовёт `refuse_execution`, брокер откатывает представление сделки и помечает исполнение «отвергнуто» (`consumed = 3`), «в пути» оно не считается — расхождение показывает сверка; исполнение по сделке вне журнала — так же; эмуляция без изменений;
  - тесты: выход и стоп, исполненные до разбора очереди, без второй заявки; сквозной тест отказа журнала; прогон восстановления на копии баз тестового робота 02.11 (три лишних исполнения отвергнуты, позиция контура по журналу, «в пути» пусто).
