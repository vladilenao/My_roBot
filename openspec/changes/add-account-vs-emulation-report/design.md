## Context

- **Два контура, одни сигналы.**
  - Эмуляция (`data/contours/emulation/trades.sqlite3`) торгует инструментами из своего состава всеми их привязками.
  - Песочница (`data/contours/sandbox/trades.sqlite3`) торгует своим составом привязок, обычно меньшим.
  - Ключ сигнала в обоих журналах одинаковый: `trades.signal_id` = `<привязка>:<тикер>:<ТФ>:<начало бара>:<сторона>`, например `future-si-ma-raw:SiZ6:5m:2026-11-06T04:25:00:SELL`. `trades.created_at` — логическое время сигнала, а не часы контура.
- **Ресурсы торговли** `…/trades`, `…/performance`, `…/positions` (`src/bot/trades_view.py`) уже читают журнал контура только на чтение. Карточка закрытой сделки уже содержит входы, выходы, вид выхода, нетто и `result_r`.
- **Отказы по сигналу** в журнале контура: строки `calculations` с `outcome = 'REJECTED'`, `signal_id` и кодом причины, например `intraday-session-closed`, `risk-budget`, `trend-opposes-entry`, `contour-stopping`. Сделка песочницы с отказом брокера или неисполненным лимитом входа остаётся строкой `trades` в фазе `REJECTED` или `CANCELLED` без исполнений входа.
- **Комиссии.**
  - Эмуляция — по настройкам (`fee_source = configured`).
  - Песочница сейчас тоже по настройкам: брокер контура отдаёт исполнение с `fee = None`, менеджер оценивает его.
  - Поправка комиссии уже есть: `FeeAdjustment` в `BrokerPort`, `TradeManager.consume` → `reducer.apply_fee_adjustment` → `cost_adjustments`. Поправка меняет `fills.fee`, `fee_source = 'broker'`, комиссии позиции и счёта; повтор с тем же ключом ничего не делает.
- **Разведка С1, П12:** сделка и комиссия видны в `GetOperationsByCursor` не позже минуты. Комиссия там есть дважды: полем `commission` у операции покупки и отдельной операцией `OPERATION_TYPE_BROKER_FEE`.
- **Исполнение песочницы** в журнале заявок брокера: `execution_id = tinvest:<номер сделки биржи>`.
- **Решения владельца 08.11:**
  - пары по ключу сигнала;
  - отчёт — в API для UI, без файла;
  - настоящие комиссии правят журнал;
  - ветка `feature/broker-protection`.

## Goals / Non-Goals

**Goals:**

- По одному запросу видно, какие сигналы дали сделку в обоих контурах, в каком одном и почему, и чем отличились пары.
- Сделка без пары объяснена причиной из журнала другого контура, а не просто «нет».
- Комиссия песочницы в журнале — настоящая, брокерская, и итоги контура на ней.

**Non-Goals:**

- Сравнение со счётом: это Р2, тот же отчёт с третьим контуром позже.
- Файл отчёта и встроенные страницы робота.
- Настоящие комиссии в эмуляции: у неё нет брокера.
- Вывод «почему разошлось» сверх кодов расхождений: вид выхода и стоп внутри минуты видны из самих полей пары.
- Сравнение отказов без сделки в обоих контурах: если ни один не вошёл, пары нет.

## Decisions

### 1. Отчёт строит ядро из двух журналов

`GET /api/v1/sandbox/comparison` обслуживает API управления ядра. Ядро открывает оба `trades.sqlite3` только на чтение, каждый — одной транзакцией на ответ, как `ContourTrades`. Контур не участвует, ответ есть и у остановленных контуров. Код — `src/bot/comparison_view.py`, он переиспользует чтение журнала `ContourTrades` (карточка закрытой сделки, позиции, имена, `trade_ref`).

Альтернатива — отчёт в процессе песочницы. Отвергнута: песочница не должна читать журнал эмуляции, а отчёт нужен и при остановленном контуре.

### 2. Что входит в отчёт

- **Привязки отчёта** — привязки текущего состава песочницы плюс привязки сделок песочницы за период. Сигналы привязок, которых в песочнице нет и не было, в отчёт не входят: эмуляция торгует шире, и иначе отчёт состоял бы из «только в эмуляции».
- **Сделка в отчёте** — строка `trades` с хотя бы одним исполнением входа.
  - Сделка `REJECTED` или `CANCELLED` без исполнений не сделка, а причина для другой стороны.
  - Открытые сделки входят: у пары может быть закрыта одна сторона.
- **Период** — по `trades.created_at`, то есть по времени сигнала. Правила `period`, `from`, `to` — как у `…/performance`, по умолчанию `day`. У отказа без сделки время — `created_at` строки `calculations`.

### 3. Пара и её расхождения

Пара — две сделки с одинаковым `signal_id`. Из-за уникального активного индекса `(assignment_id, instrument_id)` и `processed_signals` у сигнала в контуре не больше одной сделки.

У каждой стороны пары: `id` (`trade_ref`), `state` (`open` или `closed`), `entry` (`at`, `price` — средняя, `lots`), `exit` (`at`, `price` — средняя, `kind`, `code`, `label`) или `null` у открытой, `net`, `net_per_lot`, `result_r`, `fees`, `fees_source`.

`net_per_lot` = `net / max_quantity`: лоты контуров разные, потому что капитал разный. Сравниваются цены, R и нетто на лот, а не рубли.

Расхождения — список кодов, каждый с `label` и значением:

| Код | Когда | Значение |
|---|---|---|
| `entry_price` | средние входа отличаются на 1 шаг цены и больше | разница в шагах: песочница − эмуляция, со знаком стороны (плюс — песочница хуже) |
| `entry_time` | первые входы разошлись больше чем на 60 секунд | секунды: песочница − эмуляция |
| `lots` | разный наибольший объём | лоты обеих сторон |
| `exit_kind` | обе закрыты, вид выхода разный | виды обеих сторон |
| `exit_price` | обе закрыты, вид одинаковый, средние выхода отличаются на 1 шаг и больше | разница в шагах со знаком стороны (плюс — песочница хуже) |
| `exit_time` | обе закрыты, последние выходы разошлись больше чем на 60 секунд | секунды |
| `closed_one_side` | одна закрыта, другая открыта | какая закрыта |

Пороги 1 шаг и 60 секунд — константы кода, не настройка: отчёт сравнивает, а не судит.

Шаг цены — из `trades.price_step` сделки песочницы. Если его нет — из сделки эмуляции. Если нет у обеих, ценовые коды не считаются, а у пары появляется отметка `steps_unknown`.

### 4. Причина сделки без пары

Для сделки только в одном контуре причина ищется в журнале другого по тому же `signal_id`, по порядку:

1. **Отказ решения** — последняя строка `calculations` с `outcome = 'REJECTED'`: `code` и `label` по `reason_label`, как у отказов в журнале.
2. **Сделка без входа** — строка `trades` в фазе `REJECTED` или `CANCELLED`. Код — причина последней отмены или отказа сделки: `broker:<код>`, `limit-entry-cancelled`, `stop-pending` и так далее.
3. **Вход ещё ждёт** — сделка без исполнений входа в другой фазе: код `entry-pending`, «вход ещё не исполнен».
4. **Сделки нет** — код `not-seen`, «сигнала в контуре не было». Привязки нет в составе или контур не работал.

Сделка песочницы на привязке, которой нет в эмуляции, — тоже `not-seen`.

### 5. Ответ и сводка

```
{ "currency": "RUB", "period": {...}, "as_of": "…",
  "summary": {...}, "items": [...], "earlier": bool, "_links": {...} }
```

- **`items`** — пары и сделки без пары, новые сверху по времени сигнала, `limit` по умолчанию 200, не больше 1000. У элемента:
  - `signal` — `binding`, `instrument`, `timeframe`, `side`, `at`;
  - `kind` — `pair`, `emulation_only` или `sandbox_only`;
  - `emulation` и `sandbox` — сторона или `null`;
  - у пары — `diffs`;
  - у сделки без пары — `missing_reason` (`contour`, `code`, `label`).
- **`summary`** считается по всему периоду и фильтрам, без учёта `limit`:
  - `pairs`, `emulation_only`, `sandbox_only` — числа;
  - `missing_reasons` — число по каждой причине и стороне;
  - `diffs` — число пар по каждому коду;
  - `entry_steps` и `exit_steps` — среднее и наибольшее по модулю отклонение в шагах по парам, где оно посчитано;
  - `paired_result` — по закрытым с обеих сторон парам: сумма `result_r` и сумма `net_per_lot` у каждой стороны;
  - `sandbox_fees` — число исполнений песочницы с комиссией брокера и с оценкой.
- **Ошибки** — `400 INVALID_REQUEST`, как у `…/performance`, плюс неизвестная привязка в фильтре. Нет журнала — пустой ответ `200`.

Отдельного ресурса на пару нет: элемент содержит всё, что нужно строке таблицы UI.

### 6. Настоящие комиссии из операций

`src/broker_contour/fees.py` работает внутри процесса песочницы, на каждом проходе сверщика (`reconcile_every_min`). Новой настройки нет.

1. **Ждущие исполнения** — исполнения журнала сделок контура с `fee_source <> 'broker'` и `execution_id`, начинающимся с `tinvest:`, не старше 7 дней. Нет таких — запроса нет.
2. **Операции счёта.** `GetOperationsByCursor` с самого раннего ждущего исполнения минус минута до «сейчас», состояние «исполнена», типы — покупка, продажа, комиссия брокера. Страницы — до конца курсора, не больше 10 за проход.
3. **Сопоставление.** Операция покупки или продажи содержит номера сделок биржи (`trades_info`). Исполнение `tinvest:<номер>` относится к операции с этим номером.
4. **Комиссия операции:**
   - сумма модулей операций «комиссия брокера» с `parent_operation_id`, равным номеру операции;
   - если таких нет, а операции больше 15 минут, — модуль поля `commission` операции;
   - иначе исполнение ждёт следующего прохода.
5. **Деление.** Комиссия операции делится между её сделками биржи пропорционально количеству с точностью до копейки, остаток — последней сделке операции.
6. **Поправка.** `FeeAdjustment(adjustment_id = "opfee:<источник>:<номер операции>:<execution_id>", execution_id, new_fee)` уходит в `TradeManager.consume` той же очередью, что исполнения. Поправка выпускается и при сумме, равной оценке: она меняет источник на `broker`, и исполнение больше не ждёт. Повтор после рестарта ничего не делает: ключ тот же.
7. **Устаревшие.** Исполнение старше 7 дней без комиссии брокера остаётся с оценкой. В лог один раз пишется `warning` с числом таких исполнений.

Источник в ключе показывает в журнале `cost_adjustments`, откуда взята сумма. После поправки исполнение больше не ждёт, поэтому поздняя «комиссия брокера» к нему не применяется.

**Лимиты.** Один проход — обычно один запрос раз в минуту. У песочницы 200 запросов операций в минуту, у счёта тоже 200.

**Ошибки.** Сбой запроса пишется в лог типом исключения, без текста ответа. Проход повторяется на следующей сверке. Сверку и торговлю ошибка не останавливает.

**Уведомлений нет.** Карточка в канале уже ушла с оценкой. Настоящая цифра видна в API и в `trade_summary.csv`.

Альтернатива — брать `executed_commission` из стрима или `GetOrderState`. Отвергнута по двум причинам. У заявки, порождённой стоп-заявкой, нет ответа `PostOrder`. Комиссия заявки делится на сделки биржи только оценкой. Операции — то, что брокер списал на самом деле, по каждой операции сделки.

### 7. Разведка П25–П26 в `probe-stops`

Владелец ещё не запускал `probe-stops`. Две проверки комиссий добавляются в тот же прогон, отдельного запуска нет. После покупки 2 лотов и до уборки:

| № | Проверка | «да», когда |
|---|---|---|
| П25 | Номер сделки в операции | операция покупки в `GetOperationsByCursor` содержит в `trades_info` номера сделок биржи из стрима |
| П26 | Комиссия связана с операцией | операция «комиссия брокера» с `parent_operation_id`, равным номеру операции покупки, появилась не позже 60 секунд; подробность — сумма, сумма поля `commission`, совпадают ли |

П26 `нет` не ломает решение 6: остаётся запасное правило «поле `commission` через 15 минут». Тогда в Open Questions записывается, что запасное правило основное.

### 8. API 2.10.0

`2.9.0` занят С6 в `feature/account-guards`. С7 в `feature/broker-protection` сразу берёт `2.10.0`: при слиянии веток номера не столкнутся, порядок версий сохранится. До слияния в этой ветке OpenAPI будет идти `2.8.0 → 2.10.0`.

## Risks / Trade-offs

- **[Время сигнала не совпадает с заходом в период]** → Период по времени сигнала, а не закрытия. Сделка, открытая вчера и закрытая сегодня, попадает в «вчера». Для сравнения поведения это правильнее: пара не разрывается границей периода.
- **[Ключ сигнала изменится]** → Отчёт опирается на формат `signal_id`. Тест фиксирует, что сигналы одной привязки в двух контурах дают одинаковый ключ.
- **[Разные составы]** → Сигналы привязки, которая есть в песочнице, но не в эмуляции, становятся «только в песочнице: сигнала не было». Так видно, что сравнивать не с чем, а не что песочница ошиблась.
- **[Запасная комиссия]** → Если П26 покажет, что «комиссии брокера» нет, комиссия ставится из поля операции через 15 минут. Двойного счёта нет: учитывается одна из двух.
- **[Комиссии меняют прошлые итоги]** → Итоги дня и кривая песочницы сдвигаются на разницу оценки и брокерской цифры после прихода операций. Это ожидаемо и видно по `fees_source`.

## Migration Plan

Таблиц и настроек не добавляется. Поправки комиссии пишутся в существующую `cost_adjustments`. После выката контур при первой сверке правит комиссии исполнений за последние 7 дней. Откат: поправки остаются в журнале, они верны.
