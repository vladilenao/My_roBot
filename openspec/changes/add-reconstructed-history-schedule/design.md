## Context

Путь расписания в историческом прогоне:

```
эмулятор GET /api/v1/trading-schedules (снимок прогона)
  └─ EmulatorScheduleSource.service        — разбор ответа, проверка версии дня
       └─ SnapshotScheduleStore             — непостоянное хранилище снимка
            └─ MarketCalendar
                 ├─ expectation / calendar_for  → ожидание свечей, сверка покрытия,
                 │                                 проверка правых границ, графики
                 ├─ calendar_for (run.py _session_calendar_provider)
                 │                               → сессионная защита TradeManager
                 └─ usage()                      → раздел расписания в отчёте
```

Ответ эмулятора (после доработки):

```json
{
  "instrument_id": "98937d66-…", "exchange": "forts_futures_weekend",
  "binding_provenance": "reconstructed", "snapshot_generation": 13729788,
  "days": [{"trading_date": "2025-03-27", "version": "…", "is_trading_day": true,
            "source": "emulator-reconstructed", "provenance": "reconstructed",
            "rules_version": "forts_futures_weekend/1", "day": { /* TradingDay */ }}],
  "missing_dates": []
}
```

`provenance` бывает `my_robot_export` (день из ленты робота, наблюдённый у брокера) или `reconstructed`. Версия восстановленного дня — тот же sha256 канонического JSON `TradingDay`. Проверка: все 650 дней `forts_futures_weekend/1` проходят `_sdk_day` → `day_version` без расхождений.

Восстановленные окна 2025 года отличаются от текущих: утренней сессии нет, основная 09:00–18:49:59, вечерняя 19:05–23:50, сессии выходного дня с 2025-08-16. При настройках по умолчанию рубеж входа — 17:50, закрытие — 18:30 МСК.

## Goals / Non-Goals

**Goals:**
- Внутридневные стратегии торгуют в историческом прогоне по восстановленному расписанию по тем же правилам, что в live.
- Восстановленный день не становится доказательством там, где сейчас доказательство даёт только расписание брокера.
- Из отчёта прогона сразу видно, по какому расписанию шли решения и какие стратегии не торговали и почему.

**Non-Goals:**
- Изменения эмулятора, live-режима, схем БД, подсчёта разрывов. Остановка прогона без расписания.

## Decisions

### D1. Происхождение дня и привязки

Внутри робота у дня два значения: `broker` (в ответе эмулятора `my_robot_export`) и `reconstructed`.

| Ответ эмулятора | Результат |
|---|---|
| поля `provenance` нет | `broker` (старый эмулятор отдавал только ленту робота) |
| `my_robot_export` | `broker` |
| `reconstructed` и непустой `rules_version` | `reconstructed` |
| `reconstructed` без `rules_version` или другое значение | день отвергается; страница не применяется, ошибка источника `schedule_unavailable: …` |

Так же разбирается `binding_provenance` (нет поля → `broker`). Версия дня по-прежнему сверяется с `day_version`. Происхождение в версию не входит: эталонный восстановленный день может совпадать с брокерским побайтно, и это нормально.

### D2. Хранение

`StoredScheduleDay` получает поля `provenance: str = "broker"` и `rules_version: str | None = None`. `SnapshotScheduleStore.record_schedule_day` и `record_schedule_binding` принимают их с теми же значениями по умолчанию. `MarketDataStore` и схема `market-data.sqlite3` не меняются: live пишет только брокерские дни, а восстановленные живут только в непостоянном хранилище снимка. `CalendarDay` получает те же два поля (по умолчанию `broker`/`None`), `_calendar_day` переносит их из записи.

### D3. Два вида календаря

`MarketCalendar.calendar_for(uid, now, *, include_reconstructed=False)` и `calendar(exchange, now, *, include_reconstructed=False)`:

- **по умолчанию** — только `broker`-дни. Ожидание свечей, `MarketReconciler` (`scheduled_closed`, `interval_state`, `stored_calendars`), проверка правых границ и представление графиков получают ровно то же, что сейчас;
- **`include_reconstructed=True`** — `broker`-день, а если его нет, `reconstructed`-день той же даты. Использует только `_session_calendar_provider` в `run.py`, и только когда `[historical.schedule].use_reconstructed = true`.

Почему восстановление включается явно, а не исключается из доказательств: потребителей-доказательств много (ожидание, сверка, графики, границы), а сессионная защита одна. Новый потребитель по умолчанию получит безопасный вид. Кроме того, восстановленный день построен по тем же барам, которые он проверял бы, — доказательство было бы круговым.

Привязка UID → режим торгов с `binding_provenance = reconstructed` используется обоими видами: она указывает, где искать расписание, а не доказывает отсутствие свечей. Если в доказательном виде у режима только восстановленные дни, календарь пуст, и прежние правила неизвестной фазы действуют как сейчас.

### D4. Сессионная защита

Решения D4–D8 изменения `add-intraday-session-guard` не меняются: восстановленный день применяется как известный. Неторговый восстановленный день по-прежнему даёт `session-schedule-unknown` (как неторговый день брокера). Трасса `session.intraday` получает `algorithm_version = "2"` и входы:

- `schedule_provenance` (`broker` | `reconstructed` | `null`, если дня нет);
- `schedule_rules_version` (строка или `null`).

### D5. Выключатель

```toml
[historical.schedule]
use_reconstructed = true   # восстановленное расписание эмулятора для сессионной защиты
```

Строгие ключи, `ConfigError` с файлом и ключом. При `false` восстановленные дни не попадают ни в один вид календаря, но учитываются в отчёте как «восстановлено, не использовалось». Значение пишется в отчёт.

### D6. Предварительная загрузка и предупреждение

После закрепления снимка и построения цепочки контрактов прогон запрашивает расписание каждого UID цепочки на диапазон `[начало − 7 дн, конец + 7 дн]`. Запросы идут кусками не длиннее 366 дней — это предел эмулятора. Ответы ложатся в то же хранилище снимка, что и при ленивой загрузке, и закрывают её диапазоны (`_loaded`), так что ленивые запросы на тиках не повторяются. Ошибка предзагрузки не прерывает прогон: даты остаются для ленивой загрузки, причина пишется в лог.

Затем считаются торговые даты диапазона для каждого UID по участкам цепочки: с подтверждённым днём, с восстановленным, без расписания. Если `[trading.intraday].enabled` и у внутридневных привязок (таймфрейм ≤ `max_timeframe`) есть даты без применимого дня с учётом выключателя D5, в консоль и `bot_debug.log` (уровень WARNING) выводится:

```
⚠ Расписание торгов: 141 дата без расписания (2025-03-10 — 2025-09-10).
  Внутридневные входы в эти даты будут отклонены: future-br-macd (5m), future-br-ma (15m).
```

Прогон продолжается. Если расписание есть везде, выводится одна строка INFO: подтверждено N, восстановлено M, версии правил.

### D7. Отчёт: расписание

`MarketCalendar.usage()` и `CalendarScheduleMetadata` дополняются:

- `day_versions` — кортежи `(exchange, date, version, provenance)`;
- `provenance_counts` — `{"broker": n, "reconstructed": m}` по использованным дням;
- `rules_versions`, `binding_provenance` по режимам;
- `use_reconstructed`.

В тексте отчёта даты без расписания выводятся диапазонами подряд идущих дат (`2025-03-10 — 2025-03-14, 2025-03-17 …`), а не 141 датой в строку.

### D8. Отчёт: сигналы и недопуски по стратегиям

Не каждый недопуск попадает в трассу: например, `contract-expiring` и `no-contract-metadata` возвращаются без записи. Поэтому счёт ведётся не по `calculations`, а в одной точке, где бот получает `SignalAdmission`: в историческом цикле, после `actions_for_signal`.

Накопитель прогона `SignalAdmissionStats` хранит по `assignment_id`:
- множество `signal_id`;
- коды первого недопуска каждого сигнала;
- число сигналов, давших действие.

Повторное рассмотрение того же `signal_id` не считается дважды. Сделки берутся из журнала. В отчёт идут таблица (привязка, таймфрейм, сигналов, сделок, недопуски «код — число — русский текст» по `rejection_message`) и предупреждение:

```
⚠ future-br-macd: 0 сделок — 845 из 845 сигналов отклонены: расписание торгов неизвестно.
```

Предупреждение выводится, если у привязки нет сделок и не меньше половины её сигналов отклонено с `session-schedule-unknown`. Машиночитаемый отчёт содержит ту же структуру без русских текстов.

## Risks / Trade-offs

- **Восстановленные окна могут быть неточны** (сокращённые дни, разовые изменения режима). Это влияет только на сессионную защиту в истории и видно по версии правил в трассе и отчёте. Если результат сомнителен, его можно сравнить с прогоном при `use_reconstructed = false`.
- **Неверное восстановление выходных.** Сессии выходного дня в правилах — по режиму торгов, а не по инструменту. Инструмент без баров в такой выходной сигналов не даст, так что лишних входов это не создаёт.
- **Предзагрузка увеличивает старт** на несколько запросов на контракт; на тиках запросов становится меньше.

## Migration Plan

Схемы не меняются. Со старым эмулятором (без `provenance`) всё ведёт себя как сейчас. Откат: `use_reconstructed = false`, полностью — откат изменения.
