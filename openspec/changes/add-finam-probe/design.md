## Context

- Робот торгует на реальном счёте Т-Инвест контуром «Счёт» (`src/broker_contour/`, исполнитель `TInvestBroker`, адаптер `TInvestApi`). Свечи и анализ — у ядра на `TINKOFF_TOKEN`.
- Финам подключается вторым реальным брокером отдельным контуром `finam`. Финам только исполняет: свечей и анализа у него робот не берёт.
- Finam Trade API 2.24.0 — gRPC на `api.finam.ru:443` (TLS), REST-шлюз к тем же методам. Официальный репозиторий `github.com/FinamWeb/finam-trade-api` (релиз 2.24.0, коммит `c66614f`, 16.11.2026) содержит proto и Python SDK `finam-sdk`.
- Доступ: секрет с портала (`tradeapi.finam.ru`, страница «Токены») → `AuthService.Auth` → JWT около 15 минут; JWT передаётся в метаданных `authorization` каждого вызова. `SubscribeJwtRenewal` — стрим новых JWT по секрету.
- По `.ai/skills` официального репозитория демо-счёт открывается на той же странице токенов, живёт 2 недели и «работает так же, как реальный» — это надо проверить, а не принять на веру.
- Образец — разведка песочницы Т-Инвест (`openspec/changes/archive/2026-10-29-add-sandbox-probe`, `src/sandbox/`): шлюз как единственная точка входа, записи вызовов, проверки с итогами «да / нет / не проверено / ошибка», уборка в любом случае.

Что известно из proto 2.24.0 и важно для разведки:

| Тема | Что в proto | Что остаётся выяснить |
|---|---|---|
| Заявка | `Order`: `symbol`, `quantity` (Decimal, «шт.»), `side`, `type` (MARKET/LIMIT/STOP/STOP_LIMIT/MULTI_LEG), `time_in_force`, `limit_price`, `stop_price`, `stop_condition` (LAST_UP/LAST_DOWN), `client_order_id` (≤20), `valid_before` (END_OF_DAY/GOOD_TILL_CANCEL; GOOD_TILL_DATE только у SL/TP), `comment` (≤128) | единицы цены и количества, повтор ключа |
| Состояние заявки | `OrderState`: `order_id`, `exec_id`, `status` (30 значений, в том числе WATCHING, EXECUTED, SL_*/TP_*), `order` (эхо заявки), `transact_at`/`accept_at`/`withdraw_at`, `initial/executed/remaining_quantity` (только у биржевой), `triggered_order_id`, `status_description` | какие статусы на деле у стопа, номер порождённой заявки |

| Сделка | `AccountTrade`: `trade_id`, `order_id`, `price`, `size` («шт.»), `commission` «заполняется для исторических сделок», `currency` может быть пустой в стриме | есть ли комиссия у свежей сделки |
| Транзакция | `Transaction`: `transaction_category` (COMMISSION и др.), `change` (рубли), `trade` (size, price за штуку), `symbol` | как связать комиссию со сделкой — общего номера в proto нет |

| Инструмент | `GetAsset`: `lot_size`, `min_step` + `decimals`, `price_step`, `future_details.contract_size`, `expiration`; `GetAssetParams`: `is_tradable`, `longable`/`shortable`, `long/short_initial_margin`, `trade_lot_size`, риск-ставки | **стоимости шага цены в API нет**; границ цены (аналог limit up/down) нет |

## Goals / Non-Goals

**Goals:**

- Ответить на вопросы а–к фактом, полученным от API, а не из документации.
- Записать настоящие ответы API для будущего фейкового шлюза Ф1–Ф3.
- Ни одной сделки на реальном счёте без явного действия владельца; заявки разведки не исполняются по построению.

**Non-Goals:**

- Порт брокера, контур `finam`, адаптер заявок — Ф1–Ф3.
- Сравнение Финама с Т-Инвест по сделкам, перенос привязок — Ф4.
- Telegram, API робота, UI, дистрибутив: команда пишет только в консоль и файлы и запускается из исходников.
- Свечи и рыночные данные Финама для анализа: анализ остаётся у ядра на Т-Инвест.
- SL/TP-заявки (`PlaceSLTPOrder`) и мульти-лег: при надобности — отдельной разведкой на Ф3.

## Decisions

### 1. gRPC-заглушки из официальных proto, без новой зависимости

Заглушки генерируются из proto релиза 2.24.0 и кладутся в `src/finam/proto/` как код: `grpc/tradeapi/v1/*` и то, что они импортируют, — `google/api/{annotations,http}`, `google/type/{decimal,date,interval,money}`, `grpc/gateway/protoc_gen_openapiv2/options/*`. В заголовке каждого файла и в `src/finam/proto/VERSION` — версия proto, коммит официального репозитория и версия генератора. Импорты корней `grpc.tradeapi`, `grpc.gateway`, `google.api`, `google.type` переписываются на `src.finam.proto.…`: иначе `grpc.tradeapi` спорит с пакетом `grpc`, а `google.api` / `google.type` требуют `googleapis-common-protos`, которого в окружении нет. `google.protobuf` берётся из рантайма protobuf. Перегенерация — `python tools/finam_proto.py <checkout> --version 2.24.0`.

Проверено 23.11 в `.venv`: `grpcio-tools 1.81.1` (уже стоит как зависимость `iprotopy` ← `t-tech-investments`) генерирует код protobuf 6.33.5; он импортируется рядом с `t_tech.invest` при `protobuf 6.33.6` и `grpcio 1.83.0` и собирает сообщения. Сгенерированный код требует `grpcio ≥ 1.81.1` и `protobuf ≥ 6.33.5, < 7`; `t-tech-investments 1.49.3` разрешает `protobuf ≥ 6.31.1, < 7` и `grpcio ≥ 1.75`. Чтобы чистая установка не взяла слишком старые версии, в `requirements.txt` добавляются нижние границы `grpcio>=1.81.1` и `protobuf>=6.33.5,<7` — это не новые пакеты, а уточнение уже стоящих (**нужно согласие владельца**).

Отклонённые варианты:

- Официальный SDK `finam-sdk 2.24.0` — требует `protobuf ≥ 7.35.1`, а `t-tech-investments` держит `protobuf < 7`: в одном окружении они не уживаются. Плюс новая зависимость и чужая логика повторов, которая прячет то, что разведка должна увидеть.
- REST через `requests` — работает, но стримов (`SubscribeOrders`, `SubscribeJwtRenewal`) у REST нет, а именно их поведение — часть вопросов г, д и ж. Контур на Ф3 всё равно пойдёт по gRPC.

### 2. Шлюз Финама — единственная точка входа

`src/finam/gateway.py`, `FinamGateway`:

- один TLS-канал на `api.finam.ru:443`, другого адреса нет;
- `Auth(secret)` при входе; JWT передаётся в метаданных `authorization` каждого вызова; без признака возраста JWT старше 10 минут шлюз перед вызовом получает новый `Auth`. `probe-jwt` отключает обновление, чтобы увидеть истечение;
- каждый полученный JWT сразу идёт в `register_secrets`; в записи и лог JWT не попадает, вместо него — `jwt#N` (номер выдачи);
- срок каждого унарного вызова 30 секунд (`timeout`);
- `RESOURCE_EXHAUSTED` повторяется до трёх раз только у методов чтения (пауза — `grpc-retry-pushback-ms` из ответа, иначе 1, 2, 4 с). `PlaceOrder` и `CancelOrder` не повторяются: повтор ключа — предмет разведки, а не скрытое поведение шлюза. `probe-limits` повторы выключает;
- ошибка gRPC → `BrokerCallError` (из `src.sandbox.gateway`) с кодом и `details()` брокера; номер счёта в описании маскируется, объект исключения не печатается и не логируется.

Шлюз — заготовка для адаптера Ф1–Ф3: порт брокера получит такой же шлюз.

### 3. Счёт и токен: реальный и демо

- Реальный: `FINAM_SECRET_TOKEN` и `FINAM_ACCOUNT_ID`.
- Демо (`--demo`): `FINAM_DEMO_SECRET_TOKEN` и `FINAM_DEMO_ACCOUNT_ID`; если демо-счёт выдан тем же секретом, `FINAM_DEMO_SECRET_TOKEN` можно не задавать — берётся `FINAM_SECRET_TOKEN`.
- Перед любым действием `TokenDetails` должен перечислить выбранный номер счёта среди `account_ids` токена; иначе — код 1 и список номеров последними четырьмя символами. Токен с `readonly = true` запрещает `probe`, `probe-stops`, `probe-trigger` и `cleanup` до сети заявок (код 2).
- Все четыре значения — в `secrets=` логирования `run.py` и команды. Номер счёта в выводе и отчёте — `mask_account` (`…1234`), в `responses.jsonl` — `finam-account` / `finam-demo-account`.

### 4. Имена инструментов — как в роботе, сопоставление через справочник Т-Инвест

Владелец пишет инструмент так же, как в эмуляции и в команде песочницы: тикер акции, короткое имя контракта (`NG-12.26`) или код семейства (`NG` → ближайший контракт). Имя разрешается существующим `resolve_instrument` через справочник Т-Инвест на `TINKOFF_TOKEN` (только чтение, `instruments.*` и `market_data.get_last_prices`): так получаются биржевой тикер, лот, шаг, стоимость шага и ГО карточки Т-Инвест для вопроса б. Символ Финама ищется в `Assets` по биржевому тикеру (`ticker`, не архивный); найденные кандидаты пишутся в записи, а выбор — по совпадению тикера и площадке Московской биржи. Без `TINKOFF_TOKEN` принимаются только акции (`SBER` → поиск `SBER` в `Assets`), а сравнение с карточкой Т-Инвест получает «не проверено».

По правилу проекта биржевой тикер фьючерса и полный `symbol` Финама в консоль и `report.md` не выводятся: там короткое имя и площадка (`Si-12.26: символ найден, площадка RTSX`). Полный `symbol` — только в `responses.jsonl`, откуда он попадёт в «Факты разведки» как формат.

Ответ `Assets` большой: в записи идёт сводка (число инструментов, найденные кандидаты), а не весь список.

### 5. Действия и проверки

Номера проверок — `Ф0.N`, буква в скобках — вопрос, на который проверка отвечает.

**`account [инструменты…] [--days N] [--demo]`** — только чтение. По умолчанию инструменты `Si BR NG GOLD SBER`, `--days 30`.

| № | Проверка | Что печатается и пишется |
|---|---|---|
| Ф0.1 | Токен (а, ж) | JWT получен; `TokenDetails`: `created_at`, `expires_at` и срок жизни, `readonly`, права на рыночные данные, номера счетов (маска), выбранный счёт среди них |
| Ф0.2 | Счёт (а, в, к) | `GetAccount`: тип, статус, `equity`, `unrealized_profit`, `cash`, вид портфеля и его поля, позиции (имя, `quantity`, `average_price`, `current_price`, `maintenance_margin`) |
| Ф0.3 | Заявки (г, д) | `GetOrders`: все заявки — `client_order_id`, статус, тип, сторона, количество, цены, время, `triggered_order_id`; самая старая заявка в ответе |
| Ф0.4 | Сделки (в, е) | `Trades` за `--days`: число, цена и размер, есть ли `commission`, `order_id` |
| Ф0.5 | Транзакции (е) | `Transactions` за `--days`: число по категориям, комиссии рядом со сделками по времени и инструменту |
| Ф0.6 | Инструменты (б, и) | по каждому: символ найден, площадка; `GetAsset` (лот, шаг, `contract_size`, экспирация) и `GetAssetParams` (торгуется, лонг/шорт, ГО лонг/шорт, `trade_lot_size`) рядом с карточкой Т-Инвест: лот и шаг совпали или нет, стоимость шага у Финама — «нет в API», ГО Финама против ГО Т-Инвест |
| Ф0.7 | Цены (в) | `LastQuote` (last, bid, ask, время) и верх `OrderBook` рядом с последней ценой Т-Инвест: одна шкала или нет |
| Ф0.8 | Расписание (и) | `Schedule` по каждому: типы сессий и интервалы на ближайшие дни (вечерняя, выходного дня); `Clock` |
| Ф0.9 | Лимиты (з) | `GetUsageMetrics`: квоты, лимит, остаток, время сброса |

**`probe [инструмент] [--offset-pct 3] [--demo]`** — одна лимитная заявка на покупку 1 лота далеко от рынка. Инструмент по умолчанию — `NG`. У акции количество — `lot_size` из `GetAsset` (один лот в штуках), у фьючерса — 1; как брокер повторит это число в `initial_quantity` и позиции, отвечает на «штуки или лоты».

| № | Проверка | «да», когда |
|---|---|---|
| Ф0.10 | Стримы открыты | `SubscribeOrders`, `SubscribeTrades` и `SubscribeOrderTrade` открыты в своих потоках до первой заявки |
| Ф0.11 | Ошибочная заявка с ключом K1 (г) | заявка с ценой не по шагу (на полшага ниже) с `client_order_id = K1` отклонена; подробность — код и описание. Если принята — снимается сразу, итог «нет» |
| Ф0.12 | Тот же K1 после ошибки (г) | правильная заявка с K1 принята. Если отказ из-за ключа — заявка ставится с новым ключом K2, итог «нет» с ответом брокера |
| Ф0.13 | Поиск по ключу (г, в) | заявка с нашим ключом найдена в `GetOrders`, `GetOrder` по `order_id` отдал её же; подробность — статус, эхо `quantity` и `limit_price`, `initial_quantity` |
| Ф0.14 | Повтор ключа после приёма (г) | повтор `PlaceOrder` с тем же ключом не создал вторую активную заявку; подробность — что ответил брокер. Вторая заявка, если появилась, снимается сразу |
| Ф0.15 | События стримов (г) | событие о заявке пришло не позже 30 с; подробность — номер заявки в первом событии против номера из `PlaceOrder`, статусы событий по порядку |
| Ф0.16 | Снятие | после `CancelOrder` статус «снята», событие в стриме не позже 30 с |
| Ф0.17 | Снятая видна (г) | снятая заявка осталась в `GetOrders`, с каким статусом и временем снятия |
| Ф0.99 | Уборка | активных заявок разведки по инструменту нет |

Цена заявки — последняя цена минус `--offset-pct` процентов, вниз к шагу. Если брокер отклонил её как цену вне допустимых границ, это записывается в подробность (вопрос и), и заявка ставится один раз с половинным отступом. Заявка живёт секунды и стоит ниже рынка: исполниться она не должна; если всё же исполнилась (частично или полностью), разведка останавливается с итогом «ошибка» и печатает, что на счёте появилась позиция, — закрывать её разведка не будет, решает владелец.

**`probe-stops [инструмент] [--offset-pct 10] [--side buy|sell] [--keep] [--demo]`** — стоп-заявка 1 лот далеко от рынка: по умолчанию покупка `LAST_UP` на 10% выше последней цены, `valid_before = GOOD_TILL_CANCEL`.

| № | Проверка | «да», когда |
|---|---|---|
| Ф0.20 | Стоп-заявка принята (д) | `PlaceOrder` с `ORDER_TYPE_STOP` принят; подробность — статус и номер в ответе |
| Ф0.21 | Видна в `GetOrders` (д, в) | найдена по ключу; подробность — тип, статус, эхо `stop_price`, `stop_condition`, `valid_before`, заполнены ли `initial_quantity`, `triggered_order_id` |
| Ф0.22 | `GetOrder` по номеру (д) | отдал ту же стоп-заявку |
| Ф0.23 | Повтор ключа стоп-заявки (г) | вторая стоп-заявка не появилась; подробность — ответ брокера |
| Ф0.24 | События стримов (д) | что пришло о стоп-заявке в каждый стрим |
| Ф0.25 | Снятие (д) | при `--keep` — «не проверено», стоп оставлен; иначе статус «снята», видна в `GetOrders` |

С `--keep` стоп остаётся на ночь и выходные: владелец смотрит его через `account` утром и после выходных, затем снимает `cleanup`.

**`probe-trigger [инструмент] [--ticks 1] [--side buy|sell] [--wait 15] [--real] [--demo]`** — единственное действие, которое совершает сделку. Перед первой заявкой печатает, что будет сделано (стоп на N шагов от рынка, покупка или продажа 1 лота при срабатывании, затем закрытие позиции по рынку, примерная стоимость комиссии неизвестна), и ждёт ввода `ДА`; любой другой ввод — код 2 без заявок. Без `--demo` требует ещё и `--real`, иначе код 2 до сети. Проверки:

| № | Проверка | «да», когда |
|---|---|---|
| Ф0.30 | Стоп у рынка принят (д) | стоп на `--ticks` шагов от последней цены принят |
| Ф0.31 | Срабатывание (д) | за `--wait` минут статус изменился; подробность — последовательность статусов с временем, `triggered_order_id`. Цена не дошла — «не проверено», стоп снимается |
| Ф0.32 | Порождённая заявка (д) | `GetOrder(triggered_order_id)` нашёл биржевую заявку; её тип, статус, исполненный объём; события стримов о ней |
| Ф0.33 | Сделка и единицы (в, е) | сделка в стриме и в `Trades`: цена (пункты или рубли), размер, комиссия сразу и через минуту |
| Ф0.34 | Позиция (в, к) | позиция в `GetAccount`: `quantity`, цены, `maintenance_margin`, изменение `cash`, `equity`, `available_cash` |
| Ф0.35 | Закрытие | рыночная заявка в обратную сторону на тот же объём исполнена, позиция инструмента вернулась к исходной |
| Ф0.36 | Комиссия в транзакциях (е) | через 60 с в `Transactions` есть комиссия по инструменту в момент сделок; подробность — как её связать со сделкой |

Уборка выполняется всегда: снять стоп и порождённые активные заявки разведки, а позицию закрыть только на тот объём, который открыла разведка (сравнение с позицией до первой заявки).

**`probe-jwt [--minutes 20] [--demo]`** — только чтение. Один `Auth`, обновление выключено. Открывает `SubscribeOrders` со старым JWT и `SubscribeJwtRenewal` с секретом. Раз в минуту `GetAccount` со старым JWT. Проверки: Ф0.40 срок жизни JWT по `TokenDetails`; Ф0.41 когда приходят новые JWT в `SubscribeJwtRenewal` и их срок; Ф0.42 когда унарный вызов со старым JWT получает отказ и с каким кодом; Ф0.43 что стало со стримом на старом JWT (закрыт с кодом, молчит или живёт).

**`probe-limits [--calls 250] [--demo]`** — только чтение. `GetUsageMetrics`, затем подряд `Clock` без повторов до первого отказа или `--calls` вызовов, затем снова `GetUsageMetrics`. **`cleanup [--demo]`** — снимает активные заявки и стоп-заявки, у которых `client_order_id` начинается с префикса разведки `fp`. Чужие заявки не трогает и перечисляет их числом. Позиции не закрывает.

### 6. Ключи заявок разведки

`client_order_id` = `fp` + время UTC в base36 + 6 случайных символов base36, всего не больше 20 символов. Префикс отделяет заявки разведки от ручных заявок владельца — на нём держится `cleanup`.

### 7. Ход разведки и уборка

Как у песочницы: проверка получает «да», «нет», «не проверено» или «ошибка»; «нет» — ответ разведки, а не сбой. Проверки, зависящие от проваленной, получают «не проверено» с причиной. Перед заявками — `Schedule` и `LastQuote`: если торги по инструменту не идут или последней цены нет, заявок нет, код 1. Уборка (Ф0.99 и её аналоги) выполняется всегда, когда была хотя бы одна заявка, в том числе после исключения и Ctrl+C, и снимает только заявки с ключами этого запуска: всё с префиксом `fp` снимает лишь `cleanup` по команде владельца.

Стримы — в потоках-демонах с очередью событий; разведка ждёт событий до 30 с. Стримы закрываются отменой вызова в конце.

### 8. Записи и отчёт

Каталог `data/finam/<действие>-ГГГГММДД-ЧЧММСС/` (UTC):

- `responses.jsonl` — строка на вызов и на сообщение стрима: время, метод, запрос, ответ (`MessageToDict` с именами полей proto) или код и описание ошибки с ключами метаданных ответа об ошибке, длительность. Секрет, JWT и номер счёта заменяются (`[secret]`, `jwt#N`, `finam-account`) до записи строки; JWT из ответов `Auth` и `SubscribeJwtRenewal` и прочие номера счетов токена (`account-…XXXX`) становятся секретами до записи ответа, в котором пришли. Метаданные запроса не пишутся.
- `report.md` — действие, параметры, время начала и конца, таблица «проверка, итог, подробность».

Отчёт печатается в консоль вместе с путём к каталогу и пишется и после сбоя. Лог команды — `data/finam/finam.log` с маскированием секретов.

### 9. Коды выхода

0 — действие выполнено (у разведки — дошла до отчёта), 1 — не выполнено из-за ответа брокера или сети, 2 — ошибка запуска (нет секрета или номера счёта, неверные параметры, неизвестное имя, нет подтверждения).

## Risks / Trade-offs

- [Реальный счёт] → `probe` и `probe-stops` не исполняются по построению (лимит ниже рынка на секунды, стоп в 10% от рынка); единственная сделка — `probe-trigger` с вводом `ДА` и `--real`. Рекомендованный порядок — сначала демо, потом реальный.
- [Стоп с `--keep` на ночь может сработать на сильном движении] → по умолчанию 10% от рынка и 1 лот; владелец снимает его `cleanup` сразу после проверки утром. Сработавший стоп откроет позицию в 1 лот — это видно в `account`.
- [ГО под лимитную и стоп-заявку] → на реальном счёте нужны свободные деньги под 1 лот; при нехватке брокер откажет, и это тоже факт для вопроса и.
- [Демо может отличаться от реального] → `probe` и `probe-stops` прогоняются на обоих; различия записываются в «Факты разведки».
- [Демо живёт 2 недели] → для стенда Ф3 это значит переоткрытие демо и новый номер счёта; проверим на деле.
- [`probe-limits` может дать временную блокировку] → вызовы только `Clock`, не дальше первого отказа, запускать вне торговли роботом.
- [Сгенерированные `google.api` / `google.type` в нашем пространстве имён] → если в окружении появится `googleapis-common-protos` и оба набора загрузятся в один процесс с разным содержимым, пул дескрипторов protobuf откажет. Сейчас пакета нет; если он появится — перегенерировать заглушки с импортом из него.
- [Официальный SDK держит `protobuf ≥ 7`] → когда `t-tech-investments` перейдёт на protobuf 7, вопрос «свои заглушки или `finam-sdk`» вернётся к Ф1.

## Open Questions

- Согласие владельца на нижние границы `grpcio>=1.81.1` и `protobuf>=6.33.5,<7` в `requirements.txt` (решение 1).
- Демо выдаётся отдельным секретом или тем же — узнаем при выпуске токена (решение 3 поддерживает оба случая).
