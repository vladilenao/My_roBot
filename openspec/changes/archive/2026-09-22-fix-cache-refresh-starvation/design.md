## Context

Мотивация и требования — в `proposal.md` и дельте `specs/data-cache/spec.md`.
Корень проблемы (воспроизведён на HEAD v4.1.0, работающий код + тест-скаффолд):

- `MarketDataCache.refresh_if_new_candle(timeframe, force=True)` (cache.py:115)
  применяется в цикле `wait_until_bar_published` (timing.py:317) при ожидании бара,
  который публикуется с задержкой.
- Кэш хранит по одному кадру на пару «инструмент — ТФ» (`self._frames`), вставка
  идёт в порядке первого обращения (`frame_for`/`_initial_load`).
- `_load` (cache.py:50) в начале сама выставляет глобальный страж
  `self._last_api_attempt`. Значит за одно окно `data_refresh_min_interval`
  физически успевает выполниться только один API-вызов.
- Текущий цикл идёт по кадрам в порядке вставки: первый кадр (не троттлится)
  дозагружается, следующие упираются в `_throttled` и **помечаются**
  `_observed[key] = boundary` и переходят дальше (cache.py:138–140). При
  `force=True` `_observed` игнорируется, поэтому каждый следующий цикл повторно
  дозагружает **тот же первый кадр**, а остальные кадры этого ТФ никогда не
  обновляются («голодание»).
- `has_fresh_closed_bar` (жёсткий AND либо терпимый гейт) требует свежего бара у
  всех активных пар ТФ → из-за одного «голодающего» кадра готовность ТФ не
  наступает, `wait_until_bar_published` возвращает пустой набор кандидатов, тик
  молча простаивает. В проде после бара 11:15 анализы 15m 11:30/11:45 не вышли
  (заморозка ~46 минут).

## Goals / Non-Goals

**Goals:**

- Повторяющаяся (форс-)дозагрузка ТФ распределяет `data_refresh_min_interval`
  между ВСЕМИ кадрами таймфрейма: каждый кадр с данными получает обновление за
  ограниченное число окон ожидания (≤ числа кадров).
- Приоритет у самого отстающего кадра; свежие кадры не перезапрашиваются
  вхолостую (лимит не тратится).
- Кадр, пропущенный из-за интервального лимита, НЕ помечается обновлённым для
  текущей границы.
- Существующее поведение одиночного кадра, `force=False`, rate-limit паузы
  (`_retry_after`) и bounded backfill не меняется.

**Non-Goals:**

- Переработка `has_fresh_closed_bar`, его терпимости и конфигурации — не в scope.
- Изменение `data_refresh_min_interval` (остаётся 5с по умолчанию, `config.py:55`).
- `ensure_loaded` (дозагрузка неактивных ТФ) — другая ветка, по одному кадру,
  голодания не создаёт; не трогаем.
- Смена ритма/сеток/планировщика.

## Decisions

**D1 — Порядок дозагрузки: от самого отсталого кадра к свежему.**

Цикл `refresh_if_new_candle` перестраивается:

1. Собрать кандидатов — кадры этого ТФ, ещё не отслеженные для текущей границы
   (при `force` — все кадры с данными). Кадры `None`/пустые по-прежнему
   помечаются `_observed = boundary` и пропускаются (нечего дозагружать).
2. Отсортировать кандидатов по возрастанию «устаревания»: самый старый последний
   закрытый бар — первый (`datetime.min`, если закрытых баров нет вовсе — впереди
   всех). Сортировка детерминирована ключом кадра.
3. Идти по кандидатам по порядку. Как только вызов упирается в `_throttled` —
   **немедленно вернуться, ничего не помечая** (this — главное изменение). После
   успешной дозагрузки кадр помечается `_observed = boundary`; следующий кадр
   списка в этом же вызове упрётся в только что выставленный `_last_api_attempt`
   и завершит вызов. За одно окно физически выполняется ≤ 1 API-вызов.

Гарантия сходимости: каждое открытое окно дозагружает самый отстающий кадр;
после его загрузки он становится не старше остальных недозагруженных, и в
следующем окне выбирается следующий по устареванию. Число окон до готовности всех
`N` кадров ≤ `N`.

Почему не круговая ротация (курсор): столько же окон сходимости, но ротация не
учитывает реальное устаревание и при забравшемся вперёд кадре тратит лимит
впустую; сортировка по устареванию дешевле и детерминирована, пригодится и
`force`, и обычному тику.

**D2 — Троттлированный кадр не помечается обновлённым.**

Убран `self._observed[key] = boundary` в ветке `_throttled` (cache.py:138–140):
кадр, которому не достался API-слот, остаётся кандидатом на следующее окно.
Это и устраняет «ложную обработку» в цикле: раньше все кадры, кроме первого,
помечались отслеженными, но данными так и не обновлялись.

**D3 — Свежие кадры не перезапрашиваются без явного skip.**

Отдельной ветки «пропустить свежий» нет: при `force` цикл терминируется гейтом
`has_fresh_closed_bar` (все кадры свежие → повторных вызовов нет), а пока хоть
один кадр отстаёт, самым отстающим будет именно он, и лимит уходит ему. Так
сохраняется сегодняшняя семантика одиночного кадра (`test_force_reload_throttled_within_interval`
остаётся зелёным: единственный кадр при `force` в открытом окне обязан
дозагрузиться).

**D4 — Rate-limit в цикле завершает вызов.**

При `RESOURCE_EXHAUSTED` ветка ставит `_retry_after` и возвращает управление
(вместо прежнего `continue`): продолжать перебор в этом же вызове бессмысленно —
страж `_last_api_attempt` уже выставлен, а `_retry_after` всё равно вернёт из
следующего вызова раньше. Семантика паузы не меняется.

**D5 — `_load` обновляет `_last_api_attempt` сама — не трогаем.**

Единая точка троттлинга остаётся в `_load` (cache.py:50): она же обслуживает
`_initial_load`, `ensure_loaded` и выборку. Логика честного распределения живёт
только в упорядочивании кандидатов и раннем выходе из `refresh_if_new_candle`.

## What Changes

- `src/data/cache.py`, `refresh_if_new_candle` (cache.py:115):
  - сбор кандидатов с сортировкой «самый отсталый первый»;
  - ветка `_throttled` → ранний `return` без записи в `_observed`;
  - ветка rate-limit → установка `_retry_after` и `return` вместо `continue`;
  - обновить docstring метода (честное распределение окон между кадрами ТФ).
- `tests/unit/data/test_cache.py`:
  - `test_force_fairly_refreshes_all_frames_across_windows` — 3 пары на 1h, поздно
    опубликованные бары; каждое открытое окно дозагружает следующий по порядку;
    готовность наступает в пределах N окон;
  - `test_throttled_frame_not_marked_observed` — при `force` в закрытом окне
    `_observed` кадров не меняется, API не дёргается; после открытия окна
    дозагружается самый отстающий кадр;
  - `test_refresh_prioritizes_most_stale_frame` — отстающий кадр (данные ещё не
    обновлены) перезапрашивается, а свежий кадр в цикле не трогается.
- Без изменений: конфигурация, `has_fresh_closed_bar`, `ensure_loaded`,
  планировщик, run.py, внешний API кэша.

## Rollout / Verification

Поведенческое изменение: увеличивается число повторных дозагрузок (перераспределение
текущего лимита, а не новые запросы). Серьёзных рисков API-лимита нет — количество
запросов в окне то же (≤ 1). После вливания и релиза (per AGENTS.md) готовность ТФ
в проде не должна зависать на одном кадре; признак устранения — плановые анализы
15m/1h выходят во всех окнах без 46-минутной заморозки, в логе нет периодов
«GetCandles без анализов».
