## Context

Текущий экспорт событий уже преобразует UTC в МСК, сырой тикер в короткое имя и машинный статус в русскую фразу, но публикует только девять агрегированных колонок. Внутренний snapshot-запрос видит `trade_id`, `event_id` и `order_id`, однако пользовательский формат должен скрывать эти ключи. Для новой ленты нужно вычислять состояние позиции до/после события из хронологического набора подтверждённых fills, не меняя SQLite source of truth и итоговую карточку.

## Goals / Non-Goals

**Goals:**

- Зафиксировать русский словарь заголовков событийной ленты.
- Выводить читаемые объём и среднюю цену позиции до/после каждого события.
- Сохранить внутреннюю связь событий с одной сделкой и строкой summary без публикации ID.
- Сохранить атомарный экспорт двух CSV и МСК-время.

**Non-Goals:**

- Не раскрывать технические идентификаторы под русскими заголовками.
- Не менять lifecycle, PnL или состав `trade_summary.csv`.
- Не превращать пользовательский CSV в источник восстановления и не менять схему SQLite без необходимости.

## Decisions

1. **Русские заголовки задаются явной картой, а не транслитерацией.** Это даёт стабильный интерфейс для трейдера: «Время (МСК)», «Событие», «Направление», «Количество», «Цена», «Объем позиции до», «Объем позиции после», «Средняя цена до», «Средняя цена после», «Причина».

2. **Технические ID исключаются до записи CSV.** Snapshot может использовать их в JOIN и группировке, но writer получает только разрешённые пользовательские поля. Альтернатива «перевести `trade_id` как `ID сделки`» отклонена по существующему требованию приватности технических ключей.

3. **Состояние до/после строится replay-ом fills.** Для каждого события берётся позиционное состояние до применения его fill, затем состояние после; входы/доборы усредняют цену, выходы уменьшают объём и сохраняют среднюю входа для остатка. События без изменения позиции получают одинаковые значения до/после.

4. **Связь с summary остаётся логической, а не пользовательским ключом.** Один внутренний `trade_id` связывает события с одной строкой карточки; в CSV связь представляется коротким контрактом, МСК-временем, направлением и русским событием.

5. **Изменение заголовков считается breaking для CSV-потребителей.** Файлы продолжают заменяться атомарно и не требуют миграции данных, но внешние скрипты должны перейти на русские заголовки и новый набор событийных колонок.

## Risks / Trade-offs

- [Replay событий в большом журнале дороже одного SQL-агрегата] → Выполнять его внутри одного read-only snapshot и покрыть порядок событий тестом; SQLite остаётся источником данных.
- [Исторические события не содержат полного набора fills] → Оставлять недоступные значения пустыми, не подменять их нулём и сохранять существующую русскую запись события.
- [Изменение заголовков ломает CSV-скрипты] → Зафиксировать полный контракт заголовков в тесте и документации.

## Migration Plan

1. Обновить событийную проекцию и тестовые fixtures без изменения существующих SQLite-записей.
2. При старте или следующей транзакции атомарно пересоздать `trade_event.csv` с русскими заголовками.
3. Старые CSV не читать и не использовать для восстановления; rollback выполняется возвратом версии экспортера.
