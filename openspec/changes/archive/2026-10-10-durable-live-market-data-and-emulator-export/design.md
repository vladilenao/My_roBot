## Context

См. `proposal.md`. В текущем режиме `load_candles()` преобразует ответ брокера
сразу в OHLCV DataFrame, теряя `is_complete` и время получения.
`MarketDataCache` хранит кадры в памяти, а его `_merge_new_bars()` пропускает
свечи не новее последней загруженной. `TradingBot` и `JournalBroker` получают
только этот кадр. SQLite-журнал сделок содержит выборочные наблюдения по
сделкам, а не полный рыночный ряд. Исторический источник уже выбран через
`ClientProvider`; его HTTP API принадлежит отдельному приложению.

## Goals / Non-Goals

**Goals:**

- Прямой путь брокер → My Robot для текущих данных и виртуальное исполнение
  через существующий `JournalBroker`.
- Восстановимый локальный журнал полученных свечей и проверок покрытия;
  возможность повторить набор данных, который был доступен роботу.
- Отдельные границы получения, последовательной обработки и экспорта.
- Документированный внешний pull API с подтверждением и переносом в БД
  Historical Broker API Emulator без общего файла БД.

**Non-Goals:**

- Отправка реальных заявок брокеру, изменение модели внутриминутного
  проскальзывания или пересчёт уже подтверждённых сделок задним числом.
- Перенос кода Historical Broker API Emulator в этот репозиторий или
  немедленная реализация его потребителя в чужом репозитории.
- Требование получать свечу каждую минуту открытой сессии: при отсутствии
  сделок свечи может не быть.

## Decisions

### 1. Разделение приёма, хранения и представления

Новый приёмник текущих данных получает брокерские свечи вместе с
`is_complete`, временем получения и источником. Он получает сведения о
расписании секции и `trading_status` инструмента, планирует повторные запросы
истории и записывает результат в локальную БД **до** передачи в кэш.
`MarketDataCache` сохраняет публичную роль `frame_for` для стратегий и хранит
небольшой рабочий DataFrame; источником текущих завершённых свечей становится
локальное хранилище. Контроль пропусков живёт в приёмнике/хранилище, кэш
использует его результат для готовности и не выдаёт кадр за непрерывный только
по времени последней свечи.

Альтернатива — добавить SQLite, расписание и API в `MarketDataCache`. Это
создало бы класс с несовместимыми обязанностями и затруднило сохранение
старого контракта исторического прогона. Исторический режим оставляет
существующий `HistoricalClient` и виртуальные часы; новые гарантии текущего
режима включаются только при прямом брокерском источнике.

### 2. Отдельная локальная БД и журнал изменений

Локальная БД `market-data.sqlite3` лежит в `runtime_dir()` текущего режима,
рядом с `trades.sqlite3`, но отдельным файлом. При стандартном `data_dir=data`
это `<корень проекта>/data/market-data.sqlite3` в разработке и каталог `data`
рядом с исполняемым файлом в сборке. Переопределённый `data_dir` применяется
по тем же правилам, что и для `trades.sqlite3`. Исторические прогоны создают
собственные каталоги под `HIST` и не открывают эту живую БД для записи.
В локальной БД находятся:

- идентичность источника (`producer_id`, постоянный UUID этой БД);
- текущие версии свечей по `(source, instrument_uid, interval, open_time_utc)`;
- неизменяемый журнал версий и изменений состояния интервалов с монотонным
  `change_id`;
- состояния проверяемых интервалов и основания классификации;
- метаданные расписания/статусов с временем получения и источником;
- подтверждённые курсоры потребителей экспорта.

Одна транзакция атомарно сохраняет новую версию, актуальный указатель и запись
журнала изменений. Равный по содержимому повтор не создаёт новую версию;
исправление старого времени создаёт новую, даже если оно меньше последнего
полученного времени. Неполная свеча может быть сохранена для диагностики,
но не предлагается стратегиям, исполнителю или экспортному потоку. Продвижение
курсора потребителя не удаляет свечи автоматически: очистка допустима только
после подтверждения экспорта и с учётом локального периода восстановления.

Альтернатива — хранить всё в `trades.sqlite3`. Она смешивает быстрорастущий
рыночный ряд и журнал финансовых фактов, усложняет миграции, резервирование и
сроки хранения. Отдельные БД не дают общей транзакции с исполнением: это
компенсируется сохранением рыночного входа до обработки, устойчивым курсором
симуляции и идемпотентностью уже существующего редьюсера.

### 3. Покрытие и последовательность

Для каждой пары источника и инструмента сервис различает `received`,
`scheduled_closed`, `confirmed_no_trade`, `pending` и `unresolved`.
Расписание секции говорит, когда ожидать торгов, статус инструмента уточняет
фактические остановки; ни одно из них само по себе не доказывает отсутствие
сделок внутри открытого интервала. Пустой ответ или таймаут тоже этого не
доказывает. `confirmed_no_trade` разрешён только при документированном
свидетельстве полноты источника за конкретный интервал; если такого
свидетельства нет, он остаётся `unresolved`.

Новые закрытые свечи могут поступать поверх открытой дыры. Приём продолжается,
а граница последовательной обработки останавливается перед первой
неразрешённой ожидаемой минутой. Восстановление запрашивает окна вокруг самой
старой дыры отдельными порциями с ограничением размера запросов и лимитов
брокера. Текущее `data_backfill_window_seconds` ограничивает частую проверку
свежего края, **но не** поиск старой незакрытой дыры: для неё отдельная
очередь восстановления. При закрытии сессии перестают ожидать будущие
внесессионные минуты, но продолжают сверять конец прошедшей сессии.

Последняя полученная свеча, последняя непрерывно разрешённая минута и последняя
исполненная минута — отдельные границы. При неразрешённой дыре свечная
симуляция активной позиции не помечает защиту полной и не перескакивает к
следующей минуте. При превышении допустимого отставания текущая симуляция
сообщает о деградации; таймаут не превращает дыру в отсутствие сделок.
Для общего портфельного риска продвижение входов синхронизируется с уже
разрешёнными минутами всех влияющих на риск инструментов.

После обработки более поздней минуты корректирующая свеча хранится как новая
версия и экспортируется, но не меняет подтверждённое исполнение задним
числом. Исторический пересчёт — отдельный прогон с выбранной версией данных.

### 4. Граница экспортного API

My Robot публикует локальный HTTP API `/api/v1/market-data` с обязательной
OpenAPI 3.0.3 спецификацией `docs/market-data/openapi.yaml`, доступной также
по `GET /openapi.yaml`, и Swagger UI по `GET /docs`. Внешняя поверхность:
`GET /source` (идентичность и доступный
диапазон), `GET /changes?after_id=&limit=` (страницы по `change_id`),
`PUT /consumers/{consumer_id}/checkpoint` (подтверждение сохранённого
`change_id`). Ответ содержит `producer_id`, `next_after_id` и `has_more`.
Передаются завершённые версии свечей и изменения статуса покрытия; частичные
свечи не экспортируются. Повторные запросы безопасны.

Потребитель сначала сохраняет страницу в **свою** БД, включая
`(producer_id, change_id)` как уникальный ключ, затем подтверждает курсор в
My Robot. Повтор страницы после сбоя не создаёт дублей; подтверждение
монотонно. При смене `producer_id` потребитель не продолжает старый курсор.
Если курсор старше удерживаемого диапазона, API отвечает `410 Gone`, а
потребитель запускает полную сверку через согласованный исторический источник
и создаёт новую подписку с актуального источника. Такой случай считается
ошибкой покрытия, а не успешным экспортом.

Сервер по умолчанию слушает только loopback, требует токен чтения/подтверждения
и не возвращает торговые сделки, секреты и состояние счёта. Вынос на другие
компьютеры требует TLS на внешней границе и явного сетевого разрешения.
Публикация API не добавляет отправку торговых команд брокеру.
`/docs` и `/openapi.yaml` могут открываться без токена для настройки клиента;
все запросы рыночных данных и подтверждений требуют токен.

Альтернатива — прямое чтение файла SQLite эмулятором. Оно возможно на одном
хосте, но привязывает приложения к внутренней схеме робота и не подходит для
доступа через сетевую файловую систему. Альтернатива push из робота потребовала
бы, чтобы робот знал доступность эмулятора; pull позволяет восстановиться
после остановки потребителя.

### 5. Владение историей

Локальная БД фиксирует **виденное роботом**. Historical Broker API Emulator
ведёт собственный архив, принимает этот поток как один источник и независимо
дозагружает у брокера период остановки робота. При несовпадении он сохраняет
происхождение/версии и не выдаёт позднее уточнённый бар за тот, который был
известен роботу во время текущей симуляции. Инструкция подключения и примеры
запросов находятся в `docs/market-data/emulator-integration.md`.

## Risks / Trade-offs

- [Рост локальной БД при долгой недоступности эмулятора] → наблюдение объёма,
  предупреждение и запрет удаления неподтверждённых изменений.
- [Позднее исправление после исполнения] → новая версия и отдельный повторный
  прогон; уже подтверждённые финансовые факты не переписываются.
- [Сбой между записью свечи и записью исполнения] → повтор чтения локального
  входа и идемпотентное исполнение по сохранённой границе.
- [Неизвестное расписание или отсутствие сделок] → `unresolved` с причиной и
  измерением отставания, без выдуманной свечи.
- [Сложность межпроцессного API] → небольшой версионированный контракт,
  OpenAPI, локальный адрес по умолчанию и интеграционные проверки повторов.

## Migration Plan

1. Ввести локальную БД и теневую запись текущих данных без изменения решений;
   проверить полноту, времена и стоимость записи.
2. Перевести текущий `MarketDataCache` на сохранённые завершённые данные и
   состояния покрытия, затем на последовательную обработку по курсору.
3. Включить API и экспорт для тестового потребителя, проверить повтор,
   перезапуск и исправление старой свечи; после этого подключить эмулятор.
4. Отдельно проверить исторический режим, чтобы он по-прежнему читал только
   свой выбранный источник и не публиковал текущий поток.
5. Откат переключает текущий путь на прежний загрузчик; локальную БД и
   экспортный курсор сохраняют для последующей диагностики и повторного пуска.
