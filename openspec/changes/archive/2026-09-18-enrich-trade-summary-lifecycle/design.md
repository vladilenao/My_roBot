## Context

Текущий `CsvExporter` уже строит `trade_summary.csv` из read-only снимка SQLite, но выбирает только агрегированные поля позиции: количество, среднюю цену, стоп, один средний выход, PnL, комиссии и риск. Плановые значения, список выходов, сценарий исполнения, lifecycle-коды и метрики R/MAE/MFE не представлены. Существующий `trade-artifact-refactor` меняет имена пользовательских артефактов, поэтому этот change расширяет уже канонический `trade_summary.csv`, не возвращая legacy-файлы.

## Goals / Non-Goals

**Goals:**

- Сделать SQLite-модель сделки достаточной для детерминированной карточки с разделением плана и исполнения.
- Ввести единый lifecycle и явное отображение внутренних кодов в русские пользовательские labels.
- Формировать все поля карточки из согласованного снимка, включая исторические выходы, агрегаты объёмов, комиссии, риск, R, MAE и MFE.
- Сохранить атомарность и независимость торгового состояния от CSV.

**Non-Goals:**

- Не менять источник истины: CSV не становится хранилищем и не используется для восстановления.
- Не менять брокерский API, правила стратегии или формулы торгового сигнала.
- Не добавлять новые пользовательские файлы и не сохранять английские lifecycle-коды в пользовательских CSV.

## Decisions

1. **Расширять текущую проекцию, а не добавлять второй summary-файл.** Это сохраняет одну карточку на сделку и делает новый контракт явным. Вариант с отдельным `trade_metrics.csv` отклонён: он снова заставил бы трейдера собирать оценку вручную.

2. **Хранить план и факты раздельно.** План входа, стопа и TP1 читается из зафиксированного плана сделки; исполнения и комиссии агрегируются из подтверждённых fills/events. Нельзя вычислять план из фактической средней цены, иначе исчезает различие между плохой идеей и плохим исполнением.

3. **Сделать lifecycle закрытым словарём.** Внутри используются перечисленные английские коды для переходов и фильтрации; отдельная таблица labels отвечает за русский вывод. Неиспользуемые промежуточные названия вроде `BUILDING`/`REDUCING` не становятся дополнительными публичными состояниями, чтобы контракт оставался ровно из восьми значений.

4. **Агрегировать выходы на уровне fills.** Каждая причина и исполнение сохраняются в хронологическом списке; средняя выхода считается по всем выходным количествам, а сценарий собирается из порядка причин и признаков partial/remainder. Это предпочтительнее запроса только последнего выхода, который теряет TP1 перед STOP.

5. **Считать R и экстремумы относительно исходного риска.** `Result` использует Net PnL и Initial Risk. MAE/MFE используют наблюдаемые ценовые экстремумы сделки и знак направления, затем нормализуются Initial Risk; при отсутствии достаточных рыночных наблюдений поле остаётся пустым, а не получает ноль.

6. **Сохранять совместимость экспорта на уровне атомарности, но считать схему breaking.** Имена файлов и transactional export остаются прежними, однако заголовки и состав строки меняются целиком. Тесты потребителей старой схемы должны быть обновлены, а rollback выполняется возвратом версии приложения и схемы, не ручным редактированием CSV.

## Risks / Trade-offs

- [В старых сделках нет плановых значений или рыночных экстремумов] → Показывать пустые значения для отсутствующих данных, отдельно от числового нуля, и покрыть миграционные fixtures.
- [Разные источники могут дать несовпадающий lifecycle] → Разрешать переход только по подтверждённым событиям и проверять недопустимые переходы как `ERROR` с диагностикой.
- [Большая строка `Выходы` усложняет машинную обработку] → Сохранить SQLite/event trace нормализованными; CSV определить как человекочитаемую проекцию и зафиксировать стабильный формат `REASON: qty @price`.
- [Изменение заголовков ломает внешние скрипты] → Явно документировать breaking schema и добавить контрактный тест полного набора заголовков.

## Migration Plan

1. Расширить внутреннее состояние и заполнить lifecycle/плановые значения для новых сделок.
2. Экспортировать новую строку карточки из read-only снимка; старые CSV не читать и не использовать для backfill.
3. Для исторических записей экспортировать только доступные поля, оставляя отсутствующие значения пустыми.
4. Обновить тестовые fixtures и внешнюю документацию заголовков; проверить атомарное восстановление после сбоя экспорта.
5. При rollback вернуть предыдущую версию экспортера и заголовков; торговое состояние SQLite не изменять.
