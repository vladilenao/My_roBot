## Context

Мотивация изложена в `proposal.md — Why`; требования — в delta-спеках `specs/orchestration` и `specs/notification`.

Текущее состояние, значимое для подхода:

- `TradingBot._loop()` (`src/bot/trading_bot.py:64`) безусловно ждёт ближайшей календарной границы через `CandleScheduler.wait_until_bar_published` (`src/scheduler/timing.py:93`) ещё до первого `_tick()`.
- `_analyze` присваивает `decision.bar_time` время ОТКРЫТИЯ последнего бара (`trading_bot.py:113`); `DecisionFormatter` выводит `bar_time + tz_offset` (`src/notifier/base.py:19`).
- `MarketDataCache` лениво наполняет кадры при первом `frame_for()` и уже отдаёт только закрытые свечи (`datetime < current_candle_start`, `_closed_only`, `src/data/cache.py:50-58,115-117`); `_initial_load` фиксирует `_observed` на текущей границе, поэтому `refresh_if_new_candle` в том же тике — no-op.
- Планировщик — единственный владелец математики периодов таймфрейма (`_period`, `_floor`, `_PERIODS` в `src/scheduler/timing.py`).

## Goals / Non-Goals

**Goals:**
- Первый тик при запуске выполняется сразу и анализирует последнюю уже закрытую свечу.
- При запуске точно на границе первый тик ограниченно ожидает появления свежего закрытого бара, прежде чем анализировать.
- Вычислить время закрытия свечи в одном месте (планировщик) и доносить его в уведомления без участия форматтера.
- Ноль изменений логики кэша (первичная загрузка/дозагрузка уже дают правильный срез).

**Non-Goals:**
- Никакой дедупликации стартового уведомления: повторный запуск в пределах того же периода снова сообщает последнюю закрытую свечу (это явное ожидание пользователя).
- Без изменения штатного ритма, инкрементальной дозагрузки и контура расчёта стратегий.
- Без изменения того, что стратегии получают: по-прежнему только закрытые свечи.

## Decisions

### 1. Пропуск ожидания границы только на первой итерации
`_loop()` получает флаг `first`; на первой итерации вместо `wait_until_bar_published` вызывается новый `_bootstrap()`, затем `_tick()`. Флаг снимается только после успешного первого `_tick()`, чтобы при транзиентном сбое инициализации bootstrap повторялся (по fallback-паузе), а не терялся.

Альтернатива («голый» `_tick()` до входа в цикл) отвергнута: он вне `try/except` цикла (сбой первичной загрузки уронил бы бот) и не умеет дожидаться свежего бара.

### 2. `_bootstrap()`: первичное наполнение кадров + ограниченное ожидание свежего бара без границы
`_bootstrap()` сначала наполняет кадры (`data_cache.frame_for`) для всех инструментов — без этого `has_fresh_closed_bar()` тривиально возвращает `True` на пустом кэше. Затем вызывается ограниченное ожидание свежего закрытого бара. Чтобы не дублировать цикл опроса (`deadline + while not bar_ready + sleep`), в `CandleScheduler.wait_until_bar_published` добавляется параметр `wait_boundary: bool = True`; bootstrap передаёт `False` — спит до границы пропускается, таймаут опроса тот же (`TICK_TIMEOUT_SECS`).

Для запуска в середине периода это no-op с мгновенным возвратом (свежий бар уже есть); для запуска на границе — ожидание вплоть до таймаута, затем обработка с имеющимися данными (как в штатном цикле).

Альтернатива — инлайновый опрос в `TradingBot` — отвергнута: дублирует логику ожидания планировщика и размазывает ответственность за ожидание.

### 3. Время закрытия считается планировщиком и проставляется в оркестраторе
`CandleScheduler` получает публичный метод `bar_close(bar_start)` → `bar_start + _period(bar_start)` (единый источник математики периода, включая переменные периоды `1w`/`1M`). `_analyze` присваивает `decision.bar_time = timeline.bar_close(last_bar_start)` — семантика `bar_time` меняется на «момент закрытия бара». `DecisionFormatter` не меняется (по-прежнему `bar_time + tz_offset`), тесты форматтера не затрагиваются.

Рассмотренные альтернативы:
- **Период в `DecisionFormatter`** (форматтер получает период или карту timeframe→период от фабрики `get_notifier()`): отвергнуто — фабрика нотификаторов не имеет контекста таймфрейма, и математика периода попала бы в представление.
- **Новое поле `bar_close` у `Decision`**: заманчиво, но `bar_time` целиком принадлежит оркестратору (всегда перезаписывается в `_analyze`, стратегии его не задают), поэтому переиспользование поля проще и не расширяет контракт.

Для формата `HH:MM` важен только `bar_time + tz_offset`, поэтому единый тест в `_analyze` — единственная точка правки отображения.

### 4. Кэш не меняется
Первичная загрузка + `_closed_only` уже дают нужный срез «последняя закрытая свеча» на момент запуска; `_observed` фиксируется на текущей границе, исключая повторную полную перезагрузку в том же тике.

## Risks / Trade-offs

- [Запуск на границе, свежий бар не появился до таймаута] → первый тик обрабатывает имеющиеся данные и может сообщить на одну свечу старее. Митигация: таймаут тот же, что в штатном цикле; случай редкий.
- [Перезапуск в пределах того же периода повторяет уведомление о той же свече] → осознанно принято (стартовый отчёт — цель, не дефект).
- [Выходной/низколиквидный инструмент: закрытых баров нет] → `has_fresh_closed_bar` на пустых кадрах возвращает `True`, bootstrap мгновенно завершается, `_process` логирует «Нет готовых свечей» без сообщения.
- [`bar_close` для переменных периодов `1w`/`1M`] → `_period(t)` уже корректно это считает; добавить unit-тесты закрытия для недели и месяца.
- [Лишний force-refresh на старте в середине периода] → один бар на инструмент при запуске; несущественно и согласовано со штатным ритмом.

## Migration

- Конфигурации не требуется; `wait_boundary` по умолчанию `True` — существующие вызовы планировщика не меняются.
- Тестовые дубликаты планировщика в `tests/` (например `FakeTimeline`/`PollingTimeline` в `tests/unit/bot/test_trading_bot.py`) дополнить методом `bar_close`.
- Откат: вернуть `_loop`/удалить `_bootstrap` и `bar_close`; отображение времени откатится автоматически (форматтер не тронут).
