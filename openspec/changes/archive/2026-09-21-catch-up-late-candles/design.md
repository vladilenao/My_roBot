## Context

Временный фикс `tick.timeout_secs = 300` уже в продакшене (внешний `robot.toml`).
Этот дизайн устраняет корень проблемы, позволяя после внедрения вернуть короткое
окно ожидания. Мотивация — в `proposal.md` (Why), требования — в дельтах
`specs/{timing,data-cache,instruments}`.

Текущее устройство (по коду):

- `MultiTimeframeScheduler.wait_until_bar_published` (timing.py:280) вычисляет
  кандидатов через `_crossed_since(_last_tick)` **на каждом тике заново**: ТФ,
  чей бар не появился в окне, из кандидатов выпадает навсегда, а `_last_tick`
  уже обновлён — повторного опроса пропущенной границы нет.
- `MarketDataCache.has_fresh_closed_bar` (cache.py:154) — жёсткий AND по всем
  загруженным кадрам ТФ: один неликвидный/отстающий инструмент держит гейт
  защитного ТФ `1m` закрытым.
- `MarketDataCache._initial_load` (cache.py:180) и валидация селектора
  (`selector._validate_instruments`) не троттлятся `data_refresh_min_interval`:
  стартовый шторм выжигает лимит API (`RESOURCE_EXHAUSTED`), в т.ч. был замечен
  сегодня при валидации фьючерсов.
- Активный набор ТФ ритма: `sorted(set(ACTIVE_TIMEFRAMES) | {"1m"})` (run.py:73) —
  `1m` активен всегда, поэтому wakeup происходит каждую минуту, дав догону
  дешёвые точки повторной проверки без изменения ритма.

## Goals / Non-Goals

**Goals:**

- Пропущенная на тике граница (бар не опубликован в окне) остаётся кандидатом на
  следующих тиках и повторно опрашивается, пока бар не появится (горизонт догона
  в периодах ТФ). Бар, пришедший поздно, не теряется и попадает в анализ.
- Готовность ТФ становится терпимой: пара «неактивна» (не блокирует гейт), если её
  последний бар старше горизонта терпимости; гейт не «замирает» из-за одного
  отстающего инструмента, но и не выдаёт ложную готовность, когда свежих баров ни
  у кого нет.
- Стартовая нагрузка (первичные загрузки кадров, валидация селектора) разносится
  минимальным интервалом, не выжигая лимит API.
- Один конфигурационный ключ `tick.catch_up_bars` управляет и горизонтом догона,
  и порогом терпимости.

**Non-Goals:**

- Строгий синтетический реплей каждого пропущенного бара как отдельной точки
  решения (несколько тиков без ожидания границы, выдача сигналов по каждому
  позднему бару строго по порядку). Это меняет ритм «тик = закрытая свеча» и
  семантику журнала/брокера; в дизайне поздний бар попадает в последний кадр и
  обрабатывается штатным тиком.
- Изменение интерактивного выбора инструментов (вне scope; только троттлинг).

## Decisions

**D1 — Догон живёт в планировщике, а не в кэше.**

Проблема потери баров лежит в вычислении кандидатов (`_crossed_since`), кэш уже
умеет форс-дозагрузку с bounded backfill и повторные попытки. Поэтому состояние
догона держит `MultiTimeframeScheduler`:

- Новое поле `self._pending: dict[str, datetime]` — ТФ → граница, которую ждём.
- Кандидаты тика = `_crossed_since(_last_tick) ∪ {tf: pending}", где pending не
  старше горизонта `catch_up_bars × period(tf)` (период через
  `grid(tf).next_candle_close(now) - current_candle_start(now)`, как уже сделано в
  `fallback_secs`).
- После окна ожидания `self._pending = candidates - ready`, отбросив вышедшие за
  горизонт (лог «бар ТФ X потерян: горизонт догона истёк»).
- `wait_boundary=False` (bootstrap) работает с той же логикой pending.
- Ритм не меняется: добавленных wakeup'ов нет — повторная проверка происходит на
  естественных границах; `1m` в ритме даёт повторный опрос каждую минуту.

Альтернатива рассмотрена: хранить «сто кеш» пропущенных границ в кэше и разрешать
`has_fresh_closed_bar` отвечать по ним. Отклонено: задача уже решена уровнем
кандидатов, а кэш отвечает за свежесть по текущей границе; размазывание состояния
по двум слоям усложнит тесты и согласование `_last_tick`.

**D2 — Готовность ТФ терпима к «неактивным» парам, но не фабрикует свежесть.**

`has_fresh_closed_bar(tf, now=None)` меняет семантику:

- `expected = previous_candle_start(now)` (как сейчас), `period = период ТФ`,
  `tol = catch_up_bars × period`.
- Пара «активна», если её последний закрытый бар `>= expected - tol`; иначе
  «неактивна» и из гейта исключается (лог на DEBUG).
- Результат: `False`, если активных пар нет вообще (не выдумываем готовность при
  отключённом фиде); иначе `True`, когда у **каждой** активной пары последний бар
  `>= expected`.
- Кадров ТФ в кэше нет → `True` (как сейчас, JS FK семантика пустого множества).

Поведение по сценариям дельты: отстающая >tol пара исключается → гейт по свежим →
тик обрабатывается; все свежие → `True`; свежих ни у кого нет → `False`.

**D3 — Единый ключ `tick.catch_up_bars` для обеих механик.**

Чтобы не плодить поверхность конфига, один параметр служит и горизонтом догона
(D1), и признаком неактивности пары (D2). Значение по умолчанию `2`: пропущенный
бар на 15m догоняется до 30 минут спустя, пара считается неактивной, если её бар
отстаёт больше чем на `2 × period` таймфрейма. Для `1m` это 2 минуты — достаточно,
чтобы не вычислить ложную готовность при равномерной задержке публикации.
Проброс: `config.py` → `CATCH_UP_BARS = _CONFIG["tick_catch_up_bars"]`; в `run.py`
передаётся в `MultiTimeframeScheduler(catch_up_bars=...)` и
`MarketDataCache(..., freshness_tolerance_bars=...)`. В `timing.py` — новый
конструкторный параметр `MultiTimeframeScheduler(..., catch_up_bars: int = 0)`
(0 = прежнее поведение, для тестов и обратной совместимости).

**D4 — Стартовая нагрузка троттлится тем же `data_refresh_min_interval`.**

- `MarketDataCache._initial_load`: перед фактическим `_load` вызывается
  `_wait_throttle()` — если с `_last_api_attempt` прошло меньше минимума,
  `time.sleep(остаток)` (однопоточный bootstrap, честная пауза проще очереди).
  `_load` по-прежнему обновляет `_last_api_attempt`. Сценарий «Не выжигает лимит»
  дельты закрывается: первичные загрузки разнесены.
- Валидация селектора: `select_instruments(validation_pause_secs=...)` и
  `_validate_instruments` вставляют паузу между `find_working_instrument`.
  `run.py` передаёт `DATA_REFRESH_MIN_INTERVAL`; тесты — `0`. Импорта `src.config`
  в `instruments` не появляется, зависимости явные.
- При `RESOURCE_EXHAUSTED` селектор уже печатает ошибку `✗`; по сценарию дельты
  дополнительно: при rate-limit `_validate_instruments` ждёт `ratelimit_reset`
  (`rate_limit_reset_secs`) и продолжает, а не рвёт выбор. Обработка — в
  `find_working_instrument`/обвязке селектора.

Альтернатива: очередью/воркером загрузок — избыточно для однопоточного запуска.

**D5 — Каждый тик по-прежнему «один закрытый бар», строгий реплей исключён.**

Когда поздние бары приходят пачкой, последний из них становится «рабочим» баром
тика (штатная логика `_analyze`: кадр обновлён, решает `frame.iloc[-1]`), более
ранние поздние бары молча достраиваются в кадр и пересчитывают индикаторов. НЕ
создаётся синтетических тиков по каждому отстающему бару. Это сохраняет ритм,
идентификаторы событий и журнал/брокер (для которых ключ — время бара). Решение
зафиксировано как Non-Goal: строгий упорядоченный реплей сигналов по пропущенным
барам — отдельная будущая фича, если понадобится.

## Risks / Trade-offs

- [Терпимость может «простить» пару, чей бар реально нужен] → Порог терпимости
  влияет только на гейт защитного ТФ и не меняет анализ по закрытым барам пары;
  дефолт `2 × период` консервативен, ключ настраивается.
- [Равномерно задержанный фид (все бары > tol) → гейт ложен, тик после таймаута]
  → Это ожидаемо (не выдумываем свежесть); догон D1 продолжает подбирать бары по
  мере публикации, окно ожидания остаётся ограниченным `tick_timeout_secs`.
- [Больше проверок bar_ready на тик из-за pending] → проверки по кэшу дёшевы,
  форс-дозагрузки уже троттлятся `data_refresh_min_interval`.
- [Поздние бары пачкой обрабатываются как один рабочий бар, сигнал самого позднего
  не выносится] → Сознательное упрощение (D5); альтернатива (строгий реплей)
  меняет ритм и журнал.
- [Задержка старта из-за разноса загрузок] → Холодный старт на N пар добавляет
  `N × data_refresh_min_interval`, приемлемо для догона после простоя.

## Migration Plan

- Обратно совместимо: `catch_up_bars` — опциональный ключ (`_SECTIONS["tick"]`,
  `_EXPECTED_TYPES` int, дефолт 2 в `_DEFAULTS`); старые конфиги без ключа
  работают на новых значениях по умолчанию. `MultiTimeframeScheduler(catch_up_bars=0)`
  и `validation_pause_secs` с дефолтом 0 сохраняют прежнее поведение для тестов.
- Продакшен `robot.toml`: после релиза `tick.timeout_secs = 300` можно вернуть к
  65 с — догон покроет позднюю публикацию; значение 300 не мешает и может остаться.
- Деploy по стандартному релизному процессу (AGENTS.md): bump версии, тесты, ruff,
  PyInstaller-бинарь, release notes с тезисом «робот догоняет поздно
  опубликованные свечи».
