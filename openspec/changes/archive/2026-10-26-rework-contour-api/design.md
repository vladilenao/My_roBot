## Context

API управления после П4–П7 (`docs/openapi.yaml` 1.8):

```
/api/v1/contours                       GET список (emulation + прогоны), POST запуск/очередь
/api/v1/contours/{id}                  GET один контур (oneOf по kind)
/api/v1/contours/{id}/stop             POST
/api/v1/contours/{id}/instruments      POST {add} | {remove, mode}
/api/v1/contours/{id}/log              GET
/api/v1/core                           GET
/api/v1/market-data/…, /clusters/…     экспорт (ExportToken)
```

Код:

- `src/data/export_api.py` — один HTTP-сервер: экспорт, кластеры,
  управление;
- `src/bot/launch_control.py` — `LaunchControl`: разбор команд
  (`parse_command`), состояние контура, маршрутизация видов
  (`history`, `emulation`);
- `src/assembly/history_runs.py` — очередь и журнал прогонов;
- `src/assembly/core_state.py` — `desired`, `contour_members`,
  `history_runs`, `contour_commands`.

Проект целевого контракта — `docs/api/openapi-draft.yaml`, решения —
`docs/api/README.md`.

## Goals / Non-Goals

**Goals:**

- У эмуляции и истории свои ресурсы и свои схемы; прежние маршруты
  удалены.
- Слова API — слова оператора; внутренние имена базы наружу не выходят.
- Состав эмуляции меняется пачкой; одно имя инструмента во всех
  командах эмуляции.
- Интерфейс рисует кнопки по `_actions`; две одновременные команды не
  затирают друг друга молча.
- Контракты лежат в `docs/api/`, `/docs` показывает только то, что сервер
  выполняет.

**Non-Goals:**

- справочник инструментов;
- контур «Счёт»;
- изменения экспорта рыночных данных и отчёта кластеров;
- переименование таблиц и полей `core.sqlite3` и `status.json`.

## Decisions

### D1. Внутренняя модель не меняется, меняется только представление

`core.sqlite3` хранит желаемое (`running`, `stop_mode`, `generation`),
`status.json` — фактическое (`applied_generation`). API отображает их:

| Внутри | В API |
|---|---|
| `running = true` | `target.mode = "on"` |
| `running = false`, `stop_mode = no_entries` | `target.mode = "no_entries"` |
| `running = false`, `stop_mode = close_all` | `target.mode = "close_all"` |
| `generation` | `target.revision`, `ETag` |
| `actual.*`, `applied_generation` | `current.*`, `applied_revision` |
| `members[].desired` / `actual` | `instruments[].target` / `current` |
| `command` (JSON строкой) | `launch.request` (объектом) |

Отображение — в одном месте представления ответа (`launch_control`).
Контур, ядро, автоподъём и журнал команд не трогаются.

**Альтернатива:** переименовать поля базы. Отклонена: миграция ради
слов, риск для П6 (подхват и автоподъём читают эти поля).

### D2. Пуск и остановка — `PUT …/target`, остановка истории — команда

Эмуляция держит целевое состояние, поэтому команда — запись цели:
`PUT /api/v1/emulation/target {mode}`. Прогон истории — задание до
конца; отмена долгой операции — отдельная команда
`POST /api/v1/history/{id}/stop` (паттерн отмены долгой операции).

Повторы: `on` при работающей эмуляции — `409 ALREADY_RUNNING` (как
прежде), повтор той же остановки — `200` с прежней ревизией. Успешный
запуск теперь `202`, а не `201`: команда только записывает цель, контур
достигает её сам.

### D3. Состав пачкой: `POST …/instruments` и `POST …/instruments/remove`

`DELETE` с телом не используется: у тела `DELETE` в HTTP нет
определённого смысла, часть клиентов его отбрасывает, Swagger UI для
OpenAPI 3.0 поле тела не показывает. Удаление пачкой — команда `remove`
(паттерн batch delete). Внутри обе команды — прежний
`change_membership` с `add` или `remove`.

### D4. Одно имя инструмента в эмуляции

`classify_tokens` получает вид команды. Для эмуляции:

- тикер акции и короткое имя контракта — как прежде;
- `all` и отсутствие поля — как прежде, у семейств ближайший контракт;
- код семейства — отказ «Код семейства не принимается — укажите
  контракт; ближайший допустимый — NG-12.26»: ближайший считается тем же
  правилом, что для `all`;
- биржевой тикер контракта — отказ «укажите NG-12.26».

Для истории правила не меняются. Удаление сопоставляет имя только с
`name` участника: код семейства «если в составе ровно один контракт»
больше не нужен.

### D5. `id` прогона — имя папки

Внутренний ключ строки `history_runs` остаётся прежним (`history-…`):
так строки прежней версии читаются без миграции. API показывает и
принимает имя папки (`dir` без `contours/history/`). Поиск по `id` —
по имени папки; оно уникально, потому что из него и строится ключ.

### D6. Ошибки — `problem+json` только на маршрутах управления

`type` — `urn:my-robot:problem:<code>` (код в нижнем регистре через
дефис), `title` — короткая фраза, `detail` — прежний текст `message`.
Дополнительные поля — как прежде: `rejections` (поле `token`
переименовано в `instrument`), `core`, `pid`. Маршруты экспорта и
кластеров отвечают прежним `{code, message}`: их формат читает
эмулятор данных.

Разделение — по маршруту, а не по ключу: `401` на маршруте управления —
`problem+json`, на маршруте экспорта — `{code, message}`.

### D7. `_links` и `_actions` строит сервер по состоянию

Набор действий выводится из того же состояния, по которому сервер
принимает или отклоняет команды. Отдельной таблицы правил для UI нет:
функция «какие действия допустимы» используется и для `_actions`, и для
проверки команды. Так кнопка не расходится с ответом на нажатие.

### D8. `ETag` и `If-Match`

`ETag` — `"<revision>"`. Проверка `If-Match` — в той же транзакции, что
запись цели или состава: сравнение с текущим поколением и запись идут
под одной блокировкой `core.sqlite3`. Несовпадение — `412
REVISION_CHANGED`, запись в `contour_commands` с исходом `conflict`.

### D10. Запуск записывается в `core.sqlite3` при команде

Прежде главный поток отвечал на команду запуска после разрешения
инструментов, а целевое «работает» записывал позже — перед стартом
процесса, после прогрева данных. Ответ `202` тогда показывал бы прежнюю
ревизию и даже прежний режим остановки. Теперь `mark_launched` записывает
целевое состояние и состав сразу, в той же транзакции сверяет `If-Match`, а
ядро перед стартом процесса берёт поколение из базы (как при автоподъёме) и
дописывает участникам карточки контрактов без нового поколения
(`attach_contracts`). Побочный эффект: если робот упал между командой и
стартом процесса, следующий запуск поднимет контур автоподъёмом — команда
принята, значит цель записана.

### D9. Контракты в `docs/api/`

```
docs/api/
  README.md                    обзор: контракты, ключи, Swagger
  openapi.yaml                 2.0.0, отдаётся по /openapi.yaml
  v2-decisions.md              решения и «было → станет» (нынешний README проекта)
  market-events.asyncapi.yaml  события Redis
```

`openapi-draft.yaml` становится `openapi.yaml`: без `x-replaces`, без
`/api/v1/live` и справочника (сервер их не выполняет), без схемы
`LiveContour`. План «Счёта» и справочника остаётся в `v2-decisions.md`.
Путь читают `export_api.py`, `run.spec`, тесты.

## Risks / Trade-offs

- **Сохранённые запросы владельца ломаются** (Yaak) → в README и
  CHANGELOG — таблица «было → станет».
- **Два формата ошибок в одном API** → граница проста: всё под
  `ExportToken` — прежний формат, остальное — `problem+json`; описано в
  контракте.
- **`_actions` расходится с проверкой команды** → одна функция на оба
  места (D7), тесты сравнивают действия с ответом на команду.
- **`202` вместо `201` при запуске** — клиент, ждавший `201`, ошибётся;
  клиентов, кроме владельца, нет.

## Migration Plan

1. Реализация в ветке, тесты, Swagger `2.0.0`.
2. Живая проверка владельцем: запуск, состав, остановка, история, отказ
   кода семейства, `412`.
3. Откат — возврат ветки: данные и схема базы не меняются.
