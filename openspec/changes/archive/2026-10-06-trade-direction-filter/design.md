## Context

См. proposal.md (Why). Фильтр направлений — превентивная проверка «до параметров сделки»: направление сигнала становится `plan.side` (BUY/SELL) в `_plan_entry` (`src/trade_management/manager.py:911`). Тип инструмента `instrument.instrument_type` (`share`/`future`) доступен во входном кандидате `actions_for_signal`. Недопуск уже имеет штатный механизм: `SignalAdmission.rejections` с кодом + русским сообщением (`rejection_reason` в `src/trade_management/models.py:425`), который доставляется в уведомление `⛔ … Сделка не допущена: <причина>` — нового транспорта не нужно. Конфиг валидируется строго до торгового цикла (`_SECTIONS`/`_EXPECTED_TYPES` + пер-ключевые валидаторы в `src/config_loader.py`); значения счёта пробрасываются в `TradeManager` через `src/config.py` → `run.py`.

## Goals / Non-Goals

**Goals:**
- Позволить настраивать разрешённые стороны входа по типам инструментов (фьючерсы — обе, акции — только лонг) без участия стратегий и без смены профилей.
- Безопасно встроиться: отсутствие секции сохраняет текущее двустороннее поведение.

**Non-Goals:**
- Запрет/разрешение направлений по отдельным инструментам внутри одного типа (символ SMV/броса) — не требуется.
- Изменение логики стратегий (остаются двунаправленными) и профилей управления.
- Отражение фильтра в already-записанных планах/позициях: применяется только к новым входам.
- Управление открытой позицией (стопы, цели, добор) фильтром не ограничивается.

## Decisions

### 1. Проверка в допуске `actions_for_signal`, а не в стратегии/боте
Направление выбирается в `TradeManager` (единственная точка, где сигнал становится планом). Проверка входит первым шагом `_plan_entry`, до построения профиля/сайзинга, и возвращает недопуск `direction-not-allowed`.
- Каноническое отображение: BUY → `long`, SELL → `short` (совпадает с `_is_long` в `profiles/geometry.py:185`).
- HOLD не проверяется (не вход); owned-позиция обрабатывается ранее веткой `_manage_owned` и фильтром не блокируется — управление позицией не ограничивается (дизайн spec-сценария «Управление позицией не заблокировано фильтром»).
- Альтернатива «фильтровать в стратегии» отклонена: стратегии не знают тип инструмента и не должны становиться зависимыми от конфига торговли.

### 2. Внутреннее представление: `Mapping[str, frozenset[str]]`
`direction_limits` — словарь `{instrument_type: frozenset({"long","short"})}`, нормализованный один раз в `__init__` TradeManager. `None`/отсутствие типа ⇒ разрешены обе стороны. Элемент проверки: `direction := "long"|"short"` и `direction in allowed`.

### 3. Валидация конфига в `config_loader`
- `_SECTIONS["trading"]["directions"] = "directions"`, `_EXPECTED_TYPES["directions"] = dict`.
- Новый `_validate_directions` (по образцу `_validate_risk_limits`): каждый ключ — тип инструмента; значение — непустой список строк ровно из `{"long","short"}` (нижний регистр); нарушение — `ConfigError` «файл: [trading.directions] <тип> …». Некорректное значение не заменяется молча дефолтами.
- Неизвестные ключи типов НЕ отклоняются: набор типов открыт.

### 4. Проводка значений до TradeManager
`src/config.py`: `TRADING_DIRECTIONS = dict(_CONFIG.get("directions", {}))`. `run.py`: передача `direction_limits=TRADING_DIRECTIONS` в конструктор `TradeManager` (новый kwarg с дефолтом `None` → поведение без изменений).

### 5. Русское сообщение причины
Добавить в `_REJECTION_MESSAGES` (`src/trade_management/models.py:394`): `"direction-not-allowed": "направление не разрешено для этого типа инструмента"`. Код проходит штатный `rejection_reason` и шаблон недопуска без правок шаблонов.

### 6. Документация в default.toml
Комментированный блок `[trading.directions]` (пример: `future = ["long", "short"]`, `share = ["long"]`) с пояснением про дефолт «обе стороны» при отсутствии блока.

## Risks / Trade-offs

- [Изменение набора типов через future-версии] → Валидация открыта к новым ключам; значением остаётся непустой список `long`/`short`.
- [Запрет шорта может «потерять» SELL, который был закрытием/добором] → Проверка только новой позиции; owned-ветка `_manage_owned` обрабатывает сопровождение без фильтра (проверка в `_plan_entry` гарантирует это).
- [Пустой список направлений может показаться «запретить всё»] → Принято: пустой список = `ConfigError` (см. сценарии spec-дельта конфигурации); явного «запретить все входы» нет.

## Migration Plan

- Без миграции: отсутствие `[trading.directions]` не меняет поведение. Развёртывание — обычная замена конфига/бинаря; откат — удаление блока из `robot.toml`.
- Поставляемый `default.toml` получает только комментарий, значений не добавляет (чтобы не менять поведение по умолчанию).
