## Context

Изменение добавляет детекцию двух свечных паттернов в live-контур без изменения синхронного торгового цикла. Завершённые свечи и покрытия интервалов принадлежат MarketDataStore в market-data.sqlite3. Их восстановление выполняют MarketDataCache и независимые полосы данных.

SQLite остаётся источником истины для свечей. Redis Stream market.events хранит производные интеграционные события 90 суток. Он не заменяет EventBus в синхронном ядре.

## Goals / Non-Goals

**Goals:**

- Не задерживать TradingBot чтением SQLite, recovery-requester или Redis.
- Анализировать только непрерывный контекст завершённых свечей.
- Публиковать паттерны с at-least-once доставкой и дедупликацией.
- Дать независимым потребителям один durable путь чтения.

**Non-Goals:**

- Торговые решения по паттернам.
- Реплей истории и восстановление задач, отброшенных при заполненной очереди.
- Чтение паттернов торговым ядром в MVP.
- Автоматические XPENDING и XCLAIM для другого consumer.
- Архивация событий старше 90 суток.
- Контракт payload для будущего ClusterSource.

## Decisions

### 1. Изоляция торгового цикла

После фиксации нового закрытого бара TradingBot передаёт неизменяемую копию в `queue.Queue` с размером из `queue_maxsize` (по умолчанию 1024) через `put_nowait`. Рабочий поток не ждёт обработку задачи. Если очередь заполнена, новая задача отбрасывается, а воркер пишет warning с тикером, таймфреймом и временем.

Worker работает daemon-потоком. Исторический режим его не создаёт. Дедупликация задачи использует instrument UID, таймфрейм и время закрытия. Для каждой пары хранится только watermark последнего принятого закрытия и набор ключей задач, которые ещё находятся в очереди или ожидают проверки покрытия; после завершения ключ удаляется. Поэтому повтор одного бара не создаёт задачу и память дедупликации не растёт с историей, но отброшенные задачи не восстанавливаются.

### 2. Согласованный контекст SQLite

MarketDataStore получает новый read-only API контекста паттерна. Он в одной SQLite read-транзакции WAL:

1. выбирает две последние завершённые свечи указанного UID и таймфрейма;
2. ограничивает данные закрытием целевого бара;
3. возвращает свечи и состояния ожидаемых промежуточных интервалов из одного снимка.

Отдельные current_frame и coverage_state не подходят: они открывают разные соединения. Сетевой запрос в read-транзакции запрещён.

При pending или unresolved воркер передаёт `(uid, timeframe, missing_open_time)` инъецированному recovery-requester live-ingestion. Он вызывает существующий `IngestionWorker.note_loss()`, который ставит работу в Evidence/Completeness lane, и сразу возвращает управление. Воркер не вызывает брокер, `data.loader.load_candles` или приватный `MarketDataCache._load` и не обходит арбитр лимитов. Задача откладывается до следующей проверки покрытия; после фиксации результата полосой он открывает новый снимок. Детекторы запускаются только для непрерывного контекста. Scheduled_closed и confirmed_no_trade разрешают интервал без создания вымышленной свечи.

### 3. Реестр паттернов

Подпапка src/market_structure/patterns содержит:

- base.py с BasePattern и неизменяемым PatternResult;
- bullish_engulfing.py;
- bearish_engulfing.py;
- __init__.py с закрытым реестром ровно из двух классов.

Классы получают упорядоченный массив закрытых свечей и используют последние две. Математика паттернов остаётся в классах; worker отвечает только за координацию.

### 4. Outbox и публикация

До XADD worker сохраняет каноническое событие без published_at в durable outbox market-data.sqlite3. Outbox содержит уникальный event_id, сериализованный payload, число попыток, следующее время попытки и отметку успешной доставки. Перед каждой попыткой XADD worker получает Redis TIME и добавляет published_at в stream-сообщение; при повторе это поле может измениться, event_id — нет.

Event ID строится из source, schema version, тикера, таймфрейма, времени закрытия и event type. Повтор XADD после неопределённого ответа Redis допустим: потребитель дедуплицирует event_id.

Timestamp обозначает время рынка, published_at — значение Redis TIME непосредственно перед успешной попыткой XADD. Stream ID Redis не является бизнес-временем. Ошибка Redis откладывает следующую попытку outbox не менее чем на одну секунду в daemon-потоке; торговый поток не ждёт Redis.

### 5. Граница Redis и EventBus

| Вид сообщения | Транспорт | Получатели |
|---|---|---|
| Тики, торговые и системные события ядра | EventBus | существующие синхронные подписчики |
| Свечные паттерны | Redis Stream market.events | внешние сервисы и самостоятельные расширения, которым нужен replay |
| Команды роботу | вне этой capability | отдельный будущий контракт |

Redis не переводит на себя все модули внутри робота. Внутреннее расширение читает Redis, только если ему нужны независимая жизнь, сохранённая доставка или повторное чтение.

В версии 1 единственный издатель — candle_patterns. ClusterSource получает право писать в этот stream только после отдельного OpenSpec-изменения со своей типизированной AsyncAPI-схемой. Потребитель-издатель фильтрует входные source и event type и не обрабатывает свои события без явно заданного контракта.

### 6. Consumer Groups и срок хранения

Consumer Group принадлежит логическому потребителю, consumer — экземпляру. Например, group cluster-source-v1 объединяет все экземпляры ClusterSource; у каждого экземпляра своё устойчивое имя consumer.

Новый потребитель создаёт группу через XGROUP CREATE с 0-0 и MKSTREAM, сначала читает свои pending entries с ID 0, затем новые с ID >. XACK выполняется только после идемпотентной фиксации. NOACK не используется.

Worker не чаще одного раза в сутки получает Redis TIME и выполняет точный XTRIM MINID для времени Redis минус `retention_days`. Значение по умолчанию — 90 суток. MAXLEN не применяется. Pending сообщение старше настроенного срока может лишиться payload. Архивация будет отдельной capability.

### 7. Композиция и конфигурация

Настройки размещаются в `[market_structure]` внешнего `robot.toml`: `patterns_enabled`, `redis_host`, `redis_port`, `redis_db`, `queue_maxsize` и `retention_days`. Внешний файл имеет приоритет над `default.toml`. Значения по умолчанию: публикация выключена, `127.0.0.1:6379`, db 0, очередь 1024 и retention 90 суток. Пароль Redis остаётся секретом `MARKET_STRUCTURE_REDIS_PASSWORD` в окружении. `run.py` создаёт Redis-клиент и зависимости worker после MarketDataStore и MarketDataCache, запускает worker только в live-режиме при включённом `patterns_enabled` и инициирует остановку при завершении робота.

При недоступном Redis робот продолжает работу: worker сохраняет результаты в outbox и повторяет публикацию в фоне.

## Risks / Trade-offs

| Риск | Решение |
|---|---|
| Переполнение очереди | Отброс новой задачи без блокировки торгового цикла |
| Redis недоступен | SQLite outbox и повтор не ранее чем через одну секунду |
| Повтор XADD | Детерминированный event_id и идемпотентность consumer |
| Дыра в данных | Recovery lane live-ingestion и повторный SQLite-снимок |
| Consumer старше retention | Payload может быть удалён; возраст pending — операционная обязанность |
| Цикл ClusterSource | Явный фильтр source и event type |

## Testing Strategy

- Unit: паттерны, doji, равные границы тела и недостаточный контекст.
- Unit: очередь, overflow, дедупликация, DEBUG-лог, дыра и повторный снимок.
- Unit: единый SQLite-снимок, outbox и восстановление после рестарта.
- Интеграция Redis: XADD, Consumer Group, pending 0, новый поток >, XACK, идемпотентность и XTRIM MINID.
- Контракт: AsyncAPI, openspec validate strict и git diff check.
