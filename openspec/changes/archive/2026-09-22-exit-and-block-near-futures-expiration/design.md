## Context

См. proposal.md — Why. Актуальное состояние кода:

- Дата экспирации фьючерса уже читается в `src/instruments/selector.py` (`to_naive(f.expiration_date)`) при интерактивном выборе инструментов, но в рантайм-метаданные не попадает: `ContractMeta` (`src/portfolio/models.py`) содержит только `price_step, step_cost, go_buy, go_sell`.
- Торговый путь: `run.py._load_contracts_metadata` → `load_futures_contracts` (`src/api/instruments.py`) → `broker.set_contracts`/`storage.set_contract_metadata`; `TradeManager` получает метаданные через `broker.contract_for(ticker)`.
- Вход и доборы проходят через единственную воронку `TradeManager.actions_for_signal`; там уже есть отказ `no-contract-metadata`.
- `TradeManager.manage()` вызывается каждый тик для каждого инструмента по защитному ТФ и уже тянет `meta = contract_for(...)`; сейчас обрабатывает только фазы `_MANAGEABLE = {OPEN, BUILDING, REDUCING}` и пропускает `AddToTrade`.
- Отмена ожидающего входа поддерживается командой `CancelEntry` (валидна для фазы `ENTRY_PENDING`), закрытие — `CloseTrade` (валидно для `_MANAGEABLE`). Обе проходят через outbox с дедупликацией по `command_id`.
- Методы адмиссии/чекты фазы централизованы в `_validate_phase` при `submit_action`.

## Goals / Non-Goals

**Goals:**
- Блокировать новые входы и доборы по фьючерсу, до экспирации которого ≤ N календарных суток.
- Отменять незаполненные входы `ENTRY_PENDING` и закрывать живые позиции по таким контрактам, независимо от сигналов стратегии.
- Проводить решение на каждом цикле сопровождения из статичной даты экспирации и текущего времени.
- Аккуратно подключить настраиваемый порог без изменения схемы SQLite.

**Non-Goals:**
- Отмена/модификация уже поданных частичных целей или перенос стопов по экспирации.
- Перезагрузка метаданных контрактов в рантайме (статичная `expiration_date` + живое `now` достаточны).
- Обработка уже наступившей экспирации (контракт, выбранный запуском, в порог 183 дней селектора попадает только «свежим»).

## Decisions

1. **Где лежит дата экспирации.** Дополнить `ContractMeta` полем `expiration_date: datetime | None` (naive UTC). Заполнять в `load_futures_contracts` через `to_naive(f.expiration_date)` (тот же нормализатор, что в селекторе). Для акций значение `None`. Альтернатива (тянуть дату в `Instrument`) отклонена: контракт покупает/хранит брокер, и именно `ContractMeta` уже прокидывается до `TradeManager`.

2. **Единый хелпер близости.** `_expires_within(meta, now, block_days)`: возвращает `False` при `expiration_date is None`; иначе `True`, если `(expiration_date - now).total_seconds() <= block_days * 86400`. Сравнение в naive UTC; `now = datetime.now(timezone.utc).replace(tzinfo=None)`. Это и есть «календарные сутки до момента экспирации» (частичные сутки учитываются как попавшие в порог).

3. **Блокировка входа и доборов — в `actions_for_signal`.** Сразу после проверки метаданных (`no-contract-metadata`) добавить: если метаданные есть и `_expires_within(...)` → вернуть `SignalAdmission(rejections=(rejection_reason("contract-expiring", ...),))`. Покрывает и новый вход, и добор (`_manage_owned` достижим только через `actions_for_signal`). Альтернатива — отдельный фильтр на уровне бота: отклонена, т.к. дублирует механизм отказов, дважды печатает один отказ и не покрывает доборы единообразно.

4. **Отмена и закрытие — в `manage()`.** Если метаданные показывают близкую экспирацию:
   - первый проход по `restore()`: для сделок инструмента в фазе `ENTRY_PENDING` submit `CancelEntry(reason="contract-expiring")`;
   - второй проход: для `quantity > 0` и фазы в `_MANAGEABLE` submit `CloseTrade(reason="contract-expiring")`;
   - профильные расчёты для этого инструмента пропускаются.
   Размещение в `manage()` оправдано: это единственное место, которое регулярно сопровождает позиции без стратегического сигнала; `CancelEntry`/`CloseTrade` уже корректно проходят `_validate_phase` и outbox. Повторные тики не спамят: после подтверждённой отмены фаза уходит в `CANCELLED`, после полного закрытия остаток `0` — оба случая отфильтровываются условиями проходов.

5. **Конфигурация.** `_DEFAULTS["contract_expiry_block_days"] = 2` в `src/config.py`; маппинг `_SECTIONS["trading"]["contract_expiry_block_days"]` и тип `int` в `config_loader.py`; валидация неотрицательности по образцу `tick_catch_up_bars`. Проброс в `TradeManager` через конструктор из `run.py`. Порог и причина передаются в человекочитаемом отказе.

6. **Отказ с человекочитаемым описанием.** Код `contract-expiring` попадает в список причин входного допуска; описание на русском (например, «контракт скоро истекает, вход запрещён»). Пользователю контракт выводится коротким именем.

## Risks / Trade-offs

- [Повторная отправка `CancelEntry`/`CloseTrade` на соседних тиках до подтверждения брокера] → ограничивается переходами фаз (`CANCELLED`, остаток `0`); outbox сам по себе создаёт новый `command_id`, но лишние тики после исполнения не проходят фильтры проходов.
- [Порог «сутки» в тиках бессилен против скачка прямо на экспирацию] → это принятая спецификация (порог в календарных сутках), часы не вводим.
- [Сдвиг времени/наивное сравнение] → обе величины приводятся к naive UTC, разница не более порога сравнения на сутки; критичности нет.
- [Сделка уже полностью исполнена на баре экспирации] → `manage()` продолжит фильтровать по остатку; специальных действий нет.
