## ADDED Requirements

### Requirement: Календарный порт провайдера данных
Нормативный уровень: MUST. Провайдер боевого и провайдер исторического режима ДОЛЖНЫ предоставлять одинаковый календарный порт. По UID, нативному ТФ и рыночному времени порт возвращает календарное ожидание пары с фазой, последним ожидаемым интервалом, следующим событием, источником и версией расписания. Остальной контур НЕ ДОЛЖЕН ветвиться по типу провайдера для получения этих сведений. Провайдеры ДОЛЖНЫ различаться только источником расписания и правилом его применимости.

Чтение ожидания ДОЛЖНО использовать только уже загруженное расписание. Получение расписания ДОЛЖНО выполняться отдельной фоновой операцией через общий бюджет запросов, с ограничением числа фактических запросов за один шаг.

#### Scenario: Одинаковый контур в двух режимах
- **WHEN** состояние рыночных данных запрашивает ожидание пары в боевом и в историческом режиме
- **THEN** оба провайдера отвечают ожиданием одного формата, без отдельных ветвей вызывающего кода

#### Scenario: Чтение без сети
- **WHEN** торговый тик читает ожидание, а расписание для даты ещё не загружено
- **THEN** порт сразу возвращает неизвестную фазу и ставит загрузку в фоновую очередь, без сетевого вызова в тике

### Requirement: Расписание брокера в боевом режиме
Нормативный уровень: MUST. Боевой провайдер ДОЛЖЕН получать расписание у брокера по режиму торгов инструмента на окно дат вокруг текущего момента, а привязку UID к режиму — из карточки инструмента. Сохранять их ДОЛЖЕН в существующем локальном рыночном хранилище вместе с исходным ответом, временем наблюдения и версией. Боевой режим НЕ ДОЛЖЕН требовать доступности исторического эмулятора. Запросы расписания ДОЛЖНЫ учитываться в общем бюджете запросов и в лимите сервиса инструментов, соблюдать общий срок сброса ограничения брокера и НЕ ДОЛЖНЫ выполняться в торговом потоке. После перезапуска применимые сохранённые версии ДОЛЖНЫ использоваться без повторного запроса.

#### Scenario: Эмулятор не запущен
- **WHEN** боевой режим стартует при выключенном эмуляторе
- **THEN** расписание получается у брокера и сохраняется локально, календарные ожидания работают

#### Scenario: Перезапуск без доступа к брокеру
- **WHEN** робот перезапущен, брокер временно недоступен, а сохранённая версия текущей даты применима
- **THEN** ожидания строятся по сохранённой версии с признаком устаревания обновления

#### Scenario: Ограничение запросов брокера
- **WHEN** брокер вернул ограничение с временем сброса
- **THEN** запрос расписания откладывается до сброса вместе с остальными запросами и не повторяется в быстром цикле

### Requirement: Расписание исторического клиента на закреплённом снимке
Нормативный уровень: MUST. Исторический провайдер ДОЛЖЕН получать расписание у эмулятора по UID и диапазону дат. При подтверждённом снимке запрос ДОЛЖЕН содержать тот же `snapshot_generation`, что и запросы свечей прогона, а ответ с другим номером снимка ДОЛЖЕН отклоняться как ошибка контракта. Исторический провайдер НЕ ДОЛЖЕН обращаться за расписанием к брокеру и НЕ ДОЛЖЕН применять правило возраста боевого режима: применимы дни, имеющиеся в снимке.

Отсутствие ресурса расписания у эмулятора или дня в ответе ДОЛЖНО давать неизвестную фазу для затронутых дат с явной причиной, без прерывания прогона по этой причине. Если снимок не подтверждён, расписание ДОЛЖНО запрашиваться без номера снимка и обозначаться как не закреплённое снимком.

#### Scenario: Расписание и свечи одного снимка
- **WHEN** прогон использует подтверждённый снимок 42
- **THEN** запросы расписания содержат `snapshot_generation=42`, а применённые версии дней принадлежат этому снимку

#### Scenario: Эмулятор без ресурса расписания
- **WHEN** эмулятор не поддерживает запрос расписания
- **THEN** прогон продолжается с неизвестной фазой и прежними правилами проверки, причина видна в отчёте

#### Scenario: Несовпадение номера снимка
- **WHEN** ответ расписания содержит номер снимка, отличный от закреплённого
- **THEN** подготовка прогона сообщает ошибку контракта и не использует это расписание
