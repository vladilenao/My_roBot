## Context

Сейчас привязки живут в единственном словаре `STRATEGY_ASSIGNMENTS` (`src/config.py`), ключ — точный тикер инструмента. Раннер (`src/scheduler/runner.py`) делает `STRATEGY_ASSIGNMENTS.get(ticker)` для каждого инструмента; валидация `validate_assignments` (`src/strategies/__init__.py`) проверяет имена против реестра один раз до цикла. Для фьючерсов это вынуждает прописывать конкретные контракты (`"NGU6"`), которые умирают при экспирации. Мотивация и границы — см. proposal.md.

Ограничения, важные для решения:
- Тикеры контрактов MOEX имеют фиксированный формат `<двухбуквенный код базы><буква месяца><цифра года>` (например `NGU6`, `SiZ6`).
- API может возвращать тикер фьючерса в любом регистре; селектор уже сравнивает префиксы через `.upper()` (`src/instruments/selector.py`).
- Раннер уже знает `instrument_type` каждого инструмента из кортежа — отдельный резолв типа не нужен.

## Goals / Non-Goals

**Goals:**
- Бессрочная конфигурация фьючерсных привязок: одна запись на базовый актив вместо записи на каждый контракт.
- Сохранение всей существующей семантики: «многие ко многим», пропуск без привязки с логом, fail-fast валидация имён, подсказки IDE через `StrategyName`.
- Минимальная поверхность изменений: только конфиг, lookup в раннере, валидация, тесты.

**Non-Goals:**
- Автоматический перевыбор контракта при роллировании и кэширование UID (см. proposal.md, вне scope).
- Изменение селектора, лейблов уведомлений, загрузчика данных и самих стратегий.
- Поддержка перекрёстных привязок «фьючерс по точному тикеру» — не требуется текущим сценарием.

## Decisions

**D1. Два словаря с диспетчеризацией по `instrument_type`, а не один словарь с соглашением о длине ключа.**
Альтернатива — единый словарь, где 2-символьный ключ означает базу — отклонена: семантика ключа становится неявной и ломается, если когда-нибудь появится нефьючерсный тикер короче трёх символов или база длиннее двух. Явное разделение `SHARE_STRATEGIES` / `FUTURE_STRATEGIES` делает тип ключа очевидным из имени словаря, а раннер уже владеет `instrument_type`.

**D2. База выводится как `ticker[:2].upper()`.**
Формат тикера контракта фиксированной ширины гарантирует однозначность среза: все коды баз ровно двухсимвольные, поэтому префиксный поиск по списку (`startswith`) или обращение к `FUTURES_BASES` не нужны. `.upper()` обязателен из-за регистра (`SiZ6`/`SIZ6`) — так же поступает селектор. Ключи в `FUTURE_STRATEGIES` пишутся заглавными; правило нормализации живёт в одном месте — точке lookup.

**D3. Lookup остаётся в раннере, на месте прежнего `.get(ticker)`.**
Загрузчик данных и API-слой не знают о привязках — сохраняем это. Диспетчеризация — чистая функция от `(ticker, instrument_type)`: для `future` — `FUTURE_STRATEGIES`, для остальных — `SHARE_STRATEGIES`. Все нефьючерсные типы (`share`, потенциально `etf`/`currency`) попадают в `SHARE_STRATEGIES` по точному тикеру — отдельный словарь под каждый тип не вводится, пока такие инструменты реально не используются.

**D4. `validate_assignments` вызывается для обоих словарей до цикла; сообщение об ошибке называет словарь.**
Сигнатура функции сохраняется (принимает один словарь), добавляется необязательный параметр-метка источника, чтобы ошибка указывала, какой именно словарь содержит неизвестное имя. Раннер вызывает её дважды: `SHARE_STRATEGIES`, затем `FUTURE_STRATEGIES`. Альтернатива — объединять словари перед проверкой — отклонена: теряется указание источника ошибки.

**D5. Начальное содержимое конфига переносит текущую привязку.**
`FUTURE_STRATEGIES = {"NG": ["macd_rsi_stoch"]}`, `SHARE_STRATEGIES = {}` — поведение бота с NG не меняется, меняется только срок жизни записи.

## Risks / Trade-offs

- [Старый `STRATEGY_ASSIGNMENTS` после обновления молча игнорируется — бот запустится и будет пропускать все инструменты с логом] → миграционная заметка в задаче конфига; лог пропусков (существующее поведение) делает состояние видимым; fail-fast на уровне «ни одной привязки не найдено» сознательно не вводится.
- [Двухсимвольный срез перестанет быть корректным при изменении формата тикеров MOEX] → риск теоретический; формат стабилен годами, а правило локализовано в одной строке lookup.
- [Инструмент типа `etf`/`currency` получит привязки из `SHARE_STRATEGIES`] → принятое допущение D3; при появлении таких инструментов вопрос переоткрывается.
- [Тикер контракта короче двух символов невозможен по формату, но защита от пустого результата lookup уже существует — пропуск с логом] → поведение не ухудшается ни в одном краевом случае.

## Migration Plan

1. Обновить `src/config.py`: удалить `STRATEGY_ASSIGNMENTS`, создать два новых словаря.
2. Обновить раннер и валидацию, поправить unit-фикстуры.
3. Прогнать `pytest`; вручную проверить запуск с NG.
Откат — `git revert` изменения; обратной совместимости данных нет (конфиг — код).
