## Context

Где сейчас применяется фильтр привязки:

| Место | Что происходит |
|---|---|
| `TradingBot._analyze` (тиковый цикл) | с `TradeManager.actions_for_signal` кандидат сразу уходит в допуск; `SignalFilter.apply` выполняется только без менеджера |
| `LiveAnalysis._calculate` (live) | `SignalFilter.apply` до допуска, без трассы; HOLD уходит в `actions_for_signal` и даёт пустой допуск; консоль — «ОТКЛОНЕНО ФИЛЬТРОМ» без причины |
| `TradeManager._manage_owned` | `apply_with_trace` для добора по открытой сделке; трасса пишется |
| `TradeManager._plan_entry` | фильтра нет |
| `TradingBot._dispatch_management_actions` | повторная проверка добора через `apply` |

Отказ допуска уже имеет штатный путь: `SignalAdmission.rejections` → `TradingBot._publish_rejection` → событие `rejected` с `code` и `reason` → консольный блок «ОТКЛОНЕНО» под «СИГНАЛ» (`console_view._rejected`) и Telegram.

## Goals / Non-Goals

**Goals:**
- Фильтр нового входа применяется в одном месте для обоих циклов, до планирования.
- Каждое решение фильтра по входу видно в аудите.
- Отказ виден в консоли с человеческой причиной.

**Non-Goals:**
- Фильтр `order_flow` и теневой режим.
- Изменение формул существующих профилей.
- Причина в «ОТКЛОНЕНО ФИЛЬТРОМ» пути без менеджера.

## Decisions

### D1. Фильтр — первый шаг `_plan_entry`

`TradeManager._plan_entry` до проверки текущей цены, направлений, планирования и резервирования вызывает фильтр профиля `assignment.filter_profile` с `instrument_key(instrument)` и таймфреймом сигнала. Отказ возвращает `SignalAdmission(rejections=(rejection_reason("filter-rejected", message=<причина>),))`. Пропуск продолжает допуск исходным решением.

Условие применения как раньше в циклах: фильтр задан и рыночный контекст есть. Без `signal_filter` (тесты, конфигурации без фильтра) поведение не меняется.

*Альтернатива:* вернуть фильтр в `TradingBot._analyze` перед допуском. Отклонена: сырой сигнал нужен `_manage_owned` для противоположного сигнала, а правило должно жить в менеджере для обоих циклов и будущих вызывающих.

### D2. Вердикт фильтра с причиной

Фасад `SignalFilter` получает `judge(decision, ctx, profile_name, instrument, timeframe) -> FilterVerdict(decision, trace, reason)`. Профиль, у которого есть `apply_with_trace`, отдаёт трассу; человеческую причину по трассе даёт его `rejection_text(trace)`. Профиль без них получает общую трассу и причину «сигнал отклонён фильтром <профиль>». `reason` пуст, если сигнал пропущен.

Причина строится из входов трассы, поэтому трасса и текст не расходятся.

### D3. Трасса `triple_screen`

`TripleScreenFilter.apply_with_trace` повторяет `apply` и пишет трассу `filter.triple_screen` с входами: сигнал, инструмент, рабочий ТФ, `TF_int`, `TF_htf`, направление экранов 1 и 2, два последних значения гистограммы MACD, последний `%K`, пороги зон, число закрытых баров. Причины:

| reason | Текст |
|---|---|
| `binding-context-missing` | нет инструмента или таймфрейма привязки |
| `timeframe-hierarchy-unavailable` | рабочий ТФ несовместим с triple_screen |
| `screen1-not-confirmed` | экран 1 (MACD `TF_htf`) не подтверждает покупку/продажу: наклон вниз/вверх/не определён/мало свечей |
| `screen2-not-confirmed` | экран 2 (Stochastic `TF_int`) не подтверждает: `%K` и требуемая зона/мало свечей |
| `screens-not-confirmed` | оба экрана, через «; » |
| `entry-allowed` | пропуск |

`apply` остаётся прежним по результату; трассировка — отдельный метод, чтобы не менять контракт `ProfileFilter`.

### D4. Трасса `basic_levels`

Существующая трасса `filter.basic_levels` (`trend-opposes-entry`) остаётся; причина — «покупка против нисходящего тренда» или «продажа против восходящего тренда» по входам `signal` и `trend`.

### D5. Ссылки трассы

Профиль не знает привязку, поэтому менеджер дополняет ссылки трассы `assignment_id` перед записью. `signal_id` уже ставит профиль.

### D6. Live передаёт допуску сырой сигнал

`LiveAnalysis._calculate` возвращает и сырое, и отфильтрованное решение. В шаге для текущего бара при готовом исполнении и наличии `actions_for_signal` в кандидат и публикацию СИГНАЛ идёт сырое решение (`filtered_out=False`), как в тиковом цикле. Обзор при старте и информационные исторические решения по-прежнему показывают результат фильтра.

## Risks / Trade-offs

- **Больше трасс.** Одна трасса `filter.*` на входной сигнал каждой привязки, включая `raw`. Объём мал против трасс планирования.
- **Консоль в live меняется.** Вместо «ОТКЛОНЕНО ФИЛЬТРОМ · NG» будет «СИГНАЛ … / ОТКЛОНЕНО · Покупка против нисходящего тренда». Это и есть цель.
- **Противоположный сигнал в live** теперь доходит до сопровождения сырым — так требует спецификация; раньше фильтр мог подавить закрытие по `close`.
