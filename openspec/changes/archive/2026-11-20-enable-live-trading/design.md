## Context

Документ 2, этап Р2. Код торговли на брокере общий для обоих видов контура: `BrokerContour._serve_trading` поднимает торговую часть эмуляции с `TInvestBroker`, стопом у брокера, выходами лимитом, предохранителями и настоящими комиссиями — всё это проверено в песочнице (С3–С7). Контур «Счёт» (Р1) собирается в `run.py` функцией `_run_account_contour` без торговой части: `orders` там всегда `false`, загрузка настроек `true` не пропускает. Допуск при `orders = true` уже требует полный доступ токена и допуск к срочным контрактам (`src/account/admission.py`).

`AccountControl` (`src/bot/account_control.py`) наследует `SandboxControl` и до Р2 закрывает состав (`409 ACCOUNT_READ_ONLY`), предохранители и сравнение. Отчёт `ContourComparison` (`src/bot/comparison_view.py`) сравнивает два журнала — эмуляцию и песочницу — по ключу сигнала.

Решения владельца 16.11.2026 — в `proposal.md`.

## Goals / Non-Goals

**Goals:**

- Торговля привязками на брокерском счёте робота тем же кодом, что в песочнице.
- Привязка попадает на счёт только из состава песочницы.
- Защита от случайного закрытия всего: `close_all` только с подтверждением.
- Сравнение трёх сторон по сигналам привязок «Счёта».

**Non-Goals:**

- Особый размер позиции для счёта: размер — обычный, по риску от капитала счёта.
- Автоматический перенос привязки из песочницы на счёт и снятие со счёта при снятии из песочницы.
- Команды из Telegram, UI страницы «Счёт» (отдельный репозиторий).

## Decisions

### 1. Торговая часть «Счёта» — та же сборка, что у песочницы

`_run_account_contour` при `orders = true` передаёт в `BrokerContour` фабрику торговой части `_broker_trading_factory("account", …)`, `ExitPolicy` и пороги предохранителей из `[contours.account]`, каналы с торговыми событиями (`build_channels(orders=True)`). Шлюз — `AccountGateway`, правило счёта и допуск — как на Р1. Внутри `src/broker_contour/` ветвлений по виду не появляется.

Спрос свечей заявляется под `contour_id = account`; ядро обслуживает его так же, как спрос песочницы.

### 2. Настройки

`[contours.account]` получает ключи песочницы с теми же диапазонами и значениями по умолчанию:

| Ключ | По умолчанию |
|---|---|
| `exit_offset_steps` | 5 |
| `exit_requote_secs` | 15 |
| `exit_requote_attempts` | 3 |
| `stop_place_secs` | 30 |
| `max_daily_loss_pct` | 3 |
| `max_rejects_in_row` | 3 |

`orders = true` больше не отклоняется. В `default.toml` остаётся `orders = false`: деньги включает владелец сама, строкой в `robot.toml`.

### 3. Привязка — только из состава песочницы

Запуск с `bindings` и `POST /api/v1/account/bindings` проверяют каждую привязку: она в составе песочницы с `target = active` (желаемое `sandbox` в `core.sqlite3`). Нет — `422 BINDINGS_REJECTED`, причина «Привязки нет в составе песочницы: путь эмуляция → песочница → счёт». Проверка — в момент команды; если позже привязку снимут с песочницы, на счёте она остаётся, пока её не снимет человек.

Сначала работает общая проверка конфигурации (неизвестный `id`), затем проверка песочницы, затем определение инструмента.

### 4. Подтверждение только у `close_all`

`PUT /api/v1/account/target` с `mode = close_all` и `POST /api/v1/account/bindings/remove` с `mode = close_all` без `confirm: true` — `409 CONFIRM_REQUIRED`, ревизия не пишется. `confirm` — логическое поле тела; у остальных команд оно допустимо и не влияет. Запуск с составом, добавление привязки, `no_entries` — без подтверждения.

### 5. Предохранители

У «Счёта» те же `current.guards` и `POST /api/v1/account/guards/reset` (`{"guards": ["broker_rejects"]}`), что у песочницы; «дневной убыток» командой не снимается (`409 GUARD_NOT_RESETTABLE`). Состояние — в `broker.sqlite3` папки «Счёта».

### 6. Режим без заявок

При `orders = false` (Р1-режим) поведение не меняется: команды состава — `409 ACCOUNT_READ_ONLY`, процесс только читает счёт. `AccountControl` получает режим из настроек при сборке ядра.

### 7. Сравнение трёх сторон

`GET /api/v1/account/comparison` — тот же разбор, что `GET /api/v1/sandbox/comparison` (параметры, ошибки, период, деньги строками), но:

- в отчёт входят сигналы привязок состава «Счёта»;
- у элемента три стороны: `account`, `sandbox`, `emulation` — каждая с теми же полями, что сторона отчёта песочницы, или с причиной, почему сделки нет;
- расхождения считаются от счёта: `account_vs_sandbox` и `account_vs_emulation`, с теми же кодами (`entry_price`, `entry_time`, `lots`, `exit_kind`, `exit_price`, `exit_time`, `closed_one_side`);
- `summary` — число сделок и результат по каждой стороне, число пар «счёт — песочница» и «счёт — эмуляция».

`ContourComparison` обобщается на список сторон с опорной первой; отчёт песочницы — частный случай с двумя сторонами, его ответ не меняется.

### 8. API 2.12.0

Новые маршруты: `GET /api/v1/account/comparison`, `POST /api/v1/account/guards/reset`. Изменён смысл `POST /api/v1/account/bindings[/remove]` и `PUT …/target` с `bindings`. Схемы: `AccountComparison`, `AccountBindingsRemoveRequest` (с `confirm`).

## Risks / Trade-offs

- **[Маленький капитал]** → на счёте 10 000 ₽; бюджет риска может дать 0 лотов, и вход получит `REJECT risk-budget`. Это штатный отказ робота, не брокера; владелец решает, сколько денег положить.
- **[Одна привязка торгует сразу в песочнице и на счёте]** → так задумано (сравнение трёх сторон); счета разные, правило «инструмент — одна привязка» действует внутри контура.
- **[Повтор ключа на боевом счёте]** → после П20 повтора ключа стоп-заявки нет; повтор `PostOrder` тем же ключом проверен разведкой С1 только в песочнице — первые сделки Р2 смотрим вручную.
- **[Ошибка в составе — деньги]** → только привязки из песочницы, предохранители включены, `close_all` с подтверждением, откат — `no_entries`.

## Migration Plan

Включение — строкой `orders = true` в `[contours.account]` и перезапуском «Счёта». Журнал счёта остаётся тем же (отпечаток …7029). Откат: `PUT /api/v1/account/target {"mode": "no_entries"}` — новых входов нет, позиции доживают со стопом у брокера; затем `orders = false`.
