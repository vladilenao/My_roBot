# Design: Мульти-таймфреймный ритм

## Context

См. proposal.md — Why. Опорные точки текущего кода:

- `CandleScheduler` (`scheduler/timing.py`) — математика ОДНОЙ свечной сетки: `_floor`/`_period`, `next_candle_close`, `wait_until_bar_published`.
- `MarketDataCache` (`data/cache.py`) — кадр по ключу инструмента; ТФ берёт из `timeline.timeframe` в конструкторе — точка сцепления.
- `load_candles` (`data/loader.py`) уже принимает `timeframe` параметром — загрузчик ТФ-агностичен.
- `MarketContextCache` — контекст по ключу инструмента.
- `Assignment` (2.0.0) — имя стратегии + профиль; расширяется полем `timeframe`.
- `DecisionFormatter` уже принимает контекст задачи параметрами вызова (2.0.0); ТФ пока живёт в конструкторе.

## Goals / Non-Goals

**Goals:**
- Каскад ТФ: inline `tf` → `timeframe` тикера → `[robot].timeframe`; валидация по `TIMEFRAMES` на загрузке.
- Ритм: тики на границах всех активных ТФ; на тике обрабатываются привязки только тех ТФ, у которых закрылась свеча (граница пройдена И бар опубликован).
- Кэш и контекст — по паре (инструмент, ТФ).
- Обратная совместимость конфигов 2.0.0.

**Non-Goals:**
- Агрегация старших ТФ из младшего потока (каждый ТФ — свой запрос к API).
- Изменение стратегий, их контрактов и snapshot-эталонов.
- Новые профили фильтрации.

## Decisions

### D1. Активные ТФ выводятся из привязок
Множество активных ТФ собирается из развёрнутых `Assignment` при старте (после валидации). Никакой отдельной настройки «какие ТФ качать» в конфиге нет — она была бы дублирующим источником правды.

### D2. Сетка тиков: композиция сеток, пробуждение на ближайшей границе
`CandleScheduler` остаётся математикой одной сетки (не трогаем оттестированный код). Поверх — координатор активных сеток: следующий тик = минимум `next_candle_close` по активным ТФ; на пробуждении для каждого ТФ проверяется «его граница пройдена с прошлого тика». Для дели́мых сеток (15m ⊂ 1h) это эквивалентно тикам наименьшего ТФ; общий подход корректен и для смесей с 1d/1w/1M.

*Альтернатива:* тики строго по наименьшему ТФ — проще, но ломается на недели́мых смесях (15m + 1d) и будит лишний раз; отклонена.

### D3. Публикация бара — per ТФ
`wait_until_bar_published` обобщается: на тике ждём свежего закрытого бара для каждого ТФ с пройденной границей (общий poll-цикл, per-ТФ проверка готовности, тот же `timeout_secs`). Привязки ТФ, бар которого не опубликован за таймаут, пропускают тик — остальные ТФ работают.

### D4. Кэш: ключ (инструмент, ТФ), ТФ — параметр вызова
`MarketDataCache` теряет конструкторское `timeline.timeframe`: `_key(instrument, tf)`, `frame_for(instrument, tf)`, свежесть закрытого бара отслеживается per (инструмент, ТФ). Загрузчик и так принимает `timeframe` — он не меняется. Каждая пара — отдельный поток свечей.

### D5. Контекст: по (инструмент, ТФ)
`MarketContextCache.get_context(instrument, tf)` строится на кадре соответствующего ТФ. Тренд/уровни 15m-задачи не смешиваются с часовыми: фильтр привязки видит контекст её собственного ТФ.

### D6. Кэш стратегий: ключ (имя, ТФ)
Дубли одной стратегии на разных ТФ ОБЯЗАНЫ получать разные инстансы: у стратегий с внутренним состоянием (`ma_cloud_rsi_macd` — pending-сигналы, счётчики контрактов) состояние — функция истории кадра, а кадры разных ТФ различны. Дубли на одном ТФ по-прежнему делят инстанс. Идентичность задачи — (инструмент, стратегия, профиль, ТФ); идентичность инстанса — (стратегия, ТФ).

*Это уточнение D6 чейнджа 2.0.0:* аргумент «дубли делят инстанс» верен только в пределах одного ТФ.

### D7. ТФ в нотификации — параметр вызова
`DecisionFormatter` теряет конструкторский `timeframe`: блок `(ТФ)` берётся из параметра задачи; `get_notifier()` перестаёт читать глобальный `TIMEFRAME` для форматтера. `decide(ta, timeframe=...)` уже получает ТФ задачи из привязки.

### D8. Fallback-пауза при сбое ограничена наименьшим ТФ
`sleep_seconds` (3600 по умолчанию) после внешней ошибки проспал бы четыре 15m-границы. Эффективная пауза = `min(sleep_seconds, период наименьшего активного ТФ)`; факт ограничения фиксируется в логе.

## Risks / Trade-offs

- Рост API-нагрузки: запросов в час ≈ Σ по ТФ (60/период_мин) × инструменты с этим ТФ (15m+1h на 5 инструментах ≈ 25/час вместо 5/час) → дозагрузка только по границам ТФ (D2/D3), без лишних опросов; лимиты Tinkoff с запасом выдерживают такой объём.
- Смесь недели́мых сеток (15m + 1d) → координатор (D2) будит на ближайшей границе любого ТФ; корректность проверяется unit-тестами сеток.
- Бутстрэп (первый тик) → как сегодня: без ожидания границы обрабатываются все активные ТФ по последним закрытым свечам.
- Переходный период внешнего `robot.toml` у пользователя → старые ключи валидны; пример с `tf` добавляется в CHANGELOG 2.1.0.

## Migration Plan

1. Код: contracts (`Assignment.timeframe`) → config_loader/config (каскад) → timing (координатор сеток) → data/cache → market_context → bot → notifier → run.py.
2. Тесты: unit (каскад ТФ, сетки, per-ТФ кэш/контекст, маршрутизация тиков, форматтер), прогон unit+snapshot.
3. Выпуск `2.1.0` (MINOR — обратно совместимо): `__version__`, CHANGELOG с примером каскада.
4. Откат: прежняя версия пакета; конфиги 2.0.0 валидны в обеих версиях.
