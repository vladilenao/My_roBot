# Proposal: Мульти-таймфреймный ритм

## Why

Сейчас весь бот привязан к одному глобальному таймфрейму `[robot].timeframe` (1h): планировщик будит цикл только на часовых границах, кэш хранит один кадр свечей на инструмент, рыночный контекст (тренд/SR-уровни) считается на нём же. Скальперская логика (например, `macd_rsi_stoch` на 15m без контекстных фильтров) задумана под другую свечную сетку — пока её невозможно выразить: ключи `timeframe`/`tf` в секциях стратегий намеренно отклоняются загрузчиком (защита от «слепой» мисконфигурации, введённая в 2.0.0).

## What Changes

- **Каскад таймфрейма в `robot.toml`.** Таблица тикера принимает `timeframe` (база инструмента), инлайн-запись стратегии — ключ `tf` (точечное переопределение). Каскад: `tf` инлайна → `timeframe` тикера → `[robot].timeframe`. Значения валидируются по словарю `TIMEFRAMES`; старые конфиги без новых ключей остаются валидными (**НЕ breaking**).
- **`Assignment` получает поле `timeframe`** — развёрнутый каскад на момент чтения конфига.
- **Планировщик — мульти-ТФ ритм.** Тики выравниваются по границам всех активных ТФ (сетка тиков = наименьший активный ТФ); на каждом тике обрабатываются только те привязки, чей ТФ закрыл свечу. Ожидание публикации бара (`tick.timeout_secs`) — для каждого ТФ, у которого на этом тике граница.
- **Кэш данных по паре (инструмент, ТФ)**: отдельные потоки свечей на каждый активный ТФ инструмента.
- **Рыночный контекст по паре (инструмент, ТФ)**: фильтр привязки работает с трендом/уровнями её собственного ТФ, а не глобального.
- **Нотификации:** таймфрейм в строке сообщения — из задачи (параметр вызова форматтера), а не из конструктора.
- **Fallback-пауза при сбое** (`sleep_seconds`) ограничивается длительностью наименьшего активного ТФ, чтобы не проспать частые границы.
- **Non-Goals:** агрегация младшего ТФ в старший из одного потока (каждый ТФ — свой запрос к API); изменение стратегий или их snapshot-эталонов (стратегии ТФ-агностичны); новые профили фильтрации.

## Capabilities

### New Capabilities

(нет — изменения ложатся в существующие capability)

### Modified Capabilities

- `configuration`: каскад таймфрейма; ключи `timeframe` (таблица тикера) и `tf` (инлайн-запись) легализуются и валидируются по `TIMEFRAMES`; `Assignment` несёт развёрнутый ТФ.
- `timing`: планировщик выравнивает тики по границам нескольких активных ТФ; ожидание публикации бара — per ТФ на тике.
- `data-cache`: кадры ключуются парой (инструмент, ТФ); свежесть закрытого бара отслеживается per ТФ.
- `market-context-cache`: контекст строится на кадре (инструмент, ТФ) привязки.
- `orchestration`: цикл обрабатывает привязки, чей ТФ закрыл свечу на текущем тике; ТФ задачи передаётся в стратегию/фильтр/нотификатор; fallback-пауза ограничена наименьшим ТФ.
- `notification`: блок таймфрейма в строке — из задачи, конструкторский глобальный ТФ убирается.
- `strategy-contract`: привязка «инструмент × стратегия» несёт таймфрейм; идентичность привязки — кортеж (инструмент, стратегия, профиль, ТФ).

## Impact

- **Код:** `src/config_loader.py` (легализация и валидация `timeframe`/`tf`), `src/config.py` (каскад в `Assignment`), `src/strategies/contracts.py` (поле `timeframe`), `src/scheduler/timing.py` (мульти-ТФ сетка тиков), `src/data/cache.py` (+`loader.py`) (ключи (инструмент, ТФ)), `src/market_context/context_cache.py` (контекст per ТФ), `src/bot/trading_bot.py` (маршрутизация тиков по ТФ), `src/notifier/base.py` (ТФ из задачи), `run.py` (сборка).
- **Конфигурация:** `default.toml` — без изменений схемы (новые ключи опциональны); примеры с `tf` — в CHANGELOG.
- **Тесты:** unit-тесты планировщика/кэша/контекста/бота/конфига — новые кейсы мульти-ТФ; snapshot-раннер не затрагивается.
- **API-нагрузка:** запросы свечей умножаются на число активных ТФ инструмента (15m+1h → ~5× запросов в час на инструмент вместо 1×) — учесть в дизайне кэша.
- **Выпуск:** MINOR (`2.1.0`) — формат конфигурации расширен обратно совместимо.
