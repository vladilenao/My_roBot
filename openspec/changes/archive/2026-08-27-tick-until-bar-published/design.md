## Context

См. proposal.md — Why. Суть: строгая привязка дозагрузки к календарной границе `:00.000` сталкивается с непредсказуемой задержкой публикации свежего закрытого бара в Tinkoff API (живые замеры: от ~4 до ~45+ сек). Сейчас порядок тика (src/bot/trading_bot.py:63-64, 73-74):

```
wait_until_candle_close()   # ждёт до :00.000, возвращает границу
refresh_if_new_candle()     # однократная дозагрузка РОВНО на границе
_process(...)               # bar_time = последний ВИДИМЫЙ закрытый бар
```

`_closed_only` (src/data/cache.py:89-91) фильтрует `datetime < current_candle_start(now)`; если свежий закрытый бар ещё не опубликован, фильтр отдаёт более старую свечу → дубли (одна свеча на нескольких тиках), пропуски (догонка пачкой), отставание `bar_time` на 1–3+ минуты. Смещение `wait` к `:00.000` и «один тик = новая закрытая минута» подтверждены спекой (orchestration:76-86, timing:9-33, data-cache:16-39).

## Goals / Non-Goals

**Goals:**
- Гарантировать, что тик обрабатывает данные только после того, как свежий закрытый бар текущей закрытой минуты реально появился в кэше.
- Сохранить ритм «один тик = одна закрытая свеча» и привязку к календарной границе минуты (допустимо небольшое смещение момента обработки из-за ожидания бара).
- Защитить цикл от вечной блокировки при сбое API через ограниченный таймаут.
- Сохранить требование «решения только по закрытым свечам».

**Non-Goals:**
- Не переходим на свободный опрос (каждые N секунд) или на «живую/незакрытую» свечу в контуре решений.
- Не меняем формулу фильтрации `_closed_only` и не отменяем семантику закрытых свечей.
- Не трогаем формат уведомлений, дедупликацию (её в коде уже нет) и heartbeat.

## Decisions

### D1: Ожидание бара размещаем в планировщике, а проверку готовности — через callback в кэш
`CandleScheduler` получает новый метод, например `wait_until_bar_published(bar_ready: Callable[[], bool], poll_secs: float, timeout_secs: float) -> None`, который:

1. ждёт до границы закрытия текущей свечи (как `wait_until_candle_close`),
2. затем по циклу: вызывает `bar_ready()`, при `True` — завершает; иначе спит `poll_secs` и повторяет,
3. останавливается по истечении `timeout_secs` (время измеряется через инжектированный `clock`), предотвращая вечную блокировку.

Callback `bar_ready` собирается в оркестраторе и инкапсулирует «свежий закрытый бар присутствует» — см. D2. Так планировщик остаётся владельцем пауз (единое место, тестируемое инжекцией фиктивного времени), а связь с данными — на уровне составления.

Альтернативы:
- Полностью в `TradingBot._tick` цикл с `time.sleep` напрямую — дублирует логику пауз и труднее тестировать с фиктивным временем.
- Полностью в кэше — кэш не должен владеть таймингом сна и временем границы.
Выбор: планировщик владеет паузой и таймаутом; кэш — только признаком готовности.

### D2: Признак «свежий закрытый бар появился» — проверка по ожидаемой метке закрытой минуты
Кэш получает метод, отвечающий: «последний доступный закрытый бар не старше границы закрытия текущей свечи». Ожидаемый самый свежий закрытый бар — `current_candle_start(now) - period` (минута, только что закрывшаяся на границе). Проверка:

```
expected = current_candle_start(now) - period            # 20:03 → ожидаем бар 20:02
bar_ready = (кэш видит закрытый бар с datetime >= expected)
```

Последовательность вызова в оркестраторе:

```
wait_until_bar_published(bar_ready, poll_secs, timeout_secs)
refresh_if_new_candle()
_process(...)   # _closed_only теперь гарантированно содержит свежий бар
```

`refresh_if_new_candle` на первой итерации часто не увидит бар; повторные вызовы внутри проверки `bar_ready` (или непосредственно) дозагружают данные, пока бар не «доедет». В реализации один `bar_ready` может вызывать `refresh_if_new_candle` перед проверкой, либо оркестратор зовёт дозагрузку внутри цикла.

### D3: Таймаут — защита от вечной блокировки, обработка «с тем, что есть»
Таймаут выбирается с запасом над реальной задержкой публикации: `timeout_secs` порядка 60–70 с (от границы), `poll_secs` — 1–2 с. При истечении таймаута метод возвращает управление, и тик продолжается обычным путём: `refresh_if_new_candle()` + `_process(...)` с имеющимися данными. Это соответствует сценариям «Обработка по таймауту» / «Таймаут ожидания бара»: система НЕ падает и НЕ виснет, просто обрабатывает то, что есть.

Альтернативы:
- Таймаут без обработки (пропустить тик) — теряется тик и ритм heartbeat.
- Вечное ожидание — неприемлемо при сбое API.
Выбор: обработать с имеющимися данными; в худшем случае свежий бар подтянется следующим тиком.

### D4: Конфигурация через `src/config.py`
Новые параметры конфигурации: `TICK_POLL_SECS` (пауза между попытками дозагрузки, ~1 с) и `TICK_TIMEOUT_SECS` (таймаут ожидания бара, ~65 с). Передаются в `CandleScheduler`/оркестратор как параметры с дефолтами, чтобы тесты могли подставлять малые значения.

### D5: Совместимость с инжекцией фиктивного времени
Таймаут и количество попыток считаются через `self.now()`/`clock`, а не через `time.monotonic`, чтобы unit-тесты могли двигать фиктивное время без реальных засыпаний. `time.sleep(poll_secs)` может быть заменяемым (для тестов — no-op), либо тесты вызывают логику с маленьким `poll_secs=0`. Уточняется в задачах.

## Risks / Trade-offs

- [Смещение ритма тиков] Момент обработки может съезжать от `:00.000` на until ~60 с при публикации с задержкой. → Митигация: ритм «тик = закрытая свеча» сохраняется (обрабатывается та же минута), смещение ограничено таймаутом; перекрытие со следующей границей маловероятно, т.к. таймаут < периода (60–70 с < 60 с рядом с границей контролируется проверкой).
- [Зависание при сбое API] Если API перестанет отдавать свежие бары. → Митигация: таймаут `TICK_TIMEOUT_SECS`; при истечении обрабатываем имеющиеся данные, дальнейшие ошибки ловит внешний `try/except` с fallback-паузой.
- [Усложнение цикла] Добавляется петля ожидания внутри тика. → Митигация: инкапсуляция в один метод планировщика + unit-тесты на сценарии «бар появился с задержкой» и «таймаут».
- [Искусственная задержка в худшем случае] В редкие минуты с поздней публикацией обработка терпит до таймаута. → Митигация: это строго лучше текущего дублирования/пропуска; bar_time становится честным.

## Migration Plan

Изменение локализовано: добавляются методы планировщика и кэша + новый шаг в `_tick` + конфиг. Rollback — откат одного коммита без следов в данных. Пилотный запуск на одном инструменте (NG) для проверки в проде, затем раскатка на все.
