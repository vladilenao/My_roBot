## Context

См. proposal.md — Why. Сообщения формирует `DecisionFormatter` в `src/notifier/base.py` (многострочный формат с отдельными строками "Таймфрейм:" и "Индикаторы:"), доставка идёт через `NotifyOnlyExecutionPort` → нотификатор → `ConsoleNotifier`/`TelegramNotifier` (общий форматтер). Решение — dataclass `Decision` (`src/strategies/contracts.py`) с полями `signal_type`, `price`, `timeframe`, `strategy_name`, `indicator_values`.

## Goals / Non-Goals

**Goals:**
- Компактная однострочная строка вида `● <label> HH:MM | <стратегия> ➜ <сигнал>`.
- Решение несёт время последнего бара (`bar_time`).
- Минимальная правка архитектуры: меняются только форматтер и содержимое `Decision`; порт/нотификаторы/фабрика не трогаются.

**Non-Goals:**
- Не меняем протокол `Strategy.decide` и сигнатуры стратегий.
- Не разделяем формат для консоли и Telegram (общий `DecisionFormatter`).
- Не добавляем новые каналы доставки.

## Decisions

### D1: Новое поле `bar_time` в `Decision`
В dataclass `Decision` добавляется поле `bar_time: pd.Timestamp | None = None` (tz-naive, «время последнего бара»). Дефолт `None`, чтобы не ломать существующие конструкторы и тесты. По смыслу это момент последнего готового бара, из которого строится `HH:MM`.
- *Альтернатива (отклонена):* передавать время отдельным аргументом в `notify_decision`/порт `execute` — потребовало бы менять сигнатуры порта и нотификатора (архитектурное изменение, противоречит п.4).

### D2: Заполнение `bar_time` в оркестраторе через `dataclasses.replace`
В `src/bot/trading_bot.py::_analyze` после `strategy.decide(...)` берём время последнего готового бара `frame["datetime"].iloc[-1]` и через `dataclasses.replace(decision, bar_time=...)` подставляем его в решение. Протокол `Strategy.decide` не меняется.
- *Альтернатива (отклонена):* пробрасывать `bar_time` аргументом в `decide(ta, timeframe=..., bar_time=...)` — меняет протокол всех стратегий; для текущей задачи время бара доставляет инфраструктура, а не стратегия.
- `datetime` колонка фрейма уже tz-naive (loader делает `tz_localize(None)`), так что `bar_time` будет naive — согласуется с общим naive-контрактом времени.

### D3: Переработка `DecisionFormatter.format` — компактная строка
Собираем строку частями:
```
части = ["● <instrument_label>"]
if bar_time: части.append("<HH:MM>")
if strategy_name: части.append("| <strategy_name>")
затем разделитель "➜" и блок сигнала
```
- BUY → `🟢 ПОКУПКА (BUY) — Цена: {price:.3}`
- SELL → `🔴 ПРОДАЖА (SELL) — Цена: {price:.3}`
- HOLD → `⏳ Нет сигнала.` (без цены)
- Блоки `HH:MM` и `| <имя>` опускаются, если `bar_time`/`strategy_name` отсутствуют; сегменты разделяются пробелами.
- Маркер `● ` присутствует всегда.
- Таймфрейм берётся из label инструмента (`NG-10.26 (1h)` уже несёт `(1h)`), отдельные строки "Таймфрейм:"/"Индикаторы:" удаляются.
- *Альтернатива (отклонена):* печатать таймфрейм из `decision.timeframe` отдельно — даёт дубль с label и противоречит однострочному формату.

### D4: Тесты
- `tests/unit/notifier/test_formatter.py` — заменить ожидания на новый формат (buy/sell/hold, наличие/отсутствие `bar_time` и `strategy_name`).
- `tests/unit/notifier/test_notifiers.py` — проверить, что доставка проходит новым текстом.
- Проверить unit-тесты, конструирующие `Decision` (в т.ч. `tests/unit/strategies/test_signals.py`, `tests/unit/execution/test_port.py`, `tests/unit/bot/test_trading_bot.py`) — дефолт `None` не должен их ломать; при необходимости обновить ожидания.

## Risks / Trade-offs

- **Telegram получает тот же формат** (общий форматтер) → приемлемо, соответствует пожеланию «не менять архитектуру»; при необходимости позже можно разделить форматтер, но это вне текущего scope.
- **Зависимость от наличия `bar_time`** — если фрейм пуст или колонки `datetime` нет, `_analyze` пропускает инструмент ранее (уже есть проверка `frame.empty`), так что `iloc[-1]` безопасен.
- **Нестабильность `indicator_values`** — значения индикаторов перестают печататься в строке; если потребуются позже, вернём их отдельной строкой (open question, не блокирует).
