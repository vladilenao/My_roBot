# Design: Рефакторинг оркестрации робота (TradingBot)

## Context

См. proposal.md — Why. Текущий `run_bot` в `src/scheduler/runner.py` — монолитная функция (80 строк), смешивающая валидацию, диспетчеризацию стратегий, загрузку данных, анализ, уведомление, паузу и обработку ошибок. Ритм — фиксированная пауза `SLEEP_SECONDS`; решения принимаются по живой свече (`iloc[-1]`); каждый проход — полная перезагрузка истории и полный пересчёт индикаторов; сигналы не выводятся по фронту; о сбоях трейдер узнаёт только косвенно (тишина).

Ограничения: `tests/unit/scheduler/test_runner.py` (12 тестов) жёстко завязан на внутренние имена `src.scheduler.runner.*` — его удаляем вместе с `runner.py`. Снэпшот-тесты стратегий (`tests/snapshot/`) затрагивать нельзя — сигнальный слой не меняется.

## Goals / Non-Goals

**Goals:**
- Оркестратор-сценарий `TradingBot`, где каждый этап словесного описания — отдельный метод.
- Изоляция механизмов от оркестратора: тайминг, кэш данных, исполнение — отдельные слои, внедряемые через конструктор (DI).
- Расширяемость до торгового бота через абстракцию выходного слоя `ExecutionPort` без изменения контура сигналов.

**Non-Goals:**
- Не реализуем торговое исполнение ордеров (только закладываем порт-заглушку).
- Не меняем стратегии, индикаторы и контракт `Decision`/`SignalType`.
- Не переписываем `src/api`, `src/notifier`, интерактивный выбор инструментов.
- Не сохраняем обратную совместимость с `src.scheduler.runner.run_bot` (принимается переписывание тестов).

## Decisions

### D1: Главный сценарий — класс `TradingBot` в `src/bot/trading_bot.py`
`src/bot/` становится чистым оркестратором: единственный файл сценария + реэкспорт. Ранее рассмотрено размещение тайминга и исполнения прямо в `bot/` — отклонено как «god-package»: пакет отвечал бы и за оркестрацию, и за инфраструктуру. Вместо этого механизмы живут по слоям (см. D2–D4).

- `run.py` — тонкая точка сборки зависимостей + `TradingBot(...).run()`.

### D2: Тайминг отдельно — `CandleScheduler` в `src/scheduler/timing.py`
Пакет `scheduler` возвращает себе истинный смысл «планировщика»: не раннер, а синхронизатор по границе закрытия свечи. Любой будущий потребитель истории/периодичности переиспользует его вне бота.

Ключевой приём: **инжектируемые «часы»** (`clock`), чтобы тестировать сценарий «прошёл час» без реального ожидания. Границы считаются по UTC; месяц обрабатывается как нефиксированный шаг (`timedelta` между первыми числами соседних месяцев).

### D3: Кэш данных отдельно — `MarketDataCache` в `src/data/cache.py`
Дозагрузка только новых закрытых баров поверх кэша; стратегии получают только закрытые свечи. Готовность свечи определяется по границе таймфрейма через `CandleScheduler`. Это убирает полный пересбор истории на каждом тике (п.5 исходного анализа).

### D4: Выходной слой отдельно — `ExecutionPort` в `src/execution/port.py`
Интерфейс `execute(decision, instrument)` — единственная точка, куда оркестратор отдаёт решение. Сейчас реализуется `NotifyOnlyExecutionPort` (уведомление — текущее поведение). Подмена реализации (торговая) не меняет оркестратор и стратегии — это и есть мост «сигнальный → торговый бот».

### D5: DI через конструктор вместо monkeypatching глобальных имён
`TradingBot.__init__` принимает `instruments, notifier, strategy_map, data_cache, timeline, execution, strategy_factory`. Тесты строят объект напрямую с фейковыми зависимостями — отказ от `@patch("src.scheduler.runner.*")`, что и позволило развязать оркестратор.

### D6: Защита от дублей через состояние
Оркестратор хранит словарь последних состояний «(инструмент, стратегия) → (SignalType, цена)» и уведомляет только при изменении. Решение о дубле принимает оркестратор (не стратегия), так как оно зависит от времени/прохода, а не от логики отдельной стратегии.

### D7: Модель инструмента — `Instrument` dataclass
Единая нормализация 2-/3-кортежей в `(label, ticker, instrument_type)`. Размещено в `src/instruments/model.py` (рядом с выбором инструментов), а не в `bot/`, чтобы не привязывать модель данных к оркестратору.

### D8: Периодическое сердцебиение — по счётчику тиков
«Сердцебиение» — диагностическое сообщение трейдеру о работоспособности. Ритм задаётся **счётчиком тиков** (`heartbeat_every_ticks`, параметр конструктора), а не реальным временем: это детерминировано, не зависит от паузы (`fallback`) и легко тестируется через FakeTimeline. Каждые N закрытых свечей оркестратор отправляет через нотификатор сообщение со счётчиком тиков и числом ошибок с прошлого сердцебиения. Сердцебиение адресуется нотификатором оркестратора (тем же, что шлёт алерты об ошибках) и не конфликтует с алертами о сбоях — это отдельные, дополняющие друг друга сигналы.

Рассмотрена альтернатива — привязка к реальному времени (каждые K минут) — отклонена: требует отдельного планировщика и усложняет тесты; тиковый ритм согласуется с общей архитектурой «один тик = одна свеча».

## Risks / Trade-offs

- [Смена ритма с фиксированной паузы на выравнивание по свече] → Согласовано в specs (удалён «Спящий режим», добавлено «Выравнивание итерации»); для инструментов без нового бара работа не выполняется, что экономит API/CPU.
- [Риск «дзынка» сигнала при изменении цены без смены SignalType] → Дед-дубль по сигналу (не по цене строго): состояние включает `round(price, 4)`; если это окажется шумным, порог округления можно поднять без смены контракта.
- [Незакрытая свеча может искажать расчёт при близком к границе запуске] → Кэш отдаёт только закрытые свечи по границе таймфрейма; при первом запуске ждём первой границы.
- [Удаление `runner.py` рвёт сторонние импорты `run_bot`] → Принято (цель — чистая архитектура); при реальной потребности миграции возможен временный реэкспорт, но не является целью change.
- [Снэпшот-тесты зависят от неизменности сигнального слоя] → Сигнальный слой не изменяется; тесты `tests/snapshot/` остаются нетронутыми.

## Migration Plan

1. Реализовать нижние слои без изменения сигнального слоя: `Instrument` (D7), `CandleScheduler` (D2), `MarketDataCache` (D3), `ExecutionPort`+`NotifyOnlyExecutionPort` (D4).
2. Реализовать `TradingBot` (D1, D5, D6) и переписать `run.py`.
3. Удалить `src/scheduler/runner.py` и `tests/unit/scheduler/test_runner.py`.
4. Добавить тесты параллельно с кодом: `tests/unit/bot/`, `tests/unit/scheduler/test_timing.py`, `tests/unit/data/test_cache.py`, `tests/unit/execution/`.
5. Прогнать `pytest` — снэпшот-тесты должны оставаться зелёными; упавшие — только те, что относились к `runner.py`.
6. Rollback: возврат к `git revert` удаления `runner.py` и восстановление прежнего `run.py`, если новая оркестрация окажется нестабильной; сигнальный слой при этом не затрагивается.
