# Proposal: Исторический режим торговли

## Why

Сегодня единственный способ понять, зарабатывает ли стратегия, — торговать ею на реальные деньги. Прогнать стратегию за прошлый период нельзя: бот жёстко привязан к живому T-API (клиент создаётся внутри загрузчика, `now()` из SDK задаёт правую границу запроса, `datetime.now()` используется в торговой логике), а цикл работы бесконечный и не имеет правой границы. Каждая итерация настройки стратегии стоит реальной сделки.

Цель изменения — научить робота торговать на историческом диапазоне: тот же конвейер (стратегии, кэш, риск, управление позицией, исполнение, дневник), те же решения по закрытым барам, но данные из локального эмулятора, время ускоренное, а на выходе — число: прибыль или убыток стратегии за период.

## What Changes

- **Выбор режима при старте.** Диалог: `1` — боевая торговля (как сейчас, без изменений), `2` — историческая торговля. В историческом режиме дополнительно спрашиваются границы диапазона и пауза между тиками.
- **Единый код для обоих режимов.** Время и источник данных становятся явными портами (рыночные часы, клиент данных), реализации различаются по режиму. Стратегии, кэш, риск, управление позицией, исполнение и дневник — один и тот же код в обоих режимах. Требование к рефакторингу: поведение боевого режима не меняется ни на такт.
- **Виртуальное рыночное время.** Часы стартуют с нижней границы диапазона; каждый тик продвигает рынок на один минутный бар (шаг `S`), после чего тик ставится на паузу `N` реальных секунд. `N` — только темп просмотра, на результат не влияет. По умолчанию `N = 1` с явным предупреждением о масштабе прогона.
- **Источник данных — локальный эмулятор.** Вместо T-API запросы свечей и каталога инструментов идут в Historical Broker API Emulator по HTTP. Загрузчик свечей и поиск инструмента остаются теми же функциями; подменяется только клиент.
- **Границы диапазона = границы баров.** Диапазон трактуется как `[начало, конец)` по времени *начала* бара: первый обрабатываемый бар открылся в `начале`, последний — в `конец − 1m`. История, взятая до `начала` на прогрев индикаторов, вне диапазона не считается.
- **У прогона есть конец.** Достижение виртуальными часами правой границы завершает цикл (боевой цикл остаётся бесконечным) и формирует отчёт. Отсутствие свежего закрытого бара в истории означает конец данных, а не ожидание таймаута.
- **Предварительная проверка данных.** До старта робот убеждается, что источник доступен, инструменты разрешаются, а свечи покрывают запрошенный диапазон (включая прогрев перед его началом) — иначе прогон не начинается. Полнота данных внутри диапазона перепроверяется по ходу прогона: пропущенные бары считаются и попадают в отчёт, а не остаются незаметными.
- **Отдельное состояние прогона.** Всё, что в бою пишется в `data/`, в истории пишется в `HIST/<начало>_<конец>_<время запуска>/`: дневник сделок (та же схема БД, те же SQL-запросы), CSV-проекции журнала и позиций, аудит-лог расчётов, лог. Прогоны не смешивают P&L.
- **Отчёт прогона.** По завершении и при аварийной остановке пишутся `report.txt` и `report.json` с итогом по прибыли/убытку.
- **Нотификации в истории выключены.** В консоль выводится одна строка о завершении прогона и путь к отчёту; при аварийной остановке — строка с рыночной датой, на которой прогон остановился.
- **Non-Goals:** внутрисвечная точность исполнения глубже рабочего таймфрейма (исполнение и защита считаются по бару ТФ `1m`, как в бою); изменения поведения боевого режима; агрегация таймфреймов на стороне эмулятора; подключение реального брокера (исполнение в обоих режимах — свечная симуляция журнала).

## Capabilities

### New Capabilities

- `historical-mode`: выбор режима при старте, виртуальное рыночное время и его границы, прогрев истории, предварительная проверка данных, завершение прогона, отчёт по прибыли/убытку, каталог состояния прогона.

### Modified Capabilities

- `timing`: рыночные часы становятся портом с двумя реализациями; в историческом режиме тик продвигает часы на фиксированный шаг, а пауза между тиками задаётся параметром и не выводится из границ сетки.
- `orchestration`: выбор режима — часть старта; цикл в историческом режиме завершается по достижении правой границы диапазона, в боевом остаётся бесконечным.
- `api-client`: клиент данных определяется режимом запуска (токен T-API или адрес эмулятора); форма вызова (каталог инструментов, получение свечей) единая для обоих режимов.
- `data-loading`: загрузчик не знает источник данных; правая граница запроса по умолчанию берётся из рыночных часов, а не из системного времени; проверка инструмента выполняется в окне рыночного времени.
- `data-cache`: отсутствие свежего закрытого бара в историческом режиме означает конец доступных данных (прогон завершается), а не повторный опрос до таймаута; пропуски баров внутри диапазона считаются и отражаются в отчёте.
- `execution`: метки времени в журнале, TTL/клиринг и блокировка входов по близкой экспирации контракта считаются по рыночному времени, а не по системному.
- `configuration`: в историческом режиме допускается пустой список каналов уведомлений; корнем состояния прогона становится каталог `HIST/<...>`.

## Impact

- **Код:** `src/scheduler/timing.py` (порты часов), `src/api/client.py` (выбор клиента), `src/data/loader.py` (граница по рыночным часам, работа через клиент порта), `src/instruments/selector.py` (каталог инструментов из источника режима), `src/bot/trading_bot.py` (условие завершения прогона), `src/trade_management/manager.py` и `src/trade_management/audit.py`, `src/broker/journal_broker.py`, `src/trade_journal/storage.py` (рыночное время), `src/notifier/factory.py` (пустой набор каналов), `src/config.py` / `src/config_loader.py` (корень состояния прогона), `run.py` (диалог режима и сборка).
- **Границы задачи:** изменения делаются только в этом проекте. Исторический режим работы с Historical Broker API Emulator — обычный источник данных: тот же контракт запросов и ответов, что и у T-API, без обходов, заглушек и специальных веток в коде.
- **Предварительная проверка:** средствами этого проекта, до старта прогона, по текущему рыночному времени — так же, как в бою.
- **API-нагрузка:** боевой режим не меняется; исторический режим работает по локальному HTTP и не требует токена T-API.
- **Данные:** исполнение и защита считаются по минутным барам, поэтому источник должен отдавать их за весь запрошенный диапазон; полнота проверяется до старта и по ходу прогона, пропуски отражаются в отчёте.
- **Масштаб прогона:** при паузе 1 секунда на тик (1 рыночная минута за секунду) два года — около 12 суток реальной работы. Ускорение задаётся уменьшением паузы; на точность P&L не влияет.
- **Выпуск:** MINOR — появляется новый режим запуска, формат конфигурации не меняется (значения режима вводятся интерактивно).
