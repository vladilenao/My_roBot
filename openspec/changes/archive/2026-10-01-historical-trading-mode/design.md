## Context

Текущий конвейер жёстко привязан к живому T-API в трёх местах, и именно они мешают прогону по истории:

- `src/data/loader.py:60` создаёт `t_tech.invest.Client(token)` внутри функции и читает свечи как `client.get_all_candles(...)`, разбирая ответ через `candle.open.units + candle.open.nano / 1e9`;
- границы запроса по умолчанию берутся из `now()` SDK (`src/data/loader.py:46,52`), а валидация инструмента — из окна «последние 30 дней» (`src/api/client.py`, `find_working_instrument`);
- время берётся из системных часов в торговой логике (`datetime.now()` в `src/trade_management/*`, `src/broker/journal_broker.py`), а цикл `TradingBot._loop` — `while True:` без правой границы.

При этом в коде уже есть два готовых шва: `CandleScheduler`/`MultiTimeframeScheduler` принимают `clock` (`src/scheduler/timing.py:71,223`), а весь каталог состояния выводится из `runtime_dir()` (`src/config.py:228`), который вызывается всего в двух местах (`run.py:64`, `run.py:153`).

План расчёта результата уже существует: `src/trade_journal/reducer.py` держит `net_realized_pnl` по сделке и по счёту, `src/trade_journal/export.py` умеет отдавать сводку по журналу. То есть отчёту не нужен новый расчёт P&L — достаточно построить его поверх редьюсера.

Мотивация и границы изменения — в `proposal.md`; требования — в `specs/`. Ниже только то, что определяет реализацию.

## Goals / Non-Goals

**Goals:**
- Один и тот же конвейер (стратегии → кэш → риск → управление → исполнение → журнал) в обоих режимах; различия только в источнике данных, источнике времени и каталоге состояния.
- Никаких `if historical:` в контуре принятия решений: режим влияет на сборку и на порты, а не на ветки внутри логики.
- Детерминированный результат: одинаковый P&L при любой паузе между тиками и воспроизводимый при повторном прогоне того же диапазона.
- Ранний отказ вместо многочасового прогона «вхолостую» при неполных данных.
- Живой режим не меняется ни на такт: те же сборки, те же файлы, тот же вывод.

**Non-Goals:**
- Внутрисвечная точность исполнения глубже `1m` (как в бою) и честный учёт проскальзывания/комиссий сверх боевой модели.
- Автоматическая загрузка истории в эмулятор, изменение самого эмулятора и его данных.
- Параллельный прогон нескольких диапазонов, сохранение состояния между прогонами, докатирование незакрытых позиций «по последней цене» сверх боевой логики.
- Непубличные API-поля робота: порты остаются внутренними.

## Decisions

### D1. Два порта вместо флага режима

Вводятся два узких порта с реализациями «боевая» / «историческая»:

| Порт | Боевой | Исторический |
|---|---|---|
| `Clock` (`now()`, `sleep_until_boundary()`, `advance()`) | системные часы UTC, ожидание по границе сетки | виртуальные часы, шаг + пауза |
| `ClientProvider` (`client_context()`) | `t_tech.invest.Client(TINKOFF_TOKEN)` | клиент-адаптер Historical Broker API Emulator |

Всё, что уже умеет принимать `clock`, продолжает его принимать (`CandleScheduler`, `MultiTimeframeScheduler`). `load_candles` и `select_instruments` получают клиента из `ClientProvider`; `runtime_dir()` — корень состояния.

**Почему так:** режим — свойство сборки, а не поведения. Одна реализация конвейера физически не может «забыть» про режим, потому что у неё нет параметра режима.

**Альтернативы:** (1) `mode: Literal["live","history"]` в `TradingBot` и ветки `if mode ==` в `_loop`/`_tick` — отвергнуто: ветки размножаются по контуру, и «живое поведение не меняется» перестаёт быть проверяемым; (2) полиморфный наследник `TradingBot` для истории — отвергнуто: дублирование всего оркестратора.

### D2. Семантика границ: тик = момент закрытия бара

Виртуальные часы стартуют в `start` (это состояние нужно загрузчику для прогрева), но готовый бар определяется кэшем по границе **закрытия**. Поэтому первый тик сдвигает часы на шаг: `t₁ = start + S`, и обрабатывается бар `open = start`. Далее `tₖ = start + k·S`, бар `open = start + (k−1)·S`; последний полезный тик — `t = end`, бар `open = end − S`; после него прогон завершается.

Проверка на примере `S = 1m`, диапазон `01.01 00:00 … 02.01 00:00`: тиков ровно 1440, баров 1440, ни один бар вне диапазона не обрабатывается, лишнего «погревочного» тика нет.

**Почему так:** семантика «бар готов, когда наступила его граница закрытия» уже зафиксирована в `data-cache` и `timing`; менять её ради истории значило бы завести отдельный путь готовности. Смещение часов на шаг вперёд — единственное, что нужно, чтобы `start` означал *начало бара*, а не *начало обработки*.

**Альтернативы:** (1) часы на тике равны `open` обрабатываемого бара — требует переопределить `bar_is_ready` в обратную сторону и ломает живую ветку; (2) отдельный «прогревочный» тик без решений — проще, но добавляет тик, на котором `now()` меньше первого бара, и лишнюю ветку в `_loop`.

### D3. Завершение прогона — флаг в цикле, а не исключение

`TradingBot._loop` получает объект прогона с `should_stop()` и `stop_reason()`; условие цикла — `while not run.should_stop():`. Проверка выполняется **после** `_tick`, поэтому последний бар диапазона (`t = end`) успевает обработаться. В боевом режиме `should_stop()` всегда `False` — цикл остаётся бесконечным без других изменений.

**Альтернативы:** (1) sentinel-исключение `HistoricalRunComplete` — отвергнуто: его пришлось бы отличать от «настоящей» ошибки в существующем `except`-блоке `_loop`; (2) отдельный метод `_loop_history` — отвергнуто: дублирование цикла.

### D4. Конец данных — сигнал кэша, а не таймаут ожидания

В истории повторные принудительные перезагрузки отключены (`data_refresh_min_interval` и ожидание публикации не применяются): данные прошлого периода не «задерживаются». Кэш делает одну попытку; если на текущем рыночном моменте бар отсутствует, он возвращает признак конца доступных данных, счётчик пропусков и накопленные бары. Оркестратор завершает прогон с причиной «данные закончились на `<рыночная дата>`» и пишет отчёт.

Разделение двух случаев: отсутствие бара **внутри** диапазона — пропуск (счётчик++, прогон идёт дальше, строка следующего бара доступна); отсутствие баров подряд до конца доступных данных — конец прогона. Это уже сформулировано в `specs/historical-mode`; здесь фиксируется, что детектор — «подряд идущие тики без единого нового бара», а не одна неудачная попытка.

**Альтернативы:** (1) полагаться на `wait_until_bar_published` с таймаутом — отвергнуто: таймаут (`tick_timeout_secs`) добавлялся бы к каждому тику без данных, прогон становится недетерминированным по времени; (2) предварительно скачать весь диапазон в память — отвергнуто: два года `1m` это десятки тысяч баров на инструмент, а память процесса не должна зависеть от длины диапазона.

### D5. Клиент эмулятора — адаптер с тем же поверхностным API, а не DTO

`HistoricalClient` реализует ровно те вызовы, которые использует контур: `get_all_candles(instrument_id, from_, to, interval)`, `instruments.shares/futures/etfs/currencies(instrument_status=...)`, `instruments.get_futures_margin(...)`, плюс `close()`/`__enter__`/`__exit__`. Ответы приводятся к тем же атрибутам, которые читает код (`candle.time`, `candle.open.units/.nano`, `candle.volume`, `instrument.uid/figi/ticker`), с приведением цены к `Decimal` в том же порядке, что у SDK. Сетевой код (retry, пагинация, таймауты) остаётся в существующих `src/api/retry.py` и загрузчике.

**Почему так:** контур, загрузчик и `find_working_instrument` не меняются вообще; эмулятор не становится «вторым API» в коде.

**Альтернативы:** (1) эмуляторные DTO + конвертация в `load_candles` — отвергнуто: `if source is emulator` прямо в загрузчике, то есть ровно та ветка, которой избегаем; (2) запуск эмулятора, говорящего по gRPC T-API — отвергнуто как работа вне границ задачи.

### D6. Предварительная проверка — отдельный модуль до `TradingBot.run()`

`src/history/preflight.py` до старта цикла: (1) источник отвечает; (2) каждый инструмент разрешается тем же `find_working_instrument`; (3) для каждой активной пары (инструмент, ТФ) `load_candles(start − warmup, end)` возвращает данные, а первый бар ≤ `start` (прогрев) и последний ≥ `end − S`; (4) если эмулятор отдаёт границы доступных данных, проверяем вхождение диапазона. `warmup` берётся из существующего `catch_up_bars`, пересчитанного в бары наименьшего активного ТФ, — новой сущности не заводим. Любая неполнота — отказ до прогона с перечислением проблемных пар.

**Альтернативы:** (1) прогрев «как получится» — отвергнуто: отказ через несколько часов прогона стоит дороже секундной проверки; (2) проверять покрытие только в памяти эмулятора — отвергнуто: проверка должна идти тем же кодом, что и прогон.

### D7. Состояние прогона — отдельный корень, та же схема

`runtime_dir(base: Path | None = None)`; при `base=None` поведение не меняется. `run.main` строит имя каталога из границ и времени старта запуска: `HIST/<start>-<end>-<timestamp запуска>/` в компактном безопасном для ФС формате. Дальше `state_dir` передаётся в логи, SQLite журнала, экспорт CSV и аудит — все они уже выводят путь из одного места, поэтому «та же схема БД и те же SQL» выполняется автоматически, а не дисциплиной.

**Альтернативы:** (1) один каталог на все прогоны с тегом режима в именах файлов — отвергнуто: смешивание P&L разных прогонов, о котором шла речь; (2) симлинк на «последний прогон» — отвергнуто: лишняя сущность без пользы.

### D8. Отчёт поверх редьюсера, уведомления — отдельным каналом

P&L и сводка берутся из существующих `ExecutionReducer`/`export` по базе журнала прогона, к ним добавляются счётчики прогона (границы, тики, пропуски, причина завершения). `report.json` — машиночитаемый, `report.txt` — человеческий, короткое имя инструмента `NG-10.26` (не сырой тикер).

В историческом режиме `build_channels([])` возвращает пустой список; `bus.subscribe_all([])` и `close_channels([])` — no-op. Итоговая строка и сообщение об аварийной остановке пишутся напрямую в консоль, а не через шину: это единственный вывод, и он не должен зависеть от наличия каналов.

**Альтернативы:** (1) отдельный канал `history` — отвергнуто: каналы несут уведомления пользователю, а не служебный вывод прогона; (2) считать P&L отдельным просчётом по сделкам — отвергнуто: разойдётся с журналом, который уже является источником истины.

## Risks / Trade-offs

- **Длинный прогон** (2 года при паузе 1 с ≈ 12 суток) → пауза выносится в явный параметр с предупреждением о масштабе; для отладки предлагается запуск на коротком диапазоне, а дефолтом остаётся 1 с.
- **Эмулятор отдаёт неполные минуты** → предварительная проверка покрытия (D6) + счётчик пропусков в отчёте; пропуски не маскируются, а отражаются, чтобы P&L можно было пересчитать после дозагрузки данных.
- **Расхождение с биржевой реальностью** (тики, стопы внутри бара, проскальзывание) → исполнение сознательно остаётся баровым `1m`, тем же кодом, что и в бою; в отчёте фиксируется, что результат — баровая модель.
- **Расхождение с эмулятором по составу эндпоинтов** (нет части методов SDK) → адаптер реализует используемое подмножество; неизвестный вызов SDK в контуре всплывает в тестах контракта, а не в рантайме прогона.
- **`1m` обязателен для защиты** даже если стратегии работают на старших ТФ → `{"1m"}` уже добавляется в `ACTIVE_TIMEFRAMES` в `run.py:79`; в истории это же требование означает, что источник обязан отдавать минутные бары за весь диапазон.
- **Хрупкость порогов готовности** при переходе на шаг `S > 1m` → `S` жёстко связан с наименьшим активным ТФ, а не задаётся свободно.
- **Дрейф живого режима** при правках общих модулей → порты вводятся с сохранением текущих значений по умолчанию, а изменение живого поведения закрывается существующими тестами `tests/unit` и `tests/snapshot`.

## Migration Plan

Изменение обратно совместимо по запуску: `python run.py` без изменений идёт в боевой режим после выбора режима, формат `robot.toml` не меняется, версия — MINOR.

Порядок внедрения (каждый шаг — с тестами, регрессия живого режима):

1. Порты `Clock`/`ClientProvider` + реализация «боевая» как текущее поведение; `run.py` собирает их явно. Ничего не меняется снаружи.
2. Каталог состояния прогона (`runtime_dir(base)`, режим в `run.py`), отчёт и счётчики — на живом режиме они не создаются.
3. Виртуальные часы, шаг и завершение по границе; закрытие цикла по D2/D3.
4. Клиент-адаптер эмулятора и перевод `load_candles`/`find_working_instrument` на `ClientProvider` (живой путь — тот же `t_tech` клиент).
5. Предварительная проверка, отключение повторных перезагрузок в истории, учёт пропусков.
6. Тихий режим: пустые каналы, одна строка по завершении, отчёт при аварийной остановке.

Откат: каждый шаг — отдельный коммит; feature не выносится за флаг, а включается выбором режима, поэтому откат = переход на «всегда боевой режим» одной правкой в `run.py`. Данные прогонов лежат в отдельном каталоге и не влияют на боевые файлы, поэтому откат не требует миграции данных.
