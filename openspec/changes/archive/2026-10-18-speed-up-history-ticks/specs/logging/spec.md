## ADDED Requirements

### Requirement: Лог исторического прогона
Нормативный уровень: MUST.
Исторический прогон ДОЛЖЕН настраивать `bot_debug.log` в каталоге прогона по необязательной секции `[historical.logging]`; боевой режим ДОЛЖЕН по-прежнему использовать `[logging]`.

| Ключ | Тип | По умолчанию |
|---|---|---|
| `level` | DEBUG/INFO/WARNING/ERROR/CRITICAL, без учёта регистра | `INFO` |
| `max_bytes` | целое ≥ 0; `0` — без ротации | `0` |
| `backup_count` | целое ≥ 0 | `0` |
| `debug_from`, `debug_to` | момент `ГГГГ-ММ-ДД ЧЧ:ММ` (без зоны — UTC, с зоной — приводится к UTC) или пустая строка | пусто |

`debug_from` и `debug_to` ДОЛЖНЫ задаваться вместе, и `debug_to` ДОЛЖЕН быть позже `debug_from`. Внутри окна `[debug_from, debug_to)` по рыночному времени прогона в лог ДОЛЖНЫ попадать и записи ниже `level`; вне окна — только записи уровня `level` и выше. Незнакомый ключ, неизвестный уровень, отрицательное или нецелое число, неразборчивый момент, половина окна или пустое окно ДОЛЖНЫ завершать загрузку `ConfigError` с указанием файла и секции.

#### Scenario: Значения по умолчанию
- **WHEN** секции `[historical.logging]` нет
- **THEN** лог прогона пишется с уровня INFO одним файлом без ротации

#### Scenario: Окно отладки
- **WHEN** задано `debug_from = "2025-08-07 14:00+03:00"`, `debug_to = "2025-08-07 18:00+03:00"`
- **THEN** DEBUG-записи пишутся только пока рыночное время прогона в `[2025-08-07 11:00, 2025-08-07 15:00)` UTC

### Requirement: Учёт ротаций лога
Нормативный уровень: MUST.
Обработчик `bot_debug.log` ДОЛЖЕН запоминать момент каждой ротации (рыночный — если переданы рыночные часы). Если ротаций больше `backup_count`, система ДОЛЖНА сообщать, что начало лога удалено, и момент начала самой старой сохранённой части.

#### Scenario: Ротаций больше копий
- **WHEN** при `backup_count = 2` произошло 5 ротаций
- **THEN** лог считается неполным, сохранён с момента третьей ротации

### Requirement: Подтверждение входа стратегии без истории
Нормативный уровень: MUST.
Стратегия, восстанавливающая состояние проигрышем истории кадра, ДОЛЖНА логировать подтверждение входа только для решения по последнему бару, а не для каждого исторического бара проигрыша.

#### Scenario: Проигрыш истории ma_cloud_rsi_macd
- **WHEN** `ma_cloud_rsi_macd` вызывается на каждом баре растущего кадра
- **THEN** строк `Entry Long/Short: third indicator confirmed` столько же, сколько решений BUY/SELL
