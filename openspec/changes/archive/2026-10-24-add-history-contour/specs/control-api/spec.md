## ADDED Requirements

### Requirement: Старт робота и API управления до ядра
Нормативный уровень: MUST. Робот ДОЛЖЕН запускаться без параметров и НЕ ДОЛЖЕН задавать вопросов в консоли. Порядок старта:

1. блокировка `data/robot.pid` и журнал;
2. `core.sqlite3`, пульс, очередь истории;
3. API управления;
4. ядро: рыночная база, арбитр лимитов, календарь, полосы.

API управления ДОЛЖЕН подниматься до ядра и НЕ ДОЛЖЕН зависеть от рыночной базы, брокера, `[market_data] export_enabled` и `independent_lanes`. Адрес — `[market_data] export_host` и `export_port`. После подъёма консоль ДОЛЖНА печатать «Робот запущен» с адресом API без значения ключа.

Без `ROBOT_CONTROL_TOKEN` и при неудачном подъёме API робот ДОЛЖЕН печатать причину и завершаться с кодом `2`. Занятая блокировка `data/robot.pid` ДОЛЖНА завершать запуск с кодом `1`, как прежде.

**Экспорт.** Маршруты экспорта рыночных данных и отчёта кластеров ДОЛЖНЫ отвечать:

- `503` с кодом `MARKET_DATA_NOT_READY`, пока ядро не открыло рыночную базу;
- `404` при `export_enabled = false`.

Ключ экспорта ДОЛЖЕН требоваться, как прежде.

#### Scenario: Обычный старт
- **GIVEN** задан `ROBOT_CONTROL_TOKEN`
- **WHEN** робот запущен без параметров
- **THEN** вопросов в консоли нет, печатается «Робот запущен, API: http://127.0.0.1:8101», затем стартует ядро

#### Scenario: Ключ управления не задан
- **WHEN** робот запущен, а `ROBOT_CONTROL_TOKEN` пуст
- **THEN** печатается, что без ключа управления роботом нельзя управлять, процесс завершается с кодом `2`

#### Scenario: Экспорт до готовности ядра
- **WHEN** ядро ещё открывает рыночную базу, а приходит запрос экспорта с ключом экспорта
- **THEN** ответ `503` с кодом `MARKET_DATA_NOT_READY`

### Requirement: Повтор старта ядра
Нормативный уровень: MUST. Сбой старта ядра НЕ ДОЛЖЕН останавливать робота. Робот ДОЛЖЕН:

- записать причину в консоль и журнал: тип и текст ошибки без секретов;
- закрыть всё, что успела открыть неудачная попытка: полосы, поток, базу;
- повторить старт через 30 секунд, затем с паузой вдвое больше прежней, но не больше 5 минут.

Без `TINKOFF_TOKEN` повтор НЕ ДОЛЖЕН выполняться: ядро остаётся в `failed` до перезапуска робота. Ctrl+C во время паузы ДОЛЖЕН штатно останавливать робота. Пропадание сети после успешного старта сбоем старта не считается: его переживают полосы, как прежде.

При `independent_lanes = false` ядро ДОЛЖНО считаться готовым, когда открыта рыночная база.

**Пока ядро не готово:**

- API управления и история работают;
- `POST /api/v1/contours` отвечает `409` с кодом `CORE_NOT_READY` и состоянием ядра;
- автоподъём контура эмуляции ДОЛЖЕН ждать готовности ядра.

#### Scenario: Брокер недоступен при старте
- **WHEN** старт ядра упал из-за ошибки связи с брокером
- **THEN** робот продолжает работать, `GET /api/v1/core` показывает `state = retrying`, причину и `next_retry_at` через 30 секунд, следующая неудача — через 60 секунд

#### Scenario: Ядро поднялось после повтора
- **GIVEN** желаемое эмуляции «работает», первая попытка старта ядра упала
- **WHEN** вторая попытка удалась
- **THEN** `state = ready`, экспорт отвечает, контур эмуляции поднимается автоподъёмом

#### Scenario: Нет токена брокера
- **WHEN** робот запущен, а `TINKOFF_TOKEN` пуст
- **THEN** ядро в `failed` без повтора, запуск эмуляции отвечает `409 CORE_NOT_READY`, прогоны истории принимаются

### Requirement: Прогон истории командой API
Нормативный уровень: MUST. `POST /api/v1/contours` с телом `{"kind": "history", "from", "to", "pause", "instruments"}` ДОЛЖЕН ставить исторический прогон в очередь робота. Прогон — контур вида `history`; это единственный способ запустить историю.

**Поля тела:**

- `from`, `to` — обязательные, формат `ГГГГ-ММ-ДД ЧЧ:ММ`; без зоны — UTC. `to` не входит в прогон.
- `pause` — пауза между тиками в секундах, число не меньше 0. Без поля — прежнее значение по умолчанию.
- `instruments` — список токенов по правилам параметров запуска. Без поля — `all`.

**Идентификатор.** `id` прогона ДОЛЖЕН иметь вид `history-ГГГГММДД-ЧЧММСС` по времени приёма; при совпадении к нему добавляется `-2`, `-3`. Папка прогона — `data/contours/history/ГГГГММДД-ЧЧММСС[-N]/`.

**Проверка до ответа.** Без обращения к эмулятору данных:

- даты разбираются, начало раньше конца;
- пауза не отрицательная;
- у каждого токена есть привязки в конфигурации;
- семейство и его же контракт не названы вместе.

Выбор контрактов у эмулятора, предпроверка покрытия и прогрев ДОЛЖНЫ выполняться процессом прогона после старта.

**Ответы:**

- `202` — прогон принят; тело — контур прогона в состоянии `queued` или `starting`, заголовок `Location` — `/api/v1/contours/{id}`;
- `400` — тело не JSON-объект, неизвестные поля, нет дат, неразборчивая дата, начало не раньше конца, пауза не число или отрицательная, `instruments` не список строк;
- `401` — нет или неверный ключ управления;
- `422` — хотя бы один токен отклонён; тело содержит отказы с токеном и причиной; прогон НЕ ДОЛЖЕН ставиться в очередь.

Команда ДОЛЖНА приниматься при любом состоянии ядра и контура эмуляции: пока ядро стартует, повторяет старт или не стартовало совсем; в ожидании команды эмуляции, при торговле, после остановки. Прогон НЕ ДОЛЖЕН менять желаемое и состав эмуляции. Инструмент, названный и в истории, и в эмуляции, ДОЛЖЕН торговаться по одним и тем же привязкам `robot.toml`. Эмуляция получает свечи из ядра, прогон — исторические свечи эмулятора данных.

#### Scenario: История без эмуляции
- **GIVEN** робот запущен без параметров и ждёт команду эмуляции
- **WHEN** приходит `POST /api/v1/contours` с `{"kind": "history", "from": "2026-09-01 10:00", "to": "2026-09-08 10:00", "pause": 0, "instruments": ["NG"]}` и верным ключом
- **THEN** ответ `202` с `id` вида `history-20261024-101500` и состоянием `queued` или `starting`, прогон NG начинается, а эмуляция продолжает ждать команду

#### Scenario: История параллельно с эмуляцией
- **GIVEN** контур эмуляции торгует BR
- **WHEN** приходит команда прогона истории с `"instruments": ["BR"]`
- **THEN** прогон BR идёт по историческим свечам эмулятора данных с теми же привязками BR, эмуляция продолжает торговать BR по свечам ядра, желаемое эмуляции не меняется

#### Scenario: История при неготовом ядре
- **GIVEN** ядро не стартовало и ждёт повтора: брокер недоступен
- **WHEN** приходит команда прогона истории с `"instruments": ["SBER"]`
- **THEN** ответ `202`, прогон идёт по свечам эмулятора данных; сверка импорта не подтверждена, это видно в `market_data_sync` и в отчёте

#### Scenario: Начало позже конца
- **WHEN** приходит команда прогона с `"from": "2026-09-08 10:00", "to": "2026-09-01 10:00"`
- **THEN** ответ `400` с причиной, прогон не ставится в очередь

#### Scenario: Токен без привязок
- **WHEN** приходит команда прогона с `"instruments": ["NG", "AFLT"]`, а у AFLT нет привязок
- **THEN** ответ `422` называет AFLT и причину, прогон не ставится в очередь ни по NG, ни по AFLT

#### Scenario: Контракт не найден в эмуляторе
- **WHEN** принят прогон с `"instruments": ["NG-03.20"]`, а такого контракта нет среди контрактов эмулятора на начало прогона
- **THEN** прогон завершается в состоянии `failed`, `reason` и отказы называют NG-03.20, торговля прогона не начинается

### Requirement: Очередь прогонов истории
Нормативный уровень: MUST. Одновременно ДОЛЖНО идти не больше `[contours] max_history_runs` прогонов. Остальные прогоны ДОЛЖНЫ ждать в очереди и стартовать в порядке поступления, как только освободится место.

Перед стартом каждого прогона робот ДОЛЖЕН сам сверить импорт эмулятора данных по требованию «Сверка импорта перед историческим прогоном». Сверки ДОЛЖНЫ выполняться по одной: две сверки одновременно НЕ ДОЛЖНЫ отправляться.

Каждый прогон ДОЛЖЕН идти отдельным процессом того же исполняемого файла с `--contour history <id>`. Журнал прогонов ДОЛЖЕН храниться в таблице `history_runs` базы `core.sqlite3`, писать его ДОЛЖЕН только процесс робота. Вывод процесса прогона в консоль ДОЛЖЕН записываться в `console.log` папки прогона. Консоль робота ДОЛЖНА получать одну строку о старте прогона и одну об итоге.

#### Scenario: Третий прогон ждёт
- **GIVEN** `max_history_runs = 2`, идут два прогона
- **WHEN** приходит команда третьего прогона
- **THEN** ответ `202` с состоянием `queued` и `queue_position = 1`; прогон стартует после завершения одного из двух

#### Scenario: Сверки не пересекаются
- **WHEN** два прогона приняты подряд при свободных местах
- **THEN** робот отправляет вторую сверку импорта только после ответа на первую, и каждый прогон получает свой номер снимка

### Requirement: Состояние прогонов истории
Нормативный уровень: MUST. Прогон ДОЛЖЕН показываться как контур вида `history` в `GET /api/v1/contours` и `GET /api/v1/contours/{id}` (требование «Состояние контура»).

**Состояния прогона:**

| Состояние | Значение |
| --- | --- |
| `queued` | ждёт в очереди |
| `starting` | робот сверяет импорт и запускает процесс |
| `running` | процесс жив |
| `stopping` | стоп запрошен, процесс ещё жив |
| `finished` | процесс вышел с кодом 0 без стопа |
| `stopped` | процесс вышел с кодом 0 после стопа |
| `failed` | процесс не запустился или вышел с другим кодом |
| `cancelled` | убран из очереди командой или остановкой робота |
| `interrupted` | робот перезапущен, процесса прогона нет, итог не записан |

**Поля прогона:**

- `id`, `kind = history`, `state`;
- `request`: `from`, `to`, `pause`, `instruments`;
- времена: `accepted_at`, `started_at`, `finished_at`;
- `queue_position` — только у `queued`;
- `pid` — пока процесс жив; `exit_code` — после выхода;
- `reason` — причина отказа, отмены или сбоя;
- `market_data_sync`: `status`, `snapshot_generation`;
- `actual` из `status.json` прогона или `null`: `phase` (`checking`, `running`, `finishing`), `start`, `end` с учётом сдвига начала, `market_now`, `ticks`, `progress` от 0 до 1;
- `result` из `report.json` или `null`: `covered`, `stop_reason`, `trades`, `net_pnl`, `fees`, `balance`, `open_positions`;
- `dir` — папка прогона относительно папки данных.

Полей эмуляции (`members`, `desired`, `recovery`) у прогона НЕТ. Ответ НЕ ДОЛЖЕН содержать секреты и адрес эмулятора данных.

`POST /api/v1/contours/{id}/instruments` для прогона ДОЛЖЕН отвечать `409` с кодом `NOT_SUPPORTED`: состав прогона после приёма не меняется.

#### Scenario: Прогон идёт
- **GIVEN** прогон NG с 01.09 10:00 по 08.09 10:00 дошёл до 04.09 12:00 рыночного времени
- **WHEN** приходит `GET /api/v1/contours/{id}` прогона
- **THEN** `kind = history`, состояние `running`, `actual.phase = running`, `actual.market_now` — 04.09 12:00, `progress` около 0,44, `result = null`

#### Scenario: Прогон закончен
- **WHEN** процесс прогона записал отчёт и вышел с кодом 0
- **THEN** состояние `finished`, `exit_code = 0`, `result` содержит число сделок и `net_pnl` из `report.json`

#### Scenario: Прогон отклонён предпроверкой
- **WHEN** предпроверка не нашла свечей NG в диапазоне и процесс вышел с кодом 2
- **THEN** состояние `failed`, `exit_code = 2`, `reason` — причина предпроверки

#### Scenario: Состав прогона не меняется
- **WHEN** приходит `POST /api/v1/contours/{id}/instruments` прогона с `{"add": ["SBER"]}`
- **THEN** ответ `409` с кодом `NOT_SUPPORTED`, прогон продолжается

### Requirement: Остановка прогона истории
Нормативный уровень: MUST. `POST /api/v1/contours/{id}/stop` прогона ДОЛЖЕН:

- принимать пустое тело или `{}`; поле `mode` ДОЛЖНО игнорироваться;
- прогон в очереди переводить в `cancelled`, процесс не запускается;
- идущий прогон переводить в `stopping`; процесс останавливается после тика и пишет отчёт с причиной «остановлено оператором»;
- для завершённого прогона отвечать `409` с кодом `NOT_RUNNING`;
- для неизвестного `id` отвечать `404`.

Ответ `200` ДОЛЖЕН содержать прогон после команды.

**Остановка робота.** При штатной остановке робота (Ctrl+C) ДОЛЖНО выполняться:

1. прогоны в очереди переходят в `cancelled` с причиной «робот остановлен»;
2. идущие прогоны останавливаются после тика с отчётом;
3. робот ждёт их выхода до 30 секунд, затем завершает принудительно.

**Рестарт робота.** После рестарта робот НЕ ДОЛЖЕН возобновлять очередь и прерванные прогоны:

- `queued` и `starting` из `history_runs` — `cancelled` с причиной «робот перезапущен»;
- `running` и `stopping` — по папке прогона:
  - **живой прогон** (pid из `robot.pid` жив, `status.json` называет тот же pid, `alive_at` свежее `heartbeat_timeout_secs`) — робот следит за ним по pid, прогон занимает место в очереди, стоп передаётся флагом в `history_runs`; итог берётся из `status.json`;
  - **иначе** — `interrupted`.

Процесс прогона ДОЛЖЕН останавливаться:

- по `stop` в stdin;
- по Ctrl+C;
- по пульсу робота `stopped`;
- по флагу стопа своей строки `history_runs`.

Потеря пульса и пульс другой версии НЕ ДОЛЖНЫ останавливать прогон.

#### Scenario: Отмена из очереди
- **GIVEN** прогон ждёт в очереди
- **WHEN** приходит `POST /api/v1/contours/{id}/stop` прогона
- **THEN** ответ `200`, состояние `cancelled`, процесс не запускается, следующий прогон очереди сдвигается вперёд

#### Scenario: Стоп идущего прогона
- **WHEN** приходит стоп идущего прогона
- **THEN** состояние `stopping`, после тика процесс пишет отчёт «остановлено оператором» и выходит, состояние `stopped`, `result` заполнен

#### Scenario: Ctrl+C робота
- **GIVEN** идут два прогона, один ждёт в очереди
- **WHEN** пользователь нажимает Ctrl+C в консоли робота
- **THEN** оба прогона пишут отчёты и переходят в `stopped`, ждавший — в `cancelled`; после нового старта робота ни один не запускается

#### Scenario: Робот убит при идущем прогоне
- **GIVEN** идёт прогон, процесс робота завершён `kill -9`
- **WHEN** робот запущен снова, а прогон ещё идёт
- **THEN** прогон не прерывается, `GET /api/v1/contours/{id}` показывает `running`, стоп этого прогона работает через флаг в `history_runs`

### Requirement: Лог прогона истории
Нормативный уровень: MUST. `GET /api/v1/contours/{id}/log?tail=N` прогона ДОЛЖЕН отдавать последние строки `bot_debug.log` папки прогона по правилам лога контура: тот же предел `tail`, `text/plain`, `404` для неизвестного `id`.

#### Scenario: Хвост лога прогона
- **WHEN** приходит `GET /api/v1/contours/{id}/log?tail=50` прогона
- **THEN** ответ `200` с последними 50 строками лога прогона

## MODIFIED Requirements

### Requirement: Ожидание команды запуска
Нормативный уровень: MUST. Робот ДОЛЖЕН всегда стартовать в ожидании команд API: эмуляция — командой `POST /api/v1/contours` с `kind = emulation` или автоподъёмом по желаемому, история — той же командой с `kind = history`. Пока робот ждёт, полосы рыночных данных ДОЛЖНЫ работать по сохранённому составу, торговля эмуляции НЕ ДОЛЖНА начинаться без команды или автоподъёма. Консоль ДОЛЖНА показывать адреса команд без значения ключа.

Параметры `--mode`, `--instruments`, `--wait-command`, `--no-prompt`, `--from`, `--to`, `--pause` ДОЛЖНЫ отклоняться: процесс печатает, что робот запускается без параметров, и называет команду `POST /api/v1/contours` для эмуляции и истории, затем завершается с кодом `2`.

#### Scenario: Робот ждёт команды
- **GIVEN** задан `ROBOT_CONTROL_TOKEN`, желаемого «работает» нет
- **WHEN** робот запущен без параметров и ядро стартовало
- **THEN** полосы данных работают, торговли нет, в консоли — «Робот ждёт команду запуска: POST http://127.0.0.1:8101/api/v1/contours», а `GET /api/v1/contours` показывает состояние `waiting_command`

#### Scenario: Ключ управления не задан
- **WHEN** робот запущен, а `ROBOT_CONTROL_TOKEN` пуст
- **THEN** печатается, что без ключа управления роботом нельзя управлять, процесс завершается с кодом `2`

#### Scenario: Несовместимые параметры
- **WHEN** робот запущен с `--mode emulation --instruments NG`
- **THEN** печатается, что робот запускается без параметров, а эмуляция запускается командой `POST /api/v1/contours`; процесс завершается с кодом `2`

### Requirement: Запуск эмуляции командой API
Нормативный уровень: MUST. `POST /api/v1/contours` с телом `{"kind": "emulation", "instruments": [...]}` ДОЛЖЕН запускать торговлю эмуляции выбранными инструментами. Поле `instruments` НЕ ОБЯЗАТЕЛЬНО, его отсутствие ДОЛЖНО означать `all`. Токены инструментов ДОЛЖНЫ разрешаться и проверяться по правилам требования «Инструменты из параметров запуска». Разрешение, сборка торговых компонентов и запуск ДОЛЖНЫ выполняться главным потоком робота, а не потоком HTTP.

Команда ДОЛЖНА приниматься, когда робот ждёт команду, а также после остановки (`stopped`) или падения (`failed`) контура: ядро ДОЛЖНО запустить процесс контура заново тем же процессом робота, без перезапуска приёма данных. Набор инструментов повторного запуска МОЖЕТ отличаться от прежнего. Принятая команда ДОЛЖНА записывать в `core.sqlite3` желаемое «работает» с новым номером поколения и выбранным составом.

Ответы:
- `201` — инструменты разрешены, торговля запускается; тело — состояние контура с выбранными контрактами, эквивалентной командой и номером поколения;
- `202` — проверка инструментов не уложилась в 60 секунд; тело — состояние `starting`, итог виден в `GET /api/v1/contours`;
- `400` — тело не JSON, неизвестные поля, `kind` не `emulation` и не `history` (код `UNSUPPORTED_KIND`), `instruments` не список строк. Команда с `kind = history` ДОЛЖНА обрабатываться по требованию «Прогон истории командой API»;
- `401` — нет или неверный ключ управления;
- `409` — один из кодов:
  - `ALREADY_RUNNING` — контур запускается или торгует;
  - `STOPPING` — контур выполняет остановку и доживает сделки;
  - `CORE_NOT_READY` — ядро стартует, повторяет старт или не стартовало;
  - `CONTOUR_DIR_BUSY` — папку контура держит процесс, который не подтвердил себя контуром;

  тело содержит текущее состояние, набор инструментов не меняется;
- `422` — хотя бы один токен отклонён; тело содержит список отказов с токеном и причиной; торговля НЕ ДОЛЖНА начинаться ни по одному инструменту.

После `422` робот ДОЛЖЕН продолжать ждать команды. Контракты в ответах ДОЛЖНЫ называться коротким именем, а не биржевым тикером. Эквивалентная команда — тело `POST /api/v1/contours` с выбранными контрактами коротким именем; консоль и журнал ДОЛЖНЫ печатать её строкой «Повторить запуск: POST /api/v1/contours {…}».

#### Scenario: Запуск газа и Сбера
- **GIVEN** робот ждёт команды, у NG и SBER есть привязки
- **WHEN** приходит `POST /api/v1/contours` с `{"kind": "emulation", "instruments": ["NG", "SBER"]}` и верным ключом
- **THEN** ответ `201` содержит NG-12.26 с днями до экспирации, SBER, эквивалентную команду `{"kind": "emulation", "instruments": ["NG-12.26", "SBER"]}` и номер поколения, а торговля этими инструментами начинается

#### Scenario: Один инструмент отклонён
- **WHEN** приходит команда с `["NG", "AFLT"]`, а у AFLT нет привязок
- **THEN** ответ `422` называет AFLT и причину, торговля не начинается ни по NG, ни по AFLT, робот продолжает ждать

#### Scenario: Повторный запуск
- **WHEN** торговля уже идёт, а приходит новая команда запуска
- **THEN** ответ `409` с кодом `ALREADY_RUNNING` и текущим состоянием, набор инструментов не меняется

#### Scenario: История через API
- **WHEN** приходит `POST /api/v1/contours` с `{"kind": "history", "from": "2026-09-01 10:00", "to": "2026-09-08 10:00"}`
- **THEN** ответ `202`, прогон истории поставлен в очередь, контур эмуляции и его желаемое не меняются

#### Scenario: Долгая проверка у брокера
- **WHEN** проверка инструментов у источника заняла больше 60 секунд из-за лимитов
- **THEN** ответ `202` с состоянием `starting`, а `GET /api/v1/contours` затем показывает `running` или отказы

#### Scenario: Запуск после остановки другим набором
- **GIVEN** контур эмуляции торговал NG и SBER и остановлен командой, процесс завершился с кодом 0
- **WHEN** приходит `POST /api/v1/contours` с `{"kind": "emulation", "instruments": ["BR", "SBER"]}`
- **THEN** ответ `201` с новым поколением, ядро без перезапуска приёма данных запускает новый процесс контура с BR и SBER

#### Scenario: Запуск во время дожития сделок
- **GIVEN** контур остановлен командой `no_entries` и сопровождает открытую позицию NG
- **WHEN** приходит `POST /api/v1/contours`
- **THEN** ответ `409` с кодом `STOPPING`, остановка продолжается

#### Scenario: Ядро не готово
- **GIVEN** старт ядра упал и ждёт повтора
- **WHEN** приходит `POST /api/v1/contours` с `{"kind": "emulation"}`
- **THEN** ответ `409` с кодом `CORE_NOT_READY` и состоянием ядра, желаемое не меняется

#### Scenario: Папка контура занята
- **GIVEN** `robot.pid` папки контура называет живой процесс, который не подтвердил себя контуром
- **WHEN** приходит команда запуска
- **THEN** ответ `409` с кодом `CONTOUR_DIR_BUSY` и pid; робот, API и история продолжают работать

### Requirement: Состояние контура
Нормативный уровень: MUST. `GET /api/v1/contours` с ключом управления ДОЛЖЕН возвращать список контуров процесса, `GET /api/v1/contours/{id}` — один контур или `404`.

**Состав списка без фильтра:**

- ровно один контур эмуляции с `id` и `kind`, равными `emulation`;
- все прогоны истории в очереди и в работе;
- 20 последних завершённых прогонов, новые первыми.

`?kind=emulation` или `?kind=history` ДОЛЖЕН оставлять один вид; `?limit=N` (1–200) ДОЛЖЕН задавать число завершённых прогонов вместо 20. Неверный `kind` или `limit` — `400`. Ответ ДОЛЖЕН содержать `limits`: `max_history_runs` и число идущих и ждущих прогонов. Поля прогона истории задаёт требование «Состояние прогонов истории».

Поля контура эмуляции:

- **Общее состояние:** `waiting_command`, `starting`, `running`, `stopping_no_entries`, `stopping_close_all`, `stopped` или `failed`.
- **О запуске:**
  - источник запуска: `api`; у желаемого, записанного прежними версиями, МОГУТ быть `cli` или `menu`;
  - время запуска;
  - эквивалентная команда — тело `POST /api/v1/contours`;
  - отказы последней команды, если она отклонена;
  - `recovery`: `autostart`, если процесс поднят ядром без команды; `adopted`, если подхвачен живым; иначе `null`. При автоподъёме и подхвате источник и команда ДОЛЖНЫ браться из желаемого.
- **Текущий желаемый активный состав (`instruments`):** контракты коротким именем с днями до экспирации. После изменения состава командой поле ДОЛЖНО показывать новый состав, а не состав запуска.
- **Участники (`members`):** все инструменты желаемого состава. У каждого:
  - короткое имя и тип;
  - желаемое: `active` или `removed`;
  - режим снятия;
  - фактическое из `status.json`: `warming`, `trading`, `draining`, `closing` или `null`.
- **Желаемое (`desired`)** из `core.sqlite3`:
  - `running` — `true`, если контур должен работать;
  - `stop_mode`;
  - `generation`.
- **Фактическое (`actual`)** из `status.json` контура или `null`, если файла нет или он не читается:
  - состояние;
  - `applied_generation`;
  - `open_positions`;
  - `pending_entries`;
  - `last_tick_at`;
  - `core_link`: `ok` или `lost` — видит ли контур пульс ядра.
- **Процесс контура:** `pid`, пока процесс жив, и `exit_code` после завершения. У подхваченного процесса код выхода неизвестен: `exit_code = null`.

Общее состояние ДОЛЖНО определяться так:

1. **Процесс завершился:** `stopped` при коде 0, `failed` при другом коде или неизвестном коде подхваченного процесса. Если в этом запуске ядра процесс не создавался и не подхватывался — `waiting_command`.
2. **Процесс жив, желаемое «остановлен»:** `stopping_<режим>`.
3. **Процесс жив, контур ещё ни разу не подтвердил курсор ленты в этом запуске ядра:** `starting`.
4. **Иначе:** `running`.

После рестарта ядра без автоподъёма и подхвата контур ДОЛЖЕН показываться в `waiting_command` с прежним желаемым из `core.sqlite3`. Ответ НЕ ДОЛЖЕН содержать сделки, баланс и секреты.

#### Scenario: Торговля запущена параметрами
- **WHEN** эмуляция запущена командой `POST /api/v1/contours` с NG, контур подтвердил курсор, а затем приходит `GET /api/v1/contours`
- **THEN** контур `emulation` в состоянии `running` с источником `api`, контрактом NG, `desired.running = true`, `recovery = null` и `pid` процесса контура

#### Scenario: Последняя команда отклонена
- **WHEN** команда запуска получила `422`, а затем приходит `GET /api/v1/contours`
- **THEN** контур в состоянии `waiting_command` и содержит отказы последней команды

#### Scenario: Процесс контура упал
- **WHEN** процесс контура завершился с кодом 1, а затем приходит `GET /api/v1/contours`
- **THEN** контур в состоянии `failed`, `pid` — `null`, `exit_code` — 1

#### Scenario: Ядро перезапущено, желаемое — работает
- **GIVEN** до рестарта ядра контур работал с поколением 5, источник `api`
- **WHEN** робот запущен снова, контур подтвердил курсор, а затем приходит `GET /api/v1/contours`
- **THEN** контур в состоянии `running`, `recovery = autostart`, источник `api`, `desired.generation = 5`

#### Scenario: Подхваченный контур завершился сам
- **GIVEN** контур подхвачен и завершился, не записав `exited_at`
- **WHEN** приходит `GET /api/v1/contours`
- **THEN** контур в состоянии `failed`, `exit_code = null`

#### Scenario: Фактическое отстаёт от желаемого
- **GIVEN** контур работает с применённым поколением 3
- **WHEN** приходит команда остановки, а `GET` выполняется до следующей границы тика
- **THEN** `desired.generation = 4`, `actual.applied_generation = 3`, общее состояние `stopping_no_entries`

#### Scenario: Список с прогонами
- **GIVEN** эмуляция торгует, идёт один прогон, один ждёт, 25 прогонов завершены
- **WHEN** приходит `GET /api/v1/contours`
- **THEN** в списке эмуляция, оба активных прогона и 20 последних завершённых; `limits` — `max_history_runs = 2`, `running = 1`, `queued = 1`

#### Scenario: Состав после изменения
- **GIVEN** эмуляция запущена с NG и SBER, затем добавлен BR и убран SBER с открытой позицией
- **WHEN** приходит `GET /api/v1/contours/emulation`
- **THEN** `instruments` содержит NG-12.26 и BR-12.26, а `members` — NG `active/trading`, BR `active/warming` и SBER `removed/no_entries/draining`

### Requirement: Автоподъём и подхват контура при старте ядра
Нормативный уровень: MUST. Когда ядро стало готово (требование «Повтор старта ядра»), оно ДОЛЖНО определить судьбу контура эмуляции по `robot.pid` папки контура, её `status.json` и желаемому из `core.sqlite3`.

**Живой контур.** Контур считается живым при трёх условиях:

1. pid из `robot.pid` папки контура жив;
2. `status.json` называет тот же pid;
3. `alive_at` в `status.json` свежее `heartbeat_timeout_secs`.

- **Та же версия.** Ядро ДОЛЖНО подхватить живой контур: НЕ ДОЛЖНО запускать второй процесс, ДОЛЖНО следить за найденным процессом по pid и передавать стоп и состав через `core.sqlite3`. Поле `recovery` — `adopted`.
- **Другая версия.** Ядро ДОЛЖНО ждать выхода контура до 30 секунд. Контур выходит сам, увидев пульс другой версии. Если процесс не вышел, ядро ДОЛЖНО завершить его принудительно. Затем ядро ДОЛЖНО действовать так, как если бы живого контура не было.
- **Контур уже выходит.** `status.json` того же pid содержит `exited_at`, а процесс ещё жив. Ядро ДОЛЖНО ждать его выхода так же, как контура другой версии.
- **Процесс не подтвердил себя.** pid из `robot.pid` жив, но два других условия не выполнены. Ядро НЕ ДОЛЖНО завершать такой процесс и НЕ ДОЛЖНО запускать контур. Консоль и журнал ДОЛЖНЫ назвать pid, который нужно завершить. Робот ДОЛЖЕН продолжать работать: API и история доступны, команда запуска эмуляции проверяет папку заново и отвечает `409 CONTOUR_DIR_BUSY`, пока процесс жив.

**Живого контура нет.**

- **Явного запуска при старте нет:** робот всегда стартует в ожидании команды. Новое желаемое с новым поколением ДОЛЖНА записывать только команда `POST /api/v1/contours`.
- **Автоподъём.** При `[contours] autostart = true` (по умолчанию) ядро ДОЛЖНО поднимать контур без команды в двух случаях:
  - желаемое «работает»;
  - желаемое «остановлен», а последний `status.json` показывает `stopping_*`, а не `stopped`.

  Иначе ядро ДОЛЖНО ждать команду.
- **Автоподъём:**
  - НЕ ДОЛЖЕН создавать новое поколение и менять режим остановки;
  - состав процесса — активные участники и снятые участники, которых последний `status.json` ещё показывал в `members`;
  - карточки контрактов ядро ДОЛЖНО запросить заново, при сбое — взять сохранённые;
  - поле `recovery` — `autostart`.

Подхват ДОЛЖЕН работать и при `autostart = false`.

Итог выхода подхваченного процесса:
- `status.json` с `exited_at` позже подхвата — `stopped` с кодом 0;
- иначе — `failed` с `exit_code = null`.

При остановке ядра подхваченный процесс ДОЛЖЕН останавливаться по пульсу `stopped`. Если процесс не вышел за 30 секунд, ядро ДОЛЖНО завершить его принудительно. Ни при каком исходе на одной папке контура НЕ ДОЛЖНО работать два процесса.

#### Scenario: Рестарт после Ctrl+C
- **GIVEN** эмуляция торговала NG с открытой позицией, ядро остановлено Ctrl+C, контур завершился с кодом 0
- **WHEN** робот запущен снова
- **THEN** ядро без команды запускает контур с NG и прежним поколением, `recovery = autostart`, позиция NG восстановлена из журнала и сопровождается

#### Scenario: Ядро убито, контур жив
- **GIVEN** ядро завершено `kill -9`, контур той же версии жив и пишет `alive_at`
- **WHEN** ядро запущено снова
- **THEN** второй процесс контура не запускается, `GET /api/v1/contours` показывает прежний pid и `recovery = adopted`, команда `stop` доходит до контура через `core.sqlite3`

#### Scenario: Обновление версии
- **GIVEN** контур версии 7.1.0 жив после аварийной смерти ядра 7.1.0
- **WHEN** запускается робот 7.2.0
- **THEN** контур 7.1.0 видит пульс другой версии и выходит после тика, ядро 7.2.0 поднимает контур своей версии с прежним составом и поколением

#### Scenario: Остановка не дожила
- **GIVEN** контур выполнял `stop no_entries` с открытой позицией SBER, ядро и контур остановлены Ctrl+C
- **WHEN** робот запущен снова
- **THEN** контур поднимается, продолжает остановку `no_entries`, после закрытия SBER выходит со `stopped` и больше не поднимается

#### Scenario: Контур был остановлен командой
- **GIVEN** желаемое «остановлен», последний `status.json` — `stopped`
- **WHEN** робот запущен
- **THEN** контур не запускается, ядро ждёт команду

#### Scenario: Явный запуск важнее базы
- **GIVEN** желаемое «работает» с NG, контур поднят автоподъёмом и затем остановлен командой
- **WHEN** приходит `POST /api/v1/contours` с `["SBER"]`
- **THEN** записано новое поколение с SBER, контур запускается с SBER

#### Scenario: Явный запуск при живом контуре
- **GIVEN** живой контур той же версии торгует NG и подхвачен после рестарта робота
- **WHEN** приходит `POST /api/v1/contours` с `["SBER"]`
- **THEN** ответ `409 ALREADY_RUNNING`, желаемое не меняется, контур продолжает с NG

#### Scenario: Чужой процесс с тем же pid
- **GIVEN** `robot.pid` папки контура называет живой pid, а `alive_at` в `status.json` устарел
- **WHEN** ядро стартует
- **THEN** процесс не завершается, контур не запускается, консоль называет pid, который нужно завершить, робот продолжает работать

#### Scenario: Нет ключа управления
- **GIVEN** желаемое «работает», `ROBOT_CONTROL_TOKEN` пуст
- **WHEN** робот запущен
- **THEN** контур не поднимается, запуск завершается с кодом `2`

#### Scenario: Автоподъём отключён
- **GIVEN** `[contours] autostart = false`, желаемое «работает», живого контура нет
- **WHEN** робот запущен
- **THEN** ядро ждёт команду, `GET /api/v1/contours` показывает `waiting_command` с прежним желаемым

#### Scenario: Автоподъём ждёт ядро
- **GIVEN** желаемое «работает» с NG, первая попытка старта ядра упала
- **WHEN** повтор старта ядра удался
- **THEN** только после этого ядро поднимает контур с NG и прежним поколением, `recovery = autostart`

### Requirement: Состояние ядра
Нормативный уровень: MUST. `GET /api/v1/core` с ключом управления ДОЛЖЕН возвращать:

- версию, pid и время старта ядра;
- состояние старта ядра `state`: `starting`, `ready`, `retrying` или `failed`; `error` — причина последней неудачи без секретов или `null`; `attempts` — число попыток; `next_retry_at` — время следующей попытки или `null`;
- время последнего удара пульса и `heartbeat_secs`;
- сводку рыночных данных:
  - `producer_id` и наибольший номер изменения ленты;
  - число живых пар и их число по состояниям готовности;
- запросы к брокеру за последнюю минуту по сервисам: число, потолок, разбивку по полосам и паузу после ограничения.

До `ready` сводка рыночных данных ДОЛЖНА быть `null`, а запросы к брокеру — пустыми. Маршрут ДОЛЖЕН отвечать при любом состоянии ядра.

Ответ НЕ ДОЛЖЕН содержать секреты, адреса и токены. Маршрут ДОЛЖЕН подчиняться правилам доступа к управлению. Ключ экспорта рыночных данных ДОЛЖЕН получать `401`.

#### Scenario: Состояние ядра
- **WHEN** приходит `GET /api/v1/core` с ключом управления
- **THEN** ответ `200` с версией робота, временем удара не старше 5 секунд, числом пар по состояниям и запросами котировок за минуту

#### Scenario: Чужой ключ
- **WHEN** приходит `GET /api/v1/core` с ключом экспорта рыночных данных
- **THEN** ответ `401`

#### Scenario: Ядро повторяет старт
- **WHEN** старт ядра упал и приходит `GET /api/v1/core`
- **THEN** ответ `200` с `state = retrying`, типом ошибки в `error`, `attempts = 1`, `next_retry_at` и `market_data = null`

### Requirement: Остановка контура командой
Нормативный уровень: MUST. `POST /api/v1/contours/{id}/stop` с телом `{"mode": "no_entries"}` или `{"mode": "close_all"}` ДОЛЖЕН записывать в `core.sqlite3` желаемое «остановлен» с режимом и новым поколением и отвечать `202` с номером поколения и состоянием контура. Повтор команды с тем же режимом ДОЛЖЕН отвечать `200` с прежним поколением и НЕ ДОЛЖЕН его менять. `close_all` поверх `no_entries` ДОЛЖЕН приниматься новым поколением. `no_entries` поверх `close_all` ДОЛЖЕН отклоняться `409`.

Остальные ответы:
- `409` — контур не работает: `waiting_command`, `stopped` или `failed`;
- `400` — неверный режим или лишние поля;
- `404` — неизвестный `id`;
- `401`/`403` — по правилам доступа к управлению.

Правила этого требования относятся к контуру эмуляции. Остановку прогона истории задаёт требование «Остановка прогона истории»: тело может быть пустым, режим не применяется.

Остановка НЕ ДОЛЖНА останавливать ядро, приём данных и локальный API. Ctrl+C ядра ДОЛЖЕН по-прежнему останавливать процесс контура после тика, не меняя желаемое состояние.

#### Scenario: Остановка без новых входов
- **GIVEN** контур работает, поколение 3
- **WHEN** приходит `POST /api/v1/contours/emulation/stop` с `{"mode": "no_entries"}`
- **THEN** ответ `202` с поколением 4, в `core.sqlite3` желаемое «остановлен, no_entries», ядро и приём данных продолжают работать

#### Scenario: Повтор остановки
- **GIVEN** уже принята остановка `no_entries` с поколением 4
- **WHEN** та же команда приходит снова
- **THEN** ответ `200` с поколением 4, в журнале команд исход `ignored`

#### Scenario: Закрыть всё поверх дожития
- **GIVEN** контур доживает сделки после `no_entries`, поколение 4
- **WHEN** приходит `stop` с `{"mode": "close_all"}`
- **THEN** ответ `202` с поколением 5, контур переходит к закрытию всех позиций

#### Scenario: Нечего останавливать
- **WHEN** контур в состоянии `stopped`, а приходит `stop`
- **THEN** ответ `409`, поколение не меняется
