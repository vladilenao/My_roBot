## ADDED Requirements

### Requirement: Исторический контур отдельным процессом
Нормативный уровень: MUST. Каждый исторический прогон ДОЛЖЕН идти отдельным процессом того же исполняемого файла с `--contour history <id>`. Процесс запускает робот из очереди прогонов (спецификация `control-api`).

Процесс ДОЛЖЕН:

1. занять блокировку `robot.pid` папки прогона;
2. вести `bot_debug.log` по настройкам `[historical.logging]`, с маскированием секретов, как другие процессы робота;
3. прочитать `launch.json`: диапазон, паузу, токены инструментов, итог сверки импорта и номер снимка;
4. пройти прежний путь истории:
   - выбор контрактов у эмулятора данных;
   - контрактная цепочка и расписание прогона;
   - предпроверка покрытия;
   - тики;
   - отчёт `report.txt` и `report.json`;
5. вести `status.json`: фаза (`checking`, `running`, `finishing`), диапазон с учётом сдвига начала, рыночное время, число тиков, отказы инструментов, признак жизни, итог выхода.

Если предпроверка сдвинула начало на первую доступную свечу, процесс ДОЛЖЕН собрать прогон заново в той же папке. Файлы журнала и выбора прошлой попытки удаляются; `launch.json`, `status.json`, логи и `robot.pid` остаются. Повтор ровно один, на том же снимке.

Коды выхода:

- `0` — отчёт записан;
- `2` — прогон отклонён до первого тика;
- другой — сбой. Отчёт при сбое пишется, как прежде.

Процесс НЕ ДОЛЖЕН читать ленту ядра и обращаться к брокеру. Уведомления НЕ ДОЛЖНЫ отправляться.

#### Scenario: Прогон тем же путём
- **GIVEN** прежний `--mode history` на диапазоне, инструментах и снимке дал набор сделок
- **WHEN** тот же диапазон и инструменты запущены командой `POST /api/v1/contours` с `kind = history` на том же снимке
- **THEN** процесс прогона даёт те же сделки и тот же итог `report.json`, кроме времени запуска и пути папки

#### Scenario: Сдвиг начала
- **GIVEN** первая доступная свеча позже начала диапазона
- **WHEN** предпроверка сдвигает начало
- **THEN** прогон собирается заново в той же папке, `status.json` показывает новое начало, журнал содержит только сделки второй попытки

## MODIFIED Requirements

### Requirement: Выбор режима при старте
Нормативный уровень: MUST. При старте робот НЕ ДОЛЖЕН предлагать выбор режима и НЕ ДОЛЖЕН задавать вопросов: ни меню, ни параметров режима. Робот запускается без параметров и ждёт команд API (спецификация `control-api`):

- эмуляция (торговля на живых данных с симулятором исполнения, прежде — «боевой» режим) — `POST /api/v1/contours` или автоподъём по желаемому;
- историческая торговля — `POST /api/v1/contours` с `kind = history`.

Историческая торговля НЕ ДОЛЖНА зависеть от готовности ядра: прогон принимается и идёт, пока ядро стартует, повторяет старт или не стартовало.

Параметры `--mode`, `--instruments`, `--wait-command`, `--no-prompt`, `--from`, `--to` и `--pause` ДОЛЖНЫ отклоняться: процесс печатает, что робот запускается без параметров, называет оба маршрута API и завершается с кодом `2` без запуска торговли.

#### Scenario: Выбран боевой режим
- **WHEN** пользователь запускает робота без параметров
- **THEN** вопросов о режиме и инструментах нет, консоль печатает адрес API, эмуляция запускается командой `POST /api/v1/contours` или автоподъёмом

#### Scenario: Выбран исторический режим
- **WHEN** пользователь хочет исторический прогон
- **THEN** он отправляет `POST /api/v1/contours` с `kind = history` работающему роботу; консоль о диапазоне не спрашивает

#### Scenario: История параметрами без вопросов
- **WHEN** робот запущен с `--mode history --from "2026-09-01 10:00" --to "2026-09-08 10:00" --pause 0`
- **THEN** печатается, что робот запускается без параметров, а история — командой `POST /api/v1/contours` с `kind = history`; процесс завершается с кодом `2`, прогон не начинается

#### Scenario: Ошибка в параметрах
- **WHEN** робот запущен с `--from "2026-09-01 10:00"`
- **THEN** печатается та же подсказка, процесс завершается с кодом `2`

#### Scenario: Запуск без вопросов по старому флагу
- **WHEN** робот запущен с `--no-prompt`
- **THEN** печатается, что флаг больше не нужен и робот запускается без параметров; процесс завершается с кодом `2`

#### Scenario: Повтор запуска из меню
- **WHEN** пользователь скопировал эквивалентную команду из консоли или из состояния контура
- **THEN** это тело `POST /api/v1/contours`, и запрос с ним запускает эмуляцию с теми же контрактами

#### Scenario: История без готового ядра
- **GIVEN** старт ядра упал и ждёт повтора
- **WHEN** приходит `POST /api/v1/contours` с `kind = history`
- **THEN** прогон ставится в очередь и идёт по свечам эмулятора данных

### Requirement: Изоляция состояния прогона
Нормативный уровень: MUST. Все данные, которые в эмуляции сохраняются в папке контура, исторический прогон ДОЛЖЕН сохранять в своей папке `data/contours/history/ГГГГММДД-ЧЧММСС/` по времени приёма прогона; при совпадении к имени добавляется номер. Контур прогона в API называется `history-` и именем папки. Данные прогона НЕ ДОЛЖНЫ смешиваться с данными эмуляции и других прогонов, в том числе идущих одновременно. Дневник сделок ДОЛЖЕН использовать ту же схему базы данных и те же SQL-запросы, что и в эмуляции, отличаясь только расположением файла. Старые прогоны в `HIST/` ДОЛЖНЫ оставаться на месте.

#### Scenario: Два прогона не смешивают результаты
- **WHEN** два прогона по разным диапазонам выполняются одновременно
- **THEN** каждый прогон имеет собственную папку в `data/contours/history/`, и результаты прогонов не влияют друг на друга

#### Scenario: Боевые данные не затронуты
- **WHEN** выполняется исторический прогон при работающей эмуляции
- **THEN** файлы журнала сделок и проекций контура эмуляции не изменяются

#### Scenario: Схема дневника совпадает с боевой
- **WHEN** исторический прогон записывает сделки в дневник
- **THEN** используется та же схема базы данных и те же SQL-запросы, что и в эмуляции

### Requirement: Сверка импорта перед историческим прогоном
Нормативный уровень: MUST. Перед стартом каждого нового исторического прогона робот ДОЛЖЕН вызвать у Historical Broker API Emulator внеочередную синхронизацию журнала через `POST /api/v1/market-import/sync`. Вызов ДОЛЖЕН предшествовать запуску процесса прогона, а значит выбору инструментов, предпроверке покрытия, прогреву и чтению свечей. Сверки разных прогонов ДОЛЖНЫ выполняться по одной. Если ядро не готово и экспорт My Robot не отвечает, сверка не подтверждается, и прогон идёт по правилу ниже.

Успешной сверкой ДОЛЖЕН считаться только ответ `synchronized=true` с корректным номером снимка и достигнутой границей журнала. Итог сверки и номер снимка ДОЛЖНЫ передаваться процессу прогона в `launch.json`. Процесс ДОЛЖЕН использовать этот снимок на протяжении всего прогона, включая повтор после сдвига начала диапазона, и НЕ ДОЛЖЕН вызывать синхронизацию сам. Новый прогон ДОЛЖЕН получать новую сверку.

Если эмулятор не подтвердил синхронизацию, робот ДОЛЖЕН явно показать причину и НЕ ДОЛЖЕН объявлять прогон синхронизированным с My Robot:

- в строке консоли робота о старте прогона;
- в `market_data_sync` прогона в API;
- в отчётах прогона.

Прогон МОЖЕТ продолжиться по независимой исторической БД без снимка при успешной обычной предпроверке доступности и покрытия. Статус сверки, `producer_id`, граница, достигнутый курсор и номер снимка ДОЛЖНЫ быть сохранены в текстовом и машинном отчётах прогона. Неизвестные значения остаются пустыми, секреты не записываются.

#### Scenario: Журнал догнан перед новым прогоном
- **WHEN** эмулятор подтверждает достижение границы журнала и возвращает номер снимка
- **THEN** робот передаёт снимок в `launch.json`, процесс прогона начинает предпроверку и прогон с этим снимком и сохраняет подтверждённый статус в отчёте

#### Scenario: Экспорт недоступен, но историческая БД доступна
- **WHEN** `sync` возвращает ошибку или не подтверждает догоняющую синхронизацию, а обычная предпроверка исторической БД проходит
- **THEN** робот сообщает, что импорт My Robot не подтверждён, прогон продолжается без снимка, статус отражён в API и отчёте

#### Scenario: Сам исторический источник недоступен
- **WHEN** синхронизация не удалась и обычная предпроверка эмулятора также не проходит
- **THEN** прогон не начинается по существующему правилу предварительной проверки данных и завершается в состоянии `failed`

#### Scenario: Начало диапазона сдвинуто предпроверкой
- **WHEN** предпроверка требует повторного построения того же прогона с более позднего начала
- **THEN** процесс прогона сохраняет снимок из `launch.json` и не вызывает `sync`

#### Scenario: Пользователь начинает следующий прогон
- **WHEN** предыдущий исторический прогон закончился и запущен новый
- **THEN** робот заново вызывает `sync`, новый прогон не наследует номер снимка предыдущего
