## Context

Сейчас журнал считает реализованный PnL в «сырых» единицах `направление × (выход − средняя) × объём` в чистой функции reducer'а (`src/trade_journal/reducer.py`, ветка reduce). Рублёвое значение живёт только в памяти брокера-симулятора (`src/broker/journal_broker.py::_pnl` = `(выход − средняя) / price_step × step_cost × qty` со знаком стороны, fallback в сырьё при `price_step <= 0`) и в SQLite не сохраняется. При этом `Initial Risk` (`reservations.original_risk_amount` → `export._initial_risk`) и комиссии (`event.fee`) уже рублёвые.

Ограничения текущего состояния, которые формируют дизайн:
- в `trades` (schema v7) нет колонок факторов контракта, а `TradePlan` метаданных контракта не несёт;
- метаданные контракта (`price_step`, `step_cost`) доходят до брокера (`run.py: broker.set_contracts`) и CSV-экспортёра (`storage.set_contract_metadata`), но НЕ до reducer'а;
- схема версионирована (SCHEMA_VERSION 7, цветочная цепочка миграций v1…v7 в `initialize_schema`);
- по решению пользователя пересчёт истории НЕ выполняется: рублёвая эпоха начинается только для сделок, созданных после апгрейда.

## Goals / Non-Goals

**Goals:**
- Схема v8: снапшот факторов контракта (`price_step`, `step_cost`) на каждой создаваемой сделке.
- Reducer считает и сохраняет Gross/Net PnL в рублях для сделок новой эпохи (детерминированно, пригодно к реплею).
- Агрегаты счёта переосновываются на рублёвую эпоху, чтобы не смешивать единицы.
- `trade_summary.csv` помечает единицы PnL: `RUB` (новая эпоха) / `RAW` (история), `Result`/`MAE`/`MFE` для рублёвых сделок становятся корректными R.
- Обновление `docs/database.md` (версия 8, политика единиц и re-baseline).

**Non-Goals:**
- Пересчёт/бэкфилл закрытых сделок прежней эпохи.
- Изменение источника и правил комиссии (остаётся `event.fee` из события исполнения).
- Изменение рублёвой бухгалтерии в памяти брокера-симулятора.
- Новые пользовательские файлы.

## Decisions

**1. Снапшот факторов хранится в `trades` (колонки `price_step`, `step_cost`).**
Сделка получает факторы один раз при создании. Это даёт детерминированный пересчёт при реплее независимо от живого `contracts`-маппинга (шаг цены фьючерса может меняться между сессиями/экспирациями) и аудируемость.
Альтернатива: передать контрактный маппинг в Storage/reducer (механизм `set_contract_metadata` уже есть) и брать факторы по `trades.instrument_id` на момент закрытия. Отклонена: реплей после рестарта зависел бы от «сегодняшнего» маппинга, а не момента сделки, и был бы недетерминирован при смене контракта.

**2. Источник факторов при создании сделки — метаданные контракта в менеджере.**
`TradePlan` факторов не содержит, но в месте допуска сигнала (`admit_signal`) доступны `meta.price_step`/`meta.step_cost`. «Рублёвая стоимость пункта» уже считается менеджером в `_size_open_quantity` (`step_cost / price_step`). Дизайн: `submit_plan` получает параметры `price_step: Decimal | None = None`, `step_cost: Decimal | None = None`; `admit_signal` передаёт их из `meta`; `INSERT INTO trades` пишет их. `NULL` означает «сделка без факторов» → прежний сырой расчёт (fallback).

**3. Рублёвая формула живёт в reducer'е — единственном источнике PnL журнала.**
`apply_fill`/`apply_fill_with_trace` получают опциональные `price_step`/`step_cost`. Для reducing-филла, когда `price_step` не NULL и > 0:
`gross = direction × (price − avg) / price_step × step_cost × quantity` (Decimal-арифметика, как требуется снапшоту); иначе — прежний сырой `gross = direction × (price − avg) × quantity` (тот же fallback, что у брокера при `price_step <= 0`). `ExecutionReducer.apply` дочитывает факторы из `trades` вместе с `side` (текущий `SELECT side`) и пробрасывает в `apply_fill_with_trace`. Net = gross − fee; fee из `event.fee` (решение №6). Баланс/equity накапливают `gross − fee`, как сегодня — но для новой эпохи уже в рублях.

**4. Re-baseline счёта на миграции v7→v8 (рублёвая эпоха).**
Следствие выбора «только новые сделки»: агрегаты `account` нельзя смешивать (баланс содержал бы legacy-«сырьё» плюс новые рубли). В миграции v7→v8 агрегаты переосновываются один раз: `balance = equity = initial_deposit`, `realized_pnl = fees = net_realized_pnl = '0'`. `initial_deposit` берётся из конфигурации: `initialize_schema(connection, initial_balance: str | None = None)`, значение пробрасывается через `connect(...)` и конструктор `Storage` (новый необязательный параметр; `None` — только схема, без сброса, для инструментов без конфига). Reset выполняется внутри транзакции миграции → строго один раз. Ratio: результат за «сырую» эпоху технически был бессмыслен в рублях, поэтому сброс честен; история сделок при этом не удаляется и остаётся в БД и CSV.

**5. Экспорт помечает единицы PnL.**
Маркер выводится всегда (однозначность, а не только при смешанной истории): в `trade_summary.csv` добавляется колонка с заголовком «Ед. PnL» и значениями `RUB`/`RAW` (тип логики: у сделки есть ненулевые факторы → `RUB`, иначе `RAW`). Для `RAW`-строк `Result`/`MAE`/`MFE` вычисляются как раньше (история не трогается); для `RUB`-строк обе части R-отношений рублёвые.

**6. Комиссия и остальные пользовательские поля не меняются.**
Источник комиссии — `event.fee` из события исполнения (текущая практика; брокер где нужно применяет 0.1%). `trade_event.csv` единиц не приобретает (в нём нет PnL-колонок).

## Risks / Trade-offs

- [Смешанные единицы в базе/CSV (RAW история + RUB новые)] → маркер «Ед. PnL» в карточке; агрегаты счёта изолированы re-baseline; политика зафиксирована в `docs/database.md`.
- [Потеря кумулятивного итога счёта «сырой» эпохи (гросс-сумм в прежних единицах)] → прямое следствие выбора «только новые сделки»; необратимо только в агрегате, строки сделок сохраняются.
- [Открытые на момент миграции сделки без факторов: их последующие выходы журналируются в сырых единицах] → согласуется с «только новые сделки»; допускается как известное ограничение; дозаполнение факторов открытым позициям — вне scope (можно отдельным change).
- [Re-baseline требует `initial_deposit` из конфига; если депозит в конфиге изменился] → сброс использует значение на момент миграции (единственный доступный); миграция однократна, значение фиксируется в SQLite в момент выполнения.
- [Расхождение 1 коп. между Decimal-расчётом журнала и `round`-брокера] → журнал — источник истины; брокерская память остаётся внутренним состоянием симулятора.
- [Деление на `price_step <= 0` или NULL] → fallback в сырьё (то же условие, что у брокера); защищено в reducer-функции.

## Migration Plan

1. Перед первым запуском версии с v8 — резервная копия `data/trades.sqlite3` (инструкция в release-заметках; робот применяет миграцию при открытии базы).
2. Деплой кода с `SCHEMA_VERSION = 8`: `initialize_schema` поднимет существующую v7-базу, добавив колонки факторов и выполнив re-baseline счёта; `initial_deposit` приходит из конфига через `Storage`/`connect`.
3. Проверка: полный `pytest`, затем сверка экспорта — строки за 2026-09-24 остаются помечены `RAW`, новая сделка закрывается с рублёвым PnL.
4. Откат: восстановление резервной копии; «понижающей» миграции v8→v7 нет (v7-бинарник не откроет базу v8).

Нет: ключевые развилки (маркер всегда, reset баланса, fallback для открытых позиций) решены выше и отражены в спеках; оставшиеся мелочи не меняют спеки, подход или разбивку задач.
