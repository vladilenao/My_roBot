## Why

При запуске бота первый тик вместо анализа последней закрытой свечи часто упирается в rate limit Tinkoff Invest API (`RESOURCE_EXHAUSTED`). Причина — избыточные запросы: на каждом опросе ожидания свежего бара принудительно перекачиваются все инструменты, а каждая дозагрузка заново вызывает `find_working_instrument` (листинг инструментов + пробная свеча), хотя данные уже есть в кэше.

## What Changes

- Первый тик при запуске перекачивает данные с API только если ожидаемый закрытый бар отсутствует в кэше: проверка готовности бара выполняется по текущим данным, принудительная дозагрузка — только когда бара действительно нет.
- UID инструмента кэшируется на время сессии и переиспользуется при инкрементальных дозагрузках: `find_working_instrument` вызывается один раз на инструмент, а не на каждый `refresh`.
- Поведение границы сохраняется: при запуске сразу после закрытия и отсутствии свежего бара первый тик по-прежнему ограниченно опрашивает API с малыми паузами до появления бара (или до таймаута).

### Modified Capabilities
- `orchestration`: требование «Выравнивание итерации по закрытию свечи» — первый тик не должен дозагружать уже доступные данные; принудительная перекачка выполняется только при отсутствии ожидаемого закрытого бара.
- `data-loading`: требование «Определение UID инструмента» — разрешённый UID переиспользуется при повторных загрузках того же инструмента, повторное разрешение не выполняется.

## Impact

- `src/bot/trading_bot.py` — `_bar_is_ready()` получает early-exit на проверке кэша.
- `src/data/cache.py` — кэш UID инструментов, передача в загрузчик.
- `src/data/loader.py` — приём уже разрешённого `instrument_id`, пропуск `find_working_instrument`.
- Тесты: `tests/unit/bot/test_trading_bot.py`, `tests/unit/data/test_loader.py` (и при необходимости `tests/unit/data/test_cache.py`).
- Снижение объёма запросов к API, устойчивость к rate limit при запуске.
