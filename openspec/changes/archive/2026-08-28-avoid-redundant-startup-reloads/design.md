## Context

См. proposal.md — «Why»: при запуске первый тик упирается в rate limit из-за двух источников избыточных запросов.

Текущее состояние, релевантное дизайну:

- `TradingBot._bar_is_ready()` (`src/bot/trading_bot.py:112`) безусловно вызывает `refresh_if_new_candle(force=True)` перед проверкой `has_fresh_closed_bar()` — лишняя перекачка даже когда ожидаемый закрытый бар уже есть в кэше.
- `MarketDataCache._load()` (`src/data/cache.py:37`) каждый раз создаёт клиент и вызывает `load_candles`, который внутри делает `find_working_instrument` (листинг инструментов + пробная свеча) — при инкрементальных дозагрузках повторяет разрешение на каждом refresh.
- `load_candles` уже возвращает `(df, instrument_id)` (`src/data/loader.py:14`), но кэш это значение игнорирует.

## Goals / Non-Goals

**Goals:**
- Устранить повторные API-запросы на старте: готовность бара проверять по кэшу, дозагружать только при реальном отсутствии бара.
- Разрешать UID инструмента один раз за сессию и переиспользовать при дозагрузках.
- Сохранить сценарий «Первый тик на границе ожидает свежий бар» (ограниченный опрос до появления бара/таймаута).

**Non-Goals:**
- Троттлинг/батчинг самой первичной загрузки 30-дневной истории (не входит в scope, retry остаётся страховкой).
- Изменение retry-политики (`src/api/retry.py`) и поведения `find_working_instrument`.

## Decisions

1. **Early-exit в `_bar_is_ready` (уровень оркестратора)**

   ```
   if data_cache.has_fresh_closed_bar(): return True
   data_cache.refresh_if_new_candle(force=True)
   return data_cache.has_fresh_closed_bar()
   ```
   Запуск в середине периода (обычный случай) делает ноль лишних перекачек; запуск на границе по-прежнему опрашивает API, пока бар не появится (цикл опроса гоняет `_bar_is_ready` с паузами до таймаута).
   *Альтернатива:* оставить безусловную перекачку, но реже (увеличить `poll_secs`). Отклонено — лечит симптом, а не причину; на границе свежий бар всё равно нужен.

2. **Кэш UID в `MarketDataCache` (уровень кэша)**

   - `_load()` сохраняет возвращённый `instrument_id` в `self._uids[(ticker, instrument_type)]`.
   - Повторные `_load()` того же инструмента передают закэшированный `instrument_id` в `load_candles`, что пропускает `find_working_instrument`.
   - `load_candles` получает необязательный параметр `instrument_id=None`; при переданном значении разрешение не выполняется, UID используется как есть.
   *Альтернатива:* модульный dict внутри `load_candles`. Отклонено — глобальное состояние вне жизненного цикла кэша сложнее тестировать (тесты `tests/unit/data/`).

## Risks / Trade-offs

- **UID может смениться в рамках сессии (ролл фьючерсного контракта)** → кэш ключуется по `(ticker, instrument_type)`; тикер привязан к конкретному контракту, библиотека редко меняет UID, а новая сессия заново разрешает оба. При сбое загрузки UID просто не кэшируется (кэшируем только после успешного ответа).
- **Первичная загрузка может оставаться тяжёлой** (много инструментов × 30 дней пачками) → Mitigation: вне scope, `api_call_with_retry` и так ждёт rate-limit; цель этого change — убрать повторяющиеся запросы.
- **Изменение поведения в тестах бота** (`FailOnceRefresh`/`LateBarCache` полагаются на то, что `_bar_is_ready` всегда дёргает refresh) → обновить только тесты, не семантику: early-exit делает refresh только при отсутствии бара в кэше.

## Migration Plan

Не деплойная миграция: поведение улучшающее, обратная совместимость загрузчика сохранена (новый параметр опциональный, UID-кэш прозрачен для вызова). Откат — revert изменений трёх файлов (`trading_bot.py`, `cache.py`, `loader.py`).
