# Дизайн: stateless decide + дедупликация входа в брокере

## Context

См. `proposal.md — Why`: привязки одного `(стратегия, ТФ)` делят один инстанс, а `decide()` у `ma_cloud_rsi_macd` мутирует `_pending_*`/`_long_contracts`/`_short_contracts` (`src/strategies/ma_cloud_rsi_macd_strategy.py`). Два вызова за тик «съедают» состояние второго. Плюс: если оба профиля пропустят вход, исполнение получит два идентичных ордера.

Ограничения текущего кода:
- `_strategy_cache` в `src/bot/trading_bot.py` — ключ `(имя, ТФ)`, инстанс общий (`_analyze()` вызывает `decide()` на каждую привязку, `trading_bot.py:189`).
- `expected_events()` гоняет `decide(ta.iloc[:i+1])` на свежем `runner` (`ma_cloud_rsi_macd_strategy.py:81-127`) — уже «реплей-семантика», но по префиксам (O(n²)).
- `tests/unit/strategies/test_ma_cloud_rsi_macd.py` — ~13 тестов инжектируют приватное состояние (`_long_contracts = 2` и т.п.) и проверяют поведение «память между вызовами».
- Snapshot-эталоны (`*_expected_signals.csv`) генерируются через `expected_events()`, свежий инстанс на вызов — служат оракулом: при корректном рефакторинге они остаются зелёными БЕЗ перегенерации.
- Брокерский слой исполнения в исходниках текущей ветки отсутствует (пустые `src/broker/`, `src/trade_journal/`, `src/portfolio/` с остатками `__pycache__`); реализация есть на ветке `feature/deal-note` (`JournalBroker`, `BrokerExecutionAdapter`, портфель).

## Goals / Non-Goals

**Goals:**
- `decide()` стратегии — чистая функция накопительной истории: детерминизм, идемпотентность, безопасное разделение инстанса привязками одного ТФ.
- Сравнение «один инструмент, один ТФ, разные фильтры» работает: обе привязки видят одинаковое решение, различие — только после фильтрации.
- Брокер создаёт максимум один входящий ордер на пару (инструмент, ТФ) за сигнальный бар.
- Рефакторинг не меняет ни одно опубликованное решение: snapshot-эталоны зелёные без перегенерации.

**Non-Goals:**
- Не разделяем инстансы по профилям (ключ кэша `(имя, ТФ)` сохраняется).
- Не добавляем конфигурируемые параметры стратегии на привязку (сравнение «RSI 14 vs 21» — отдельная история).
- Не делаем «один decide на тик» в оркестраторе как гарантию корректности — в этом больше нет необходимости.
- Не перегенерируем snapshot-эталоны.
- Не откладываем удаление `expected_events`-префиксного пути: он заменяется однопроходным реплеем.

## Decisions

### D1. Явный объект состояния + чистая пошаговая функция
Внутреннее состояние выносится из атрибутов инстанса в явную неизменяемую структуру `MaCloudState`:
```python
@dataclass(frozen=True)
class MaCloudState:
    pending_long: tuple[tuple[str, int], ...] = ()
    pending_short: tuple[tuple[str, int], ...] = ()
    long_contracts: int = 0
    short_contracts: int = 0
```
Логика текущего `decide()` (пурж окна, регистрация голосов, вход, `_check_exit`, `_check_scale_in`) переводится в чистый шаг:
```python
_step(state: MaCloudState, bar_idx: int, row: pd.Series) -> tuple[MaCloudState, Decision]
```
Шаг ДОЛЖЕН побайтово воспроизводить текущий «stateful» путь: те же условия, те же приоритеты выхода, тот же `ENTRY_WINDOW` (пурж по абсолютному `bar_idx`). Гвард «`len(ta) < 3` → HOLD без мутаций» переносится в шаг как «для `bar_idx < 2` → (state, HOLD) без изменений».

**Альтернатива, отклонена:** оставить инстансы stateful и делить их по профилям (профиль в ключе кэша). Даёт независимость, но не убирает риск двойного ордера, удваивает память и не делает контракт безопасным в общем виде. Пользователем выбран stateless-путь.

**Альтернатива, отклонена:** «один `decide()` на пару за тик, фильтры поверх» в оркестраторе. Решает сценарий, но завязывает корректность на группировку привязок в `_analyze` и не усиливает контракт для любых будущих потребителей.

### D2. `decide()` = однопроходный реплей
```python
def decide(self, ta, timeframe=None):
    state = _EMPTY
    decision = HOLD-заглушка
    for bar_idx, row in enumerate(rows(ta)):
        state, decision = self._step(state, bar_idx, row)
    return decision (с timeframe, strategy_name)
```
- Возвращается решение последнего бара; решения промежуточных баров отбрасываются.
- Фрейм — всегда полная история или префикс от начала (`bar_idx` абсолютен и совпадает между вызовами), что соответствует контракту.
- Инстанс не хранит состояния между вызовами → разделение синстансом на привязках и повторные вызовы безопасны.

Производительность: O(n) скалярных операций на тик. Для реалистичных внутридневных фреймов (сотни–первые тысячи баров) на такте 5 с — приемлемо. Если при росте кэша истории понадобится — допускается мемоизация шагов по идентификатору `ta` (идемпотентность по входу сохраняется: результат определяется входом, а не историей вызовов).

### D3. `expected_events()` = тот же однопроходный реплей с сбором событий
Вместо O(n²) вызовов `decide(префиксы)` на свежем runner — один проход `_step` по всем барам, сбор не-HOLD решений в события `EVENT_COLUMNS`. Пути совпадают (тот же `_step`), поэтому эталоны сохраняются без перегенерации. `expected_events` не изменяет состояние инстанса — он читает только `ta`.

### D4. Шов для существующих тестов с состоянием
~13 unit-тестов сохраняют свою проверяемую ценность («при известном состоянии — СТАChitude решения определённые»). Тесты переводятся на внутренний (непубличный) вход:
- `_decide_from_state(ta, state, timeframe) -> Decision` — логика последнего бара из явного состояния (без реплея).
Тесты собирают `MaCloudState(long_contracts=2, ...)` и вызывают эту функцию; цепочки («partial выход, затем full» на двух барах) — через `_step` или повторный `_decide_from_state` с обновленным состоянием, возвращаемым шагом.

**Альтернатива, отклонена:** строить full synthetic-историю до нужного состояния каждого теста — громоздко и хрупко, тест уже не читается как «данное состояние → данное решение».

### D5. Дедупликация входа — в брокерском слое исполнения
Дедупликация размещается на пути создания заявки (в `JournalBroker` или адаптере `BrokerExecutionAdapter`), НЕ в сигнальном контуре:
- Ключ: `(инструмент, таймфрейм, bar_time)` для решений с входящим действием (`action="entry"`).
- При создании входящего ордера ключ записывается в ограниченную карту `по_клику → bar_time`.
- Повторный вход с тем же ключом: ордер НЕ создаётся, в журнал фиксируется причина `duplicate`; решение при желании всё равно отображается в консоли (трейдер видит «второй фильтр пропустил, но вход уже исполнен»).
- Прунинг карты по устаревшим `bar_time` (старые ключи удаляются) — карта не растёт.
- Выходы и доборы не дедуплицируются; следующий бар создаёт новый ордер.
- `NotifyOnlyExecutionPort` не трогаем (ордеров не создаёт): консольное сравнение привязок работает как раньше.

**Альтернатива, отклонена:** дедуплицировать на уровне `_emit`/оркестратора. Разрешило бы тик-дубли, но контракт `ExecutionPort` «один вход» должен жить там, где создаются ордера, чтобы защищать и будущие ветки исполнения.

### D6. Брокерский слой — предпосылка задач
Текущая ветка не содержит исходников брокера. Варианты поставки: (а) перенести `feature/deal-note` (JournalBroker + портфель + журнал) и писать дедупликацию поверх; (б) реализовать брокерский слой заново в рамках этого изменения. Рекомендуется (а) — слой уже проработан; но выбор влияет на порядок задач → см. Open Questions.

## Risks / Trade-offs

- **[R] Незаметное изменение решений из-за рефакторинга.** Шаг обязан воспроизводить текущий порядок действий (пурж → регистрация голосов → вход → выход → добор). → Мит: snapshot-эталоны как оракул (без перегенерации); полный прогон тестов 645 до/после; эталонные unit-тесты D4 переводятся заблаговременно.
- **[R] Идемпотентность ≠ O(1): реплей по всей истории на каждый тик.** → Мит: реалистичные размеры фреймов; опциональная мемоизация шагов по входному фрейму (детерминизм сохраняется).
- **[R] `expected_events` и `decide` могут разойтись в пути событий** (например, из-за гварда прогрева). → Мит: оба построены на одном `_step`; snapshot-сравнение по всем кейсам.
- **[R] Дедup может «удушить» легитимный вход, если `bar_time` нестабилен.** → Мит: ключ строго из `Decision.bar_time`, задаваемого в `_analyze` (`trading_bot.py:190`); граница действия — один бар.
- **[R] Мусор: в текущей ветке пустые пакеты `src/broker`, `src/trade_journal`, `src/portfolio` с `__pycache__`.** → Мит: до реализации разобраться: либо наполнить из `feature/deal-note`, либо очистить директории (зависит от D6).

## Migration Plan

1. Подготовка: зафиксировать зелёный набор тестов (645) на текущем коде; убедиться, что snapshot-эталоны на месте.
2. Перевод ~13 unit-тестов на шов `_decide_from_state` (красные → зелёные после D2–D4) — делается вместе с рефакторингом, не после.
3. Stateless-рефакторинг стратегии; прогон стратегии через snapshot-раннер БЕЗ перегенерации эталонов.
4. Добавление новых тестов: идемпотентность, «два профиля на одном ТФ», `expected_events` на инстансе с предысторией вызовов.
5. Брокерский слой (D6) → дедупликация + её тесты (`TestBrokerEntryDedup`).
6. Откат: изменения малы и локальны (стратегия + брокер); откат = revert коммитов, эталоны не трогаются.

## Open Questions

- **Порядок поставки брокера (D6).** Переносить ли `feature/deal-note` целиком (JournalBroker, портфель, журнал сделок) до задач дедупликации, или брокерский слой реализуется внутри этого изменения? Влияет на состав задач, не на спеки.
- **Отображение дубликата.** Показывать ли повторно пропущенный фильтром вход в консоли отдельным статусом (например, «⚠️ вход уже исполнен — дубликат»), или только фиксировать в журнале/логе? Минимальное поведение (спека) — журнал + причина `duplicate`; косметика уведомления может быть решена позже без изменения спецификации.
