## Context

См. proposal.md — мотивация. Текущее состояние:

- `TradingBot._loop` ждёт бар через `_timeline.wait_until_bar_published(_bar_is_ready, poll_secs=1, timeout_secs=65)`; `_bar_is_ready` при отсутствии свежего бара вызывает `refresh_if_new_candle(tf, force=True)` — запрос API на **каждый** 1-секундный опрос (src/bot/trading_bot.py:196-200).
- `refresh_if_new_candle` даже с `force=True` не ограничен по времени; каждый вызов `_load(start_date=last_loaded)` заново перекачивает окно от последнего известного бара (src/data/cache.py:91-115).
- `load_candles` итерирует `api_call_with_retry(client.get_all_candles, ...)` (src/data/loader.py:55): обёртка retry покрывает только создание генератора, `RESOURCE_EXHAUSTED` при итерации не ретраится и улетает в `_loop`.
- Пауза после сбоя фиксирована: `fallback_secs()` = 3600, ограниченный периодом наименьшего активного ТФ (src/scheduler/timing.py:265-278); `ratelimit_reset` в ней не учитывается.
- Лимит один на токен/учётку (600 в 60 с), поэтому защита должна быть общая, а не per-ТФ.

## Goals / Non-Goals

**Goals:**
- Резко снизить частоту запросов свечей в цикле ожидания бара (с ~1/с до 1 за `data_refresh_min_interval`).
- Не выжигать лимит в штатном цикле и быстро восстанавливаться после его исчерпания (учёт `ratelimit_reset`).
- Не менять внешнее поведение анализа: по каждому свежему закрытому бару по-прежнему доставляется решение, в пределах существующего таймаута публикации.

**Non-Goals:**
- «Держать» массовую стартовую загрузку истории (30 дней × инструменты × ТФ) — она остаётся одноразовой; решается только её восстановление после лимита.
- Уменьшать потребление одного запроса (это отдельный вопрос пагинации/глубины — вне рамок).
- Менять планировщик `wait_until_bar_published`: он остаётся генеральным циклом опроса колбэка; политика частоты API живёт в кэше данных.

## Decisions

### D1. Троттлинг форс-дозагрузки живёт в `MarketDataCache`
В кэш добавляется глобальный страж последнего обращения к API (`_last_api_attempt`) и минимальный интервал `data_refresh_min_interval`. `refresh_if_new_candle(tf, force=False)` перед вызовом `_load` проверяет: если `now - _last_api_attempt < data_refresh_min_interval` — вызов API пропускается (флаг готовности остаётся прежним). `force=True` больше НЕ снимает это ограничение: форс означает «стараться догрузить», но с шагом не чаще интервала.

- Альтернатива: увеличить `poll_secs` планировщика (например, до 10). Отклонено: опрос колбэка — дешёвая проверка по кэшу и должен оставаться частым (своевременная реакция на появление бара); частота API — отдельная политика, ей место в слое данных.
- Альтернатива: per-ТФ страж. Отклонено: лимит один на токен, общий страж точнее отражает общий бюджет и проще в тестах.

Побочный эффект: появление бара может быть замечено с задержкой до `data_refresh_min_interval` от публикации (в пределах таймаута). Для сконфигурированного по умолчанию значения 5 с это несущественно.

### D2. Ограниченное окно дозагрузки (bounded backfill)
Инкрементальные и принудительные дозагрузки (`refresh_if_new_candle`, `ensure_loaded`) вычисляют `start_date = max(last_dt, now - data_backfill_window)`: даже если последний известный бар старше окна, API запрашивает только свежие бары окна. Слияние (`_merge_new_bars`) добавляет только бары, отсутствующие в кэше, поэтому корректность не меняется, а повторная перекачка накопленного окна при отставании публикации (~45 с) исчезает.

Первичная загрузка пары (`_initial_load`, `start_date=None`) остаётся сессионной (30 дней) — это осознанно: нужен прогрев индикаторов.

### D3. Ретрай потока свечей при итерации
В `load_candles` итерация по `client.get_all_candles(...)` оборачивается так, что `RESOURCE_EXHAUSTED` **во время итерации** повторно открывает поток с экспоненциальной паузой, ограниченной `ratelimit_reset` (парсинг выносится в публичный хелпер `rate_limit_reset_secs(exc)` в `src/api/retry.py`; существующий `_parse_reset_delay` переиспользуется). Уже собранные свечи до сбоя сохраняются, повторный поток продолжает сбор (без потери строк). Ошибки при создании генератора по-прежнему ловит `api_call_with_retry`.

- Альтернатива: «полностью высушить» генератор в одном вызове через `list()`. Отклонено: для 30-дневных 1m-срезов избыточно по памяти и откладывает сбор до конца.

### D4. Учёт `ratelimit_reset` в кэше и в паузе тика
- Кэш: при `RESOURCE_EXHAUSTED` из `_load` фиксируется `_retry_after = now + max(reset, минимальная пауза)`; до этого момента любые дозагрузки пропускаются (сценарий «Лимит исчерпан»), затем возобновляются. Парсинг — через `rate_limit_reset_secs`; без подсказки — фиксированная пауза (`DEFAULT_BASE_DELAY`).
- Оркестратор: в `_loop` при ошибке тика выбирается пауза `min(fallback_secs(), reset)` если ошибка `RESOURCE_EXHAUSTED` с указанным `ratelimit_reset`, иначе как раньше. `_report_error` и `time.sleep` остаются на месте.

### D5. Конфигурация
В `_DEFAULTS` (src/config.py) добавляются:
- `data_refresh_min_interval` (сек, default 5) — интервал между API-дозагрузками;
- `data_backfill_window_seconds` (сек, default 3600) — окно дозагрузки свежих баров.

Значения пробрасываются в `MarketDataCache(...)` (параметры с дефолтами, инжектируемые в тесты). Существующий `robot.toml` без этих ключей работает с дефолтами — обратная совместимость.

## Risks / Trade-offs

- Задержка фиксации свежего бара до `data_refresh_min_interval` → Mitigation: дефолт 5 с, таймаут ожидания (65 с) не меняется; анализ может отставать на единицы секунд.
- Общий страж `_last_api_attempt` может задержать легитимную дозагрузку другого ТФ → Mitigation: интервал мал (5 с); при необходимости переключиться на per-ТФ страж — локальное изменение в кэше, спецификацию не затрагивает.
- Стартовая массовая загрузка всё ещё способна кратко превысить 600/мин → Mitigation: D3+D4 обеспечивают восстановление по `ratelimit_reset` вместо часового простоя; полная «размазка» стартовой загрузки — отдельная задача вне рамок.
- Ретрай итерации потока без учёта совместимости серверного потока (reopen) → Mitigation: повторный `get_all_candles` с теми же `from_/to` идемпотентен по природе API (диапазонный запрос); риск минимален.

## Migration Plan

- Правки кода в одном релизе; новые ключи конфигурации опциональны (дефолты в `_DEFAULTS`). Старые `robot.toml` продолжают работать.
- Проверка: `pytest -q` + `ruff check .`; ручная проверка на логе — число `GetCandles` в час падает с десятков тысяч до единиц сотен, `RESOURCE_EXHAUSTED` исчезает из штатного цикла.
- Откат: revert коммита/перевыпуск бинаря; поведение возвращается к прежнему.
