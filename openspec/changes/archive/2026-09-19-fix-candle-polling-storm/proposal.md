## Why

Робот непрерывно «долбит» Invest API запросами свечей, выжигая лимит 600/мин и
на сутки зависая в ошибках `RESOURCE_EXHAUSTED`. Замер по
`data/bot_debug.log`: за 2026-09-18…19 ≈ **167 тыс. вызовов GetCandles**
(37 330 + 50 909 + 61 055 + 18 538), ночью — 570 ошибок лимита, утром — 48.
Пока лимит исчерпан, бот не получает бары: ни один вход не активируется, журнал
сделок пуст (тот самый «пустой trade_event» утром 19 сен). Шторм воспроизводится
на релизном бинаре v4.0.0 и стал главным блокером работоспособности робота.

Корень: цикл ожидания свежего закрытого бара (`_bar_is_ready`) выполняет
**форс-дозагрузку раз в секунду** (`TICK_POLL_SECS=1`) и **игнорирует сторож
`_observed`** (`force=True`), каждая дозагрузка перекачивает окно от последнего
бара заново; при лимитах `api_call_with_retry` не ретраит потоковый
`get_all_candles` (исключение возникает при итерации, а не при создании
генератора), а fallback-пауза после сбоя фиксирована и не учитывает
`ratelimit_reset`.

## What Changes

- Ожидание свежего закрытого бара больше НЕ перезагружает данные каждую секунду:
  опросы между принудительными дозагрузками проверяют только кэш (без API), а
  сама дозагрузка выполняется не чаще сконфигурированного минимального интервала
  перезагрузки данных (`data_refresh_min_interval`).
- Принудительная дозагрузка запрашивает **только свежие бары с ограниченным
  окном** (не тянуть историю заново при отставании API на время публикации).
- Повторные дозагрузки прекращаются при исчерпании лимита API: кэш не выполняет
  запросов до наступления `ratelimit_reset` из текста ошибки.
- Потоковый вызов свечей (`get_all_candles`) при `RESOURCE_EXHAUSTED` во время
  итерации возобновляется повторным открытием потока с экспоненциальной паузой,
  ограниченной `ratelimit_reset`.
- Fallback-пауза после сбоя тика учитывает `ratelimit_reset` (когда он указан),
  но не длиннее периода наименьшего активного ТФ.
- **BREAKING**: появляется сконфигурированный минимальный интервал перезагрузки
  данных и окно дозагрузки; поведение ожидания бара меняется с «1 запрос/с» на
  «до 1 запроса за интервал». Для пользователя внешне меняется только частота
  сетевых запросов; анализ по-прежнему выполняется по каждому свежему закрытому
  бару в пределах таймаута публикации.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `data-cache`: форс-дозагрузка при ожидании свежего бара выполняется с
  интервалом не чаще сконфигурированного минимума, запрашивает только свежие бары
  с ограниченным окном дозагрузки и прекращается при исчерпании лимита API до
  наступления `ratelimit_reset`.
- `data-loading`: `RESOURCE_EXHAUSTED` во время итерации потокового
  `get_all_candles` ретраится повторным открытием потока с паузой, ограниченной
  `ratelimit_reset`; окно дозагрузки ограничивается bounded backfill.
- `orchestration`: ожидание появления свежего закрытого бара не выполняет запросы
  API на каждом опросе (опросы дешевле — по кэшу); после сбоя тика пауза
  учитывает `ratelimit_reset` (не длиннее наименьшего активного ТФ).

## Impact

- Код: `src/data/cache.py` (`refresh_if_new_candle`, троттлинг и окно дозагрузки),
  `src/data/loader.py` (ретрай итерации потока), `src/bot/trading_bot.py`
  (`_bar_is_ready`, обработка сбоя тика), `src/config.py` (новые параметры
  `data_refresh_min_interval`, `data_backfill_window`), `run.py` (проброс настроек).
- Конфигурация: добавляются опциональные ключи в `robot.toml`/`default.toml` с
  разумными значениями по умолчанию (например, минимум 5–10 с, backfill 1 ч).
- Поведение: частота запросов свечей резко падает, лимит 600/мин не исчерпывается
  в штатном цикле; при перерасходе (например, массовая стартовая загрузка) часы
  простоя из-за лимита устраняются учётом `ratelimit_reset`.
- Тесты: `tests/unit/` — троттлинг форс-дозагрузки, окно дозагрузки, стоп при
  rate-limit до `ratelimit_reset`, ретрай итерации потока, учёт `ratelimit_reset`
  в fallback-паузе.
