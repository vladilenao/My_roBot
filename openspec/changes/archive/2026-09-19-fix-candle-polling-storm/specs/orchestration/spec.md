# Оркестрация

## MODIFIED Requirements

### Requirement: Выравнивание итерации по закрытию свечи
Ритм работы системы ДОЛЖЕН синхронизироваться с границами закрытия свечей всех активных таймфреймов привязок: каждая штатная (не первая) итерация начинается на ближайшей границе закрытия свечи среди активных ТФ, а не по фиксированной паузе. Обработка индикаторов и принятие решений ДОЛЖНЫ выполняться по завершённым (закрытым) свечам соответствующего ТФ.

Первый тик при запуске ДОЛЖЕН выполняться сразу, без ожидания ближайшей календарной границы: анализируется последняя уже закрытая свеча каждого активного ТФ, и по ней немедленно доставляется решение. Если ожидаемый закрытый бар уже присутствует в загруженных данных, повторная дозагрузка данных с API НЕ ДОЛЖНА выполняться: готовность проверяется по текущему кэшу. Если при запуске ближайшая граница закрытия только что пройдена и свежий закрытый бар ещё не опубликован, первый тик ДОЛЖЕН повторно дозагружать данные с паузами не чаще минимального интервала перезагрузки данных, пока не будет подтверждено появление свежего закрытого бара; между принудительными дозагрузками готовность проверяется по кэшу без обращения к API. Ожидание ДОЛЖНО быть ограничено тем же таймаутом, что и штатное удержание тика, после чего первый тик обрабатывается с имеющимися данными без бесконечной блокировки.

После достижения календарной границы закрытия свечи таймфрейма система ДОЛЖНА удерживать обработку этого ТФ и повторно дозагружать данные до подтверждения появления свежего закрытого бара, но НЕ чаще одного запроса к API за минимальный интервал перезагрузки данных; проверка готовности между дозагрузками выполняется по кэшу и НЕ ДОЛЖНА обращаться к API. Ожидание ДОЛЖНО быть ограничено таймаутом: если свежий бар не появился за отведённое время, тик обрабатывается с имеющимися данными, без бесконечной блокировки.

#### Scenario: Итерация по границе
- **WHEN** на штатной итерации (после первого тика текущего запуска) текущая свеча таймфрейма ещё не закрыта
- **THEN** обработка привязок этого ТФ не выполняется до наступления границы закрытия свечи

#### Scenario: Первый тик при запуске выполняет последнюю закрытую свечу
- **WHEN** бот запускается в середине периода таймфрейма (например, 09:58 при 1h) и последняя закрытая свеча уже доступна
- **THEN** первый тик выполняется немедленно, решение доставляется по последней закрытой свече (8:00–9:00), без ожидания следующей границы закрытия (10:00)

#### Scenario: Первый тик без повторной дозагрузки
- **WHEN** при запуске ожидаемый закрытый бар уже присутствует в загруженных данных
- **THEN** первый тик обрабатывается немедленно, повторный запрос к API не выполняется

#### Scenario: Решение по готовой свече
- **WHEN** стратегия принимает решение
- **THEN** в расчёте участвуют только закрытые свечи таймфрейма привязки; незакрытая текущая свеча не влияет на решение

#### Scenario: Первый тик на границе ожидает свежий бар
- **WHEN** запуск происходит сразу после календарной границы, а свежий закрытый бар ещё не появился в данных
- **THEN** первый тик не обрабатывается немедленно; система дозагружает данные с паузами не чаще минимального интервала перезагрузки, пока свежий закрытый бар не появится

#### Scenario: Таймаут первого тика на границе
- **WHEN** свежий закрытый бар не появился в течение ограниченного таймаута ожидания первого тика
- **THEN** первый тик обрабатывается с имеющимися данными, не блокируясь бесконечно

#### Scenario: Тик удерживается до появления свежего бара
- **WHEN** календарная граница закрытия свечи достигнута на штатной итерации, но свежий закрытый бар ещё не появился в данных
- **THEN** тик не обрабатывается немедленно; система повторно дозагружает данные с паузами не чаще минимального интервала перезагрузки, пока свежий закрытый бар текущей закрытой минуты не появится

#### Scenario: Проверка готовности между дозагрузками не обращается к API
- **WHEN** ожидается появление свежего закрытого бара, но интервал с последней дозагрузки меньше минимального интервала перезагрузки данных
- **THEN** запрос к API не выполняется; готовность проверяется по закэшированным данным

#### Scenario: Обработка по таймауту
- **WHEN** свежий закрытый бар не появился в течение ограниченного таймаута ожидания на штатной итерации
- **THEN** обработка тика выполняется с имеющимися данными, не блокируясь бесконечно

#### Scenario: На одном тике работают только ТФ с закрывшейся свечой
- **WHEN** активны привязки `15m` и `1h`, тик на границе `10:45 UTC` (закрылась только 15m-свеча)
- **THEN** обрабатываются только привязки с таймфреймом `15m`; привязки `1h` ждут своей границы

### Requirement: Устойчивость к ошибкам и диагностика
Система ДОЛЖНА перехватывать исключения на уровне отдельной стратегии и всего цикла. Ошибка стратегии НЕ ДОЛЖНА блокировать другие стратегии. Ошибка тика/цикла ДОЛЖНА фиксироваться в логе и уведомление о сбое ДОЛЖНО доставляться трейдеру через нотификатор (не только в консоль), после чего цикл продолжается. Fallback-пауза после сбоя ДОЛЖНА быть не длиннее периода наименьшего активного ТФ (ограничение фиксируется в логе), чтобы не пропускать частые границы. Если ошибка тика связана с исчерпанием лимита запросов API (`RESOURCE_EXHAUSTED`) и в тексте ошибки указан `ratelimit_reset`, пауза после сбоя ДОЛЖНА учитывать это время сброса (повторные запросы не выполняются в течение окна сброса), но НЕ должна превышать период наименьшего активного ТФ.

#### Scenario: Отказ одной стратегии
- **WHEN** `compute()` или `decide()` одной стратегии выбрасывает исключение
- **THEN** остальные стратегии этого инструмента обрабатываются штатно, отказ зафиксирован в логе

#### Scenario: Ошибка тика уведомляет трейдера
- **WHEN** возникает необработанное исключение в цикле
- **THEN** ошибка логируется, трейдеру доставляется уведомление о сбое через нотификатор, применяется fallback-пауза (не длиннее наименьшего активного ТФ) и цикл продолжается

#### Scenario: Пауза после rate-limit учитывает сброс лимита
- **WHEN** ошибка тика содержит `RESOURCE_EXHAUSTED` с `ratelimit_reset=30`, а период наименьшего активного ТФ больше 30 секунд
- **THEN** следующий запрос к API выполняется не ранее чем через 30 секунд
