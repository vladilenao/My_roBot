## Context

Мотивация описана в `proposal.md`. `CsvExporter._snapshot()` читает `positions JOIN trades` и сейчас сортирует по `positions.trade_id`. `_summary_row()` уже получает подтверждённые исполнения через `_fills()`, где входами считаются действия `OPEN` и `ADD`. Таблица `fills` допускает только положительный объём. Снимок служит общим источником двух CSV, а `Storage` запускает экспорт после транзакций и при открытии базы.

Технический дизайн нужен для согласования выбора первого входа, ключа сортировки и отображаемого времени: текущий `ORDER BY f.executed_at` сравнивает текст, а строка МСК теряет доли секунды. Эти представления нельзя использовать как эквивалент фактического момента при разных ISO-смещениях.

## Goals / Non-Goals

**Goals:**
- Использовать один и тот же набор входных исполнений для допуска карточки, определения первого входа и сортировки.
- Сохранить существующее атомарное построение двух проекций из одного read-only снимка и избежать дополнительного чтения исполнений ради фильтрации.
- Учитывать полную точность сохранённой временной метки без новых пользовательских колонок.

**Non-Goals:**
- Миграция SQLite, удаление торговых записей, изменение lifecycle и вычислений финансовых показателей.
- Изменение состава или порядка событий `trade_event.csv`, ручная очистка CSV и создание нового отчёта.

## Decisions

### 1. Источник включения — нормализованные входные исполнения

Использовать существующие `fills JOIN orders` и классификацию входов `OPEN`/`ADD`, а не статусы заявок или остаток позиции. Отфильтровывать карточку до расчёта её показателей, когда входных исполнений нет; передавать уже прочитанные исполнения в построение карточки, чтобы не добавлять повторную выборку.

Альтернативы: исключение только статусов `CANCELLED`/`REJECTED` оставляет планы и ожидающие заявки; фильтр `positions.quantity > 0` удаляет закрытые сделки. Отдельный SQL `EXISTS` допустим, но дублирует критерий входа рядом с `_fills()`; общий набор исполнений проще поддерживать согласованным.

### 2. Первый вход и сортировка используют нормализованный момент

Разбирать `executed_at` как ISO datetime и приводить к UTC, сохраняя доли секунды. Для старой метки без часового пояса использовать UTC, как уже делает `_msk()`. Упорядочивать исполнения карточки по нормализованному моменту и `fill_id`; первый элемент входов определяет и `Время входа`, и ключ карточки. После формирования подходящих карточек сортировать их по `(первый вход UTC, trade_id)` до сериализации CSV.

Альтернативы: сортировка по отформатированной строке МСК теряет субсекундную точность; текстовый минимум ISO-меток неверен при разных часовых смещениях. SQL-преобразования времени усложняют согласование точности с Python. Пара ключа и строки остаётся внутренней структурой экспортера; в CSV попадают только существующие колонки.

### 3. Пересборка всей истории через существующий экспорт

Правила действуют на весь снимок, включая legacy-сделки. Экспорт при запуске заново строит сводку: неисполненные карточки исчезают из CSV, но остаются в SQLite и событийной ленте. При отсутствии исполненных входов стандартная запись заголовка создаёт корректный пустой отчёт.

## Risks / Trade-offs

- [Незаметная потеря закрытых или частично исполненных сделок при фильтрации по состоянию] → Проверять факт входа и покрыть нулевой остаток, отменённую заявку после частичного fill, открытые и частично закрытые позиции.
- [Расхождение отображаемого первого входа с сортировкой] → Использовать один нормализованный набор исполнений; проверить разные смещения, доли секунды и доборы.
- [Старые тестовые карточки без fills ожидают строку] → Обновить только ожидания нового контракта; добавить реальные исполнения в фикстуры, которые проверяют показатели состоявшейся сделки.
- [Рост стоимости сортировки] → Сортировать уже загруженные карточки в памяти; текущий экспорт и так собирает весь список. Новые индексы и оптимизацию общего экспортера не добавлять без измеренной необходимости.

## Migration Plan

После внедрения обычный запуск или следующий экспорт применит новый состав и порядок ко всей базе. Миграция данных не нужна. Проверить пересборку на временной базе с историей обоих типов; исходные строки и события должны сохраниться. Откат к прежнему экспортеру возвращает прежнюю проекцию из той же SQLite без восстановления данных.
