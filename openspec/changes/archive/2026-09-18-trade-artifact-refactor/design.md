# Дизайн: rename-user-artifacts-and-record-traces

## Context

См. proposal.md — Why. Реализация уже почти готова, но не закончена:
- Проекции CSV уже пишутся через `CsvExporter` в пути из конфигурации (`journal_file`/`positions_file`), один атомарный read-only снимок (`export_revision`), автоэкспорт после транзакций и при старте. Имена файлов и колонок сейчас `trade_journal.csv`/`trade_journal_positions.csv` — надо переименовать по proposal.
- Аудит «полуживой»: `CalculationTrace` строится в вычислительных точках (ATR/MA indicator.py:55/74, basic_levels filter:44, portfolio/risk.py:303, профильные геометрии base.py:98/111, reducer apply_fill:114, резервирование storage.py:256), но в боевом цикле запись этих следов в SQLite и выгрузка в лог НЕ происходят — `trade_audit.log` пуст, `calculations=0`.

## Goals / Non-Goals

**Goals**
- Зафиксировать точные имена и зоны ответственности трёх пользовательских артефактов: `trade_event.csv` (лента «что произошло и когда»), `trade_summary.csv` (карточка «состояние и итог сделки»), `trade_decision_trace.log` (как система пришла к решению и числам).
- Включить запись следов торговых решений в боевой цикл, чтобы файл трассировки наполнялся.

**Non-Goals**
- НЕ создаём legacy-копии старого формата; старые файлы больше не создаются и не читаются.
- НЕ меняем SQLite-схему (следы уже в `calculations`, снимки в `market_inputs`, состояние экспортов в `export_state`).
- НЕ трассируем потиковые пересчёты индикаторов (ATR/MA на каждом тике) — только решения.

## Decisions

1. **Имена — каноническими путями через конфигурацию.** CSV уже производятся по `journal_file`/`positions_file`; меняем дефолты: `journal_file` → `trade_event.csv`, `positions_file` → `trade_summary.csv`, `audit_file` → `trade_decision_trace.log`. Ручной переименования старого журнала в новые имена НЕ производится (non-goal). Конфигурация сохраняет переопределение имён — приложение не хардкодит имена.
2. **Запись следов — через существующий `CalculationTraceRepository.record()`** в каждой точке принятия торгового решения (см. список ниже). След пишется в той же транзакции SQLite, что и решение (атомарность с торговым состоянием), а выгрузка в `trade_decision_trace.log` остаётся за `AuditExporter` (уже работает идемпотентно по `audit_exported_revision`).
3. **Что именно записываем** — только следы решений (не индикаторных пересчётов): расчёт размера позиции, стопа, тейков, допустимого/фактического риска, оценку сигнала, проверку каждого фильтра, slippage guard, лимит экспозиции, решение о доборе, перенос стопа, trailing stop. Каждый след: входы с единицами, формула/правило, шаги, промежуточные и округлённые значения, причина; для трейлинга/переноса — старый/новый стоп и правило монотонности.
4. **Наполнение лога не обязано ждать рефакторинга всех точек сразу**: точки, где построение следа уже есть (риск/профили/apply_fill), подключаются к `record()` немедленно; в остальных (фильтры сигнала, slippage guard, лимит экспозиции, доборы, перенос стопа, trailing) след создаётся там, где принимается решение. Для единства все следы идут через один `CalculationTraceRepository` из `Storage` (уже инжектирован во все сервисы).

5. **Запись внутри торговой транзакции**: `CalculationTraceRepository` сохраняет публичный `record()` для автономной записи, а также предоставляет `record_in_transaction(connection, trace, market_input)`. Торговые менеджеры используют второй вариант внутри уже открытой транзакции, чтобы решение и его след фиксировались атомарно без вложенной SQLite-транзакции.

6. **Slippage guard на первом этапе**: добавляется наблюдаемая заглушка. Она записывает входную цену, допустимое проскальзывание и результат проверки, но всегда возвращает `ACCEPTED` и не меняет поведение исполнения. Реальное сравнение цены и правила отклонения будут отдельным изменением.

7. **ATR/MA**: потиковые пересчёты индикаторов не записываются. Их значения включаются в trace только когда реально участвуют в торговом решении: расчёте стопа, trailing stop, тейка, входа или добора.

## Risks / Trade-offs

- [Удаление старых имён ломает внешние скрипты/настройки] → Mitigation: имена задаются конфигурацией, не хардкодятся; предлагаемые дефолты зафиксированы в спеке, в proposal отмечено BREAKING.
- [Потиковая запись следов индикаторов раздует лог/БД] → Mitigation: записываются только решения, не пересчёты индикаторов.
- [Двойная запись следа при повторе события] → Mitigation: `record()` идемпотентен по `calculation_id` (детерминированный хеш содержимого), как и существующий экспорт.

## Migration Plan

При первом старте новой версии: меняются дефолтные имена в конфигурации; `trade_event.csv`/`trade_summary.csv` создаются атомарным экспортом, старые файлы `trade_journal.csv`/`trade_journal_positions.csv`/`trade_audit.log` больше не создаются, ревизии SQLite остаются единственным состоянием. Откат: вернуть прежние дефолты имён; состояние торговли не меняется (CSV — проекции, не источник истины).

## Open Questions

- Где именно в цикле принимать точки «slippage guard» и «лимит экспозиции» и в какой форме фиксировать причину — уточнено по proposal: гарантии исполнения и лимиты экспозиции фиксируются как следы отклонения/принятия решений по правилу «Доступность аудита». Оставшиеся микродетали (точный текст причины) — на уровне реализации, не влияют на спеки.
