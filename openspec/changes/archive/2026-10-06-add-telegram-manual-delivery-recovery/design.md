## Context

Действующий worker сохраняет claim события до HTTP, а `attempts` содержит только окончательный статус и message_id. Повторный claim подавляется, PNG существует только в памяти. Очередь ограничена, при остановке остаток теряется. Эталонное демо и текущий transport успешно отправили синтетические PNG; известен различающийся RU/NL маршрут, но причинность не доказана.

## Goals / Non-Goals

**Goals:** точные исходные материалы для ручного повтора; устойчивость к рестарту, переполнению и прерыванию; безопасная работа с подтверждёнными receipts; сохранение навигации сделки.

**Non-Goals:** автоматическая рассылка всего остатка после рестарта, exactly-once при неизвестном результате Bot API, изменение сети/VPN/Worker, REST-сервер, Telegram-команды управления, повтор торговли, восстановление отсутствующих исторических PNG по новым котировкам.

## Decisions

### 1. Два этапа постоянного хранения

`handle()` фильтрует событие и сохраняет его версионированный неизменяемый сериализуемый снимок в SQLite, присваивая локальный ID и порядок приёма. Короткая локальная транзакция допустима; сеть и renderer не выполняются в торговом потоке. Отдельные соединения принадлежат своим потокам; используются ограниченный busy_timeout и WAL. Ошибка диска/БД фиксируется безопасно и не останавливает торговлю, но событие нельзя объявить сохранённым.

Worker читает принятый снимок, готовит публикацию и сохраняет полные операции до первого HTTP. Ограниченная очередь становится сигналом пробуждения, а SQLite — источником работы текущего запуска: потеря сигнала пробуждения не теряет события. После рестарта старый остаток виден в списке и отправляется только по явной команде; новые события текущего запуска обрабатываются обычно.

Состояния уведомления: `captured` → `ready`, либо `preparation_failed`. Операции: `pending`, `attempting`, `confirmed`, `failed`, `uncertain`, `blocked`, `superseded`. Незавершённая HTTP-попытка после сбоя становится `uncertain`; подготовка без HTTP может безопасно возобновляться из сохранённого снимка.

### 2. Материалы и миграция

Новые таблицы: envelopes (ID, namespace, trade/event ID, порядок, время UTC, снимок, версия формата, статус подготовки), operations (стабильный ключ, метод, полный payload, dependencies, file_id/hash, статус, confirmed receipt) и append-only attempt_history (номер, источник initial/automatic/manual, время начала/конца, исход, HTTP/error code, retry_after, безопасная причина). Существующие events/trades/attempts/stages мигрируются с сохранением идентичности и receipts; миграция транзакционная и версионированная.

Файлы хранятся в отдельной таблице `telegram_files` той же `telegram_delivery.sqlite3`: `file_id` (opaque ID), `namespace`, `filename`, `mime_type`, `content BLOB`, `size_bytes`, `sha256`, `created_at` (UTC). Операция с фотографией содержит `file_id` и ожидаемую контрольную сумму. Это не торговая база. PNG и готовая операция записываются одной SQLite-транзакцией; ready не существует без сохранённого BLOB. Отдельных постоянных PNG на диске нет; экспорт в файл допустим только как явно запрошенная диагностика.

Перед отправкой проверяются наличие BLOB, размер и SHA-256. Утраченный, испорченный или удалённый по сроку файл блокирует операцию с фотографией; тихого перехода на текст или пересчёта нет. Если renderer не смог построить фото до создания ready-материала, исходный текстовый fallback сохраняется как самостоятельное исходное представление.

Сохраняются подпись/текст, parse_mode, все продолжения и кнопки. Ни токен, ни полный Bot API URL не пишутся в новые payload/logs/history. Namespace хранит прежнюю идентичность бота/канала/каталога; секреты берутся из текущей конфигурации. Смена канала/бота не переносит накопленные уведомления новому адресату. Ротация токена того же бота не теряет историю.

Старые receipts без payload помечаются `legacy_unrecoverable`, сохраняют свои message_id и показываются пользователю. LKOH/BR из обсуждения не могут быть точно восстановлены этим обновлением. Файлы хранятся семь суток с момента первой записи в telegram_files, независимо от подтверждения доставки. Повтор не продлевает срок и не создаёт копию BLOB. Текст, receipts и история попыток этой задачей очистки не удаляются; после удаления PNG точная переотправка фотографии недоступна.

### 3. Пользовательский интерфейс

Предлагаемый CLI:

```
./robot --telegram-pending --state-dir data
./robot --telegram-retry --id 42 --state-dir data
./robot --telegram-retry --from 2026-10-06 --to 2026-10-06 --state-dir data
./robot --telegram-retry --trade-id <ID> --include-uncertain --state-dir data
```

Для исходников эквивалентен запуск `.venv/bin/python run.py ...`. `--telegram-pending` — только чтение: локальный ID, короткое имя инструмента, событие, исходное время, статус, попытки, причина и доступность материалов. По умолчанию retry включает `pending`, `failed`, восстановимые ошибки подготовки; `uncertain` требует отдельного `--include-uncertain`, который означает осознанное согласие на возможный дубль. Пустой selector — ошибка, никаких неявных «повторить всё». Даты трактуются в настроенном часовом поясе; дата `--to` включительна целиком, в БД сравнивается UTC. У каждого запуска конечный снимок выбранных ID, вывод предварительного состава и финального отчёта; новые события в него не добавляются.

Команды разбираются до торговых и брокерских инициализаций. Просмотр разрешён при работающем роботе с read-only connection; повтор использует эксклюзивный runtime lock того же каталога и при работающем роботе завершает работу с понятной причиной без HTTP. Робот и два replay-процесса не должны отправлять одну операцию одновременно. Пользователь может остановить робот и запустить команду из нужного окружения/маршрута; CLI не управляет VPN.

### 4. Повторы, отказ и неопределённость

У ручного запуска отдельный bounded-бюджет транспортных попыток, использующий текущие request_timeout/max_transport_attempts. Ни confirmed операция, ни confirmed root повторно не публикуются. История старых попыток остаётся, а claim_event не используется как запрет пользовательского повтора сохранённой операции. Отказ `ok=false` не повторяется автоматически, но доступен следующему ручному запросу после устранения причины. До retry_after для 429 ручная отправка блокируется с указанием срока.

Таймаут может означать доставленный пост без полученного подтверждения. `--include-uncertain` разрешает повтор только выбранных операций и необходимых зависимостей с тем же namespace; CLI до HTTP выводит предупреждение. Новый успешный message_id связывается с локальной операцией; возможный неизвестный старый дубль удалить автоматически невозможно. Фолбэк sendMessage после HTTP-таймаута sendPhoto не добавляется.

### 5. Порядок и связи

Хранятся зависимости: корневой сигнал → этапы сделки → текстовые продолжения → обновления навигации. При выборе этапа недостающие восстановимые зависимости включаются в состав команды и показываются до отправки; uncertain зависимости без флага блокируют ветку. Невосстановимый корень оставляет ветку blocked с объяснением. Другая сделка может продолжить доставку при сбое одной ветки.

Финансовый текст, свечи и PNG неизменны. Кнопки с ID восстановленного корня/этапов разрешаются из сохранённых логических ссылок и новых confirmed receipts; это единственное допустимое изменение исходного представления, кроме технического chat_id из совпадающего namespace. В позднем восстановлении промежуточные root edits не должны откатывать уже подтверждённую более новую revision: они становятся superseded, а актуальное обновление формируется из последнего сохранённого снимка и известных receipts, без новых котировок/торговых расчётов. По confirmed edit без изменений успех фиксируется без нового поста.

### 6. Отдельная задача очистки файлов

Задача `telegram-files-cleanup` отдельно от доставки выполняется при запуске Telegram-runtime и затем раз в 24 часа в фоновом обслуживании с собственным SQLite-соединением. Также доступен автономный CLI `--telegram-cleanup-files --state-dir data` для запуска системным планировщиком, даже когда робот остановлен. Создание расписания ОС/автоматизации не входит в оформление этого change.

На начало запуска фиксируется cutoff `now_utc - 7 суток`. Удаляются только строки telegram_files с `created_at < cutoff` (ровно семь суток ещё не «старше семи дней»). Правило одинаково для confirmed, failed, pending и uncertain. В одной транзакции операции, которым нужен удаляемый файл, получают признак `media_expired` и время очистки, ссылки file_id обнуляются, BLOB-строки удаляются. Подтверждённые receipts, message_id, текст, история и логические зависимости сохраняются; confirmed статус не превращается в отказ. Просмотр показывает «Картинка удалена: срок хранения 7 дней».

Cleanup и replay согласуют работу через атомарную краткосрочную lease файла в БД: активное чтение/отправка откладывает удаление до следующей очистки; повтор не обновляет created_at. Lease ограничена по времени, освобождается после завершения, истекает после аварии. Cleanup транзакционно повторно проверяет срок и lease, чтобы не гоняться с replay. При отказе БД/диска задача сообщает безопасную ошибку, не мешает торговле, повторяется при следующем штатном запуске. Повторный запуск идемпотентен.

Команда очистки не требует остановки робота: использует координацию SQLite/lease и не выполняет HTTP или торговых действий. Команда replay, как и прежде, требует свободного runtime lock. Если робот не работает и внешнее расписание не настроено, очистка выполняется при следующем запуске; непрерывное удаление в выключенном приложении не обещается.

Удаление BLOB освобождает страницы для повторного использования SQLite, но размер файла БД не обязан немедленно уменьшиться. Полный VACUUM не запускается ежедневно в фоне торговли; обслуживание физического размера базы — отдельная задача.

## Risks / Trade-offs

- Короткая запись SQLite в handle меняет прежнее «немедленно» на ограниченный локальный IO; тестировать конкуренцию и отказ, не обещать сохранность при недоступном диске.
- BLOB и готовая операция сохраняются одной транзакцией; растут SQLite/WAL и время записи, поэтому операции должны быть короткими.
- Семидневная очистка удаляет и недоставленные картинки: поздняя точная отправка фото невозможна. Текст и история сохраняются; пользователь видит причину блокировки.
- Неизвестный HTTP-исход допускает дубль даже при идеальном локальном дедупе.
- Runtime lock означает, что ручной replay выполняется после остановки робота; просмотр доступен всегда.

## Validation

Изолированные tests/unit/notifier/: миграция v1, атомарность BLOB/операции и аварии SQLite, queue overflow/shutdown, restart, точные BLOB PNG/hash и граница семи суток, mixed confirmed/failed/uncertain, 429, namespace, selectors, зависимости/новый root ID, stale revisions, parallel locks и отчёт частичного успеха. Проверять lease/cleanup/replay race, просроченную lease, идемпотентность, удаление failed/uncertain PNG без потери текста/receipts, отсутствие обновления TTL при повторе. CLI проверяется без реального брокера/Telegram. Опциональный живой тест — только по отдельному поручению пользователя с синтетическими материалами; unit-тесты не публикуют в рабочий канал.
