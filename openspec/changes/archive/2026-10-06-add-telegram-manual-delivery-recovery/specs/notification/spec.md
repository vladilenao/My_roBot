## MODIFIED Requirements

### Requirement: Рабочая отправка в Telegram
Нормативный уровень: MUST.
Канал Telegram ДОЛЖЕН отправлять реальные HTTP POST в Telegram Bot API через настроенный базовый адрес Cloudflare, используя токен и идентификатор канала из `.env`, переданные фабрикой из `src.config`. Текст доставляется методом `sendMessage`, график с подписью — `sendPhoto`; обновление существующей карточки выполняется через `editMessageCaption` либо `editMessageText` в зависимости от её исходного представления, навигация — через inline URL-кнопки. Получение метаданных канала выполняется через `getChat`. Таймаут одного HTTP-запроса по умолчанию 10 секунд и настраивается конфигурацией канала (`[notifier.telegram] request_timeout`). Успехом ДОЛЖЕН считаться только HTTP 200 с `ok=true`; идентификатор нового сообщения сохраняется только из подтверждённого результата API.

Принятое событие ДОЛЖНО сохраняться короткой ограниченной локальной транзакцией в постоянном хранилище до постановки в очередь. Форматирование, рендеринг и сеть выполняются фоновым работником; вызывающий поток не ждёт эти операции. Ограниченная очередь служит сигналом пробуждения, потеря её элемента НЕ ДОЛЖНА удалять сохранённое событие. Порядок соответствует порядку приёма. Перезапуск не запускает автоматическую рассылку остатка прежних запусков; ручное восстановление подчиняется telegram-delivery-recovery. Ошибка хранения изолируется от торговли с явным предупреждением.

Текст ДОЛЖЕН укладываться в лимит 4096 символов, подпись фотографии — в 1024 символа по правилам Telegram. Длинные подробности отправляются текстовыми продолжениями по границам строк, с сохранением порядка и корректного HTML; строка длиннее лимита режется принудительно без разрыва HTML-сущности или тега. Основная карточка сохраняет инструмент, статус, вход/стоп, краткую сводку целей и навигацию; продолжение содержит не уместившиеся детали. Динамические значения ДОЛЖНЫ экранироваться; визуальные сообщения используют только поддерживаемую Telegram HTML-разметку.

Неуспешный HTTP/`ok=false`, включая 429, ДОЛЖЕН фиксироваться в модульном логгере без вывода в stdout. `retry_after` из ответа 429 ДОЛЖЕН попадать в запись логгера. Сетевое исключение ДОЛЖНО перехватываться без прерывания работы бота. После известного отрицательного ответа (`ok=false`, включая 429) автоматических повторов НЕ ДОЛЖНО быть. Явный ручной повтор сохранённой операции разрешается согласно telegram-delivery-recovery. Неопределённый исход HTTP — таймаут, обрыв соединения или прочее транспортное исключение — ДОЛЖЕН повторяться не более одного раза, только пока в delivery-состоянии нет подтверждённого `message_id` этой доставки; общее число транспортных попыток ограничено конфигурацией (`[notifier.telegram] max_transport_attempts`, вшитый дефолт — 1, поставляемая конфигурация — 2). Повтор — это повтор того же запроса с тем же телом, а не новая публикация: локальная невозможность построить график до HTTP допускает одно текстовое представление того же события, а сетевой таймаут `sendPhoto` НЕ ДОЛЖЕН запускать вторую публикацию `sendMessage`.

Ответ «message is not modified» на редактирование ДОЛЖЕН считаться безвредным результатом. Сбой редактирования карточки НЕ ДОЛЖЕН создавать её копию или препятствовать последующим независимым событиям. Остановка ДОЛЖНА дренировать обработку за отведённое время (по умолчанию 5 секунд), а недоставленный остаток — сохраняться для ручного восстановления с предупреждением.

#### Scenario: Успешная отправка
- **WHEN** канал получает текстовое событие при настроенном Telegram
- **THEN** выполняется HTTP POST `sendMessage` через настроенный адрес с `chat_id`, текстом и заявленным таймаутом (по умолчанию 10 секунд); HTTP 200 с `ok=true` подтверждает доставку

#### Scenario: Публикация не ждёт сеть
- **WHEN** сеть или рендеринг медленны и канал получает событие
- **THEN** вызывающий поток выполняет только ограниченное локальное сохранение и не ждёт визуализацию или сеть; они выполняются фоновым работником

#### Scenario: Некорректный ответ API
- **WHEN** Telegram отвечает HTTP не 200 либо HTTP 200 с `ok=false`
- **THEN** записывается ошибка без секретов, неподтверждённый message_id не сохраняется, повтор не выполняется; работа продолжается

#### Scenario: Ответ 429 не повторяется
- **WHEN** Telegram отвечает `429` с `retry_after`
- **THEN** запрос выполняется один раз, `retry_after` попадает в логгер

#### Scenario: Повтор при неопределённом исходе
- **WHEN** запрос завершается таймаутом или обрывом соединения и в delivery-состоянии нет подтверждённого `message_id` этой доставки
- **THEN** выполняется не более одного повтора того же запроса; после подтверждения повторы прекращаются, `message_id` сохраняется только из подтверждённого ответа

#### Scenario: Вторая неопределённость не повторяется
- **WHEN** неопределённым оказалась и повторная попытка
- **THEN** запросы прекращаются, попытка фиксируется как неопределённая, бот продолжает работу

#### Scenario: Сетевое исключение
- **WHEN** запрос завершается исключением или таймаутом
- **THEN** ошибка записывается в логгер, выполняется не более одного повтора того же запроса, альтернативная публикация не выполняется; бот продолжает работу

#### Scenario: Длинное сообщение разбивается
- **WHEN** HTML-текст или подпись превышают соответствующий лимит
- **THEN** подробности переносятся в корректные текстовые продолжения в исходном порядке без разрыва тегов, сущностей и потери фактов

#### Scenario: Переполнение очереди
- **WHEN** очередь заполнена, а приходит новое событие
- **THEN** теряется только сигнал пробуждения; оба принятых события остаются в постоянном хранилище и обрабатываются в порядке приёма

#### Scenario: Остановка дренирует очередь
- **WHEN** канал закрывается при непустой очереди
- **THEN** события обрабатываются за отведённое время; неотправленный остаток сохраняется для ручного восстановления с предупреждением

#### Scenario: Дефолтные токены из .env
- **WHEN** фабрика создаёт Telegram-канал
- **THEN** она передаёт значения из `.env`, загруженные `src.config`; канал самостоятельно конфигурацию не читает

#### Scenario: Фото и подтверждение публикации
- **WHEN** готов график сделки и API подтверждает `sendPhoto`
- **THEN** отправлены фото, HTML-подпись и кнопки; возвращённый message_id становится доступным для последующей навигации

#### Scenario: Повторное редактирование без изменений
- **WHEN** API возвращает «message is not modified» для карточки
- **THEN** существующий пост сохраняется, копия карточки не публикуется

#### Scenario: Ручное восстановление
- **WHEN** пользователь выбирает сохранённую неподтверждённую операцию командой восстановления
- **THEN** выполняются требования telegram-delivery-recovery без сброса receipts и без изменения торгового состояния

### Requirement: Неблокирующая доставка и изоляция ошибок
Нормативный уровень: MUST.
Публикация НЕ ДОЛЖНА прерываться ошибкой одного канала; ошибка ДОЛЖНА фиксироваться в логге, доставка остальным каналам продолжается. Для Telegram допускается короткое ограниченное локальное сохранение; сеть и рендеринг НЕ ДОЛЖНЫ блокировать торговый поток. Подтверждённые операции НЕ ДОЛЖНЫ повторяться. Ограниченные автоматические транспортные повторы и явно запрошенное ручное восстановление неподтверждённых операций допускаются согласно требованиям Telegram; при uncertain возможны дубли, гарантия «не более одного раза» для этих повторов не заявляется.

#### Scenario: Сбой канала не мешает другим
- **WHEN** Telegram выбрасывает исключение
- **THEN** консоль получает событие, ошибка записана в лог

#### Scenario: Ошибка не влияет на торговлю
- **WHEN** каналы выбрасывают исключения
- **THEN** торговый цикл продолжает работу

#### Scenario: Подтверждённая доставка не повторяется
- **WHEN** та же операция повторно получена или выбрана для ручной доставки
- **THEN** подтверждённый receipt исключает новый HTTP-запрос этой операции
