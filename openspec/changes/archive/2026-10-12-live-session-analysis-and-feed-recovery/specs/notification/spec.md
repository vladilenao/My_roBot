## ADDED Requirements

### Requirement: Датированный стартовый обзор
Нормативный уровень: MUST. Система ДОЛЖНА публиковать стартовый обзор текущего запуска как отдельное информационное событие `startup_analysis`. Для каждой назначенной пары обзор ДОЛЖЕН содержать короткое имя инструмента, ТФ, полную дату и время закрытия последней доступной свечи с часовым поясом, результаты назначенных стратегий/профилей, краткие существенные значения индикаторов и состояние достаточности/покрытия данных. BUY/SELL ДОЛЖНЫ быть помечены как результат обзора, а не принятая сделка. Отсутствие сигнала ДОЛЖНО быть видно по каждой паре и НЕ ДОЛЖНО растворяться в обычной сводке HOLD без времени анализируемой свечи. Время публикации ДОЛЖНО указываться отдельно и НЕ ДОЛЖНО подменять время бара.

#### Scenario: Стартовый HOLD
- **WHEN** все привязки пары дали отсутствие сигнала
- **THEN** обзор содержит пару, дату закрытия её свечи и результаты привязок, а не только число HOLD текущего тика

#### Scenario: Старый BUY
- **WHEN** последний закрытый бар предыдущей сессии дал BUY
- **THEN** обзор показывает исходную дату, индикаторы и информационный статус, не утверждая принятие сделки

#### Scenario: Разные последние свечи
- **WHEN** последние доступные бары двух ТФ относятся к разным временам или сессиям
- **THEN** каждый результат имеет собственную дату и время закрытия

#### Scenario: Недостаточный прогрев
- **WHEN** часть привязок не получила достаточную историю
- **THEN** обзор показывает их причину и доступное/требуемое число свечей, не подменяя результат HOLD

### Requirement: Наблюдаемое состояние рыночных данных
Нормативный уровень: MUST. Система ДОЛЖНА публиковать событие `market_data_status` при смене состояния пары и с ограниченным повтором неизменного ожидания. Оно ДОЛЖНО различать ожидание открытия сессии, обычное ожидание завершения/публикации бара, задержку данных, недостаток прогрева/покрытия, неизвестное расписание, ограничение API и восстановление. Сообщение ДОЛЖНО содержать инструмент, ТФ, момент наблюдения, последнюю полученную закрытую свечу и последний реально проанализированный бар с полными датами/поясом, ожидаемый интервал и известную причину; неизвестные значения обозначаются явно. Подтверждённое следующее открытие ДОЛЖНО отображаться при ожидании сессии.

Плановый перерыв НЕ ДОЛЖЕН отображаться как ошибка фида только по календарному возрасту свечи. Сообщения ДОЛЖНЫ публиковаться и при отсутствии успешных торговых тиков; технические DEBUG-строки не заменяют пользовательское состояние. Изменение последнего полученного/проанализированного бара отражается в следующем ограниченном сообщении, а не вызывает поток уведомлений на каждом опросе.

#### Scenario: Рынок закрыт
- **WHEN** после обзора применимый календарь подтверждает перерыв
- **THEN** показаны последняя сессия, ожидание возобновления и известное время открытия

#### Scenario: Данные задерживаются при открытом рынке
- **WHEN** ожидаемый торговый бар не пришёл за срок публикации
- **THEN** пользователь видит затронутую пару, последнюю полученную и проанализированную свечи, ожидаемый интервал и длительность задержки

#### Scenario: Ничего не анализируется
- **WHEN** все пары ожидают данные и анализ не выполнялся
- **THEN** сообщение состояния доставляется по своей периодичности, а последний анализ не выдумывается

#### Scenario: Повтор одинаковой проверки
- **WHEN** состояние не изменилось и период повторного уведомления не истёк
- **THEN** новое одинаковое сообщение не выводится

#### Scenario: Данные вернулись
- **WHEN** после задержки появились данные
- **THEN** публикуется переход к восстановлению/актуальному состоянию с фактическими границами прогресса; оставшийся пробел не скрывается

## MODIFIED Requirements

### Requirement: Каталог типов событий
Нормативный уровень: MUST. Каталог ДОЛЖЕН содержать 19 существующих типов пользовательских уведомлений, два новых типа `startup_analysis` и `market_data_status` и два служебных типа `tick_started` и `tick_finished`. Консоль по умолчанию ДОЛЖНА принимать все 21 пользовательский тип и обе служебные границы. Telegram по умолчанию ДОЛЖЕН получать девять lifecycle-типов: `signal`, `trade_opened`, `position_added`, `stop_hit`, `target_hit`, `stop_moved`, `trade_closed`, `trade_cancelled`, `order_rejected`; новые информационные типы доступны только при явной подписке.

Отмена/отклонение заявки актуализируют карточку с учётом текущего состояния и НЕ ДОЛЖНЫ автоматически означать закрытие уже открытой позиции. Явные наборы событий пользователя ДОЛЖНЫ сохраняться без скрытого добавления новых отображаемых событий. Служебные границы ДОЛЖНЫ доставляться технически независимо от пользовательских списков и НЕ ДОЛЖНЫ включать отключённые сообщения. Схемы новых событий ДОЛЖНЫ быть самодостаточными: каналы не запрашивают рынок или торговую базу для их отображения.

#### Scenario: Состав по умолчанию
- **WHEN** наборы событий не переопределены
- **THEN** консоль получает 21 пользовательский тип и две служебные границы, Telegram — девять lifecycle-типов

#### Scenario: Отказ не попадает в Telegram
- **WHEN** сигнал не допущен
- **THEN** rejected идёт в консоль, Telegram по умолчанию не создаёт карточку

#### Scenario: Явный список событий сохраняется
- **WHEN** пользователь оставил Telegram только signal и trade_closed
- **THEN** остальные типы, включая новые информационные, скрыто не доставляются

#### Scenario: Старый список консоли не требует миграции
- **WHEN** пользователь задал консоли events = ["decision", "error"]
- **THEN** обязательные границы продолжают доставляться, новые информационные типы автоматически не добавляются

#### Scenario: Информационный тип явно включён в Telegram
