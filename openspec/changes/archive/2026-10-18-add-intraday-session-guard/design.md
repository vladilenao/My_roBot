## Context

Новый вход проходит одну точку допуска в обоих циклах, а сопровождение — один вызов `manage` на каждом цикле защиты (таймфрейм защиты `1m`):

```
TradingBot._analyze / LiveAnalysis._calculate
  └─ TradeManager.actions_for_signal
       ├─ контрактный переход / близкая экспирация → недопуск contract-expiring
       ├─ сделка связки открыта → _manage_owned (противоположный сигнал, добор)
       └─ иначе → _plan_entry (фильтры, план профиля, портфельный допуск)

TradingBot / LiveAnalysis (цикл защиты)
  └─ TradeManager.manage
       ├─ действия без бара: переход контракта, экспирация (_close_expiring), таймаут входа
       └─ профиль на таймфрейме плана

TradeManager.submit_action — единая точка отправки; увеличения (OpenTrade, AddToTrade) уже проверяются здесь на контрактный переход
```

Расписание торгов приходит от брокера (`TradingSchedules`) по режиму торгов инструмента, хранится по торговым датам в `market-data.sqlite3` и разбирается в `TradingCalendar` → `CalendarDay` → `SessionWindow(start, end, kind, raw_type)`. `raw_type` различает сессии. Расписание 16.10.2026 (МСК):

| Окно (`raw_type`) | Акции (`moex_mrng_evng_e_wknd_dlr`) | Фьючерсы (`forts_futures_weekend`) |
|---|---|---|
| `regular_trading_session_morning` | 07:00:00–08:59:59 | 07:00:00–08:59:59 |
| `regular_trading_session_main` | 09:00:00–18:54:59 | 09:00:00–18:59:59 |
| `closing_auction_main` | 18:55:00–18:59:30 | — |
| `regular_trading_session_evening` | 19:00:01–23:49:59 | 19:00:00–23:50:00 |
| `holiday_trading_session_morning` (сб, вс) | 10:00–19:00 | 10:00–19:00 |

Дневной клиринг FORTS 14:00–14:05 в ответе брокера не виден, его ведёт `[trading].clearing_times`.

Live получает календарь пары через `MarketDataCache.calendar_for` (сверщик рыночных данных, сохранённые дни, без сети на торговом тике). Исторический прогон — через `MarketCalendar` снимка прогона.

## Goals / Non-Goals

**Goals:**
- Короткие сделки не открываются в вечерней сессии и в сессиях выходного дня и не переносятся через закрытие торгового дня.
- Позиция, которая уже взяла первую цель и защищена безубытком всей сделки, может пережить перерыв: гэп рискует только прибылью.
- Одинаковое поведение в live и в историческом прогоне, решения видны в трассе и журнале.

**Non-Goals:**
- Метка горизонта у привязки, защита свинговых сделок, дневной клиринг, ручное закрытие, поиск уровней.

## Decisions

### D1. Внутридневная сделка

Сделка внутридневная, если длительность таймфрейма её плана (`TradePlan.timeframe`, сохраняется в плане и переживает перезапуск) не больше `max_timeframe`. Для сигнала до создания плана берётся таймфрейм привязки, с которым идёт допуск. Таймфрейм сравнивается по длительности из общего маппинга таймфреймов, не по строке. Сделка без известного таймфрейма плана считается свинговой: правило не закрывает то, чью природу не знает.

Альтернатива — ключ `horizon` у привязки — отклонена владельцем: стратегии робота работают и на коротких, и на длинных таймфреймах, природу сделки определяет таймфрейм.

### D2. Типы сессий

`entry_sessions` принимает имена:

| Имя | `raw_type` окна |
|---|---|
| `morning` | `regular_trading_session_morning` |
| `main` | `regular_trading_session_main` |
| `evening` | `regular_trading_session_evening` |
| `weekend` | `holiday_trading_session_morning`, `holiday_trading_session_evening` |

Аукционы, клиринг, дилерские (`dealer_*`) и родовые окна (`regular_trading_session`, `opening_auction`, `closing_auction`) ни к одному имени не относятся: вход в них не разрешается этим правилом, а конец сессии акций — конец непрерывных торгов, а не аукциона закрытия. Неизвестный `raw_type` тоже не относится ни к одному имени.

### D3. Блок разрешённых сессий и его рубежи

На торговую дату инструмента берутся окна разрешённых типов в порядке времени. Соседние окна, между которыми не больше 60 секунд, сливаются в один блок (утренняя 08:59:59 → основная 09:00:00). Конец окна — `end` с округлением вверх до целой минуты: 18:54:59 → 18:55, 18:59:59 → 19:00, 23:50:00 → 23:50.

Для блока с концом `E`:
- **рубеж входа** `E − no_entry_before_close_min`;
- **рубеж закрытия** `E − flatten_before_close_min`.

При значениях по умолчанию и расписании 16.10.2026: акции — вход до 17:55, закрытие в 18:35; фьючерсы — вход до 18:00, закрытие в 18:40. Если разрешены, например, `main` и `evening`, они сливаются в один блок до 23:50, и рубежи считаются от него.

### D4. Допуск нового входа

Проверка выполняется в `actions_for_signal` после контрактных проверок и до `_manage_owned`/`_plan_entry`, только для внутридневного таймфрейма и только для нового входа (сигнал по уже открытой сделке своей связки идёт в сопровождение; добор проверяется в D8). Момент решения — рыночное время менеджера `now` (для live это время допуска после закрытия бара; для 15.10 23:10).

| Условие в момент `now` | Результат |
|---|---|
| нет применимого дня расписания, день неторговый или в нём нет ни одного типизированного окна | `session-schedule-unknown` |
| `now` не внутри окна разрешённого типа | `intraday-session-closed` |
| `now` внутри блока, но `now ≥` рубежа входа | `intraday-close-near` |
| иначе | правило пропускает, допуск идёт дальше |

Причины входят в `SignalAdmission.rejections` с русским описанием, как прочие недопуски, и видны в консоли блоком ОТКЛОНЕНО. Устаревшее расписание (`stale`, последнее обновление не удалось) применяется как известное.

### D5. Снятие незаполненного входа

В `manage` для внутридневной сделки в `ENTRY_PENDING`, если `now ≥` рубежа входа текущего блока или `now` вне разрешённых окон, отправляется `CancelEntry` с причиной `intraday-session-end`. Действие не зависит от бара (как экспирация и таймаут), повторная отмена не дублирует незавершённую команду. Если одновременно действует экспирация или контрактный переход, применяется их причина и одна команда.

### D6. Закрытие перед концом блока

Обязательство закрыть внутридневную позицию (фазы `OPEN`, `BUILDING`, `REDUCING`, остаток > 0) возникает в момент `now ≥` рубежа закрытия блока, в котором позиция открыта или в который была перенесена, и сохраняется до исполнения закрытия или до одобрения переноса (D7). Это закрывает и позицию, пережившую рубеж из-за остановки робота: на первом цикле после перезапуска она будет закрыта или перенесена по D7, даже если блок уже закончился (в вечернюю сессию — сразу, ночью — на открытии следующей сессии).

Закрытие — `CloseTrade` с причиной `intraday-session-end`, исполняется по общим правилам исполнения (следующий доступный бар). Повтор на следующем цикле не создаёт вторую незавершённую команду закрытия. Экспирация и контрактный переход имеют приоритет и дают одну команду со своей причиной.

### D7. Перенос защищённой позиции

При `keep_if_tp1_and_breakeven = true` на рубеже закрытия:

1. **Первая фиксация.** Для профилей с целями (`levels_rr`, `pattern_targets`, `atr_trend`) — подтверждена цель `tp-1`. Для `ma_cloud`, у которого нет целей, — подтверждён первый частичный выход профиля (`ReduceTrade`) с положительной валовой прибылью. Без первой фиксации — закрытие по D6.
2. **Безубыток всей сделки** `BE` — по формуле требования «Безубыток всей сделки после первой цели» (реализованная прибыль, все начисленные комиссии, ожидаемая комиссия выхода остатка, запас проскальзывания), с округлением LONG вверх и SHORT вниз, **без** порога `min_be_r`. При неизвестных расходах BE не считается — закрытие по D6.
3. **Решение** (`d` = +1 для LONG, −1 для SHORT; `close` — закрытие последнего бара цикла защиты):
   - `d×(подтверждённый стоп − BE) ≥ 0` — позиция переносится без действий;
   - иначе, если `d×(close − BE) > 0` — `MoveStop` в `BE` с причиной `intraday-carry-break-even`, позиция переносится после подтверждения стопа;
   - иначе — `CloseTrade` по D6.

Пока `MoveStop` не подтверждён, позиция остаётся под обязательством закрытия и на каждом цикле решается заново (например, рынок ушёл ниже BE — закрытие). Одобренный перенос записывается в состояние профиля сделки с концом блока (`intraday_carry_until`), чтобы не повторять решение в этом блоке. На следующий торговый день перенесённая позиция снова проверяется на своём рубеже закрытия.

Пример YDEX 16.10.2026: LONG 10 по 3442.5, TP1 5 по 3466.5, остаток q=5, G=120 ₽, F=22.5 ₽, выход остатка 7.5 ₽, запас 2.5 ₽, V=1, шаг 0.5. `BE = 3442.5 + (22.5 + 7.5 + 2.5 − 120)/5 = 3425.0`. Стоп 3422.5 хуже BE. При `close = 3450` в 18:35 стоп переносится в 3425.0 и позиция остаётся; при `close = 3424` — закрытие.

### D8. Доборы

`submit_action` отклоняет `AddToTrade` внутридневной сделки, если в момент отправки вход по D4 не был бы допущен; отказ получает тот же код (`intraday-session-closed`, `intraday-close-near`, `session-schedule-unknown`), пишется в трассу и не считается ошибкой. Так запрет покрывает и добор по сигналу, и ретест-добор профиля `ma_cloud`. Перенесённая позиция ведётся профилем как обычно: стоп, цели, сигнальные и противоположные выходы работают в любой сессии.

### D9. Источник расписания

`TradeManager` получает провайдер `session_calendar(instrument_key) -> TradingCalendar | None` и настройки `IntradaySettings`. Live: провайдер поверх `MarketDataCache.calendar_for` — только сохранённые дни, без сети. История: `MarketCalendar` снимка прогона, то же расписание, что у ожидания свечей. Торговая дата для `now` — `exchange_date` из `src/market_calendar/intervals.py`. Сама политика — чистые функции в `src/trade_management/session_guard.py` от таймфрейма, окон дня, настроек и `now`; менеджер только применяет результат.

Без расписания закрытие по D6 не выполняется (нет рубежа), а вход и добор запрещены (D4, D8) — так при сбое расписания робот не открывает короткие сделки, но и не закрывает позиции по выдуманному времени.

### D10. Трасса

Каждое решение правила, отличное от «правило пропускает», пишется трассой `session.intraday` (`algorithm_version = "1"`) в транзакции решения: входы — таймфрейм плана, `max_timeframe`, `now`, торговая дата, версия дня расписания, разрешённые типы, границы блока, оба рубежа; при D7 — первая фиксация, BE, подтверждённый стоп, `close`; итог — код причины и действие.

### D11. Конфигурация

```toml
[trading.intraday]
enabled = true                       # выключатель правила целиком
max_timeframe = "15m"                # сделки на таймфрейме не больше — внутридневные
entry_sessions = ["morning", "main"] # morning, main, evening, weekend
no_entry_before_close_min = 60       # рубеж последнего входа, минут до конца блока
flatten_before_close_min = 20        # рубеж закрытия, минут до конца блока
keep_if_tp1_and_breakeven = true     # перенос позиции с первой фиксацией и стопом в безубытке
```

Ограничения: `max_timeframe` — известный таймфрейм; `entry_sessions` — список без повторов из четырёх имён, может быть пустым (внутридневные входы запрещены всегда); минуты — целые ≥ 0; `flatten_before_close_min ≤ no_entry_before_close_min` (иначе позиция, открытая между рубежами, закрывалась бы сразу). Незнакомый ключ или нарушение — `ConfigError` с файлом и ключом. Без секции действуют значения по умолчанию.

## Risks / Trade-offs

- **Меняется поведение по умолчанию.** Часть прежних прибыльных вечерних и ночных сделок исчезнет. Сравнение — исторический прогон на одном диапазоне с `enabled = false` и `true`: число сделок, сумма R, максимальный убыток сделки в R.
- **Прогон по датам без расписания** (ранние диапазоны) не получит внутридневных входов: `session-schedule-unknown`. Это видно в отчёте прогона по причинам недопуска; молча торговать без расписания хуже.
- **Закрытие в 18:35/18:40** платит комиссию и проскальзывание по позиции, которая могла бы дойти до цели. Перенос по D7 оставляет такие позиции, если они уже прибыльны.
- **Позиция, пропустившая рубеж из-за остановки робота,** закрывается после гэпа. Это не спасает от уже случившегося гэпа, но не оставляет короткий стоп на следующую ночь.
- **Брокер изменит типы окон.** Неизвестный `raw_type` не разрешает вход; если расписание дня останется без типизированных окон — `session-schedule-unknown`, что заметно сразу.

## Migration Plan

Схемы баз не меняются. Открытые на момент выкладки внутридневные позиции подчиняются правилу с первого цикла: без первой фиксации после рубежа закрытия — закрываются, с ней — переносятся по D7. Откат — `enabled = false` в `robot.toml`.
