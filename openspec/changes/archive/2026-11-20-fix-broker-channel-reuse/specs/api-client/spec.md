## MODIFIED Requirements

### Requirement: Аутентифицированный клиент (контекстный менеджер)
- Система ДОЛЖНА предоставлять функцию `client_context(token=None)`, возвращающую `Client` как контекстный менеджер (`with`).
- Если `token` не передан, используется `TINKOFF_TOKEN` из конфигурации.
- Способ получения клиента ДОЛЖЕН определяться режимом прогона: в боевом режиме возвращается аутентифицированный клиент T-Банка, в историческом режиме — клиент исторического источника. Набор методов, используемых контуром робота, ДОЛЖЕН быть одинаковым в обоих режимах; остальному коду ДОЛЖЕН быть доступен единый клиент выбранного источника.
- В боевом режиме unary-вызовы ДОЛЖНЫ использовать одно долгоживущее подключение на токен: новое подключение к брокеру в части случаев устанавливается ~2 с, открытое отвечает за десятки миллисекунд. Выход из блока `with` НЕ ДОЛЖЕН закрывать общее подключение. Вызов, завершившийся `UNAVAILABLE`, ДОЛЖЕН сбрасывать общее подключение, чтобы следующий вызов открыл новое. Поток свечей ДОЛЖЕН открывать отдельное подключение. Закрытие провайдера при остановке ядра ДОЛЖНО закрывать общее подключение.

#### Scenario: Контекстный менеджер используется через with
- **WHEN** `with client_context() as client:` выполняется в вызывающем коде повторно
- **THEN** клиент открывается при первом вызове, следующие вызовы используют то же подключение, выход из блока `with` его не закрывает

#### Scenario: Кастомный токен
- **WHEN** `client_context(token="custom-token")` вызывается с явным токеном
- **THEN** клиент создаётся с указанным токеном, а не с `TINKOFF_TOKEN`, и подключение не делится с другим токеном

#### Scenario: Обрыв подключения
- **WHEN** вызов внутри `with client_context()` завершается ошибкой `UNAVAILABLE`
- **THEN** общее подключение сбрасывается, следующий вызов открывает новое

#### Scenario: Исторический режим
- **WHEN** прогон выполняется в историческом режиме
- **THEN** `client_context()` возвращает клиент исторического источника с тем же набором методов, что и в боевом режиме
