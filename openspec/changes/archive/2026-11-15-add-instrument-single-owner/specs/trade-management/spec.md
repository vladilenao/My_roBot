## MODIFIED Requirements

### Requirement: Владелец и жизненный цикл сделки
Нормативный уровень: MUST.
Система ДОЛЖНА связывать сделку с устойчивым ID привязки, конкретным контрактом и неизменным снимком параметров профиля. Идентификатор сохраняемой сделки строится из идентичности связки (инструмент, стратегия, профиль фильтрации, таймфрейм) вместе с временем бара и направлением и ДОЛЖЕН быть уникален в её пределах: две связки одной стратегии на одном таймфрейме с разными профилями фильтрации ДОЛЖНЫ получать разные `trade_id`. На пару (привязка, контракт) разрешена одна незавершённая сделка, включая ожидающий вход. Повторный входной сигнал той же связки по тому же бару ДОЛЖЕН отклоняться на уровне бизнес-логики до записи в `trades`, с причиной `duplicate-signal`, и НЕ ДОЛЖЕН приводить к ошибке ограничения PRIMARY KEY. Состояние объёма, средней цены и выполненных действий ДОЛЖНО определяться подтверждёнными исполнениями, а не сигналами.

На инструмент в контуре ДОЛЖНА приходиться одна привязка-владелица. Инструмент — контракт или всё семейство фьючерса (переход BR-6.25 → BR-7.25 — тот же инструмент). Инструмент занят, пока у какой-либо привязки по нему есть незавершённая сделка: ожидающий вход или ненулевой объём. Новый вход ДРУГОЙ привязки по занятому инструменту ДОЛЖЕН отклоняться до планирования и резервирования: в ту же сторону — с причиной `instrument-busy`, во встречную — с причиной `opposite-exposure`. Существующая сделка при этом НЕ ДОЛЖНА меняться. Текст отказа ДОЛЖЕН называть контракт и занявшую привязку (стратегия и таймфрейм), отказ ДОЛЖЕН записываться следом расчёта `portfolio.instrument-busy` или `portfolio.opposite-exposure` со списком блокирующих сделок. Добор, сокращение, выходы, перенос стопа и закрытие своей сделки владелицей НЕ ДОЛЖНЫ ограничиваться этим правилом; разворот владелицы допускается как новый вход после подтверждённого закрытия.

Кандидаты одного тика ДОЛЖНЫ проходить эту проверку по очереди в порядке ранжирования цикла: следующий кандидат видит ожидающий вход уже допущенного. Отказ кандидату по бюджету, фильтру, сессии или другой причине инструмент НЕ занимает. Инструмент освобождается, когда по нему не осталось незавершённых сделок; отклонённый сигнал НЕ ДОЛЖЕН откладываться или повторяться. Если по инструменту уже открыты сделки нескольких привязок (до введения правила или после восстановления), они НЕ ДОЛЖНЫ закрываться и сопровождаются каждая своей привязкой, включая добор; новые входы других привязок отклоняются, пока открыта хотя бы одна из них. Правило ДОЛЖНО действовать одинаково во всех видах контуров — эмуляции, истории, песочнице и счёте — без настройки.

#### Scenario: Две стратегии на одном инструменте
- **GIVEN** в контуре «Эмуляция» привязка `macd_rsi_stoch · 4h` держит лонг GAZP 10 лотов
- **WHEN** привязка `ma_cloud_rsi_macd · 1h` получила BUY по GAZP и бюджет допускает вход
- **THEN** вход отклонён с причиной `instrument-busy` и текстом «по GAZP уже ведёт сделку macd_rsi_stoch · 4h», новая сделка не создаётся, сделка владелицы не меняется

#### Scenario: Ожидающий вход занимает инструмент
- **GIVEN** у привязки A по Si выставлен лимитный вход BUY, исполнения нет
- **WHEN** привязка B получила BUY по Si
- **THEN** вход B отклонён с причиной `instrument-busy`

#### Scenario: Два сигнала в одном тике
- **WHEN** в одном тике привязки A (выше по ранжированию) и B получили BUY по одному инструменту
- **THEN** A получает ожидающий вход, B отклонена с причиной `instrument-busy`

#### Scenario: Отказ бюджета не занимает инструмент
- **WHEN** в одном тике привязке A отказано по бюджету, а привязка B получила BUY по тому же инструменту
- **THEN** B допускается по обычным правилам

#### Scenario: Две связки одной стратегии с разными профилями
- **WHEN** на Si 5m одна и та же стратегия `ma_cloud_rsi_macd` дала BUY из привязок с профилями `raw` и `triple_screen` в одном тике
- **THEN** первая по ранжированию получает сделку в состоянии `ENTRY_PENDING`, вторая отклонена с причиной `instrument-busy`; ошибка `UNIQUE constraint failed: trades.trade_id` не возникает

#### Scenario: Добор владелицы
- **GIVEN** привязка A держит лонг по инструменту
- **WHEN** A получила допустимый сигнал добора
- **THEN** добор проходит по правилам профиля, правило занятости его не ограничивает

#### Scenario: Инструмент освобождается после выхода
- **GIVEN** сделка привязки A по инструменту закрыта и подтверждена, других незавершённых сделок по нему нет
- **WHEN** привязка B получила BUY по этому инструменту на следующем баре
- **THEN** B допускается по обычным правилам

#### Scenario: Семейство фьючерса
- **GIVEN** привязка A держит лонг BR-6.25
- **WHEN** привязка B получила BUY по BR-7.25
- **THEN** вход B отклонён с причиной `instrument-busy`

#### Scenario: Уже открытые сделки двух привязок
- **GIVEN** до правки по GAZP открыты лонги привязок A и B
- **WHEN** робот запущен на правке, A получила сигнал добора, а привязка C — BUY по GAZP
- **THEN** сделки A и B не закрываются, добор A проходит по правилам профиля, вход C отклонён с причиной `instrument-busy`

#### Scenario: Правило в истории
- **WHEN** контур «История» прогоняет две привязки одного инструмента и обе дают BUY, пока сделка первой открыта
- **THEN** вторая отклонена с причиной `instrument-busy`, как в эмуляции

#### Scenario: Повтор сигнала внутри одной связки
- **WHEN** та же привязка повторно доставляет сигнал по тому же бару
- **THEN** результат допуска содержит причину `duplicate-signal`, новая сделка не создаётся, существующая не изменяется

#### Scenario: Отказ во встречном входе
- **WHEN** по инструменту есть LONG либо незавершённая заявка BUY и другая привязка предлагает SHORT
- **THEN** новый вход отклоняется с причиной `opposite-exposure`, существующая сделка не закрывается

#### Scenario: Частично исполненный вход
- **WHEN** из двух разрешённых контрактов исполнен один
- **THEN** сопровождается один контракт, риск неисполненного остатка зарезервирован; новый вход не создаётся
