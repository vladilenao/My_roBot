## Context

Доставка в Telegram идёт через единого фонового работника: `TelegramChannel._deliver` → `TelegramTransport.request` → запись в `data/telegram_delivery.sqlite3` (namespace `telegram`, статусы `delivered`/`failed`/`uncertain`, `message_id`). Сейчас любой неуспешный HTTP-исход (включая таймаут/обрыв — `ApiResult.ok=False, status="uncertain"`) фиксируется как `uncertain` с `message_id=NULL`, а спека `notification` запрещает любые автоматические повторы. Таймаут жёстко 10 с, прокси Cloudflare не успевает — отсюда потерянная карточка NG (см. proposal.md). Повторы при этом не должны создавать дублей: подтверждённый `message_id` — единственный признак того, что пост дошёл.

## Goals / Non-Goals

**Goals:**
- Один транспортный повтор при неопределённом исходе (таймаут/обрыв), пока нет подтверждённого `message_id`.
- Общее число попыток ограничено конфигом `[notifier.telegram] max_transport_attempts` (лоадер-дефолт 1, `default.toml` — 2).
- Ноль дублей: после подтверждённого ответа повторы прекращаются, `message_id` пишется один раз.

**Non-Goals:**
- Повторы при `ok=false`/429 (по-прежнему без повторов; `retry_after` — только в лог).
- Фолбэк `sendMessage` после таймаута `sendPhoto` (запрещён спекой).
- Ретраи `editMessage*`, фоновой очереди, других каналов.
- Backfill/догон не доставленных `uncertain`-событий после рестарта — только повтор в рамках живой обработки.

## Decisions

1. **Где живёт признак повторяемости**: `ApiResult` в `telegram_transport.py` получает поле `retryable: bool` — `True` только для транспортных исключений (`requests.RequestException` и не-HTTP ошибки чтения ответа), `False` для любого разобранного ответа (HTTP != 200, `ok=false`). Альтернатива — рекласифицировать `status` в transportе («uncertain»/«failed»): отвергнуто, статус в БД — это состояние доставки, а «можно ли повторять» — свойство исхода одной HTTP-попытки; мешать их нельзя, иначе ломается существующая семантика `uncertain`.

2. **Где выполняется повтор**: в `_deliver` (`telegram.py`), между вызовом `request` и записью в delivery-БД — повторяется только сам запрос, тело/рендер не пересоздаются. В `request()` повтор не предлагается: транспорт не знает про delivery-состояние (нужно проверять `message_id`), а транспортный слой не должен читать БД. Альтернатива — `Retry-After`-цикл в транспорте: отвергнута (не видит `message_id`, нарушает «один запрос = один результат»).

3. **Условие повтора**: `result.retryable is True` **и** в `attempts` по ключу доставки нет строки с `message_id IS NOT NULL` **и** число уже выполненных попыток < `max_transport_attempts`. Задержка перед повтором — фиксированные ~2 с (`time.sleep` в фоновом работнике допустим: он и так дренирует очередь). Альтернатива — без задержки: отвергнута, мгновенный повтор на том же обрыве бесполезен; экспоненциальная backoff — избыточна для одной повторной попытки.

4. **Запись промежуточной неопределённости**: если первая попытка uncertain и повтор не разрешён (лимит/уже есть `message_id`), статус `uncertain` пишется как раньше. Если разрешён — статус `uncertain` НЕ фиксируется до исхода повтора: либо приходит `delivered` с `message_id`, либо финальный статус последней попытки. Это исключает окно, в котором БД говорит «uncertain, повторять нельзя», хотя повтор ещё в полёте.

5. **Конфиг**: новый ключ валидируется в `_parse_notifier_subsection` (только `[notifier.telegram]`, целое ≥ 1, рядом с уже добавленным `request_timeout`), тип в `_EXPECTED_TYPES`, дефолт в `_DEFAULTS` (`src/config.py`) — 1, в `default.toml` — 2. Фабрика читает `src.config` и передаёт значение в `TelegramChannel` (как `request_timeout`). Лоадер-дефолт 1 означает «повтор выключен, пока пользователь не включил» — безопасное поведение для старых внешних `robot.toml`.

## Risks / Trade-offs

- [Повтор доставил пост, а подтверждённый ответ первого запроса потерялся] → исход первой попытки — только `uncertain` (нет `message_id` в ответе), а подтверждение = `message_id`; если `message_id` уже сохранён, повтор запрещён условием 3. Дубль возможен только если Telegram принял пост, ответ потерялся, и повторный запрос тоже был принят — это теоретически возможно, но: (а) задержка 2 с, (б) спека допускает ровно одну такую гонку на доставку, в) вторая публикация того же ключа после `delivered` невозможна.
- [Спека запрещает повторы — архивация изменит её напрямую] → дельты в change переписывают оба требования целиком (MODIFIED), архивация применит их штатно.
- [Внешний `robot.toml` без новых ключей] → лоадер-дефолты: `request_timeout=10` (прежнее поведение), `max_transport_attempts=1` (повторы выключены) — ни одно существующее окружение не меняет поведение молча; `default.toml` поставки включает оба значения явно.
- [Фоновый работник спит 2 с на повторе] → один сон на доставку; очередь с переполнением и дренированием при закрытии это уже допускает (окно дренажа 5 с — повтор укладывается).

## Migration Plan

Код и конфиг меняются в одном релизе, миграция БД не требуется (схема `attempts` не меняется). Откат = откат релиза: новое поле `retryable` и ключи конфига игнорируются старым кодом. В течение переходного окна (старый бот уже запущен без pid-файла) `data/robot.pid` создаётся вручную — см. runtime lock, отдельного шага здесь нет.

## Open Questions

- Нужен ли отдельный счётчик попыток в БД: решено — нет. PK `attempts(namespace, operation_key)` даёт ровно одну строку на ключ, сосчитать попытки по строкам нельзя; счётчик попыток — локальный в рамках одного вызова `_operation` между `begin_attempt` и `finish_attempt`. Условие «нет подтверждённого `message_id`» обеспечивается самим `begin_attempt`: у уже подтверждённого ключа строка существует, повтор невозможен. Схема не меняется.
