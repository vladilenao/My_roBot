# Design: ООП-рефакторинг пакета notifier

## Context

Сейчас `src/notifier` — два свободных модуля (`formatter.py`, `sender.py`); раннер сам склеивает «решение → текст → доставку». В `send_signal` стоит безусловный `return`: HTTP-блок отправки недостижим (баг), фактически бот только печатает в stdout. Мотивация и границы — см. proposal.md («Why»).

## Goals / Non-Goals

**Goals:**

- Классовая иерархия нотификаторов с общей абстракцией и внедрением зависимостей через конструктор.
- Восстановление рабочей отправки в Telegram (HTTP-блок переносится дословно).
- Выбор единственного канала доставки правкой одной строки конфигурации.
- Сохранение наблюдаемого формата сообщений без изменений.

**Non-Goals:**

- Ретраи, очереди и гарантии доставки сообщений — качество доставки остаётся как в текущем HTTP-блоке.
- Новые каналы доставки (email и т.п.) — архитектура их допускает, но классы не вводятся.
- Изменение текстов сообщений, эмодзи и правил округления.
- Перевод стратегий с `Protocol` на ABC — разные механизмы под разные задачи.

## Decisions

### D1. Абстракция — ABC, а не Protocol
Базовый класс несёт не только интерфейс, но и общее поведение: хранение внедрённого форматтера и конкретный мостик `notify_decision`. `Protocol` общее состояние наследникам раздать не умеет и не гарантирует реализацию метода при создании экземпляра. ABC даёт fail-fast: наследник без `notify()` не создаётся вовсе. Альтернатива (Protocol, как у стратегий) отклонена: там контракт описывает чужие классы, здесь мы владеем всей иерархией.

### D2. Разделение уровней API: `notify(text)` и мостик `notify_decision(decision, label)`
Абстрактный `notify()` принимает только готовый текст — транспортная обязанность, чистая точка расширения для будущих каналов. Мостик «решение → форматтер → notify» живёт в базовом классе, поэтому раннер вызывает одну строку и не знает про тексты. Решение зафиксировано пользователем (вариант A из обсуждения). Альтернатива «раннер форматирует сам» отклонена: она оставляет склейку конвейера в раннере и делает внедрение форматтера бессмысленным.

### D3. Форматтер — класс `DecisionFormatter`, внедряемый через конструктор
Тело бывшей функции `format_decision` переезжает в метод `format(decision, instrument_label="")` класса; дефолт конструктора — экземпляр этого класса. Подмена форматтера возможна без наследования (тесты, кастомные шаблоны). Альтернативы: оставить функцию (не ООП, нет полиморфизма) или сделать форматтер методом каждого нотификатора (дублирование между наследниками).

### D4. Починка отправки без переписывания логики запроса
Недостижимый HTTP-блок становится исполняемым дословно (тот же URL, payload, таймаут 10с, обработка не-200 и исключений). Два сопутствующих изменения: (1) в ветке «токены не заданы» добавляется ранний выход — иначе POST ушёл бы с пустым токеном; (2) убирается эхо-печать `print(text)` — сообщение теперь реально уходит в Telegram, дубль в консоли вводит в заблуждение. Источник значений — атрибуты экземпляра вместо констант модуля.

### D5. Токены — дефолтные параметры конструктора из `.env`
Конструктор принимает `bot_token=None, channel_id=None` и подставляет значения из `src.config` (тот уже читает `.env` через dotenv). Явная передача в тестах исключает моки глобального состояния. Альтернатива — читать константы внутри метода — отклонена: скрытая зависимость усложняет тесты.

### D6. Выбор канала: скалярная константа в конфиге + фабрика с валидацией
В `config.py` появляется строковая константа `NOTIFIER` (по умолчанию `"telegram"`); фабрика `get_notifier()` в `src/notifier/__init__.py` отображает значение в класс по простому словарю и падает с ошибкой с перечнем доступных каналов — стиль ошибок повторяет `get_strategy`. «Ровно один канал» обеспечивается типом данных (строка, а не список). Альтернативы: реестр-декоратор как у стратегий (избыточен для двух классов), переменная окружения поверх константы (лишняя косвенность — пользователь просил выбор именно в конфиге).

### D7. Раскладка пакета
```
src/notifier/
├── __init__.py   # витрина: Notifier-экспорты + get_notifier()
├── base.py       # DecisionFormatter + AbstractNotifier(ABC)
├── telegram.py   # TelegramNotifier
└── console.py    # ConsoleNotifier
```
Имя абстракции — `AbstractNotifier` (PascalCase, питоновская норма; camelCase-вариант пользователя нормализован).

## Risks / Trade-offs

- [Первое включение боевой отправки: настроенный канал начнёт получать сообщения, которых раньше не было (всё шло в stdout)] → перед запуском в проде проверить заполненность `.env`; локальная отладка — `NOTIFIER="console"`.
- [Отправка без ретраев: разовый сбой сети теряет сообщение (останется только запись в консоли)] → осознанный trade-off, унаследован от текущего кода; улучшение доставки — вне scope.
- [Удаление публичных функций `format_decision`/`send_signal` ломает внешних потребителей] → в проекте один потребитель (`runner.py`) и один тестовый файл; оба меняются этой же сменой.
- [`src/notifier` начинает зависеть от `src.strategies.base` (Decision) в новом месте (base.py)] → направление зависимости то же, что у старого formatter.py; циклов не возникает.

## Migration Plan

Порядок шагов отражён в tasks.md: сначала строится новый пакет параллельно старому, затем переключается раннер, удаляются старые модули, переписываются тесты. Откат — обычный git revert ветки; отдельной миграции данных нет.
