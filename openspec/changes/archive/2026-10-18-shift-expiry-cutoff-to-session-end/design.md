## Context

Рубеж выхода перед экспирацией задан в календарных сутках, и спецификация `futures-rollover` прямо говорит, что N — сутки по 24 часа, а не торговые сессии. Владелец выбрал вариант: сохранить календарные N суток, но не оставлять рубеж в перерыве.

## Decisions

1. **Сдвиг только назад.** Эффективный рубеж = конец последнего торгового окна перед календарным рубежом минус запас, но не раньше начала этого окна. Поздний сдвиг (на открытие следующей сессии) отклонён: он и есть исходная проблема.
2. **Перерыв должен быть доказан расписанием.** Торговые окна — интервалы видов `continuous` и `unknown`, как в остальном календаре. Сдвиг применяется, только если расписание содержит каждую торговую дату от даты последнего окна до даты календарного рубежа. Иначе действует календарный рубеж с происхождением `schedule-unknown`. Отсутствие расписания не должно ни переносить рубеж, ни останавливать прогон.
3. **Запас до конца сессии.** Команда, поставленная на рубеже, исполняется на следующем 1m-баре, поэтому рубеж ровно на конце сессии снова дал бы исполнение на открытии следующей. Запас задаётся ключом `[trading] contract_expiry_close_before_end_min` (по умолчанию 20 минут, как `flatten_before_close_min` сессионной защиты).
4. **Короткие перерывы тоже считаются.** Рубеж в дневном или вечернем клиринге сдвигается на конец предыдущего окна минус запас. Правило одно для всех перерывов: стоимость — несколько десятков минут, выигрыш — отсутствие особых случаев.
5. **Восстановленное расписание в истории.** Сдвиг только приближает рубеж, поэтому ошибка восстановленного дня может лишь закрыть позицию раньше. Восстановленные дни допускаются для рубежа в истории на тех же условиях, что и для сессионной защиты (`[historical.schedule].use_reconstructed`). В боевом режиме — только дни брокера.
6. **Порядок в истории.** Цепочка строится по календарным рубежам (нужны UID контрактов для расписания), затем загружается расписание, затем цепочка перестраивается с эффективными рубежами и только после этого сохраняется и проходит предпроверку. Сдвиг назад не меняет состав контрактов, кроме случая, когда эффективный рубеж первого контракта оказался не позже начала прогона, — тогда работает обычное правило выбора начального контракта.
7. **Одна функция для истории и боевого режима.** `src/market_calendar/expiry.py` вычисляет эффективный рубеж из календарного рубежа, календаря и запаса; история и `TradeManager` используют её одинаково.

## Risks / Trade-offs

- Повторный запуск того же прогона даёт те же рубежи, только если расписание снимка то же. При сбое загрузки расписания рубежи станут календарными, и идентичность перехода (`transition_id` включает рубеж) изменится. Это видно в отчёте по происхождению рубежа.
- Боевое расписание брокера загружается на 7 дней вперёд, поэтому при N ≤ 2 даты до рубежа покрыты. Если расписания нет, поведение прежнее.
