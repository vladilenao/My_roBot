## Context

Мотивация и одобренные Telegram-посты перечислены в `proposal.md`. Контракт поведения — `specs/telegram-trade-cards/spec.md` и delta `specs/notification/spec.md`.

Сейчас `TelegramChannel` кладёт готовую строку в bounded-очередь и отправляет только `sendMessage` через Cloudflare. Он использует те же шаблоны, что консоль; результат Bot API и message_id не сохраняются. Дефолт — пять событий, `stop_moved` не отображается даже в общем deal-шаблоне. Matplotlib есть только в dev-зависимостях.

`Event.signal` передаёт цены целей, но не их целые аллокации, свечи и единицу количества. В `TradingBot._admit_candidate` уже доступен исходный frame. В SQLite-режиме `TradeManager.consume` применяет брокерский результат, затем вызывает observer для исполнений с накопленными gross/net/fees; `run.py` публикует эти факты. ACK переноса проходит отдельным путём `_confirm_stop`; ACK с reason=`next-bar` ещё не меняет действующий стоп. Текущий SQL-контур не должен потерять этот порядок ради графика.

Канал пользователя публичный, без группы обсуждений. Демо доказало работу фото, HTML, inline URL и редактирования через имеющийся Cloudflare transport. Числа демо синтетические; формат воспроизводится с реальными планами и фактическими финансовыми snapshots.

## Goals / Non-Goals

**Goals:**
- Отделить Telegram-представление от консоли, сохранив общие подтверждённые финансовые факты.
- Построить графики без IO к брокеру из worker и без Matplotlib в торговом потоке.
- Коррелировать корень/этапы по сделке, а не тикеру; переживать рестарт и повторный execution без дублей.
- Поддержать существующую семантику best-effort/at-most-once, bounded-очередь и изоляцию ошибок канала.

**Non-Goals:**
- Новые правила стопа, BE, целей, sizing, комиссии или исполнения; график визуализирует уже принятые решения.
- Обязательные discussion threads, polling/webhook callback handlers, команды управления сделкой из Telegram.
- Гарантия exactly-once или восстановление публикаций с неизвестным HTTP-исходом; повторная рассылка прежней истории при обновлении робота.
- Изменение пользовательских CSV/консольного оформления или превращение `tools/visualize_signals.py` в runtime renderer.

## Decisions

### 1. Собственное Telegram-представление

Разделить модули Telegram-шаблонов, построение семантической chart-scene, PNG-renderer, transport и delivery repository внутри `src/notifier/`. Консоль продолжает пользоваться нынешними текстовыми шаблонами. Цены/деньги форматируются на основе структурных чисел, но русское HTML-представление принадлежит Telegram. Пользовательские значения экранируются, ID остаются внутренними.

Единый словарь: `Вход`, `СТОП`, `ЦЕЛЬN`, `ПОКУПКА`/`ПРОДАЖА`, `До комиссии`, `Комиссии`, `Итог после комиссий`. Таймфрейм получает русскую подпись (`15м`, `1ч`), время — настроенное смещение и явный пояс. Подписи цены используют точность шага инструмента; «лот»/«контракт» берётся из метаданных количества. R/payoff остаются в финансовых данных и консольном тексте, в Telegram отображаются денежные значения с объяснением.

Альтернатива — расширить общий строковый formatter HTML-тегами — отклонена: это изменит консоль и не позволит независимо эволюционировать layout.

### 2. Самодостаточный снимок, а не чтение базы каналом

Ввести версионированный вложенный visual snapshot с глубоко неизменяемыми структурами и исполнимой JSON Schema. Предусмотреть:

| Блок | Содержимое |
|---|---|
| Корреляция | trade_id, устойчивый event key, ревизия состояния, порядок уведомления, as_of |
| Контекст | короткое имя, сторона, таймфрейм, точность цены, единица quantity/размер лота |
| Первоначальный план | вход/стоп, упорядоченные target_id → номер/цена/целая аллокация, трейлинговый остаток, версия и деньги плана |
| Текущее состояние | phase, исполненный вход, средняя, остаток, подтверждённый стоп/цели и их заполнение |
| История | execution key, время, роль OPEN/ADD/ЦЕЛЬN/СТОП/прочий выход, количество/цена; confirmed stop old/new/effective time и основание |
| Финансы | накопленные результат до/после комиссий, fees total, units, известность и источник расходов |
| Рынок | до 80 закрытых свечей нужного таймфрейма, границы окна и полнота; не DataFrame или изменяемые references |

Снимок строится у владельца фактов из уже доступных frames и одного согласованного чтения состояния после применения execution. Для принятого плана — в admission-пути, при исходах — через lifecycle observer и runtime wiring. Ограниченный chart-context cache пополняется существующим рыночным потоком по instrument/timeframe; не запрашивает историю для каждого уведомления. После рестарта при отсутствии окна отправляется текст до появления новых доступных данных.

Целые аллокации берутся из сохранённой экономики плана/подтверждённых целей, не рассчитываются шаблоном из share=0.5. Номер берётся из порядка первоначальных target_id и не сдвигается при нулевых/исполненных целях. Первоначальные уровни и актуальные rebased уровни отдельны.

Ограничить детальные исполнения и переносы в снимке последними 64 элементами каждого вида. Старые исполнения сворачиваются по роли/цели/стороне в явно подписанные агрегаты с периодом, количеством, средней ценой и числом операций; не считаются отдельными точными маркерами. Для ранней истории стопа сохраняются уровень на границе видимого окна и сводка пропущенных переносов. Неполный график подписывается; финансовые totals и состояние всегда полные из владельца фактов. Если лимит переносов достигнут внутри окна, не рисовать ложную непрерывную ступень на пропущенном участке.

Использовать только свечи, закрывшиеся не позже `as_of`; текущий незавершённый бар не выдаётся за полный OHLC. Маркер фактического исполнения может оказаться правее последней закрытой свечи. Разрывы сохраняются и обозначаются, смешение protection timeframe со strategy timeframe запрещено. Decimal остаётся точным до преобразования координат renderer.

Альтернативы — канал читает SQLite/брокера или в событие кладётся весь DataFrame — отклонены: первая ломает самодостаточность и получает более позднее состояние, вторая нарушает неизменяемость и раздувает очередь.

### 3. Единый подтверждённый lifecycle-путь

Сохранить reducer → подтверждение защиты/post-fill → snapshot → observer → bus; reducer не публикует. Добавить observer-факты для вступившего в силу MOVESTOP и подтверждённых отмен/отказов. Прочитать прежний confirmed_stop до его обновления, новый — после фиксации. Acceptance `next-bar` не выдаёт `stop_moved`; публикация происходит один раз на effective ACK. Основание «учёт прибыли и расходов всей сделки» переносится из принятого управленческого решения, а не угадывается по цене стопа.

Дефолт Telegram расширить до девяти типов из delta notification. `order_rejected` и `trade_cancelled` нужны для статуса ожидающего входа: при ненулевой открытой позиции они сообщают отказ/отмену операции, не ликвидацию позиции. Explicit event lists сохраняются. Старые события без visual snapshot остаются текстовыми и не получают выдуманный остаток или неизвестный номер цели.

Терминальное исполнение определяется `phase=CLOSED` и quantity_remaining=0. `target_hit`/`stop_hit`, закрывающие остаток, дают один итоговый график с причиной/номером цели вместо дополнительного краткого поста об этом же fill. `trade_closed` с ненулевым остатком — частичный выход. Если несколько уведомляющих типов описывают один execution, delivery key учитывает execution и роль, чтобы терминальный итог не продублировался.

Альтернатива — использовать legacy broker сообщения параллельно с observer — отклонена: у адресных сделок она создаёт дубли и лишает уведомление актуальных итогов SQLite.

### 4. Жизнь карточки и навигация

| Подтверждённый факт | Новый пост | Изменение корня |
|---|---|---|
| `signal` | фото плана + подпись, либо текст при отсутствии графика | создание корня |
| вход / добор | короткий текст с ценой, количеством и остатком | статус, средняя, остаток |
| нетерминальная цель/стоп/прочий выход | короткий текст с фактом и актуальными уровнями | остаток, краткая история, ссылка этапа |
| `stop_moved` | фото сопровождения + old/new подтверждённые уровни | действующий стоп, история, ссылка `СТОП` |
| терминальный выход | фото итога + общие деньги/причина | «Закрыта», остаток 0, итог и ссылка |
| отмена/отказ заявки | краткий русский факт при наличии контекста сделки | статус заявки без подмены состояния позиции |

Корень редактируется только по caption/text и reply_markup, исходный graph/photo сохраняется. Дочерний пост содержит URL «Открыть сделку» только при подтверждённом корне. Root-кнопки указывают на последний подтверждённый пост каждой цели, последний перенос стопа и итог; детали нескольких частичных исполнений сохраняются в связанной ленте. При множестве целей клавиатура переносится на строки, подпись оставляет краткую историю, полные детали идут продолжением.

`getChat` в worker получает метаданные один раз на экземпляр канала; public username даёт `t.me/<username>/<id>`, private channel/supergroup — `t.me/c/<id без -100>/<message>`. Для другого типа чата/неудачи metadata события отправляются без прямых ссылок. Наличие linked discussion не требуется. Ошибка root-edit не отменяет уже доставленный этап; не создаётся replacement root. Более поздний новый факт может снова обновить старый корень текущим snapshot.

Альтернативы — replies в канал/обязательная группа обсуждений или редактирование исходного графика каждым событием — отклонены: первые не подходят текущему каналу, последнее скрывает исходную идею.

### 5. Фоновый transport и долговечные receipts

`handle()` фильтрует и кладёт Event в очередь; работа с Matplotlib, HTTP и delivery SQLite — в одном worker. PNG рендерится в BytesIO, HTTP multipart отправляет его через существующий Cloudflare base. Transport обрабатывает `sendMessage`, `sendPhoto`, `editMessageCaption`, `editMessageText`, `getChat`; HTML/caption splitter сохраняет корректные теги и лимиты после parsing. Continuation получает тот же контекст и root-link, если он известен. Отсутствие/ошибка renderer до отправки выбирает sendMessage; HTTP failure не запускает вторую публикацию.

Отдельная версионированная база `<state_dir>/telegram_delivery.sqlite3` инжектируется фабрикой из выбранного runtime state_dir. Не добавлять Telegram-колонки в торговый журнал и не использовать его execution-outbox для сетевой доставки. Namespace включает chat_id, identity бота (без хранения токена; устойчивый fingerprint) и каталог запуска. Connection принадлежит worker. NotifyOnly также получает явный каталог состояния; исторический запуск, отключающий каналы, не создаёт delivery-базу.

Хранить корень (message_id, photo/text, последний snapshot/revision), этапы (key/роль/message_id), attempts (operation key/status) и последнюю обработанную последовательность. Перед каждым HTTP записать попытку; после подтверждения API — message_id и receipt. Между этими шагами не держать SQLite-транзакцию открытой на сеть. При crash/timeout незавершённая попытка остаётся `uncertain`: повтор после рестарта не выполняется, ссылка не создаётся. `ok=false`/429 фиксируются как неуспех без retries. `message is not modified` удовлетворяет конкретное редактирование.

Одно событие может иметь отдельные operation keys для основного поста, продолжений и root-edit. Повтор execution не повторяет операций, stale sequence не откатывает корень; другой partial-fill key при той же цене остаётся новым фактом. Schema/state initialization failure отключает Telegram-канал с понятным логом; консоль и торговля продолжают работу. Секреты и полный URL с токеном в логах/базе отсутствуют.

Альтернатива — JSON receipts как в одноразовом демо — отклонена из-за частичных записей и растущей карты событий. Durable retry-outbox не выбран: он меняет существующее at-most-once поведение и может повторить уже принятый Telegram-пост.

### 6. Renderer и поставка

Использовать Matplotlib Agg, объектный Figure API и закрытие ресурсов после каждого render. Начальный размер — 1440×960, тёмная тема и кириллический шрифт DejaVu Sans из поставки Matplotlib; никаких GUI-backends или шрифтов машины пользователя. Цвета и размещение соответствуют одобренному демо, с поправкой на переменную точность/число целей и направление сделки.

Сначала строить детерминированную semantic scene (candles, levels, markers, stop segments, labels), затем PNG. Это позволяет проверять факты отдельно от пиксельных различий библиотек. Matplotlib переносится в runtime dependencies; PyInstaller включает Agg, font data и нужные assets. Windows CI и локальный macOS smoke проверяют headless render с кириллицей. Выходные PNG не сохраняются постоянно в пользовательском data-dir.

Альтернатива — внешние chart services/browser screenshots — отклонена: они требуют дополнительных сетевых зависимостей и усложняют автономные бинарники.

## Risks / Trade-offs

- [Ответ Telegram потерян после принятия поста] → неопределённая попытка не повторяется; возможен неполный набор кнопок, но не автоматический дубль. Exactly-once не обещается.
- [Рендеринг замедляет worker] → ограниченные snapshots, один worker, лимит очереди и сохранение свежего состояния в каждом событии; локальный render failure даёт текст.
- [Длинная сделка/много fills/целей] → явно ограниченное окно, подписанные агрегаты старых исполнений, HTML-продолжения и перенос кнопок; полный финансовый итог не зависит от графика.
- [Снимок раньше закрытия бара или после рестарта без истории] → закрытые свечи только до as_of, отдельные маркеры и текстовый fallback; без look-ahead/дозагрузки из renderer.
- [Legacy/неизвестные/оценочные комиссии] → те же units и provenance, что у финансовых фактов; не подписывать оценку как брокерский факт.
- [Внешний список events не включает новые типы] → сохранить пользовательский выбор, документировать набор для полного визуального lifecycle; не добавлять скрытые подписки.
- [Различия PNG между ОС] → контрактные scene snapshots плюс небольшие визуальные smoke-проверки читаемости/кириллицы в фиксированном окружении.

## Migration Plan

1. Добавить optional visual context/schema и lifecycle observers с тестами подтверждённых фактов; старые события сохраняют текстовое поведение.
2. Подключить отдельные Telegram-шаблоны, renderer, transport и delivery-state через фабрику/runtime. Delivery schema создаётся отдельно и не мигрирует торговую базу.
3. Обновить дефолтный список событий и документацию; явно заданные `robot.toml` списки не переписываются.
4. Прогнать изолированные transport/lifecycle тесты и data-driven сцены на LONG/SHORT, нулевых/частичных/неизвестных данных; сравнить с одобренными постами. Проверить Agg/кириллицу в поставляемых сборках без выпуска версии в рамках change.
5. При откате вернуть прежний Telegram-код: побочная delivery-база игнорируется, торговая схема и финансовое состояние совместимы. При повторном включении новое delivery-state предотвращает повторную рассылку подтверждённых постов; прежние сообщения, созданные до change без receipts, автоматически не импортируются.
