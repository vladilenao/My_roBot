## Context

См. proposal.md — Why. Время бара в уведомлении печатается как `bar_time.strftime("%H:%M")` в `src/notifier/base.py:16`. `bar_time` — последний закрытый бар, tz-naive **UTC**. Пользователь в МСК (UTC+3) видит `06:15` вместо `09:15`. Нужно показывать время в его поясе, не меняя внутреннее UTC-значение.

Сейчас форматтер создаётся по умолчанию: `AbstractNotifier.__init__` (base.py:33-34) использует `DecisionFormatter()`, `get_notifier()` (notifier/__init__.py:12-17) не передаёт форматтер вообще.

## Goals / Non-Goals

**Goals:**
- Выводить блок времени `HH:MM` в локальном часовом поясе пользователя через сконфигурированное смещение от UTC.
- Сохранить внутреннее `decision.bar_time` в UTC (не влияет на индикаторы/решения/логику кэша).
- Нулевое смещение по умолчанию = сохранить текущее поведение (UTC).
- Разрешить тонкую настройку смещения в часах через конфиг.

**Non-Goals:**
- Не менять время в данных (`bar_time` решения), только отображение.
- Не вводить полноценную поддержку timezone-объектов/летнего времени (простое смещение в часах).
- Не трогать формат стратегий, сигналов, лейблов.

## Decisions

### D1: `DecisionFormatter` получает параметр смещения и сдвигает только отображение
`DecisionFormatter.__init__(self, tz_offset_hours: float = 0.0)`. В `format()` блок времени формируется как `(bar_time + timedelta(hours=self._tz_offset_hours)).strftime("%H:%M")`. Внутренний `decision.bar_time` не изменяется.

Это точечно и изолированно: не влияет ни на данные, ни на другие потребители `bar_time` (индикаторы, решения). Дефолт `0` сохраняет прежний вывод (UTC).

Альтернативы:
- Сдвигать сам `decision.bar_time` (в `trading_bot._analyze`) — меняет внутреннюю семантику, хрупко, отбрасываем.
- Хардкод `+3` в форматтере — не гибко, отбрасываем.
Выбор: параметр конструктора `DecisionFormatter` + дефолт 0.

### D2: Смещение приходит из конфига через `get_notifier()`
В `src/config.py` добавляется `BAR_TIME_TZ_OFFSET_HOURS = 0`. `get_notifier()` (notifier/__init__.py) читает его и собирает `formatter=DecisionFormatter(tz_offset_hours=BAR_TIME_TZ_OFFSET_HOURS)`, передавая в конструктор выбранного нотификатора (все наследники `AbstractNotifier` уже принимают `formatter`). Так одно место конфигурации покрывает оба канала (телеграм/консоль).

Альтернатива: деньги передавать из `run.py` в `get_notifier`. Но `get_notifier()` уже берёт `NOTIFIER` из `src.config` напрямую — логично и смещение брать там же, не расширяя сигнатуру `run.py`. Выбор: конфиг внутри `get_notifier()`.

### D3: Поддержка отрицательных и дробных смещений
Параметр — число часов (float), допускает отрицательные (запад от UTC) и дробные (например 5.5 = Индия) значения. Приложить родовой `timedelta(hours=offset)`. Тесты покрывают `0`, `+3`, отрицательное.

## Risks / Trade-offs

- [Смешение naive-времени и пояса] `bar_time` остаётся naive UTC; смещение чисто отобразительное, поэтому корректно для любого фиксированного пояса. → Митигация: задокументировано в дизайне; Timezone DST не поддерживается (осознанное non-goal).
- [Неправильный конфиг] Пользователь может задать неверное смещение. → Митигация: единственная явная константа, дефолт 0 безопасен.
- [Рассинхрон в существующих тестах форматтера] Тесты, ожидающие точный UTC-вывод, должны остаться валидными при дефолте 0. → Митигация: не меняем дефолтное поведение; новые тесты используют явное смещение.

## Migration Plan

Локализованное изменение: `DecisionFormatter` + `get_notifier()` + константа конфига. Rollback — откат коммита. Пользователь выставляет `BAR_TIME_TZ_OFFSET_HOURS=3` в `.env`/конфиге и перезапускает бота.
