## Context

Таймфрейм сделки уже хранится в плане: `TradePlan.timeframe` (`src/trade_management/models.py`) заполняется в `TradeManager._plan_entry` и сохраняется в `plan_json`. Требование «Таймаут незаполненного входа» уже опирается на него, «а не на текущий обрабатываемый таймфрейм». Для сопровождения такого правила нет.

Где сейчас вызывается профиль сопровождения:

| Место | Что передаётся | Проблема |
|---|---|---|
| `LiveAnalysis.step` (`src/bot/live_analysis.py`) | для каждого таймфрейма привязок инструмента и каждого свежего бара — `bot._manage(instrument, bindings, work_frame, context, tf)`, `work_frame = asof.tail(_required(binding)[tf])` | профиль считается для всех сделок инструмента на каждом таймфрейме; длина кадра — по требованию первой привязки этого таймфрейма |
| `TradingBot._process` (`src/bot/trading_bot.py`, исторический и виртуальный прогон) | таймфреймы `(привязки ∪ {protection_timeframe}) ∩ ready_tfs`, затем `_manage(...)` | плюс защитный `1m`: профиль считается по минутной истории |
| `TradeManager.manage` (`src/trade_management/manager.py`) | `frame`, `timeframe` | перебирает все открытые сделки инструмента, `timeframe` не сверяется с `plan.timeframe` |
| `TradeManager._manage_owned` | сигнал своей связки, кадр её таймфрейма | таймфрейм сигнала не сверяется с `plan.timeframe` (после смены конфигурации) |

Живой цикл берёт таймфреймы только из текущих привязок: `{a.timeframe for a in _strategies_for(instrument)}` в `LiveAnalysis.register_needs`, `_bootstrap` и `step`, `TradingBot._assigned_timeframes` (плюс защитный 1m). У `live_data_requirements` (`src/history/warmup.py`) есть параметр `saved_requirements` («удалённая входная привязка не удаляет этот ТФ»), но в `src/` эта функция не вызывается. Таймфрейм открытой сделки без привязок сейчас не загружается и не обходится.

Наблюдение 15.10.2026: сделка ED-12.26 на 1h (`ma_cloud`) получала перенос стопа на каждом 15m-баре из-за привязки `future-ed-flat` на 15m.

## Goals / Non-Goals

**Goals:**
- Одна точка правила: профиль сопровождения сделки считается только кадром таймфрейма её плана.
- Сделка на таймфрейме без привязок продолжает сопровождаться.
- Исторический прогон и live применяют одно правило.
- В аудите видно, по какому таймфрейму принято решение.

**Non-Goals:**
- Настраиваемый таймфрейм сопровождения, трейлинг по младшему таймфрейму после N·R.
- Изменение формул профилей и правил исполнения заявок.
- Пересмотр уже подтверждённых стопов.

## Decisions

### D1. Фильтр в `TradeManager.manage`

`manage(instrument, assignments, frame, context, *, timeframe, now)` рассчитывает профиль только для сделок, у которых `plan.timeframe == timeframe`. Остальные сделки инструмента в этом вызове пропускаются без расчёта, без трассы профиля и без записи `profile_state_json`. Общие действия, не связанные с баром (`_cancel_stale_entries`, `_close_expiring`, `drain_contract`), остаются в начале `manage` и выполняются, как сейчас.

`timeframe=None` больше не означает «любой»: без таймфрейма профиль не считается ни для одной сделки. Вызывающий код всегда передаёт таймфрейм кадра.

*Альтернатива:* фильтровать в `LiveAnalysis`/`TradingBot`. Отклонена: правило должно держаться в менеджере для обоих путей и для будущих вызывающих.

### D2. Неизвестный таймфрейм плана

Если `plan.timeframe` пуст или не входит в лестницу таймфреймов, сделка пропускается на любом кадре. Причина `management-timeframe-unknown` записывается в аудит трассой расчёта (не чаще одного раза на сделку за запуск) и в лог предупреждением. Действующий стоп у брокера не трогается. В текущих базах все сделки имеют таймфрейм. Ветка нужна для старых журналов.

### D3. Таймфреймы сопровождения в живом цикле

`LiveAnalysis.step` для инструмента обходит `таймфреймы привязок ∪ таймфреймы планов открытых сделок инструмента`. На таймфрейме без привязок сопровождение запускается на каждом новом закрытом баре текущего времени (`current` и `execution_complete`, как сейчас), без расчёта стратегий и без публикации решений. Ключ `managed = (instrument, tf, stamp)` сохраняется: один вызов `manage` на бар таймфрейма.

Потребности прогрева (`LiveAnalysis.register_needs`, `_bootstrap`) дополняются таймфреймами планов незавершённых сделок инструмента с прогревом их профилей: `TradeManager.management_obligations` читает журнал без регистрации у брокера, `obligation_requirements` из `src/history/warmup.py` даёт прогрев, `TradingBot._management_needs` оставляет только распознанные таймфреймы планов. Для таймфрейма без привязок `LiveAnalysis` создаёт состояние пары без обзора стратегий и без публикации паттернов. Так бары таймфрейма без привязок загружаются и публикуют состояние данных. Если пара по такому таймфрейму не готова, это видно в `market_data_status`, как для любой пары. Набор открытых сделок читается из журнала менеджера (`restore()`) в начале шага. Сделка, открытая во время работы, добавляет свой таймфрейм к следующему шагу.

### D4. Длина кадра сопровождения

Кадр для `manage` — не `tail` требований первой привязки таймфрейма, а `tail(max(требования привязок таймфрейма, management_requirement профилей открытых сделок этого таймфрейма))`. Так сделка `ma_cloud` получает свои 40 баров, даже если бар запустила привязка с меньшим прогревом.

### D5. Исторический прогон

`TradingBot._process` сохраняет вызов `manage` на защитном `protection_timeframe`: на нём выполняются действия, не связанные с баром (таймаут незаполненного входа, близкая экспирация, `drain_contract`), и их точность не должна падать до часа. Профиль на 1m не считается благодаря фильтру D1. К таймфреймам сопровождения добавляются таймфреймы планов незавершённых сделок инструмента (`TradingBot._management_needs`). В историческом прогоне сделки открываются привязками того же прогона, поэтому их таймфреймы уже загружены; набор загрузки `_assigned_timeframes` не расширяется, чтобы не запрашивать данные сверх подготовленных preflight.

### D6. Сигналы своей связки

`_manage_owned` и противоположный сигнал применяются к сделке, только если таймфрейм сигнала равен `plan.timeframe`. Иначе сигнал для открытой сделки игнорируется с трассой `management-timeframe-mismatch`. Новый вход по этому сигналу и так невозможен, пока у связки есть незавершённая сделка.

### D7. Аудит

Трасса `profile.<name>.manage` получает вход `timeframe` (единица `timeframe`) рядом с уже существующим `market.bar_id`.

### D8. Переход

Миграции нет. После выката открытые сделки сопровождаются по своему таймфрейму. Стоп, ранее подтянутый по младшему таймфрейму, не ослабляется: профили переносят стоп только при улучшении.

## Risks / Trade-offs

- **Нет баров таймфрейма плана** → сделка держится только под действующим стопом до восстановления данных. Это видно в состоянии данных пары, и это безопаснее, чем решения по чужому таймфрейму.
- **Стоп реагирует реже** (раз в час вместо раза в 15 минут) → сделка на 1h отдаёт больше прибыли при развороте. Это осознанная цена соответствия геометрии плана; размер позиции рассчитан под неё.
- **Тесты, сопровождающие сделку кадром другого таймфрейма**, ломаются и переписываются под правило.
