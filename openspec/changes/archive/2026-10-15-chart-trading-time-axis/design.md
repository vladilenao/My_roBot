## Context

График сделки строится в два этапа:

1. **Снимок.** `market_snapshot(frame, timeframe, as_of)` в `src/events/visual.py` берёт до 80 последних закрытых свечей кадра и кладёт их в `visual.market.candles`. Снимок собирается без чтения базы и без сети: его вызывают `TradeManager.remember_market` (из `TradingBot._analyze`) и `signal_snapshot` (из `TradingBot` при публикации плана). Флаг `gaps` сейчас истинен, если хоть одна пара соседних свечей не идёт подряд по сетке ТФ, — значит, почти всегда.
2. **Рендер.** `build_scene` и `render_png` в `src/notifier/telegram_chart.py` работают в фоновом воркере Telegram. Ось X — календарное время `dates.date2num`, ширина свечи — доля периода ТФ.

Слой рыночных данных уже знает причину каждого отсутствующего интервала. `MarketDataStore.interval_coverage` хранит состояние (`received`, `scheduled_closed`, `confirmed_no_trade`, `source_absent`, `pending`, `unresolved`) и доказательство (`applicable_trading_schedule:…`, `schedule_unavailable`, …). `MarketDataReconciler.interval_state` по этому же календарю решает, ждать ли свечу. `MarketDataStore.window_snapshot` пакетно читает свечи, состояния и проверки окна пары одним запросом.

Календарь в рабочей базе есть с 13.10.2026; интервалы раньше размечены `unresolved` с доказательством `schedule_unavailable` (у LKOH 664 интервала 15m и 146 интервалов 1h).

## Goals / Non-Goals

**Goals:**
- Неторговое время не занимает места на графике, торговое время читается как в терминале.
- Ночь, выходные и клиринг отличаются от настоящего пропуска данных по тому же календарю, по которому работает торговый контур.
- Интервал без расписания не выдаётся ни за пропуск данных, ни за полные данные.
- Подпись о неполноте появляется только тогда, когда неполнота есть.

**Non-Goals:**
- Менять загрузку, восстановление или разметку свечей; заполнять пропуски.
- Загружать расписание для прошлых дат (брокер не отдаёт `TradingSchedules` раньше текущей даты).
- Перерисовывать уже отправленные графики.
- Менять готовность данных, `coverage_for` и торговые решения.

## Decisions

### D1. Ось X — порядковый номер свечи в окне

Свеча `i` окна стоит в позиции `i`, ширина тела — прежние 0,58 периода, теперь 0,58 единицы. Разрыв любой длины между свечами `i` и `i+1` занимает ноль места; его граница — позиция `i + 0.5`.

Подписи оси — `FixedLocator` по выбранным номерам свечей и форматтер из их времени в поясе пользователя: `ЧЧ:ММ` внутри дня, `дд.мм\nЧЧ:ММ` на первой свече дня и на первой свече окна. Шаг подписей выбирается так, чтобы их было от 3 до 10, как у нынешнего `AutoDateLocator`. Подпись оси: `Время UTC+3 · неторговое время скрыто`.

**Альтернативы.** Сжатие только длинных разрывов до фиксированной ширины оставляет календарную ось и разные масштабы на одном графике — хуже читается и сложнее. Показ только текущей сессии теряет вчерашний контекст: утром на графике 1–3 свечи.

### D2. Отображение моментов на ось

Одна функция `position(t)` для исполнений, шагов стопа, `from_time` линии стопа, `as_of` и правой границы:

- `t` внутри свечи `i` (`open_i ≤ t < open_i + period`): `i − 0.5 + (t − open_i) / period`;
- `t` в разрыве после свечи `i`: `i + 0.5`;
- `t` позже закрытия последней свечи `n−1`: `n − 0.5 + (t − close_{n−1}) / period` — правое поле продолжает время, как сейчас;
- `t` раньше первой свечи: не используется, такие исполнения уже уходят в `before_window`, а шаг стопа — к левому краю.

Так маркер не может оказаться «внутри ночи», а порядок событий на оси сохраняется.

### D3. Виды разрывов и их источник

Разрыв — пара соседних свечей окна, между открытиями которых есть хотя бы один интервал сетки ТФ. Каждый отсутствующий интервал получает вид:

| Состояние интервала | Вид |
|---|---|
| `scheduled_closed` | `closed` |
| `confirmed_no_trade`, `source_absent` | `no_trade` |
| нет состояния, `unresolved`, `pending`; календарь на этот момент есть и биржа закрыта | `closed` |
| нет состояния, `unresolved`, `pending`; календарь на этот момент есть и биржа открыта | `missing` |
| нет состояния, `unresolved`, `pending`; календаря на этот момент нет | `schedule_unavailable` |

Вид разрыва — худший из видов его интервалов в порядке `missing` > `schedule_unavailable` > `no_trade` > `closed`. Так ночь, внутри которой не пришла утренняя свеча аукциона, честно станет `missing`.

Вычисляет вид `MarketDataCache.chart_breaks(instrument, timeframe, frame)`:

- одно чтение `MarketDataStore.window_snapshot` на диапазон окна вместо запроса на каждый интервал (у 1m выходные — около 3000 интервалов);
- календарь — только уже загруженный в память или сохранённые наблюдения `trading_schedule` через новый метод reconciler без RPC; путь `_calendar_for` с бюджетом запросов не используется, потому что он может обратиться к брокеру;
- без записи: в отличие от `interval_state`, классификация для графика не материализует `scheduled_closed` в хранилище;
- без reconciler (кэш без рыночного хранилища) все разрывы — `schedule_unavailable`.

**Почему в кэше, а не в снимке или renderer.** `visual.py` по своему контракту не делает IO, renderer работает в другом потоке и не имеет доступа к рыночному хранилищу. Кэш уже владеет UID пары, reconciler и `window_snapshot`, и та же логика стоит в `coverage_for`.

**Альтернатива** — переиспользовать `interval_state` по интервалу. Отвергнута: запрос на каждый интервал, побочная запись и возможный RPC за расписанием из потока уведомления.

### D4. Снимок: поле `market.breaks`

`market_snapshot(frame, timeframe, as_of, breaks=None)` принимает готовую классификацию (словарь «время открытия свечи перед разрывом → вид и число интервалов») и пишет её в снимок для тех разрывов, что попали в окно после отсечения будущих свечей и лимита 80:

```json
"breaks": [{"after": "2026-10-14T20:45:00", "before": "2026-10-15T03:45:00", "kind": "closed", "missing": 27}]
```

Разрыв, для которого классификация не передана, получает `schedule_unavailable`. `market.gaps` = есть разрыв `missing` или `schedule_unavailable`.

`visual_schema`: `breaks` — необязательный массив объектов с обязательными `after`, `before`, `kind` (enum из четырёх видов), `missing` (целое ≥ 1). `version` остаётся `1`: снимки без поля валидны, а новые поля только добавляются.

`TradingBot` передаёт классификатор в `remember_market` и `signal_snapshot`; `TradeManager.remember_market` и `signal_snapshot` пробрасывают его в `market_snapshot`. Классификация считается на торговом потоке там же, где уже есть кадр, и не задерживает тик сверх одного запроса SQLite.

### D5. Сцена и рендер

`build_scene` переносит `breaks` в сцену. Снимок без поля `breaks` (старый) получает в сцене разрывы, вычисленные по смежности свечей и сетке ТФ, вида `schedule_unavailable`.

`render_png`:

- `closed` и `no_trade` — без метки; смена дня между свечами в поясе пользователя — тонкая сплошная вертикаль цвета сетки в `i + 0.5`;
- `missing` — вертикальная полоса шириной 0,3 единицы с цветом `RED` и прозрачностью, над ней подпись `пропуск N` (N — число интервалов сетки);
- `schedule_unavailable` — пунктирная вертикаль цвета `#8794a7`; подпись `расписание недоступно` только у первой такой границы, чтобы не засорять 1m-графики.

### D6. Подпись под графиком

Вместо одной фразы «Ограниченное окно / неполная история» — составная из имеющихся частей через ` · `:

- `окно: N свечей с дд.мм ЧЧ:ММ` — если окно обрезано лимитом (`market.limited`);
- `пропуски данных: K` — число разрывов `missing`;
- `расписание недоступно: M разрывов` — число разрывов `schedule_unavailable`;
- `неполная история исполнений` — `history_limited` или `stop_history_limited`;
- ни одной части — прежняя фраза `План и подтверждённые исполнения`.

Хвост про исполнения раньше окна сохраняется. Те же пункты (`chart_notes` в `telegram_templates`) выводит строка «График: …» текста карточки; без пунктов строки нет, «пропуски не дорисованы» добавляется только при `market.gaps`.

Подписи оси: если начало дня ближе к первой свече, чем полшага подписей, дата ставится только у начала дня — иначе две подписи налезают друг на друга (найдено на графиках LKOH 15.10).

## Risks / Trade-offs

- **Сжатие скрывает длительность разрыва.** → Подписи оси показывают реальное время, день отмечен разделителем, пропуск — числом интервалов.
- **Ось по номерам непривычна для очень разреженных 1m-рядов** (неликвидные фьючерсы с частыми `no_trade`). → Это стандарт торговых терминалов; время на подписях остаётся настоящим.
- **Старые периоды без календаря** будут помечены «расписание недоступно» на итоговых графиках давних сделок и в историческом режиме. → Это честно и согласовано владельцем; число таких разрывов со временем уходит из окна.
- **Классификация на торговом потоке.** → Один пакетный запрос SQLite на окно ≤ 80 свечей, без сети; при ошибке чтения снимок получает разрывы `schedule_unavailable`, торговый шаг не падает.
- **Строгая JSON-схема у внешнего потребителя.** → Известных потребителей нет; схема в `docs/notification/visual-snapshot.json` обновляется вместе с кодом.

## Migration Plan

Миграций БД нет. Снимок проверяется схемой только при создании (`VisualSnapshot.__post_init__`), а очередь Telegram хранит готовый PNG в `telegram_files`. Поэтому старые снимки, если где-то рисуются повторно, рисуются по D5, а откат — простой возврат кода. При реализации нужно подтвердить, что ни один путь восстановления доставки не пересобирает снимок из сохранённого JSON (задача 1.2).
