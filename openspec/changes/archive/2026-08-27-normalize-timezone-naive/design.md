## Context

Сейчас в коде два «мира» времени, из-за чего падает приложение (см. proposal.md — Why). Планировщик и загрузчик создают aware-время (UTC-пояс), а кэш и выходные данные сводят к naive. Источники aware: `src/scheduler/timing.py` (`datetime.now(timezone.utc)`, `astimezone`, `tzinfo`), `src/data/loader.py` (`now()` для `start_date`/`end_date`), `src/instruments/selector.py` (`datetime.now(timezone.utc)`), `src/api/instruments.py` (`now()`). Падение: `src/data/loader.py:34` сравнивает naive `start_date` (из кэша) с aware `end_date`.

## Goals / Non-Goals

**Goals:**
- Единый канонический вид времени внутри робота — tz-naive (UTC подразумевается по соглашению сетки и цветов Tinkoff, но без `tzinfo`).
- На исходящей границе к Tinkoff API время **aware UTC** (клиент `t_tech` не принимает naive `from_`/`to` — подтверждено на практике).
- Инкрементальная дозагрузка свечей работает без падения типа времени.
- Планировщик по-прежнему выравнивает цикл по календарной сетке таймфрейма.

**Non-Goals:**
- НЕ переводим на время с произвольным пользовательским поясом (пояс не нужен, все операции в UTC).
- НЕ меняем семантику таймфреймов и границ свечей — только снимаем с них пояс.
- НЕ затрагиваем организации snapshot-тестов и стратегий.

## Decisions

### D1: Канонический мир — tz-naive UTC, на выходе к API — aware UTC
Все `datetime`/`pd.Timestamp` внутри робота — без `tzinfo` (naive). Календарная сетка таймфрейма и данные Tinkoff трактуются как UTC по соглашению, без хранения пояса. Исключение — исходящий край запросов к Tinkoff API (`get_all_candles`), где время должно быть aware UTC: naive-значение локализуется как UTC через `to_aware_utc` (см. D2), чтобы клиент принял запрос.
- *Альтернатива (отклонена):* держать всё aware — противоречит решению пользователя и текущему naive-контракту данных и кэша.
- *Альтернатива (отклонена):* свести к naive только в месте падения — оставило бы две «правды», риск рецидива.
- *Альтернатива (отклонена):* отдавать в API naive — Tinkoff-клиент не принимает naive `from_`/`to` (подтверждено фактической ошибкой «инструмент не найден»), поэтому на границу ставится `to_aware_utc`.

### D2: Единая точка нормализации
Вводятся два общих helper в `src/data/timeutil.py`:
- `to_naive(dt)`: `pd.Timestamp(dt)` и, если есть `tzinfo`, `tz_localize(None)` — единая нормализация наивного мира.
- `to_aware_utc(dt)`: naive трактуется как UTC и локализуется (`tz_localize("UTC")`), aware конвертируется в UTC (`tz_convert("UTC")`) — единая нормализация исходящей границы API.
- Планировщик: `clock` возвращает naive, убраны `tzinfo=timezone.utc`, `astimezone`, `tzinfo=` в `_month_span`.
- Loader: `start_date`/`end_date` приводятся к aware UTC до сравнения и до передачи в API — через `to_aware_utc` (наименьшее общее: обе границы aware-UTC, сравнение не падает, клиент принимает).
- Cache: границы готовности и отслеживание баров в naive; `_naive()` сохраняется как дешёвая защита (вход уже naive → no-op).
- Selector: `now`/`cutoff` — naive-UTC (`datetime.now(timezone.utc).replace(tzinfo=None)`); `expiration_date` из API сводится к naive через `to_naive` для сравнения.
- API (`find_working_instrument`): тестовый запрос свечей идёт с aware `from_`/`to` (как принимает клиент).

### D3: Снятие «лишней» нормализации
Поскольку источник времени становится naive, вспомогательная конвертация в кэше сводится к no-op. Она остаётся как защита от будущего рецидива aware, не требуя переписывания логики.

### D4: Нормализация внешних полей на границе
Внешние данные с поясом сводятся к naive на входе в робота. В частности, `expiration_date` фьючерсов из API (`fetch_active_futures`) нормализуется к naive до сравнения с локальным `now`/`cutoff` (которые тоже станут naive-UTC), чтобы не воспроизвести naive/aware-аварию в селекторе. Это расширяет naive-контракт на внешний API-поле, помимо внутренних данных.

## Risks / Trade-offs

- **R1: Tinkoff API принимает только aware `from_`/`to`** → подтверждено при применении: naive-передача приводит к «инструмент не найден» (см. итог apply). **Mitigation (реализована):** на исходящую границу API ставится `to_aware_utc` — время всегда aware-UTC; внутри робот остаётся naive. Задача-проверка 6.1 стала необязательной — поведение клиента выяснено на практике.
- **R2: Изменение поведения планировщика** (aware → naive) для вызывающего кода/тестов, ожидавших `tzinfo` → **Mitigation:** обновить unit-тесты `timing`/`cache`/`loader`, добавить проверки naive (без пояса).
- **R3: Ручной подсчёт месяца (`_month_span`)** зависит от `tzinfo` → **Mitigation:** заменить конструкторы with `tzinfo=UTC` на naive-конструкторы; проверить таймфрейм `1M` тестом.
- **Trade-off:** наивность экономит сложность поясов, но требует дисциплины «внутри naive, на исходящем крае к API aware» — любые внешние данные с поясом сводим на входе (`to_naive`), исходящие запросы поднимаем до aware (`to_aware_utc`).

## Migration Plan

- Починка падающей строки loader — минимальный первый шаг (независимо от остального).
- Последовательный перевод планировщика, кэша, selector, api на naive.
- Прогон `pytest` (unit + snapshot) после каждого шага; снапшот-стратегии не должны измениться.
- Проверка реального запроса к API: обнаружила, что клиент не принимает naive → добавлен `to_aware_utc` на границу (см. R1).

## Open Questions

- _Снято при применении._ Вопрос «принимает ли Tinkoff naive `from_`/`to`» (R1) решён на практике: не принимает. Итоговый контракт — naive внутри, aware-UTC на исходящем крае к API.
