# Дизайн: защитные закрытия докладываются исполнением

## Context

Мотивация — proposal.md (инцидент 22.09: стоп 98.94 пересечён, сделка осталась в
SQLite «открыта»). Ключевые ограничения текущей архитектуры, которые определяют
решение:

- Защита адресных сделок исполняется в брокере (`src/broker/journal_broker.py`):
  `_process_addressed_stop` (613–630) и целевой цикл (599–611) убавляют позицию в
  in-memory `PositionManager`, но не добавляют `ExecutionEvent` в `_addressed_events`
  (обновление списка — только в `_execute_scheduled`, строки 580/583). Поэтому
  `on_bar` (`run.py:224-233`) получает пустой поток, и `consume()`/редьюсер ничего
  не знают о закрытии.
- `ExecutionEvent` (порт) требует непустых `command_id`/`execution_id`/`reason`.
  Редьюсер применяет филл только при наличии строки `orders` по `command_id`
  (`_order()`, reducer.py:205), а `orders.command_id` — FK на `outbox`;
  `fills.order_id`/`command_id` — NOT NULL FK на `orders`. У защитного закрытия
  нет команды менеджера → «наивная» вставка филла невозможна без синтеза строк.
- Синтетические заявки/филлы должны помещаться в существующую схему, чтобы
  преимущества были бесплатными: экспортёр уже умеет рисовать событие «СТОП»/
  частичную цель (`_describe_event`, export.py:528-547), replayer и `_update_phase`
  понимают action_type `STOP`/`TARGET:<id>` (reducer.py:308-311, 281-298),
  `REASON_LABELS["protective"]="стоп"` уже в словаре русских причин.
- `restore()` (`manager.py:126-133`) регистрирует у брокера только план
  (`register_trade`, setdefault), но не живое состояние: после перезапуска у
  открытой сделки `confirmed_stop=None`, `revision=0`, позиция не восстановлена →
  защита мертва, а команды менеджера отклоняются как `stale-state-revision`.

## Goals / Non-Goals

**Goals:**
- Стоп и цели адресных сделок при срабатывании порождают `ExecutionEvent` с
  детерминированным идентификатором, объёмом, ценой и временем — в общем канале
  с подтверждёнными командами.
- Такое закрытие применяется редьюсером к устойчивому состоянию без изменения
  схемы БД: филл, заявка `STOP`/`TARGET:<id>`, фаза `CLOSED`/`REDUCING`, CSV, PnL.
- Защита открытой сделки переживает перезапуск: восстановление позиции, активного
  стопа и состояния целей; повторное выполнение входа не требуется.

**Non-Goals:**
- Реальная биржа/брокерский адаптер: работает только адресная свечная симуляция.
- Модель комиссий: защитные филлы получают `fee=0`, как уже существующие
  адресные филлы входа (`_command_fill`); переработка комиссий — отдельная тема.
- Вынос защиты из брокера в менеджер/профили: причинность стопа по OHLC остаётся
  микроструктурной ответственностью брокера.
- Не-адресные (legacy) пути: строки 478-497 `track_bar` не меняются.
- Резерв неисполненного остатка добора при стопе: снимается существующими
  правилами (отсутствие закрытия остатка у отменённой заявки, TTL/клиринг).

## Decisions

### D1 — Защитные закрытия = broker-initiated `ExecutionEvent` с детерминированным id
В `_process_addressed_stop` и целевом цикле после мутации in-memory состояния
формируется и добавляется в `_addressed_events` событие:
- command_id (он же execution_id base, order_id = command_id):
  - стоп: `f"{trade_id}:pv:stop:{<метка бара>}"`,
  - цель: `f"{trade_id}:pv:tp:{target_id}:{<метка бара>}"`
  execution_id = `f"{command_id}:fill"` (тот же паттерн, что `_command_fill`);
- status `FILL`, filled_quantity = закрытый объём, price = цена исполнения
  (стопа или гэп-open); reason = `protective` / `tp:<target_id>`;
  fee = `Decimal("0")`; timestamp = время бара.
- цена стопа: как раньше, `open` при гэпе хуже стопа, иначе стоп;
- метка бара — детерминированная строка времени (ISO без tz/по микро-секундам),
  гарантирующая «один защитный акт на бар» и идемпотентность при реплее.

Почему так: сохраняет контракт порта (непустые id) без правки общего dataclass
и конструкторов; идемпотентность определяется существующим дедупом редьюсера
(execution_id в `fills`/`events`) плюс дедупом брокера `(ticker, bar_now)`.

Альтернатива (отклонена): ослабить `ExecutionEvent` до nullable command_id —
портит общий контракт и все вызывающие, не решает FK в ре¸dюсер/схеме.

### D2 — Редьюсер принимает broker-initiated филлы через синтез durable-строк
В `ExecutionReducer.apply` перед применением: если `event.command_id` содержит
маркер `:pv:` — `INSERT OR IGNORE` синтетической пары строк:
- `outbox` (command_id, trade_id, payload, status=`SENT`, created/sent_at=now),
- `orders` (order_id=command_id, trade_id=command_id, action_type=`STOP` либо
  `TARGET:<target_id>`, status=`NEW`, quantity=filled_quantity, filled=0,
  requested_price=NULL, created/updated=now).
Дальше применяется существующий путь филла без изменений (обновление
`orders.filled_quantity`/status, вставка `fills` с FK, `_update_target`,
`_update_phase`, `_update_reservation` автоматически пропускается — строк
`reservations` по такому order нет). Идемпотентность: если execution_id уже в
`fills`/`events` — функция вернёт False до синтеза.

Схема (FK outbox/orders/fills) не меняется. `outbox.status='SENT'` не попадает в
`claim_outbox` (подтвердить фильтр в безопасности: статус заявки не выдиспатчится
повторно) — валидируется тестом.

Альтернатива (отклонена): сделать `fills.order_id`/`command_id` nullable —
миграция схемы и потеря инварианта «филл всегда относится к заявке».
Альтернатива (отклонена): заранее создавать заявки `STOP`/`TARGET` при
планировании сделки — дели целево распределяются по фактическим филлам входа /
остатку позиции, строки получились бы фантомными и мешали `dispatch`.

### D3 — Восстановление защиты при `restore()`
`manager.restore()` перед `register_trade` проверяет `broker.has_trade(trade_id)`.
Если сделка «новая» в брокере (свежий процесс после рестарта), после регистрации
вызывается `broker.resume_trade(recovered)`, который заполняет живое состояние:
- позицию в `PositionManager` (qty, avg из `state`, side, stop_price = активный стоп);
- `trade.entry_quantity = state.quantity`;
- `trade.confirmed_stop = state.confirmed_stop or plan.stop_price` (pending_stop
  НЕ активен и не применяется);
- `trade.target_filled` из `targets.filled_quantity` (источник — storage);
- `trade.revision = state.state_revision` (иначе команды менеджера ошибочно
  отклоняются `stale-state-revision`);
- `trade.opened_bar = None` (защита допускается со следующего бара).
Для уже известных брокеру сделок (тот же процесс, живое состояние) ничего не
перезаписывается — регистрация остаётся `setdefault`.

Почему так: restore() вызывается каждый тик, поэтому «всегда обновлять» нельзя —
это сбросило бы live-ревизию/`target_filled` и сломало бы оптимистичный контроль.

Альтернатива (отклонена): восстанавливать состояние только в `__init__` раннера
(одна точка) — restore() уже является источником truth и вызывается на каждой
привязке; разовая проверка дешевле и не зависит от порядка инициализации.

### D4 — Комиссия и уведомления
- `fee=0` для защитных филлов — консистентно с адресными филлами входа.
- Пользовательские события: в `_process_addressed_stop`/целевом цикле дополнительно
  `_emit("fill", now, trade_id, "Защитный стоп {qty} {display} по {price}")` /
  аналог для цели, чтобы консоль/Telegram показывали факт закрытия (legacy-канал
  `drain_events` уже подключён в `on_bar`).

## Risks / Trade-offs

- **Фантомные строки** `outbox`/`orders` с маркером `:pv:` видны в таблицах →
  метка в id и `status='SENT'` (не выдиспатчивается); unit-тест проверяет, что
  `claim_outbox` их не подхватывает.
- **Коллизия id с реальными командами** → command_id реальных команд — uuid hex;
  id вида `<trade_id>:pv:…` практично уникален, prefix документируется.
- **Восстановление `target_filled`** — при пропуске пережитог остатка целей после
  рестарта распределение `_target_remaining` разошлётся с фактом → источник
  `targets.filled_quantity` заводится в `load_trades` (поле в `RecoveredTrade`), и
  это покрывается тестом «после перезапуска цель дожимается с уже заполненным
  объёмом без задвоения».
- **Исполнение входа в том же баре, что и стоп** — существующая причинность
  (стоп приоритетнее, `opened_bar` guard) сохраняется без изменений; меняется
  только факт доклада события.
- **Частичный тейк по нескольким барам** → на каждый бар своя pv-заявка; суммы
  филлов по каждой строке ≤ её quantity (quantity=филл бара); `_update_target`
  следит за `planned_quantity`.

## Migration Plan

- Схема БД не меняется; миграции нет. Новые строки появляются только для новых
  защитных закрытий.
- Деплой: обновлённые `src/` — поведение вступает в силу на следующем такте;
  открытые на момент обновления сделки восстановят защиту через `restore()` при
  очередном вызове.
- Откат: вернуть прежние модули; уже созданные `:pv:`-строки инертны и не мешают.
