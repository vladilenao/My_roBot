## Context

Схема журнала (`src/trade_journal/schema.py`, `SCHEMA_VERSION = 6`) объявляет `target_id TEXT PRIMARY KEY` глобально, а все профили управления генерируют короткие ярлыки `tp-1`/`tp-2` для каждой сделки (мотивация — в `proposal.md`). Вся остальная работа с целями уже идёт в рамках сделки: запросы пишутся `WHERE trade_id = ? AND target_id = ?`, в таблице есть `UNIQUE (trade_id, target_index)`. Обращение к целям происходит из `manager.py`, `reducer.py`, `storage.py`, `journal_broker.py` и `export.py`; схема версионируется через `PRAGMA user_version` и мигрируется в `initialize_schema`.

## Goals / Non-Goals

**Goals:**
- Уникальность цели ограничить рамками сделки: составной первичный ключ `(trade_id, target_id)`.
- Бесшовный перенос существующих баз (v6 → v7) с живыми сделками.
- Человекочитаемое русское описание причины недопуска при ошибке целостности БД.

**Non-Goals:**
- Не меняем сами значения `tp-1`/`tp-2`, пользовательский формат журнала, ленты и уведомления.
- Не трогаем логику разбора защитных закрытий `:pv:`.
- Не устраняем другие возможные причины `admission-error` (обрабатываются как и раньше).

## Decisions

### Составной ключ вместо «глобализации» id цели
`PRIMARY KEY (trade_id, target_id)`. Значения id целей остаются короткими и одинаковыми для всех сделок.

Альтернатива — строить глобально уникальный id вида `{trade_id}:tp-1` — отклонена: (1) разбор command_id защитных закрытий (`reducer._pv_action`) делит строку по `:` (`payload.partition(":")[0]`), и встроенный в цель `trade_id` сломает выделение id; (2) длинные id протекли бы в события, аудит и уведомления.

### Пересоздание таблицы — единственный способ сменить PK
SQLite не позволяет менять первичный ключ существующей таблицы. План миграции `MIGRATE_V6_TO_V7_SQL`:
`CREATE TABLE targets_new` (та же структура, `PRIMARY KEY (trade_id, target_id)`, `UNIQUE (trade_id, target_index)`), `INSERT INTO targets_new SELECT … FROM targets`, `DROP TABLE targets`, `ALTER TABLE targets_new RENAME TO targets`.

Ключевые ограничения:
- **Порядок колонок сохраняется** (`target_id, trade_id, target_index, price, planned_quantity, filled_quantity, status`): вставка в `manager.py:186` позиционная (`INSERT INTO targets VALUES (?, …)`), и в этой же правке разумно перевести её на явный список колонок, чтобы снизить хрупкость.
- На `targets` нет входящих внешних ключей, поэтому `DROP TABLE`/`RENAME` безопасны при включённых `foreign_keys`; после миграции тянется штатный `PRAGMA foreign_key_check`.
- Дублирования `(trade_id, target_id)` быть не может: сейчас `target_id` уникален глобально, значит уникален и в каждой сделке.

### Версионирование и каскад миграций
`SCHEMA_VERSION = 7`; новый блок `MIGRATE_V6_TO_V7_SQL`; в `initialize_schema` ветки версий 1–5 дополняются цепочкой до v7, ветка `version == 6` выполняет только `MIGRATE_V6_TO_V7_SQL`. Миграция выполняется при старте до открытия торговой активности, в одной транзакции.

### Русское сообщение об ошибке БД
В except-ветке допуска (`manager.py:308`) специально обрабатывается `sqlite3.IntegrityError`: его текст заменяется на «Ошибка на уровне БД: нарушение целостности данных». Полный traceback уже пишется в лог (`log.warning(..., exc_info=True)`), поэтому пользователь видит короткое русское описание, а диагностика сохраняется. Остальные исключения проходят прежним путём (`rejection_message`). Итоговая строка в консоли: «Сделка не допущена: Ошибка при допуске сигнала: Ошибка на уровне БД: нарушение целостности данных».

Альтернатива — маппинг по подстроке `"UNIQUE constraint failed"` внутри `_REJECTION_MESSAGES` — отклонена: проверка типа исключения надёжнее строкового сравнения и не зависит от формулировок драйвера.

## Risks / Trade-offs

- **Смена версии схемы необратима для старой версии приложения** — старый бинарник не откроет базу v7 (`UnsupportedSchemaVersion`) → перед обновлением сделать резервную копию базы; откат — восстановление копии.
- **Позиционная вставка целей** зависит от порядка колонок → в этой же правке перевести `INSERT INTO targets` на явный список колонок (см. Decisions).
- **Пересоздание таблицы при активном соединении** → миграция выполняется однократно при старте в момент, когда торговли ещё нет; изменений конкурентных нет.
- **Итоговая фраза содержит два раза слово «Ошибка»** («Ошибка при допуске сигнала: Ошибка на уровне БД…») — принято, текст детали выбран пользователем; при желании позже можно сократить префикс.

## Migration Plan

1. Резервная копия текущей базы (рекомендация пользователю перед обновлением бинарника).
2. Сборка/обновление приложения; при старте `initialize_schema` поднимает БД 6 → 7 автоматически: пересоздаёт `targets` с составным ключом и переносит данные.
3. Проверка после старта: `PRAGMA user_version = 7`, существующая сделка и её цели на месте, второй вход по другой связке открывается.
4. Откат: остановить робота, вернуть резервную копию базы, запустить прежнюю версию.
