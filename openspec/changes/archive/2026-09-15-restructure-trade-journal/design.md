## Context

Сейчас журнал — один плоский CSV (`trade_journal.csv`, 23 колонки, `JournalEvent`/`JournalBroker` в `src/trade_journal/journal.py` и `src/broker/journal_broker.py`). Статусная лента: NEW → FILLED (FILLED перегружен). Времена в ленте — UTC (`format_dt` конвертирует в UTC), консоль показывает МСК. Контракт в ленте — сырой тикер (`signal.ticker`). Файл `trade_journal.csv` уже повреждён (склеенная строка). Историю позиции (вход/добор/тейки/выход) прочитать невозможно. Мотивация — в `proposal.md` (Why).

## Goals / Non-Goals

**Goals:**
- Двухфайловая модель: `journal.csv` (append-only лента, источник истины) + `positions.csv` (производные карточки, одна строка = жизнь позиции).
- Явные типы операций (ЗАЯВКА/ВХОД/ДОБОР/ТЕЙК/ВЫХОД/СНИМОК/ОТМЕНА) вместо перегруженного FILLED.
- Пользовательский формат: короткое имя контракта (`NG-10.26`), времена МСК, без системно-пустых колонок.
- Реплей состояния целиком из `journal.csv` (баланс, позиции, отложенные заявки).

**Non-Goals:**
- Миграция повреждённого легаси-`trade_journal.csv` (файл содержит только клиринговые снимки и битые строки — состояние не переносится, начинается с чистых файлов).
- Плавающий PnL открытых позиций в карточках (остаётся в консоли/событиях).
- Добор/частичный тейк «в исполнении»: движок пока генерирует вход/выход целиком; структура обязана их поддерживать, но генерация промежуточных операций — вне этой работы.
- Изменение форматов консоли/Telegram (кроме уже принятого правила NG-10.26 в пользовательском выводе).

## Decisions

**1. `journal.csv` — append-only источник истины; `positions.csv` — производная.**
Реплей и всё восстановление читают только `journal.csv`. Карточки в памяти поддерживаются инкрементально (на append-записи), а файл `positions.csv` переписывается снапшотом: фиксированная переоценка после каждой пачки записей (после `track_bar`/`run_clearing`) и на перезапуске при завершении работы. При старте карточки пересчитываются полным реплеем ленты для консистентности.
*Альтернативы:* одиночный событийный файл (проще, но теряется «вся жизнь позиции одной строкой»); одна широкая строка на позицию (отвергнута: переменное число доборов/тейков → взрыв или пустые колонки, хрупкий реплей).

**2. Тип операции — отдельная колонка; статус заявки не несёт семантики «вход/выход».**
Значения: ЗАЯВКА (принята, ещё не исполнена), ВХОД, ДОБОР, ТЕЙК, ВЫХОД, СНИМОК, ОТМЕНА (отменённая/истёкшая заявка). Исполнение заявки — отдельная запись: ЗАЯВКА → ВХОД/ДОБОР. Реплей связывает их по `order_id`. Неисполненная ЗАЯВКА восстанавливается как отложенный ордер.

**3. Колонки `journal.csv`** (все даты — МСК, контракт — короткое имя):
`id, операция, ts, order_id, position_id, контракт, сторона, qty, цена, стоп, pnl_часть, комиссия, депозит, риск_%, риск_руб, го, причина, заметки`
- открывающие (ЗАЯВКА/ВХОД/ДОБОР): стоп, риск_%, риск_руб, го;
- закрывающие (ТЕЙК/ВЫХОД): pnl_часть, комиссия;
- СНИМОК: депозит, qty=число открытых позиций, причина=clearing.

**4. Колонки `positions.csv`** (одна строка на позицию):
`position_id, контракт, направление, ts_входа, qty_итог, цена_средняя, стоп, ts_выхода, цена_выхода_средняя, pnl_итог, комиссия_итог, риск_%, риск_руб, го_макс, статус, причина_выхода`
Средняя цена агрегирует ВХОД+ДОБОР; PnL/комиссия суммируются по ТЕЙК+ВЫХОД; го_макс — максимум ГО за жизнь позиции.

**5. Времена в файлах — МСК.** Внутри движок продолжает считать в UTC: при чтении МСК-метка конвертируется в UTC (граница разбора), при записи — UTC→МСК. TTL/клиринг/дедлайны не меняются. Консоль уже МСК (`BAR_TIME_TZ_OFFSET_HOURS=3`), расхождения «19:22 vs 22:22» больше не возникает.
*Альтернатива:* хранить UTC, отображать МСК — файл оставался бы в UTC, а пользователь читает его как есть; отклонена (пользовательская поверхность — файл).

**6. Короткое имя контракта в пользовательских файлах.** Внутренние ключи (`_contracts`, сигналы, `position_id`) остаются на тикере. В брокерский слой добавляется отображение тикер → `short_name` (из `Instrument`/селектора), которое подставляется при записи строк журнала и в сообщениях событий.

**7. Обработка повреждённых записей.** Неизвестная/битая строка ленты: отбрасывается с предупреждением в лог, реплей продолжается (требование из спеки). Плюс на старте идёт проверка целостности заголовков: заголовок файла регенерируется как истина, поля располагаются по схеме.

## Risks / Trade-offs

- **Расхождение двух файлов** (карточки устарели относительно ленты) → карточки всегда производная, никогда не источник истины; перерасчёт по ленте гарантирует консистентность при старте и после каждой пачки записей.
- **Рост ленты** → полный реплей на старте деградирует. Признано приемлемым для имитационного исполнения (журналы небольшие); при необходимости позже — инкрементальный реплей (вне скоупа).
- **Смена часового пояса в файлах** → риск ошибок смещения в TTL/клиринге. Митигирован концентрацией преобразования в одном слое парсинга/форматирования (`format_dt`/`parse_dt`) и тестами на границы.
- **Потеря легаси-журнала** → сознательно: файл не подлежит миграции (битая строка, только снимки). Пользователю сохраняется резервная копия `trade_journal.csv` рядом.

## Migration Plan

1. На старте (в рамках этой change) при наличии `trade_journal.csv` — копия в `trade_journal.csv.bak` и создание чистых `journal.csv`/`positions.csv`.
2. Переключение `TradeJournal` на ленту+карточки; `journal_file` в конфиге по-прежнему задаёт ленту, `positions_file` — карточки (дефолт: вывод из `journal_file` + `_positions`).
3. Откат: возврат к однофайловой модели не предусмотрен; старый файл сохранён резервной копией. Точка безусловного перехода — мажорная версия (2.3.0).
