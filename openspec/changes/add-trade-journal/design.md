## Context

См. `proposal.md` — мотивация и границы. Текущее состояние, влияющее на проект:

- Исполнение — `NotifyOnlyExecutionPort` (`src/execution/port.py`), оркестратор вызывает `execute(decision, instrument, ...)` и не получает результата.
- Состояние позиции инкапсулировано внутри стратегии `ma_cloud_rsi_macd` (`_long_contracts`/`_short_contracts`), умирает вместе с процессом и не доступно риск-менеджменту.
- `Decision` (`src/strategies/contracts.py`) уже несёт поля-действия: `action` (`entry`/`scale_in`), `exit_reason`, `exit_contracts` — они станут источником торговых событий без изменения стратегий.
- `RiskManager` (`src/decision/risk.py`) — чистый трансформер (SL/TP по S/R); не знает о балансе и количестве.
- Ритм — «тик = закрытая свеча активного ТФ», все решения по закрытым барам; метаданные инструментов доступны через Tinkoff API (`src/api/instruments.py`, спецификации, `GetFuturesMargin`).
- Конфиг-паттерн: секции `robot.toml` с валидацией в `src/config_loader.py` и вшитыми дефолтами `default.toml`; файлы рядом с исполняемым через `app_dir()` (как `bot_debug.log`).

## Goals / Non-Goals

**Goals:**
- Дневник `trade_journal.csv` как единый источник истины: append-only события, восстановление состояния при рестарте.
- Портфель (баланс, позиции, средние цены, суммарный риск, ГО-ёмкость) и брокер (lifecycle ордеров, защитные стоп/TP, TTL, клиринг, FIFO+over-risk).
- Четыре тонких границы подмены на реальный API; имена модулей нейтральны (`broker`/`portfolio`/`trade_journal`).
- Сохранение текущего конвейера сигналов, фильтров и риск-менеджмента без их переписывания.

**Non-Goals:**
- Реальная торговля через брокера (только точки подмены).
- Модель проскальзывания/частичного исполнения на интрабаре (исполнение детерминировано по закрытым свечам).
- Учёт комиссий/лота/иных торговых издержек реальной биржи (поле `fee_rub` есть, значения 0).
- Перенос счётчиков контрактов из стратегии в портфель (стратегия продолжает владеть своей логикой событий, портфель — актуальным состоянием исполнения).

## Decisions

### D1: Три новых модуля с нейтральными именами
- `src/trade_journal/` — `TradeJournal`: чтение/дозапись CSV, парсинг строки, восстановление состояния (баланс, позиции, активные заявки), снимки.
- `src/portfolio/` — `Account` (баланс: депозит + реализованный + плавающий P/L) и `PositionManager` (позиции, средняя цена, агрегированный риск, проверка ГО).
- `src/broker/` — абстрактный `BrokerPort` с четырьмя границами (`load_state`, `place_order`, `track_bar`, `cancel_order`) и локальная реализация `JournalBroker` (исполнение лимиток по закрытым свечам, стоп/TP, TTL, клиринг, FIFO). Будущая `TinkoffBroker` реализует тот же порт.

Альтернатива «только один пакет `trade_journal` со всей логикой» отклонена: при переходе на реальный API пришлось бы выдирать ордерную логику из хранилища. `execution` остаётся интерфейсом оркестратора.

### D2: Append-only журнал, состояние пересобирается при старте
Файл — событийный лог: каждая запись — строка с `id` и `position_id`; статусы ордера идут последовательными строками одной позиции. При старте `TradeJournal.load()` прогоняет строки и восстанавливает `Account`/`PositionManager`/активные заявки. Это закрывает «виртуальную позицию, умирающую с процессом» и даёт аудит. Конкурентная дозапись не требуется (один процесс).

### D3: `Decision` → торговое событие без изменения стратегий
Брокер интерпретирует существующие поля: `action="entry"|"scale_in"` и BUY/SELL → лимитная заявка; `exit_reason` без `exit_contracts` → полный выход; `exit_reason` с `exit_contracts=N` → частичный выход `N`. Дополнительный гамма-тип действий вводить не будем — существующий контракт уже описывает события (см. `strategy-contract` spec), брокер лишь добавляет статусы ордеров.

### D4: Размер позиции считает риск-слой, а не брокер
`PositionSizer` (в `src/decision/`, рядом с `RiskManager`): `qty = floor(risk_budget / (|вход−стоп| × step_cost / step))`, `risk_budget = equity × MAX_RISK_PCT`. Вызывается перед размещением входной заявки; источник баланса — `Account.equity()`, метаданные контракта — кэш, заполненный из реального Tinkoff API (не имитация). Решение сохраняет `risk_pct`/`risk_rub` для дневника.

### D5: `ExecutionPort` расширяется результатом, брокер — через адаптер
`ExecutionPort.execute` возвращает результат исполнения (id заявки + статус или «нет сделки»). Новая реализация `BrokerExecutionPort` композирует `portfolio → broker → trade_journal`; `NotifyOnlyExecutionPort` остаётся как режим без торговли. `BrokerPort` (четыре границы) ниже `ExecutionPort` — замена на реальное API на уровне `JournalBroker → TinkoffBroker` не трогает ни оркестратор, ни портфель.

### D6: Защитные стоп/TP — независимые стоящие ордера
Привязываются к позиции из полей `stop_loss`/`take_profit` решения; срабатывают по закрытым свечам; на клиринге снимаются и перевыставляются по исходным уровням. Трейлинг и каскад частичных целей (TP1/TP2) — вне скоупа. На реальном брокере (Tinkoff нет нативного «bracket») два свободных ордера сохранят ту же семантику.

### D7: Клиринг и TTL в оркестраторе, не в стратегиях
`clearing_times` (МСК, `["14:05","19:00"]`) сравниваются каждый тик (базовое время — `bar_time` с поправкой `BAR_TIME_TZ_OFFSET_HOURS`); при пересечении — `broker.apply_clearing()` (снятие заявок, перевыставление защитных, снимок в журнал). TTL лимитки: обратный сигнал стратегии на инструмент → отмена; тайм-дедлайн по ТФ (≤30m → 1ч, 1h → 4ч, ≥4h → до клиринга).

### D8: FIFO и over-risk
Сигналы обрабатываются в порядке появления на тике; перед каждой лимиткой — проверка `PositionManager.risk_ok(новый_риск)` и ГО. Если лимит нарушается для неисполненной заявки — `cancel(reason="risk_cap")`. Если превышение обнаружено после исполнения (детерминированно на закрытых свечах возможно только при обработке пачки сигналов одного тика) — запись дневника `over_risk=true` и контр-заявка на закрытие лишнего объёма по цене закрытия; событие уходит в нотификатор.

### D9: Конфигурация `[trading]` и режим исполнения
Новые ключи: `initial_deposit`, `max_risk_pct`, `journal_file`, `clearing_times` (валидация в `config_loader`). В `default.toml` добавляется секция `[trading]` (депозит по умолчанию 100000, риск 2%, `trade_journal.csv`, 14:05/19:00). Торговый режим активен при наличии `[trading]` (в дефолтной сборке — всегда); её отсутствие в пользовательском `robot.toml` без дефолтов оставляет `NotifyOnly`. Выбор реализации — точка сборки `run.py`, как и требует `execution` spec.

### D10: Уведомления о событиях сделок
`DecisionFormatter` расширяется новыми шаблонами: «заявка подана (инструмент, цена, qty, position_id)», «вход исполнен», «отмена по причине», «превышение риска + контр-заявка», «клиринговый снимок (баланс, реализованный P/L)». Существующие тексты решений не меняются.

## Risks / Trade-offs

- [Определённое исполнение по закрытым барам расходится с реальной интрабаровой лимиткой] → Допущение зафиксировано в spec; при переходе на реальный API исполнение даёт брокер.
- [CSV как состояние: битые/обрезанные строки] → При старте нечитаемые строки пропускаются с пометкой в лог; обязательные колонки валидируются, отсутствие заголовка → создание нового файла.
- [Плавающий P/L по последней цене бара устаревает между тиками] → Для риск-лимитов приемлемо; база — закрытые свечи по дизайну ритма.
- [Контр-заявка при over-risk исполняется «идеально» без проскальзывания] → В локальной модели — честно по цене закрытия; флаг `over_risk` и причина сохраняются для статистики.
- [Расширение `ExecutionPort` (возврат результата) меняет существующие вызовы] → Только `trading_bot._analyze` и тесты; поведение NotifyOnly-ветки сохраняется обратносовместимым.
- [Средний риск-лимит не защищает от каскадного наращивания в одной сделке (доборы)] → Суммарный риск считается по всем открытым позициям, включая доборы; лимит общий.

## Migration Plan

1. Добавить `[trading]` в `default.toml` и валидацию в `src/config_loader.py` → константы в `src/config.py`. Старые конфиги без секции сохраняют поведение.
2. Слои снизу вверх: `trade_journal` (хранение, парсинг, восстановление) → `portfolio` (баланс/позиции) → `broker` (lifecycle, исполнение, клиринг, FIFO) → адаптер `BrokerExecutionPort` → оркестратор.
3. Расширить `DecisionFormatter`, подключить брокер в `run.py` и `trading_bot`.
4. Откат: секция `[trading]` убирается из конфига → активен `NotifyOnlyExecutionPort`, дневник остаётся на диске невостребованным; данные портфеля не разрушают старый контур сигналов.
