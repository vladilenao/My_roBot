## Why

Робот принимает торговые решения, но не знает о собственном счёте и позициях: исполнение ограничено уведомлениями, состояние позиции живёт внутри стратегии и исчезает вместе с процессом. Трейдеру нужен управляемый жизненный цикл сделок (вход, добор, частичная фиксация, выход), честная оценка риска (допустимый % от депозита, суммарный риск открытых позиций) и дневник, фиксирующий не только факты сделок, но и умозаключения — то, чего нет ни у брокера, ни на бирже.

## What Changes

- **Дневник сделок `trade_journal.csv`** как источник истины: append-only журнал событий рядом с исполняемым файлом, колонки фактов сделок (время заявки/входа, side, цены, количество, стоп, P/L, шаг цены, стоимость шага, ГО покупателя/продавца) и колонки reasoning (стратегия × профиль фильтра, заложенный риск, комментарий). При старте состояние восстанавливается из файла.
- **Слой «портфель»**: баланс (депозит + реализованный P/L + плавающий), открытые позиции со средними ценами, агрегированный риск открытых позиций, проверка ГО-емкости.
- **Брокерный слой с имитацией исполнения в ровно четырёх точках**: состояние счёта, подача заявки, отслеживание исполнения, отмена. Имена модулей нейтральны (`broker`/`portfolio`/`trade_journal`) и готовы к замене локальных реализаций на реальный Tinkoff API без изменения логики решений.
- **Управление риском на входе**: количество контрактов вычисляется из риск-бюджета (`qty = риск_руб / (|вход − стоп| / шаг × стоимость шага)`), суммарный риск открытых позиций не должен превышать `max_risk_pct %` от текущего баланса.
- **Жизненный цикл заявки**: `NEW → FILLED | CANCELLED | EXPIRED`; лимитки ждут достижения цены по закрытым свечам; защитные стоп/TP — стоящие ордера, которые снимаются и перевыставляются при клиринге; открытые позиции при клиринге **не закрываются**.
- **Клиринг по расписанию FORTS** (`14:05`, `19:00` МСК): отмена неисполненных заявок, перевыставление защитных ордеров, снимок баланса в дневник.
- **Обработка сигналов по очереди появления (FIFO)**; при превышении лимита риска неисполненная заявка отменяется; если превышение обнаружено после исполнения — в дневник пишется отметка «свершена с превышением риска» и выставляется контр-заявка на закрытие.
- **Конфигурация**: `initial_deposit`, `max_risk_pct`, `journal_file`, `clearing_times`, правило TTL заявки (до обратного сигнала любой стратегии либо по дедлайну таймфрейма: 1 час для ТФ ≤ 30m, 4 часа для 1h, до клиринга для ≥ 4h).
- **BREAKING**: конвейер исполнения меняется с «уведомить» на «брокер + дневник», расширяется `ExecutionPort`; уведомления продолжают сопровождать события.

## Capabilities

### New Capabilities
- `trade-journal`: файл-дневник сделок — формат и колонки, append-only события, восстановление состояния при старте, снимки при клиринге, группы событий по `position_id`, поле reasoning.
- `portfolio`: баланс и позиции — учёт депозита и P/L, средняя цена входа, агрегированный риск открытых позиций, проверка ГО-емкости, восстановление счёта из дневника.
- `broker`: исполнение и жизненный цикл ордеров — лимитные заявки, защитные стоп/TP, статусы ордеров, TTL и клиринг, FIFO-обработка и контр-заявка при over-risk, точки подмены на реальный API.

### Modified Capabilities
- `risk-management`: изменение REQUIREMENT — добавление расчёта количества контрактов из риск-бюджета и фиксации риск-снимка (risk_pct/risk_руб) в решении.
- `configuration`: изменение REQUIREMENT — добавление ключей торгового раздела (`initial_deposit`, `max_risk_pct`, `journal_file`, `clearing_times`, правило TTL заявок) и констант конфигурации.
- `execution`: изменение REQUIREMENT — расширение порта исполнения торговыми действиями (вход/добор/частичный/полный выход, защитные ордера) и возврат результата исполнения; добавление реализации на базе дневника.
- `orchestration`: изменение REQUIREMENT — встраивание слоёв portfolio/broker в тик: проверка риска до входа, отслеживание ордеров и защитных стопов на каждом тике, клиринг по расписанию.

## Impact

- **Новые модули**: `src/trade_journal/`, `src/portfolio/`, `src/broker/` (нейтральные имена, готовые к реальному API).
- **Изменяемые модули**: `src/execution/port.py` (расширение порта), `src/decision/risk.py` (размер позиции), `src/bot/trading_bot.py` (конвейер тика), `src/config.py` и `src/config_loader.py` (секция торговли), `run.py` (композиция зависимостей), `src/notifier/` (тексты событий сделок).
- **Реальное использование API сейчас**: метаданные контракта (шаг цены, стоимость шага, ГО покупателя/продавца) загружаются через Tinkoff Invest API (`GetFuturesMargin`, спецификации) — не имитируются.
- **Данные**: файл `trade_journal.csv` рядом с исполняемым файлом (рядом с `robot.toml`/`bot_debug.log`).
- **Тесты**: unit-тесты журнала/портфеля/брокера, снапшот-тесты конвейера сделок в `tests/`; требования окружения (pandas-совместимый CSV).
