## Purpose

Файл-дневник сделок — источник истины о портфеле робота: append-only журнал событий в формате CSV, фиксирующий факты сделок и умозаключения трейдера, восстанавливающий состояние при старте и делающий снимки баланса при клиринге.

## ADDED Requirements

### Requirement: Файл дневника и его расположение
Система ДОЛЖНА вести дневник сделок в файле `trade_journal.csv` в формате CSV. Файл ДОЛЖЕН создаваться рядом с конфигурационным файлом: для собранного исполняемого файла — в папке самого исполняемого файла, в режиме разработки — в корне проекта. Расположение и имя ДОЛЖНЫ переопределяться ключом `journal_file` торговой секции конфигурации. Файл ДОЛЖЕН открываться табличным редактором (допустима кодировка UTF-8-SIG).

#### Scenario: Создание рядом с исполняемым файлом
- **WHEN** робот впервые запускается из собранного бинарника без явного `journal_file`
- **THEN** `trade_journal.csv` создаётся рядом с исполняемым файлом

#### Scenario: Хранение колонок
- **WHEN** создаётся новый дневник
- **THEN** файл содержит строку заголовка: `id,position_id,Статус,Время заявки,Дата,Сторона,Время входа,Депозит,Риск %,Риск руб,Цена входа,Цена стопа,Кол-во,Цена выхода,Прибыль руб,Комиссия руб,Шаг цены,Стоимость шага,ГО (покупка),ГО (продажа),Контракт,Причина,Заметки` — человекочитаемые русские названия; технические поля (`id`, `position_id`) остаются латиницей

### Requirement: Append-only журнал событий
Каждое событие сделки (подача заявки, исполнение, частичный выход, добор, полный выход, отмена, контр-заявка) ДОЛЖНО записываться новой строкой с собственным уникальным `id`. События одной позиции ДОЛЖНЫ связываться общим `position_id` формата `{тикер}-{uuid}`. Запись дневника НЕ ДОЛЖНА перезаписывать предыдущие события.

#### Scenario: Исполнение дописывает строку
- **WHEN** заявка исполнилась
- **THEN** в файл дописывается новая строка с тем же `position_id` и статусом исполнения; предыдущие строки не изменяются

#### Scenario: Связывание добора с позицией
- **WHEN** стратегия даёт событие добора по открытой позиции
- **THEN** событие добора записывается с `position_id` исходной позиции

### Requirement: Восстановление состояния при старте
При запуске система ДОЛЖНА читать дневник и восстанавливать: текущий баланс, открытые позиции со средними ценами входа и количествами, а также признак «заявка свершена с превышением риска» по соответствующим отметкам. Открытые позicии, восстановленные из дневника, ДОЛЖНЫ продолжать отслеживаться (защитные ордера, выходы по событиям стратегии).

#### Scenario: Рестарт после входа
- **WHEN** робот перезапущен, а в дневнике есть открытая позиция
- **THEN** баланс включает исполненные этапы сделки, позиция восстанавливается и участвует в расчёте суммарного риска и проверке ГО

#### Scenario: Пустой дневник
- **WHEN** дневника нет или он пуст
- **THEN** портфель стартует с начального депозита из конфигурации, открытых позиций нет

### Requirement: Снимок живой прибыли и клиринговые записи
Система ДОЛЖНА включать в запись входа срез баланса (`deposit` — сумма на счёте на момент входа, включая плавающий P/L открытых позиций). При каждом клиринге система ДОЛЖНА дописывать строку-снимок: текущий баланс, реализованный P/L, число открытых позиций, значение `max_risk_pct`, применявшееся в сессии.

#### Scenario: Снимок при клиринге
- **WHEN** наступает время клиринга
- **THEN** в дневник дописывается снимок баланса и открытых позиций с пометкой события клиринга

### Requirement: Метаданные контракта в записи
Каждая запись сделки ДОЛЖНА содержать шаг цены, стоимость шага и ГО покупателя/продавца. Для фьючерсов значения ДОЛЖНЫ загружаться из реального Tinkoff Invest API (валютные и спецификационные данные контракта); для нефьючерсных инструментов колонки шага/стоимости шага заполняются применимыми значениями, ГО — пустые.

#### Scenario: Фьючерс с метаданными
- **WHEN** сделка по фьючерсному контракту
- **THEN** колонки `price_step`, `step_cost`, `go_buy`, `go_sell` заполнены значениями из API

#### Scenario: Акция
- **WHEN** сделка по акции
- **THEN** `go_buy` и `go_sell` пустые, шаг цены и стоимость шага указываются в применимых единицах

### Requirement: Reasoning по сделке
Каждая запись входной заявки ДОЛЖНА содержать причину входа: имя стратегии, профиль фильтрации (`reason`) и свободное текстовое обоснование (`notes`, например, значения индикаторов, соображения по сделке). Эти данные ДОЛЖНЫ записываться вместе с заявкой и сохраняться во всех последующих событиях позиции.

#### Scenario: Причина входа
- **WHEN** стратегия `ma_cloud_rsi_macd` с профилем `basic_levels` подаёт сигнал
- **THEN** запись заявки содержит `reason = "ma_cloud_rsi_macd [basic_levels]"` и текст `notes` из контекста решения
