## Purpose

Слой исполнения сделок и жизненный цикл ордеров: лимитные заявки, защитные стоп/тейк-ордера, статусы ордеров, таймауты и клиринг, последовательная (FIFO) обработка сигналов с лимитом риска. Четыре точки операций со счётом спроектированы как абстрактные границы для замены локальной (журнальной) реализации на реальный брокерский API.

## ADDED Requirements

### Requirement: Торговые действия и подача лимитной заявки
Система ДОЛЖНА принимать торговые действия: вход (`entry`), добор (`scale_in`), частичный выход (`partial`), полный выход (`full`). Вход и добор ДОЛЖНЫ превращаться в лимитную заявку по цене решения сигнального бара; частичный и полный выходы исполняются по рыночной цене закрытой свечи или по защитным ордерам. Каждая заявка получает уникальный идентификатор и записывается в дневник со статусом исполнения.

#### Scenario: Сигнал входа порождает заявку
- **WHEN** стратегия возвращает решение `action="entry"`, прошедшее фильтр и риск-менеджмент
- **THEN** создаётся лимитная заявка по цене сигнального бара со статусом «подана» и количеством из риск-менеджмента

#### Scenario: Добор по открытой позиции
- **WHEN** стратегия возвращает решение `action="scale_in"` по открытой позиции
- **THEN** создаётся новая лимитная заявка, привязанная к `position_id` позиции

### Requirement: Статусы и переходы ордера
Ордер ДОЛЖЕН находиться в одном из статусов: `NEW` (подана), `FILLED` (исполнена), `CANCELLED` (отменена), `EXPIRED` (не исполнена за время жизни). Переходы фиксируются записями дневника: `NEW → FILLED`, `NEW → CANCELLED`, `NEW → EXPIRED`.

#### Scenario: Заявка исполнена
- **WHEN** цена достигла лимитной цены заявки
- **THEN** статус ордера становится `FILLED`, фиксируется время исполнения

#### Scenario: Заявка отменена
- **WHEN** заявка снята (TTL, клиринг или лимит риска)
- **THEN** статус ордера становится `CANCELLED` и причина отмены записывается в дневник

### Requirement: Исполнение лимитной заявки по закрытым свечам
Исполнение лимитных ордеров ДОЛЖНО проверяться на закрытых свечах таймфрейма инструмента: BUY-заявка исполняется, когда минимум бара стал не выше лимитной цены (вход по лимитной цене); SELL-заявка — когда максимум бара стал не ниже лимитной цены (выход по лимитной цене). Исполнение НЕ ДОЛЖНО происходить по незакрытым свечам.

#### Scenario: BUY-заявка исполнилась
- **WHEN** на закрытой свече `low ≤ цена_лимитки`
- **THEN** заявка исполнена по лимитной цене

#### Scenario: Цена не дошла до лимитки
- **WHEN** на закрытых свечах цена ни разу не достигла лимитной цены
- **THEN** заявка остаётся в статусе `NEW` до TTL/клиринга

### Requirement: Защитные стоп и тейк как стоящие ордера
К каждой исполненной позиции ДОЛЖНЫ привязываться защитные ордера: стоп-лосс и тейк-профит из риск-менеджмента. Они ДОЛЖНЫ срабатывать по закрытым свечам (стоп — при пробое цены, тейк — при достижении целевой цены) и считаться стоящими ордерами: при клиринге снимаются и перевыставляются.

#### Scenario: Срабатывание стопа
- **WHEN** на закрытой свече BUY-позиции цена опустилась до уровня стоп-лосс
- **THEN** стоп-событие закрывает позицию (или её этап), фиксируется P/L

#### Scenario: Перевыставление защитных ордеров после клиринга
- **WHEN** защитный ордер снят клирингом
- **THEN** после клиринга стоп/тейк выставляются заново по исходным уровням позиции

### Requirement: Время жизни заявки (TTL)
Неисполненная лимитная заявка ДОЛЖНА быть снята, когда наступает любое из условий: обратный сигнал любой активной стратегии по инструменту; срок жизни по таймфрейму — 1 час для ТФ не длиннее 30 минут, 4 часа для часового ТФ, до ближайшего клиринга для ТФ от 4 часов. Отмена с причиной «TTL» фиксируется в дневнике.

#### Scenario: Обратный сигнал
- **WHEN** подана BUY-заявка, а затем стратегия дала SELL-сигнал
- **THEN** BUY-заявка снимается с причиной «обратный сигнал»

#### Scenario: Тайм-дедлайн
- **WHEN** заявка на ТФ `15m` не исполнилась в течение 1 часа
- **THEN** заявка снимается с причиной «TTL»

### Requirement: Клиринг по расписанию FORTS
При наступлении времени клиринга из конфигурации (`clearing_times`, по умолчанию `14:05`, `19:00` МСК) система ДОЛЖНА: снять все неисполненные заявки; снять и перевыставить защитные стоп/тейк открытых позиций; НЕ закрывать открытые позиции; дописать в дневник снимок баланса.

#### Scenario: Неисполненная заявка на момент клиринга
- **WHEN** наступает время клиринга, есть неисполненная заявка
- **THEN** заявка снимается, защитные ордера перевыставляются, позиции остаются открытыми, пишется снимок

### Requirement: Последовательная обработка сигналов с лимитом риска
Сигналы на вход/добор ДОЛЖНЫ обрабатываться в порядке появления (FIFO). Перед размещением заявки система ДОЛЖНА проверить, что суммарный риск открытых позиций вместе с новой заявкой не превышает лимита; при превышении заявка НЕ размещается или снимается, если ещё не исполнена.

#### Scenario: Очередные сигналы в лимите
- **WHEN** несколько сигналов поступили на одном тике, но суммарный риск всех заявок в пределах лимита
- **THEN** все заявки размещаются в порядке появления

#### Scenario: Неисполненная заявка превышает лимит риска
- **WHEN** предыдущая заявка исполнилась, а следующая по FIFO увеличила бы суммарный риск сверх лимита и ещё не исполнена
- **THEN** следующая заявка снимается с причиной «превышение лимита риска»

### Requirement: Четыре границы подмены на реальный брокерский API
Операции со счётом ДОЛЖНЫ быть изолированы за абстрактными границами: загрузка состояния счёта, размещение заявки, отслеживание исполнения, отмена заявки. Локальная реализация выполняет их через дневник и рыночные данные; альтернативная реализация ДОЛЖНА выполнять те же операции через реальный брокерский API, не затрагивая конвейер решений.

#### Scenario: Подмена реализации исполнения
- **WHEN** локальная реализация брокера заменяется на реализацию реального API
- **THEN** конвейер фильтров, риск-менеджмента и дневника не изменяется; те же четыре операции вызываются в новой реализации
