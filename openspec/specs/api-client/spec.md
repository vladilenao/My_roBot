# API-клиент и обработка ошибок API

## Purpose

Обеспечивает доступ к Invest API Т-Банка: аутентифицированная фабрика клиента, утилита поиска инструментов (тикер → UID), и механизм повторных вызовов при ошибках лимита запросов (RESOURCE_EXHAUSTED).

## Requirements

### Requirement: Аутентифицированный клиент (прямой вызов)
- Система ДОЛЖНА предоставлять функцию `get_client()`, возвращающую аутентифицированный `t_tech.invest.Client` с использованием `TINKOFF_TOKEN`.
- Клиент НЕ является контекстным менеджером; ответственность за закрытие лежит на вызывающем коде.

#### Scenario: Успешное создание клиента
- **WHEN** вызывается `get_client()` при наличии валидного `TINKOFF_TOKEN`
- **THEN** возвращается экземпляр `t_tech.invest.Client`

### Requirement: Аутентифицированный клиент (контекстный менеджер)
- Система ДОЛЖНА предоставлять функцию `client_context(token=None)`, возвращающую `Client` как контекстный менеджер (`with`).
- Если `token` не передан, используется `TINKOFF_TOKEN` из конфигурации.

#### Scenario: Контекстный менеджер используется через with
- **WHEN** `with client_context() as client:` выполняется в вызывающем коде
- **THEN** клиент создаётся и автоматически закрывается при выходе из блока `with`

#### Scenario: Кастомный токен
- **WHEN** `client_context(token="custom-token")` вызывается с явным токеном
- **THEN** клиент создаётся с указанным токеном, а не с `TINKOFF_TOKEN`

### Requirement: Поиск инструмента по тикеру
- Система ДОЛЖНА предоставлять функцию `find_working_instrument(client, ticker, instrument_type="share")`, возвращающую UID найденного инструмента.
- Все вызовы API внутри функции обёрнуты в `api_call_with_retry`.

#### Scenario: Найден валидный инструмент со свечными данными
- **WHEN** тикер существует и имеет хотя бы одну дневную свечу за последние 30 дней
- **THEN** возвращается UID инструмента

#### Scenario: Тикер существует, но нет свечных данных
- **WHEN** тестовая выборка свечей возвращает пустой список
- **THEN** система продолжает поиск; если данных нет ни у одного — выбрасывается `ValueError`

#### Scenario: Тикер не найден
- **WHEN** тикер не соответствует ни одному инструменту
- **THEN** выбрасывается `ValueError` с сообщением "не найден или недоступен"

### Requirement: Поддержка типов инструментов
- Параметр `instrument_type` ДОЛЖЕН принимать: `"share"`, `"future"`, `"etf"`, `"currency"`.

#### Scenario: Неподдерживаемый тип
- **WHEN** `instrument_type` не входит в поддерживаемые значения
- **THEN** выбрасывается `ValueError` "Неподдерживаемый тип инструмента"

### Requirement: Вызов соответствующего эндпоинта API
- Для каждого типа система ДОЛЖНА вызывать соответствующий метод: `client.instruments.shares()`, `client.instruments.futures()`, `client.instruments.etfs()`, `client.instruments.currencies()`.

#### Scenario: Поиск среди фьючерсов
- **WHEN** `instrument_type` равен `"future"`
- **THEN** вызывается `client.instruments.futures()`

#### Scenario: Поиск среди акций
- **WHEN** `instrument_type` равен `"share"`
- **THEN** вызывается `client.instruments.shares()`

### Requirement: Валидация свечными данными
- При нахождении совпадения по тикеру система ДОЛЖНА валидировать инструмент попыткой получить свечи за 30 дней.

#### Scenario: Валидация проходит успешно
- **WHEN** тестовая выборка возвращает непустой список
- **THEN** UID возвращается вызывающему коду

#### Scenario: Исключение при запросе тестовых свечей
- **WHEN** при запросе тестовых свечей перехватывается исключение
- **THEN** система переходит к следующему подходящему инструменту

### Requirement: Механизм повторных вызовов при rate-limit
- Система ДОЛЖНА предоставлять функцию `api_call_with_retry(fn, *args, max_retries=3, base_delay=10, max_delay=60, **kwargs)`.

#### Scenario: Успешный вызов с первой попытки
- **WHEN** API возвращает результат без ошибки
- **THEN** результат возвращается без повторных попыток

#### Scenario: Повтор при RESOURCE_EXHAUSTED
- **WHEN** API выбрасывает исключение с `RESOURCE_EXHAUSTED` в тексте
- **THEN** функция повторяет вызов с экспоненциальной задержкой (10 → 20 → 40 сек), максимум `max_retries` попыток

#### Scenario: Лимит попыток исчерпан
- **WHEN** количество повторов достигло `max_retries` и ошибка повторяется
- **THEN** последнее исключение пробрасывается вызывающему коду

#### Scenario: Не-rate-limit ошибка
- **WHEN** исключение НЕ содержит `RESOURCE_EXHAUSTED`
- **THEN** исключение пробрасывается немедленно без повторов

#### Scenario: Чтение времени сброса лимита
- **WHEN** в тексте исключения присутствует `ratelimit_reset=N`
- **THEN** задержка перед повтором ограничивается значением `N` секунд

### Requirement: Декоратор with_retry
- Система ДОЛЖНА предоставлять декоратор `@with_retry`, оборачивающий функцию в `api_call_with_retry`.

#### Scenario: Декоратор без аргументов
- **WHEN** `@with_retry` применяется без скобок
- **THEN** функция оборачивается с параметрами по умолчанию

#### Scenario: Декоратор с аргументами
- **WHEN** `@with_retry(max_retries=5)` применяется с параметрами
- **THEN** функция оборачивается с указанными параметрами
