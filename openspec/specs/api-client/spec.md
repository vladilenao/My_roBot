# API-клиент и обработка ошибок API

## Purpose

Обеспечивает доступ к Invest API Т-Банка: аутентифицированная фабрика клиента, утилита поиска инструментов (тикер → UID), и механизм повторных вызовов при ошибках лимита запросов (RESOURCE_EXHAUSTED).

## Requirements

### Requirement: Аутентифицированный клиент (прямой вызов)
- Система ДОЛЖНА предоставлять функцию `get_client()`, возвращающую аутентифицированный `t_tech.invest.Client` с использованием `TINKOFF_TOKEN`.
- Клиент НЕ является контекстным менеджером; ответственность за закрытие лежит на вызывающем коде.

#### Scenario: Успешное создание клиента
- **WHEN** вызывается `get_client()` при наличии валидного `TINKOFF_TOKEN`
- **THEN** возвращается экземпляр `t_tech.invest.Client`

### Requirement: Аутентифицированный клиент (контекстный менеджер)
- Система ДОЛЖНА предоставлять функцию `client_context(token=None)`, возвращающую `Client` как контекстный менеджер (`with`).
- Если `token` не передан, используется `TINKOFF_TOKEN` из конфигурации.
- Способ получения клиента ДОЛЖЕН определяться режимом прогона: в боевом режиме возвращается аутентифицированный клиент T-Банка, в историческом режиме — клиент исторического источника. Набор методов, используемых контуром робота, ДОЛЖЕН быть одинаковым в обоих режимах; остальному коду ДОЛЖЕН быть доступен единый клиент выбранного источника.

#### Scenario: Контекстный менеджер используется через with
- **WHEN** `with client_context() as client:` выполняется в вызывающем коде
- **THEN** клиент создаётся и автоматически закрывается при выходе из блока `with`

#### Scenario: Кастомный токен
- **WHEN** `client_context(token="custom-token")` вызывается с явным токеном
- **THEN** клиент создаётся с указанным токеном, а не с `TINKOFF_TOKEN`

#### Scenario: Исторический режим
- **WHEN** прогон выполняется в историческом режиме
- **THEN** `client_context()` возвращает клиент исторического источника с тем же набором методов, что и в боевом режиме

### Requirement: Поиск инструмента по тикеру
- Система ДОЛЖНА предоставлять функцию `find_working_instrument(client, ticker, instrument_type="share")`, возвращающую UID найденного инструмента.
- Все вызовы API внутри функции обёрнуты в `api_call_with_retry`.

#### Scenario: Найден валидный инструмент со свечными данными
- **WHEN** тикер существует и имеет хотя бы одну дневную свечу за последние 30 дней
- **THEN** возвращается UID инструмента

#### Scenario: Тикер существует, но нет свечных данных
- **WHEN** тестовая выборка свечей возвращает пустой список
- **THEN** система продолжает поиск; если данных нет ни у одного — выбрасывается `ValueError`

#### Scenario: Тикер не найден
- **WHEN** тикер не соответствует ни одному инструменту
- **THEN** выбрасывается `ValueError` с сообщением "не найден или недоступен"

### Requirement: Поддержка типов инструментов
- Параметр `instrument_type` ДОЛЖЕН принимать: `"share"`, `"future"`, `"etf"`, `"currency"`.

#### Scenario: Неподдерживаемый тип
- **WHEN** `instrument_type` не входит в поддерживаемые значения
- **THEN** выбрасывается `ValueError` "Неподдерживаемый тип инструмента"

### Requirement: Вызов соответствующего эндпоинта API
- Для каждого типа система ДОЛЖНА вызывать соответствующий метод: `client.instruments.shares()`, `client.instruments.futures()`, `client.instruments.etfs()`, `client.instruments.currencies()`.

#### Scenario: Поиск среди фьючерсов
- **WHEN** `instrument_type` равен `"future"`
- **THEN** вызывается `client.instruments.futures()`

#### Scenario: Поиск среди акций
- **WHEN** `instrument_type` равен `"share"`
- **THEN** вызывается `client.instruments.shares()`

### Requirement: Валидация свечными данными
- При нахождении совпадения по тикеру система ДОЛЖНА валидировать инструмент попыткой получить свечи за 30 дней.
- Окно валидации ДОЛЖНО отсчитываться от текущего рыночного времени прогона, а не от системных часов.

#### Scenario: Валидация проходит успешно
- **WHEN** тестовая выборка возвращает непустой список
- **THEN** UID возвращается вызывающему коду

#### Scenario: Исключение при запросе тестовых свечей
- **WHEN** при запросе тестовых свечей перехватывается исключение
- **THEN** система переходит к следующему подходящему инструменту

#### Scenario: Окно валидации от рыночного времени
- **WHEN** выполняется исторический прогон с рыночным временем `2023-05-10 12:00`
- **THEN** проверочная выборка берётся за 30 дней до `2023-05-10 12:00`, а не до текущей системной даты

### Requirement: Механизм повторных вызовов при rate-limit
- Система ДОЛЖНА предоставлять функцию `api_call_with_retry(fn, *args, max_retries=3, base_delay=10, max_delay=60, **kwargs)`.

#### Scenario: Успешный вызов с первой попытки
- **WHEN** API возвращает результат без ошибки
- **THEN** результат возвращается без повторных попыток

#### Scenario: Повтор при RESOURCE_EXHAUSTED
- **WHEN** API выбрасывает исключение с `RESOURCE_EXHAUSTED` в тексте
- **THEN** функция повторяет вызов с экспоненциальной задержкой (10 → 20 → 40 сек), максимум `max_retries` попыток

#### Scenario: Лимит попыток исчерпан
- **WHEN** количество повторов достигло `max_retries` и ошибка повторяется
- **THEN** последнее исключение пробрасывается вызывающему коду

#### Scenario: Не-rate-limit ошибка
- **WHEN** исключение НЕ содержит `RESOURCE_EXHAUSTED`
- **THEN** исключение пробрасывается немедленно без повторов

#### Scenario: Чтение времени сброса лимита
- **WHEN** в тексте исключения присутствует `ratelimit_reset=N`
- **THEN** задержка перед повтором ограничивается значением `N` секунд

### Requirement: Декоратор with_retry
- Система ДОЛЖНА предоставлять декоратор `@with_retry`, оборачивающий функцию в `api_call_with_retry`.

#### Scenario: Декоратор без аргументов
- **WHEN** `@with_retry` применяется без скобок
- **THEN** функция оборачивается с параметрами по умолчанию

#### Scenario: Декоратор с аргументами
- **WHEN** `@with_retry(max_retries=5)` применяется с параметрами
- **THEN** функция оборачивается с указанными параметрами

### Requirement: Загрузка метаданных акций
Нормативный уровень: MUST.
Система ДОЛЖНА загружать торговые метаданные акций отдельным вызовом каталога акций `client.instruments.shares()` с фильтрацией по выбранным тикерам. Для каждой акции метаданные ДОЛЖНЫ содержать: `price_step` — минимальный шаг цены из `min_price_increment`; `step_cost` — `price_step × lot`, то есть цену одного лота в рублях; `go_buy` и `go_sell` — 0, поскольку у акции нет гарантийного обеспечения; `expiration_date` — `None`, поскольку акция не экспирируется. Отношение `step_cost / price_step` ДОЛЖНО равняться размеру лота в акциях и ДОЛЖНО использоваться как цена одного контракта при расчёте риска и прибыли.

Акции с нулевым шагом цены или нулевым размером лота ДОЛЖНЫ исключаться из карты метаданных с предупреждением: из них нельзя достоверно вычислить ни риск, ни прибыль.

#### Scenario: Цена лота вычислена из каталога
- **WHEN** в каталоге акций есть `SBER` с минимальным шагом цены 0.01 ₽ и лотом 100 акций
- **THEN** метаданные содержат `price_step` = 0.01 и `step_cost` = 1.0, а `step_cost / price_step` = 100

#### Scenario: У акции нет ГО и даты экспирации
- **WHEN** загружены метаданные акции
- **THEN** `go_buy` и `go_sell` равны 0, а `expiration_date` равен `None`

#### Scenario: Вызывается каталог акций
- **WHEN** загружаются метаданные акций
- **THEN** вызывается `client.instruments.shares()`, а не `client.instruments.futures()`

#### Scenario: Запрошены только выбранные акции
- **WHEN** выбраны акции `SBER` и `GAZP`
- **THEN** в карту метаданных попадают только `SBER` и `GAZP`

#### Scenario: Акция без лота исключается
- **WHEN** в каталоге акция `SBER` имеет нулевой размер лота
- **THEN** акция не попадает в карту метаданных, в лог пишется предупреждение

### Requirement: Единая карта метаданных выбранных инструментов
Нормативный уровень: MUST.
При старте торговли система ДОЛЖНА собирать метаданные всех выбранных инструментов в одну карту: фьючерсы — из каталога фьючерсов, акции — из каталога акций. Источник данных ДОЛЖЕН соответствовать режиму запуска: в историческом режиме — клиент провайдера истории, в боевом — клиент по токену. Отсутствие метаданных для части выбранных инструментов ДОЛЖНО логироваться с перечислением тикеров и ДОЛЖНО приводить к отказу допуска только по этим инструментам. Сбой загрузки метаданных одного типа инструментов (например, недоступен каталог акций) НЕ ДОЛЖЕН отменять уже загруженные метаданные другого типа.

#### Scenario: Акции и фьючерсы в одной карте
- **WHEN** выбраны фьючерс `NGV6` и акция `SBER`
- **THEN** карта метаданных содержит оба тикера, и сигнал по акции проходит входной допуск

#### Scenario: В историческом режиме используется провайдер истории
- **WHEN** бот запущен в историческом режиме и загружает метаданные акций
- **THEN** запрос выполняется через клиент провайдера истории, а не по боевому токену

#### Scenario: Каталог акций недоступен
- **WHEN** загрузка метаданных акций завершилась ошибкой, а метаданные фьючерсов загрузились
- **THEN** карта содержит фьючерс, акции остаются без метаданных, а вход по акции отклоняется с кодом `no-contract-metadata`

#### Scenario: Перечислены инструменты без метаданных
- **WHEN** метаданные не найдены для части выбранных инструментов
- **THEN** в лог пишется предупреждение с перечислением тикеров, не имеющих метаданных

### Requirement: Метаданные фьючерсного контракта из источника данных
Нормативный уровень: MUST.
Метаданные фьючерсного контракта, полученные у источника данных, ДОЛЖНЫ содержать достоверные значения, а не заглушки: **шаг цены** — минимальный шаг из карточки инструмента; **стоимость шага** — `min_price_increment_amount` из той же карточки; **гарантийное обеспечение при покупке и продаже** — `initial_margin_on_buy` и `initial_margin_on_sell` из карточки; **дата экспирации** — `expiration_date` из карточки, разобранная как время. Источник ДОЛЖЕН отдавать дату экспирации в виде даты и времени с часовым поясом (ISO 8601, например `2025-06-20T00:00:00+00:00`); система ДОЛЖНА приводить её к единому naive-UTC виду так же, как остальные даты.

Адаптер источника данных НЕ ДОЛЖЕН подставлять константы вместо значений карточки: нулевое гарантийное обеспечение и пустая дата экспирации допустимы только когда источник действительно их не отдаёт. Поведение при отсутствующих полях ДОЛЖНО быть явным: стоимость шага при отсутствии берётся из шага цены, а отсутствующая дата экспирации трактуется как «экспирации нет» и НЕ ДОЛЖНА превращаться в текущую дату.

Получение метаданных по фьючерсу в историческом режиме ДОЛЖНО работать без токена боевого API: токен не является условием доступа к локальному источнику данных.

#### Scenario: ГО и стоимость шага взяты из карточки
- **WHEN** в карточке фьючерса указаны `min_price_increment` 1.0, `min_price_increment_amount` 1.0, `initial_margin_on_buy` 12345.67 и `initial_margin_on_sell` 12345.67
- **THEN** метаданные содержат шаг цены 1.0, стоимость шага 1.0 и гарантийное обеспечение 12345.67 при покупке и при продаже

#### Scenario: Дата экспирации разобрана из строки источника
- **WHEN** карточка фьючерса содержит `expiration_date` равный `2025-06-20T00:00:00+00:00`
- **THEN** в метаданных дата экспирации равна 2025-06-20 в naive-UTC виде, а не пустому значению

#### Scenario: У акции экспирации нет
- **WHEN** карточка акции содержит `expiration_date` равный `null`
- **THEN** в метаданных акции дата экспирации отсутствует, и акция не считается экспирирующей

#### Scenario: Отсутствующее поле не подменяется константой молча
- **WHEN** карточка инструмента не содержит стоимости шага цены
- **THEN** стоимость шага берётся из шага цены, и это поведение одинаково для всех источников данных

#### Scenario: Метаданные фьючерса доступны без токена
- **WHEN** прогон идёт в историческом режиме с локальным источником данных и переменная `TINKOFF_TOKEN` не задана
- **THEN** метаданные выбранных фьючерсов загружаются, а входы по ним допускаются без отказа по отсутствию метаданных

### Requirement: Закреплённый снимок свечей исторического клиента
Нормативный уровень: MUST. Исторический провайдер ДОЛЖЕН хранить номер
снимка только для текущего прогона и передавать его всем создаваемым им
клиентам. При подтверждённом снимке каждый запрос страницы
`GET /api/v1/candles` ДОЛЖЕН включать тот же `snapshot_generation`, в том
числе запросы прогрева, предпроверки, повторного чтения и последующих страниц
пагинации. Если синхронизация не подтверждена, параметр НЕ ДОЛЖЕН
передаваться. Боевой клиент ДОЛЖЕН сохранять прежнее поведение.

#### Scenario: Две страницы одной выборки
- **WHEN** эмулятор возвращает продолжение свечной выборки для подтверждённого снимка 42
- **THEN** первая и каждая следующая страница запрашиваются с `snapshot_generation=42`

#### Scenario: Новый клиент в том же прогоне
- **WHEN** предпроверка и торговый цикл создают разные исторические клиенты из одного провайдера
- **THEN** оба клиента используют один номер снимка

#### Scenario: Проверка импорта не удалась
- **WHEN** номер снимка не подтверждён из-за ошибки или неполного импорта
- **THEN** исторический клиент запрашивает обычное актуальное представление свечей без `snapshot_generation`
