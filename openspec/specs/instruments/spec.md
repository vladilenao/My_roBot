# Интерактивный выбор инструментов

## Purpose

Обеспечивает интерактивный двухэтапный выбор торговых инструментов (акции индекса РТС или фьючерсы) перед запуском основного цикла бота. Формирует список инструментов в формате `(display_name, ticker, instrument_type, short_name)` с валидацией через API, дедупликацией и единым форматом отображения.

## Requirements

### Requirement: Двухэтапный выбор типа инструментов
- Система ДОЛЖНА предоставить меню выбора типа: `1` — Акции (индекс РТС), `2` — Фьючерсы.

#### Scenario: Пользователь выбирает акции
- **WHEN** пользователь вводит `1`
- **THEN** отображается пронумерованный список акций индекса РТС

#### Scenario: Пользователь выбирает фьючерсы
- **WHEN** пользователь вводит `2`
- **THEN** система загружает фьючерсы через API и отображает список

### Requirement: Список акций индекса РТС
- Система ДОЛЖНА включать 15 акций: SBER, GAZP, LKOH, GMKN, ROSN, NVTK, YDEX, TCSG, VTBR, MTSS, PHOR, ALRS, MOEX, PLZL, TATN.

#### Scenario: Отображение списка акций
- **WHEN** пользователь выбрал пункт `1`
- **THEN** отображается пронумерованный список из 15 тикеров

### Requirement: Динамическая загрузка фьючерсов
Нормативный уровень: MUST.
Система ДОЛЖНА загружать фьючерсы через API `client.instruments.futures()`. В боевом и фиксированном историческом выборе система ДОЛЖНА отображать конкретные контракты. В автоматическом историческом выборе система ДОЛЖНА отображать поддерживаемые семейства из исторического каталога и разрешать их в календарную цепочку для выбранного диапазона.

#### Scenario: Фьючерсы успешно загружены
- **WHEN** API вернул список фьючерсов для выбора конкретных контрактов
- **THEN** отображается пронумерованный список, сгруппированный по базовому активу

#### Scenario: Ошибка загрузки фьючерсов
- **WHEN** при загрузке произошла ошибка
- **THEN** выводится сообщение об ошибке, пользователь может продолжить выбор

#### Scenario: Автоматическая история
- **WHEN** пользователь выбирает автоматическую историческую торговлю фьючерсами
- **THEN** отображаются семейства для выбора, а не необходимость вручную перечислить все выпуски диапазона

### Requirement: Поддерживаемые базы фьючерсов
- Система ДОЛЖНА включать фьючерсы для баз: RTS, BR, Si, SBRF, ED, NG, GOLD, SILV.

#### Scenario: Все базы присутствуют
- **WHEN** API вернул фьючерсы всех баз
- **THEN** каждая база представлена в списке

### Requirement: Фильтрация микро/мини и expired
Нормативный уровень: MUST.
Система ДОЛЖНА исключать контракты с "микро"/"мини" в названии из стандартных фьючерсов. При выборе конкретного контракта система ДОЛЖНА исключать контракты с экспирацией менее 0 дней или более 183 дней от момента выбора: системного времени в боевом режиме, рыночного времени в фиксированном историческом режиме. Для автоматической исторической цепочки система ДОЛЖНА использовать даты обращения и календарную допустимость на каждом участке; сегодняшний expired и ограничение 183 дней на весь диапазон НЕ ДОЛЖНЫ исключать нужные исторические выпуски.

#### Scenario: Микро-контракт исключён
- **WHEN** фьючерс содержит "мини" в названии
- **THEN** он не включается в стандартный список или цепочку

#### Scenario: Истёкший контракт исключён
- **WHEN** при выборе конкретного контракта `expiration_date < now` момента выбора
- **THEN** контракт не включается

#### Scenario: Далёкий контракт исключён
- **WHEN** при выборе конкретного контракта `expiration_date > now + 183 дней`
- **THEN** контракт не включается

#### Scenario: Длинная автоматическая цепочка
- **WHEN** исторический диапазон длиннее 183 дней
- **THEN** цепочка включает все нужные выпуски диапазона без общего шестимесячного ограничения

### Requirement: Единый формат отображения фьючерсов
- Фьючерсы ДОЛЖНЫ отображаться в формате `{base_name} ({label}) — {contract_name}` (например, `NG (Природный газ) — NG-9.26`).

#### Scenario: Формат отображения
- **WHEN** фьючерс с тикером `NGU6` и именем `NG-9.26 Природный газ`
- **THEN** отображается `NG (Природный газ) — NG-9.26`

### Requirement: Двухуровневая сортировка фьючерсов
- Фьючерсы ДОЛЖНЫ быть отсортированы сначала по типу базового актива (в порядке FUTURES_BASES), затем по дате экспирации от ближайшей к дальней внутри каждого типа.

#### Scenario: Сортировка по базе и экспирации
- **WHEN** загружены RTS-9.26, RTS-12.26, BR-9.26, BR-12.26
- **THEN** порядок: RTS-9.26, RTS-12.26, BR-9.26, BR-12.26

### Requirement: Множественный выбор
- Пользователь ДОЛЖЕН иметь возможность выбрать несколько инструментов, указав номера через запятую.

#### Scenario: Выбор по номерам
- **WHEN** пользователь вводит `1,3,5`
- **THEN** выбираются инструменты под номерами 1, 3 и 5

#### Scenario: Выбор по тикерам
- **WHEN** пользователь вводит `SBER,LKOH`
- **THEN** выбираются соответствующие инструменты

#### Scenario: Пустой ввод
- **WHEN** пользователь нажимает Enter без ввода
- **THEN** ничего не выбирается

#### Scenario: Номер вне диапазона
- **WHEN** номер превышает количество доступных инструментов
- **THEN** выводится предупреждение

### Requirement: Валидация выбранных инструментов
- Каждый выбранный инструмент ДОЛЖЕН быть проверен через `find_working_instrument`.

#### Scenario: Инструмент валиден
- **WHEN** `find_working_instrument` вернул UID
- **THEN** инструмент добавляется в список с подтверждением `✓`

#### Scenario: Инструмент невалиден
- **WHEN** `find_working_instrument` выбросил исключение
- **THEN** выводится ошибка `✗` и инструмент не добавляется

### Requirement: Дедупликация
- Один и тот же тикер НЕ ДОЛЖЕН появляться дважды в результирующем списке.

#### Scenario: Повторный тикер
- **WHEN** пользователь выбирает один и тот же тикер в разных раундах
- **THEN** он включается только один раз (первое вхождение)

### Requirement: Повторные раунды выбора
- После каждого раунда система ДОЛЖНА спрашивать "Добавить ещё инструменты?".

#### Scenario: Пользователь хочет добавить ещё
- **WHEN** пользователь отвечает "да"/"y"/"yes"
- **THEN** начинается новый раунд выбора

#### Scenario: Пользователь завершает выбор
- **WHEN** пользователь отвечает "нет"/"n"/"no"
- **THEN** процесс выбора завершается

### Requirement: Минимум один инструмент
- Если после завершения выбора список пуст, система ДОЛЖНА потребовать повторить выбор.

#### Scenario: Пустой список
- **WHEN** выбрано 0 инструментов
- **THEN** выводится сообщение и процесс выбора начинается заново

### Requirement: Возврат списка инструментов
Нормативный уровень: MUST.
Для боевого и фиксированного исторического выбора функция ДОЛЖНА вернуть список кортежей `(display_name, ticker, instrument_type, short_name)`, где short_name — краткое имя инструмента для уведомлений: для фьючерсов — читаемое имя контракта из API, для акций — тикер. Автоматический исторический выбор ДОЛЖЕН дополнительно сохранять идентичности выбранных семейств и их разрешённый план конкретных контрактов; семейство НЕ ДОЛЖНО подменять идентичность конкретного инструмента в торговой сделке.

#### Scenario: Формат возврата для акций
- **WHEN** выбран SBER
- **THEN** возвращается `[("SBER", "SBER", "share", "SBER")]`

#### Scenario: Формат возврата для фьючерсов
- **WHEN** выбран контракт NG-9.26 с соответствующей карточкой API в режиме конкретного контракта
- **THEN** возвращается кортеж с его display_name, внутренним тикером, типом future и short_name NG-9.26

#### Scenario: Семейство разрешено в конкретные контракты
- **WHEN** выбран автоматический исторический NG через несколько экспираций
- **THEN** выбор сохраняет NG и план участков, каждая торговая сделка указывает конкретный контракт своего участка

### Requirement: Использование контекстного менеджера API
- Функция ДОЛЖНА использовать `client_context()` как контекстный менеджер.

#### Scenario: Клиент закрывается
- **WHEN** выбор завершается
- **THEN** контекстный менеджер клиента корректно закрывается

### Requirement: Валидация с учётом лимита API
Проверка выбранных инструментов через `find_working_instrument` ДОЛЖНА выполняться с
паузой не чаще сконфигурированного минимального интервала перезагрузки данных между
проверками, а при исчерпании лимита запросов API (`RESOURCE_EXHAUSTED`) —
приостанавливаться до момента сброса лимита (`ratelimit_reset`) и затем
продолжаться. Объёмные выборы (например, много фьючерсов) НЕ ДОЛЖНЫ выжигать лимит
и прерывать старт робота.

#### Scenario: Пауза между проверками инструментов
- **WHEN** выбрано несколько фьючерсов для валидации
- **THEN** между проверками соблюдается минимальный интервал перезагрузки данных

#### Scenario: Лимит при валидации
- **WHEN** `find_working_instrument` возвращает `RESOURCE_EXHAUSTED` с `ratelimit_reset`
- **THEN** проверки приостанавливаются до наступления сброса лимита и продолжаются
  после него

### Requirement: Исторический выбор семейства или контракта
Нормативный уровень: MUST.
При выборе фьючерсов в историческом режиме система ДОЛЖНА предложить автоматическую торговлю семейством по умолчанию и явный выбор фиксированного контракта. ДОЛЖНЫ поддерживаться существующие семейства RTS, BR, Si, SBRF, ED, NG, GOLD, SILV, множественный выбор и сочетание с акциями. Повторный выбор семейства ДОЛЖЕН дедуплицироваться; сочетание автоматического семейства и фиксированного контракта этого же семейства ДОЛЖНО отклоняться как конфликт. Пользовательское отображение контрактов ДОЛЖНО использовать короткие имена, а не биржевые коды.

#### Scenario: Выбор семейства по умолчанию
- **WHEN** пользователь в истории выбирает фьючерсы и принимает предложенный режим
- **THEN** он выбирает семейства с автоматической сменой контрактов

#### Scenario: Исследование фиксированного контракта
- **WHEN** пользователь явно выбирает фиксированный исторический контракт
- **THEN** прогон остаётся привязанным к нему без автоматической смены

#### Scenario: Смешанный портфель
- **WHEN** выбраны два автоматических семейства и акция
- **THEN** семейства имеют независимые цепочки, акция не участвует в переходах, все используют общий счёт прогона

#### Scenario: Конфликт режимов одного семейства
- **WHEN** пользователь выбирает автоматический NG и фиксированный контракт NG
- **THEN** выбор сообщает конфликт и требует устранить его до запуска

### Requirement: Инструменты из параметров запуска
Нормативный уровень: MUST. Инструменты запуска ДОЛЖНЫ задаваться списком токенов без учёта регистра из одного из трёх источников: параметра `--instruments` (через запятую), поля `instruments` команды API или выбора в меню, итогом которого ДОЛЖЕН быть такой же список. Правила разрешения ДОЛЖНЫ быть одинаковыми для всех источников. Без параметра или поля ДОЛЖНО применяться значение `all`.

Токены:
- `all` — все акции из секций `[strategies.share.*]` и все семейства фьючерсов из `[strategies.future.*]` конфигурации;
- тикер акции — эта акция;
- код семейства фьючерсов или его биржевой префикс (`NG`, `RTS` или `RI`, `SBRF` или `SR`) — в эмуляции один контракт семейства по правилу ниже, в истории автоматическая цепочка контрактов семейства;
- контракт коротким именем (`NG-12.26`) или биржевым тикером — этот контракт; в истории — фиксированный контракт.

Для семейства в эмуляции ДОЛЖЕН выбираться ближайший по экспирации стандартный контракт из списка активных фьючерсов, до экспирации которого больше `contract_expiry_block_days` суток. Выбор ДОЛЖЕН печататься коротким именем с числом суток до экспирации.

Токен, у которого нет привязок в конфигурации, ДОЛЖЕН отклоняться. Семейство и его же контракт в одном запуске ДОЛЖНЫ отклоняться как конфликт. Каждый разрешённый инструмент ДОЛЖЕН проверяться у источника так же, как при выборе в меню. При запуске с параметрами любой отклонённый токен ДОЛЖЕН завершать процесс с кодом `2` и причиной без запуска торговли; в команде API — давать ответ `422` со списком отказов без запуска торговли. При выборе в меню отклонённый инструмент ДОЛЖЕН помечаться `✗` и пропускаться, а пустой итог ДОЛЖЕН возвращать к выбору.

Выбранный инструмент ДОЛЖЕН, как и прежде, включать все свои привязки конфигурации.

#### Scenario: Все инструменты из привязок
- **GIVEN** в конфигурации есть привязки для акции SBER и семейств NG и BR
- **WHEN** робот запущен с `--mode emulation` без `--instruments`
- **THEN** торгуются SBER, один контракт NG и один контракт BR, выбранные по правилу ближайшего контракта

#### Scenario: Ближайший контракт пропускается из-за экспирации
- **GIVEN** `contract_expiry_block_days = 2`, у NG до экспирации ближайшего контракта NG-11.26 осталось одни сутки, у следующего NG-12.26 — 31 сутки
- **WHEN** робот запущен с `--mode emulation --instruments NG`
- **THEN** выбирается NG-12.26, и в консоли печатается `NG → NG-12.26, до экспирации 31 сутки`

#### Scenario: Семейство в истории
- **WHEN** робот запущен с `--mode history --from … --to … --instruments NG`
- **THEN** NG торгуется автоматической цепочкой контрактов, как при выборе семейства в меню

#### Scenario: Явный контракт
- **WHEN** робот запущен с `--mode emulation --instruments NG-03.27`
- **THEN** торгуется контракт NG-03.27, правило ближайшего контракта не применяется

#### Scenario: Инструмент без привязок
- **GIVEN** у акции AFLT нет секции `[strategies.share.AFLT]`
- **WHEN** робот запущен с `--mode emulation --instruments SBER,AFLT`
- **THEN** печатается, что у AFLT нет привязок в конфигурации, процесс завершается с кодом `2` и торговля не начинается

#### Scenario: Конфликт семейства и контракта
- **WHEN** робот запущен с `--mode history --from … --to … --instruments NG,NG-12.26`
- **THEN** печатается конфликт семейства и фиксированного контракта, процесс завершается с кодом `2`

#### Scenario: Неизвестный инструмент в меню
- **WHEN** в меню выбраны SBER и опечатка `SBEER`
- **THEN** SBER принимается с `✓`, `SBEER` помечается `✗`, запуск продолжается с SBER
