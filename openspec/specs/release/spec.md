# Релиз

## Purpose

Определяет версионирование и состав распространяемой сборки робота: номер версии SemVer, журнал изменений и проверенные macOS/Windows ZIP-дистрибутивы на GitHub Release.

## Requirements

### Requirement: Версия SemVer
Система ДОЛЖНА иметь единственный источник правды номера версии — атрибут `__version__` в `src/__init__.py`, формата `MAJOR.MINOR.PATCH`. Правила нумерации ДОЛЖНЫ быть зафиксированы комментарием в том же файле: `MAJOR` — изменение поведения сигналов или ломающее конфигурацию; `MINOR` — новое обратно совместимое (новая стратегия, модуль); `PATCH` — исправления без изменения поведения сигналов.

#### Scenario: Версия импортируется из пакета
- **WHEN** выполняется `from src import __version__`
- **THEN** возвращается строка вида `"1.3.0"` (MAJOR.MINOR.PATCH)

#### Scenario: Правила нумерации зафиксированы в коде
- **WHEN** разработчик открывает `src/__init__.py`
- **THEN** рядом с `__version__` находится комментарий с правилами MAJOR/MINOR/PATCH

### Requirement: Версия в логе при старте
Система ДОЛЖНА при каждом запуске робота выводить в лог строку с номером версии.

#### Scenario: Запуск робота
- **WHEN** робот запускается
- **THEN** в лог пишется сообщение, содержащее номер версии (например `Робот v1.3.0 запущен`)

### Requirement: Имя исполняемого файла сборки
Нормативный уровень: MUST.
Собираемый исполняемый файл ДОЛЖЕН называться `robot-v<версия>-<платформа>` (например `robot-v1.3.0-windows-x64.exe`), где `<версия>` — значение `__version__`, а `<платформа>` содержит ОС и архитектуру. PyInstaller ДОЛЖЕН собирать binary нативно для заявленной платформы.

#### Scenario: Сборка с версией в имени
- **WHEN** выполняется сборка версии 1.3.0
- **THEN** итоговый исполняемый файл называется `robot-v1.3.0-macos-arm64` либо `robot-v1.3.0-windows-x64.exe`

### Requirement: Версионный ZIP-дистрибутив
Нормативный уровень: MUST.
Каждая поддерживаемая платформа ДОЛЖНА распространяться отдельным ZIP-архивом `robot-v<версия>-<платформа>.zip` на GitHub Release соответствующего тега. Внутри архива ДОЛЖНА быть одна одноимённая папка с binary, `VERSION.txt`, `README.txt`, безопасным `robot.toml.example` и текстовым файлом `robot-v<версия>.txt` с тезисами изменений. Дистрибутив НЕ ДОЛЖЕН содержать `.env`, токены, рабочий `robot.toml`, базы данных или логи.

#### Scenario: Текстовый файл сопровождает сборку
- **WHEN** выпускается версия 1.3.0
- **THEN** GitHub Release содержит `robot-v1.3.0-windows-x64.zip`, в котором рядом с binary находятся `VERSION.txt`, `README.txt`, `robot.toml.example` и `robot-v1.3.0.txt` с перечнем изменений версии 1.3.0

### Requirement: Согласованность версии, тега и журнала изменений
Нормативный уровень: MUST.
Релизный тег ДОЛЖЕН иметь вид `v<версия>` и точно совпадать с `__version__`. Перед публикацией ДОЛЖНЫ быть успешно выполнены pytest, Ruff и smoke-проверки готовых binary. В `CHANGELOG.md` ДОЛЖНА быть секция `## <версия> — <дата>` и новый заголовок `## Unreleased`.

#### Scenario: Тег соответствует версии
- **WHEN** `__version__` равно `1.3.0` и публикуется релиз
- **THEN** допустим только тег `v1.3.0`, а артефакты, VERSION.txt и секция CHANGELOG используют `1.3.0`

#### Scenario: Несоответствующий тег останавливает выпуск
- **WHEN** `__version__` равно `1.3.0`, а workflow запущен для тега `v1.3.1`
- **THEN** выпуск завершается ошибкой до создания или изменения GitHub Release

### Requirement: Публикация проверенных дистрибутивов
Нормативный уровень: MUST.
CI ДОЛЖЕН нативно собрать macOS arm64 и Windows x64, проверить каждый готовый binary и опубликовать оба ZIP-дистрибутива, release notes и файл `checksums.txt` на GitHub Release тега. `checksums.txt` ДОЛЖЕН содержать SHA-256 каждого опубликованного ZIP. Временные artifacts GitHub Actions НЕ ДОЛЖНЫ быть единственным каналом распространения релиза.

#### Scenario: Релиз опубликован для двух платформ
- **WHEN** CI завершил выпуск версии
- **THEN** GitHub Release содержит проверенные ZIP-дистрибутивы macOS arm64 и Windows x64, release notes и SHA-256 checksums

#### Scenario: Пользователь получает Windows-сборку
- **WHEN** Windows-пользователь открывает GitHub Release версии
- **THEN** он скачивает `robot-v<версия>-windows-x64.zip` без обращения к техническим artifacts Actions

### Requirement: Журнал изменений CHANGELOG.md
Система ДОЛЖНА сопровождаться журналом изменений в корне репозитория — файлом `CHANGELOG.md`. Текущие правки ДОЛЖНЫ накапливаться под заголовком `## Unreleased`; при выпуске версии секция ДОЛЖНА переименовываться в `## <версия> — <дата>`. Содержимое — тезисы изменений, понятные тому, кто запускает робота.

#### Scenario: Правки накапливаются до выпуска
- **WHEN** разработчик вносит изменения между релизами
- **THEN** они фиксируются в секции `## Unreleased`

#### Scenario: Секция релиза получает номер и дату
- **WHEN** выпускается версия 1.3.0
- **THEN** секция Unreleased переименовывается в `## 1.3.0 — <дата>` и описывает изменения, заметные пользователю
