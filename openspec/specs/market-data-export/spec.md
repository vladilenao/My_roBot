# market-data-export Specification

## Purpose
Даёт Historical Broker API Emulator документированный и восстанавливаемый способ переносить подтверждённые изменения рыночных данных My Robot в собственное хранилище.

## Requirements

### Requirement: Версионированный внешний контракт
Нормативный уровень: MUST. My Robot ДОЛЖЕН предоставлять версионированный
HTTP API `/api/v1/market-data`, отдавать OpenAPI 3.0.3 контракт по
`GET /openapi.yaml` и предоставлять Swagger UI по `GET /docs`.
Контракт ДОЛЖЕН описывать все внешние запросы, ответы, авторизацию,
ошибки и примеры подключения потребителя. API ДОЛЖЕН сообщать постоянный
`producer_id` локальной базы и доступный диапазон курсора.

Контракт ДОЛЖЕН быть единым для всех HTTP-сервисов робота: файл
`docs/openapi.yaml`, по одному тегу на сервис (`MarketDataExport`,
`Clusters`, `Contours`). `GET /openapi.yaml` ДОЛЖЕН отдавать именно этот файл.
Отдельные файлы контрактов HTTP-сервисов робота НЕ ДОЛЖНЫ создаваться.
Каждая схема ключа (`ExportToken`, `ControlToken`) ДОЛЖНА быть описана в
контракте отдельно, а маршрут ДОЛЖЕН ссылаться только на свою схему.

#### Scenario: Потребитель начинает подключение
- **WHEN** Historical Broker API Emulator запрашивает `GET /source`
- **THEN** он получает идентификатор производителя и допустимый диапазон курсора для последующих запросов

#### Scenario: Один контракт на все сервисы
- **WHEN** пользователь открывает `GET /docs`
- **THEN** Swagger UI показывает экспорт рыночных данных, отчёт кластерного фильтра и управление контурами из `docs/openapi.yaml`

#### Scenario: Ключ управления в Swagger
- **WHEN** пользователь открывает в Swagger UI маршрут `POST /api/v1/contours`
- **THEN** маршрут требует схему `ControlToken`, а не `ExportToken`

### Requirement: Постраничный поток подтверждённых изменений
Нормативный уровень: MUST. `GET /changes` ДОЛЖЕН возвращать изменения строго
по возрастанию монотонного `change_id`, начиная после переданного `after_id`.
Ответ ДОЛЖЕН содержать `producer_id`, `next_after_id`, `has_more` и данные
изменений. Свечные изменения ДОЛЖНЫ содержать только завершённые версии;
изменения состояния покрытия ДОЛЖНЫ передаваться отдельно. Повтор чтения
страницы ДОЛЖЕН возвращать те же идентификаторы без пропуска позднего
исправления старой свечи.

#### Scenario: Исправлена старая свеча
- **WHEN** после экспорта свечи 12:03 получено исправление 12:01
- **THEN** исправление имеет новый `change_id` и доступно запросом после предыдущего курсора

#### Scenario: Потребитель читает повторно
- **WHEN** потребитель повторяет запрос с тем же `after_id`
- **THEN** он получает те же изменения и может удалить дубли по `(producer_id, change_id)`

### Requirement: Подтверждение после сохранения у потребителя
Нормативный уровень: MUST. API ДОЛЖЕН позволять авторизованному потребителю
монотонно подтверждать последний сохранённый `change_id` через
`PUT /consumers/{consumer_id}/checkpoint`. Повтор подтверждения ДОЛЖЕН быть
безопасен. Неподтверждённые изменения НЕ ДОЛЖНЫ удаляться по обычному правилу
хранения, даже когда исторический сервис недоступен.

Правило хранения ленты `/changes`: в живом режиме система ДОЛЖНА удалять из
начала ленты изменения, записанные раньше `[market_data] changes_retention_days`
суток назад. Удаление НЕ ДОЛЖНО заходить дальше наименьшего подтверждённого
`change_id` среди потребителей ленты `/changes` текущего `producer_id`.
Подтверждения ленты расписаний очистку ленты `/changes` НЕ ДОЛЖНЫ удерживать.
Если подтвердивших потребителей нет, очистку ограничивает только срок.
Значение `0` ДОЛЖНО выключать очистку. Исторический режим очистку НЕ ДОЛЖЕН
выполнять.

Удаляться ДОЛЖЕН только непрерывный префикс ленты, порциями короткими
транзакциями, не блокирующими запись свечей дольше одной порции. В той же
транзакции, что и порция, `min_after_id` ДОЛЖЕН подниматься до последнего
удалённого `change_id`. `max_change_id` в `GET /source` НЕ ДОЛЖЕН быть меньше
`min_after_id`, в том числе когда лента очищена целиком. Итог прохода и
потребитель, удерживающий очистку, с его отставанием ДОЛЖНЫ попадать в журнал.

#### Scenario: Сбой после записи страницы
- **WHEN** эмулятор сохранил страницу у себя, но связь пропала до подтверждения
- **THEN** он может получить страницу повторно, не создать дублей и затем подтвердить её

#### Scenario: Эмулятор долго недоступен
- **WHEN** потребитель не подтверждает изменения длительное время
- **THEN** неподтверждённые изменения сохраняются, а накопленное отставание доступно диагностике

#### Scenario: Потребителей нет, лента старше срока
- **GIVEN** `changes_retention_days = 7` и ни один потребитель ленты `/changes` не подтверждал чтение
- **WHEN** проходит очистка, а в начале ленты лежат изменения десятидневной давности
- **THEN** изменения старше семи суток удаляются, `GET /source` отдаёт `min_after_id`, равный последнему удалённому `change_id`, а запрос с меньшим `after_id` получает `410 Gone`

#### Scenario: Подтверждение удерживает старые изменения
- **GIVEN** потребитель подтвердил `change_id = 100`, а изменения 101–500 старше срока
- **WHEN** проходит очистка
- **THEN** удаляются только изменения по 100 включительно, изменения после 100 сохраняются до их подтверждения

#### Scenario: Подтверждение расписаний не удерживает ленту свечей
- **GIVEN** есть только подтверждение ленты расписаний, а изменения ленты `/changes` старше срока
- **WHEN** проходит очистка
- **THEN** изменения ленты `/changes` удаляются по сроку, лента расписаний не меняется

#### Scenario: Лента очищена целиком
- **WHEN** все изменения ленты оказались старше срока и удалены
- **THEN** `max_change_id` равен `min_after_id`, а потребитель с курсором `min_after_id` получает пустую страницу и может подтвердить этот курсор

#### Scenario: Очистка выключена
- **WHEN** `changes_retention_days = 0`
- **THEN** изменения ленты не удаляются и `min_after_id` не меняется

### Requirement: Явные ошибки курсора и безопасность доступа
Нормативный уровень: MUST. API ДОЛЖЕН отклонять курсор другого `producer_id`
и курсор старше доступного диапазона с различимыми ошибками. По умолчанию
API ДОЛЖЕН слушать только локальный интерфейс и требовать токен доступа.
Ответы НЕ ДОЛЖНЫ содержать торговые команды, сделки, баланс или секреты.

#### Scenario: Локальная БД пересоздана
- **WHEN** потребитель продолжает с `producer_id` прежней базы
- **THEN** API возвращает конфликт идентичности, и прежний курсор не принимается

#### Scenario: Курсор вышел за удержанный диапазон
- **WHEN** `after_id` старше минимально допустимого курсора
- **THEN** API возвращает `410 Gone`, а потребитель не считает экспорт полным

#### Scenario: Нет токена доступа
- **WHEN** запрос к API не содержит корректного токена
- **THEN** рыночные данные и подтверждения курсора недоступны

### Requirement: Отдельная лента наблюдений расписания
Нормативный уровень: MUST. My Robot ДОЛЖЕН предоставлять наблюдения расписания отдельным ресурсом версионированного API `/api/v1/market-data` с собственным монотонным курсором и собственным подтверждением потребителя. Наблюдения включают:
- дни расписания с режимом торгов, торговой датой, версией, временем наблюдения и исходным ответом;
- привязки UID к режиму торгов со временем наблюдения.

Существующий поток `/changes` НЕ ДОЛЖЕН получать новые виды изменений из-за расписания, а его курсор, состав и правила подтверждения НЕ ДОЛЖНЫ меняться. Для ленты расписания ДОЛЖНЫ действовать те же правила, что для потока изменений:
- повтор страницы без пропусков;
- различимые ошибки чужого `producer_id` и устаревшего курсора;
- хранение неподтверждённых записей;
- локальный интерфейс и токен доступа;
- отсутствие торговых данных и секретов.

OpenAPI-контракт ДОЛЖЕН описывать новый ресурс аддитивно.

#### Scenario: Текущий потребитель без поддержки расписания
- **WHEN** эмулятор, знающий только свечи и состояния покрытия, читает `/changes`
- **THEN** он получает прежние виды изменений без неизвестных записей, его курсор продвигается как раньше

#### Scenario: Брокер изменил расписание дня
- **WHEN** робот сохранил новую версию уже экспортированного дня
- **THEN** новая версия получает новый курсор ленты расписания и доступна после предыдущего подтверждённого курсора

#### Scenario: Повторное чтение ленты расписания
- **WHEN** потребитель повторяет запрос с тем же курсором
- **THEN** он получает те же записи и может удалить дубли по производителю и курсору

### Requirement: Совместимая передача отсутствия свечи у источника
Нормативный уровень: MUST. Интервал в состоянии «у источника нет» ДОЛЖЕН экспортироваться в ленте `/changes` как изменение состояния покрытия со значением `unresolved` и доказательством, начинающимся с `source_absent`. Доказательство ДОЛЖНО включать число и время проверок. Новое значение состояния НЕ ДОЛЖНО появляться в ленте без отдельного версионированного изменения контракта. Последующее получение свечи этого интервала ДОЛЖНО экспортироваться обычным изменением свечи.

#### Scenario: Потребитель знает только прежние состояния
- **WHEN** эмулятор, принимающий `scheduled_closed`, `confirmed_no_trade`, `pending` и `unresolved`, читает изменение минуты «у источника нет»
- **THEN** он получает `unresolved` с доказательством `source_absent:…` и не останавливает импорт

#### Scenario: Свеча пришла позже
- **WHEN** после экспорта `source_absent` источник вернул свечу этой минуты
- **THEN** в ленте появляется изменение свечи с новым `change_id`, и потребитель видит минуту полученной
