# Уведомления

## Purpose

Доставляет сообщения с торговыми сигналами через выбранный в конфигурации канал — Telegram Bot API или stdout. Решение форматируется внедрённым форматтером; когда Telegram не настроен — выводится предупреждение и HTTP-запрос пропускается.

## Requirements

### Requirement: Компактный формат сигналов
Нормативный уровень: MUST.
Формат решения определяется шаблоном `src/notifier/templates/decision.py`, а не общим форматтером: за каждым каналом стоит свой шаблон, и общий форматтер запрещён. Каждое решение оформляется одной строкой. Для BUY — `🟢 ПОКУПКА (BUY) — Цена: X`; для SELL — `🔴 ПРОДАЖА (SELL) — Цена: X`; для HOLD — `⏳ Нет сигнала.` без цены; для отклонённого фильтром решения (`filtered_out=True`) — `❌ Отклонено фильтром.` без цены. Строка ДОЛЖНА начинаться с маркера `● `; за маркером ДОЛЖЕН следовать `<инструмент>`, к которому через один пробел добавляется блок таймфрейма `(<таймфрейм>)` при наличии заданного задаче таймфрейма; блок времени бара `HH:MM` и блок стратегии `| <имя>` включаются только при наличии соответствующих значений; блок профиля фильтрации `[<профиль>]` ДОЛЖЕН следовать за блоком стратегии и включается только при наличии значения профиля.

Значение `bar_time` решения ДОЛЖНО представлять момент ЗАКРЫТИЯ свечи последнего бара, а не момент её начала: момент начала бара в tz-naive UTC, сложенный с длительностью периода таймфрейма. Блок времени `HH:MM` ДОЛЖЕН отображать `bar_time` в локальном часовом поясе пользователя: к значению применяется сконфигурированное смещение от UTC, заданное в часах. При нулевом смещении выводится UTC-время закрытия без изменений.

#### Scenario: Покупка
- **WHEN** решение имеет тип BUY, цену X, время закрытия бара 22:00, стратегию `macd_rsi_stoch`, профиль `raw`, а таймфрейм задачи `15m`
- **THEN** сообщение равно `● <инструмент> (15m) 22:00 | macd_rsi_stoch [raw] ➜ 🟢 ПОКУПКА (BUY) — Цена: X`

#### Scenario: Продажа
- **WHEN** решение имеет тип SELL, цену X, время закрытия бара 22:00, стратегию `macd_rsi_stoch`, профиль `basic_levels`, а таймфрейм задачи `1h`
- **THEN** сообщение равно `● <инструмент> (1h) 22:00 | macd_rsi_stoch [basic_levels] ➜ 🔴 ПРОДАЖА (SELL) — Цена: X`

#### Scenario: Нет сигнала
- **WHEN** решение имеет тип HOLD
- **THEN** сообщение содержит `⏳ Нет сигнала.` и не содержит цены

#### Scenario: Отклонено фильтром
- **WHEN** решение доставляется с признаком `filtered_out=True`
- **THEN** сообщение содержит статус `❌ Отклонено фильтром.` и не содержит цены

#### Scenario: Нет профиля фильтрации
- **WHEN** профиль фильтрации не задан (пустое значение)
- **THEN** блок `[<профиль>]` в строке опускается

#### Scenario: Нет времени бара
- **WHEN** решение не имеет `bar_time`
- **THEN** блок времени в строке опускается (нет `HH:MM`)

#### Scenario: Нет имени стратегии
- **WHEN** решение не имеет имени стратегии
- **THEN** блок `| <имя>` в строке опускается

#### Scenario: Нет таймфрейма
- **WHEN** задаче не задан таймфрейм (пустое значение параметра)
- **THEN** блок `(<таймфрейм>)` в строке опускается, маркер `● ` и `<инструмент>` выводятся без него

#### Scenario: Время в локальном поясе
- **WHEN** смещение часового пояса задано, например `+3` часа, а `bar_time` равен `06:00` UTC (момент закрытия свечи)
- **THEN** в сообщении блок времени выводится как `09:00` (к значению закрытия прибавлено смещение)

#### Scenario: Нулевое смещение сохраняет UTC
- **WHEN** смещение часового пояса равно `0`, а `bar_time` равен `06:00` UTC (момент закрытия свечи)
- **THEN** блок времени выводится как `06:00` (UTC-время закрытия без изменений)

### Requirement: Формат уведомления о недопуске сделки
Нормативный уровень: MUST.
Недопуск сделки отображается шаблоном `src/notifier/templates/decision.py` сообщением вида `⛔ <инструмент> (<таймфрейм>) HH:MM | <стратегия> [<профиль>] ➜ Сделка не допущена: <причина>`, где `<инструмент>` — краткое имя инструмента (short name, например `NG-10.26`), `<таймфрейм>` — таймфрейм задачи (блок опускается при отсутствии), `HH:MM` — время закрытия последнего бара в локальном поясе (блок опускается при отсутствии), `<стратегия>` — имя стратегии (блок опускается при отсутствии), `<профиль>` — профиль фильтрации (блок опускается при отсутствии), `<причина>` — человекочитаемое описание причины недопуска на русском. Маркер `⛔ ` ДОЛЖЕН отличать сообщение о недопуске от обычных сигналов (`● `). Формат обычных сигналов НЕ изменяется.

#### Scenario: Недопуск из-за нулевого объёма
- **WHEN** решение BUY по привязке `15m`/`macd_rsi_stoch`/`basic_levels` не допущено с причиной «Объём позиции ниже минимального»
- **THEN** доставленное сообщение равно `⛔ <инструмент> (15m) | macd_rsi_stoch [basic_levels] ➜ Сделка не допущена: Объём позиции ниже минимального`

#### Scenario: Без таймфрейма, стратегии и профиля
- **WHEN** недопуск произошёл по решению без заданных таймфрейма, имени стратегии и профиля
- **THEN** сообщение содержит `⛔ <инструмент> ➜ Сделка не допущена: <причина>` без блоков `(таймфрейм)`, `| стратегия` и `[профиль]`

#### Scenario: Обычный сигнал сохраняет формат
- **WHEN** сигнал BUY допущен и доставляется как обычно
- **THEN** сообщение начинается с `●` и имеет прежний формат `🟢 ПОКУПКА (BUY) — Цена: X`, без маркера `⛔`

#### Scenario: Недопуск дублирующего сигнала
- **WHEN** повторный сигнал той же связки по тому же бару не допущен с причиной `duplicate-signal`
- **THEN** доставленное сообщение содержит маркер `⛔`, контекст задачи и причину «дублирующий сигнал, сделка не взята в работу»

### Requirement: Уведомление о принятой в работу сделке
Нормативный уровень: MUST.
После успешного допуска входа система ДОЛЖНА доставить трейдеру уведомление с коротким инструментом, таймфреймом, направлением, выбранным целым объёмом, плановыми входом/стопом/целями, версией алгоритма и явным статусом «в работе, ждёт подтверждения». При уменьшении относительно явно запрошенного объёма показываются исходное количество и ограничившая причина (риск, ГО, предел количества или профиль), без утверждения о закрытии несуществующей позиции. Оно НЕ ДОЛЖНО утверждать факт исполнения или подавлять обычное уведомление о решении стратегии. В Telegram это корневая карточка события `signal`, а не вторая отдельная рекомендация по тому же допуску.

Для полного ценового выхода уведомление ДОЛЖНО показывать плановый валовой результат по целым аллокациям, риск до стопа, оценку круговых издержек и чистую плановую прибыль. Консоль сохраняет две цифры после точки для R и чистого payoff: например при нулевых расходах `валовой план 1.50R ≈ 375 ₽ (риск 250 ₽)`. Telegram использует русские денежные подписи «Плановая прибыль до расходов», «Риск до стопа», «Расходы ≈», «Плановая прибыль после расходов», без обязательного вывода сокращений R/payoff. При ненулевых издержках результаты до/после расходов ДОЛЖНЫ различаться явно. Значения НЕ ДОЛЖНЫ называться статистическим матожиданием, гарантией прибыли или фактически списанной комиссией.

При нулевом R, отсутствии целей либо неизвестном трейлинговом остатке общий результат/полный payoff отсутствуют, а не равны нулю. Для отсутствующих целей блок результата опускается; для частичной лестницы допускается отдельный блок «фиксируемая часть», явно не итог сделки. Плановые оценки и фактические комиссии различаются; подтверждённые данные показываются только после соответствующего факта.

#### Scenario: Успешный допуск входа
- **WHEN** допущен SELL по Si 5m, объём семь и полный план известен
- **THEN** уведомление содержит `Si-12.26`, контекст, уровни, план до/после расходов, издержки, риск, версию и ожидание подтверждения

#### Scenario: Исполнение ещё не подтверждено
- **WHEN** брокер не подтвердил fill
- **THEN** текст не утверждает открытие позиции или списание фактической комиссии

#### Scenario: Ожидаемый результат считается по плану
- **WHEN** SELL имеет риск расстояния 4, полный выход по целям на 4 и 8 ниже входа, чётный объём, доли 0.5/0.5 и расходы нулевые
- **THEN** валовой план соответствует 1.50R; консоль показывает R, Telegram — соответствующую денежную величину

#### Scenario: Денежная величина ожидаемого результата
- **WHEN** R=250 ₽, полный валовой план 1.50R и C=0
- **THEN** консоль содержит `1.50R ≈ 375 ₽ (риск 250 ₽)`, Telegram — плановую прибыль 375 ₽ и риск до стопа 250 ₽

#### Scenario: Риск нулевой
- **WHEN** диагностический план имеет нулевой риск либо целей нет
- **THEN** отсутствующий результат не печатается как `0.00R` или нулевая денежная доходность

#### Scenario: План без целей не показывает нулевую доходность
- **WHEN** допущен ma_cloud без целей
- **THEN** видны вход/стоп и отсутствие целей, но нет нулевой либо выдуманной доходности

#### Scenario: Ненулевые издержки видны отдельно
- **WHEN** полный gross=160 ₽, R=80 ₽, C=40 ₽
- **THEN** оба канала различают план до расходов 160 ₽, риск 80 ₽, чистую прибыль 120 ₽ и оценку издержек 40 ₽; консоль дополнительно сохраняет 2R и payoff 1.5

#### Scenario: Трейлинг не превращается в полную доходность
- **WHEN** часть atr_trend остаётся под трейлингом
- **THEN** общий payoff и полная плановая прибыль не показываются как известные; известные цели подписаны «фиксируемая часть»

#### Scenario: Размер уменьшен до заявки
- **WHEN** вместо запрошенных пяти допущены два контракта из-за свободного ГО
- **THEN** уведомление показывает два, исходный запрос пять и ограничение ГО; не заявляет продажу трёх или реализованный убыток
### Requirement: Проверка конфигурации Telegram
Нормативный уровень: MUST.
Если `TELEGRAM_BOT_TOKEN` или `TELEGRAM_CHANNEL_ID` не заданы (None/пустые), канал Telegram ДОЛЖЕН записать предупреждение в модульный логгер и пропустить HTTP-запрос. Дублирующий вывод сообщения в консоль при этом НЕ ДОЛЖЕН выполняться. Канал при этом ДОЛЖЕН оставаться подписанным на свои типы событий и НЕ ДОЛЖЕН влиять на доставку другим каналам.

#### Scenario: Telegram не настроен
- **WHEN** токен или идентификатор канала равен `None`
- **THEN** в логгер записывается предупреждение, HTTP-запрос не выполняется, эхо-печать сообщения отсутствует

#### Scenario: Остальные каналы работают
- **WHEN** Telegram не настроен, активны консоль и Telegram
- **THEN** консоль получает все события, торговый цикл не прерывается

### Requirement: Рабочая отправка в Telegram
Нормативный уровень: MUST.
Канал Telegram ДОЛЖЕН отправлять реальные HTTP POST в Telegram Bot API через настроенный базовый адрес Cloudflare, используя токен и идентификатор канала из `.env`, переданные фабрикой из `src.config`. Текст доставляется методом `sendMessage`, график с подписью — `sendPhoto`; обновление существующей карточки выполняется через `editMessageCaption` либо `editMessageText` в зависимости от её исходного представления, навигация — через inline URL-кнопки. Получение метаданных канала выполняется через `getChat`. Таймаут одного HTTP-запроса по умолчанию 10 секунд. Успехом ДОЛЖЕН считаться только HTTP 200 с `ok=true`; идентификатор нового сообщения сохраняется только из подтверждённого результата API.

Публикация события ДОЛЖНА возвращаться немедленно: неизменяемое событие кладётся в ограниченную очередь, а форматирование, рендеринг, запись delivery-состояния и отправка выполняются единственным фоновым работником. Порядок обработки ДОЛЖЕН соответствовать порядку публикации. При переполнении очереди ДОЛЖНО отбрасываться самое старое событие; отбрасывания агрегируются в предупреждение со счётчиком. Каждое новое событие содержит актуальный снимок сделки, чтобы потеря промежуточного события не превращала свежий статус в старый.

Текст ДОЛЖЕН укладываться в лимит 4096 символов, подпись фотографии — в 1024 символа по правилам Telegram. Длинные подробности отправляются текстовыми продолжениями по границам строк, с сохранением порядка и корректного HTML; строка длиннее лимита режется принудительно без разрыва HTML-сущности или тега. Основная карточка сохраняет инструмент, статус, вход/стоп, краткую сводку целей и навигацию; продолжение содержит не уместившиеся детали. Динамические значения ДОЛЖНЫ экранироваться; визуальные сообщения используют только поддерживаемую Telegram HTML-разметку.

Неуспешный HTTP/`ok=false`, включая 429, ДОЛЖЕН фиксироваться в модульном логгере без вывода в stdout. `retry_after` из ответа 429 ДОЛЖЕН попадать в запись логгера. Сетевое исключение ДОЛЖНО перехватываться без прерывания работы бота. Автоматических повторных запросов после ошибки либо неопределённого результата НЕ ДОЛЖНО быть. Локальная невозможность построить график до HTTP допускает одно текстовое представление того же события; сетевой таймаут `sendPhoto` НЕ ДОЛЖЕН запускать вторую публикацию `sendMessage`.

Ответ «message is not modified» на редактирование ДОЛЖЕН считаться безвредным результатом. Сбой редактирования карточки НЕ ДОЛЖЕН создавать её копию или препятствовать последующим независимым событиям. Остановка ДОЛЖНА дренировать очередь за отведённое время (по умолчанию 5 секунд), а недренированный остаток — отбрасываться с предупреждением.

#### Scenario: Успешная отправка
- **WHEN** канал получает текстовое событие при настроенном Telegram
- **THEN** выполняется HTTP POST `sendMessage` через настроенный адрес с `chat_id`, текстом и таймаутом 10 секунд; HTTP 200 с `ok=true` подтверждает доставку

#### Scenario: Публикация не ждёт сеть
- **WHEN** сеть или рендеринг медленны и канал получает событие
- **THEN** вызывающий поток возвращается сразу, визуализация и отправка выполняются фоновым работником

#### Scenario: Некорректный ответ API
- **WHEN** Telegram отвечает HTTP не 200 либо HTTP 200 с `ok=false`
- **THEN** записывается ошибка без секретов, неподтверждённый message_id не сохраняется; работа продолжается

#### Scenario: Ответ 429 не повторяется
- **WHEN** Telegram отвечает `429` с `retry_after`
- **THEN** запрос выполняется один раз, `retry_after` попадает в логгер

#### Scenario: Сетевое исключение
- **WHEN** запрос завершается исключением или таймаутом
- **THEN** ошибка записывается в логгер, повтор или альтернативная публикация не выполняются; бот продолжает работу

#### Scenario: Длинное сообщение разбивается
- **WHEN** HTML-текст или подпись превышают соответствующий лимит
- **THEN** подробности переносятся в корректные текстовые продолжения в исходном порядке без разрыва тегов, сущностей и потери фактов

#### Scenario: Переполнение очереди
- **WHEN** очередь заполнена, а приходит новое событие
- **THEN** самое старое событие отбрасывается, новое ставится в очередь, в логгер пишется предупреждение со счётчиком

#### Scenario: Остановка дренирует очередь
- **WHEN** канал закрывается при непустой очереди
- **THEN** события обрабатываются за отведённое время; неотправленный остаток отбрасывается с предупреждением

#### Scenario: Дефолтные токены из .env
- **WHEN** фабрика создаёт Telegram-канал
- **THEN** она передаёт значения из `.env`, загруженные `src.config`; канал самостоятельно конфигурацию не читает

#### Scenario: Фото и подтверждение публикации
- **WHEN** готов график сделки и API подтверждает `sendPhoto`
- **THEN** отправлены фото, HTML-подпись и кнопки; возвращённый message_id становится доступным для последующей навигации

#### Scenario: Повторное редактирование без изменений
- **WHEN** API возвращает «message is not modified» для карточки
- **THEN** существующий пост сохраняется, копия карточки не публикуется

### Requirement: Консольный канал доставки
Нормативный уровень: MUST.
Система ДОЛЖНА предоставлять консольный канал `ConsoleChannel`: доставка сообщения — вывод текста в stdout, сетевые вызовы отсутствуют. Канал ДОЛЖЕН быть подписан на все типы каталога по умолчанию и доставлять событие синхронно, в вызывающем потоке. Канал ДОЛЖЕН игнорировать события, не входящие в его набор типов.

#### Scenario: Сообщение печатается
- **WHEN** консольный канал получает событие
- **THEN** текст сообщения выводится в stdout

#### Scenario: Событие неподдерживаемого типа пропускается
- **WHEN** в наборе типов канала событие отсутствует
- **THEN** событие игнорируется, вывода нет

### Requirement: Фабрика выбора канала
Нормативный уровень: MUST.
Пакет `src/notifier` ДОЛЖЕН предоставлять фабрику `build_channels()`, собирающую экземпляры каналов для списка из конфигурационной константы `NOTIFIER_CHANNELS` в порядке конфигурации; допустимые значения — `"telegram"` и `"console"`. Неизвестное значение ДОЛЖНО завершаться ошибкой с перечнем доступных каналов. Пустой список активных каналов ДОЛЖЕН отвергаться загрузкой конфигурации.

Фабрика ДОЛЖНА подписывать собранные каналы на шину в порядке конфигурации. Telegram ДОЛЖЕН создаваться ненастроенным без ошибки (см. «Проверка конфигурации Telegram»).

Остановка каналов ДОЛЖНА быть отдельной операцией `close_channels()`: каждый канал закрывается с таймаутом, ошибка одного канала при остановке НЕ ДОЛЖНА мешать остановке остальных.

#### Scenario: Выбран Telegram
- **WHEN** `NOTIFIER_CHANNELS=["telegram"]` и вызывается фабрика
- **THEN** возвращается список с единственным экземпляром канала Telegram

#### Scenario: Выбрана консоль
- **WHEN** `NOTIFIER_CHANNELS=["console"]` и вызывается фабрика
- **THEN** возвращается список с единственным экземпляром консольного канала

#### Scenario: Несколько каналов
- **WHEN** `NOTIFIER_CHANNELS=["console", "telegram"]`
- **THEN** возвращаются оба канала в порядке конфигурации и подписываются на шину в том же порядке

#### Scenario: Неизвестный канал
- **WHEN** список содержит незарегистрированное имя канала
- **THEN** выбрасывается ошибка с перечнем доступных каналов

### Requirement: Паттерн разводки уведомлений
Нормативный уровень: MUST.
Разводка уведомлений по каналам ДОЛЖНА быть построена строго на **Observer (GoF) + Publish/Subscribe (POSA)**. Обязательные следствия паттерна:
- издатель события НЕ ДОЛЖЕН знать, какие каналы существуют, сколько их и кто они;
- канал-подписчик ДОЛЖЕН получать событие и самостоятельно решать, относится ли оно к его набору типов;
- доставка ДОЛЖНА быть неблокирующей для издателя: публикация события НЕ ДОЛЖНА ждать завершения сетевой доставки;
- подписка и отписка ДОЛЖНЫ быть независимыми от формата события.

Прямое обращение издателя к конкретному каналу и обращение канала к издателю ДОЛЖНЫ быть запрещены.

#### Scenario: Добавление канала не трогает издателя
- **WHEN** в конфигурации добавлен третий канал, а код торговой логики не менялся
- **THEN** новый канал получает события без правок в коде издателя

#### Scenario: Издатель не знает про каналы
- **WHEN** разработчик читает модуль, публикующий событие
- **THEN** в нём нет упоминаний конкретного канала

#### Scenario: Публикация не ждёт сеть
- **WHEN** канал Telegram отвечает медленно
- **THEN** публикация возвращается немедленно и не блокирует торговый цикл

### Requirement: Шина событий не зависит от предметной области
Нормативный уровень: MUST.
Шина событий ДОЛЖНА быть общим механизмом обмена. Ни `EventBus`, ни `Event`, ни `EventType` НЕ ДОЛЖНЫ содержать сведений о торговле, каналах, шаблонах или форматировании. Доставка — «не более одного раза».

#### Scenario: Переиспользование шины
- **WHEN** модуль публикует событие, не относящееся к уведомлениям
- **THEN** событие доставляется подписчикам без изменения кода шины

#### Scenario: Шина свободна от торговых терминов
- **WHEN** разработчик читает пакет шины событий
- **THEN** в нём нет торговых терминов

### Requirement: Событие неизменяемо и самодостаточно
Нормативный уровень: MUST.
Событие ДОЛЖНО быть неизменяемым, включая вложенные коллекции визуального контекста. Оно ДОЛЖНО содержать все данные для отображения, включая короткое имя контракта: для фьючерсов — в формате `NG-10.26`, для акций — тикер акции (`SBER`, `GAZP`, `LKOH`). Запрет на сырой биржевой тикер относится к инструментам с отдельным кодом контракта и НЕ распространяется на акции. Сериализуемая форма описывается схемой в `docs/notification/event-schemas.md`; расхождение со схемой ДОЛЖНО приводить к падению сборки.

Для визуальных торговых уведомлений событие ДОЛЖНО содержать ограниченный снимок доступных на момент события свечей, первоначальный план с упорядоченными целями и целыми аллокациями, текущий подтверждённый остаток/среднюю входа/стоп, последовательность фактических исполнений и подтверждённых переносов, финансовые суммы и происхождение комиссий. Внутренние ключи сделки, события и ревизии служат корреляции и дедупликации, не пользовательскому тексту. Неизвестные/отсутствующие значения не подменяются нулём. Совместимость со старыми событиями без визуального контекста ДОЛЖНА сохраняться через текстовое представление.

Канал НЕ ДОЛЖЕН запрашивать брокера, торговую базу или историю свечей ради построения сообщения. Он допускает только собственное delivery-хранилище подтверждённых Telegram-ссылок и попыток, не источник финансовой истины, и явно переданные настройки транспорта/пояса времени.

#### Scenario: Канал получает всё в событии
- **WHEN** канал обрабатывает визуальное событие
- **THEN** цена, свечи, план, объёмы, исполнения и деньги берутся из его снимка; торговая база и брокер не опрашиваются

#### Scenario: Сырой тикер не попадает
- **WHEN** событие содержит короткое имя `NG-10.26`
- **THEN** пользовательский текст и график не содержат биржевого тикера `NGU6`

#### Scenario: Имя контракта, введённого вручную, берётся из каталога
- **WHEN** фьючерс выбран вводом тикера вручную, а не номером из списка
- **THEN** короткое имя берётся из каталога без дополнительных запросов; при его отсутствии показывается `контракт не указан`

#### Scenario: Акция называется своим тикером
- **WHEN** событие по акции `SBER` не содержит явно заданного короткого имени
- **THEN** событие и пользовательское представление используют `SBER`, не заглушку

#### Scenario: Дрейф схемы ломает сборку
- **WHEN** событие изменило структуру относительно схемы, включая вложенный визуальный снимок
- **THEN** проверка сборки падает

#### Scenario: Источник не меняет событие после публикации
- **WHEN** исходный DataFrame или список исполнений изменяется после публикации
- **THEN** ранее опубликованный снимок и его график не изменяются

#### Scenario: Старое событие без свечей
- **WHEN** совместимое событие не содержит визуального снимка
- **THEN** канал отправляет доступные факты текстом, не загружает и не выдумывает свечи

### Requirement: Каталог типов событий
Нормативный уровень: MUST.
Каталог сохраняет 19 типов с видимостью по каналам. Консоль по умолчанию получает все типы; Telegram — девять lifecycle-типов: `signal`, `trade_opened`, `position_added`, `stop_hit`, `target_hit`, `stop_moved`, `trade_closed`, `trade_cancelled`, `order_rejected`. Отмена/отклонение заявки актуализируют карточку с учётом её текущего состояния, а не автоматически означают закрытие уже открытой позиции. Явно заданные пользователем наборы типов ДОЛЖНЫ сохраняться без скрытого добавления подписок.

| Тип | Консоль | Telegram по умолчанию | Источник |
|---|---|---|---|
| `decision` | ✓ | — | решение стратегии |
| `signal` | ✓ | ✓ | допуск пройден |
| `trade_opened` | ✓ | ✓ | подтверждённое исполнение |
| `position_added` | ✓ | ✓ | подтверждённое исполнение |
| `stop_hit` | ✓ | ✓ | подтверждённое исполнение |
| `target_hit` | ✓ | ✓ | подтверждённое исполнение |
| `trade_closed` | ✓ | ✓ | подтверждённое исполнение |
| `rejected` | ✓ | — | допуск |
| `trade_cancelled` | ✓ | ✓ | подтверждённая отмена |
| `order_accepted` | ✓ | — | подтверждение заявки |
| `order_rejected` | ✓ | ✓ | подтверждённый отказ заявки |

#### Scenario: Состав по умолчанию
- **WHEN** наборы типов не переопределены
- **THEN** консоль получает все 19 типов, Telegram — девять перечисленных lifecycle-типов

#### Scenario: Отказ не попадает в Telegram
- **WHEN** сигнал не допущен
- **THEN** `rejected` идёт в консоль, Telegram не получает его и не создаёт карточку

#### Scenario: Явный список событий сохраняется
- **WHEN** пользователь оставил Telegram только `signal` и `trade_closed`
- **THEN** остальные типы не доставляются скрыто; доступные карточки и итоги работают без обязательного промежуточного поста

### Requirement: Раздельные точки публикации сигнала и решения
Нормативный уровень: MUST.
`decision` публикуется на этапе решения стратегии (до расчёта размера). `signal` публикуется после допуска и построения плана (со стопом, целями, объёмом, ожидаемым R). `signal` не публикуется при отказе допуска.

#### Scenario: Без допуска рекомендация не публикуется
- **WHEN** стратегия дала сигнал, но допуск не пройден
- **THEN** Telegram не получает `signal`

#### Scenario: Рекомендация содержит план
- **WHEN** допуск пройден
- **THEN** `signal` содержит стоп, цели, объём и ожидаемый результат в R

### Requirement: Порт канала уведомлений
Нормативный уровень: MUST.
Абстракция канала ДОЛЖНА объявлять `supported_types` и ДОЛЖНА иметь абстрактный метод обработки события. Создание экземпляра абстракции, как и создание наследника без переопределения метода обработки, ДОЛЖНО завершаться ошибкой.

#### Scenario: Канал фильтрует по типу
- **WHEN** канал подписан на ограниченный набор типов
- **THEN** события других типов игнорируются

#### Scenario: Абстрактный канал нельзя инстанцировать
- **WHEN** создаётся экземпляр абстрактного канала
- **THEN** выбрасывается ошибка

### Requirement: Шаблон принадлежит каналу
Нормативный уровень: MUST.
Представление события ДОЛЖНО определяться шаблоном внутри канала; общий форматтер ЗАПРЕЩЁН. Telegram ДОЛЖЕН иметь собственные HTML-шаблоны и визуальное представление карточек; консоль сохраняет существующие текстовые шаблоны и финансовые обозначения. Совпадение шаблонов Telegram и консоли больше не является контрактом. Данные событий и расчётные финансовые факты общие, формат отображения и delivery-корреляция принадлежат каналу.

#### Scenario: Представление зависит от канала
- **WHEN** Telegram показывает график с русскими подписями и HTML
- **THEN** консоль получает прежний текст без HTML, кнопок и изменений финансовых величин

### Requirement: Торговые события публикуются по подтверждению брокера
Нормативный уровень: MUST.
Торговое событие (`trade_opened`, `position_added`, `stop_hit`, `target_hit`, `trade_closed`, `order_accepted`, `order_rejected`, `trade_cancelled`, `protection_armed`, `stop_moved`, `risk_limit_hit`, `clearing_done`, `reservation_changed`) ДОЛЖНО публиковаться только после подтверждения исхода, не в момент постановки заявки или намерения исполнителя. Подтверждённый исход — источник истины для уведомления; финансовые и защитные факты обогащаются после применения результата к состоянию сделки.

Редьюсер НЕ ДОЛЖЕН публиковать уведомления в шину. Владелец lifecycle ДОЛЖЕН составлять самодостаточный структурированный снимок после фиксации факта; повторное применение того же execution/ACK не публикует второе событие. Шина служит представлению, а не управлению защитой или торговыми решениями.

`stop_moved` ДОЛЖЕН содержать прежний и новый подтверждённые уровни и момент вступления изменения в силу. Pending-stop НЕ ДОЛЖЕН заменять действующий стоп в карточке или на графике. Подтверждение с отложенной активацией публикуется как состоявшийся перенос только после достижения момента действия.

#### Scenario: Заявка не подтверждена — уведомления о сделке нет
- **WHEN** исполнитель поставил заявку, но подтверждённого исхода нет
- **THEN** `trade_opened` и `order_accepted` не публикуются; пользователь видит рекомендацию `signal` с ожиданием подтверждения

#### Scenario: Журнал не публикует уведомления
- **WHEN** редьюсер зафиксировал событие в базе
- **THEN** он сам не отправляет события в шину; публикацию выполняет владелец lifecycle после применения факта

#### Scenario: Подтверждённый исход приходит один раз
- **WHEN** подтверждённый результат повторно доставлен после рестарта
- **THEN** повторное применение не публикует второе событие, детали исходного факта сохраняются

#### Scenario: Pending-стоп не объявлен действующим
- **WHEN** запрошен перенос с 297.00 на 297.25, но он ещё не вступил в силу
- **THEN** карточка и график сохраняют 297.00 как действующий уровень и не сообщают «СТОП перенесён и подтверждён»

#### Scenario: Перенос вступил в силу
- **WHEN** подтверждено вступление нового стопа 297.25 в силу
- **THEN** публикуется один `stop_moved` с прежним 297.00, новым 297.25 и effective time

### Requirement: Неблокирующая доставка и изоляция ошибок
Нормативный уровень: MUST.
Публикация не прерывается ошибкой одного канала. Ошибка фиксируется в логге, доставка остальным каналам продолжается. Семантика — «не более одного раза».

#### Scenario: Сбой канала не мешает другим
- **WHEN** Telegram выбрасывает исключение
- **THEN** консоль получает событие, ошибка записана в лог

#### Scenario: Ошибка не влияет на торговлю
- **WHEN** каналы выбрасывают исключения
- **THEN** торговый цикл продолжает работу

### Requirement: Прямая публикация событий без слоя перевода
Нормативный уровень: MUST.
Торговый контур ДОЛЖЕН публиковать события в шину напрямую. Методов `notify_decision`, `notify_plan`, `notify_entry_accepted`, `notify_rejection`, `notify_event` в API ДОЛЖНО НЕ оставаться: переходный слой перевода, введённый предыдущим change, удаляется вместе с ним.

Модуль, публикующий событие, ДОЛЖЕН использовать конструктор типа события из каталога и ДОЛЖЕН передавать данные, достаточные для представления. Публикация ДОЛЖЕН оставаться синхронной и неблокирующей для торгового цикла, как требует требование «Неблокирующая доставка и изоляция ошибок».

#### Scenario: Бот публикует напрямую
- **WHEN** `_admit_candidate` получает допущенный план
- **THEN** бот публикует событие `signal` в шину, отдельного посредника вызова нет

#### Scenario: Слоя перевода в API нет
- **WHEN** разработчик ищет метод `notify_decision`
- **THEN** такого метода в проекте не существует

#### Scenario: Решения не теряют тип
- **WHEN** публикуется решение стратегии
- **THEN** тип события задан конструктором каталога, а не строковым параметром

### Requirement: События исполнителя структурированы
Нормативный уровень: MUST.
Событие, которое исполнитель сообщает наружу для уведомления, ДОЛЖНО быть структурированным: тип из каталога, время, идентификатор сделки и набор полей (сторона, объём, цена, идентификатор заявки, причина, финансовый результат). Текст сообщения ДОЛЖЕН формироваться шаблоном канала; сборка русских фраз в слое исполнителя или в моделях предметной области ЗАПРЕЩЕНА.

Один тип события ДОЛЖЕН соответствовать одному смыслу. Исполнитель ДОЛЖЕН различать принятие заявки и её отклонение, вход, срабатывание цели, срабатывание стопа и прочее закрытие позиции; передача типа значением переменной вместо значения из каталога ЗАПРЕЩЕНА.

Идентификатор позиции ДОЛЖЕН отсутствовать в уведомляющем событии как поле представления; `trade_id` ДОЛЖЕН оставаться во внутренней части события для корреляции и ДОЛЖЕН НЕ выводиться в текст сообщения.

#### Scenario: Исполнитель не формирует текст
- **WHEN** исполнитель сообщает о размещении заявки
- **THEN** он передаёт тип, цену, объём, сторону и идентификатор заявки, а не готовую фразу

#### Scenario: Вход и выход различаются
- **WHEN** исполнитель сообщает об исполнении
- **THEN** тип события один из `trade_opened`, `target_hit`, `stop_hit`, `trade_closed`, а не общий «fill»

#### Scenario: Принятие и отклонение различаются
- **WHEN** заявка размещена либо отклонена
- **THEN** тип события `order_accepted` либо `order_rejected` соответственно

#### Scenario: Тип не подставляется значением
- **WHEN** исполнитель сообщает о закрытии позиции
- **THEN** передаётся значение типа из каталога, а не строка, вычисленная по другому признаку

#### Scenario: Идентификатор сделки не виден пользователю
- **WHEN** канал формирует сообщение о закрытии
- **THEN** `trade_id` присутствует во внутренней части события и отсутствует в тексте

### Requirement: Шина не используется как шина управления
Нормативный уровень: MUST.
Шина событий ДОЛЖНА обслуживать доставку уведомлений и ДОЛЖНА НЕ использоваться для управления торговым контуром. Обработка события исполнения, применение post-fill проверок, запись решения-трейса и обновление проекций журнала ДОЛЖНЫ выполняться прямыми вызовами в определённом порядке, а не доставкой подписчикам.

Порядок «редьюсер применяет событие, затем менеджер выполняет post-fill действия» ДОЛЖЕН сохраняться: нарушение порядка привело бы к решениям по ещё не записанному состоянию.

#### Scenario: Post-fill проверки не уходят в шину
- **WHEN** исполнение применено редьюсером
- **THEN** менеджер выполняет post-fill проверки прямой вызовой сразу после применения, до любой доставки подписчикам

#### Scenario: Управление не размазывается по подписчикам
- **WHEN** разработчик ищет подписчика, изменяющего состояние сделки
- **THEN** таких подписчиков нет: изменение состояния выполняет владелец состояния

### Requirement: Экономический недопуск имеет русский смысл и код
Нормативный уровень: MUST.
Экономические причины ДОЛЖНЫ доставляться существующим форматом недопуска, с коротким инструментом и контекстом сигнала. Код сохраняется в структурированном событии; пользователь получает русский текст и проверяемые денежные величины/порог: `risk-cost-ratio` — «риск до стопа слишком мал относительно издержек», `slippage-risk-ratio` — «запас проскальзывания превышает допустимую долю риска», `payoff-below-floor` — «чистая плановая прибыль относительно риска ниже порога», `stop-bounds-conflict` — «минимальное расстояние стопа превышает допустимый потолок». Старые `cost-exceeds-reward`, `risk-below-floor`, бюджетные и структурные причины сохраняются. Низкий положительный payoff НЕ ДОЛЖЕН называться гарантированным убытком, а свечное отклонение — доказанной неликвидностью стакана.

#### Scenario: Малый риск без целей
- **WHEN** вход VTBR с R=4.85 ₽ и C=40 ₽ отклонён по R/C
- **THEN** сообщение на русском объясняет соотношение и порог 2; не утверждает payoff=0.21

#### Scenario: Положительный payoff ниже порога
- **WHEN** P=1.4 при пороге 1.5
- **THEN** событие содержит `payoff-below-floor`, текст говорит о недостаточном отношении, не о заведомом убытке

#### Scenario: Бюджетный отказ сохраняется
- **WHEN** sizing не допускает положительного объёма из-за ACTIVE-резервов маржи
- **THEN** остаётся конкретная бюджетная причина, а не подмена экономическим кодом

### Requirement: Общий риск и превышение видны пользователю
Нормативный уровень: MUST.
Диагностика допуска ДОЛЖНА показывать базу капитала, эффективный общий процент, денежный бюджет, риск открытых остатков, незаполненные резервы, свободный остаток и итоговое количество/ограничение. Дефолт 2% ДОЛЖЕН обозначаться общим для счёта, не индивидуальным. Если после подтверждённого события либо изменения B риск выше лимита, сообщение ДОЛЖНО называть занятую сумму, лимит, превышение и запрет новых входов/доборов; оно не заявляет автоматическое закрытие позиций ради бюджета. Неизвестный риск имеет код risk-state-unknown и русский текст с причиной неизвестности.

#### Scenario: Превышение не является продажей
- **WHEN** занято 2100 ₽ при бюджете 2000 ₽
- **THEN** диагностика сообщает превышение 100 ₽ и блокировку новых увеличений, без утверждения о принудительном сокращении

#### Scenario: Один лимит для разных стратегий
- **WHEN** несколько стратегий заняли 1700 ₽ при общем бюджете 2000 ₽
- **THEN** свободный остаток показан как 300 ₽, а не новый бюджет 2000 ₽ каждому сигналу

#### Scenario: Неизвестный риск имеет объяснение
- **WHEN** новый вход отклонён из-за отсутствующего подтверждённого стопа старой позиции
- **THEN** пользователь получает русское описание risk-state-unknown и доступные данные общего бюджета

### Requirement: Консольный отчёт согласован с портфельным бюджетом
Нормативный уровень: MUST.
`tools/show_state.py` ДОЛЖЕН читать единственный процент `portfolio_pct` и строить отчёт из одного согласованного read-only снимка SQLite. База B, текущий риск фактических остатков, будущие расходы и незаполненные ACTIVE-резервы ДОЛЖНЫ соответствовать требованиям единого бюджета в `risk-management`, независимо от версии профиля. В отчёте видны общий процент, денежный лимит, открытый риск, pending-риск, свободный остаток и превышение; отдельные процентные лимиты сделки/инструмента не читаются и не выводятся.

Pending-stop ДОЛЖЕН показываться только как ожидаемое намерение и НЕ ДОЛЖЕН заменять confirmed_stop в денежном расчёте. Неизвестные необходимые стопы, сохранённые денежные факторы либо суммы НЕ ДОЛЖНЫ превращаться в нулевой занятый риск или достоверный свободный бюджет: отчёт явно сообщает `risk-state-unknown`, причину и доступную известную часть. Неизвестное обеспечение открытых позиций также обозначается отдельно, без фиктивной нулевой суммы. Legacy-оценка будущих расходов ДОЛЖНА быть явно подписана и не выдаваться за историческую фактическую комиссию.

Отчёт ДОЛЖЕН сохранять короткие пользовательские имена, диагностику активных/осиротевших резервов и последние отказы. Чтение НЕ ДОЛЖНО мигрировать или менять базу, переписывать планы/fees, освобождать резервы, отправлять заявки или инициировать закрытие позиций. Превышение означает видимую блокировку новых допусков, а не выполненную ликвидацию.

#### Scenario: Отчёт запускается с новой конфигурацией
- **WHEN** заданы portfolio_pct=2 и оценки расходов без trade_pct/instrument_pct/groups
- **THEN** отчёт запускается и показывает единый общий лимит 2%, не требует удалённых ключей

#### Scenario: Открытый риск и pending считаются вместе
- **WHEN** B=100000 ₽, общий процент 2%, открытые остатки занимают 1200 ₽ и незаполненные резервы 500 ₽
- **THEN** отчёт показывает бюджет 2000 ₽, занято 1700 ₽ и свободно 300 ₽

#### Scenario: Прибыльный подтверждённый стоп
- **WHEN** у LONG E=100, confirmed_stop=105, V=100, q=1 и будущие расходы 2 ₽
- **THEN** отчёт показывает ценовой риск 0 и бюджетный риск 2 ₽, не модуль 500 ₽ и не первоначальный стоп; SHORT рассчитывается зеркально

#### Scenario: Pending-защита не освобождает риск
- **WHEN** у LONG E=100, V=100, q=1 активен confirmed_stop=96 и запрошен pending_stop=100
- **THEN** ценовой риск остаётся 400 ₽ до подтверждения, ожидаемый стоп показан отдельно; отсутствие confirmed_stop даёт unknown-state

#### Scenario: Legacy и новая эпоха в одном отчёте
- **WHEN** вместе читаются legacy и economics-v2 остатки с сохранёнными факторами и резервы
- **THEN** они входят в один общий бюджет; оценка будущих legacy-расходов подписана, старые fees и планы не меняются

#### Scenario: Уменьшение базы показывает превышение
- **WHEN** при открытом риске 2100 ₽ актуальный B и portfolio_pct дают лимит 2000 ₽
- **THEN** отчёт показывает превышение 100 ₽, свободный риск 0 и запрет новых увеличений без закрывающей команды

#### Scenario: Неизвестные суммы не дают фиктивного остатка
- **WHEN** у открытой позиции отсутствует confirmed_stop или сохранённый денежный фактор
- **THEN** отчёт показывает risk-state-unknown с причиной и известные компоненты, не выдаёт неполную сумму за свободный бюджет

#### Scenario: Чтение не изменяет журнал
- **WHEN** отчёт выполнен на базе с открытыми позициями, ACTIVE-резервами и последними отказами
- **THEN** хеш базы до и после чтения совпадает, факты и резервы сохранены, инструменты выведены короткими именами
