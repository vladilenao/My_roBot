# Уведомления

## Purpose

Доставляет сообщения с торговыми сигналами через выбранный в конфигурации канал — Telegram Bot API или stdout. Решение форматируется внедрённым форматтером; когда Telegram не настроен — выводится предупреждение и HTTP-запрос пропускается.

## Requirements

### Requirement: Иерархия нотификаторов
Пакет `src/notifier` ДОЛЖЕН предоставлять абстрактный класс `AbstractNotifier`: метод `notify(message)` — абстрактный, принимает только готовый текст сообщения; метод `notify_decision(decision, instrument_label="", *, filter_profile="", filtered_out=False, timeframe="")` — конкретный, форматирует решение через внедрённый форматтер и доставляет результат через `notify`. Форматтер ДОЛЖЕН внедряться через конструктор нотификатора; по умолчанию используется `DecisionFormatter`. Создание экземпляра `AbstractNotifier` и наследника без реализации `notify` ДОЛЖНО завершаться ошибкой. Форматтер ДОЛЖЕН выдавать компактную однострочную строку вида `● <инструмент> (<таймфрейм>) HH:MM | <стратегия> [<профиль>] ➜ <сигнал>`, где `<инструмент>` — краткое имя инструмента (`instrument_label`), `<таймфрейм>` — таймфрейм задачи, переданный параметром вызова, `HH:MM` — время последнего бара (поле `bar_time` решения), `<стратегия>` — имя стратегии, `<профиль>` — профиль фильтрации задачи; при отсутствии `bar_time`, имени стратегии, профиля или таймфрейма их блоки в строке ДОЛЖНЫ опускаться.

#### Scenario: Мостик от решения к доставке
- **WHEN** вызывается `notify_decision` с решением BUY, кратким именем инструмента «NG-10.26», таймфреймом задачи `15m`, именем стратегии `macd_rsi_stoch`, профилем `raw` и `bar_time` 22:00
- **THEN** нотификатор доставляет отформатированное решение текстом `● NG-10.26 (15m) 22:00 | macd_rsi_stoch [raw] ➜ 🟢 ПОКУПКА (BUY) — Цена: X` единственным вызовом `notify`

#### Scenario: Абстрактный класс нельзя инстанцировать
- **WHEN** выполняется попытка создания экземпляра `AbstractNotifier`
- **THEN** выбрасывается ошибка (класс абстрактный)

#### Scenario: Наследник обязан реализовать notify
- **WHEN** создаётся наследник без переопределения `notify`
- **THEN** создание экземпляра завершается ошибкой

#### Scenario: Подмена форматтера
- **WHEN** в конструктор нотификатора передан альтернативный форматтер
- **THEN** `notify_decision` форматирует решение им, а не `DecisionFormatter` по умолчанию

### Requirement: Компактный формат сигналов
`DecisionFormatter` ДОЛЖЕН оформлять каждое решение одной строкой. Для BUY — `🟢 ПОКУПКА (BUY) — Цена: X`; для SELL — `🔴 ПРОДАЖА (SELL) — Цена: X`; для HOLD — `⏳ Нет сигнала.` без цены; для отклонённого фильтром решения (`filtered_out=True`) — `❌ Отклонено фильтром.` без цены. Строка ДОЛЖНА начинаться с маркера `● `; за маркером ДОЛЖЕН следовать `<инструмент>`, к которому через один пробел добавляется блок таймфрейма `(<таймфрейм>)` при наличии заданного задаче таймфрейма; блок времени бара `HH:MM` и блок стратегии `| <имя>` включаются только при наличии соответствующих значений; блок профиля фильтрации `[<профиль>]` ДОЛЖЕН следовать за блоком стратегии и включается только при наличии значения профиля.

Значение `bar_time` решения ДОЛЖНО представлять момент ЗАКРЫТИЯ свечи последнего бара, а не момент её начала: момент начала бара в tz-naive UTC, сложенный с длительностью периода таймфрейма. Блок времени `HH:MM` ДОЛЖЕН отображать `bar_time` в локальном часовом поясе пользователя: к значению применяется сконфигурированное смещение от UTC, заданное в часах. При нулевом смещении выводится UTC-время закрытия без изменений.

#### Scenario: Покупка
- **WHEN** решение имеет тип BUY, цену X, время закрытия бара 22:00, стратегию `macd_rsi_stoch`, профиль `raw`, а таймфрейм задачи `15m`
- **THEN** сообщение равно `● <инструмент> (15m) 22:00 | macd_rsi_stoch [raw] ➜ 🟢 ПОКУПКА (BUY) — Цена: X`

#### Scenario: Продажа
- **WHEN** решение имеет тип SELL, цену X, время закрытия бара 22:00, стратегию `macd_rsi_stoch`, профиль `basic_levels`, а таймфрейм задачи `1h`
- **THEN** сообщение равно `● <инструмент> (1h) 22:00 | macd_rsi_stoch [basic_levels] ➜ 🔴 ПРОДАЖА (SELL) — Цена: X`

#### Scenario: Нет сигнала
- **WHEN** решение имеет тип HOLD
- **THEN** сообщение содержит `⏳ Нет сигнала.` и не содержит цены

#### Scenario: Отклонено фильтром
- **WHEN** решение доставляется с признаком `filtered_out=True`
- **THEN** сообщение содержит статус `❌ Отклонено фильтром.` и не содержит цены

#### Scenario: Нет профиля фильтрации
- **WHEN** профиль фильтрации не задан (пустое значение)
- **THEN** блок `[<профиль>]` в строке опускается

#### Scenario: Нет времени бара
- **WHEN** решение не имеет `bar_time`
- **THEN** блок времени в строке опускается (нет `HH:MM`)

#### Scenario: Нет имени стратегии
- **WHEN** решение не имеет имени стратегии
- **THEN** блок `| <имя>` в строке опускается

#### Scenario: Нет таймфрейма
- **WHEN** задаче не задан таймфрейм (пустое значение параметра)
- **THEN** блок `(<таймфрейм>)` в строке опускается, маркер `● ` и `<инструмент>` выводятся без него

#### Scenario: Время в локальном поясе
- **WHEN** смещение часового пояса задано, например `+3` часа, а `bar_time` равен `06:00` UTC (момент закрытия свечи)
- **THEN** в сообщении блок времени выводится как `09:00` (к значению закрытия прибавлено смещение)

#### Scenario: Нулевое смещение сохраняет UTC
- **WHEN** смещение часового пояса равно `0`, а `bar_time` равен `06:00` UTC (момент закрытия свечи)
- **THEN** блок времени выводится как `06:00` (UTC-время закрытия без изменений)

### Requirement: Формат уведомления о недопуске сделки
Нотификатор ДОЛЖЕН уметь отображать недопуск сделки сообщением вида `⛔ <инструмент> (<таймфрейм>) HH:MM | <стратегия> [<профиль>] ➜ Сделка не допущена: <причина>`, где `<инструмент>` — краткое имя инструмента (short name, например `NG-10.26`), `<таймфрейм>` — таймфрейм задачи (блок опускается при отсутствии), `HH:MM` — время закрытия последнего бара в локальном поясе (блок опускается при отсутствии), `<стратегия>` — имя стратегии (блок опускается при отсутствии), `<профиль>` — профиль фильтрации (блок опускается при отсутствии), `<причина>` — человекочитаемое описание причины недопуска на русском. Маркер `⛔ ` ДОЛЖЕН отличать сообщение о недопуске от обычных сигналов (`● `). Формат обычных сигналов НЕ изменяется.

#### Scenario: Недопуск из-за нулевого объёма
- **WHEN** решение BUY по привязке `15m`/`macd_rsi_stoch`/`basic_levels` не допущено с причиной «Объём позиции ниже минимального»
- **THEN** доставленное сообщение равно `⛔ <инструмент> (15m) | macd_rsi_stoch [basic_levels] ➜ Сделка не допущена: Объём позиции ниже минимального`

#### Scenario: Без таймфрейма, стратегии и профиля
- **WHEN** недопуск произошёл по решению без заданных таймфрейма, имени стратегии и профиля
- **THEN** сообщение содержит `⛔ <инструмент> ➜ Сделка не допущена: <причина>` без блоков `(таймфрейм)`, `| стратегия` и `[профиль]`

#### Scenario: Обычный сигнал сохраняет формат
- **WHEN** сигнал BUY допущен и доставляется как обычно
- **THEN** сообщение начинается с `●` и имеет прежний формат `🟢 ПОКУПКА (BUY) — Цена: X`, без маркера `⛔`

#### Scenario: Недопуск дублирующего сигнала
- **WHEN** повторный сигнал той же связки по тому же бару не допущен с причиной `duplicate-signal`
- **THEN** доставленное сообщение содержит маркер `⛔`, контекст задачи и причину «дублирующий сигнал, сделка не взята в работу»

### Requirement: Уведомление о принятой в работу сделке
Нормативный уровень: MUST.
После успешного допуска входа система ДОЛЖНА доставить трейдеру уведомление о принятой в работу сделке. Уведомление ДОЛЖНО содержать краткое имя инструмента, таймфрейм, направление и объём, плановые цену входа, стоп и цели, а также явное указание, что сделка находится в работе и заявка ждёт подтверждения. Уведомление НЕ ДОЛЖНО заявлять факт исполнения до подтверждения брокера и НЕ ДОЛЖНО подавлять обычное уведомление о сигнале.

#### Scenario: Успешный допуск входа
- **WHEN** кандидат допущен и создано действие открытия позиции по Si 5m, SELL, объём 7, план входа/стоп/цели заданы
- **THEN** трейдеру доставлено отдельное уведомление с кратким контрактом `Si-12.26`, таймфреймом, направлением, объёмом, плановыми уровнями и формулировкой «в работе, ждёт подтверждения»

#### Scenario: Исполнение ещё не подтверждено
- **WHEN** по принятой в работу сделке брокер ещё не подтвердил исполнение
- **THEN** текст уведомления описывает ожидание подтверждения и не утверждает, что позиция открыта

### Requirement: Проверка конфигурации Telegram
- Если `TELEGRAM_BOT_TOKEN` или `TELEGRAM_CHANNEL_ID` не заданы (None/пустые), Telegram-нотификатор ДОЛЖЕН вывести предупреждение в stdout и пропустить HTTP-запрос; дублирующий вывод сообщения в консоль при этом НЕ ДОЛЖЕН выполняться.

#### Scenario: Telegram не настроен
- **WHEN** токен или идентификатор канала равен `None`
- **THEN** выводится предупреждение «Telegram не настроен», HTTP-запрос не выполняется, эхо-печать сообщения отсутствует

### Requirement: Рабочая отправка в Telegram
Telegram-нотификатор ДОЛЖЕН отправлять сообщение реальным HTTP POST на `https://api.telegram.org/bot{token}/sendMessage` с параметрами `chat_id` (идентификатор канала) и `text` (сообщение) и таймаутом 10 секунд. Ответ со статусом, отличным от 200, ДОЛЖЕН фиксироваться записью с телом ответа; исключение сети ДОЛЖНО перехватываться с записью об ошибке без прерывания работы бота. Токен и идентификатор канала ДОЛЖНЫ браться из `.env` через `src.config` как дефолтные параметры конструктора.

#### Scenario: Успешная отправка
- **WHEN** нотификатор доставляет сообщение при настроенном Telegram
- **THEN** выполняется HTTP POST с `chat_id` и текстом сообщения, таймаут 10 секунд; ответ 200 не порождает ошибок

#### Scenario: Некорректный ответ API
- **WHEN** Telegram API отвечает статусом, отличным от 200
- **THEN** в stdout пишется ошибка с телом ответа; работа продолжается

#### Scenario: Сетевое исключение
- **WHEN** запрос завершается исключением (сеть/таймаут)
- **THEN** исключение перехватывается, в stdout пишется запись об ошибке; бот продолжает работу

#### Scenario: Дефолтные токены из .env
- **WHEN** нотификатор создан без явных параметров
- **THEN** используются значения из `.env`, загруженные `src.config`

### Requirement: Консольный канал доставки
Система ДОЛЖНА предоставлять консольный нотификатор: доставка сообщения — вывод текста в stdout, сетевые вызовы отсутствуют.

#### Scenario: Сообщение печатается
- **WHEN** консольный нотификатор доставляет сообщение
- **THEN** текст сообщения выводится в stdout

### Requirement: Фабрика выбора канала
Пакет `src/notifier` ДОЛЖЕН предоставлять фабрику `get_notifier()`, возвращающую экземпляр нотификатора для канала из конфигурационной константы `NOTIFIER`; допустимые значения — `"telegram"` и `"console"`. Неизвестное значение ДОЛЖНО завершаться ошибкой с перечнем доступных каналов.

#### Scenario: Выбран Telegram
- **WHEN** `NOTIFIER="telegram"` и вызывается фабрика
- **THEN** возвращается экземпляр Telegram-нотификатора

#### Scenario: Выбрана консоль
- **WHEN** `NOTIFIER="console"` и вызывается фабрика
- **THEN** возвращается экземпляр консольного нотификатора

#### Scenario: Неизвестный канал
- **WHEN** `NOTIFIER` содержит незарегистрированное значение
- **THEN** выбрасывается ошибка с перечнем доступных каналов
