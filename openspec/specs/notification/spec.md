# Уведомления

## Purpose

Доставляет сообщения с торговыми сигналами через выбранный в конфигурации канал — Telegram Bot API или stdout. Решение форматируется внедрённым форматтером; когда Telegram не настроен — выводится предупреждение и HTTP-запрос пропускается.

## Requirements

### Requirement: Компактный формат сигналов
Нормативный уровень: MUST.
Формат решения определяется шаблоном `src/notifier/templates/decision.py`, а не общим форматтером: за каждым каналом стоит свой шаблон, и общий форматтер запрещён. Каждое решение оформляется одной строкой. Для BUY — `🟢 ПОКУПКА (BUY) — Цена: X`; для SELL — `🔴 ПРОДАЖА (SELL) — Цена: X`; для HOLD — `⏳ Нет сигнала.` без цены; для отклонённого фильтром решения (`filtered_out=True`) — `❌ Отклонено фильтром.` без цены. Строка ДОЛЖНА начинаться с маркера `● `; за маркером ДОЛЖЕН следовать `<инструмент>`, к которому через один пробел добавляется блок таймфрейма `(<таймфрейм>)` при наличии заданного задаче таймфрейма; блок времени бара `HH:MM` и блок стратегии `| <имя>` включаются только при наличии соответствующих значений; блок профиля фильтрации `[<профиль>]` ДОЛЖЕН следовать за блоком стратегии и включается только при наличии значения профиля.

Значение `bar_time` решения ДОЛЖНО представлять момент ЗАКРЫТИЯ свечи последнего бара, а не момент её начала: момент начала бара в tz-naive UTC, сложенный с длительностью периода таймфрейма. Блок времени `HH:MM` ДОЛЖЕН отображать `bar_time` в локальном часовом поясе пользователя: к значению применяется сконфигурированное смещение от UTC, заданное в часах. При нулевом смещении выводится UTC-время закрытия без изменений.

#### Scenario: Покупка
- **WHEN** решение имеет тип BUY, цену X, время закрытия бара 22:00, стратегию `macd_rsi_stoch`, профиль `raw`, а таймфрейм задачи `15m`
- **THEN** сообщение равно `● <инструмент> (15m) 22:00 | macd_rsi_stoch [raw] ➜ 🟢 ПОКУПКА (BUY) — Цена: X`

#### Scenario: Продажа
- **WHEN** решение имеет тип SELL, цену X, время закрытия бара 22:00, стратегию `macd_rsi_stoch`, профиль `basic_levels`, а таймфрейм задачи `1h`
- **THEN** сообщение равно `● <инструмент> (1h) 22:00 | macd_rsi_stoch [basic_levels] ➜ 🔴 ПРОДАЖА (SELL) — Цена: X`

#### Scenario: Нет сигнала
- **WHEN** решение имеет тип HOLD
- **THEN** сообщение содержит `⏳ Нет сигнала.` и не содержит цены

#### Scenario: Отклонено фильтром
- **WHEN** решение доставляется с признаком `filtered_out=True`
- **THEN** сообщение содержит статус `❌ Отклонено фильтром.` и не содержит цены

#### Scenario: Нет профиля фильтрации
- **WHEN** профиль фильтрации не задан (пустое значение)
- **THEN** блок `[<профиль>]` в строке опускается

#### Scenario: Нет времени бара
- **WHEN** решение не имеет `bar_time`
- **THEN** блок времени в строке опускается (нет `HH:MM`)

#### Scenario: Нет имени стратегии
- **WHEN** решение не имеет имени стратегии
- **THEN** блок `| <имя>` в строке опускается

#### Scenario: Нет таймфрейма
- **WHEN** задаче не задан таймфрейм (пустое значение параметра)
- **THEN** блок `(<таймфрейм>)` в строке опускается, маркер `● ` и `<инструмент>` выводятся без него

#### Scenario: Время в локальном поясе
- **WHEN** смещение часового пояса задано, например `+3` часа, а `bar_time` равен `06:00` UTC (момент закрытия свечи)
- **THEN** в сообщении блок времени выводится как `09:00` (к значению закрытия прибавлено смещение)

#### Scenario: Нулевое смещение сохраняет UTC
- **WHEN** смещение часового пояса равно `0`, а `bar_time` равен `06:00` UTC (момент закрытия свечи)
- **THEN** блок времени выводится как `06:00` (UTC-время закрытия без изменений)

### Requirement: Формат уведомления о недопуске сделки
Нормативный уровень: MUST.
Недопуск сделки отображается шаблоном `src/notifier/templates/decision.py` сообщением вида `⛔ <инструмент> (<таймфрейм>) HH:MM | <стратегия> [<профиль>] ➜ Сделка не допущена: <причина>`, где `<инструмент>` — краткое имя инструмента (short name, например `NG-10.26`), `<таймфрейм>` — таймфрейм задачи (блок опускается при отсутствии), `HH:MM` — время закрытия последнего бара в локальном поясе (блок опускается при отсутствии), `<стратегия>` — имя стратегии (блок опускается при отсутствии), `<профиль>` — профиль фильтрации (блок опускается при отсутствии), `<причина>` — человекочитаемое описание причины недопуска на русском. Маркер `⛔ ` ДОЛЖЕН отличать сообщение о недопуске от обычных сигналов (`● `). Формат обычных сигналов НЕ изменяется.

#### Scenario: Недопуск из-за нулевого объёма
- **WHEN** решение BUY по привязке `15m`/`macd_rsi_stoch`/`basic_levels` не допущено с причиной «Объём позиции ниже минимального»
- **THEN** доставленное сообщение равно `⛔ <инструмент> (15m) | macd_rsi_stoch [basic_levels] ➜ Сделка не допущена: Объём позиции ниже минимального`

#### Scenario: Без таймфрейма, стратегии и профиля
- **WHEN** недопуск произошёл по решению без заданных таймфрейма, имени стратегии и профиля
- **THEN** сообщение содержит `⛔ <инструмент> ➜ Сделка не допущена: <причина>` без блоков `(таймфрейм)`, `| стратегия` и `[профиль]`

#### Scenario: Обычный сигнал сохраняет формат
- **WHEN** сигнал BUY допущен и доставляется как обычно
- **THEN** сообщение начинается с `●` и имеет прежний формат `🟢 ПОКУПКА (BUY) — Цена: X`, без маркера `⛔`

#### Scenario: Недопуск дублирующего сигнала
- **WHEN** повторный сигнал той же связки по тому же бару не допущен с причиной `duplicate-signal`
- **THEN** доставленное сообщение содержит маркер `⛔`, контекст задачи и причину «дублирующий сигнал, сделка не взята в работу»

### Requirement: Уведомление о принятой в работу сделке
Нормативный уровень: MUST.
После успешного допуска входа система ДОЛЖНА доставить трейдеру уведомление о принятой в работу сделке. Уведомление ДОЛЖНО содержать краткое имя инструмента, таймфрейм, направление и объём, плановые цену входа, стоп и цели, ожидаемый результат в долях сопровождающего риска с точностью до сотых, а также явное указание, что сделка находится в работе и заявка ждёт подтверждения. Уведомление НЕ ДОЛЖНО заявлять факт исполнения до подтверждения брокера и НЕ ДОЛЖНО подавлять обычное уведомление о сигнале.

Ожидаемый результат ДОЛЖЕН считаться из плановых уровней: сумма долей целей, умноженная на отношение движения к цели к риску входа, с разворотом знака для SELL. При нулевом риске входа или отсутствии целей ожидаемый результат равен нулю.

#### Scenario: Успешный допуск входа
- **WHEN** кандидат допущен и создано действие открытия позиции по Si 5m, SELL, объём 7, план входа/стоп/цели заданы
- **THEN** трейдеру доставлено отдельное уведомление с кратким контрактом `Si-12.26`, таймфреймом, направлением, объёмом, плановыми уровнями, ожидаемым результатом в R и формулировкой «в работе, ждёт подтверждения»

#### Scenario: Исполнение ещё не подтверждено
- **WHEN** по принятой в работу сделке брокер ещё не подтвердил исполнение
- **THEN** текст уведомления описывает ожидание подтверждения и не утверждает, что позиция открыта

#### Scenario: Ожидаемый результат считается по плану
- **WHEN** допущен SELL с риском 4 и целями на 4 и 8 ниже входа с долями 0.5 и 0.5
- **THEN** уведомление содержит ожидаемый результат `1.50R`

#### Scenario: Риск нулевой
- **WHEN** у допущенного плана цена входа равна стопу или цели не заданы
- **THEN** ожидаемый результат равен `0.00R`

### Requirement: Проверка конфигурации Telegram
Нормативный уровень: MUST.
Если `TELEGRAM_BOT_TOKEN` или `TELEGRAM_CHANNEL_ID` не заданы (None/пустые), канал Telegram ДОЛЖЕН записать предупреждение в модульный логгер и пропустить HTTP-запрос. Дублирующий вывод сообщения в консоль при этом НЕ ДОЛЖЕН выполняться. Канал при этом ДОЛЖЕН оставаться подписанным на свои типы событий и НЕ ДОЛЖЕН влиять на доставку другим каналам.

#### Scenario: Telegram не настроен
- **WHEN** токен или идентификатор канала равен `None`
- **THEN** в логгер записывается предупреждение, HTTP-запрос не выполняется, эхо-печать сообщения отсутствует

#### Scenario: Остальные каналы работают
- **WHEN** Telegram не настроен, активны консоль и Telegram
- **THEN** консоль получает все события, торговый цикл не прерывается

### Requirement: Рабочая отправка в Telegram
Нормативный уровень: MUST.
Канал Telegram ДОЛЖЕН отправлять сообщение реальным HTTP POST на `https://api.telegram.org/bot{token}/sendMessage` с параметрами `chat_id` (идентификатор канала) и `text` (сообщение) и таймаутом 10 секунд. Токен и идентификатор канала ДОЛЖНЫ браться из `.env` через `src.config` как дефолтные параметры конструктора.

Публикация события ДОЛЖНА возвращаться немедленно: текст кладётся в ограниченную очередь, а отправкой занимается единственный фоновый поток. Порядок доставки ДОЛЖЕН соответствовать порядку публикации. При переполнении очереди ДОЛЖНО отбрасываться самое старое сообщение, чтобы не потерять свежие состояния сделки; отбрасывания агрегируются в предупреждение со счётчиком.

Сообщение длиннее лимита Telegram (4096 символов) ДОЛЖНО разбиваться по границам строк, а строка длиннее лимита — резаться принудительно; порядок частей ДОЛЖЕН сохраняться.

Ответ со статусом, отличным от 200, ДОЛЖЕН фиксироваться записью с телом ответа в модульный логгер, а не печатью в stdout. Ответ `429` НЕ ДОЛЖЕН приводить к повторной попытке; `retry_after` из тела ответа, если он пришёл, ДОЛЖЕН попадать в запись логгера. Сетевое исключение ДОЛЖНО перехватываться с записью `log.exception` без прерывания работы бота. Повторных попыток отправки НЕ ДОЛЖНО быть.

Остановка ДОЛЖНА дренировать очередь за отведённое время (по умолчанию 5 секунд), а недренированный остаток — отбрасываться с предупреждением.

#### Scenario: Успешная отправка
- **WHEN** канал получает событие при настроенном Telegram
- **THEN** выполняется HTTP POST с `chat_id` и текстом сообщения, таймаут 10 секунд; ответ 200 не порождает ошибок

#### Scenario: Публикация не ждёт сеть
- **WHEN** сеть недоступна и канал получает событие
- **THEN** вызывающий поток возвращается сразу, отправка выполняется фоновым потоком

#### Scenario: Некорректный ответ API
- **WHEN** Telegram API отвечает статусом, отличным от 200
- **THEN** в модульный логгер пишется ошибка с телом ответа; работа продолжается

#### Scenario: Ответ 429 не повторяется
- **WHEN** Telegram API отвечает `429` с `retry_after`
- **THEN** запрос выполняется один раз, `retry_after` попадает в логгер

#### Scenario: Сетевое исключение
- **WHEN** запрос завершается исключением (сеть/таймаут)
- **THEN** исключение перехватывается, в логгер пишется запись об ошибке; бот продолжает работу

#### Scenario: Длинное сообщение разбивается
- **WHEN** текст длиннее 4096 символов
- **THEN** отправляются несколько сообщений по границам строк, их порядок сохраняется

#### Scenario: Переполнение очереди
- **WHEN** очередь заполнена, а приходит новое событие
- **THEN** самое старое сообщение отбрасывается, новое ставится в очередь, в логгер пишется предупреждение со счётчиком

#### Scenario: Остановка дренирует очередь
- **WHEN** канал закрывается при непустой очереди
- **THEN** очередь отправляется за отведённое время; неотправленный остаток отбрасывается с предупреждением

#### Scenario: Дефолтные токены из .env
- **WHEN** канал создан без явных параметров
- **THEN** используются значения из `.env`, загруженные `src.config`

### Requirement: Консольный канал доставки
Нормативный уровень: MUST.
Система ДОЛЖНА предоставлять консольный канал `ConsoleChannel`: доставка сообщения — вывод текста в stdout, сетевые вызовы отсутствуют. Канал ДОЛЖЕН быть подписан на все типы каталога по умолчанию и доставлять событие синхронно, в вызывающем потоке. Канал ДОЛЖЕН игнорировать события, не входящие в его набор типов.

#### Scenario: Сообщение печатается
- **WHEN** консольный канал получает событие
- **THEN** текст сообщения выводится в stdout

#### Scenario: Событие неподдерживаемого типа пропускается
- **WHEN** в наборе типов канала событие отсутствует
- **THEN** событие игнорируется, вывода нет

### Requirement: Фабрика выбора канала
Нормативный уровень: MUST.
Пакет `src/notifier` ДОЛЖЕН предоставлять фабрику `build_channels()`, собирающую экземпляры каналов для списка из конфигурационной константы `NOTIFIER_CHANNELS` в порядке конфигурации; допустимые значения — `"telegram"` и `"console"`. Неизвестное значение ДОЛЖНО завершаться ошибкой с перечнем доступных каналов. Пустой список активных каналов ДОЛЖЕН отвергаться загрузкой конфигурации.

Фабрика ДОЛЖНА подписывать собранные каналы на шину в порядке конфигурации. Telegram ДОЛЖЕН создаваться ненастроенным без ошибки (см. «Проверка конфигурации Telegram»).

Остановка каналов ДОЛЖНА быть отдельной операцией `close_channels()`: каждый канал закрывается с таймаутом, ошибка одного канала при остановке НЕ ДОЛЖНА мешать остановке остальных.

#### Scenario: Выбран Telegram
- **WHEN** `NOTIFIER_CHANNELS=["telegram"]` и вызывается фабрика
- **THEN** возвращается список с единственным экземпляром канала Telegram

#### Scenario: Выбрана консоль
- **WHEN** `NOTIFIER_CHANNELS=["console"]` и вызывается фабрика
- **THEN** возвращается список с единственным экземпляром консольного канала

#### Scenario: Несколько каналов
- **WHEN** `NOTIFIER_CHANNELS=["console", "telegram"]`
- **THEN** возвращаются оба канала в порядке конфигурации и подписываются на шину в том же порядке

#### Scenario: Неизвестный канал
- **WHEN** список содержит незарегистрированное имя канала
- **THEN** выбрасывается ошибка с перечнем доступных каналов

### Requirement: Паттерн разводки уведомлений
Нормативный уровень: MUST.
Разводка уведомлений по каналам ДОЛЖНА быть построена строго на **Observer (GoF) + Publish/Subscribe (POSA)**. Обязательные следствия паттерна:
- издатель события НЕ ДОЛЖЕН знать, какие каналы существуют, сколько их и кто они;
- канал-подписчик ДОЛЖЕН получать событие и самостоятельно решать, относится ли оно к его набору типов;
- доставка ДОЛЖНА быть неблокирующей для издателя: публикация события НЕ ДОЛЖНА ждать завершения сетевой доставки;
- подписка и отписка ДОЛЖНЫ быть независимыми от формата события.

Прямое обращение издателя к конкретному каналу и обращение канала к издателю ДОЛЖНЫ быть запрещены.

#### Scenario: Добавление канала не трогает издателя
- **WHEN** в конфигурации добавлен третий канал, а код торговой логики не менялся
- **THEN** новый канал получает события без правок в коде издателя

#### Scenario: Издатель не знает про каналы
- **WHEN** разработчик читает модуль, публикующий событие
- **THEN** в нём нет упоминаний конкретного канала

#### Scenario: Публикация не ждёт сеть
- **WHEN** канал Telegram отвечает медленно
- **THEN** публикация возвращается немедленно и не блокирует торговый цикл

### Requirement: Шина событий не зависит от предметной области
Нормативный уровень: MUST.
Шина событий ДОЛЖНА быть общим механизмом обмена. Ни `EventBus`, ни `Event`, ни `EventType` НЕ ДОЛЖНЫ содержать сведений о торговле, каналах, шаблонах или форматировании. Доставка — «не более одного раза».

#### Scenario: Переиспользование шины
- **WHEN** модуль публикует событие, не относящееся к уведомлениям
- **THEN** событие доставляется подписчикам без изменения кода шины

#### Scenario: Шина свободна от торговых терминов
- **WHEN** разработчик читает пакет шины событий
- **THEN** в нём нет торговых терминов

### Requirement: Событие неизменяемо и самодостаточно
Нормативный уровень: MUST.
Событие ДОЛЖНО быть неизменяемым. Оно ДОЛЖНО содержать все данные для отображения, включая короткое имя контракта: для фьючерсов — в формате `NG-10.26`, для акций — тикер акции (`SBER`, `GAZP`, `LKOH`), который для акции и является коротким именем. Запрет на показ сырого биржевого тикера относится к инструментам с отдельным кодом контракта (фьючерсы, ETF, валюты) и НЕ распространяется на акции. Сериализуемая форма описывается схемой в `docs/notification/event-schemas.md`; расхождение со схемой ДОЛЖНО приводить к падению сборки.

#### Scenario: Канал получает всё в событии
- **WHEN** канал обрабатывает событие
- **THEN** ему не требуется обращаться к базе, брокеру или конфигурации

#### Scenario: Сырой тикер не попадает
- **WHEN** событие содержит короткое имя `NG-10.26`
- **THEN** пользовательский текст не содержит биржевого тикера `NGU6`

#### Scenario: Имя контракта, введённого вручную, берётся из каталога
- **WHEN** фьючерс выбран вводом тикера вручную, а не номером из списка
- **THEN** короткое имя контракта берётся из каталога источника без дополнительных запросов, а если имя в каталоге отсутствует — в тексте остаётся заглушка `контракт не указан`

#### Scenario: Акция называется своим тикером
- **WHEN** событие по акции `SBER` не содержит явно заданного короткого имени
- **THEN** в событии и в пользовательском тексте указано `SBER`, а не заглушка `контракт не указан`

#### Scenario: Дрейф схемы ломает сборку
- **WHEN** событие изменило структуру относительно схемы
- **THEN** проверка сборки падает

### Requirement: Каталог типов событий
Нормативный уровень: MUST.
Определён каталог из 19 типов с видимостью по каналам. Telegram — только `signal`, `trade_opened`, `stop_hit`, `target_hit`, `trade_closed`. Консоль — все типы.

| `decision` | ✓ | — | решение стратегии |
| `signal` | ✓ | ✓ | допуск пройден |
| `trade_opened` | ✓ | ✓ | редьюсер |
| `position_added` | ✓ | — | брокер |
| `stop_hit` | ✓ | ✓ | редьюсер |
| `target_hit` | ✓ | ✓ | редьюсер |
| `trade_closed` | ✓ | ✓ | редьюсер |
| `rejected` | ✓ | — | допуск |
| `trade_cancelled` | ✓ | — | редьюсер |
| `order_accepted` | ✓ | — | брокер |
| `order_rejected` | ✓ | — | брокер |
| `protection_armed` | ✓ | — | брокер |

#### Scenario: Состав по умолчанию
- **WHEN** наборы типов не переопределены
- **THEN** консоль получает все 19 типов, Telegram — только пять торговых

#### Scenario: Отказ не попадает в Telegram
- **WHEN** сигнал не допущен
- **THEN** `rejected` идёт в консоль, Telegram не получает его

### Requirement: Раздельные точки публикации сигнала и решения
Нормативный уровень: MUST.
`decision` публикуется на этапе решения стратегии (до расчёта размера). `signal` публикуется после допуска и построения плана (со стопом, целями, объёмом, ожидаемым R). `signal` не публикуется при отказе допуска.

#### Scenario: Без допуска рекомендация не публикуется
- **WHEN** стратегия дала сигнал, но допуск не пройден
- **THEN** Telegram не получает `signal`

#### Scenario: Рекомендация содержит план
- **WHEN** допуск пройден
- **THEN** `signal` содержит стоп, цели, объём и ожидаемый результат в R

### Requirement: Порт канала уведомлений
Нормативный уровень: MUST.
Абстракция канала ДОЛЖНА объявлять `supported_types` и ДОЛЖНА иметь абстрактный метод обработки события. Создание экземпляра абстракции, как и создание наследника без переопределения метода обработки, ДОЛЖНО завершаться ошибкой.

#### Scenario: Канал фильтрует по типу
- **WHEN** канал подписан на ограниченный набор типов
- **THEN** события других типов игнорируются

#### Scenario: Абстрактный канал нельзя инстанцировать
- **WHEN** создаётся экземпляр абстрактного канала
- **THEN** выбрасывается ошибка

### Requirement: Шаблон принадлежит каналу
Нормативный уровень: MUST.
Представление события определяется шаблоном внутри канала. Общий форматтер ЗАПРЕЩЁН. На момент перехода шаблон Telegram повторяет консольный — это временное совпадение отражено в документации.

#### Scenario: Представление зависит от канала
- **WHEN** у канала своё представление события
- **THEN** изменение шаблона одного канала не влияет на другой

### Requirement: Торговые события публикуются по подтверждению брокера
Нормативный уровень: MUST.
Торговое событие (`trade_opened`, `position_added`, `stop_hit`, `target_hit`, `trade_closed`, `order_accepted`, `order_rejected`, `trade_cancelled`, `protection_armed`, `stop_moved`, `risk_limit_hit`, `clearing_done`, `reservation_changed`) ДОЛЖНО публиковаться только после подтверждения исхода брокером, а не в момент постановки заявки или намерения исполнителя. Подтверждённый исход — источник истины для уведомления.

Журнал состояния (`ExecutionReducer`, `TradeManager.consume`) НЕ ДОЛЖЕН быть источником уведомлений: он фиксирует состояние, а детали вроде PnL, баланса, идентификатора заявки и установленных защитных уровней знает только брокер. Публикация из журнала продублировала бы уведомление о том же событии.

#### Scenario: Заявка не подтверждена — уведомления о сделке нет
- **WHEN** исполнитель поставил заявку, но брокер не вернул подтверждённый исход
- **THEN** события `trade_opened` и `order_accepted` не публикуются, пользователь видит только ранее отправленную рекомендацию `signal`

#### Scenario: Журнал не публикует уведомления
- **WHEN** `ExecutionReducer` зафиксировал событие в базе
- **THEN** шина не получает от него ни одного события

#### Scenario: Подтверждённый исход приходит один раз
- **WHEN** брокер сообщил о подтверждённом исходе по заявке
- **THEN** соответствующее событие публикуется один раз, и текст уведомления сохраняет детали, известные только брокеру

### Requirement: Неблокирующая доставка и изоляция ошибок
Нормативный уровень: MUST.
Публикация не прерывается ошибкой одного канала. Ошибка фиксируется в логге, доставка остальным каналам продолжается. Семантика — «не более одного раза».

#### Scenario: Сбой канала не мешает другим
- **WHEN** Telegram выбрасывает исключение
- **THEN** консоль получает событие, ошибка записана в лог

#### Scenario: Ошибка не влияет на торговлю
- **WHEN** каналы выбрасывают исключения
- **THEN** торговый цикл продолжает работу

### Requirement: Прямая публикация событий без слоя перевода
Нормативный уровень: MUST.
Торговый контур ДОЛЖЕН публиковать события в шину напрямую. Методов `notify_decision`, `notify_plan`, `notify_entry_accepted`, `notify_rejection`, `notify_event` в API ДОЛЖНО НЕ оставаться: переходный слой перевода, введённый предыдущим change, удаляется вместе с ним.

Модуль, публикующий событие, ДОЛЖЕН использовать конструктор типа события из каталога и ДОЛЖЕН передавать данные, достаточные для представления. Публикация ДОЛЖЕН оставаться синхронной и неблокирующей для торгового цикла, как требует требование «Неблокирующая доставка и изоляция ошибок».

#### Scenario: Бот публикует напрямую
- **WHEN** `_admit_candidate` получает допущенный план
- **THEN** бот публикует событие `signal` в шину, отдельного посредника вызова нет

#### Scenario: Слоя перевода в API нет
- **WHEN** разработчик ищет метод `notify_decision`
- **THEN** такого метода в проекте не существует

#### Scenario: Решения не теряют тип
- **WHEN** публикуется решение стратегии
- **THEN** тип события задан конструктором каталога, а не строковым параметром

### Requirement: События исполнителя структурированы
Нормативный уровень: MUST.
Событие, которое исполнитель сообщает наружу для уведомления, ДОЛЖНО быть структурированным: тип из каталога, время, идентификатор сделки и набор полей (сторона, объём, цена, идентификатор заявки, причина, финансовый результат). Текст сообщения ДОЛЖЕН формироваться шаблоном канала; сборка русских фраз в слое исполнителя или в моделях предметной области ЗАПРЕЩЕНА.

Один тип события ДОЛЖЕН соответствовать одному смыслу. Исполнитель ДОЛЖЕН различать принятие заявки и её отклонение, вход, срабатывание цели, срабатывание стопа и прочее закрытие позиции; передача типа значением переменной вместо значения из каталога ЗАПРЕЩЕНА.

Идентификатор позиции ДОЛЖЕН отсутствовать в уведомляющем событии как поле представления; `trade_id` ДОЛЖЕН оставаться во внутренней части события для корреляции и ДОЛЖЕН НЕ выводиться в текст сообщения.

#### Scenario: Исполнитель не формирует текст
- **WHEN** исполнитель сообщает о размещении заявки
- **THEN** он передаёт тип, цену, объём, сторону и идентификатор заявки, а не готовую фразу

#### Scenario: Вход и выход различаются
- **WHEN** исполнитель сообщает об исполнении
- **THEN** тип события один из `trade_opened`, `target_hit`, `stop_hit`, `trade_closed`, а не общий «fill»

#### Scenario: Принятие и отклонение различаются
- **WHEN** заявка размещена либо отклонена
- **THEN** тип события `order_accepted` либо `order_rejected` соответственно

#### Scenario: Тип не подставляется значением
- **WHEN** исполнитель сообщает о закрытии позиции
- **THEN** передаётся значение типа из каталога, а не строка, вычисленная по другому признаку

#### Scenario: Идентификатор сделки не виден пользователю
- **WHEN** канал формирует сообщение о закрытии
- **THEN** `trade_id` присутствует во внутренней части события и отсутствует в тексте

### Requirement: Шина не используется как шина управления
Нормативный уровень: MUST.
Шина событий ДОЛЖНА обслуживать доставку уведомлений и ДОЛЖНА НЕ использоваться для управления торговым контуром. Обработка события исполнения, применение post-fill проверок, запись решения-трейса и обновление проекций журнала ДОЛЖНЫ выполняться прямыми вызовами в определённом порядке, а не доставкой подписчикам.

Порядок «редьюсер применяет событие, затем менеджер выполняет post-fill действия» ДОЛЖЕН сохраняться: нарушение порядка привело бы к решениям по ещё не записанному состоянию.

#### Scenario: Post-fill проверки не уходят в шину
- **WHEN** исполнение применено редьюсером
- **THEN** менеджер выполняет post-fill проверки прямой вызовой сразу после применения, до любой доставки подписчикам

#### Scenario: Управление не размазывается по подписчикам
- **WHEN** разработчик ищет подписчика, изменяющего состояние сделки
- **THEN** таких подписчиков нет: изменение состояния выполняет владелец состояния
