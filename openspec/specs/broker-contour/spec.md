# broker-contour Specification

## Purpose
Контур на брокере — отдельный процесс под надзором ядра рядом с эмуляцией: допуск к старту, отпечаток счёта, сверщик счёта с журналом, состав из привязок, подъём после рестарта раньше эмуляции, уведомления в свой канал. Этап С2 документа 2 «Робот на реальном счёте»: вид `sandbox`, только чтение счёта; на С3 он начнёт торговать, на Р1 из того же кода соберётся контур «Счёт».

## Requirements

### Requirement: Контур «Песочница» отдельным процессом
Нормативный уровень: MUST. Контур на брокере вида `sandbox` ДОЛЖЕН работать процессом `run.py --contour sandbox`, который запускает ядро. Папка контура — `data/contours/sandbox/`. В ней ДОЛЖНЫ лежать:

- блокировка `robot.pid`;
- лог `bot_debug.log`;
- `launch.json` — файл запуска от ядра;
- `status.json` — фактическое состояние;
- `broker.sqlite3` — отпечаток счёта, отчёты сверки и журнал заявок брокера;
- `trades.sqlite3` — журнал сделок торговой части (при `orders = true`);
- `telegram_delivery.sqlite3` — доставка в канал контура.

С брокером контур ДОЛЖЕН работать только через шлюз песочницы `src/sandbox` (адрес песочницы, токен `TINKOFF_SANDBOX_TOKEN`).

При `[contours.sandbox] orders = false` контур работает только на чтение, как на С2:

- НЕ ДОЛЖЕН отправлять заявки и стоп-заявки;
- НЕ ДОЛЖЕН читать свечи;
- НЕ ДОЛЖЕН заявлять спрос в ленте ядра.

При `orders = true` контур торгует по требованию «Торговля привязками в контуре на брокере». Стоп-заявки он НЕ ДОЛЖЕН отправлять до введения стоп-заявок у брокера.

`status.json` ДОЛЖЕН содержать поля, по которым ядро решает подхват (`pid`, `version`, `alive_at`, `exited_at`, `state`, `applied_generation`, `members`), а также:

- `orders_enabled` — режим заявок, `true` или `false`;
- `account` — номер счёта последними четырьмя символами;
- `capital` — `rub` и `liquid_portfolio`;
- `positions`, `orders`, `stop_orders` — что есть на счёте;
- `trades` — число открытых сделок журнала;
- `orders_in_flight` — число незавершённых заявок журнала заявок;
- `frozen` — замороженные инструменты;
- `last_reconcile_at`;
- `account_link` — `ok` или `lost`;
- `stream_link` — `ok` или `lost`;
- `reason` — причина отказа или выхода.

У каждого участника в `members` ДОЛЖНО быть состояние привязки: `warming`, `trading`, `draining`, `closing`, `rejected` (инструмент не определён) или `watching` (режим только чтения).

#### Scenario: Процесс песочницы
- **WHEN** ядро запускает контур «Песочница»
- **THEN** работает процесс `run.py --contour sandbox`, его лог и `status.json` лежат в `data/contours/sandbox/`, а процесс эмуляции, если он есть, работает дальше

#### Scenario: Только чтение
- **GIVEN** `orders = false`, контур «Песочница» работает со стартовым составом из двух привязок
- **WHEN** проходит любое число шагов
- **THEN** в записях вызовов шлюза нет `PostOrder`, `PostStopOrder`, `CancelOrder` и `CancelStopOrder`

#### Scenario: Без стоп-заявок
- **GIVEN** `orders = true`, у контура открытая сделка
- **WHEN** проходит любое число тиков
- **THEN** в записях вызовов шлюза нет `PostStopOrder`

### Requirement: Надзор ядра за контуром на брокере
Нормативный уровень: MUST. Ядро ДОЛЖНО надзирать за контуром «Песочница» отдельным потоком, не занимая главный поток эмуляции. Надзиратель ДОЛЖЕН:

- запускать процесс по команде запуска (`PUT /api/v1/sandbox/target` с `mode = on`), записав `launch.json`;
- отмечать выход процесса: код, время, `stopped` для штатного выхода и `failed` для остального;
- передавать процессу `stop` при остановке робота (Ctrl+C) и ждать его выхода так же, как эмуляции.

После выхода процесса ядро НЕ ДОЛЖНО запускать его снова само: повторный запуск — только командой. Остановка, запуск и падение песочницы НЕ ДОЛЖНЫ влиять на процесс эмуляции, и наоборот. Пока ядро не готово (требование «Повтор старта ядра»), команды песочницы ДОЛЖНЫ отвечать `409 CORE_NOT_READY`.

#### Scenario: Падение песочницы не трогает эмуляцию
- **GIVEN** торгуют эмуляция и контур «Песочница»
- **WHEN** процесс песочницы завершается с ошибкой
- **THEN** `GET /api/v1/sandbox` показывает `failed` с кодом выхода, эмуляция продолжает торговать, ядро песочницу само не перезапускает

#### Scenario: Ctrl+C
- **WHEN** робот останавливается по Ctrl+C
- **THEN** процесс песочницы получает `stop`, выходит на ближайшем шаге, `status.json` содержит `exited_at`

### Requirement: Подъём контура «Песочница» при старте ядра
Нормативный уровень: MUST. Когда ядро стало готово, оно ДОЛЖНО решить судьбу контура «Песочница» по `robot.pid` и `status.json` папки `data/contours/sandbox/` и желаемому из `core.sqlite3` по тем же правилам, что у эмуляции (требование «Автоподъём и подхват контура при старте ядра»): подхват живого контура той же версии, ожидание выхода другой версии, отказ трогать неподтверждённый pid, автоподъём при `[contours] autostart = true`.

Судьба песочницы ДОЛЖНА решаться и её процесс ДОЛЖЕН запускаться или подхватываться раньше, чем решается судьба эмуляции. Автоподъём песочницы НЕ ДОЛЖЕН создавать новое поколение, его состав — привязки из `contour_members`. Неподтверждённый pid в папке песочницы НЕ ДОЛЖЕН мешать подъёму эмуляции.

#### Scenario: Рестарт робота
- **GIVEN** перед остановкой робота работали эмуляция и контур «Песочница», `autostart = true`
- **WHEN** робот запускается снова
- **THEN** процесс песочницы поднимается без команды раньше процесса эмуляции, поколение песочницы не меняется, `launch.recovery = autostart`

#### Scenario: Подхват
- **GIVEN** ядро перезапустилось, а процесс песочницы той же версии жив и обновляет `alive_at`
- **WHEN** ядро стало готово
- **THEN** второй процесс песочницы не запускается, `launch.recovery = adopted`

### Requirement: Допуск контура на брокере к старту
Нормативный уровень: MUST. До первого шага контур ДОЛЖЕН проверить по порядку:

1. задан `TINKOFF_SANDBOX_TOKEN`;
2. в окружении заданы бот и канал из `[contours.sandbox] telegram_bot_env` и `telegram_channel_env`;
3. счёт робота в песочнице определяется по правилу требования «Счёт робота в песочнице»: найден или открыт, и он один;
4. отпечаток счёта совпадает с записанным в `broker.sqlite3` или записывается впервые;
5. капитал, позиции, заявки и стоп-заявки счёта прочитаны.

Любой отказ ДОЛЖЕН завершать процесс с кодом 2 до первого шага. Причина ДОЛЖНА попадать в `status.json` (`state = failed`, `reason`), в лог и в `GET /api/v1/sandbox` (`current.reason`). Имя переменной окружения в причине называется, значение — нет. Отказ на пунктах 3–5 ДОЛЖЕН уходить в канал контура тревогой, если канал задан.

#### Scenario: Нет канала
- **GIVEN** переменная из `telegram_channel_env` не задана
- **WHEN** приходит команда запуска песочницы
- **THEN** процесс выходит с кодом 2, `GET /api/v1/sandbox` показывает `failed` и причину с именем переменной, к песочнице брокера запросов нет

#### Scenario: Первый старт
- **GIVEN** у токена песочницы нет счёта `My_roBot`, в папке контура нет `broker.sqlite3`
- **WHEN** контур стартует
- **THEN** счёт открывается, отпечаток записывается, в канал уходит `started` с капиталом 0 ₽

### Requirement: Отпечаток счёта
Нормативный уровень: MUST. `broker.sqlite3` контура ДОЛЖЕН хранить отпечаток счёта:

- вид брокера (`sandbox`);
- sha256 номера счёта;
- последние четыре символа номера;
- время записи.

Полный номер счёта НЕ ДОЛЖЕН храниться в `broker.sqlite3`, `status.json`, логе и уведомлениях. Если счёт, найденный при старте, не совпадает с отпечатком, контур НЕ ДОЛЖЕН стартовать: причина «Журнал контура принадлежит другому счёту …XXXX» с последними символами записанного счёта. Отпечаток НЕ ДОЛЖЕН перезаписываться автоматически. Чтобы начать с другим счётом, человек удаляет папку контура.

#### Scenario: Подменили счёт
- **GIVEN** отпечаток записан для счёта …09c3, а теперь у токена единственный счёт `My_roBot` …7f21
- **WHEN** контур стартует
- **THEN** процесс выходит с кодом 2, причина называет …09c3, отпечаток не меняется

### Requirement: Шаг контура на брокере
Нормативный уровень: MUST. При `orders = false` после допуска контур ДОЛЖЕН работать шагами раз в 10 секунд. При `orders = true` та же работа ДОЛЖНА выполняться на границах тика торговой части и не реже раза в 10 секунд, даже без новых свечей. По порядку:

1. пульс ядра: «остановлено» или пульс другой версии — штатный выход после шага, как у эмуляции; пульс старше `heartbeat_timeout_secs` — работа продолжается, `core_link = lost`, новые входы не допускаются;
2. целевое состояние из `core.sqlite3`: новое поколение применяется на этом шаге, `applied_generation` — его номер;
3. разбор заявок `unknown` и очереди исполнений;
4. капитал, если было своё исполнение;
5. сверка, если с прошлой сверки прошло не меньше `reconcile_every_min` минут;
6. запись `status.json` с `alive_at`.

При `orders = false` остановка (`no_entries` или `close_all`) ДОЛЖНА завершать процесс на шаге её применения, со `state = stopped`, и НЕ ДОЛЖНА трогать счёт. При `orders = true` остановка действует по требованию «Остановка контура на брокере с открытыми сделками».

#### Scenario: Добавили привязку
- **GIVEN** песочница работает, применено поколение 4
- **WHEN** команда добавляет привязку и пишет поколение 5
- **THEN** не позже чем через 10 секунд `status.json` показывает `applied_generation = 5` и привязку в `members`

#### Scenario: Остановка с закрытием
- **GIVEN** `orders = false`, на счёте песочницы ручная позиция NG
- **WHEN** приходит `PUT /api/v1/sandbox/target` с `mode = close_all`
- **THEN** процесс выходит на ближайшем шаге со `state = stopped`, позиция NG на счёте остаётся

### Requirement: Состав контура на брокере из привязок
Нормативный уровень: MUST. Участник состава контура «Песочница» ДОЛЖЕН быть привязкой — `id` из `[strategies.*]`. Состав ДОЛЖЕН храниться в `contour_members` `core.sqlite3` с ключом — `id` привязки и:

- карточкой привязки: инструмент, стратегия, управление, фильтр, таймфрейм;
- инструментом привязки, который ядро определяет по правилам запуска эмуляции: акция — по тикеру, фьючерс — действующий контракт семейства с запасом до экспирации;
- карточкой контракта от ядра.

Если инструмент привязки определить нельзя, ДОЛЖЕН следовать отказ `422 BINDINGS_REJECTED` с причиной, а состав НЕ ДОЛЖЕН меняться. `launch.json` контура ДОЛЖЕН нести привязки, их инструменты и карточки контрактов.

Состав ДОЛЖЕН меняться только командами API и НЕ ДОЛЖЕН задаваться в `robot.toml`. Состав эмуляции и состав песочницы НЕ ДОЛЖНЫ влиять друг на друга.

Привязка, добавленная на работающий контур, ДОЛЖНА начинать торговать на ближайшей границе тика после прогрева своего инструмента. Привязка, сохранённая без инструмента (С2), получает его заново при запуске командой `PUT /api/v1/sandbox/target`. При автоподъёме или если определить инструмент не удалось, привязка помечается `rejected` с причиной, а остальные торгуют.

Ключ инструмента у контура тот же, что у эмуляции (тикер, если UID не известен). Для заявок контур ДОЛЖЕН определять UID инструмента у брокера (`GetInstrumentBy` по тикеру) и хранить в журнале заявок UID.

#### Scenario: Независимые составы
- **GIVEN** эмуляция торгует NG всеми стратегиями
- **WHEN** в песочницу добавлена одна привязка NG
- **THEN** состав эмуляции не меняется, `GET /api/v1/sandbox/bindings` отмечает эту привязку как торгующую в эмуляции и в песочнице

#### Scenario: Контракт привязки
- **GIVEN** у семейства NG действуют контракты NG-11.26 и NG-12.26, до экспирации NG-11.26 меньше `contract_expiry_block_days`
- **WHEN** в песочницу добавляется привязка NG
- **THEN** её инструмент — NG-12.26, как выбрала бы эмуляция

### Requirement: Сверщик счёта
Нормативный уровень: MUST. Сверщик ДОЛЖЕН сравнивать по каждому инструменту, у которого есть что-то на счёте или в журнале контура:

- позицию в лотах (`GetPortfolio`) с суммой знаковых остатков открытых сделок журнала;
- активные заявки (`GetOrders`) с незавершёнными строками журнала заявок, у которых есть номер брокера;
- активные стоп-заявки (`GetStopOrders`) с активными строками `broker_stop_orders`.

Сверка ДОЛЖНА выполняться при старте, после разбора журнала заявок и до первого тика, и затем не реже раза в `reconcile_every_min` минут. Перед каждой сверкой ДОЛЖНА разбираться очередь исполнений. Перед каждой сверкой ДОЛЖЕН работать хранитель стопа: недостающую или несовпадающую по объёму свою стоп-заявку он исправляет сам, без тревоги. Инструмент, у которого есть заявка или стоп-заявка в `sending`, `unknown` или `cancelling`, непроведённое исполнение или незнакомый отчёт стрима моложе 60 секунд, в этой сверке НЕ ДОЛЖЕН сравниваться и ДОЛЖЕН попадать в отчёт отметкой `in_flight`. Чужая стоп-заявка на счёте — расхождение `stop_order`.

Инструмент с любым расхождением ДОЛЖЕН попадать в заморозку, инструмент без расхождений — выходить из неё. Заморозка ДОЛЖНА запрещать по инструменту новые входы и доборы с причиной «инструмент заморожен сверкой». Выходы, сокращения и стоп заморозка НЕ ДОЛЖНА трогать. При `orders = false` журнал пуст, поэтому любая позиция, заявка или стоп-заявка на счёте — расхождение «на счёте есть, в журнале нет».

Уведомления сверщика:

- при переходе из «совпадает» в «расхождение» и при каждом изменении состава расхождений — событие `broker_account` с `kind = reconcile_alarm`;
- при переходе в «совпадает» — `reconcile_cleared`;
- одинаковые подряд отчёты НЕ ДОЛЖНЫ уведомлять повторно.

Каждый отчёт ДОЛЖЕН сохраняться в `broker.sqlite3` (последние 100) и содержать:

- время;
- итог `ok` или `mismatch`;
- расхождения: инструмент коротким именем, что (`position`, `order`, `stop_order`), на счёте, по журналу;
- инструменты `in_flight`;
- замороженные инструменты.

Если счёт не прочитан (сеть, брокер), сверка ДОЛЖНА пропускаться с предупреждением в лог, `account_link = lost`, заморозки — оставаться как были. Третий подряд пропуск ДОЛЖЕН давать `reconcile_alarm` с причиной «счёт недоступен».

#### Scenario: Ручная покупка
- **GIVEN** песочница работает, расхождений нет
- **WHEN** командой `python -m src.sandbox buy NG 1` куплен 1 лот, и наступила сверка
- **THEN** отчёт `mismatch`: NG, `position`, на счёте на 1 больше, чем по журналу; NG заморожен; в канал «Песочница» уходит одна тревога

#### Scenario: Сделка контура совпадает
- **GIVEN** контур купил 2 лота NG, исполнение проведено
- **WHEN** наступила сверка
- **THEN** отчёт `ok`, NG не заморожен

#### Scenario: Исполнение ещё в пути
- **GIVEN** сделка биржи по входу NG пришла в стрим, но ещё не проведена
- **WHEN** наступила сверка
- **THEN** очередь разбирается до сравнения, а если исполнение всё равно не проведено, NG в отчёте `in_flight` и не заморожен

#### Scenario: Журнал не принял исполнение
- **GIVEN** исполнение брокера больше открытой позиции сделки, reducer его не принял
- **WHEN** наступила сверка
- **THEN** исполнение помечено «отвергнуто», инструмента нет в `in_flight`, отчёт `mismatch` с тревогой и заморозкой, позиция сделки у контура — по журналу

#### Scenario: Заморозка не мешает выходу
- **GIVEN** NG заморожен, у контура открытая позиция NG
- **WHEN** стратегия даёт сигнал на добор, а затем срабатывает стоп
- **THEN** добор отклонён с причиной «инструмент заморожен сверкой», выход по стопу выполнен

#### Scenario: Расхождение устранено
- **GIVEN** NG заморожен из-за ручной позиции
- **WHEN** позиция закрыта командой `sell NG 1`, и наступила сверка
- **THEN** отчёт `ok`, заморозки нет, в канал уходит `reconcile_cleared`

#### Scenario: Тревога не повторяется
- **GIVEN** расхождение по NG уже отправлено тревогой
- **WHEN** следующие сверки дают тот же состав расхождений
- **THEN** новых сообщений в канал нет, отчёты сохраняются

#### Scenario: После рестарта тревога на месте
- **GIVEN** NG заморожен, робот перезапущен
- **WHEN** контур песочницы поднялся и выполнил стартовую сверку
- **THEN** NG снова заморожен, `GET /api/v1/sandbox/reconcile` показывает расхождение, в канал уходит `started` и тревога

#### Scenario: Своя стоп-заявка
- **GIVEN** у контура открытая сделка NG и активная стоп-заявка на её остаток
- **WHEN** наступила сверка
- **THEN** отчёт `ok`, NG не заморожен

#### Scenario: Чужая стоп-заявка
- **GIVEN** командой песочницы или в обход контура поставлена стоп-заявка по NG
- **WHEN** наступила сверка
- **THEN** отчёт `mismatch`: NG, `stop_order`, на счёте на 1 больше, чем по журналу; NG заморожен, в канал уходит тревога

### Requirement: Уведомления контура на брокере
Нормативный уровень: MUST. Контур ДОЛЖЕН публиковать события в свою шину и доставлять их Telegram-каналом с ботом из `telegram_bot_env` в канал из `telegram_channel_env`, с сохранением и досылкой по правилам `telegram-delivery-recovery` в своём `telegram_delivery.sqlite3`.

Канал контура ДОЛЖЕН получать:

- `broker_account`;
- `broker_order`;
- `order_accepted`;
- девять lifecycle-типов торговли своего контура: `signal`, `trade_opened`, `position_added`, `stop_hit`, `target_hit`, `stop_moved`, `trade_closed`, `trade_cancelled`, `order_rejected`.

Списки `[notifier.telegram] events` эмуляции на канал контура НЕ ДОЛЖНЫ влиять. Карточки сделок контура ДОЛЖНЫ строиться по правилам `telegram-trade-cards` с меткой контура «ПЕСОЧНИЦА» в заголовке. Строки `order_accepted` и `broker_order` ДОЛЖНЫ дописываться в корневую карточку своей сделки.

| `kind` `broker_account` | Содержание |
|---|---|
| `started` | вид контура, счёт …XXXX, рубли, `liquid_portfolio`, число позиций, заявок и стоп-заявок, число привязок, поколение, режим заявок |

| `sent` | заявка отправлена: вход, добор, цель, стоп или выход, лимитная цена, лоты |

- **WHEN** событие доставлено

Они НЕ ДОЛЖНЫ появляться в `status.json`, `launch.json`, `broker.sqlite3`, ответах API и уведомлениях. `launch.json` НЕ ДОЛЖЕН содержать токенов: процесс контура читает их из окружения сам.

#### Scenario: Поиск секретов

- **THEN** ни одно значение не найдено

### Requirement: Торговля привязками в контуре на брокере
Нормативный уровень: MUST. При `[contours.sandbox] orders = true` процесс контура «Песочница» после допуска ДОЛЖЕН поднимать ту же торговую часть, что у эмуляции:

- свечи из ленты ядра;
- стратегии и фильтр;
- `TradeManager` с outbox в `trades.sqlite3` папки контура;
- карточки сделок.

Отличий три:

- стратегии — только привязки состава песочницы, каждая со своими стратегией, управлением, фильтром и таймфреймом;
- брокер — `TInvestBroker` поверх шлюза песочницы;
- капитал для допуска берётся со счёта (требование «Капитал контура на брокере»).

Эмуляция и история НЕ ДОЛЖНЫ менять поведение.

Спрос свечей инструментов своих привязок контур ДОЛЖЕН заявлять в ленте ядра под `contour_id = sandbox`. Инструмент привязки ДОЛЖЕН получать свечи, даже если эмуляция им не торгует.

Входы ДОЛЖНЫ идти только лимитными заявками. Команда входа или добора по рынку ДОЛЖНА получать `REJECT` с причиной `limit-entry-required` без обращения к брокеру.

#### Scenario: Одна привязка NG при эмуляции на всех стратегиях
- **GIVEN** эмуляция торгует NG всеми стратегиями, в составе песочницы одна привязка NG
- **WHEN** стратегия другой привязки NG даёт сигнал
- **THEN** сигнал виден в эмуляции, в песочнице сделки по нему нет

#### Scenario: Инструмента нет в эмуляции
- **GIVEN** эмуляция не торгует SBER, в песочницу добавлена привязка SBER
- **WHEN** контур заявил спрос
- **THEN** ядро грузит свечи SBER, стратегия привязки получает закрытые бары

### Requirement: Заявки контура на брокере
Нормативный уровень: MUST. `TInvestBroker` ДОЛЖЕН реализовывать `BrokerPort` и те методы, которые у `JournalBroker` вызывают `TradeManager` и сборка контура. Ответ `submit` ДОЛЖЕН быть немедленным:

- `ACK` — брокер принял заявку или её судьба неизвестна (причина `broker-unknown`);
- `REJECT` — отказ брокера (причина `broker:<код>`) или отказ проверки до отправки.

Исполнения, подтверждённые снятия и поздние отказы ДОЛЖНЫ приходить позже через `drain_addressed_events` и проводиться тем же `consume`.

| Команда | Действие у брокера |
|---|---|
| `OpenTrade`, `AddToTrade` (лимит) | `PostOrder` лимитная заявка по `limit_price`, ключ из `command_id`; `AddToTrade` при несовпадающей стоп-заявке сделки — `REJECT stop-pending` |
| `CloseTrade`, `ReduceTrade` без цели | цикл выхода по требованию «Выходы лимитными заявками» |
| `CancelEntry` | `CancelOrder` по каждому неисполненному входу сделки |
| `MoveStop` | новый стоп в представлении контура; стоп-заявку у брокера пересоздаёт хранитель стопа по требованию «Стоп-заявка у брокера» |

Ключ идемпотентности (`order_id` запроса) ДОЛЖЕН быть UUID, однозначно выведенным из `command_id`: тот же `command_id` даёт тот же ключ и после рестарта. Повторный `submit` команды, по ключу которой уже есть строка в журнале заявок, НЕ ДОЛЖЕН ставить новую заявку и ДОЛЖЕН отвечать её текущим состоянием.

`CANCEL` команды входа ДОЛЖЕН приходить только после подтверждения снятия брокером. Сделка биржи, пришедшая до подтверждения, ДОЛЖНА проводиться обычным исполнением. После частичного исполнения снимается остаток, а сделка продолжается с исполненным объёмом. Отказ брокера на вход ДОЛЖЕН отменять план без повторов.

#### Scenario: Вход принят и исполнен
- **GIVEN** привязка NG дала сигнал на покупку 2 лотов по 2,845
- **WHEN** команда входа доставлена брокеру, а затем пришли две сделки биржи по 1 лоту
- **THEN** `submit` отвечает `ACK` с номером заявки; журнал получает `PARTIAL` 1 лот и `FILL` 1 лот с ценами в пунктах; позиция 2 лота

#### Scenario: Повторная доставка той же команды
- **GIVEN** заявка входа отправлена, процесс упал до отметки outbox `SENT`
- **WHEN** после подъёма outbox снова отдаёт команду в `submit`
- **THEN** второй `PostOrder` не выполняется, у брокера одна заявка с этим ключом

#### Scenario: TTL входа
- **GIVEN** лимитный вход не исполнился за TTL таймфрейма
- **WHEN** `TradeManager` выпускает `CancelEntry` с `entry-timeout`
- **THEN** у брокера выполняется `CancelOrder`, `CANCEL` входа проводится только после подтверждения снятия

#### Scenario: Исполнение раньше отмены
- **GIVEN** по входу отправлен `CancelOrder`
- **WHEN** до подтверждения снятия пришла сделка биржи на 1 из 2 лотов, затем подтверждение
- **THEN** позиция 1 лот, вход завершён отменой остатка, сделка сопровождается дальше

#### Scenario: Отказ брокера на вход
- **WHEN** брокер отклонил лимитную заявку входа
- **THEN** план отменён, резерв освобождён, повторной заявки нет, в канале отказ с кодом брокера

### Requirement: Журнал заявок брокера
Нормативный уровень: MUST. Контур ДОЛЖЕН вести журнал заявок брокера в `broker.sqlite3` своей папки. Одна строка — одна заявка у брокера. Строка ДОЛЖНА записываться до вызова `PostOrder` и содержать:

- ключ, `command_id`, `trade_id`;
- вид — `entry`, `add`, `target`, `stop`, `exit`, `emergency`;
- инструмент, направление, тип заявки, лоты, цену в пунктах;
- состояние, номер заявки брокера, исполненные лоты, среднюю цену исполнения в пунктах;
- причину, число отправок, время создания, отправки и изменения.

Состояния: `sending`, `accepted`, `partial`, `filled`, `rejected`, `cancelling`, `cancelled`, `unknown`. Завершённые — `filled`, `rejected`, `cancelled`.

Каждая сделка биржи ДОЛЖНА записываться в журнал отдельной строкой с `execution_id = tinvest:<номер сделки биржи>` до проведения через `consume` и помечаться проведённой после него. Одна и та же сделка биржи НЕ ДОЛЖНА проводиться дважды, откуда бы она ни пришла: из стрима, из `GetOrderState` или после рестарта.

Исполнение без сделок биржи (по сумме заявки) ДОЛЖНО считаться заглушкой на те же лоты, что и сделки, пришедшие позже. Сумма исполнений заявки НЕ ДОЛЖНА превышать её лоты и итог `lots_executed` брокера: лишнее ДОЛЖНО сниматься с непроведённых исполнений (сначала с исполнения по сумме заявки) до выдачи в `consume`, в том числе для журнала, записанного раньше. Исполнение по сумме заявки ДОЛЖНО записываться только на положительный остаток `min(lots_executed, лоты заявки) − уже исполнено`. Если остатка нет, досверка НЕ ДОЛЖНА писать исполнение, падать или ставить заявку на повторную досверку — даже когда `lots_executed` брокера больше лотов заявки.

`order_id` каждого события брокера ДОЛЖЕН совпадать с заявкой журнала сделок — id её команды; номер заявки брокера в `order_id` НЕ ДОЛЖЕН попадать.

Полный номер счёта НЕ ДОЛЖЕН храниться в журнале заявок.

#### Scenario: Сделка пришла дважды
- **GIVEN** сделка биржи по входу пришла из стрима и проведена
- **WHEN** после переподключения стрима `GetOrderState` вернул ту же сделку в `stages`
- **THEN** объём позиции не меняется, новой строки исполнения нет

#### Scenario: Сделка стрима после исполнения по сумме заявки
- **GIVEN** вход на 10 лотов, `GetOrderState` вернул «исполнена» без сделок, и исполнение по сумме заявки записано
- **WHEN** следом стрим прислал сделку биржи на те же 10 лотов
- **THEN** в журнале сделок проведено 10 лотов, исполнение входа проходит reducer, сделка в позиции на 10 лотов

#### Scenario: Брокер исполнил больше лотов заявки
- **GIVEN** заявка на 10 лотов, в журнале заявок исполнено 10 лотов по сделкам биржи
- **WHEN** `GetOrderState` вернул «исполнена» с `lots_executed` больше 10, которое не переводится в лоты, и без сделок
- **THEN** новой строки исполнения нет, обслуживание брокера контура не прерывается, заявка не досверяется повторно

### Requirement: Исполнения из стрима
Нормативный уровень: MUST. Контур ДОЛЖЕН держать `OrderStateStream` по счёту робота в отдельном потоке. Поток ДОЛЖЕН:

- сопоставлять каждое событие со строкой журнала заявок по `order_request_id`, а если его нет (событие «исполнена» песочница присылает без ключа) — по уже известному постоянному номеру заявки брокера; временный `order_id` первого события НЕ ДОЛЖЕН становиться номером заявки;
- писать новые сделки биржи в журнал заявок и в очередь исполнений;
- обновлять состояние строки по статусу и `lots_executed`.

Событие по заявке без нашего ключа НЕ ДОЛЖНО попадать в очередь исполнений.

Поток стрима НЕ ДОЛЖЕН писать в `trades.sqlite3`. Очередь исполнений ДОЛЖНА разбираться главным потоком через `consume` не реже раза в `tick_poll_secs`, а не только на новой свече.

При обрыве стрим ДОЛЖЕН переподключаться с паузой 1, 2, 4… до 30 с. После переподключения каждая незавершённая строка журнала заявок ДОЛЖНА досверяться через `GetOrderState` по ключу. Пропущенные сделки берутся из `stages`.

#### Scenario: Временный номер заявки
- **GIVEN** стрим прислал событие с временным `order_id` и нашим `order_request_id`, затем событие с постоянным номером
- **WHEN** оба события обработаны
- **THEN** это одна строка журнала заявок, номер брокера — постоянный

#### Scenario: Обрыв стрима во время исполнения
- **GIVEN** вход отправлен, стрим оборвался
- **WHEN** вход исполнился, пока стрима не было, и стрим переподключился
- **THEN** исполнение найдено по ключу, проведено один раз, позиция совпадает со счётом

### Requirement: Восстановление заявки по ключу
Нормативный уровень: MUST. Заявка ДОЛЖНА становиться `unknown`, если:

- `PostOrder` закончился тайм-аутом, `UNAVAILABLE`, `DEADLINE_EXCEEDED`, `INTERNAL` или обрывом соединения;
- при старте найдена строка в `sending`.

Контур НЕ ДОЛЖЕН отправлять такую заявку повторно, не спросив брокера. На ближайшей границе тика, а после старта до первого тика, контур ДОЛЖЕН выполнить `GetOrderState` с `ORDER_ID_TYPE_REQUEST` по ключу:

- найдена — состояние и сделки берутся из ответа;
- не найдена, а команда актуальна — `PostOrder` тем же ключом. Вход актуален, если сделка ждёт входа и TTL не истёк; выход — пока у сделки есть остаток;
- не найдена и вход устарел — вход завершается `CANCEL` с причиной `entry-undelivered`.

Ответ `INVALID_ARGUMENT` с кодом 30057 («дубликат») на `PostOrder` ДОЛЖЕН вести к поиску по ключу, а не к отказу.

Если шлюз исчерпал повторы при `RESOURCE_EXHAUSTED`, вход ДОЛЖЕН получать `REJECT` с причиной `rate-limited`, а выход — повторяться на следующем шаге.

Перед первым тиком после старта контур ДОЛЖЕН разобрать все незавершённые строки журнала заявок и провести через `consume` все непроведённые исполнения.

#### Scenario: Процесс убит между отправкой и исполнением
- **GIVEN** заявка входа отправлена, процесс контура убит до ответа
- **WHEN** ядро поднимает контур снова
- **THEN** до первого тика заявка найдена по ключу, второй заявки у брокера нет, исполнение, если было, проведено один раз

#### Scenario: Заявка не дошла
- **GIVEN** `PostOrder` входа закончился тайм-аутом
- **WHEN** поиск по ключу ничего не нашёл, TTL входа не истёк
- **THEN** заявка отправляется снова тем же ключом, у брокера одна заявка

#### Scenario: Дубликат ключа
- **WHEN** повторный `PostOrder` получил ошибку 30057
- **THEN** контур находит заявку по ключу и продолжает с её состоянием, отказа в журнале нет

### Requirement: Цены, лоты и ГО заявок
Нормативный уровень: MUST. Перед отправкой контур ДОЛЖЕН:

- округлять цену лимитной заявки до шага цены в безопасную сторону: покупка вниз, продажа вверх;
- отправлять её в пунктах;
- отправлять количество в лотах;
- отклонять заявку с ценой вне коридора инструмента причиной `price-out-of-band`, без запроса `PostOrder`.

Цена сделки биржи в стриме (`trades`) приходит котировкой в пунктах. Суммы заявки (`executed_order_price`) и цены сделок `GetOrderState.stages` приходят суммой в рублях за контракт фьючерса. Контур ДОЛЖЕН переводить рублёвые цены в пункты: `пункты = рубли × min_price_increment / min_price_increment_amount` из `GetFuturesMargin`, с округлением до шага. У акций цена в рублях за бумагу и есть цена в пунктах. Если брокер присылает объём сделки в штуках, а не в лотах, контур ДОЛЖЕН делить его на размер лота. Итог исполнения заявки (`lots_executed` ответа `PostOrder`, стрима и `GetOrderState`) ДОЛЖЕН переводиться в лоты так же: если он больше лотов заявки в журнале, кратен размеру лота и после деления не больше лотов заявки, это штуки, и контур ДОЛЖЕН делить его на размер лота до разбора отчёта. Иначе число брокера берётся как есть. Ориентир — лоты нашей заявки в журнале, а не `lots_requested` брокера.

ГО на контракт ДОЛЖНО браться из `GetFuturesMargin` (`initial_margin_on_buy` или `initial_margin_on_sell`) при допуске инструмента и обновляться раз в сутки. Оно заменяет ГО карточки контракта у контура.

### Requirement: Капитал контура на брокере
Нормативный уровень: MUST. Капиталом контура «Песочница» для допуска сделок ДОЛЖНЫ быть рубли на счёте из `GetPositions`. `liquid_portfolio` ДОЛЖЕН показываться рядом и НЕ ДОЛЖЕН влиять на допуск. Капитал ДОЛЖЕН читаться при старте, после каждого своего исполнения (на следующей границе тика) и при каждой сверке. Кандидаты одного тика ДОЛЖНЫ допускаться по одному снимку капитала.

Вход или добор ДОЛЖЕН допускаться по ГО, только если лоты × ГО на контракт не больше рублей на счёте за вычетом ГО неисполненных входов контура. Отказ ДОЛЖЕН публиковаться прежним событием ограничения бюджета с причиной «не хватает ГО».

Если капитал не прочитан, новые входы и доборы ДОЛЖНЫ отклоняться с причиной «счёт недоступен», а выходы и сокращения ДОЛЖНЫ работать.

Эмуляция ДОЛЖНА по-прежнему брать капитал из `initial_deposit`.

### Requirement: Выходы лимитными заявками
Нормативный уровень: MUST. Выходы контура ДОЛЖНЫ идти лимитными заявками. Рыночная заявка допускается только как аварийный выход после исчерпания перевыставлений.

**Цели.** После каждого исполнения входа или добора контур ДОЛЖЕН держать у брокера лимитную заявку на каждую неисполненную цель:

- по цене цели после пересчёта от средней;
- на объём цели по прежнему распределению;
- в сторону выхода.

Изменился объём или цена цели — заявка перевыставляется: сначала снимается старая, потом ставится новая. Каждая сделка биржи по заявке цели ДОЛЖНА проводиться отдельным защитным исполнением с `command_id` вида `<trade>:pv:tp:<target>:<номер сделки биржи>`. Если брокер снял заявку цели в конце дня без исполнения, контур ДОЛЖЕН поставить её заново после открытия торгов.

**Стоп.** Основной стоп сделки — стоп-заявка у брокера по требованию «Стоп-заявка у брокера». Пока у сделки нет активной стоп-заявки на весь желаемый объём по желаемой цене, контур ДОЛЖЕН проверять условие стопа по закрытым минутным свечам ядра по тем же правилам, что симулятор эмуляции: стоп важнее целей, гэп через стоп на открытии. При срабатывании контур ДОЛЖЕН:

1. снять заявки целей сделки;
2. поставить лимитную заявку на остаток, не занятый живыми заявками целей, по цене стопа с запасом `exit_offset_steps` шагов в сторону исполнения: продажа — стоп минус запас, покупка — стоп плюс запас;
3. если заявка не исполнилась целиком за `exit_requote_secs` секунд, снять её и поставить новую на весь текущий остаток по последней цене с тем же запасом;
4. после `exit_requote_attempts` перевыставлений выйти рыночной заявкой на остаток и отправить тревогу.

Каждая сделка биржи по заявке стопа проводится отдельным защитным исполнением с `command_id` вида `<trade>:pv:stop:<момент срабатывания>:<номер сделки биржи>`.

Условие стопа сделки ДОЛЖНО проверяться только по минутам, закрывшимся после её первого исполнения входа; минута входа проверяется. После рестарта граница прогона пропущенных минут ДОЛЖНА учитывать исполнения, проведённые при старте до первого тика. Стоп, пробитый за время простоя после входа, ДОЛЖЕН закрывать позицию.

**Сигнальные выходы и закрытие.** `CloseTrade` и `ReduceTrade` без цели ДОЛЖНЫ идти тем же циклом, от последней цены: лимит с запасом, перевыставление, аварийный рынок. Это сигнал стратегии, сессионная защита, экспирация, `close_all`.

- Перед `CloseTrade` снимаются заявки целей и стоп-заявка сделки; первая заявка выхода ставится только после подтверждения снятия стоп-заявки. Если стоп-заявка при снятии оказалась исполненной, выход ждёт её по правилу стопа.
- `ReduceTrade` на q лотов сначала уменьшает стоп-заявку сделки на q; заявка выхода ставится после снятия прежней стоп-заявки.
- `ReduceTrade` берёт сначала лоты, не занятые заявками целей, затем уменьшает заявку самой дальней цели.

**Объём.** Сумма лотов живых выходных заявок сделки НЕ ДОЛЖНА превышать её остаток. Стоп-заявка у брокера входит в эту сумму вместе с заявками выхода контура; заявки целей стоят рядом со стоп-заявкой на весь остаток и в сумму со стопом не входят. Кроме заявок целей, у сделки ДОЛЖНО быть не больше одной выходной заявки в работе. Сигнальный выход, пришедший при незавершённом стопе, ждёт его. Если после завершения остаток ноль, сигнальный выход получает `REJECT trade-not-open`.

Остаток для новой заявки выхода или цели ДОЛЖЕН считаться по исполнениям, уже учтённым сделкой. Пока у сделки есть непроведённые исполнения или заявка её выхода ждёт своих сделок, новая заявка выхода или цели НЕ ДОЛЖНА ставиться.

**Отказ брокера на выход** или заявку цели ДОЛЖЕН повторяться не чаще раза в минуту новым ключом, пока заявка не пройдёт или остаток не станет нулевым. О первом отказе в канал уходит тревога.

### Requirement: Остановка контура на брокере с открытыми сделками
Нормативный уровень: MUST. Команды остановки контура «Песочница» ДОЛЖНЫ действовать на его сделки по правилам эмуляции:

- `no_entries` — неисполненные входы снимаются у брокера, открытые сделки сопровождаются до выхода;
- `close_all` — дополнительно каждая открытая сделка закрывается по требованию «Выходы лимитными заявками».

Процесс ДОЛЖЕН завершаться сам со `state = stopped`, когда у контура не осталось открытых сделок, незавершённых заявок и живых стоп-заявок. При `no_entries` стоп-заявки открытых сделок остаются у брокера до их выхода.

Снятие привязки ДОЛЖНО действовать так же, но только на сделки этой привязки:

- `no_entries` — привязка не открывает новых входов, сопровождает свои сделки и уходит из состава после последней;
- `close_all` — то же, плюс её сделки закрываются.

Последняя привязка инструмента уводит и инструмент.

Штатный выход по Ctrl+C, концу стандартного ввода или пульсу «остановлено» ДОЛЖЕН оставлять заявки входа и целей, стоп-заявки у брокера и позиции на счёте как есть. Сообщение `stopped` ДОЛЖНО называть число открытых позиций и число стоп-заявок у брокера (`broker_stops`).

### Requirement: Сторож исполнения 1m контура
Нормативный уровень: MUST. Торговый контур в живом режиме ДОЛЖЕН следить, не держит ли барьер покрытия полученные минуты инструмента, по которому в журнале есть открытая позиция или неисполненный вход. Пока исполнение 1m по инструменту стоит, его виртуальный стоп не проверяется и переоценка не обновляется.

- Удержание короче `5` минут — норма тонкого рынка: минута без сделок разрешается ядром за 1–3 минуты. Такое удержание НЕ ДОЛЖНО давать тревогу.
- Удержание дольше `5` минут по инструменту со сделками ДОЛЖНО давать WARNING в журнал контура с коротким именем, последней исполненной и последней полученной минутой. Пока удержание длится, WARNING ДОЛЖЕН повторяться раз в `15` минут, а не один раз и не каждый тик.
- Контур на брокере ДОЛЖЕН отправить в канал одно сообщение «Исполнение стоит» на начало такого удержания и одно «Исполнение возобновлено» на его конец. Текущие удержания ДОЛЖНЫ быть в `status.json` (`execution_holds`) и в `GET /api/v1/sandbox` (`current.execution_holds`).
- Удержание инструмента без сделок тревоги НЕ ДОЛЖНО давать.
- Сторож только наблюдает: он НЕ ДОЛЖЕН менять исполнение, границу или барьер, а его сбой НЕ ДОЛЖЕН прерывать шаг исполнения.

### Requirement: Снимок счёта в статусе контура на брокере
Нормативный уровень: MUST. `capital`, `positions`, `orders` и `stop_orders` в `status.json` — снимок счёта брокера. Вместе с ним ДОЛЖЕН записываться момент снимка `account_at`, и API ДОЛЖЕН отдавать его в `current.account_at`. Снимок ДОЛЖЕН браться при старте, на каждой сверке и перед записью `stopped`: после остановки статус больше никто не обновит.

Если перед остановкой счёт не прочитан, в статусе ДОЛЖЕН остаться прежний снимок с `account_link: lost`. Процесс, убитый без остановки, оставляет последний снимок со своим `account_at`.

### Requirement: Привязки песочницы определяются пакетом
Нормативный уровень: MUST. `PUT /api/v1/sandbox/target` с `bindings` и `POST /api/v1/sandbox/bindings` ДОЛЖНЫ определять инструменты и карточки контрактов всех привязок команды одним пакетом. В пакете одинаковый запрос к сервису инструментов брокера ДОЛЖЕН уходить один раз: каталог фьючерсов — один раз на команду, маржа — один раз на контракт. Сбой одного запроса НЕ ДОЛЖЕН запоминаться.

Запросы к брокеру НЕ ДОЛЖНЫ идти под замком ресурса песочницы: остановка и чтение не ждут определения привязок. Если состав песочницы изменился, пока шли запросы, команда ДОЛЖНА завершиться `412 REVISION_CHANGED` без записи состава и без запуска.

- **THEN** к сервису инструментов уходит один запрос каталога и 6 запросов маржи вместо 57 и 19, квота брокера не исчерпывается, ответ приходит за секунды

#### Scenario: Состав изменился во время определения
- **WHEN** пока определялись привязки запуска, состав песочницы изменили другой командой
- **THEN** запуск отвечает `412 REVISION_CHANGED`, процесс не запущен, записано только другое изменение

### Requirement: Предохранитель дневного убытка
Нормативный уровень: MUST. Контур на брокере ДОЛЖЕН считать убыток торгового дня не реже раза в минуту и не чаще раза в 10 секунд. Торговый день начинается в 19:00 МСК. Убыток дня — это минус сумма двух частей, если она отрицательна, иначе ноль:

- **закрытый результат** — по исполнениям журнала сделок с начала дня: каждый выход даёт `(цена выхода − средняя входа сделки) × лоты × стоимость шага / шаг` со знаком стороны, минус комиссии всех исполнений дня, включая входы. Частичные выходы открытых сделок входят сюда;
- **открытый результат** — по каждой открытой сделке `(последняя цена − средняя) × остаток × стоимость шага / шаг` со знаком стороны. Последняя цена — закрытие последней минуты ядра. Если её нет, открытый результат сделки — ноль, а в подробности отмечается «нет цены».

Лимит — `max_daily_loss_pct` процентов от капитала контура на начало дня. Капитал на начало дня ДОЛЖЕН фиксироваться первым снимком капитала после начала дня и храниться в `broker.sqlite3`. Если контур поднялся посреди дня без такой строки, берётся текущий капитал с отметкой «дня не застал с начала». `max_daily_loss_pct = 0` выключает предохранитель.

Когда убыток дня достигает лимита, контур ДОЛЖЕН:

- запретить новые входы и доборы по всему контуру до начала следующего торгового дня;
- не закрывать позиции: стоп и цели у брокера, выходы и сокращения работают;
- отправить тревогу `guard_tripped` с убытком, лимитом, капиталом на начало дня и моментом снятия.

Возврат убытка ниже лимита в тот же день НЕ ДОЛЖЕН снимать запрет. На первом опросе после начала следующего дня запрет ДОЛЖЕН сниматься с сообщением `guard_cleared`.

#### Scenario: Убыток дня достиг лимита
- **GIVEN** капитал на начало дня 1 000 000 ₽, `max_daily_loss_pct = 1`, за день закрыта сделка с результатом −6 000 ₽, открытая позиция в минусе на 4 500 ₽
- **WHEN** контур считает убыток дня
- **THEN** убыток 10 500 ₽ ≥ 10 000 ₽, новые входы и доборы запрещены до 19:00 МСК, в канале тревога, открытая позиция сопровождается со стопом у брокера

#### Scenario: Убыток вернулся ниже лимита
- **GIVEN** предохранитель дневного убытка сработал
- **WHEN** открытая позиция выросла, и убыток дня стал меньше лимита
- **THEN** запрет остаётся до начала следующего торгового дня

#### Scenario: Новый торговый день
- **GIVEN** предохранитель сработал днём
- **WHEN** наступило 19:00 МСК, и прошёл первый опрос
- **THEN** запрет снят, в канале «предохранитель снят: новый торговый день», капитал на начало нового дня записан

#### Scenario: Сделка прошлого дня
- **GIVEN** сделка закрыта в 18:30 МСК с убытком
- **WHEN** контур считает убыток дня после 19:00 МСК
- **THEN** её результат в убыток нового дня не входит

### Requirement: Предохранитель отказов брокера подряд
Нормативный уровень: MUST. Контур на брокере ДОЛЖЕН считать отказы брокера подряд по всему контуру:

- отказ на вход или добор с причиной `broker:<код>` или `rate-limited`;
- отказ на стоп-заявку, кроме отказа из-за закрытых торгов.

Отказы проверки до отправки (`price-out-of-band`, `stop-pending`, `limit-entry-required`, `no-contract-card`, `unknown-trade`) и отказы на выходы НЕ ДОЛЖНЫ считаться. Принятая брокером заявка входа или стоп-заявка ДОЛЖНА обнулять счётчик.

Когда счётчик достигает `max_rejects_in_row`, контур ДОЛЖЕН запретить новые входы и доборы по всему контуру и отправить тревогу `guard_tripped` с числом отказов и последними причинами, не больше трёх. Выходы, стоп и цели продолжают работать. Сам запрет НЕ ДОЛЖЕН сниматься: его снимает только команда сброса из ядра — поколение сброса новее применённого. Сброс обнуляет счётчик и отправляет `guard_cleared`.

#### Scenario: Три отказа подряд
- **GIVEN** `max_rejects_in_row = 3`
- **WHEN** брокер трижды подряд отклонил вход по ГО
- **THEN** новые входы и доборы запрещены, в канале тревога с тремя причинами, `current.guards` показывает `broker_rejects`

#### Scenario: Принятая заявка обнуляет счётчик
- **GIVEN** два отказа брокера подряд
- **WHEN** следующий вход принят брокером
- **THEN** счётчик обнулён, запрета нет

#### Scenario: Отказ проверки не считается
- **WHEN** вход отклонён до отправки с `price-out-of-band`
- **THEN** счётчик не меняется

#### Scenario: Сброс командой
- **GIVEN** предохранитель отказов сработал
- **WHEN** ядро записало новое поколение сброса
- **THEN** на ближайшей границе тика запрет снят, счётчик обнулён, в канале «предохранитель снят командой»

### Requirement: Состояние предохранителей
Нормативный уровень: MUST. Состояние предохранителей ДОЛЖНО храниться в `broker.sqlite3` и переживать рестарт процесса:

- вид, сработал ли он, когда, до какого момента;
- подробность, включая счётчик отказов;
- применённое поколение сброса;
- капитал на начало каждого торгового дня.

После подъёма контур ДОЛЖЕН до первого тика применить сработавшие предохранители к запрету входов. Состояние ДОЛЖНО попадать в `status.json` (`guards`) и в `current.guards` API.

#### Scenario: Рестарт при сработавшем предохранителе
- **GIVEN** предохранитель отказов сработал, процесс контура убит
- **WHEN** контур запущен снова
- **THEN** до первого тика входы запрещены, `current.guards` показывает предохранитель с тем же `since`

### Requirement: Настоящие комиссии из операций брокера
Нормативный уровень: MUST. Контур на брокере ДОЛЖЕН на каждом проходе сверщика заменять оценку комиссии в журнале сделок контура комиссией, которую брокер списал по операциям счёта.

**Какие исполнения ждут комиссию.** Исполнения журнала сделок контура:
- с источником комиссии не `broker`;
- от сделок биржи (`execution_id` вида `tinvest:<номер сделки биржи>`) или заглушки исполнения без сделок биржи (`tinvest-order:<номер заявки>:<лоты заявки>`);
- не старше 7 дней.

Нет таких исполнений — запроса к брокеру НЕ ДОЛЖНО быть. Запрос операций делается только для исполнений от сделок биржи.

**Запрос операций.** `GetOperationsByCursor`:
- период — с самого раннего ждущего исполнения минус минута до текущего момента;
- состояние «исполнена»;
- типы — покупка, продажа, комиссия брокера;
- не больше 10 страниц за проход.

**Сопоставление.** Исполнение относится к операции покупки или продажи, в номерах сделок биржи которой есть его номер. Комиссия операции:
1. сумма модулей операций «комиссия брокера», у которых `parent_operation_id` равен номеру операции;
2. если таких нет, а операции больше 15 минут, — модуль поля комиссии самой операции;
3. иначе исполнение ждёт следующего прохода.

**Деление и поправка.** Комиссия операции ДОЛЖНА делиться между её исполнениями журнала пропорционально лотам с точностью до копейки, остаток — последней сделке биржи операции.

Поправка ДОЛЖНА уходить в менеджер сделок как `FeeAdjustment` той же очередью, что исполнения:
- ключ — `opfee:<источник>:<номер операции>:<execution_id>`, источник `broker_fee` или `commission`;
- поправка с суммой, равной оценке, ДОЛЖНА выпускаться: она меняет источник на `broker`, и исполнение больше не ждёт;
- повтор поправки после рестарта НЕ ДОЛЖЕН менять журнал.

**Заглушка без сделок биржи.** У заглушки нет номера сделки биржи, по операциям она не сопоставляется. Её комиссия ДОЛЖНА браться из `executed_commission` состояния заявки (`GetOrderState`, `PostOrder`):
- доля заглушки — `executed_commission × лоты заглушки / lots_executed` заявки, до копейки;
- брокер сообщил ненулевую комиссию при проведении заглушки — исполнение ДОЛЖНО сразу уйти в журнал сделок с этой комиссией и источником `broker`, и карточка исполнения показывает её, а не оценку. Журнал заявок хранит её вместе с исполнением (`broker_executions.fee`), повтор после рестарта даёт ту же сумму;
- иначе исполнение получает оценку, а проход сверщика ДОЛЖЕН запросить `GetOrderState` по номеру заявки из `execution_id`. Ненулевая комиссия даёт `FeeAdjustment` с ключом `orderfee:<номер заявки>:<execution_id>`; нулевая, «не найдена» или ошибка — исполнение ждёт;
- одно исполнение-заглушку проход НЕ ДОЛЖЕН запрашивать чаще раза в 15 минут.

**Устаревшие и ошибки.**
- Исполнение старше 7 дней без комиссии брокера остаётся с оценкой; лог получает одно предупреждение с числом таких исполнений.
- Сбой запроса операций или состояния заявки ДОЛЖЕН записываться в лог типом исключения без текста ответа и без номера счёта целиком. Сбой НЕ ДОЛЖЕН останавливать сверку и торговлю, проход повторяется на следующей сверке.
- Поправка комиссии НЕ ДОЛЖНА давать сообщений в канал.

#### Scenario: Комиссия брокера пришла
- **GIVEN** вход на 2 лота исполнен двумя сделками биржи по 1 лоту, оценка комиссии 12,00 ₽ на исполнение; в операциях — покупка с этими номерами и «комиссия брокера» 23,96 ₽ с её номером в `parent_operation_id`
- **WHEN** проходит сверка
- **THEN** у исполнений комиссия 11,98 ₽ и 11,98 ₽ с источником `broker`, комиссии позиции и итоги контура уменьшились на 0,04 ₽

#### Scenario: Только поле комиссии
- **GIVEN** операции покупки 20 минут, «комиссии брокера» к ней нет, поле комиссии операции −11,98 ₽
- **WHEN** проходит сверка
- **THEN** у исполнения комиссия 11,98 ₽ с источником `broker`, ключ поправки с источником `commission`

#### Scenario: Операция ещё свежая
- **GIVEN** операции покупки 3 минуты, «комиссии брокера» к ней ещё нет
- **WHEN** проходит сверка
- **THEN** поправки нет, исполнение ждёт следующего прохода

#### Scenario: Рестарт после поправки
- **GIVEN** поправка комиссии исполнения уже записана в журнал
- **WHEN** контур перезапускается и проходит сверку
- **THEN** журнал не меняется, запроса операций нет, если других ждущих исполнений нет

#### Scenario: Сбой запроса операций
- **GIVEN** `GetOperationsByCursor` отвечает ошибкой
- **WHEN** проходит сверка
- **THEN** в логе тип исключения, сверка и торговля продолжаются, исполнения ждут следующей сверки

#### Scenario: Цель исполнена без сделок биржи
- **GIVEN** ЦЕЛЬ1 SHORT GOLD-12.26 на 5 лотов исполнена в книге заявок, стрим и `stages` сделок не дали; `GetOrderState` — `FILL`, `lots_executed` 5, `executed_commission` 851,12 ₽
- **WHEN** брокер контура проводит заглушку `tinvest-order:<номер>:5`
- **THEN** у исполнения в журнале сделок комиссия 851,12 ₽ с источником `broker`; итог сделки в карточке закрытия считается с ней

#### Scenario: Заглушка уточняется сверщиком
- **GIVEN** исполнение-заглушка 09.11 записано с оценкой 7,50 ₽, а `GetOrderState` его заявки теперь отдаёт `executed_commission` 849,00 ₽
- **WHEN** проходит сверка
- **THEN** поправка `orderfee:<номер заявки>:<execution_id>` ставит 849,00 ₽ с источником `broker`; запроса операций нет, если других ждущих нет; следующая сверка заявку не запрашивает

#### Scenario: Брокер комиссию заглушки не сообщил
- **GIVEN** `GetOrderState` заявки заглушки отдаёт `executed_commission` 0
- **WHEN** проходят две сверки за 10 минут
- **THEN** исполнение остаётся с оценкой, `GetOrderState` по нему вызван один раз

### Requirement: Стоп-заявка у брокера
Нормативный уровень: MUST. У каждой открытой сделки контура на брокере ДОЛЖНА стоять у брокера ровно одна стоп-заявка `STOP_LOSS` со сроком «до отмены» (`GOOD_TILL_CANCEL`):

- на сторону выхода сделки;
- на объём, равный учтённому остатку минус объём заявок выхода контура в работе;
- по цене подтверждённого стопа, округлённой до шага цены в безопасную сторону: стоп продажи вверх, стоп покупки вниз.

Сумма стоп-заявок инструмента НЕ ДОЛЖНА превышать позицию того же знака на счёте по последнему снимку сверки. Если на счёте меньше, чем по журналу, объём срезается сначала у самых поздних сделок, иначе стоп перезакрыл бы позицию.

Исключения: у сделки ещё нет исполненного входа, объём выходит нулевым или контур сам выходит по стопу (стоп-задание). Заявки целей из объёма стопа НЕ ДОЛЖНЫ вычитаться: стоп стоит на весь остаток рядом с ними.

Стоп-заявки ДОЛЖНЫ храниться в таблице `broker_stop_orders` в `broker.sqlite3` контура. Строка пишется до `PostStopOrder` и хранит:

- ключ — UUID из `<trade>:bs:<номер постановки>`;
- сделку, инструмент, сторону, лоты, стоп-цену в пунктах;
- состояние (`sending`, `active`, `cancelling`, `cancelled`, `executed`, `expired`, `rejected`, `unknown`, `lost` — ответ на постановку потерян, стоп-заявка у брокера не найдена, вместо неё поставлена новая);
- номер стоп-заявки и номер порождённой заявки;
- причину и время.

Номер счёта в таблице НЕ ДОЛЖЕН храниться.

Хранитель стопа ДОЛЖЕН приводить стоп-заявку к желаемой на каждом обслуживании, после разбора очереди исполнений и перед сверкой. Если у живой стоп-заявки другой объём или цена, контур ДОЛЖЕН сначала снять её и дождаться подтверждения (`cancelled`, `executed` или `expired`) и только потом поставить новую. Две живые стоп-заявки одной сделки НЕ ДОЛЖНЫ существовать ни в какой момент. Пока у сделки есть непроведённые исполнения, хранитель НЕ ДОЛЖЕН менять её стоп-заявку.

Если за `stop_place_secs` секунд с появления желаемого стопа у сделки нет активной стоп-заявки:

- отказ брокера из-за закрытых торгов — постановка повторяется не чаще раза в минуту без выхода;
- иначе — выход из сделки циклом выхода требования «Выходы лимитными заявками» с причиной `stop-not-placed` и тревога `stop_failed` в канал.

`AddToTrade` у сделки, чья стоп-заявка не совпадает с желаемой, ДОЛЖЕН получать `REJECT stop-pending`.

#### Scenario: Стоп после входа
- **GIVEN** вход 10 лотов NG исполнен по 2.943, подтверждённый стоп 2.901
- **WHEN** очередь исполнений разобрана
- **THEN** у брокера одна стоп-заявка `STOP_LOSS` на продажу 10 лотов по 2.901 со сроком «до отмены», в карточке строка «стоп у брокера 2.901 · 10 лотов»

#### Scenario: Цель взята
- **GIVEN** у длинной сделки NG 2 лота стоп-заявка на 2 лота и заявка цели 1 на 1 лот
- **WHEN** цель 1 исполнилась
- **THEN** стоп-заявка на 2 лота снята, после подтверждения поставлена стоп-заявка на 1 лот, двух живых стоп-заявок не было ни в один момент, в карточке «стоп пересоздан на остаток 1»

#### Scenario: Перенос стопа
- **GIVEN** у сделки активная стоп-заявка по 2.901
- **WHEN** `TradeManager` выпустил `MoveStop` на 2.916
- **THEN** у брокера одна стоп-заявка по 2.916 на тот же объём

#### Scenario: Добор до пересоздания стопа
- **GIVEN** добор сделки исполнен, стоп-заявка на новый объём ещё не активна
- **WHEN** стратегия даёт следующий добор
- **THEN** он получает `REJECT stop-pending`

#### Scenario: Стоп не принят
- **GIVEN** вход исполнен, брокер отклоняет стоп-заявку по причине, не связанной с закрытыми торгами
- **WHEN** проходит `stop_place_secs`
- **THEN** сделка закрывается циклом выхода с причиной `stop-not-placed`, в канал уходит тревога «стоп не принят»

#### Scenario: Торги закрыты
- **GIVEN** брокер отклоняет стоп-заявку, потому что торги закрыты
- **WHEN** проходит `stop_place_secs`
- **THEN** выхода нет, постановка повторяется раз в минуту, условие стопа проверяет контур по минутам

### Requirement: Срабатывание стоп-заявки у брокера
Нормативный уровень: MUST. Отчёт стрима заявки, которой нет в журнале заявок (нет нашего ключа, номер незнаком), НЕ ДОЛЖЕН отбрасываться. Контур ДОЛЖЕН искать его стоп-заявку через `GetStopOrders` по `exchange_order_id`. Опрос `GetStopOrders` ДОЛЖЕН выполняться:

- при незнакомом отчёте;
- на каждой сверке, если у контура есть живые стоп-заявки.

Опросов — не больше 30 в минуту.

Если стоп-заявка найдена, контур ДОЛЖЕН:

- отметить её `executed`;
- завести строку журнала заявок вида `broker_stop` с номером порождённой заявки;
- провести каждую сделку биржи защитным исполнением с `command_id` вида `<trade>:pv:stop:<номер стоп-заявки>:<номер сделки биржи>`;
- снять заявки целей сделки;
- отправить в канал строку «стоп сработал у брокера».

Остаток, не исполненный рыночной заявкой за `exit_requote_secs`, ДОЛЖЕН добирать цикл выхода от последней цены. Незнакомый отчёт, не сопоставленный за 60 секунд, ДОЛЖЕН считаться чужим: его показывает сверщик. Сопоставление только по инструменту, стороне и объёму НЕ ДОЛЖНО делаться.

Стоп-заявка, которую брокер показал снятой или истёкшей без отмены контура, ДОЛЖНА закрываться в журнале. Хранитель стопа ставит новую.

Пока у сделки есть активная стоп-заявка на весь желаемый объём по желаемой цене, контур НЕ ДОЛЖЕН проверять условие стопа по минутам. Без неё (стоп ставится, пересоздаётся, отклонён из-за закрытых торгов) условие ДОЛЖЕН проверять контур по требованию «Выходы лимитными заявками».

#### Scenario: Стоп сработал у брокера
- **GIVEN** у длинной сделки NG 2 лота активная стоп-заявка по 2.812 и заявка цели на 1 лот
- **WHEN** песочница исполнила стоп-заявку, стрим принёс отчёт порождённой рыночной заявки без нашего ключа
- **THEN** стоп-заявка найдена по `exchange_order_id`, продажа 2 лотов проведена защитным выходом, заявка цели снята, сделка закрыта, в канале «стоп сработал у брокера», лишних заявок нет

#### Scenario: Минута через стоп при живом стопе у брокера
- **GIVEN** у сделки активная стоп-заявка на весь остаток
- **WHEN** закрытая минута ядра прошла через стоп, а отчёт брокера ещё не пришёл
- **THEN** контур своего выхода не начинает, выход приходит от стоп-заявки брокера

#### Scenario: Окно пересоздания
- **GIVEN** прежняя стоп-заявка снята, новая ещё не активна
- **WHEN** закрытая минута ядра прошла через стоп
- **THEN** контур выходит стоп-лимитом по циклу выхода, новая стоп-заявка не ставится

#### Scenario: Чужая заявка
- **GIVEN** стрим принёс отчёт заявки, которой нет ни в журнале, ни среди `exchange_order_id` наших стоп-заявок
- **WHEN** прошло 60 секунд
- **THEN** отчёт считается чужим, расхождение показывает сверка

### Requirement: Стоп-заявки после простоя
Нормативный уровень: MUST. До первого тика, после разбора журнала заявок и до сверки, контур ДОЛЖЕН:

1. сверить незавершённые строки стоп-заявок с `GetStopOrders` за период с самой ранней;
2. стоп-заявку, исполненную за простой, провести по требованию «Срабатывание стоп-заявки у брокера». Сделки берутся из `GetOrderState` по номеру биржи порождённой заявки, а без сделок — средняя по сумме заявки;
3. разобрать строки `unknown`;
4. привести стоп-заявки к желаемым: срезать объём, поставить недостающие, снять стоп-заявки сделок без остатка.

Потерянный ответ `PostStopOrder` (тайм-аут, обрыв, процесс упал в `sending`) ДОЛЖЕН переводить строку в `unknown`. Разбор:

- поиск среди активных стоп-заявок того же инструмента, стороны, объёма и стоп-цены, созданных не раньше чем за 5 секунд до отправки и не привязанных к другой строке;
- найдена одна — строка `active` с её номером;
- не найдена, желаемого нет — `cancelled`;
- не найдена, а с отправки прошло меньше 15 секунд — строка ждёт следующего опроса;
- не найдена через 15 секунд — строка становится `lost`, и хранитель ставит новую стоп-заявку **новым ключом** обычным путём;
- найдено больше одной — строка остаётся `unknown`, расхождение показывает сверка.

`PostStopOrder` тем же ключом НЕ ДОЛЖЕН повторяться: песочница на повтор ключа создаёт вторую стоп-заявку (разведка П20).

Строка `lost` ДОЛЖНА ждать своей стоп-заявки у брокера 10 минут с отправки по тем же признакам. Нашлась ровно одна — контур ДОЛЖЕН привязать её к строке и сразу снять (`CancelStopOrder`), строка `cancelled` с причиной `duplicate`, в канал — событие `broker_order` `stop_duplicate_cancelled` («лишняя стоп-заявка снята»). Через 10 минут без находки строка `cancelled` с причиной `undelivered`. Пока у инструмента есть строки `lost`, его стоп-заявки в сверке считаются «в пути» и не сравниваются.

Потерянный ответ `CancelStopOrder` ДОЛЖЕН разбираться по статусу из `GetStopOrders`.

Штатный выход процесса, `kill` и `no_entries` ДОЛЖНЫ оставлять стоп-заявки у брокера.

#### Scenario: Стоп сработал, пока контур убит
- **GIVEN** у сделки NG активная стоп-заявка, процесс контура убит, за простой песочница исполнила стоп-заявку
- **WHEN** контур запущен снова
- **THEN** до первого тика сделка закрыта по сделкам порождённой заявки, заявки целей сняты, стоп-заявок нет, сверка `ok`

#### Scenario: Потерянный ответ на постановку
- **GIVEN** `PostStopOrder` ушёл, процесс упал до ответа, стоп-заявка у брокера активна
- **WHEN** контур запущен снова
- **THEN** стоп-заявка найдена по инструменту, стороне, объёму и цене, у брокера одна стоп-заявка

#### Scenario: Потерянный ответ, стоп-заявка показалась позже
- **GIVEN** ответ на `PostStopOrder` 10 лотов NG по 2.901 потерян, 15 секунд `GetStopOrders` её не показывает
- **WHEN** хранитель ставит новую стоп-заявку новым ключом, а на следующем опросе у брокера видны обе
- **THEN** первая привязана к строке `lost` и снята, у брокера одна стоп-заявка на 10 лотов, в канале «лишняя стоп-заявка снята», тревоги сверки нет

#### Scenario: Потерянный ответ, стоп-заявка не дошла
- **GIVEN** ответ на `PostStopOrder` потерян, у брокера её нет
- **WHEN** проходит 15 секунд, затем 10 минут
- **THEN** через 15 секунд стоит новая стоп-заявка новым ключом, через 10 минут строка прежней — `cancelled` с причиной `undelivered`, тем же ключом ничего не отправлялось

#### Scenario: Ручная продажа части за простой
- **GIVEN** у длинной сделки 10 лотов стоп-заявка на 10, процесс убит, командой песочницы продано 4 лота
- **WHEN** контур запущен снова
- **THEN** сверка показывает расхождение позиции тревогой, позиция по журналу не меняется, стоп-заявка срезана до 6 лотов — позиции на счёте

#### Scenario: Сделка открыта до обновления
- **GIVEN** сделка открыта сборкой без стоп-заявок, стопа у брокера нет
- **WHEN** контур поднялся на новой сборке
- **THEN** до первого тика у брокера поставлена стоп-заявка на остаток с причиной «рестарт»

### Requirement: Контур «Счёт» отдельным процессом
Нормативный уровень: MUST. Контур на брокере вида `account` ДОЛЖЕН работать процессом `run.py --contour account`, который запускает ядро. Папка контура — `data/contours/account/`, состав файлов тот же, что у песочницы (требование «Контур «Песочница» отдельным процессом»). Процесс, сверщик, уведомления, журнал и `status.json` ДОЛЖНЫ быть общим кодом с песочницей; вид отличается шлюзом, правилом счёта, допуском и настройками.

До Р2 контур «Счёт» ДОЛЖЕН работать только на чтение, как песочница при `orders = false`:

- НЕ ДОЛЖЕН отправлять и снимать заявки и стоп-заявки;

- НЕ ДОЛЖЕН строить торговую часть.

Карточки контура ДОЛЖНЫ уходить в канал «Счёт» с меткой «СЧЁТ».

#### Scenario: Процесс счёта
- **WHEN** ядро запускает контур «Счёт»
- **THEN** работает процесс `run.py --contour account`, его лог и `status.json` лежат в `data/contours/account/`, процессы песочницы и эмуляции работают дальше

#### Scenario: Только чтение
- **GIVEN** контур «Счёт» работает
- **WHEN** проходит любое число шагов
- **THEN** в записях вызовов шлюза счёта нет `PostOrder`, `PostStopOrder`, `CancelOrder` и `CancelStopOrder`

### Requirement: Шлюз и счёт контура «Счёт»
Нормативный уровень: MUST. С брокером контур «Счёт» ДОЛЖЕН работать через шлюз счёта: обычный клиент Т-Инвест на адресе брокера с токеном `TINKOFF_TRADE_TOKEN`. Повторы при лимите частоты, дедлайн вызова и записи вызовов ДОЛЖНЫ быть такими же, как у шлюза песочницы. Вызов сервиса песочницы (`sandbox.*`) через шлюз счёта ДОЛЖЕН отклоняться до сети ошибкой шлюза с кодом `SANDBOX_ONLY`.

Счёт робота ДОЛЖЕН определяться так:

1. `GetAccounts` по токену;
2. открытый счёт ровно один, и его номер равен `TINKOFF_ACCOUNT_ID`;
3. `access_level` этого счёта — полный доступ или только чтение.

Контур НЕ ДОЛЖЕН открывать, переименовывать или выбирать счёт по имени.

#### Scenario: Токен видит два счёта
- **GIVEN** токен видит два открытых счёта
- **WHEN** контур «Счёт» стартует
- **THEN** процесс выходит с кодом 2, причина называет число счетов и их последние четыре символа, полных номеров нет нигде

#### Scenario: Номер не совпал
- **GIVEN** токен видит один счёт, а `TINKOFF_ACCOUNT_ID` указывает другой
- **WHEN** контур «Счёт» стартует
- **THEN** процесс выходит с кодом 2, причина «Токен видит счёт …XXXX, а TINKOFF_ACCOUNT_ID задаёт другой»

#### Scenario: Вызов песочницы
- **WHEN** код вызывает `sandbox.sandbox_pay_in` через шлюз счёта
- **THEN** ошибка шлюза с кодом `SANDBOX_ONLY`, к брокеру запроса нет

### Requirement: Допуск контура «Счёт» к старту
Нормативный уровень: MUST. До первого шага контур «Счёт» ДОЛЖЕН проверить по порядку:

1. заданы `TINKOFF_TRADE_TOKEN` и `TINKOFF_ACCOUNT_ID`;
2. в окружении заданы бот и канал из `[contours.account] telegram_bot_env` и `telegram_channel_env`;
3. счёт определён по требованию «Шлюз и счёт контура «Счёт»»;
4. права токена допустимы для режима: при `orders = false` — только чтение или полный доступ, при `orders = true` — только полный доступ;
5. `GetInfo` прочитан: тариф и список `qualified_for_work_with`; при `orders = true` в списке ДОЛЖЕН быть допуск к срочным контрактам;
6. `GetUserTariff` прочитан;
7. отпечаток счёта вида `account` совпадает с записанным или записывается впервые;
8. капитал, позиции, заявки и стоп-заявки счёта прочитаны.

Отказ на пунктах 1–5, 7, 8 ДОЛЖЕН завершать процесс с кодом 2 до первого шага с причиной в `status.json`, логе и `GET /api/v1/account`, как у песочницы. При `orders = false` нет допуска к срочным контрактам или сбой `GetUserTariff` НЕ ДОЛЖНЫ мешать старту: это предупреждения в карточке `started`, в `status.json` и в `current.admission.warnings`.

Факты допуска ДОЛЖНЫ попадать в `status.json` и `GET /api/v1/account` (`current.admission`): права токена, список `qualified_for_work_with`, есть ли допуск к срочным контрактам, тариф, лимиты сервисов заявок, стоп-заявок и операций, предупреждения.

### Requirement: Порядок подъёма контуров на брокере
Нормативный уровень: MUST. Ядро ДОЛЖНО держать по надзирателю на каждый вид контура на брокере. Когда ядро стало готово, судьбы контуров ДОЛЖНЫ решаться по порядку: «Счёт», затем «Песочница», затем эмуляция — каждая по своей папке и желаемому состоянию, по правилам требования «Подъём контура «Песочница» при старте ядра». Отказ, ожидание выхода другой версии или ожидание команды у одного контура НЕ ДОЛЖНЫ задерживать решение по следующим. Автоподъём «Счёта» НЕ ДОЛЖЕН создавать новое поколение.

- **WHEN** робот запускается снова
- **THEN** процесс «Счёта» запускается раньше процесса песочницы, песочницы — раньше эмуляции, у всех `launch.recovery = autostart`

### Requirement: Разведка комиссий на чужой сделке
Нормативный уровень: MUST. Пока контур «Счёт» работает только на чтение, после каждого найденного сверщиком изменения чужой позиции по инструменту контур ДОЛЖЕН через 15 минут прочитать `GetOperationsByCursor` по этому инструменту за окно от минуты до предыдущей сверки до текущего момента и записать в `broker.sqlite3`:

- время, инструмент, номер операции сделки последними четырьмя символами;
- П25 — есть ли в операции `trades_info` с номерами сделок биржи;
- П26 — есть ли операция «комиссия брокера» с `parent_operation_id`, равным номеру операции сделки, её сумма и сумма поля `commission`.

Последние 10 записей ДОЛЖНЫ быть в `GET /api/v1/account/reconcile` (`fee_probes`), каждая запись — одной строкой в логе. Сбой чтения операций ДОЛЖЕН записываться типом ошибки и повторяться на следующей сверке не более трёх раз. Правило комиссии исполнений НЕ ДОЛЖНО меняться.

- **WHEN** проходит 15 минут

Полный номер счёта и токен НЕ ДОЛЖНЫ попадать в `broker.sqlite3`, `status.json`, лог, карточки, ответы API и записи вызовов шлюза; номер — только последними четырьмя символами. Ошибки шлюза счёта ДОЛЖНЫ логироваться типом и кодом, без текста ответа брокера.

#### Scenario: Номер счёта в логе
