# control-api Specification

## Purpose
Управление запуском торгового контура через локальный HTTP API робота: ожидание команды, запуск эмуляции выбранными инструментами, состояние контура и доступ по отдельному ключу управления. Первый этап перехода к ядру и торговым контурам (`docs/architecture/core-contours.md`).

## Requirements

### Requirement: Ожидание команды запуска
Нормативный уровень: MUST. Робот ДОЛЖЕН всегда стартовать в ожидании команд API: эмуляция — командой `PUT /api/v1/emulation/target` с `mode = on` или автоподъёмом по целевому состоянию, история — командой `POST /api/v1/history`. Пока робот ждёт, полосы рыночных данных ДОЛЖНЫ работать по сохранённому составу, торговля эмуляции НЕ ДОЛЖНА начинаться без команды или автоподъёма. Консоль ДОЛЖНА показывать адреса команд без значения ключа.

Параметры `--mode`, `--instruments`, `--wait-command`, `--no-prompt`, `--from`, `--to`, `--pause` ДОЛЖНЫ отклоняться: процесс печатает, что робот запускается без параметров, называет команду `PUT /api/v1/emulation/target` для эмуляции и `POST /api/v1/history` для истории, затем завершается с кодом `2`.

#### Scenario: Робот ждёт команды
- **GIVEN** задан `ROBOT_CONTROL_TOKEN`, целевого состояния «работает» нет
- **WHEN** робот запущен без параметров и ядро стартовало
- **THEN** полосы данных работают, торговли нет, в консоли — «Робот ждёт команду запуска: PUT http://127.0.0.1:8101/api/v1/emulation/target», а `GET /api/v1/emulation` показывает состояние `waiting_command`

#### Scenario: Ключ управления не задан
- **WHEN** робот запущен, а `ROBOT_CONTROL_TOKEN` пуст
- **THEN** печатается, что без ключа управления роботом нельзя управлять, процесс завершается с кодом `2`

#### Scenario: Несовместимые параметры
- **WHEN** робот запущен с `--mode emulation --instruments NG`
- **THEN** печатается, что робот запускается без параметров, а эмуляция запускается командой `PUT /api/v1/emulation/target`; процесс завершается с кодом `2`

### Requirement: Запуск эмуляции командой API
Нормативный уровень: MUST. `PUT /api/v1/emulation/target` с телом `{"mode": "on", "instruments": [...]}` ДОЛЖЕН запускать торговлю эмуляции выбранными инструментами. Поле `instruments` НЕ ОБЯЗАТЕЛЬНО, его отсутствие ДОЛЖНО означать `all`. Имена инструментов ДОЛЖНЫ разрешаться и проверяться по правилам требования «Инструменты из параметров запуска» (спецификация `instruments`). Разрешение, сборка торговых компонентов и запуск ДОЛЖНЫ выполняться главным потоком робота, а не потоком HTTP.

Команда ДОЛЖНА приниматься, когда робот ждёт команду, а также после остановки (`stopped`) или падения (`failed`) контура: ядро ДОЛЖНО запустить процесс контура заново тем же процессом робота, без перезапуска приёма данных. Набор инструментов повторного запуска МОЖЕТ отличаться от прежнего. Принятая команда ДОЛЖНА записывать в `core.sqlite3` желаемое «работает» с новым номером поколения и выбранным составом.

Ответы:
- `202` — инструменты разрешены, торговля запускается; тело — эмуляция (требование «Состояние контура») с выбранными контрактами в составе, эквивалентной командой и `target.revision`, заголовки `Location: /api/v1/emulation` и `ETag`. Если проверка инструментов не уложилась в 60 секунд, тело — состояние `starting` без новой ревизии, итог виден в `GET /api/v1/emulation`;
- `400` — тело не JSON-объект, неизвестные поля, `mode` не `on`, `no_entries` или `close_all`, `instruments` не список строк или передан вместе с режимом остановки;
- `401`, `403` — по правилам доступа к управлению;
- `409` — один из кодов:
  - `ALREADY_RUNNING` — контур запускается или торгует;
  - `STOPPING` — контур выполняет остановку и доживает сделки;
  - `CORE_NOT_READY` — ядро стартует, повторяет старт или не стартовало;
  - `CONTOUR_DIR_BUSY` — папку контура держит процесс, который не подтвердил себя контуром;

  целевое состояние и набор инструментов не меняются;
- `412` — по требованию «Защита от одновременных команд»;
- `422` — хотя бы одно имя отклонено; тело содержит `rejections` с именем и причиной; торговля НЕ ДОЛЖНА начинаться ни по одному инструменту.

После `422` робот ДОЛЖЕН продолжать ждать команды. Контракты в ответах ДОЛЖНЫ называться коротким именем, а не биржевым тикером. Эквивалентная команда — `launch.request`: тело `PUT /api/v1/emulation/target` объектом с выбранными контрактами коротким именем. Консоль и журнал ДОЛЖНЫ печатать её строкой «Повторить запуск: PUT /api/v1/emulation/target {…}».

#### Scenario: Запуск газа и Сбера
- **GIVEN** робот ждёт команды, у NG и SBER есть привязки
- **WHEN** приходит `PUT /api/v1/emulation/target` с `{"mode": "on", "instruments": ["NG-12.26", "SBER"]}` и верным ключом
- **THEN** ответ `202` содержит NG-12.26 с днями до экспирации, SBER, `launch.request = {"mode": "on", "instruments": ["NG-12.26", "SBER"]}` и `target.revision`, а торговля этими инструментами начинается

#### Scenario: Всё с привязками
- **WHEN** приходит `PUT /api/v1/emulation/target` с `{"mode": "on"}` без `instruments`
- **THEN** торгуются все акции и ближайшие контракты всех семейств с привязками, `launch.request` называет контракты коротким именем

#### Scenario: Один инструмент отклонён
- **WHEN** приходит команда с `["NG-12.26", "AFLT"]`, а у AFLT нет привязок
- **THEN** ответ `422` называет AFLT и причину, торговля не начинается ни по NG-12.26, ни по AFLT, робот продолжает ждать

#### Scenario: Повторный запуск
- **WHEN** торговля уже идёт, а приходит `PUT /api/v1/emulation/target` с `mode = on`
- **THEN** ответ `409` с кодом `ALREADY_RUNNING`, набор инструментов не меняется

#### Scenario: История через API
- **WHEN** приходит `POST /api/v1/history` с `{"from": "2026-09-01 10:00", "to": "2026-09-08 10:00"}`
- **THEN** ответ `202`, прогон истории поставлен в очередь, контур эмуляции и его целевое состояние не меняются

#### Scenario: Долгая проверка у брокера
- **WHEN** проверка инструментов у источника заняла больше 60 секунд из-за лимитов
- **THEN** ответ `202` с состоянием `starting`, а `GET /api/v1/emulation` затем показывает `running` или отказы в `launch.rejections`

#### Scenario: Запуск после остановки другим набором
- **GIVEN** контур эмуляции торговал NG-12.26 и SBER и остановлен командой, процесс завершился с кодом 0
- **WHEN** приходит `PUT /api/v1/emulation/target` с `{"mode": "on", "instruments": ["BR-12.26", "SBER"]}`
- **THEN** ответ `202` с новой ревизией, ядро без перезапуска приёма данных запускает новый процесс контура с BR-12.26 и SBER

#### Scenario: Запуск во время дожития сделок
- **GIVEN** контур остановлен командой `no_entries` и сопровождает открытую позицию NG-12.26
- **WHEN** приходит `PUT /api/v1/emulation/target` с `mode = on`
- **THEN** ответ `409` с кодом `STOPPING`, остановка продолжается

#### Scenario: Ядро не готово
- **GIVEN** старт ядра упал и ждёт повтора
- **WHEN** приходит `PUT /api/v1/emulation/target` с `{"mode": "on"}`
- **THEN** ответ `409` с кодом `CORE_NOT_READY` и полем `core`, целевое состояние не меняется

#### Scenario: Папка контура занята
- **GIVEN** `robot.pid` папки контура называет живой процесс, который не подтвердил себя контуром
- **WHEN** приходит команда запуска
- **THEN** ответ `409` с кодом `CONTOUR_DIR_BUSY` и `pid`; робот, API и история продолжают работать

### Requirement: Состояние контура
Нормативный уровень: MUST. `GET /api/v1/emulation` с ключом управления ДОЛЖЕН возвращать контур эмуляции и заголовок `ETag`. Поля:

- **`state`** — общее состояние: `waiting_command`, `starting`, `running`, `stopping_no_entries`, `stopping_close_all`, `stopped` или `failed`.
- **`target`** — целевое состояние из `core.sqlite3` или `null`, если эмуляцию ни разу не запускали:
  - `mode` — `on`, `no_entries` или `close_all`;
  - `revision`.
- **`current`** — текущее состояние из `status.json` контура или `null`, если файла нет или он не читается:
  - `state`;
  - `applied_revision`;
  - `open_positions`;
  - `pending_entries`;
  - `last_tick_at`;
  - `core_link`: `ok` или `lost` — видит ли контур пульс ядра.
- **`launch`** — о запуске:
  - `source`: `api`; у целевого состояния, записанного прежними версиями, МОГУТ быть `cli` или `menu`;
  - `recovery`: `autostart`, если процесс поднят ядром без команды; `adopted`, если подхвачен живым; иначе `null`;
  - `started_at`;
  - `request` — эквивалентная команда объектом;
  - `rejections` — отказы последней команды, если она отклонена.

  При автоподъёме и подхвате источник и команда ДОЛЖНЫ браться из целевого состояния.
- **`process`** — `pid`, пока процесс жив; `exit_code` и `exited_at` после завершения; `dir` — папка контура. У подхваченного процесса код выхода неизвестен: `exit_code = null`.
- **`instruments`** — все инструменты целевого состава, включая убираемые. У каждого:
  - `name` — короткое имя контракта или тикер акции, то же имя, что в командах;
  - `instrument_type` и `days_to_expiry`;
  - `target`: `active` или `removed`, и `remove_mode`;
  - `current` из `status.json`: `warming`, `trading`, `draining`, `closing` или `null`;
  - `_links` и `_actions`.

  После изменения состава командой поле ДОЛЖНО показывать новый состав, а не состав запуска.
- **`_links`** и **`_actions`** — по требованию «Ссылки и доступные действия».

Общее состояние ДОЛЖНО определяться так:

1. **Процесс завершился:** `stopped` при коде 0, `failed` при другом коде или неизвестном коде подхваченного процесса. Если в этом запуске ядра процесс не создавался и не подхватывался — `waiting_command`.
2. **Процесс жив, целевое состояние — остановка:** `stopping_<режим>`.
3. **Процесс жив, контур ещё ни разу не подтвердил курсор ленты в этом запуске ядра:** `starting`.
4. **Иначе:** `running`.

`GET /api/v1/emulation/target` ДОЛЖЕН возвращать только `target` с `ETag` или `404`, если эмуляцию не запускали. `GET /api/v1/emulation/instruments` ДОЛЖЕН возвращать состав с `revision`, `GET /api/v1/emulation/instruments/{name}` — одного участника или `404`.

После рестарта ядра без автоподъёма и подхвата контур ДОЛЖЕН показываться в `waiting_command` с прежним целевым состоянием. Ответ НЕ ДОЛЖЕН содержать сделки, баланс и секреты. Список прогонов истории задаёт требование «Состояние прогонов истории».

#### Scenario: Торговля запущена параметрами
- **WHEN** эмуляция запущена командой `PUT /api/v1/emulation/target` с NG-12.26, контур подтвердил курсор, а затем приходит `GET /api/v1/emulation`
- **THEN** состояние `running`, `launch.source = api`, NG-12.26 в `instruments`, `target.mode = on`, `launch.recovery = null` и `process.pid` процесса контура

#### Scenario: Последняя команда отклонена
- **WHEN** команда запуска получила `422`, а затем приходит `GET /api/v1/emulation`
- **THEN** состояние `waiting_command`, `launch.rejections` содержит отказы последней команды

#### Scenario: Процесс контура упал
- **WHEN** процесс контура завершился с кодом 1, а затем приходит `GET /api/v1/emulation`
- **THEN** состояние `failed`, `process.pid = null`, `process.exit_code = 1`

#### Scenario: Ядро перезапущено, желаемое — работает
- **GIVEN** до рестарта ядра контур работал с ревизией 5, источник `api`
- **WHEN** робот запущен снова, контур подтвердил курсор, а затем приходит `GET /api/v1/emulation`
- **THEN** состояние `running`, `launch.recovery = autostart`, источник `api`, `target.revision = 5`

#### Scenario: Подхваченный контур завершился сам
- **GIVEN** контур подхвачен и завершился, не записав `exited_at`
- **WHEN** приходит `GET /api/v1/emulation`
- **THEN** состояние `failed`, `process.exit_code = null`

#### Scenario: Фактическое отстаёт от желаемого
- **GIVEN** контур работает с применённой ревизией 3
- **WHEN** приходит команда остановки, а `GET` выполняется до следующей границы тика
- **THEN** `target.revision = 4`, `current.applied_revision = 3`, общее состояние `stopping_no_entries`

#### Scenario: Состав после изменения
- **GIVEN** эмуляция запущена с NG-12.26 и SBER, затем добавлен BR-12.26 и убран SBER с открытой позицией
- **WHEN** приходит `GET /api/v1/emulation`
- **THEN** `instruments` — NG-12.26 `active/trading`, BR-12.26 `active/warming` и SBER `removed/no_entries/draining`

#### Scenario: Список с прогонами
- **GIVEN** эмуляция торгует, идёт один прогон истории, один ждёт
- **WHEN** приходит `GET /api/v1/emulation`
- **THEN** ответ — только контур эмуляции; прогоны показывает `GET /api/v1/history`

### Requirement: Доступ к управлению
Нормативный уровень: MUST. Маршруты управления — `/api/v1/core`, `/api/v1/emulation…` и `/api/v1/history…` — ДОЛЖНЫ требовать ключ `ROBOT_CONTROL_TOKEN` в заголовке `Authorization: Bearer` и НЕ ДОЛЖНЫ принимать его в адресе запроса или cookie. Точка входа `GET /api/v1` ДОЛЖНА принимать любой из двух ключей. Ключ экспорта рыночных данных НЕ ДОЛЖЕН давать доступ к управлению, а ключ управления — к экспорту. Маршруты управления ДОЛЖНЫ отклонять запрос, если заголовок `Host` не равен `127.0.0.1`, `localhost` или `[::1]` с портом сервера. Сервер НЕ ДОЛЖЕН отдавать заголовки CORS. `ROBOT_CONTROL_TOKEN` ДОЛЖЕН быть в `secrets` журнала и НЕ ДОЛЖЕН печататься нигде.

#### Scenario: Ключ экспорта для управления
- **WHEN** команда запуска приходит с ключом `MARKET_DATA_EXPORT_TOKEN`
- **THEN** ответ `401` с кодом `UNAUTHORIZED`, торговля не начинается

#### Scenario: Чужой Host
- **WHEN** команда запуска приходит с верным ключом, но с заголовком `Host: evil.example:8101`
- **THEN** ответ `403`, торговля не начинается

#### Scenario: Ключ в адресе
- **WHEN** ключ передан параметром адреса, а заголовка `Authorization` нет
- **THEN** ответ `401`

### Requirement: Остановка контура командой
Нормативный уровень: MUST. `PUT /api/v1/emulation/target` с телом `{"mode": "no_entries"}` или `{"mode": "close_all"}` ДОЛЖЕН записывать в `core.sqlite3` желаемое «остановлен» с режимом и новым поколением и отвечать `202` с эмуляцией и новой `target.revision`. Повтор команды с тем же режимом ДОЛЖЕН отвечать `200` с прежней ревизией и НЕ ДОЛЖЕН её менять. `close_all` поверх `no_entries` ДОЛЖЕН приниматься новой ревизией. `no_entries` поверх `close_all` ДОЛЖЕН отклоняться `409` с кодом `MODE_CONFLICT`.

Остальные ответы:
- `409 NOT_RUNNING` — контур не работает: `waiting_command`, `stopped` или `failed`;
- `400` — неверный режим, лишние поля, `instruments` вместе с режимом остановки;
- `412` — по требованию «Защита от одновременных команд»;
- `401`/`403` — по правилам доступа к управлению.

Остановку прогона истории задаёт требование «Остановка прогона истории».

Остановка НЕ ДОЛЖНА останавливать ядро, приём данных и локальный API. Ctrl+C ядра ДОЛЖЕН по-прежнему останавливать процесс контура после тика, не меняя целевое состояние.

#### Scenario: Остановка без новых входов
- **GIVEN** контур работает, ревизия 3
- **WHEN** приходит `PUT /api/v1/emulation/target` с `{"mode": "no_entries"}`
- **THEN** ответ `202` с `target.revision = 4`, в `core.sqlite3` желаемое «остановлен, no_entries», ядро и приём данных продолжают работать

#### Scenario: Повтор остановки
- **GIVEN** уже принята остановка `no_entries` с ревизией 4
- **WHEN** та же команда приходит снова
- **THEN** ответ `200` с ревизией 4, в журнале команд исход `ignored`

#### Scenario: Закрыть всё поверх дожития
- **GIVEN** контур доживает сделки после `no_entries`, ревизия 4
- **WHEN** приходит `PUT /api/v1/emulation/target` с `{"mode": "close_all"}`
- **THEN** ответ `202` с ревизией 5, контур переходит к закрытию всех позиций

#### Scenario: Дожитие поверх закрытия
- **GIVEN** принята остановка `close_all`
- **WHEN** приходит `{"mode": "no_entries"}`
- **THEN** ответ `409` с кодом `MODE_CONFLICT`, ревизия не меняется

#### Scenario: Нечего останавливать
- **WHEN** контур в состоянии `stopped`, а приходит `{"mode": "no_entries"}`
- **THEN** ответ `409` с кодом `NOT_RUNNING`, ревизия не меняется

### Requirement: Желаемое состояние и журнал команд ядра
Нормативный уровень: MUST. Ядро ДОЛЖНО хранить желаемое состояние контуров в `data/core.sqlite3`: вид, должен ли работать, режим остановки, номер поколения, состав, источник и эквивалентную команду. Каждая команда управления ДОЛЖНА записываться в журнал `contour_commands`: время, действие, тело без секретов, поколение и исход (`accepted`, `rejected`, `conflict`, `ignored`).

Номер поколения ДОЛЖЕН расти монотонно на каждую команду, меняющую желаемое. Писать в `core.sqlite3` ДОЛЖНО только ядро, контур ДОЛЖЕН открывать её только на чтение. База ДОЛЖНА хранить версию схемы.

#### Scenario: Поколения растут
- **WHEN** подряд приняты запуск, остановка `no_entries` и остановка `close_all`
- **THEN** их поколения — 1, 2, 3, а журнал содержит три записи с исходом `accepted`

#### Scenario: Отклонённый запуск в журнале
- **WHEN** команда запуска получила `422`
- **THEN** в журнале запись с исходом `rejected` и причинами, поколение не меняется

### Requirement: Лог контура через API
Нормативный уровень: MUST. `GET /api/v1/emulation/log?tail=N` ДОЛЖЕН отдавать последние `N` строк журнала процесса контура эмуляции в `text/plain; charset=utf-8`. По умолчанию `N` равно 200, допустимо от 1 до 1000, иначе `400`. Отсутствующий журнал — пустой ответ `200`.

Ответ ДОЛЖЕН содержать строки так, как они записаны в журнал, где секреты уже заменены на `[скрыто]`. Маршрут ДОЛЖЕН требовать ключ управления.

#### Scenario: Последние строки
- **GIVEN** в журнале контура 5000 строк
- **WHEN** приходит `GET /api/v1/emulation/log?tail=3`
- **THEN** ответ — три последние строки журнала

#### Scenario: Слишком длинный хвост
- **WHEN** приходит `GET /api/v1/emulation/log?tail=5000`
- **THEN** ответ `400`

### Requirement: Состав контура командами
Нормативный уровень: MUST. Состав работающей эмуляции ДОЛЖЕН меняться без перезапуска контура двумя пакетными командами:

- **Добавить** — `POST /api/v1/emulation/instruments` с `{"instruments": [имена]}`. Имена — тикеры акций и короткие имена контрактов по требованию «Инструменты из параметров запуска»; разрешение — в главном потоке ядра, карточку контракта ДОЛЖНО получать ядро. Отказ строгий: если хотя бы одно имя отклонено, состав НЕ ДОЛЖЕН меняться (`422`).
- **Убрать** — `POST /api/v1/emulation/instruments/remove` с `{"instruments": [имена], "mode": "no_entries" | "close_all"}`. Имя ДОЛЖНО совпадать с `name` участника состава. Без `mode` ДОЛЖЕН применяться `no_entries`. Если хотя бы одного имени нет в составе, состав НЕ ДОЛЖЕН меняться (`422`).

Метод `DELETE` для удаления из состава НЕ ДОЛЖЕН использоваться.

Принятая команда ДОЛЖНА записывать изменение в таблицу `contour_members` базы `core.sqlite3` одной транзакцией и поднимать поколение контура один раз. Ответ — `202` с составом (как `GET /api/v1/emulation/instruments`), его `revision` и заголовком `ETag`.

Повторы и переходы:

- **Повтор без изменений.** Если команда ничего не меняет — добавляется уже активный инструмент, повторно убирается с тем же режимом — ответ ДОЛЖЕН быть `200` с прежней ревизией.
- **`close_all` поверх `no_entries`** у убираемого инструмента ДОЛЖЕН приниматься.
- **`no_entries` поверх `close_all`** ДОЛЖЕН отклоняться `409 MODE_CONFLICT`.
- **Добавление убираемого инструмента** ДОЛЖНО возвращать его в активный состав.

Остальные ответы:

- `409 NOT_RUNNING` — процесс контура не работает;
- `409 STOPPING` — контур выполняет остановку;
- `400` — неверное тело;
- `412` — по требованию «Защита от одновременных команд»;
- `202` с `revision = null` — разрешение не уложилось в 60 секунд, итог виден в `GET /api/v1/emulation`.

Запуск контура (`mode = on`) ДОЛЖЕН заменять целевой состав составом запуска. Каждая команда состава ДОЛЖНА записываться в журнал команд.

#### Scenario: Добавить газ на ходу
- **GIVEN** эмуляция торгует SBER, ревизия 1
- **WHEN** приходит `POST /api/v1/emulation/instruments` с `{"instruments": ["NG-12.26"]}`
- **THEN** ответ `202` с ревизией 2, в `contour_members` NG-12.26 `active` с карточкой контракта, SBER продолжает торговать

#### Scenario: Убрать Сбер без режима
- **WHEN** приходит `POST /api/v1/emulation/instruments/remove` с `{"instruments": ["SBER"]}`
- **THEN** SBER становится `removed` с режимом `no_entries`, ответ `202`

#### Scenario: Убрать два инструмента сразу
- **GIVEN** эмуляция торгует NG-12.26 и SBER, ревизия 2
- **WHEN** приходит `POST /api/v1/emulation/instruments/remove` с `{"instruments": ["NG-12.26", "SBER"], "mode": "close_all"}`
- **THEN** ответ `202` с ревизией 3, оба инструмента `removed` с режимом `close_all`

#### Scenario: Отклонённое добавление

- **THEN** ответ `422` называет AFLT, NG-12.26 не добавляется, ревизия не меняется

#### Scenario: Убрать то, чего нет

- **THEN** ответ `422` называет GAZP, SBER не убирается, состав не меняется

#### Scenario: Состав во время остановки контура
- **GIVEN** контур выполняет остановку `no_entries`
- **WHEN** приходит `POST /api/v1/emulation/instruments` с `{"instruments": ["NG-12.26"]}`
- **THEN** ответ `409 STOPPING`, состав не меняется

- **WHEN** приходит `POST /api/v1/emulation/instruments` с `{"instruments": ["SBER"]}`
- **THEN** ответ `202` с новой ревизией, SBER снова `active`

### Requirement: Пульс ядра
Нормативный уровень: MUST. Ядро ДОЛЖНО вести в `core.sqlite3` таблицу `heartbeat`. Состав строки:

- pid и версия ядра;
- время старта;
- время последнего удара;
- состояние: `running` или `stopped`.

Ядро ДОЛЖНО обновлять время удара раз в `[contours] heartbeat_secs` (по умолчанию 5 с) отдельным потоком. Первый удар ДОЛЖЕН быть записан до подхвата или запуска процесса контура. При штатной остановке ядро ДОЛЖНО записать состояние `stopped` до ожидания выхода контура. Писать таблицу ДОЛЖНО только ядро. Конфигурация с `heartbeat_timeout_secs`, не превышающим `heartbeat_secs`, ДОЛЖНА отклоняться при загрузке.

#### Scenario: Пульс идёт
- **WHEN** ядро работает 20 секунд с `heartbeat_secs = 5`
- **THEN** время удара в `heartbeat` обновлялось не реже раза в 5 секунд, состояние `running`, версия равна версии робота

#### Scenario: Штатная остановка ядра
- **WHEN** пользователь нажимает Ctrl+C в консоли ядра
- **THEN** строка `heartbeat` получает состояние `stopped` раньше, чем ядро начинает ждать выхода контура

### Requirement: Автоподъём и подхват контура при старте ядра
Нормативный уровень: MUST. Когда ядро стало готово (требование «Повтор старта ядра»), оно ДОЛЖНО определить судьбу контура эмуляции по `robot.pid` папки контура, её `status.json` и желаемому из `core.sqlite3`.

**Живой контур.** Контур считается живым при трёх условиях:

1. pid из `robot.pid` папки контура жив;
2. `status.json` называет тот же pid;
3. `alive_at` в `status.json` свежее `heartbeat_timeout_secs`.

- **Та же версия.** Ядро ДОЛЖНО подхватить живой контур: НЕ ДОЛЖНО запускать второй процесс, ДОЛЖНО следить за найденным процессом по pid и передавать стоп и состав через `core.sqlite3`. Поле `launch.recovery` — `adopted`.
- **Другая версия.** Ядро ДОЛЖНО ждать выхода контура до 30 секунд. Контур выходит сам, увидев пульс другой версии. Если процесс не вышел, ядро ДОЛЖНО завершить его принудительно. Затем ядро ДОЛЖНО действовать так, как если бы живого контура не было.
- **Контур уже выходит.** `status.json` того же pid содержит `exited_at`, а процесс ещё жив. Ядро ДОЛЖНО ждать его выхода так же, как контура другой версии.
- **Процесс не подтвердил себя.** pid из `robot.pid` жив, но два других условия не выполнены. Ядро НЕ ДОЛЖНО завершать такой процесс и НЕ ДОЛЖНО запускать контур. Консоль и журнал ДОЛЖНЫ назвать pid, который нужно завершить. Робот ДОЛЖЕН продолжать работать: API и история доступны, команда запуска эмуляции проверяет папку заново и отвечает `409 CONTOUR_DIR_BUSY`, пока процесс жив.

**Живого контура нет.**

- **Явного запуска при старте нет:** робот всегда стартует в ожидании команды. Новое желаемое с новым поколением ДОЛЖНА записывать только команда `PUT /api/v1/emulation/target`.
- **Автоподъём.** При `[contours] autostart = true` (по умолчанию) ядро ДОЛЖНО поднимать контур без команды в двух случаях:
  - желаемое «работает»;
  - желаемое «остановлен», а последний `status.json` показывает `stopping_*`, а не `stopped`.

  Иначе ядро ДОЛЖНО ждать команду.
- **Автоподъём:**
  - НЕ ДОЛЖЕН создавать новое поколение и менять режим остановки;
  - состав процесса — активные участники и снятые участники, которых последний `status.json` ещё показывал в `members`;
  - карточки контрактов ядро ДОЛЖНО запросить заново, при сбое — взять сохранённые;
  - поле `launch.recovery` — `autostart`.

Подхват ДОЛЖЕН работать и при `autostart = false`.

Итог выхода подхваченного процесса:
- `status.json` с `exited_at` позже подхвата — `stopped` с кодом 0;
- иначе — `failed` с `exit_code = null`.

При остановке ядра подхваченный процесс ДОЛЖЕН останавливаться по пульсу `stopped`. Если процесс не вышел за 30 секунд, ядро ДОЛЖНО завершить его принудительно. Ни при каком исходе на одной папке контура НЕ ДОЛЖНО работать два процесса.

- **THEN** ядро без команды запускает контур с NG и прежним поколением, `launch.recovery = autostart`, позиция NG восстановлена из журнала и сопровождается

- **WHEN** робот запущен снова

- **THEN** контур не запускается, ядро ждёт команду

#### Scenario: Явный запуск важнее базы

- **WHEN** ядро стартует
- **THEN** процесс не завершается, контур не запускается, консоль называет pid, который нужно завершить, робот продолжает работать

- **WHEN** робот запущен

- **WHEN** повтор старта ядра удался
- **THEN** только после этого ядро поднимает контур с NG и прежним поколением, `launch.recovery = autostart`

### Requirement: Состояние ядра
Нормативный уровень: MUST. `GET /api/v1/core` с ключом управления ДОЛЖЕН возвращать:

- версию, pid и время старта ядра;
- состояние старта ядра `state`: `starting`, `ready`, `retrying` или `failed`; `error` — причина последней неудачи без секретов или `null`; `attempts` — число попыток; `next_retry_at` — время следующей попытки или `null`;
- время последнего удара пульса и `heartbeat_secs`;
- сводку рыночных данных:
  - `producer_id` и наибольший номер изменения ленты;
  - число живых пар и их число по состояниям готовности;
- запросы к брокеру за последнюю минуту по сервисам: число, потолок, разбивку по полосам и паузу после ограничения.

До `ready` сводка рыночных данных ДОЛЖНА быть `null`, а запросы к брокеру — пустыми. Маршрут ДОЛЖЕН отвечать при любом состоянии ядра.

Ответ НЕ ДОЛЖЕН содержать секреты, адреса и токены. Маршрут ДОЛЖЕН подчиняться правилам доступа к управлению. Ключ экспорта рыночных данных ДОЛЖЕН получать `401`.

#### Scenario: Состояние ядра
- **WHEN** приходит `GET /api/v1/core` с ключом управления
- **THEN** ответ `200` с версией робота, временем удара не старше 5 секунд, числом пар по состояниям и запросами котировок за минуту

#### Scenario: Чужой ключ
- **WHEN** приходит `GET /api/v1/core` с ключом экспорта рыночных данных
- **THEN** ответ `401`

#### Scenario: Ядро повторяет старт
- **WHEN** старт ядра упал и приходит `GET /api/v1/core`
- **THEN** ответ `200` с `state = retrying`, типом ошибки в `error`, `attempts = 1`, `next_retry_at` и `market_data = null`

### Requirement: Старт робота и API управления до ядра
Нормативный уровень: MUST. Робот ДОЛЖЕН запускаться без параметров и НЕ ДОЛЖЕН задавать вопросов в консоли. Порядок старта:

1. блокировка `data/robot.pid` и журнал;
2. `core.sqlite3`, пульс, очередь истории;
3. API управления;
4. ядро: рыночная база, арбитр лимитов, календарь, полосы.

API управления ДОЛЖЕН подниматься до ядра и НЕ ДОЛЖЕН зависеть от рыночной базы, брокера, `[market_data] export_enabled` и `independent_lanes`. Адрес — `[market_data] export_host` и `export_port`. После подъёма консоль ДОЛЖНА печатать «Робот запущен» с адресом API без значения ключа.

Без `ROBOT_CONTROL_TOKEN` и при неудачном подъёме API робот ДОЛЖЕН печатать причину и завершаться с кодом `2`. Занятая блокировка `data/robot.pid` ДОЛЖНА завершать запуск с кодом `1`, как прежде.

**Экспорт.** Маршруты экспорта рыночных данных и отчёта кластеров ДОЛЖНЫ отвечать:

- `503` с кодом `MARKET_DATA_NOT_READY`, пока ядро не открыло рыночную базу;
- `404` при `export_enabled = false`.

Ключ экспорта ДОЛЖЕН требоваться, как прежде.

#### Scenario: Обычный старт
- **GIVEN** задан `ROBOT_CONTROL_TOKEN`
- **WHEN** робот запущен без параметров
- **THEN** вопросов в консоли нет, печатается «Робот запущен, API: http://127.0.0.1:8101», затем стартует ядро

#### Scenario: Ключ управления не задан
- **WHEN** робот запущен, а `ROBOT_CONTROL_TOKEN` пуст
- **THEN** печатается, что без ключа управления роботом нельзя управлять, процесс завершается с кодом `2`

#### Scenario: Экспорт до готовности ядра
- **WHEN** ядро ещё открывает рыночную базу, а приходит запрос экспорта с ключом экспорта
- **THEN** ответ `503` с кодом `MARKET_DATA_NOT_READY`

### Requirement: Повтор старта ядра
Нормативный уровень: MUST. Сбой старта ядра НЕ ДОЛЖЕН останавливать робота. Робот ДОЛЖЕН:

- записать причину в консоль и журнал: тип и текст ошибки без секретов;
- закрыть всё, что успела открыть неудачная попытка: полосы, поток, базу;
- повторить старт через 30 секунд, затем с паузой вдвое больше прежней, но не больше 5 минут.

Без `TINKOFF_TOKEN` повтор НЕ ДОЛЖЕН выполняться: ядро остаётся в `failed` до перезапуска робота. Ctrl+C во время паузы ДОЛЖЕН штатно останавливать робота. Пропадание сети после успешного старта сбоем старта не считается: его переживают полосы, как прежде.

При `independent_lanes = false` ядро ДОЛЖНО считаться готовым, когда открыта рыночная база.

**Пока ядро не готово:**

- API управления и история работают;
- запуск эмуляции (`PUT /api/v1/emulation/target` с `mode = on`) отвечает `409` с кодом `CORE_NOT_READY` и состоянием ядра;
- автоподъём контура эмуляции ДОЛЖЕН ждать готовности ядра.

#### Scenario: Брокер недоступен при старте
- **WHEN** старт ядра упал из-за ошибки связи с брокером
- **THEN** робот продолжает работать, `GET /api/v1/core` показывает `state = retrying`, причину и `next_retry_at` через 30 секунд, следующая неудача — через 60 секунд

#### Scenario: Ядро поднялось после повтора
- **GIVEN** желаемое эмуляции «работает», первая попытка старта ядра упала
- **WHEN** вторая попытка удалась
- **THEN** `state = ready`, экспорт отвечает, контур эмуляции поднимается автоподъёмом

#### Scenario: Нет токена брокера
- **WHEN** робот запущен, а `TINKOFF_TOKEN` пуст
- **THEN** ядро в `failed` без повтора, запуск эмуляции отвечает `409 CORE_NOT_READY`, прогоны истории принимаются

### Requirement: Прогон истории командой API
Нормативный уровень: MUST. `POST /api/v1/history` с телом `{"from", "to", "pause", "instruments"}` ДОЛЖЕН ставить исторический прогон в очередь робота. Это единственный способ запустить историю.

**Поля тела:**

- `from`, `to` — обязательные, формат `ГГГГ-ММ-ДД ЧЧ:ММ`; без зоны — UTC. `to` не входит в прогон.
- `pause` — пауза между тиками в секундах, число не меньше 0. Без поля — прежнее значение по умолчанию.
- `instruments` — список имён по правилам истории из требования «Инструменты из параметров запуска»: код семейства — автоматическая цепочка, контракт — фиксированный. Без поля — `all`.

**Идентификатор.** `id` прогона ДОЛЖЕН иметь вид `ГГГГММДД-ЧЧММСС` по времени приёма; при совпадении к нему добавляется `-2`, `-3`. `id` ДОЛЖЕН совпадать с именем папки прогона `data/contours/history/<id>/`. Префикс `history-` НЕ ДОЛЖЕН входить в `id` API. Прогоны, записанные прежней версией, ДОЛЖНЫ показываться и находиться по имени своей папки.

**Проверка до ответа.** Без обращения к эмулятору данных:

- даты разбираются, начало раньше конца;
- пауза не отрицательная;
- у каждого имени есть привязки в конфигурации;
- семейство и его же контракт не названы вместе.

Выбор контрактов у эмулятора, предпроверка покрытия и прогрев ДОЛЖНЫ выполняться процессом прогона после старта.

**Ответы:**

- `202` — прогон принят; тело — прогон в состоянии `queued` или `starting`, заголовок `Location` — `/api/v1/history/{id}`;
- `400` — тело не JSON-объект, неизвестные поля, нет дат, неразборчивая дата, начало не раньше конца, пауза не число или отрицательная, `instruments` не список строк;
- `401`, `403` — по правилам доступа к управлению;
- `422` — хотя бы одно имя отклонено; тело содержит `rejections` с именем и причиной; прогон НЕ ДОЛЖЕН ставиться в очередь.

Команда ДОЛЖНА приниматься при любом состоянии ядра и контура эмуляции: пока ядро стартует, повторяет старт или не стартовало совсем; в ожидании команды эмуляции, при торговле, после остановки. Прогон НЕ ДОЛЖЕН менять целевое состояние и состав эмуляции. Инструмент, названный и в истории, и в эмуляции, ДОЛЖЕН торговаться по одним и тем же привязкам `robot.toml`. Эмуляция получает свечи из ядра, прогон — исторические свечи эмулятора данных.

#### Scenario: История без эмуляции
- **GIVEN** робот запущен без параметров и ждёт команду эмуляции

- **THEN** ответ `202` с `id` вида `20261024-101500` и состоянием `queued` или `starting`, прогон NG начинается, а эмуляция продолжает ждать команду

- **THEN** ответ `200` с этим прогоном и `id = 20261024-091000`

### Requirement: Очередь прогонов истории
Нормативный уровень: MUST. Одновременно ДОЛЖНО идти не больше `[contours] max_history_runs` прогонов. Остальные прогоны ДОЛЖНЫ ждать в очереди и стартовать в порядке поступления, как только освободится место.

Перед стартом каждого прогона робот ДОЛЖЕН сам сверить импорт эмулятора данных по требованию «Сверка импорта перед историческим прогоном». Сверки ДОЛЖНЫ выполняться по одной: две сверки одновременно НЕ ДОЛЖНЫ отправляться.

Каждый прогон ДОЛЖЕН идти отдельным процессом того же исполняемого файла с `--contour history <id>`. Журнал прогонов ДОЛЖЕН храниться в таблице `history_runs` базы `core.sqlite3`, писать его ДОЛЖЕН только процесс робота. Вывод процесса прогона в консоль ДОЛЖЕН записываться в `console.log` папки прогона. Консоль робота ДОЛЖНА получать одну строку о старте прогона и одну об итоге.

#### Scenario: Третий прогон ждёт
- **GIVEN** `max_history_runs = 2`, идут два прогона
- **WHEN** приходит команда третьего прогона
- **THEN** ответ `202` с состоянием `queued` и `queue_position = 1`; прогон стартует после завершения одного из двух

#### Scenario: Сверки не пересекаются
- **WHEN** два прогона приняты подряд при свободных местах
- **THEN** робот отправляет вторую сверку импорта только после ответа на первую, и каждый прогон получает свой номер снимка

### Requirement: Состояние прогонов истории
Нормативный уровень: MUST. Прогоны истории ДОЛЖНЫ показываться ресурсом `/api/v1/history`.

**Список** `GET /api/v1/history`:

- без фильтра — все прогоны в очереди и в работе и 20 последних завершённых, новые первыми;
- `?state=active` — только в очереди и в работе; `?state=finished` — только завершённые;
- `?limit=N` (1–200) — число завершённых вместо 20;
- неверный `state` или `limit` — `400`;
- ответ содержит `limits` (`max` — `max_history_runs`, `running`, `queued`), `items` и `_links`.

**Один прогон** `GET /api/v1/history/{id}` — прогон или `404`. **Итог** `GET /api/v1/history/{id}/report` — итог из `report.json` или `404` с кодом `REPORT_NOT_READY`, пока отчёта нет.

**Состояния прогона:**

| Состояние | Значение |
| --- | --- |
| `queued` | ждёт в очереди |
| `starting` | робот сверяет импорт и запускает процесс |
| `running` | процесс жив |
| `stopping` | стоп запрошен, процесс ещё жив |
| `finished` | процесс вышел с кодом 0 без стопа |
| `stopped` | процесс вышел с кодом 0 после стопа |
| `failed` | процесс не запустился или вышел с другим кодом |
| `cancelled` | убран из очереди командой или остановкой робота |
| `interrupted` | робот перезапущен, процесса прогона нет, итог не записан |

**Поля прогона:**

- `id`, `state`;
- `request`: `from`, `to`, `pause`, `instruments`;
- времена: `accepted_at`, `started_at`, `finished_at`;
- `queue_position` — только у `queued`;
- `reason` — причина отказа, отмены или сбоя;
- `market_data_sync`: `status`, `snapshot_generation`;
- `progress` из `status.json` прогона или `null`: `phase` (`checking`, `running`, `finishing`), `start`, `end` с учётом сдвига начала, `market_now`, `ticks`, `fraction` от 0 до 1;
- `process`: `pid` — пока процесс жив, `exit_code` и `exited_at` — после выхода, `dir` — папка прогона относительно папки данных;
- `_links`: `self`, `log`, `report` — когда отчёт записан; `_actions` — по требованию «Ссылки и доступные действия».

**Поля итога:** `covered`, `stop_reason`, `trades`, `net_pnl`, `fees`, `balance` (суммы — `{amount, currency}`), `open_positions`.

Полей эмуляции (`target`, `instruments`, `launch`) у прогона НЕТ. Ответ НЕ ДОЛЖЕН содержать секреты и адрес эмулятора данных. Маршрутов изменения состава у прогона НЕТ: состав после приёма не меняется.

#### Scenario: Прогон идёт
- **GIVEN** прогон NG с 01.09 10:00 по 08.09 10:00 дошёл до 04.09 12:00 рыночного времени
- **WHEN** приходит `GET /api/v1/history/{id}` прогона
- **THEN** состояние `running`, `progress.phase = running`, `progress.market_now` — 04.09 12:00, `progress.fraction` около 0,44, ссылки `report` нет, а `GET /api/v1/history/{id}/report` отвечает `404` с кодом `REPORT_NOT_READY`

#### Scenario: Прогон закончен
- **WHEN** процесс прогона записал отчёт и вышел с кодом 0
- **THEN** состояние `finished`, `process.exit_code = 0`, `GET /api/v1/history/{id}/report` содержит число сделок и `net_pnl` из `report.json`

#### Scenario: Прогон отклонён предпроверкой
- **WHEN** предпроверка не нашла свечей NG в диапазоне и процесс вышел с кодом 2
- **THEN** состояние `failed`, `process.exit_code = 2`, `reason` — причина предпроверки

#### Scenario: Список прогонов
- **GIVEN** идёт один прогон, один ждёт, 25 прогонов завершены
- **WHEN** приходит `GET /api/v1/history`
- **THEN** в `items` оба активных прогона и 20 последних завершённых; `limits` — `max = 2`, `running = 1`, `queued = 1`

#### Scenario: Состав прогона не меняется
- **WHEN** приходит `POST /api/v1/history/{id}/instruments` с `{"instruments": ["SBER"]}`
- **THEN** ответ `404`, прогон продолжается с прежним составом

### Requirement: Остановка прогона истории
Нормативный уровень: MUST. `POST /api/v1/history/{id}/stop` ДОЛЖЕН:

- не требовать тела; переданное тело ДОЛЖНО игнорироваться;
- прогон в очереди переводить в `cancelled`, процесс не запускается;
- идущий прогон переводить в `stopping`; процесс останавливается после тика и пишет отчёт с причиной «остановлено оператором»;
- отвечать `202` с прогоном после команды, а повтор уже принятой остановки — `200`;
- для завершённого прогона отвечать `409` с кодом `NOT_RUNNING`;
- для неизвестного `id` отвечать `404`.

**Остановка робота.** При штатной остановке робота (Ctrl+C) ДОЛЖНО выполняться:

1. прогоны в очереди переходят в `cancelled` с причиной «робот остановлен»;
2. идущие прогоны останавливаются после тика с отчётом;
3. робот ждёт их выхода до 30 секунд, затем завершает принудительно.

**Рестарт робота.** После рестарта робот НЕ ДОЛЖЕН возобновлять очередь и прерванные прогоны:

- `queued` и `starting` из `history_runs` — `cancelled` с причиной «робот перезапущен»;
- `running` и `stopping` — по папке прогона:
  - **живой прогон** (pid из `robot.pid` жив, `status.json` называет тот же pid, `alive_at` свежее `heartbeat_timeout_secs`) — робот следит за ним по pid, прогон занимает место в очереди, стоп передаётся флагом в `history_runs`; итог берётся из `status.json`;
  - **иначе** — `interrupted`.

Процесс прогона ДОЛЖЕН останавливаться:

- по `stop` в stdin;
- по Ctrl+C;
- по пульсу робота `stopped`;
- по флагу стопа своей строки `history_runs`.

Потеря пульса и пульс другой версии НЕ ДОЛЖНЫ останавливать прогон.

#### Scenario: Отмена из очереди
- **GIVEN** прогон ждёт в очереди
- **WHEN** приходит `POST /api/v1/history/{id}/stop`
- **THEN** ответ `202`, состояние `cancelled`, процесс не запускается, следующий прогон очереди сдвигается вперёд

- **THEN** ответ `202` с состоянием `stopping`, после тика процесс пишет отчёт «остановлено оператором» и выходит, состояние `stopped`, итог доступен в `/report`

#### Scenario: Повтор стопа
- **GIVEN** стоп идущего прогона уже принят, прогон в `stopping`
- **WHEN** стоп приходит снова
- **THEN** ответ `200`, состояние `stopping`

#### Scenario: Ctrl+C робота

- **WHEN** пользователь нажимает Ctrl+C в консоли робота
- **THEN** оба прогона пишут отчёты и переходят в `stopped`, ждавший — в `cancelled`; после нового старта робота ни один не запускается

- **WHEN** робот запущен снова, а прогон ещё идёт
- **THEN** прогон не прерывается, `GET /api/v1/history/{id}` показывает `running`, стоп этого прогона работает через флаг в `history_runs`

### Requirement: Ресурсы контуров
Нормативный уровень: MUST. Каждый вид торгового контура ДОЛЖЕН быть отдельным ресурсом API со своей схемой:

- эмуляция — `/api/v1/emulation`, один контур на робота;
- история — `/api/v1/history`, коллекция прогонов;
- песочница — `/api/v1/sandbox`, один контур на брокере на робота.

Общие части ДОЛЖНЫ быть общими схемами контракта: целевое состояние, текущее состояние, запуск, процесс, участник состава. Контур «Песочница» и будущий контур «Счёт» ДОЛЖНЫ строиться на них же; участником состава у них служит привязка, а не инструмент.

Маршруты `/api/v1/contours`, `/api/v1/contours/{id}` и все вложенные в них ДОЛЖНЫ быть удалены: запрос к ним ДОЛЖЕН получать `404` с кодом `NOT_FOUND` без перенаправления и без выполнения команды.

API ДОЛЖЕН называть состояние словами оператора:

| В API | В `core.sqlite3` и `status.json` |
| --- | --- |
| `target` — целевое состояние | желаемое |
| `target.mode = on` | «работает» |
| `target.mode = no_entries` / `close_all` | «остановлен» с этим режимом |
| `target.revision`, заголовок `ETag` | номер поколения |
| `current` — текущее состояние | фактическое из `status.json` |
| `current.applied_revision` | применённое поколение |

Имена `desired`, `actual`, `generation`, `applied_generation`, `running`, `stop_mode` НЕ ДОЛЖНЫ появляться в запросах и ответах API управления. Внутренние имена базы и `status.json` НЕ ДОЛЖНЫ меняться.

#### Scenario: Прежний маршрут
- **WHEN** приходит `POST /api/v1/contours` с `{"kind": "emulation"}` и верным ключом
- **THEN** ответ `404` с кодом `NOT_FOUND`, торговля не начинается, целевое состояние не меняется

- **GIVEN** эмуляция торгует, в `core.sqlite3` поколение 3
- **WHEN** приходит `GET /api/v1/emulation`
- **THEN** ответ содержит `target = {"mode": "on", "revision": 3}` и `current.applied_revision`, а ключей `desired`, `actual` и `generation` в нём нет

#### Scenario: Песочница на общих схемах
- **WHEN** приходит `GET /api/v1/sandbox`
- **THEN** `target`, `current.applied_revision`, `launch` и `process` устроены так же, как у эмуляции, а участники состава — привязки

### Requirement: Точка входа API
Нормативный уровень: MUST. `GET /api/v1` ДОЛЖЕН принимать ключ управления или ключ экспорта и отвечать при любом состоянии ядра. Ответ ДОЛЖЕН содержать:

- `version` — версию робота;
- `core.state` — состояние старта ядра;
- `emulation` — `state`, число инструментов и открытых позиций; `null` для ключа экспорта;
- `history` — число идущих и ждущих прогонов и `max_history_runs`; `null` для ключа экспорта;
- `sandbox` — `state`, число привязок, число замороженных инструментов и итог последней сверки; `null` для ключа экспорта;
- `live` — `null`, пока контур «Счёт» не реализован;
- `_links` — ссылки на разделы, разрешённые ключу: для ключа управления — `core`, `emulation`, `history`, `sandbox`, `docs`; для ключа экспорта — `market-data` (`/api/v1/market-data/source`), `clusters-report`, `docs`.

Без ключа или с неверным ключом — `401`.

#### Scenario: Ключ управления
- **WHEN** приходит `GET /api/v1` с ключом управления
- **THEN** ответ `200` со сводкой эмуляции, истории и песочницы и ссылками на ядро, эмуляцию, историю и песочницу, без ссылок на экспорт

#### Scenario: Ключ экспорта
- **WHEN** приходит `GET /api/v1` с ключом экспорта
- **THEN** ответ `200`, `emulation`, `history` и `sandbox` равны `null`, ссылки — только на рыночные данные, отчёт кластеров и Swagger

#### Scenario: Ядро ещё не готово
- **GIVEN** старт ядра упал и ждёт повтора
- **WHEN** приходит `GET /api/v1` с ключом управления
- **THEN** ответ `200` с `core.state = retrying`, сводка эмуляции, истории и песочницы показана

### Requirement: Ошибки API управления
Нормативный уровень: MUST. Ответ с ошибкой на точке входа и на маршрутах управления (`/api/v1/core`, `/api/v1/emulation…`, `/api/v1/history…`) ДОЛЖЕН быть `application/problem+json` (RFC 9457) с полями:

- `type` — `urn:my-robot:problem:<код>`, код в нижнем регистре через дефис;
- `title` — короткое название ошибки;
- `status` — код HTTP;
- `code` — код ошибки: `INVALID_REQUEST`, `UNAUTHORIZED`, `FORBIDDEN_HOST`, `NOT_FOUND`, `REPORT_NOT_READY`, `ALREADY_RUNNING`, `STOPPING`, `NOT_RUNNING`, `MODE_CONFLICT`, `CORE_NOT_READY`, `CONTOUR_DIR_BUSY`, `REVISION_CHANGED`, `INSTRUMENTS_REJECTED`;
- `detail` — понятная причина.

Дополнительные поля:

- `rejections` — у `INSTRUMENTS_REJECTED`: список `{instrument, reason}`, где `instrument` — имя из запроса как есть;
- `core` — у `CORE_NOT_READY`: состояние, число попыток и время следующей;
- `pid` — у `CONTOUR_DIR_BUSY`.

Ответ НЕ ДОЛЖЕН содержать секреты. Маршруты экспорта рыночных данных и отчёта кластеров ДОЛЖНЫ сохранить прежний формат `{code, message}` в `application/json`, включая ответ `401`: их читает Historical Broker API Emulator.

#### Scenario: Отказ инструмента
- **WHEN** запуск эмуляции получил отказ по AFLT
- **THEN** ответ `422` в `application/problem+json` с `code = INSTRUMENTS_REJECTED` и `rejections = [{"instrument": "AFLT", "reason": …}]`

#### Scenario: Ошибка экспорта не меняется
- **WHEN** эмулятор данных запрашивает `GET /api/v1/market-data/changes` с курсором старше хранимой ленты
- **THEN** ответ `410` в `application/json` с `code = CURSOR_EXPIRED` и `message`, как в версии 1.8

### Requirement: Ссылки и доступные действия
Нормативный уровень: MUST. Ответы точки входа, ядра, эмуляции, состава, участника состава, прогона и списка прогонов ДОЛЖНЫ содержать `_links` — объект «имя связи → `{href}`» с относительными адресами.

Ответы эмуляции, участника состава и прогона ДОЛЖНЫ содержать `_actions` — команды, которые сервер примет сейчас. Поля действия: `name`, `title`, `method`, `href` и `body` — готовое тело; поля-списки в нём клиент заполняет сам.

| Объект и его состояние | Действия |
| --- | --- |
| эмуляция `waiting_command`, `stopped`, `failed` при готовом ядре | `start` |
| процесс эмуляции жив, `target.mode = on` (`starting`, `running`) | `stop`, `stop-close-all`, `add-instruments` |
| эмуляция `stopping_no_entries` | `stop-close-all` |
| эмуляция `starting` до запуска процесса | нет |
| эмуляция `stopping_close_all`; эмуляция без процесса при неготовом ядре | нет |
| участник `target = active` (команды участника — только пока эмуляции доступно `add-instruments`) | `remove`, `remove-close-all` |
| участник `target = removed`, режим `no_entries` | `remove-close-all`, `restore` |
| участник `target = removed`, режим `close_all` | `restore` |
| прогон `queued` | `cancel` |
| прогон `starting`, `running` | `stop` |
| прогон в остальных состояниях | нет |

Набор действий ДОЛЖЕН выводиться из тех же правил, по которым сервер принимает и отклоняет команды. Наличие действия НЕ ДОЛЖНО отменять проверку: сервер проверяет каждую команду заново.

#### Scenario: Эмуляция торгует
- **WHEN** эмуляция в состоянии `running`, а приходит `GET /api/v1/emulation`
- **THEN** `_actions` содержит `stop` с телом `{"mode": "no_entries"}`, `stop-close-all` и `add-instruments`, но не `start`

#### Scenario: Ждёт команду
- **GIVEN** ядро готово, эмуляция в `waiting_command`
- **WHEN** приходит `GET /api/v1/emulation`
- **THEN** `_actions` содержит только `start` с `PUT /api/v1/emulation/target` и телом `{"mode": "on"}`

#### Scenario: Действие совпадает с ответом на команду
- **WHEN** клиент выполняет любое действие из `_actions` эмуляции с его телом
- **THEN** сервер принимает команду, а не отвечает `409`

#### Scenario: Прогон в очереди
- **WHEN** приходит `GET /api/v1/history/{id}` ждущего прогона
- **THEN** `_actions` содержит `cancel` с `POST /api/v1/history/{id}/stop`

### Requirement: Защита от одновременных команд
Нормативный уровень: MUST. `GET /api/v1/emulation`, `GET /api/v1/emulation/target` и ответы команд эмуляции ДОЛЖНЫ нести заголовок `ETag` — ревизию целевого состояния в кавычках, например `"3"`.

Команды `PUT /api/v1/emulation/target`, `POST /api/v1/emulation/instruments` и `POST /api/v1/emulation/instruments/remove` ДОЛЖНЫ принимать необязательный заголовок `If-Match`. Если он не совпадает с текущей ревизией:

- ответ `412` с кодом `REVISION_CHANGED`;
- целевое состояние и состав не меняются;
- в журнале команд — исход `conflict`.

Сравнение и запись ДОЛЖНЫ выполняться атомарно: две команды с одним `If-Match` НЕ ДОЛЖНЫ быть приняты обе. Без заголовка команда ДОЛЖНА применяться к текущему целевому состоянию.

#### Scenario: Команда по устаревшему состоянию
- **GIVEN** интерфейс прочитал эмуляцию с `ETag: "3"`, затем другой клиент добавил инструмент, ревизия стала 4
- **WHEN** интерфейс отправляет `POST /api/v1/emulation/instruments/remove` с `If-Match: "3"`
- **THEN** ответ `412` с кодом `REVISION_CHANGED`, состав не меняется

#### Scenario: Без заголовка
- **WHEN** команда остановки приходит без `If-Match`
- **THEN** она применяется к текущему целевому состоянию, как прежде

### Requirement: Ресурс контура «Песочница»
Нормативный уровень: MUST. Контур «Песочница» ДОЛЖЕН быть ресурсом `/api/v1/sandbox` под ключом управления, с проверкой `Host`, ответами `application/json`, ошибками `application/problem+json`, `_links` и `_actions`, `ETag` и `If-Match` по правилам эмуляции. `confirm` контуру песочницы НЕ НУЖЕН: денег на ней нет.

| Маршрут | Что делает |
|---|---|
| `GET /api/v1/sandbox` | состояние: общее, целевое, текущее, запуск, процесс, состав |
| `GET /api/v1/sandbox/target` | целевое состояние |
| `PUT /api/v1/sandbox/target` | `{"mode": "on", "bindings": [...]}` — запуск; `{"mode": "no_entries"}` или `{"mode": "close_all"}` — остановка |
| `GET /api/v1/sandbox/bindings` | состав песочницы и все привязки конфигурации с отметкой, где каждая торгует |
| `POST /api/v1/sandbox/bindings` | `{"bindings": [...]}` — добавить в состав |
| `POST /api/v1/sandbox/bindings/remove` | `{"bindings": [...], "mode": "no_entries" \| "close_all"}` — убрать из состава |
| `GET /api/v1/sandbox/reconcile` | последний отчёт сверщика |
| `GET /api/v1/sandbox/log?lines=N` | хвост лога контура, как у эмуляции |

**Запуск.** Поле `bindings` НЕ ОБЯЗАТЕЛЬНО, пустой состав допустим. Ответы:

- `202` — состояние песочницы и `Location: /api/v1/sandbox`;
- `400` — тело не объект, неизвестные поля, `mode` не из трёх значений, `bindings` не список строк или передан вместе с режимом остановки;
- `409` — коды эмуляции: `ALREADY_RUNNING`, `STOPPING`, `NOT_RUNNING` (остановка без процесса), `CORE_NOT_READY`, `CONTOUR_DIR_BUSY`;
- `412 REVISION_CHANGED`;
- `422 BINDINGS_REJECTED` — список отказов: `id` и причина «Привязки нет в конфигурации»; запуск не начинается.

**Состав.** Добавление и снятие ДОЛЖНЫ отвечать `202` с новой ревизией или `200` без изменений (уже в составе, уже снята). Неизвестный `id` ДОЛЖЕН давать `422 BINDINGS_REJECTED`, при этом состав не меняется. Команды состава ДОЛЖНЫ приниматься и тогда, когда процесс не запущен: они меняют целевой состав для следующего запуска.

**Состояние.** `state` — то же перечисление, что у эмуляции: `waiting_command`, `starting`, `running`, `stopping_no_entries`, `stopping_close_all`, `stopped`, `failed`. `current` ДОЛЖЕН содержать:

- `applied_revision`;
- `account` — последние четыре символа;
- `capital` — `rub`, `liquid_portfolio`;
- `positions` — инструмент коротким именем, лоты;
- `orders` и `stop_orders` — число;
- `frozen` — инструменты коротким именем;
- `last_reconcile_at`;
- `account_link`, `core_link`;
- `reason`.

`bindings` — участники: `id`, инструмент, стратегия, таймфрейм, `target` (`active` или `removed`) и `current` (`watching` в С2).

**Привязки.** `GET /api/v1/sandbox/bindings` ДОЛЖЕН возвращать `members` — состав песочницы — и `available` — все привязки конфигурации. У каждой привязки — `id`, инструмент, стратегия, таймфрейм и `trades_in`:

- `emulation`, если инструмент привязки сейчас в составе эмуляции;
- `sandbox`, если привязка в составе песочницы.

#### Scenario: Запуск с составом
- **GIVEN** ядро готово, в конфигурации есть привязки `share-sber-macd-4h-triple` и `future-ng-macd`
- **WHEN** приходит `PUT /api/v1/sandbox/target` с `{"mode": "on", "bindings": ["share-sber-macd-4h-triple"]}`
- **THEN** ответ `202` с `target.revision`, в составе одна привязка, ядро запускает процесс песочницы

#### Scenario: Неизвестная привязка
- **WHEN** приходит `POST /api/v1/sandbox/bindings` с `{"bindings": ["share-xxx"]}`
- **THEN** ответ `422 BINDINGS_REJECTED` с причиной для `share-xxx`, ревизия не меняется

#### Scenario: Отчёт сверки

- **WHEN** приходит `GET /api/v1/sandbox` после очередного шага
- **THEN** `current.capital.rub` равен 1 000 000, `current.account` — четыре последних символа номера
