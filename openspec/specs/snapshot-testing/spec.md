# Snapshot-тестирование торговых сигналов

## Purpose

Data-driven проверка детерминированности расчётного конвейера (индикаторы → сигналы → решение) на зафиксированном отрезке истории: локальные свечи прогоняются через боевой расчётный модуль, результат сверяется с эталонным файлом сигналов. Тесты масштабируются на несколько стратегий динамической параметризацией по папкам кейсов.

## Requirements

### Requirement: Прогон фикстуры через боевой модуль
Тест ДОЛЖЕН прогонять фикстуру через боевые методы стратегии из реестра: события эталона вычисляет `expected_events()` выбранной по имени стратегии, агрегация повторяет её логику (скользящее окно `STRATEGY_WINDOW` над сигнальными колонками, правило событий стратегии). Прямые вызовы удалённых модулей (`tech_analyze` как единой точки расчёта) в тестах НЕ ДОЛЖНЫ использоваться.

#### Scenario: Воспроизведение оконной агрегации
- **WHEN** фикстура содержит N ≥ STRATEGY_WINDOW строк
- **THEN** `expected_events()` стратегии возвращает ровно те события, что даёт скользящая агрегация последних STRATEGY_WINDOW значений сигнальных колонок
### Requirement: Динамический импорт параметров конфигурации
Параметры расчёта ДОЛЖНЫ браться у объекта стратегии, полученного из реестра (`STRATEGY_WINDOW`, требуемая глубина истории), а не дублироваться или импортироваться из `src.config` (глобальный `SIGNAL_WINDOW` удалён).

#### Scenario: Синхронизация с продакшн-конфигом
- **WHEN** в пакете стратегии изменено значение `STRATEGY_WINDOW`
- **THEN** тест использует новое значение без правки кода теста
### Requirement: Динамическая параметризация по папкам кейсов
Единый раннер `tests/snapshot/test_strategies.py` ДОЛЖЕН автоматически собирать параметры, сканируя все папки кейсов `tests/snapshot/data/*/<ИНСТРУМЕНТ>_<ТАЙМФРЕЙМ>/` и находя файлы эталонов `<strategy_name>_expected_signals.csv`; имя файла кодирует стратегию, диспетчеризация выполняется реестром (`get_strategy(strategy_name)`). Имя папки кейса — имя кейса. Добавление инструмента, кейса ИЛИ новой стратегии НЕ ДОЛЖНО требовать правки кода тестов. Поиск ДОЛЖЕН выполняться по точному соответствию шаблону файла эталона.

#### Scenario: Новый кейс подхватывается автоматически
- **WHEN** в `tests/snapshot/data/` добавлена папка `BTC_15m/` с `candles.csv` и `macd_rsi_stoch_expected_signals.csv`
- **THEN** при следующем прогоне pytest раннер выполняет тест-кейс `(BTC_15m, macd_rsi_stoch)`

#### Scenario: Новая стратегия подхватывается автоматически
- **WHEN** в существующий кейс добавлен файл `rsi_scalp_expected_signals.csv` и стратегия зарегистрирована в реестре
- **THEN** раннер выполняет тест-кейс `(кейс, rsi_scalp)` без правки кода тестов

#### Scenario: Пустая папка данных
- **WHEN** в `tests/snapshot/data/` нет ни одного файла эталонов
- **THEN** параметризация даёт ноль кейсов; прогон завершается без ошибок

#### Scenario: Изоляция стратегий друг от друга
- **WHEN** в кейсе лежат эталоны нескольких стратегий (`macd_rsi_stoch_expected_signals.csv`, `rsi_divergence_expected_signals.csv`)
- **THEN** каждый эталон сравнивается с результатом своей стратегии; чужие эталоны игнорируются
### Requirement: Эталонный файл сигналов
Эталон ДОЛЖЕН храниться рядом с фикстурой свечей и называться `<strategy_name>_expected_signals.csv` (имя кодирует стратегию; префиксы вроде `test_` НЕ ДОЛЖНЫ использоваться). Обязательные столбцы: `datetime` (ISO без часового пояса), `signal` (`BUY`|`SELL`), `price` (float); дополнительные столбцы определяются контрактом стратегии. Содержимое эталона ДОЛЖНО полностью определяться методом `expected_events()` соответствующей стратегии — общие правила консенсуса вне пакетов стратегий НЕ ДОЛЖНЫ существовать. Несколько эталонов разных стратегий МОГУТ делить один `candles.csv` кейса.

#### Scenario: Консенсусная покупка
- **WHEN** стратегия `macd_rsi_stoch`: `macd_sum > 0` И `rsi_sum > 0` И `stoch_sum > 0` на свече t
- **THEN** строка t присутствует в эталоне с `signal=BUY` и `price=close(t)`

#### Scenario: Консенсусная продажа
- **WHEN** стратегия `macd_rsi_stoch`: все три суммы строго отрицательные на свече t
- **THEN** строка t присутствует в эталоне с `signal=SELL` и `price=close(t)`

#### Scenario: Отсутствие консенсуса
- **WHEN** суммы имеют разные знаки или нули
- **THEN** строка отсутствует в эталоне
### Requirement: Сравнение с эталоном
Основное сравнение ДОЛЖНО выполняться через `pandas.testing.assert_frame_equal`. Допустима точечная сверка (по строкам/столбцам) как диагностический режим. Сравнение цен ДОЛЖНО допускать погрешность округления float (`check_exact=False`, малый rtol).

#### Scenario: Полное совпадение
- **WHEN** фактические события равны эталону (таймстемпы, типы, цены в допуске)
- **THEN** тест проходит

#### Scenario: Расхождение
- **WHEN** фактический сигнал отличается (timestamp, тип или цена вне допуска)
- **THEN** тест падает с указанием первой расходящейся строки
### Requirement: Регенерация эталона флагом --update-snapshots
При запуске pytest с флагом `--update-snapshots` тест ДОЛЖЕН вместо сверки пересчитать сигналы боевым модулем и перезаписать `expected_signals.csv`. Изменения стратегии фиксируются осознанно через Git diff.

#### Scenario: Осознанное обновление эталона
- **WHEN** разработчик изменил логику сигналов и запустил `pytest --update-snapshots`
- **THEN** `expected_signals.csv` перезаписывается текущим поведением конвейера; diff ревьюится и коммитится

#### Scenario: Обычный прогон не изменяет файлы
- **WHEN** pytest запущен без флага
- **THEN** файлы эталонов остаются неизменными
### Requirement: Учёт прогрева индикаторов
Строки фикстуры до завершения прогрева индикаторов (MACD slow+signal ≈ 35 бар) ДОЛЖНЫ исключаться из сравнения событий (NaN-регион pandas-ta-classic).

#### Scenario: Окно покрывает прогрев
- **WHEN** фикстура содержит до 300 часовых свечей
- **THEN** после прогрева остаётся достаточное число анализируемых свечей, включая целевую последнюю
### Requirement: Детерминизм и воспроизводимость
Snapshot-тесты ДОЛЖНЫ быть детерминированными: результат зависит только от содержимого фикстуры, кода боевого модуля и зафиксированных версий библиотек.

#### Scenario: Непреднамеренное изменение поведения
- **WHEN** рефакторинг или обновление зависимости меняет расчёт индикаторов
- **THEN** snapshot-тест падает до попадания изменений в продакшн-цикл бота
### Requirement: Snapshot-раннер для analysis-слоя
Система ДОЛЖНА предоставлять отдельный data-driven раннер `tests/snapshot/test_analysis.py` для проверки детерминированности analysis-слоя (тренд и уровни S/R) на тех же общих свечах кейсов `tests/snapshot/data/*/<ИНСТРУМЕНТ>_<ТАЙМФРЕЙМ>/candles.csv`. Раннер ДОЛЖЕН параметризоваться по папкам кейсов, а не по стратегиям, и использовать собственные эталоны с суффиксом `_expected_context.csv`. Раннер и его эталоны НЕ ДОЛЖНЫ пересекаться с раннером стратегий `test_strategies.py` и его эталонами `*_expected_signals.csv`.

#### Scenario: Автоподхват кейса для analysis
- **WHEN** в папку кейса добавлен файл `trend_expected_context.csv` (или `sr_levels_expected_context.csv`)
- **THEN** раннер `test_analysis.py` выполняет проверку для этого кейса без правки кода теста

#### Scenario: Отсутствие файлов данных
- **WHEN** в `tests/snapshot/data/` нет ни одного файла `*_expected_context.csv`
- **THEN** параметризация analysis-раннера даёт ноль кейсов; прогон завершается без ошибок

#### Scenario: Изоляция от стратегических эталонов
- **WHEN** в кейсе лежат и стратегические (`*_expected_signals.csv`), и analysis (`*_expected_context.csv`) эталоны
- **THEN** анализ-раннер обрабатывает только `*_expected_context.csv`, а раннер стратегий — только `*_expected_signals.csv`; файлы не смешиваются
### Requirement: Эталон analysis-контекста
Эталон analysis-слоя ДОЛЖЕН храниться рядом с фикстурой свечей и называться по паттерну `<modes>_expected_context.csv`, где `<modes>` кодирует входной модуль анализа (например `trend`, `sr_levels`). Типичные обязательные данные: для тренда — `datetime` и `trend_direction`/`trend_strength`; для S/R — отсортированные уровни с `price`, `type`, `strength`, `label`. Содержимое эталона ДОЛЖНО полностью определяться боевым модулем analysis-слоя, а не дублировать правила стратегий.

#### Scenario: Эталон тренда
- **WHEN** эталон `trend_expected_context.csv` создан для кейса
- **THEN** он содержит столбцы `datetime` и `trend_direction`/`trend_strength`, рассчитанные по последней закрытой свече кейса

#### Scenario: Эталон уровней S/R
- **WHEN** эталон `sr_levels_expected_context.csv` создан для кейса
- **THEN** он содержит отсортированные уровни с `price`, `type` (support/resistance), `strength` и `label`, согласно ограничениям `min_touches` и `max_levels`
### Requirement: Регенерация analysis-эталонов флагом --update-snapshots
Раннер `test_analysis.py` ДОЛЖЕН поддерживать тот же флаг `--update-snapshots`, что и раннер стратегий (определённый в `tests/conftest.py`): при запуске с флагом эталоны analysis-слоя ДОЛЖНЫ пересчитываться боевым модулем и перезаписываться.

#### Scenario: Осознанное обновление analysis-эталона
- **WHEN** разработчик изменил логику тренда/S/R и запустил `pytest tests/snapshot/test_analysis.py --update-snapshots`
- **THEN** `*_expected_context.csv` перезаписывается текущим поведением analysis-слоя; diff ревьюится и коммитится

#### Scenario: Обычный прогон не изменяет analysis-эталоны
- **WHEN** pytest для `test_analysis.py` запущен без флага
- **THEN** файлы `*_expected_context.csv` остаются неизменными
### Requirement: Сравнение analysis-эталона
Сравнение анализа с эталоном ДОЛЖНО выполняться через `pandas.testing.assert_frame_equal` с допуском округления float (`check_exact=False`, малый rtol). При расхождении тест ДОЛЖЕН указывать первую расходящуюся строку.

#### Scenario: Полное совпадение
- **WHEN** фактические trend/S/R равны эталону
- **THEN** тест проходит

#### Scenario: Расхождение
- **WHEN** фактический тренд или уровень S/R отличается от эталона
- **THEN** тест падает с указанием первой расходящейся строки
### Requirement: Детерминизм analysis-слоя
Snapshot-тесты analysis-слоя ДОЛЖНЫ быть детерминированными: результат зависит только от содержимого фикстуры, боевого модуля analysis и зафиксированных версий библиотек.

#### Scenario: Непреднамеренное изменение анализа
- **WHEN** рефакторинг или обновление зависимости меняет расчёт тренда или уровней S/R
- **THEN** snapshot-тест analysis-слоя падает до попадания изменений в продакшн-цикл бота
