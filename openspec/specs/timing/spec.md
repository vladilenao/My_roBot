# Планирование времени

## Purpose

Планировщик итерации робота по границе закрытия свечи таймфрейма: вычисляет, когда закрывается текущая свеча, ждёт до этой границы и предоставляет рыночное время. Обеспечивает синхронизацию работы бота с таймфреймом вместо фиксированной паузы.

## Requirements

### Requirement: Выравнивание по закрытию свечи
Система ДОЛЖНА предоставлять механизм планирования, который определяет момент закрытия текущей свечи таймфрейма и вычисляет время ожидания до этой границы. Границы вычисляются по календарной сетке таймфрейма (UTC), а не от момента запуска бота. Все моменты времени являются tz-naive (без часового пояса).

#### Scenario: Часовая свеча
- **WHEN** таймфрейм `1h` и текущее время `10:37 UTC`
- **THEN** следующая граница закрытия свечи — `11:00 UTC`

#### Scenario: Пятиминутная свеча
- **WHEN** таймфрейм `5m` и текущее время `10:07 UTC`
- **THEN** следующая граница закрытия свечи — `10:10 UTC`

### Requirement: Блокирующее ожидание до границы
Система ДОЛЖНА предоставлять операцию, которая блокирующе ожидает наступления границы закрытия текущей свечи, а затем, если требуется, дожидается появления свежего закрытого бара текущей закрытой минуты, и возвращает момент этой границы.

Ожидание появления бара ДОЛЖНО выполняться с ограниченным таймаутом: если свежий закрытый бар не появился за отведённое время, операция ДОЛЖНА вернуть управление (и момент границы), не блокируясь бесконечно.

#### Scenario: Ожидание до границы
- **WHEN** планировщик вызывается для ожидания до границы свечи и свежий закрытый бар уже доступен сразу после границы
- **THEN** выполнение блокируется до наступления границы и возвращается её время

#### Scenario: Свежий бар появился с задержкой
- **WHEN** календарная граница минуты достигнута, но свежий закрытый бар текущей закрытой минуты ещё не опубликован
- **THEN** система повторно проверяет появление бара с малыми паузами до появления этого бара, и только затем возвращает момент границы

#### Scenario: Таймаут ожидания бара
- **WHEN** свежий закрытый бар не появляется в течение ограниченного таймаута ожидания
- **THEN** операция возвращает управление с моментом границы даже при отсутствии свежего бара, не блокируясь бесконечно

### Requirement: Fallback-пауза при сбое
Система ДОЛЖНА предоставлять значение fallback-паузы (не выровненное по свече) для использования при внешнем сбое, чтобы не выполнять запросы слишком часто, но и не блокировать на всю свечу. Эффективная fallback-пауза ДОЛЖНА быть не длиннее периода наименьшего активного ТФ: большее сконфигурированное значение ограничивается им, факт ограничения фиксируется в логе.

#### Scenario: Пауза после сбоя
- **WHEN** произошла ошибка тика и применяется fallback-пауза
- **THEN** следующая попытка выполняется через короткую фиксированную паузу, не привязанную к границе свечи

#### Scenario: Пауза ограничена наименьшим ТФ
- **WHEN** сконфигурированная fallback-пауза `3600` сек, а наименьший активный ТФ — `15m`
- **THEN** эффективная пауза — `900` секунд, в лог пишется запись об ограничении

### Requirement: Предоставление рыночного времени
Система ДОЛЖНА предоставлять текущее рыночное время (UTC) как отдельную операцию, допускающую подстановку фиктивного времени для тестирования. Возвращаемое время ДОЛЖНО быть tz-naive (без часового пояса), совместимым с расчётом границ свечи.

#### Scenario: Читаемое время
- **WHEN** планировщик запрашивает текущее время
- **THEN** возвращается текущий момент (UTC), совместимый с расчётом границ свечи

### Requirement: Мульти-таймфреймная сетка тиков
Система ДОЛЖНА поддерживать ритм по нескольким активным таймфреймам одновременно: множество активных ТФ выводится из привязок стратегий. Планировщик ДОЛЖЕН вычислять момент следующего тика как ближайшую из границ закрытия свечей всех активных ТФ (по календарным сеткам каждого ТФ в UTC), а на каждом пробуждении — определять, для каких ТФ граница закрытия пройдена с предыдущего тика. При единственном активном ТФ поведение ДОЛЖНО совпадать с однотаймфреймным ритмом.

#### Scenario: Ближайшая граница среди ТФ
- **WHEN** активны ТФ `15m` и `1h`, текущее время `10:37 UTC`
- **THEN** следующий тик планируется на `10:45 UTC` (ближайшая граница — сетка 15m)

#### Scenario: На тике закрылась свеча только младшего ТФ
- **WHEN** активны ТФ `15m` и `1h`, тик на границе `10:45 UTC`
- **THEN** пройденной границей помечается только `15m`; `1h` остаётся без новой границы

#### Scenario: На тике закрылись свечи обоих ТФ
- **WHEN** активны ТФ `15m` и `1h`, тик на границе `11:00 UTC`
- **THEN** пройденными границами помечаются оба ТФ — `15m` и `1h`

#### Scenario: Неделимая смесь сеток
- **WHEN** активны ТФ `15m` и `1d`, текущее время `10:37 UTC`
- **THEN** следующий тик планируется на ближайшую из границ обеих сеток (`10:45 UTC` — граница 15m)

#### Scenario: Ожидание публикации per ТФ
- **WHEN** на тике пройдены границы `15m` и `1h`, свежий бар `15m` опубликован, а бар `1h` — ещё нет
- **THEN** ожидание появления свежего бара продолжается для `1h` в пределах таймаута, не задерживая обработку готового `15m`

### Requirement: Сетки неактивных таймфреймов по запросу
Планировщик ДОЛЖЕН предоставлять математику сетки для любого таймфрейма лестницы, включая не входящие в множество активных ТФ. Сетки неактивных ТФ ДОЛЖНЫ возвращаться по запросу потребителям (фильтрам и кэшу данных) и НЕ ДОЛЖНЫ влиять на момент следующего тика, определение пройденных границ и fallback-паузу. Лестница сеток ДОЛЖНА поддерживать таймфреймы `30m` и `4h` наравне с существующими.

#### Scenario: Сетка неактивного ТФ доступна
- **WHEN** активны ТФ `15m` и `1h`, а запрошена сетка `4h`
- **THEN** возвращается сетка `4h` с корректной математикой границ

#### Scenario: Тридцатиминутная граница
- **WHEN** для сетки `30m` запрошена следующая граница при текущем времени `10:17 UTC`
- **THEN** граница — `10:30 UTC`

#### Scenario: Неактивный ТФ не меняет ритм
- **WHEN** активны ТФ `15m` и `1h`, а сетка `4h` запрошена потребителем
- **THEN** следующий тик планируется на ближайшую границу только активных ТФ (`15m`/`1h`)
