# Организация дерева тестов

## Purpose

Определяет физическую структуру тестового пространства проекта: строгое разделение быстрых изолированных тестов и тяжёлых data-driven snapshot-тестов по подпапкам единого корня `tests/`.

## Requirements

### Requirement: Строгое разделение тестов по типам
Все тесты ДОЛЖНЫ лежать в едином корне `tests/` и быть строго изолированы по подпапкам типов: `tests/unit/` — быстрые изолированные unit-тесты отдельных функций и математики, работающие без файлов данных; `tests/snapshot/` — тяжёлые data-driven snapshot-тесты, прогоняющие историю свечей и сверяющие результат с эталонами. Файлы тестов в корне `tests/` НЕ ДОПУСКАЮТСЯ (кроме `conftest.py`). Новый тест ДОЛЖЕН размещаться в подпапке своего типа.

#### Scenario: Быстрое подмножество запускается отдельно
- **WHEN** разработчик запускает `pytest tests/unit`
- **THEN** выполняются только unit-тесты; файлы данных не читаются, сеть не используется

#### Scenario: Тяжёлое подмножество запускается отдельно
- **WHEN** разработчик запускает `pytest tests/snapshot`
- **THEN** выполняются только snapshot-тесты над локальными артефактами `tests/snapshot/data/`

#### Scenario: Полный прогон не меняется
- **WHEN** pytest запущен без указания пути (например, pre-commit хуком из корня)
- **THEN** обнаруживаются тесты обоих подпространств

### Requirement: Общий корневой conftest
Файл `tests/conftest.py` ДОЛЖЕН оставаться на уровне корня `tests/`: общие фикстуры и CLI-опция `--update-snapshots` ДОЛЖНЫ быть доступны обоим подпространствам без дублирования.

#### Scenario: Опция регенерации доступна snapshot-тестам
- **WHEN** pytest запущен с флагом `--update-snapshots` в пределах `tests/snapshot/`
- **THEN** опция распознана и применена; определение опции присутствует ровно в одном месте (`tests/conftest.py`)
### Requirement: Хранение analysis-эталонов
Analysis-эталоны (тренд, уровни S/R) ДОЛЖНЫ храниться в той же папке кейса `tests/snapshot/data/<КЕЙС>/`, что и фикстура `candles.csv` и стратегические эталоны. Они ДОЛЖНЫ использовать отдельный суффикс `_expected_context.csv` (а не `_expected_signals.csv`), чтобы не конфликтовать с паттерном стратегических эталонов и не быть подхваченными раннером стратегий. Свечи кейса остаются общими для стратегий и analysis-слоя.

#### Scenario: Несколько типов эталонов в одном кейсе
- **WHEN** в кейсе `NG_1h/` лежат `macd_rsi_stoch_expected_signals.csv`, `trend_expected_context.csv` и `sr_levels_expected_context.csv`
- **THEN** каждый тип эталона обрабатывается своим раннером: сигналы — `test_strategies.py`, контекст — `test_analysis.py`; уровни данных в путях не смешиваются

#### Scenario: Новая analysis-продукция подхватывается автоматически
- **WHEN** появляется новый вид analysis-эталона (например, `filter_expected_context.csv`)
- **THEN** он обнаруживается параметризацией раннера `test_analysis.py` без правки кода теста
