# Кэш данных

## Purpose

Кэш истории свечей для робота: хранит загруженные данные инструмента, дозагружает только новые закрытые бары и предоставляет стратегиям данные с готовыми (закрытыми) свечами. Избавляет от полного пересчёта индикаторов и повторной выгрузки всей истории на каждом тике.

## Requirements

### Requirement: Кэширование свечей
Система ДОЛЖНА предоставлять кэш рыночных данных, который хранит DataFrame свечей для каждой пары (инструмент, таймфрейм) и возвращает его по запросу без повторной загрузки из API, если данные актуальны. Кадры разных таймфреймов одного инструмента ДОЛЖНЫ храниться и обновляться независимо.

#### Scenario: Данные в кэше
- **WHEN** данные пары (инструмент, таймфрейм) уже загружены и актуальны
- **THEN** повторная загрузка из API не выполняется, возвращается закэшированный DataFrame

#### Scenario: Разные таймфреймы — разные кадры
- **WHEN** для одного инструмента запрошены кадры `15m` и `1h`
- **THEN** возвращаются два независимых DataFrame: свечи соответствующего таймфрейма, без смешения

### Requirement: Дозагрузка только новых баров
Кэш ДОЛЖЕН определять появление новой закрытой свечи и при необходимости дозагружать только новые бары поверх имеющихся, а не пересобирать весь срез.

Перезагрузка данных ДОЛЖНА допускать повторные попытки, чтобы дождаться появления свежего закрытого бара текущей закрытой минуты, который из-за задержки публикации может быть временно недоступен. Повторные принудительные дозагрузки ДОЛЖНЫ выполняться с паузой не чаще сконфигурированного минимального интервала перезагрузки данных (`data_refresh_min_interval`): между принудительными дозагрузками проверки готовности выполняются по кэшу без обращения к API. Принудительная дозагрузка ДОЛЖНА запрашивать только свежие бары с ограниченным окном дозагрузки (не перезапрашивая накопленную историю). Повторные попытки ДОЛЖНЫ ограничиваться таймаутом, после которого перезагрузка прекращается и кэш отдаёт имеющиеся данные.

#### Scenario: Появился новый бар
- **WHEN** граница таймфрейма пройдена и появился новый закрытый бар
- **THEN** выполняется дозагрузка новых баров и кэш обновляется

#### Scenario: Бара ещё нет
- **WHEN** новая закрытая свеча ещё не появилась
- **THEN** кэш не перезагружается, данные не меняются

#### Scenario: Свежий бар появляется после повторных попыток
- **WHEN** на первой попытке после границы свежего закрытого бара в данных ещё нет, но он появляется после малой паузы
- **THEN** кэш повторно дозагружает данные, свежий закрытый бар фиксируется и кэш обновляется

#### Scenario: Таймаут ожидания бара
- **WHEN** свежий закрытый бар не появляется в течение ограниченного таймаута повторных попыток
- **THEN** перезагрузка прекращается и кэш отдаёт имеющиеся (закэшированные) данные, не блокируясь бесконечно

#### Scenario: Форс-дозагрузка не чаще минимального интервала
- **WHEN** ожидается появление свежего закрытого бара, но интервал с последней принудительной дозагрузки меньше `data_refresh_min_interval`
- **THEN** API не вызывается; готовность проверяется по закэшированным данным

#### Scenario: Ограниченное окно дозагрузки
- **WHEN** выполняется принудительная дозагрузка свежих баров
- **THEN** запрашиваются только свежие бары в пределах окна дозагрузки (bounded backfill), накопленная история повторно не запрашивается

### Requirement: Только закрытые свечи
Кэш ДОЛЖЕН предоставлять стратегиям только завершённые (закрытые) свечи; незакрытая текущая свеча не передаётся в контур принятия решений.

#### Scenario: Живая свеча исключается
- **WHEN** текущая свеча ещё не закрыта
- **THEN** её значение не включается в данные, отдаваемые стратегиям для принятия решения

### Requirement: Признак готовности свечи
Кэш ДОЛЖЕН определять готовность свечи по границе соответствующего таймфрейма, вычисляемой планировщиком времени, — для каждой пары (инструмент, таймфрейм) независимо. Границы готовности и отслеживание загруженных баров ДОЛЖНЫ вестись в одном (tz-naive) виде времени без пояса, согласованно с планировщиком и загрузчиком.

#### Scenario: Готовность по границе
- **WHEN** момент текущего времени достиг границы закрытия свечи таймфрейма пары (инструмент, ТФ)
- **THEN** соответствующий бар этой пары считается готовым и доступным стратегиям

#### Scenario: Готовность независима между ТФ
- **WHEN** для пары (инструмент, `15m`) появился свежий закрытый бар, а для пары (инструмент, `1h`) — нет
- **THEN** готовой считается только пара `15m`; обработка привязок `1h` не выполняется

#### Scenario: Единый naive-вид границ
- **WHEN** кэш сравнивает/хранит границы готовности и известные бары
- **THEN** все значения времени приводятся к единому tz-naive состоянию (без пояса), без смешения naive и aware

### Requirement: Кадры старших таймфреймов по требованию
Система ДОЛЖНА предоставлять кадр закрытых свечей для пары (инструмент, таймфрейм) не только для активных ТФ ритма, но и по требованию для любого таймфрейма лестницы `TIMEFRAMES`. Кадр ДОЛЖЕН быть ограничен свечами со временем закрытия строго не позднее заданного момента (время закрытия рабочей свечи текущего тика). Первый запрос пары ДОЛЖЕН выполнять ленивую загрузку среза; повторные запросы без изменения границы ДОЛЖНЫ возвращать закэшированный кадр. Доступ к таким парам НЕ ДОЛЖЕН добавлять таймфрейм в множество активных ТФ ритма.

#### Scenario: Ленивая первая загрузка
- **WHEN** запрошен кадр (инструмент, `4h`), ранее не загруженный
- **THEN** выполняется загрузка среза `4h`, кадр кэшируется и возвращается

#### Scenario: Повторный запрос из кэша
- **WHEN** кадр (инструмент, `4h`) уже загружен и граница таймфрейма не изменилась
- **THEN** API не вызывается, возвращается закэшированный кадр

#### Scenario: Выравнивание по рабочей свече
- **WHEN** кадр `TF_htf` подготовлен для тика, рабочая свеча привязки закрылась в момент `T`
- **THEN** кадр содержит только закрытые свечи со временем закрытия `<= T`

#### Scenario: Не влияет на ритм
- **WHEN** кадр неактивного ТФ (`4h`) запрошен фильтром
- **THEN** множество активных ТФ ритма и ближайшая граница тика не изменяются

#### Scenario: Минимальная глубина кадра
- **WHEN** запрошен кадр `TF_int`/`TF_htf`, а в срезе к моменту рабочей свечи недостаточно закрытых свечей для прогрева индикаторов
- **THEN** кадр содержит закрытые бары вплоть до предыдущей торговой сессии включительно

### Requirement: Соблюдение лимита запросов API при дозагрузке
При исчерпании лимита запросов API (ошибка `RESOURCE_EXHAUSTED`) кэш ДОЛЖЕН прекратить дозагрузку данных: повторные дозагрузки НЕ ДОЛЖНЫ выполняться до наступления времени сброса лимита, указанного в тексте ошибки (`ratelimit_reset`); при отсутствии такого указания повторная дозагрузка допускается по истечении фиксированной паузы. После наступления времени сброса дозагрузка ДОЛЖНА возобновляться штатно.

#### Scenario: Лимит исчерпан
- **WHEN** дозагрузка возвращает `RESOURCE_EXHAUSTED` с `ratelimit_reset=30`
- **THEN** кэш не выполняет дозагрузок в течение 30 секунд, после чего повторит попытку

#### Scenario: Возобновление после сброса лимита
- **WHEN** время сброса лимита истекло
- **THEN** дозагрузка данных выполняется снова и кэш обновляется штатно

#### Scenario: Ошибка без указания сброса
- **WHEN** `RESOURCE_EXHAUSTED` не содержит `ratelimit_reset`
- **THEN** повторная попытка дозагрузки выполняется не ранее чем через фиксированную паузу после ошибки

### Requirement: Терпимая готовность таймфрейма к отстающим инструментам
Готовность по таймфрейму для гейта защитного тика ДОЛЖНА вычисляться по парам
«инструмент — таймфрейм» с фактической активностью, а не по всем загруженным
инструментам: пары, у которых свежий закрытый бар отсутствует дольше допустимого
отставания (неликвидные, не торгующие или отстающие от публикации), ДОЛЖНЫ
исключаться из гейта этого таймфрейма и НЕ ДОЛЖНЫ блокировать готовые пары и тик.
Готовность каждой отдельной пары при этом остаётся независимой от остальных.

#### Scenario: Отстающая пара не блокирует тик
- **WHEN** у пары `NG-10.26` нет свежего закрытого бара `1m`, а у пары `Si-12.26` бар
  `1m` свежий
- **THEN** готовность таймфрейма `1m` определяется по активной паре `Si-12.26`, и
  тик защитного ТФ обрабатывается

#### Scenario: Все пары таймфрейма свежие
- **WHEN** у всех загруженных пар таймфрейма свежие закрытые бары
- **THEN** готовность таймфрейма верна, гейт пропускает тик

#### Scenario: Ни одна пара не активна
- **WHEN** ни у одной пары таймфрейма нет свежего закрытого бара
- **THEN** готовность таймфрейма ложна, тик защитного ТФ не формируется до появления
  бара или истечения окна ожидания

### Requirement: Плавная восстановительная загрузка
Стартовые и восстановительные загрузки кадров множества пар «инструмент —
таймфрейм» (в том числе при догоне баров после поздней публикации) ДОЛЖНЫ
выполняться с паузой не чаще сконфигурированного минимального интервала
перезагрузки данных (`data_refresh_min_interval`) между обращениями к API, чтобы не
исчерпывать лимит запросов и не терять способность к догону.

#### Scenario: Разнесённые стартовые загрузки
- **WHEN** при старте требуется загрузить кадры нескольких пар
- **THEN** обращения к API между парами выполняются с интервалом не менее
  `data_refresh_min_interval`

#### Scenario: Восстановительная загрузка не выжигает лимит
- **WHEN** загружается большое число пар после простоя
- **THEN** загрузки разнесены минимальным интервалом, лимит запросов не исчерпывается
  в штатном режиме

### Requirement: Равномерное распределение дозагрузки между кадрами таймфрейма
Повторные принудительные дозагрузки при ожидании появления с опозданием
опубликованного закрытого бара ДОЛЖНЫ распределять ограничение
`data_refresh_min_interval` между ВСЕМИ парами «инструмент — таймфрейм» обрабатываемого
ТФ, а не обновлять одну и ту же пару: каждая пара с данными ДОЛЖНА получить
обновление за число окон ожидания, не превышающее числа таких пар. Приоритет
дозагрузки ДОЛЖЕН отдаваться парам с наиболее старым последним закрытым баром;
пара, уже имеющая свежий закрытый бар, НЕ ДОЛЖНА вхолостую перезапрашиваться.
Пара, пропущенная дозагрузкой из-за интервального ограничения в текущем окне,
НЕ ДОЛЖНА помечаться обновлённой для текущей границы.

#### Scenario: Все кадры таймфрейма обновляются равномерно
- **WHEN** у таймфрейма загружены пары `A`, `B`, `C`, закрытые бары опубликованы с
  задержкой, а интервал разрешает одно обращение к API за окно ожидания
- **THEN** каждая из пар `A`, `B`, `C` получает обновление хотя бы раз за количество
  окон ожидания, не превышающее трёх

#### Scenario: Приоритет отстающего кадра
- **WHEN** у пары `A` последний закрытый бар значительно старше, чем у свежих пар `B` и `C`
- **THEN** ближайшая дозагрузка таймфрейма обновляет пару `A`, а оборот API на свежие
  пары `B` и `C` не расходуется

#### Scenario: Пропуск по интервалу не считается обновлением
- **WHEN** дозагрузка пары `A` пропущена в текущем окне из-за интервального
  ограничения
- **THEN** пара `A` не помечается обновлённой для текущей границы и будет дозагружена
  в одном из последующих окон

#### Scenario: Форс-повторы не создают голодание
- **WHEN** появление бара таймфрейма ожидается многократными принудительными
  дозагрузками в течение длительного окна ожидания
- **THEN** повторные дозагрузки не сводятся к обновлению одной и той же пары; каждая
  пара с данными со временем становится свежей, и гейт готовности таймфрейма
  открывается
