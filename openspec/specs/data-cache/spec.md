# Кэш данных

## Purpose

Кэш истории свечей для робота: хранит загруженные данные инструмента, дозагружает только новые закрытые бары и предоставляет стратегиям данные с готовыми (закрытыми) свечами. Избавляет от полного пересчёта индикаторов и повторной выгрузки всей истории на каждом тике.

## Requirements

### Requirement: Кадр стартового контекста и торговая готовность различаются
Нормативный уровень: MUST. В текущем режиме система ДОЛЖНА предоставлять для стартового обзора последнюю доступную завершённую свечу и необходимый прогрев независимо от календарного возраста последней свечи. Достаточность истории, покрытие требуемого расчётного диапазона и готовность к текущей торговле ДОЛЖНЫ различаться явно. Неразрешённый интервал внутри необходимого диапазона НЕ ДОЛЖЕН молча выдаваться за непрерывные данные или валидный торговый сигнал. Пробел вне этого диапазона НЕ ДОЛЖЕН автоматически блокировать информационный обзор; существующий исполнительный курсор проверяется отдельно.

Решение владельца по итогам пробы 8.5: брокер не отдаёт расписание прошедших дат, поэтому для пары без сохранённых обязательств непрерывность ДОЛЖНА доказываться от момента запуска (cutover) — последнего бара этого ТФ, закрытого к запуску. Неразрешённый интервал прогрева раньше cutover, для которого нет сохранённого доказательства, НЕ ДОЛЖЕН блокировать расчёт; число таких пробелов ДОЛЖНО быть видно в диагностике пары, то есть они не скрываются молча. Интервалы после cutover проверяются строго. Для UID с сохранённой границей исполнения критический 1m-префикс ДОЛЖЕН проверяться строго от этой границы, независимо от cutover. Поиск пропусков, recovery и handoff НЕ ДОЛЖНЫ уходить раньше применимой границы.

#### Scenario: Старый конец достаточного кадра
- **WHEN** последняя закрытая свеча относится к предыдущей сессии и прогрева достаточно
- **THEN** стартовый обзор доступен с исходной датой свечи, без утверждения актуального торгового допуска

#### Scenario: Пробел вне требуемого прогрева
- **WHEN** старый пропуск находится до достаточного проверенного расчётного диапазона
- **THEN** информационный обзор не блокируется этим пропуском, восстановление истории и исполнительный барьер учитываются отдельно

#### Scenario: Пробел внутри требуемого прогрева
- **WHEN** необходимый для расчёта диапазон содержит неразрешённый ожидаемый интервал позже cutover
- **THEN** обзор явно сообщает неполное покрытие и затронутые расчёты не изображаются достоверными

#### Scenario: Пробел прогрева до запуска без доказательства
- **WHEN** пара без сохранённых обязательств запущена после выходных, а прошлые ночи не подтверждены сохранённым расписанием
- **THEN** расчёт выполняется, диагностика показывает число неподтверждённых пробелов до запуска, а пропуски после запуска удерживают пару строго

#### Scenario: Сохранённая позиция после простоя
- **WHEN** у UID есть граница исполнения раньше простоя без доказательства расписания
- **THEN** минутный префикс исполнения проверяется от этой границы, неподтверждённый простой удерживает зависимые действия UID

### Requirement: Кэширование свечей
Система ДОЛЖНА предоставлять кэш рыночных данных, который хранит DataFrame свечей для каждой пары (инструмент, таймфрейм) и возвращает его по запросу без повторной загрузки из API, если данные актуальны. Кадры разных таймфреймов одного инструмента ДОЛЖНЫ храниться и обновляться независимо.

#### Scenario: Данные в кэше
- **WHEN** данные пары (инструмент, таймфрейм) уже загружены и актуальны
- **THEN** повторная загрузка из API не выполняется, возвращается закэшированный DataFrame

#### Scenario: Разные таймфреймы — разные кадры
- **WHEN** для одного инструмента запрошены кадры `15m` и `1h`
- **THEN** возвращаются два независимых DataFrame: свечи соответствующего таймфрейма, без смешения

### Requirement: Дозагрузка только новых баров
Нормативный уровень: MUST.
Кэш ДОЛЖЕН определять появление новой закрытой свечи и при необходимости дозагружать только новые бары поверх имеющихся, а не пересобирать весь срез.

Перезагрузка данных ДОЛЖНА допускать повторные попытки, чтобы дождаться появления свежего закрытого бара текущей закрытой минуты, который из-за задержки публикации может быть временно недоступен. Повторные принудительные дозагрузки ДОЛЖНЫ выполняться с паузой не чаще сконфигурированного минимального интервала перезагрузки данных (`data_refresh_min_interval`): между принудительными дозагрузками проверки готовности выполняются по кэшу без обращения к API. Принудительная дозагрузка ДОЛЖНА запрашивать только свежие бары с ограниченным окном дозагрузки (не перезапрашивая накопленную историю). Повторные попытки ДОЛЖНЫ ограничиваться таймаутом, после которого перезагрузка прекращается и кэш отдаёт имеющиеся данные.

В историческом режиме повторные принудительные дозагрузки ДОЛЖНЫ отключаться: данные прошлого периода публикуются без задержки, поэтому повторные попытки не могут дождаться появления бара. Отсутствие бара на текущем рыночном моменте само по себе НЕ ДОЛЖНО трактоваться как конец доступных данных: отсутствие свечей объясняется разрывом в данных (перерыв между сессиями, выходной, праздник, неликвидность), а не только их исчерпанием. Кэш ДОЛЖЕН различать эти случаи, ДОЛЖЕН учитывать количество пропущенных баров внутри диапазона и ДОЛЖЕН предоставлять прогону сведения о разрыве и о следующем имеющемся баре.

#### Scenario: Появился новый бар
- **WHEN** граница таймфрейма пройдена и появился новый закрытый бар
- **THEN** выполняется дозагрузка новых баров и кэш обновляется

#### Scenario: Бара ещё нет
- **WHEN** новая закрытая свеча ещё не появилась
- **THEN** кэш не перезагружается, данные не меняются

#### Scenario: Свежий бар появляется после повторных попыток
- **WHEN** на первой попытке после границы свежего закрытого бара в данных ещё нет, но он появляется после малой паузы
- **THEN** кэш повторно дозагружает данные, свежий закрытый бар фиксируется и кэш обновляется

#### Scenario: Таймаут ожидания бара
- **WHEN** свежий закрытый бар не появляется в течение ограниченного таймаута повторных попыток
- **THEN** перезагрузка прекращается и кэш отдаёт имеющиеся (закэшированные) данные, не блокируясь бесконечно

#### Scenario: Форс-дозагрузка не чаще минимального интервала
- **WHEN** ожидается появление свежего закрытого бара, но интервал с последней принудительной дозагрузки меньше `data_refresh_min_interval`
- **THEN** API не вызывается; готовность проверяется по закэшированным данным

#### Scenario: Ограниченное окно дозагрузки
- **WHEN** выполняется принудительная дозагрузка свежих баров
- **THEN** запрашиваются только свежие бары в пределах окна дозагрузки (bounded backfill), накопленная история повторно не запрашивается

#### Scenario: Конец данных в историческом режиме
- **WHEN** в историческом прогоне на текущем рыночном моменте свежий закрытый бар отсутствует
- **THEN** повторные попытки перезагрузки не выполняются, кэш возвращает накопленные бары и сообщает прогону, есть ли следующий имеющийся бар

#### Scenario: Отсутствие бара в историческом режиме не равно конец данных
- **WHEN** в историческом прогоне свежий закрытый бар отсутствует, но следующий бар найден в допустимом горизонте
- **THEN** повторные попытки перезагрузки не выполняются, кэш НЕ сигнализирует конец доступных данных и сообщает прогону момент следующего имеющегося бара

#### Scenario: Данные действительно закончились
- **WHEN** в историческом прогоне свежий бар отсутствует и следующего бара нет во всём проверенном остатке диапазона
- **THEN** кэш сигнализирует конец доступных данных до конца диапазона и возвращает накопленные бары

#### Scenario: Молчание источника не выдаётся за конец данных
- **WHEN** при поиске следующего имеющегося бара источник отвечает ошибкой
- **THEN** кэш НЕ сигнализирует конец доступных данных, разрыв остаётся открытым, а поиск повторяется на следующих рыночных тиках

#### Scenario: Учёт пропущенных баров
- **WHEN** внутри диапазона отсутствует ожидаемый бар
- **THEN** кэш увеличивает счётчик пропусков, и значение доступно для отчёта прогона

### Requirement: Только закрытые свечи
Кэш ДОЛЖЕН предоставлять стратегиям только завершённые (закрытые) свечи; незакрытая текущая свеча не передаётся в контур принятия решений.

#### Scenario: Живая свеча исключается
- **WHEN** текущая свеча ещё не закрыта
- **THEN** её значение не включается в данные, отдаваемые стратегиям для принятия решения

### Requirement: Признак готовности свечи
Нормативный уровень: MUST. Кэш ДОЛЖЕН определять готовность каждой пары независимо по временной сетке, фактически полученному закрытому бару и доказательному покрытию необходимого диапазона. Календарная граница сама по себе НЕ ДОЛЖНА считать отсутствующий бар готовым. В stream-режиме подтверждение подписки и handoff/recovery-барьер ДОЛЖНЫ учитываться отдельно от высокого received timestamp. Время ДОЛЖНО нормализоваться в UTC и храниться в согласованном tz-naive представлении внутренних сравнений; aware-значение сначала конвертируется в UTC.

#### Scenario: Готовность по границе
- **WHEN** достигнуто время закрытия, нужный завершённый бар получен и необходимый диапазон доказательно разрешён
- **THEN** эта пара становится готовой обработке

#### Scenario: Готовность независима между ТФ
- **WHEN** 1h готова, а 15m после календарной границы всё ещё не опубликована
- **THEN** готовой считается 1h; 15m не видна стратегии как незавершённый или фиктивно закрытый бар и не исполняет преждевременный сигнал

#### Scenario: Единый naive-вид границ
- **WHEN** кэш сравнивает/хранит границы и бары из разных транспортов
- **THEN** используются UTC-naive значения после корректной UTC-конвертации, без смешения aware/naive и без сдвига open_time

#### Scenario: Время наступило, а данных нет
- **WHEN** пройдена граница минуты, но завершённый бар ещё не получен
- **THEN** readiness ложен; допустимо диагностическое ожидание/recovery, но не торговый тик по отсутствующим данным

### Requirement: Кадры старших таймфреймов по требованию
Система ДОЛЖНА предоставлять кадр закрытых свечей для пары (инструмент, таймфрейм) не только для активных ТФ ритма, но и по требованию для любого таймфрейма лестницы `TIMEFRAMES`. Кадр ДОЛЖЕН быть ограничен свечами со временем закрытия строго не позднее заданного момента (время закрытия рабочей свечи текущего тика). Первый запрос пары ДОЛЖЕН выполнять ленивую загрузку среза; повторные запросы без изменения границы ДОЛЖНЫ возвращать закэшированный кадр. Доступ к таким парам НЕ ДОЛЖЕН добавлять таймфрейм в множество активных ТФ ритма.

#### Scenario: Ленивая первая загрузка
- **WHEN** запрошен кадр (инструмент, `4h`), ранее не загруженный
- **THEN** выполняется загрузка среза `4h`, кадр кэшируется и возвращается

#### Scenario: Повторный запрос из кэша
- **WHEN** кадр (инструмент, `4h`) уже загружен и граница таймфрейма не изменилась
- **THEN** API не вызывается, возвращается закэшированный кадр

#### Scenario: Выравнивание по рабочей свече
- **WHEN** кадр `TF_htf` подготовлен для тика, рабочая свеча привязки закрылась в момент `T`
- **THEN** кадр содержит только закрытые свечи со временем закрытия `<= T`

#### Scenario: Не влияет на ритм
- **WHEN** кадр неактивного ТФ (`4h`) запрошен фильтром
- **THEN** множество активных ТФ ритма и ближайшая граница тика не изменяются

#### Scenario: Минимальная глубина кадра
- **WHEN** запрошен кадр `TF_int`/`TF_htf`, а в срезе к моменту рабочей свечи недостаточно закрытых свечей для прогрева индикаторов
- **THEN** кадр содержит закрытые бары вплоть до предыдущей торговой сессии включительно

### Requirement: Соблюдение лимита запросов API при дозагрузке
Нормативный уровень: MUST. При исчерпании лимита запросов сервиса источника (ошибка `RESOURCE_EXHAUSTED`) все полосы этого сервиса ДОЛЖНЫ прекратить запросы до времени сброса, указанного источником (`ratelimit_reset`). При отсутствии такого указания повтор допускается по истечении фиксированной паузы. Пауза одного сервиса НЕ ДОЛЖНА останавливать запросы другого сервиса. После сброса запросы ДОЛЖНЫ возобновляться в порядке приоритета полос. Потолок запросов робота по сервису ДОЛЖЕН быть не выше лимита источника и оставлять настраиваемую часть квоты другим приложениям пользователя.

#### Scenario: Лимит исчерпан
- **WHEN** GetCandles возвращает `RESOURCE_EXHAUSTED` с `ratelimit_reset=30`
- **THEN** ни одна полоса не выполняет запросов сервиса котировок в течение 30 секунд, после чего запросы возобновляются

#### Scenario: Возобновление после сброса лимита
- **WHEN** время сброса лимита истекло
- **THEN** живая полоса получает квоту первой, затем полосы доказательств и полноты в пределах своих долей

#### Scenario: Ошибка без указания сброса
- **WHEN** `RESOURCE_EXHAUSTED` не содержит `ratelimit_reset`
- **THEN** повторные запросы этого сервиса выполняются не ранее чем через фиксированную паузу после ошибки

#### Scenario: Лимит одного сервиса
- **WHEN** сервис котировок ограничен, а полосе календаря нужен TradingSchedules
- **THEN** запрос сервиса инструментов выполняется без ожидания сброса котировок

### Requirement: Терпимая готовность таймфрейма к отстающим инструментам
Нормативный уровень: MUST.
Готовность по таймфрейму для гейта защитного тика ДОЛЖНА вычисляться по парам «инструмент — таймфрейм» с фактической активностью: пары, у которых свежий закрытый бар отсутствует дольше допустимого отставания, ДОЛЖНЫ исключаться из гейта и НЕ ДОЛЖНЫ блокировать готовые пары и тик. Готовность каждой отдельной пары остаётся независимой от остальных.

В автоматической истории в торговую готовность ДОЛЖНЫ входить только пары текущего или ожидающего активации контракта и контрактов с незавершёнными обязательствами. Пары исключительно прогрева будущих участков и завершённых контрактов НЕ ДОЛЖНЫ влиять на этот гейт. Готовность ожидающего контракта НЕ ДОЛЖНА сама разрешать вход до завершения переходного барьера.

#### Scenario: Отстающая пара не блокирует тик
- **WHEN** у пары NG-10.26 нет свежего 1m-бара, а у Si-12.26 бар свежий
- **THEN** готовность 1m определяется активной парой Si-12.26, защитный тик обрабатывается

#### Scenario: Все пары таймфрейма свежие
- **WHEN** у всех участвующих в торговой готовности пар свежие закрытые бары
- **THEN** готовность таймфрейма верна, гейт пропускает тик

#### Scenario: Ни одна пара не активна
- **WHEN** ни у одной участвующей торговой пары нет свежего закрытого бара
- **THEN** гейт ложен до появления бара или истечения ожидания, а календарная граница перехода обрабатывается независимо

#### Scenario: Будущий контракт загружен для прогрева
- **WHEN** следующий будущий участок загружен исключительно для прогрева
- **THEN** его отсутствие свежих баров не блокирует текущие торговые пары

### Requirement: Плавная восстановительная загрузка
Стартовые и восстановительные загрузки кадров множества пар «инструмент —
таймфрейм» (в том числе при догоне баров после поздней публикации) ДОЛЖНЫ
выполняться с паузой не чаще сконфигурированного минимального интервала
перезагрузки данных (`data_refresh_min_interval`) между обращениями к API, чтобы не
исчерпывать лимит запросов и не терять способность к догону.

#### Scenario: Разнесённые стартовые загрузки
- **WHEN** при старте требуется загрузить кадры нескольких пар
- **THEN** обращения к API между парами выполняются с интервалом не менее
  `data_refresh_min_interval`

#### Scenario: Восстановительная загрузка не выжигает лимит
- **WHEN** загружается большое число пар после простоя
- **THEN** загрузки разнесены минимальным интервалом, лимит запросов не исчерпывается
  в штатном режиме

### Requirement: Равномерное распределение дозагрузки между кадрами таймфрейма
Нормативный уровень: MUST. Повторные свежие дозагрузки ДОЛЖНЫ справедливо распределять ограничение `data_refresh_min_interval` между ВСЕМИ допустимыми парами обрабатываемого ТФ. Каждая такая пара, включая пару с пустым кадром после предыдущего ответа, ДОЛЖНА получить свежий запрос за количество разрешённых свежих окон, не превышающее числа этих пар. В текущем режиме справедливость ДОЛЖНА сохраняться и между таймфреймами при общем ограничении API.

Наиболее отстающая пара ДОЛЖНА получать первый приоритет в обороте, но отсутствие прогресса после её попытки НЕ ДОЛЖНО возвращать ей каждое следующее окно до обслуживания остальных пар. Уже свежая пара НЕ ДОЛЖНА перезапрашиваться вхолостую ради той же границы. Пропуск из-за интервального ограничения НЕ ДОЛЖЕН считаться обновлением. Восстановительные запросы ДОЛЖНЫ учитываться отдельно и НЕ ДОЛЖНЫ заменять положенные свежие запросы.

#### Scenario: Все кадры таймфрейма обновляются равномерно
- **WHEN** допустимы пары A, B, C и разрешён один свежий запрос за окно
- **THEN** каждая получает запрос хотя бы раз за три свежих окна

#### Scenario: Приоритет отстающего кадра
- **WHEN** у A последний бар старше, чем у остальных нуждающихся в обновлении пар
- **THEN** первый запрос оборота получает A, затем обслуживаются остальные пары независимо от результата A

#### Scenario: Пропуск по интервалу не считается обновлением
- **WHEN** запрос A пропущен из-за минимального интервала
- **THEN** A остаётся в очереди необслуженных пар текущего оборота

#### Scenario: Форс-повторы не создают голодание
- **WHEN** A многократно возвращает пустой ответ, а B и C имеют новые опубликованные бары
- **THEN** B и C получают свои свежие запросы в пределах оборота и становятся доступными анализу

#### Scenario: Ранее пустой кадр начинает получать данные
- **WHEN** первая загрузка пары была пустой, но сессия открылась и свечи появились
- **THEN** пара повторно опрашивается по свежей очереди и не остаётся навсегда пустой

#### Scenario: Голодание между таймфреймами
- **WHEN** несколько ТФ одновременно нуждаются в дозагрузке при общем лимите запросов
- **THEN** ни один ТФ не забирает все окна, каждый получает свежие запросы за ограниченный общий оборот

### Requirement: Учёт конца данных по рыночным тикам
Нормативный уровень: MUST.
Проверки конца доступных данных ДОЛЖНЫ агрегироваться по рыночному тику, а не
выполняться отдельно для каждого таймфрейма. Один рыночный тик ДОЛЖЕН давать
ровно одну запись в счётчик последовательных тиков без прогресса, независимо от
того, сколько таймфреймов обновлялось на этом тике.

Таймфрейм, у которого на текущем рыночном моменте закрытый бар ещё не ожидается
(старший таймфрейм внутри интервала между его границами), ДОЛЖЕН исключаться из
расчёта тика без прогресса. Тик, на котором ни у одного таймфрейма не ожидается
закрытый бар, ДОЛЖЕН игнорироваться и не учитываться ни в одном счётчике.

Счётчик ДОЛЖЕН сбрасываться при появлении любого нового закрытого бара, поэтому
наличие прогресса по одному таймфрейму ДОЛЖНО отменять сигнал конца данных,
поднятый остальными таймфреймами на том же тике.

В историческом режиме накопленный счётчик тиков без прогресса ДОЛЖЕН
преобразовываться в разрыв данных, а не в конец прогона: кэш ДОЛЖЕН искать
следующий имеющийся закрытый бар и передавать прогону его момент. Конец доступных
данных ДОЛЖЕН сигнализироваться только по результату поиска, а не по пустым тикам.
Поиск ДОЛЖЕН быть ограничен минимумом конца диапазона и текущего момента плюс
семь суток. При отсутствии бара кэш ДОЛЖЕН передать границы проверенного
горизонта и различие между полным остатком диапазона и ограниченным поиском;
отсутствие за пределами проверенного горизонта НЕ ДОЛЖНО утверждаться.

#### Scenario: Старшие таймфреймы не завершают прогон
- **WHEN** в тик приходят проверки таймфреймов `15m`, `1m`, `1h`, `5m`, у которых
  закрытые бары уже опубликованы, и только у `1m` появился новый закрытый бар
- **THEN** тик учитывается как тик с прогрессом, конец доступных данных не
  сигнализируется

#### Scenario: Тик без ожидаемого бара игнорируется
- **WHEN** на рыночном моменте не истекла граница закрытия ни для одного
  таймфрейма, поэтому ожидаемых закрытых баров нет
- **THEN** счётчик тиков без прогресса не увеличивается и конец доступных данных
  не сигнализируется

#### Scenario: Пропуск считается один раз за тик
- **WHEN** на одном тике ожидаемый закрытый бар отсутствует у нескольких
  таймфреймов
- **THEN** счётчик тиков без прогресса увеличивается ровно на единицу

#### Scenario: Повторная проверка одного таймфрейма не удваивает счётчик
- **WHEN** один и тот же таймфрейм проверяется на тике повторно
- **THEN** таймфрейм учитывается в ожидаемых барах тика один раз

#### Scenario: Тики без прогресса не обрывают прогон при наличии следующего бара
- **WHEN** ни у одного таймфрейма не появилось нового закрытого бара несколько
  рыночных тиков подряд, но следующий закрытый бар найден в допустимом горизонте
- **THEN** конец доступных данных НЕ сигнализируется, кэш сообщает момент
  следующего бара, пропущенные бары учитываются в счётчике прогона

#### Scenario: Конец данных по-прежнему объявляется
- **WHEN** ни у одного таймфрейма не появилось нового закрытого бара несколько
  рыночных тиков подряд и следующего бара нет в проверенном горизонте
- **THEN** кэш сигнализирует исчерпание проверенного горизонта с его границами; прогон отличает его от отсутствия данных во всём остатке диапазона

#### Scenario: Ограниченный поиск не доказывает конец всей истории
- **WHEN** проверенный горизонт заканчивается через семь суток раньше конца диапазона и бара в нём нет
- **THEN** кэш сообщает ограниченность поиска и не утверждает отсутствие бара после проверенного участка

### Requirement: Разрывы в данных учитываются отдельно от конца доступных данных
Нормативный уровень: MUST.
Кэш ДОЛЖЕН вести учёт разрывов в данных отдельно от конца доступных данных.
Каждый разрыв — непрерывный промежуток рыночного времени без ожидаемых баров —
ДОЛЖЕН учитываться один раз со своим моментом начала, моментом продолжения и
количеством пропущенных баров. Количество разрывов и самый длинный разрыв ДОЛЖНЫ
быть доступны для отчёта прогона.

#### Scenario: Разрыв учтён один раз
- **WHEN** на нескольких последовательных тиках ожидаемый бар отсутствует, а затем
  данные возобновляются
- **THEN** разрыв учтён ровно один раз с количеством пропущенных баров за весь
  промежуток отсутствия баров

#### Scenario: Данные возобновились — разрыв закрыт
- **WHEN** после разрыва появился новый закрытый бар
- **THEN** разрыв считается завершённым, счётчик последовательных тиков без
  прогресса сбрасывается

#### Scenario: Сведения о разрывах доступны отчёту
- **WHEN** прогон завершился после нескольких разрывов
- **THEN** отчёт содержит количество разрывов и длительность самого длинного
  разрыва

### Requirement: Кэш текущего режима поверх долговечного покрытия
Нормативный уровень: MUST. В текущем режиме кэш ДОЛЖЕН предоставлять кадры
из завершённых свечей, уже записанных в локальное хранилище. Проверка
готовности ДОЛЖНА учитывать состояние покрытия пары «источник — инструмент —
таймфрейм», а не только время последней свечи. Полученная поздняя версия
ДОЛЖНА быть видна при следующем построении кадра, сохраняя её исходное время;
сама по себе она НЕ ДОЛЖНА запускать торговое решение задним числом.

#### Scenario: Свежий конец при дыре внутри кадра
- **WHEN** в локальном хранилище есть свечи 12:00, 12:02 и 12:03, но 12:01 не разрешена
- **THEN** кэш не сообщает потребителю, что диапазон до 12:03 непрерывен

#### Scenario: Дозагружена старая минута
- **WHEN** поздно сохранена завершённая свеча 12:01
- **THEN** следующий кадр содержит её на месте между 12:00 и 12:02 без дублирования других свечей

### Requirement: Изоляция служебных пар контрактной цепочки
Нормативный уровень: MUST.
Система ДОЛЖНА различать торговые/ожидающие активации, сопровождаемые, исключительно прогреваемые и завершённые пары контрактной цепочки. Исключительно прогреваемые и завершённые пары НЕ ДОЛЖНЫ создавать исполнения, обновлять исполнительные курсоры, увеличивать статистику торговых пропусков или определять конец данных прогона. Пары сопровождения ДОЛЖНЫ сохраняться до подтверждённого завершения обязательств независимо от смены контракта для входов.

Данные каждого контракта ДОЛЖНЫ храниться отдельно и ограничиваться закрытыми свечами на рыночный момент запроса, включая прогрев и старшие фильтры. Предварительное чтение будущего покрытия ДОЛЖНО оставаться предпроверкой и не передаваться торговым решениям как уже доступная история.

#### Scenario: Прогрев не двигает исполнение
- **WHEN** загружена собственная история следующего контракта до активации
- **THEN** по ней не создаются fills, исполнительный курсор не перескакивает через первые допустимые торговые бары

#### Scenario: Завершённый контракт больше не имеет свечей
- **WHEN** старый контракт завершён и его история закончилась
- **THEN** он не создаёт дополнительные пропуски и не завершает прогон следующего участка

#### Scenario: Старый остаток ещё открыт
- **WHEN** новые входы старого контракта запрещены, но его позиция не закрыта
- **THEN** его минутные бары остаются в исполнении и переоценке до завершения обязательств

#### Scenario: Будущие свечи прочитаны предпроверкой
- **WHEN** предпроверка уже проверила конец следующего участка
- **THEN** стратегия на текущем тике всё равно получает только свечи, закрытые не позже текущего рыночного момента

### Requirement: Непрерывный handoff истории и stream
Нормативный уровень: MUST. Старт stream-пары ДОЛЖЕН последовательно обеспечить подтверждённую подписку, ограниченную буферизацию, историческое перекрытие, согласование дублей/версий и установление необходимой полноты до открытия торговой готовности. Ошибка истории, ACK, переполнение или reconnect во время старта НЕ ДОЛЖНЫ создавать незамеченный участок между источниками. При наличии сохранённых данных необходимость восстановления определяется durable границами, а не наличием непустого кадра.

#### Scenario: Свеча пришла во время загрузки истории
- **WHEN** stream доставил минуту после открытия подписки, пока GetCandles ещё загружает прошлые данные
- **THEN** минута сохранена/буферизована и согласована с перекрытием прежде READY, без потери или второго исполнения

#### Scenario: Историческая загрузка не удалась
- **WHEN** подтверждённый stream работает, но необходимая история/полнота не установлена
- **THEN** приём продолжается в пределах лимитов, соответствующая пара остаётся неготовой и диагностируется

### Requirement: Доказанный префикс и критический барьер 1m
Нормативный уровень: MUST. Проверка полноты ДОЛЖНА покрывать всю необходимую последовательность и её хвост относительно session calendar/lifecycle, включая интервалы до первого нового события после outage. Неизвестная календарная применимость, временная пустота и действительно неподтверждённый интервал НЕ ДОЛЖНЫ изображаться полученной или разрешённой минутой.

Интервал в состоянии «у источника нет» ДОЛЖЕН считаться разрешённым для непрерывного префикса и барьера 1m без создания свечи: решение владельца 13.10.2026, источник — истина для свечей. Пропуск такой минуты исполнением ДОЛЖЕН быть явно отмечен по правилам исполнения.

При обязательной защите отсутствие критической 1m без итогового состояния ДОЛЖНО сразу удерживать:
- свечное исполнение неизвестной и последующих зависимых минут;
- новые торговые решения;
- индикаторные изменения, требующие неполной истории или исполнительного результата соответствующего UID.

Подтверждённое состояние позиций и ордеров ДОЛЖНО сохраняться. Существующая обработка подтверждений и операции, действительно не зависящие от отсутствующего входа, НЕ ДОЛЖНЫ отключаться общей блокировкой UID. Они НЕ ДОЛЖНЫ изображать выполненную свечную защиту, обходить собственные предусловия либо создавать новую торговую политику. Приём данных и допустимая обработка здоровых пар ДОЛЖНЫ продолжаться. Таймаут изменяет диагностику или режим, но не создаёт полноту и не разрешает перескок.

#### Scenario: Внутренняя минута потеряна
- **WHEN** известны 12:00 и 12:02, но торговая 12:01 не разрешена
- **THEN** разрыв обнаружен несмотря на новый high-water timestamp, последующие минуты не объявляются непрерывными

#### Scenario: Нет следующей свечи, чтобы обнаружить хвост
- **WHEN** после 12:00 больше нет событий, хотя календарь ожидает завершённые торговые интервалы
- **THEN** таймер/expected-sequence обнаруживает хвостовой диапазон и ставит пару в очередь полосы доказательств

#### Scenario: Критическая 1m отсутствует
- **WHEN** открытой позиции нужна защитная обработка 12:01, а получена только 12:02
- **THEN** 12:02 не передаётся как непрерывное продолжение, индикаторное сопровождение/новые входы этого UID удерживаются, причина и границы видимы

#### Scenario: Пришёл старый пропуск до исполнения следующих
- **WHEN** 12:01 восстановлена, а 12:02 ещё удерживается перед ней
- **THEN** они обрабатываются последовательно по прежним правилам активных ордеров, ровно по одному разу

#### Scenario: Состояние существующей позиции при минутном gap
- **WHEN** UID имеет позицию, подтверждённый стоп и pending-обязательства, но критическая минута неизвестна
- **THEN** подтверждённое состояние сохраняется; OHLC-срабатывание стопа/тейка, observation и продвижение processed через gap не выдумываются, автоматическая отмена защиты или закрытие по timeout не создаются

#### Scenario: Независимое подтверждение и здоровый UID
- **WHEN** у UID A критический минутный gap, уже существует допустимое подтверждение по сохранённой операции, а UID B имеет пригодные данные
- **THEN** подтверждение проходит существующий идемпотентный путь без чтения неизвестного OHLC; данные/защита B продолжаются, общий риск сохраняет существующее право отказать увеличению при неизвестной оценке

#### Scenario: Нет рабочей 15m при готовой защите
- **WHEN** необходимая рабочая 15m отсутствует, но исполнительная 1m того же UID непрерывна и готова
- **THEN** удерживаются потребители отсутствующей 15m, а допустимая минутная защита не блокируется только из-за отсутствия рабочего бара

#### Scenario: Минута отсутствует у источника
- **WHEN** 12:01 получила «у источника нет», а 12:00 и 12:02 получены
- **THEN** префикс 1m продолжается через 12:01 без свечи, 12:02 становится непрерывным продолжением, а пропуск 12:01 отмечается исполнением

### Requirement: Нескользящее ожидание отсутствующей свечи
Нормативный уровень: MUST. Для 1m/15m/1h ожидание ДОЛЖНО фиксироваться относительно первой необходимой отсутствующей закрытой границы и отдельного настроенного publication timeout. Истечение этого срока ДОЛЖНО переводить диагностику в delayed/unresolved и планировать ограниченную проверку. Опрос, новый максимальный timestamp, ping или следующий период НЕ ДОЛЖНЫ сдвигать deadline старого gap или объявлять его разрешённым. Известный disconnect/overflow ДОЛЖЕН инициировать recovery без ожидания publication timeout. Доказанный календарный перерыв/no-trade ДОЛЖЕН учитываться отдельно от задержки/потери; срок ожидания НЕ ДОЛЖЕН расширять действующее окно актуальности решения.

#### Scenario: Новая минута пришла через внутреннюю дыру
- **WHEN** deadline установлен для отсутствующей 12:01, а позже получена 12:02
- **THEN** первоначальный deadline и неразрешённый интервал 12:01 сохраняются несмотря на продвижение received high-water

#### Scenario: Разрыв известен до publication deadline
- **WHEN** после закрытия необходимой свечи зафиксирован обрыв либо переполнение буфера
- **THEN** recovery планируется сразу по сохранённым границам, без ожидания окончания publication timeout

### Requirement: Неизменяемый вход тика и разделение курсоров
Нормативный уровень: MUST. Торговый тик ДОЛЖЕН читать согласованный неизменяемый срез версий входных свечей; конкурентная коррекция НЕ ДОЛЖНА менять OHLC уже начатого исполнения. Получение, непрерывное разрешение, анализ и исполнение ДОЛЖНЫ иметь разные границы. Input-revision ссылки начатого/обработанного пакета ДОЛЖНЫ сохраняться в рыночном состоянии для безопасного продолжения после сбоя, без миграции финансовой истины в рыночный кэш. Исполнительный cursor продвигается только после существующего durable commit; receipt или warmup его не меняют.

#### Scenario: Исправление во время тика
- **WHEN** новая версия пришла между чтением среза и commit финансовых фактов
- **THEN** начатый пакет сохраняет выбранную версию, исправление учитывается отдельно и не создаёт второе исполнение этой минуты

#### Scenario: Рестарт после финансового commit
- **WHEN** финансовая обработка минуты завершена, а market-marker ещё не записан
- **THEN** сверка использует сохранённый input-reference и существующую durable границу сделки, не проигрывает исправленную минуту заново

### Requirement: Ожидаемый завершённый интервал из календарного ожидания
Нормативный уровень: MUST. В текущем режиме кэш ДОЛЖЕН брать последний ожидаемый завершённый интервал пары и его срок публикации только из календарного ожидания. Ожидаемый интервал используется для:
- выбора пар свежей дозагрузки;
- верхней границы запроса закрытой сессии;
- обнаружения ожидаемой последовательности;
- состояния пары.

Пара, у которой этот интервал получен или разрешён, ДОЛЖНА считаться актуальной независимо от календарного возраста последней свечи. При неизвестной фазе ДОЛЖНО применяться прежнее сеточное ожидание с причиной «расписание неизвестно»; оно НЕ ДОЛЖНО объявлять пару актуальной по отсутствию расписания.

Календарное ожидание НЕ ДОЛЖНО заменять доказательное покрытие, разделение границ получения, разрешения и исполнения или барьер готовности. Ожидаемый интервал лишь указывает, какие интервалы подлежат проверке.

#### Scenario: Последний бар пятницы получен
- **WHEN** в понедельник 03:00 МСК последний ожидаемый интервал пары — получённый последний бар пятничной сессии
- **THEN** пара актуальна и не ставится в свежую дозагрузку до следующего события

#### Scenario: Последний бар закрытой сессии ещё не получен
- **WHEN** сессия закрыта, а её последний ожидаемый интервал не получен
- **THEN** пара ставится в дозагрузку собственного диапазона этой свечи без чтения ночи

#### Scenario: Расписание неизвестно
- **WHEN** у пары неизвестная фаза
- **THEN** используется сеточное ожидание, свежие запросы не сокращаются, причина видна в состоянии

### Requirement: Верхняя граница стартовой загрузки и прогрева
Нормативный уровень: MUST. Стартовая загрузка и прогрев пары ДОЛЖНЫ ограничиваться закрытием последнего ожидаемого завершённого интервала. Они НЕ ДОЛЖНЫ ждать бар, который по календарю ещё не мог завершиться, а также следующую календарную границу или открытие рынка. Достаточность прогрева ДОЛЖНА по-прежнему определяться фактическим числом закрытых баров. Перерывы и закрытия НЕ ДОЛЖНЫ считаться недостающими барами прогрева.

#### Scenario: Старт в выходной
- **WHEN** робот запущен в воскресенье, а прогрев требует 200 баров 1h
- **THEN** прогрев набирает 200 фактических закрытых часовых баров до последнего ожидаемого интервала пятницы и не ждёт понедельника

### Requirement: Свежесть текущей цены входа по календарю
Нормативный уровень: MUST. Проверка текущей цены входа ДОЛЖНА считать базовую минутную цену актуальной, только если:
- фаза «торги»;
- последний ожидаемый завершённый минутный интервал получен;
- срок его публикации не истёк без получения.

В фазе перерыва или закрытия вход ДОЛЖЕН отклоняться с причиной, называющей перерыв или закрытие. При неизвестной фазе ДОЛЖНО применяться прежнее ограничение возраста цены с причиной «расписание неизвестно». Календарь НЕ ДОЛЖЕН расширять действующее окно актуальности торгового решения, допустимое отклонение цены или ограничения риска.

#### Scenario: Цена в начале сессии
- **WHEN** сессия открылась, первая минута ещё в пределах срока публикации
- **THEN** вход ожидает актуальной цены и не использует цену прошлой сессии как текущую

#### Scenario: Вход во время клиринга
- **WHEN** кандидат проверяется в фазе «перерыв» из-за клиринга
- **THEN** вход отклоняется с причиной «перерыв в торгах»

### Requirement: Историческая свежесть по расписанию снимка
Нормативный уровень: MUST. В историческом режиме проверка свежего закрытого бара таймфрейма ДОЛЖНА использовать последний ожидаемый интервал по расписанию снимка, если оно применимо к дате. При неизвестной фазе ДОЛЖНО сохраняться прежнее сеточное правило. Историческая проверка НЕ ДОЛЖНА выполнять сетевых запросов к брокеру и НЕ ДОЛЖНА менять виртуальные часы, первый и последний обрабатываемый бар и порядок обработки.

#### Scenario: Выходные внутри исторического диапазона
- **WHEN** виртуальное время находится в субботе, а расписание снимка подтверждает закрытие
- **THEN** отсутствие новых баров не считается отставанием пары, пятничный последний бар остаётся последним ожидаемым

#### Scenario: Снимок без расписания
- **WHEN** эмулятор не вернул расписание для даты
- **THEN** свежесть проверяется прежним сеточным правилом, результат прогона не зависит от недоступного расписания
