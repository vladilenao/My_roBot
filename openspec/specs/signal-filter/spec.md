# Фильтр сигналов

## Purpose

Фильтрует торговые сигналы по именованным профилям фильтрации: фасад выбирает конкретный фильтр фабричным методом по имени профиля привязки (по умолчанию `basic_levels` — блокировка против тренда). Является чистым трансформером Decision — не зависит от ExecutionPort и не выполняет доставку.

## Requirements

### Requirement: Жёсткий фильтр по тренду
Профиль фильтрации `basic_levels` ДОЛЖЕН при противоречии тренда и сигнала заменять тип сигнала на HOLD. Противоречие: тренд `down` + сигнал BUY, или тренд `up` + сигнал SELL. При тренде `flat` или совпадении направления — сигнал пропускается без изменений.

#### Scenario: Сигнал против тренда
- **WHEN** профиль `basic_levels`, тренд `down` и сигнал BUY (или тренд `up` и сигнал SELL)
- **THEN** фильтр возвращает Decision с типом HOLD

#### Scenario: Сигнал по тренду
- **WHEN** профиль `basic_levels`, тренд `up` и сигнал BUY (или тренд `down` и сигнал SELL)
- **THEN** фильтр возвращает Decision с тем же типом сигнала, обогащённый полями тренда из MarketContext

#### Scenario: Боковой тренд
- **WHEN** профиль `basic_levels` и тренд `flat`
- **THEN** фильтр пропускает любой сигнал (BUY/SELL) без изменений

#### Scenario: HOLD не фильтруется
- **WHEN** входной Decision имеет тип HOLD
- **THEN** фильтр возвращает его без изменений при любом профиле

### Requirement: Обогащение контекстом тренда
Профиль `basic_levels` ДОЛЖЕН добавлять к Decision метаданные тренда: `trend_direction` (строковое значение направления) и `trend_confidence` (сила тренда 0.0–1.0). При HOLD по фильтру confidence ДОЛЖНА быть 0.0. Профиль `raw` НЕ ДОЛЖЕН обогащать Decision.

#### Scenario: Сигнал пропущен
- **WHEN** сигнал не заблокирован фильтром профиля `basic_levels`
- **THEN** Decision содержит `trend_direction` и `trend_confidence` из текущего MarketContext

#### Scenario: Сигнал заблокирован
- **WHEN** сигнал заменён на HOLD из-за противоречия тренду
- **THEN** Decision содержит `trend_direction` из MarketContext и `trend_confidence = 0.0`

### Requirement: Чистый трансформер
Фасад фильтрации ДОЛЖЕН быть stateless frozen dataclass с методом `apply(decision, ctx, profile_name, instrument="", timeframe="") → Decision`; опциональные `instrument` и `timeframe` передают контекст привязки данным-зависимым профилям (для выбора старших таймфреймов). Выбор конкретного фильтра ДОЛЖЕН выполняться внутри фасада фабричным методом по имени профиля. Фильтр НЕ ДОЛЖЕН выполнять доставку результатов. Зависимости от источников данных (кадры высших ТФ, рыночный контекст) профиль ДОЛЖЕН получать через конструктор при построении, а не внутри `apply`. Фасад и профили НЕ ДОЛЖНЫ зависеть от ExecutionPort и нотификатора.

#### Scenario: Независимость от порта исполнения
- **WHEN** фильтр применяется к Decision
- **THEN** ни один ExecutionPort не вызывается, доставка не выполняется

#### Scenario: Выбор фильтра фабричным методом
- **WHEN** вызвано `apply(decision, ctx, profile_name="raw", instrument="SBER", timeframe="15m")`
- **THEN** фасад конструирует фильтр профиля `raw` по имени и делегирует ему решение; параметры привязки передаются профилю

#### Scenario: Передача контекста привязки
- **WHEN** применён данные-зависимый профиль `triple_screen`
- **THEN** в `apply` переданы `instrument` и `timeframe` привязки, по которым профиль определяет старшие таймфреймы; профили без потребности в данных (`basic_levels`, `raw`) игнорируют эти параметры

### Requirement: Реестр профилей фильтрации
Система ДОЛЖНА предоставлять реестр профилей фильтрации, содержащий профили `raw`, `basic_levels` и `triple_screen`. Профиль по умолчанию — `basic_levels`. Запрос неизвестного имени профиля ДОЛЖЕН завершаться ошибкой с перечнем доступных профилей. Добавление нового профиля ДОЛЖНО выполняться регистрацией класса фильтра в реестре без изменения главного цикла робота. Регистрация данных-зависимого профиля НЕ ДОЛЖНА менять сигнатуру фасада: зависимости передаются в конструктор.

#### Scenario: Профиль по умолчанию
- **WHEN** привязка не задаёт профиль фильтрации
- **THEN** применяется профиль `basic_levels`

#### Scenario: Неизвестный профиль
- **WHEN** запрошен профиль с незарегистрированным именем
- **THEN** выбрасывается ошибка с перечнем доступных профилей

#### Scenario: Расширение реестра
- **WHEN** в реестр зарегистрирован новый класс фильтра
- **THEN** профиль доступен по имени в привязках без изменения главного цикла робота

#### Scenario: Профиль с зависимостями от данных
- **WHEN** в реестр регистрируется профиль `triple_screen` с данными-провайдером, переданным в конструктор
- **THEN** профиль доступен по имени в привязках; сигнатура `apply` не меняется

### Requirement: Профиль raw
Профиль фильтрации `raw` ДОЛЖЕН пропускать любое решение без изменений: тип сигнала сохраняется, обогащение полями тренда НЕ ДОЛЖНО выполняться.

#### Scenario: Сигнал против тренда проходит
- **WHEN** профиль `raw`, тренд `down` и сигнал BUY
- **THEN** фильтр возвращает Decision с типом BUY

#### Scenario: Без обогащения
- **WHEN** профиль `raw` применён к любому решению
- **THEN** поля `trend_direction` и `trend_confidence` остаются без изменений

### Requirement: Профиль triple_screen — иерархия таймфреймов
Профиль фильтрации `triple_screen` ДОЛЖЕН определять для рабочего таймфрейма привязки иерархию старших таймфреймов по множителю (по умолчанию 5): `TF_int` — ближайший стандартный таймфрейм лестницы, строго больший `TF_work × множитель`; `TF_htf` — ближайший стандартный таймфрейм лестницы, строго больший `TF_int × множитель`. Стандартная лестница — ключи `TIMEFRAMES` (`1m`, `5m`, `15m`, `30m`, `1h`, `4h`, `1d`, `1w`, `1M`). На рабочем ТФ выполняется базовая стратегия, на `TF_int` — оценка коррекции, на `TF_htf` — направление тренда.

#### Scenario: Иерархия по умолчанию
- **WHEN** рабочий ТФ `5m`, множитель 5
- **THEN** `TF_int = 30m`, `TF_htf = 4h`

#### Scenario: Настраиваемый множитель
- **WHEN** рабочий ТФ `15m`, множитель 3
- **THEN** `TF_int = 1h` (ближайший строго больший 45m), `TF_htf = 4h` (ближайший строго больший 3h)

### Requirement: Профиль triple_screen — направление на старшем ТФ
Экран 1 профиля ДОЛЖЕН оценивать направление тренда по наклону гистограммы MACD(12,26,9) на `TF_htf`: `Hist[t] > Hist[t-1]` — тренд вверх (разрешает входы BUY, блокирует SELL); `Hist[t] < Hist[t-1]` — тренд вниз (разрешает SELL, блокирует BUY). Гистограмма рассчитывается по закрытым свечам `TF_htf`. Если наклон не определён (равенство значений) — направление НЕ считается подтверждённым.

#### Scenario: Восходящий тренд подтверждён
- **WHEN** на `TF_htf` гистограмма MACD растёт (`Hist[t] > Hist[t-1]`)
- **THEN** экран 1 разрешает покупки и отклоняет продажи

#### Scenario: Нисходящий тренд подтверждён
- **WHEN** на `TF_htf` гистограмма MACD падает (`Hist[t] < Hist[t-1]`)
- **THEN** экран 1 разрешает продажи и отклоняет покупки

#### Scenario: Наклон не определён
- **WHEN** `Hist[t] == Hist[t-1]` или данных для сравнения недостаточно
- **THEN** экран 1 не подтверждает ни одно направление

### Requirement: Профиль triple_screen — коррекция на среднем ТФ
Экран 2 профиля ДОЛЖЕН оценивать положение рынка на `TF_int` по осциллятору Stochastic(14,3,3), линия `%K` (объёмы не используются): `%K[t] < 20` — зона перепроданности (условие отката BUY), `%K[t] > 80` — зона перекупленности (условие отката SELL). Пороги зон ДОЛЖНЫ быть настраиваемыми в конфигурации.

#### Scenario: Откат к покупке
- **WHEN** на `TF_int` `%K[t] < 20` и экран 1 подтвердил восходящий тренд
- **THEN** сигнал BUY рабочего ТФ проходит дальше

#### Scenario: Откат к продаже
- **WHEN** на `TF_int` `%K[t] > 80` и экран 1 подтвердил нисходящий тренд
- **THEN** сигнал SELL рабочего ТФ проходит дальше

#### Scenario: Отсутствие подтверждения коррекции
- **WHEN** `%K` находится вне настроенных зон (например, `20 <= %K <= 80`)
- **THEN** экран 2 не подтверждает вход ни в каком направлении

### Requirement: Профиль triple_screen — вход на рабочем ТФ и выравнивание
Экран 3 профиля ДОЛЖЕН пропускать входящий `SignalType` базовой стратегии в `risk_manager` только при одновременном подтверждении экранов 1 и 2 для соответствующего направления; иначе тип сигнала ДОЛЖЕН заменяться на HOLD. Входной HOLD ДОЛЖЕН возвращаться без изменений. Данные для расчёта `TF_htf` и `TF_int` ДОЛЖНЫ содержать только закрытые свечи со временем закрытия, строго не превышающим время закрытия свечи рабочего ТФ текущего тика (заглядывание в будущее запрещено). Окно расчёта старших ТФ ДОЛЖНО покрывать минимум предыдущую торговую сессию: при нехватке закрытых свечей текущей сессии в расчёт ДОЛЖНЫ включаться закрытые бары предыдущей торговой сессии. Если даже с включением предыдущей сессии закрытых свечей недостаточно для корректного расчёта индикаторов, сигнал ДОЛЖЕН отклоняться (HOLD) с предупреждением в `bot_debug.log`.

#### Scenario: Прохождение сигнала
- **WHEN** экраны 1 и 2 подтвердили направление BUY и базовая стратегия выдала BUY
- **THEN** Decision типа BUY передаётся в risk_manager без изменений

#### Scenario: Блокировка сигнала
- **WHEN** хотя бы один из экранов не подтвердил направление сигнала
- **THEN** фильтр возвращает Decision типа HOLD

#### Scenario: HOLD не фильтруется
- **WHEN** базовая стратегия выдала HOLD
- **THEN** фильтр возвращает HOLD без изменений

#### Scenario: Холодный старт — предыдущая торговая сессия
- **WHEN** на старте нового дня в кадре `TF_htf` или `TF_int` недостаточно закрытых свечей текущей сессии для прогрева MACD и Stochastic
- **THEN** в расчёт включаются закрытые бары предыдущей торговой сессии, сигнал проходит по обычным правилам экранов

#### Scenario: Нехватка истории старших ТФ
- **WHEN** в кадре `TF_htf` или `TF_int` недостаточно закрытых свечей для корректного расчёта MACD и Stochastic даже с учётом предыдущей торговой сессии
- **THEN** фильтр отклоняет сигнал (HOLD) и пишет предупреждение в `bot_debug.log`
