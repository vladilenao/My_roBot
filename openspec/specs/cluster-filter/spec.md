# cluster-filter Specification

## Purpose
Кластерный фильтр входа «Кластеры»: робот читает события ClusterSource из Redis Stream `cluster.events` в локальное хранилище и по ним оценивает, вошла бы сделка на кульминации движения или после инициативы крупного участника. Привязка стратегии выбирает режим `off`, `shadow` (вердикт только показывается и пишется в трассу) или `enforce` (вердикт запрещает вход). В историческом прогоне фильтр работает по копии хранилища без заглядывания вперёд.

## Requirements

### Requirement: Чтение событий ClusterSource
Нормативный уровень: MUST.
В live-режиме, если хотя бы у одной привязки `clusters` не равен `off`, робот ДОЛЖЕН читать Redis Stream `cluster.events` своей Consumer Group (по умолчанию `robot-v1`) в фоновом потоке, не блокируя тиковый цикл. Новая группа ДОЛЖНА создаваться с позиции начала потока. После рестарта потребитель ДОЛЖЕН сначала дочитать свои неподтверждённые записи, затем новые. Запись ДОЛЖНА подтверждаться (`XACK`) только после фиксации в локальном хранилище; повтор той же записи НЕ ДОЛЖЕН создавать второй строки (ключ — `event_id`). Сохраняются события `category = signal`, `category = data_quality` и `event_type = signal_revoked`; `signal_confirmed` подтверждается без сохранения. Ошибка Redis НЕ ДОЛЖНА останавливать робота: потребитель повторяет подключение с растущей паузой до 60 секунд. Подключение использует параметры Redis секции `[market_structure]` и пароль из `MARKET_STRUCTURE_REDIS_PASSWORD`; пароль НЕ ДОЛЖЕН попадать в логи и вывод.

#### Scenario: Подтверждение после записи
- **WHEN** потребитель получил пачку из 500 записей и запись в хранилище завершилась ошибкой
- **THEN** ни одна запись пачки не подтверждена в Redis и будет прочитана повторно

#### Scenario: Повтор доставки
- **WHEN** запись с тем же `event_id` пришла второй раз после рестарта
- **THEN** в хранилище остаётся одна строка, запись подтверждается

#### Scenario: Redis недоступен
- **WHEN** Redis не отвечает 3 минуты
- **THEN** робот продолжает торговый цикл, потребитель повторяет подключение не реже раза в 60 секунд, вердикты в это время — `unknown` с причиной `consumer_lag`

#### Scenario: Фильтр выключен везде
- **WHEN** у всех привязок `clusters = "off"`
- **THEN** потребитель не запускается и к Redis не подключается

### Requirement: Хранилище кластерных событий
Нормативный уровень: MUST.
События ДОЛЖНЫ храниться в отдельной SQLite-базе `cluster-events.sqlite3` в каталоге данных робота, в режиме WAL, с полями записи потока как есть и выделенными `event_id`, `category`, `event_type`, `secid`, `ticker` источника, `direction`, `signal_id`, `timestamp`, `published_at`, `received_at`. Торговое состояние в этой базе НЕ ДОЛЖНО храниться; `trades.sqlite3` остаётся единственным источником истины по сделкам.

#### Scenario: Состав строки
- **WHEN** сохранено событие `volume_spike` по `BRX6`
- **THEN** строка содержит его `event_id`, `secid = BRX6`, `direction`, `published_at` и исходные поля записи, включая `payload`

### Requirement: Исторический режим кластерного фильтра
Нормативный уровень: MUST.
В историческом режиме потребитель НЕ ДОЛЖЕН запускаться, а боевое хранилище НЕ ДОЛЖНО меняться. Прогон ДОЛЖЕН работать со своим хранилищем в каталоге прогона: копией боевого (если оно есть), догруженной перед прогоном событиями потока без Consumer Group и без подтверждения; если Redis недоступен, прогон ДОЛЖЕН идти по скопированным событиям. Вердикт в истории ДОЛЖЕН считаться тем же алгоритмом, что в live, без проверки отставания чтения.

#### Scenario: История без Redis
- **WHEN** исторический прогон за 15.10 запущен при недоступном Redis, а события за 15.10 уже есть в боевом хранилище
- **THEN** вердикты считаются по их копии так же, как они были бы посчитаны в live

#### Scenario: Боевые файлы не меняются
- **WHEN** идёт исторический прогон с включёнными «Кластерами»
- **THEN** файлы каталога состояния боевого робота остаются байт в байт прежними

#### Scenario: Период без событий
- **WHEN** исторический прогон идёт за период раньше первого сохранённого события
- **THEN** вердикты — `unknown` с причиной `no_coverage`, вход допускается как без фильтра

### Requirement: Без заглядывания вперёд
Нормативный уровень: MUST.
Вердикт для сигнала с временем закрытия бара `T` ДОЛЖЕН использовать только события с `published_at ≤ T`, только отзывы с `published_at ≤ T` и только 1m свечи, закрывшиеся не позже `T`.

#### Scenario: Событие после закрытия бара
- **WHEN** бар сигнала BUY закрылся в 12:45:00 UTC, а крупная продажа опубликована в 12:48:54 UTC
- **THEN** эта продажа не входит в вердикт этого сигнала

#### Scenario: Отзыв после бара
- **WHEN** событие опубликовано до `T`, а его `signal_revoked` — после `T`
- **THEN** событие учитывается

### Requirement: Сопоставление инструмента
Нормативный уровень: MUST.
Событие ДОЛЖНО относиться к инструменту робота, если его `secid` совпадает с биржевым тикером инструмента. Если по фьючерсу событий нет, а за последние сутки есть события того же семейства с другим `secid`, вердикт ДОЛЖЕН быть `unknown` с причиной `contract_mismatch` и указанием контракта коллектора; иначе — `unknown` с причиной `no_coverage`.

#### Scenario: Коллектор ведёт другой контракт
- **WHEN** робот торгует NGX6, а события семейства NG приходят по NGV6
- **THEN** вердикт `unknown`, причина `contract_mismatch`, текст «нет данных — коллектор ведёт NG-10.26, робот торгует NG-11.26»

### Requirement: Вердикт кластерного фильтра
Нормативный уровень: MUST.
Для сигнала BUY или SELL с временем закрытия бара `T` вердикт ДОЛЖЕН считаться по алгоритму `clusters-v1`:

- `unknown`, если: в live с последнего успешного чтения Redis прошло больше `max_consumer_lag_sec` (`consumer_lag`); инструмент не сопоставлен (`no_coverage`, `contract_mismatch`); последнее событие качества данных по инструменту до `T` — `data_degraded` (`data_degraded`); 1m истории меньше `sigma_days` торговых дней (`no_sigma_history`); нет 1m свечей к моменту `T` или за 15 минут до него (`candles_missing`);
- σ15 — медиана `|ln(close_t / close_{t−15 мин})|` по 1m свечам за `sigma_days` торговых дней до дня `T`, внутри дня;
- ход до входа — `s · ln(close_at(T) / close_at(T − 15 мин)) / σ15`, где `s` = +1 для BUY и −1 для SELL, `close_at(t)` — закрытие последней 1m свечи, закрывшейся не позже `t`;
- положение в диапазоне — `(close_at(T) − L) / (H − L)` по максимуму и минимуму 1m свечей, открытых в [T − 120 мин, T − 1 мин], для SELL — единица минус это значение;
- учитываются события `category = signal` инструмента с `published_at` в (T − `initiative_window_min`, T] без отзыва до `T`, кроме `direction = neutral`; свой ход события — тот же расчёт хода от его `published_at` со знаком его `direction`;
- метка события: `absorption` с `payload.absorbed_side`, равным стороне входа, — `absorption_against`; иначе свой ход ≥ `pre_move_veto_sigma` — `climax`; иначе свой ход < `initiative_max_sigma` — `initiative`;
- `veto` — ход до входа ≥ `pre_move_veto_sigma` и за последние `climax_window_min` есть `climax` того же направления, `absorption_against` или `initiative` встречного направления; `veto_strong` — то же при положении в диапазоне ≥ `extreme_position`;
- иначе `confirm` — есть `initiative` того же направления от `large_aggressor` или `stacked_imbalance`;
- иначе `neutral`.

#### Scenario: Запрет на кульминации (BR-11.26, 15.10)
- **WHEN** SELL с `T` = 13:50 UTC, σ15 = 12,82 б.п., `close_at(T)` = 104,63, `close_at(T − 15 мин)` = 104,92, диапазон 104,06–105,20, а в 13:40:00 опубликован `volume_spike` `short` со своим ходом +2,45σ
- **THEN** ход до входа +2,16σ, положение 0,50, вердикт `veto` (не `veto_strong`), причина `climax`

#### Scenario: Сильный запрет у края диапазона
- **WHEN** BUY, ход до входа +1,9σ, положение в диапазоне 0,96, за 20 минут до `T` — `stacked_imbalance` `long` со своим ходом +3,0σ
- **THEN** вердикт `veto_strong`

#### Scenario: Подтверждение инициативой
- **WHEN** BUY, ход до входа +3,1σ, за 25 и 12 минут до `T` — `large_aggressor` `long` со своим ходом −2,3σ и −1,5σ, кульминаций и поглощений против входа нет
- **THEN** вердикт `confirm`, причина `initiative`

#### Scenario: Ход меньше порога
- **WHEN** BUY, ход до входа +1,2σ, за 15 минут до `T` — встречная `stacked_imbalance` со своим ходом −0,75σ
- **THEN** вердикт `neutral`: запрет требует хода до входа не меньше 1,5σ

#### Scenario: Данные инструмента деградировали
- **WHEN** последнее событие качества по инструменту до `T` — `data_degraded`
- **THEN** вердикт `unknown` с причиной `data_degraded`

### Requirement: Режимы привязки
Нормативный уровень: MUST.
Вердикт ДОЛЖЕН считаться для каждого кандидата нового входа привязки с `clusters = "shadow"` или `"enforce"` в допуске менеджера сделок до фильтра профиля привязки — одинаково в тиковом и live-цикле. При `off` вердикт НЕ ДОЛЖЕН считаться. При `shadow` вердикт НЕ ДОЛЖЕН менять допуск. При `enforce` вердикт не ниже `enforce_level` ДОЛЖЕН давать штатный недопуск с кодом `cluster-climax` после фильтра профиля; при отказе фильтра профиля недопуск остаётся `filter-rejected`. Вердикт `unknown` НИКОГДА НЕ ДОЛЖЕН давать недопуск. Сигналы по открытой сделке связки и доборы вердикт не получают.

#### Scenario: Теневой запрет
- **WHEN** у привязки `clusters = "shadow"` и вердикт `veto`
- **THEN** допуск идёт дальше как без фильтра, вердикт виден в консоли и записан трассой

#### Scenario: Боевой запрет
- **WHEN** у привязки `clusters = "enforce"`, `enforce_level = "veto"`, фильтр профиля пропустил сигнал и вердикт `veto`
- **THEN** допуск возвращает недопуск `cluster-climax`, план и заявка не создаются

#### Scenario: Боевой режим только для сильного запрета
- **WHEN** `enforce_level = "veto_strong"` и вердикт `veto`
- **THEN** недопуска нет

#### Scenario: Нет данных в боевом режиме
- **WHEN** у привязки `clusters = "enforce"` и вердикт `unknown`
- **THEN** допуск идёт дальше как без фильтра

#### Scenario: Отказ фильтра тренда
- **WHEN** у привязки `clusters = "shadow"`, `basic_levels` отклонил BUY против тренда
- **THEN** вердикт всё равно посчитан и записан, недопуск — `filter-rejected`

### Requirement: Трасса кластерного вердикта
Нормативный уровень: MUST.
Каждый вердикт ДОЛЖЕН записываться трассой расчёта `filter.cluster` версии `clusters-v1` со ссылками на привязку и сигнал. Входы трассы ДОЛЖНЫ позволять воспроизвести вердикт: инструмент, таймфрейм, сторона, `T`, режим, σ15 и число дней, ход до входа, положение в диапазоне, использованные закрытия с временем свечей, максимум и минимум диапазона, пороги и каждое учтённое событие с `event_id`, типом, направлением, отношением ко входу, `published_at`, своим ходом и меткой. Выход — вердикт, причина и текст для пользователя. Исход `REJECTED` — только когда вердикт дал недопуск.

#### Scenario: Трасса теневого запрета
- **WHEN** в `shadow` посчитан `veto`
- **THEN** записана трасса `filter.cluster` с исходом `ACCEPTED`, выходом `veto` и событием-уликой во входах
