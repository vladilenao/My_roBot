# Оркестрация

## Purpose

Запускает главный цикл бота, который непрерывно для каждого выбранного инструмента: загружает рыночные данные, вычисляет индикаторы, агрегирует сигналы, принимает решения и отправляет уведомления с фиксированным интервалом. Является центральным координатором всех модулей.

## Requirements

### Requirement: Оркестратор-сценарий
Система ДОЛЖНА предоставлять класс-оркестратор `TradingBot`, в котором каждый этап сценария (запуск, цикл, обновление данных, анализ, решение, уведомление) реализован отдельным методом, чтобы файл читался как пошаговый сценарий. Монолитная функция `run_bot` НЕ ДОЛЖНА оставаться единственным носителем логики.

#### Scenario: Читаемый сценарий
- **WHEN** разработчик читает файл оркестратора
- **THEN** каждому пункту словесного сценария соответствует отдельный вызываемый метод

### Requirement: Точка входа
Система ДОЛЖНА предоставлять точку входа `run.py`, которая собирает зависимости (инструменты, нотификатор, кэш данных, планировщик времени, порт исполнения) и запускает оркестратор `TradingBot.run()`. `run.py` ДОЛЖНА вызывать `select_instruments()` и передавать выбранные инструменты оркестратору.

#### Scenario: Запуск через run.py
- **WHEN** `python run.py` выполняется
- **THEN** вызывается `select_instruments()`, собираются зависимости и запускается `TradingBot(...).run()`

### Requirement: Бесконечный цикл бота
Система ДОЛЖНА выполнять бесконечный цикл в составе оркестратора. Перед входом в цикл ДОЛЖНЫ валидироваться оба словаря привязок (`SHARE_STRATEGIES` и `FUTURE_STRATEGIES`) против реестра стратегий; при наличии неизвестных имён хотя бы в одном словаре запуск ДОЛЖЕН завершаться ошибкой до первой итерации. Каждое имя стратегии в словарях привязок ДОЛЖНО также иметь запись в карте стратегий оркестратора (быть построимым); при отсутствии хотя бы одного такого имени запуск ДОЛЖЕН завершаться ошибкой до первой итерации. Набор стратегий для каждого инструмента ДОЛЖЕН определяться диспетчеризацией по типу инструмента:
- для инструмента типа `future` — базовый актив выводится из тикера контракта (первые два символа, приведённые к верхнему регистру) и ищется в `FUTURE_STRATEGIES`;
- для остальных инструментов — точный тикер ищется в `SHARE_STRATEGIES`.

Инструмент без непустой привязки в своём словаре ДОЛЖЕН пропускаться с записью в лог.

#### Scenario: Запуск с инструментами
- **WHEN** оркестратор запускается с заданным списком инструментов
- **THEN** начинается бесконечный цикл обработки инструментов и их назначенных стратегий

#### Scenario: Стратегии фьючерса определяются базовым активом
- **WHEN** обрабатывается инструмент типа `future` с тикером `NGU6`, а `FUTURE_STRATEGIES` содержит запись `"NG"`
- **THEN** выполняются стратегии из записи `"NG"`, независимо от суффикса контракта

#### Scenario: База определяется без учёта регистра тикера
- **WHEN** тикер фьючерса содержит символы в любом регистре (например `SiZ6`)
- **THEN** база приводится к верхнему регистру и находится в `FUTURE_STRATEGIES`

#### Scenario: Стратегии акции определяются точным тикером
- **WHEN** обрабатывается инструмент типа `share`
- **THEN** используется запись `SHARE_STRATEGIES` с точным совпадением тикера; записи `FUTURE_STRATEGIES` не применяются

#### Scenario: Запуск без аргументов (fallback)
- **WHEN** оркестратор запускается без явного списка инструментов
- **THEN** используется конфигурация по умолчанию: один инструмент `(TICKER, TICKER, INSTRUMENT_TYPE)` со стратегиями по правилу диспетчеризации

#### Scenario: Инструмент без привязки пропускается
- **WHEN** словарь, соответствующий типу инструмента, не содержит для него непустого списка стратегий
- **THEN** запрос данных для него не выполняется, в лог пишется запись о пропуске

#### Scenario: Fail-fast при невалидных привязках
- **WHEN** оркестратор запускается, а хотя бы один из словарей содержит имя стратегии, отсутствующее в реестре стратегий
- **THEN** выбрасывается ошибка до входа в цикл; ни один инструмент не обрабатывается, запросы данных не выполняются

#### Scenario: Fail-fast при стратегии, заявленной в привязке, но не построимой
- **WHEN** оркестратор запускается, а хотя бы одному имени стратегии из привязок (`SHARE_STRATEGIES` или `FUTURE_STRATEGIES`) нет записи в карте стратегий оркестратора
- **THEN** выбрасывается ошибка до входа в цикл; ни один инструмент не обрабатывается, запросы данных не выполняются

### Requirement: Поддержка двух форматов инструментов
Система ДОЛЖНА принимать как 3-кортежи `(display_name, ticker, instrument_type)`, так и 2-кортежи `(ticker, instrument_type)`, нормализуя их в единую модель инструмента с полями «label», «ticker» и «instrument_type».

#### Scenario: 3-кортеж (текущий формат)
- **WHEN** элемент кортежа содержит 3 значения
- **THEN** `label = display_name`, `ticker` и `instrument_type` извлекаются отдельно

#### Scenario: 2-кортеж (legacy формат)
- **WHEN** элемент кортежа содержит 2 значения
- **THEN** `ticker` и `instrument_type` извлекаются напрямую, `label = f"{ticker} {instrument_type}"`

### Requirement: Обработка пустых данных
- Если DataFrame пуст, система ДОЛЖНА вывести сообщение и перейти к следующему инструменту.

#### Scenario: Пустые данные
- **WHEN** `load_candles` вернул пустой DataFrame
- **THEN** выводится "Нет данных" и итерация пропускается для данного инструмента

### Requirement: Выравнивание итерации по закрытию свечи
Ритм работы системы ДОЛЖЕН синхронизироваться с границами закрытия свечей всех активных таймфреймов привязок: каждая штатная (не первая) итерация начинается на ближайшей границе закрытия свечи среди активных ТФ, а не по фиксированной паузе. Обработка индикаторов и принятие решений ДОЛЖНЫ выполняться по завершённым (закрытым) свечам соответствующего ТФ.

Первый тик при запуске ДОЛЖЕН выполняться сразу, без ожидания ближайшей календарной границы: анализируется последняя уже закрытая свеча каждого активного ТФ, и по ней немедленно доставляется решение. Если ожидаемый закрытый бар уже присутствует в загруженных данных, повторная дозагрузка данных с API НЕ ДОЛЖНА выполняться: готовность проверяется по текущему кэшу. Если при запуске ближайшая граница закрытия только что пройдена и свежий закрытый бар ещё не опубликован, первый тик ДОЛЖЕН повторно дозагружать данные с малыми паузами, пока не будет подтверждено появление свежего закрытого бара; ожидание ДОЛЖНО быть ограничено тем же таймаутом, что и штатное удержание тика, после чего первый тик обрабатывается с имеющимися данными без бесконечной блокировки.

После достижения календарной границы закрытия свечи таймфрейма система ДОЛЖНА удерживать обработку этого ТФ и повторно дозагружать данные с малыми паузами, пока не будет подтверждено появление свежего закрытого бара. Ожидание ДОЛЖНО быть ограничено таймаутом: если свежий бар не появился за отведённое время, тик обрабатывается с имеющимися данными, без бесконечной блокировки.

#### Scenario: Итерация по границе
- **WHEN** на штатной итерации (после первого тика текущего запуска) текущая свеча таймфрейма ещё не закрыта
- **THEN** обработка привязок этого ТФ не выполняется до наступления границы закрытия свечи

#### Scenario: Первый тик при запуске выполняет последнюю закрытую свечу
- **WHEN** бот запускается в середине периода таймфрейма (например, 09:58 при 1h) и последняя закрытая свеча уже доступна
- **THEN** первый тик выполняется немедленно, решение доставляется по последней закрытой свече (8:00–9:00), без ожидания следующей границы закрытия (10:00)

#### Scenario: Первый тик без повторной дозагрузки
- **WHEN** при запуске ожидаемый закрытый бар уже присутствует в загруженных данных
- **THEN** первый тик обрабатывается немедленно, повторный запрос к API не выполняется

#### Scenario: Решение по готовой свече
- **WHEN** стратегия принимает решение
- **THEN** в расчёте участвуют только закрытые свечи таймфрейма привязки; незакрытая текущая свеча не влияет на решение

#### Scenario: Первый тик на границе ожидает свежий бар
- **WHEN** запуск происходит сразу после календарной границы, а свежий закрытый бар ещё не появился в данных
- **THEN** первый тик не обрабатывается немедленно; система повторно дозагружает данные с малыми паузами, пока свежий закрытый бар не появится

#### Scenario: Таймаут первого тика на границе
- **WHEN** свежий закрытый бар не появился в течение ограниченного таймаута ожидания первого тика
- **THEN** первый тик обрабатывается с имеющимися данными, не блокируясь бесконечно

#### Scenario: Тик удерживается до появления свежего бара
- **WHEN** календарная граница закрытия свечи достигнута на штатной итерации, но свежий закрытый бар ещё не появился в данных
- **THEN** тик не обрабатывается немедленно; система повторно дозагружает данные с малыми паузами, пока свежий закрытый бар текущей закрытой минуты не появится

#### Scenario: Обработка по таймауту
- **WHEN** свежий закрытый бар не появился в течение ограниченного таймаута ожидания на штатной итерации
- **THEN** обработка тика выполняется с имеющимися данными, не блокируясь бесконечно

#### Scenario: На одном тике работают только ТФ с закрывшейся свечой
- **WHEN** активны привязки `15m` и `1h`, тик на границе `10:45 UTC` (закрылась только 15m-свеча)
- **THEN** обрабатываются только привязки с таймфреймом `15m`; привязки `1h` ждут своей границы

### Requirement: Инкрементальный пересчёт данных
Система ДОЛЖНА переиспользовать актуальные закэшированные данные и дозагружать только новые закрытые бары, пересчитывая индикаторы один раз на тик, а не пересобирая всю историю на каждой итерации.

#### Scenario: Дозагрузка новых баров
- **WHEN** появляется новый закрытый бар
- **THEN** выполняется дозагрузка новых баров поверх кэша и пересчёт индикаторов

#### Scenario: Данные не изменились
- **WHEN** новый закрытый бар не появился
- **THEN** индикаторы не пересчитываются по всей истории

### Requirement: Формат уведомления
Сообщение ДОЛЖНО формироваться форматтером, внедрённым в нотификатор (`DecisionFormatter`), из решения стратегии и контекста задачи: инструмент, таймфрейм привязки, имя стратегии, профиль фильтрации. Оркестратор НЕ ДОЛЖЕН сам формировать тексты.

#### Scenario: Формат сообщения
- **WHEN** итерация завершается успешно с решением BUY по привязке с таймфреймом `15m`, стратегией `macd_rsi_stoch` и профилем `raw`
- **THEN** доставленное сообщение содержит `● <инструмент> (15m) HH:MM | macd_rsi_stoch [raw] ➜ 🟢 ПОКУПКА (BUY) — Цена: X`

### Requirement: Корректное завершение по Ctrl+C
Система ДОЛЖНА перехватывать `KeyboardInterrupt` и выводить «Бот остановлен».

#### Scenario: Остановка пользователем
- **WHEN** пользователь нажимает Ctrl+C
- **THEN** выводится «Бот остановлен» и цикл завершается

### Requirement: Устойчивость к ошибкам и диагностика
Система ДОЛЖНА перехватывать исключения на уровне отдельной стратегии и всего цикла. Ошибка стратегии НЕ ДОЛЖНА блокировать другие стратегии. Ошибка тика/цикла ДОЛЖНА фиксироваться в логе и уведомление о сбое ДОЛЖНО доставляться трейдеру через нотификатор (не только в консоль), после чего цикл продолжается. Fallback-пауза после сбоя ДОЛЖНА быть не длиннее периода наименьшего активного ТФ (ограничение фиксируется в логе), чтобы не пропускать частые границы.

#### Scenario: Отказ одной стратегии
- **WHEN** `compute()` или `decide()` одной стратегии выбрасывает исключение
- **THEN** остальные стратегии этого инструмента обрабатываются штатно, отказ зафиксирован в логе

#### Scenario: Ошибка тика уведомляет трейдера
- **WHEN** возникает необработанное исключение в цикле
- **THEN** ошибка логируется, трейдеру доставляется уведомление о сбое через нотификатор, применяется fallback-пауза (не длиннее наименьшего активного ТФ) и цикл продолжается

### Requirement: Периодическое сердцебиение
Система ДОЛЖНА периодически доставлять трейдеру «сердцебиение» — диагностическое сообщение о работоспособности робота. Сердцебиение отправляется с заданным интервалом (в тиках), независимо от наличия торговых сигналов, и содержит счётчик выполненных тиков и количество ошибок с момента предыдущего сердцебиения. Сердцебиение НЕ ДОЛЖНО подменять алерт об ошибке тика.

#### Scenario: Сердцебиение по расписанию
- **WHEN** выполняется заданное число тиков с предыдущего сердцебиения
- **THEN** трейдеру через нотификатор доставляется диагностическое сообщение о работоспособности

#### Scenario: Сердцебиение не отправляется на каждом тике
- **WHEN** интервал сердцебиения ещё не достигнут
- **THEN** сердцебиение не отправляется, обычная обработка тика продолжается

#### Scenario: Считается число ошибок за период
- **WHEN** сердцебиение отправляется после периода, в котором были ошибки тика
- **THEN** сообщение содержит количество ошибок за этот период

### Requirement: Независимые фазы сопровождения и новых возможностей
Нормативный уровень: MUST.
На обновлении система ДОЛЖНА сначала принять исполнения и обновить фактическое состояние, обработать действующую защиту и сопровождение, затем вычислить новые сигналы, направить противоположные события своим сделкам, отфильтровать увеличения и ранжировать кандидатов портфеля. Ошибка или HOLD входной стратегии НЕ ДОЛЖНЫ отключать сопровождение открытой сделки. Контекст общих пар инструмент/ТФ переиспользуется; разные ТФ не смешиваются.

#### Scenario: Нет нового входа
- **WHEN** стратегия вернула HOLD либо упала, но открытая сделка достигла цели
- **THEN** частичное закрытие обрабатывается независимо от результата стратегии

#### Scenario: Сделка удалённой связки
- **WHEN** связку убрали из конфигурации, а позиция ещё открыта
- **THEN** инструмент и ТФ сохранённой сделки остаются в подписках сопровождения до её завершения

#### Scenario: Повторный бар
- **WHEN** таймаут загрузки вернул уже обработанный бар
- **THEN** вход, добор и сигнальный выход по этому бару не дублируются; новые события исполнения принимаются

### Requirement: Честная частота защитной симуляции
Нормативный уровень: MUST.
В торговой симуляции система ДОЛЖНА обрабатывать закрытые базовые бары защиты отдельно от ТФ стратегии; базовый ТФ — 1m. Для каждой позиции интервал обрабатывается один раз и только после активации её заявок. Индикаторное сопровождение выполняется на сохранённом ТФ сделки. Отсутствие данных не изображается как успешная проверка стопа; отставание защиты логируется.

#### Scenario: Позиция часовой стратегии
- **WHEN** новая 1m-свеча коснулась активного стопа, а часовой бар ещё не закрылся
- **THEN** симулятор обрабатывает стоп, не ожидая нового часового сигнала
