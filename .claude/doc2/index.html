Робот на реальном счёте

Контур «Счёт» подключается к готовому ядру как ещё один вид торгового контура, рядом с эмуляцией и историей. Он торгует только переданными ему привязками на брокерском счёте робота, а правду о заявках, позициях и деньгах говорит брокер.

Сначала документ 1Здесь считается готовым всё из «Ядра и контуров робота»: постоянное ядро, API управления, контуры отдельными процессами, команды через желаемое состояние с поколениями, свечи из ленты изменений, свой канал Telegram у контура, состав на ходу, подъём после рестарта.
Сначала песочница, потом счётТорговля на брокере строится один раз, а запускается двумя видами контура из одного кода. Контур «Песочница» торгует в песочнице Т-Инвест (настоящий API и котировки, виртуальные деньги), контур «Счёт» — на брокерском счёте робота. Этапы С1–С7 доводят всё до конца в песочнице, этапы Р1–Р2 поднимают рядом контур «Счёт». Песочница после этого остаётся стендом. Каждый этап — отдельный change в OpenSpec с проверкой руками.
Что нового в версии 14С1–С3 сделаны: С3 в архиве с 06.11, дефекты после его проверки закрывает fix-sandbox-restart-safety. На С3 вошли выходы лимитом и команды остановки no_entries и close_all, поэтому С5 растворён в С3 и С4. Капитал песочницы — рубли на счёте. Разделы «Стоп и цели» и «Разведка» сверены с кодом С3. Новый раздел — план С4 со схемой; три вопроса к нему решены 08.11.

Ярус 1 · как включается

Настройка контуров «Песочница» и «Счёт»

[contours.sandbox]              # с С2, заявки с С3
telegram_bot_env = "TELEGRAM_ACCOUNT_BOT_TOKEN"
telegram_channel_env = "TELEGRAM_SANDBOX_CHANNEL_ID"
reconcile_every_min = 1
orders = true
exit_offset_steps = 5     # запас лимита выхода
exit_requote_secs = 15    # до перевыставления
exit_requote_attempts = 3 # потом рынок
# будут: stop_place_secs (С4),
# max_daily_loss_rub, max_rejects_in_row (С6)
# состава здесь нет — только командами API

[contours.account]              # Р1, тот же код
orders = false       # true с Р2
telegram_bot_env = "TELEGRAM_ACCOUNT_BOT_TOKEN"
telegram_channel_env = "TELEGRAM_ACCOUNT_CHANNEL_ID"
max_daily_loss_rub = 3000
max_rejects_in_row = 3
reconcile_every_min = 5

# .env, новые переменные
# TINKOFF_SANDBOX_TOKEN        токен песочницы (С1)
# TELEGRAM_ACCOUNT_BOT_TOKEN   бот «Счёт», общий
# TELEGRAM_SANDBOX_CHANNEL_ID  канал «Песочница»
# TELEGRAM_ACCOUNT_CHANNEL_ID  канал «Счёт»
# TINKOFF_TRADE_TOKEN          токен торговли (Р1)
# TINKOFF_ACCOUNT_ID           номер счёта робота (Р1)
  • Брокер задаёт вид контура, а не параметр. Ядро читает котировки старым TINKOFF_TOKEN. Контур «Песочница» ходит в sandbox-invest-public-api с TINKOFF_SANDBOX_TOKEN и сам находит или открывает счёт песочницы. Контур «Счёт» ходит в боевой API с TINKOFF_TRADE_TOKEN по счёту TINKOFF_ACCOUNT_ID; эти две переменные получает только его процесс. Переключить брокера правкой настройки или командой API нельзя.
  • Свой состав у каждого. «Песочница» и «Счёт» торгуют только перечисленными привязками — id из [strategies.*], то есть парой «инструмент + стратегия». Состав задаётся только командами API и хранится в core.sqlite3, как у эмуляции; в robot.toml его нет. Составы эмуляции, песочницы и счёта друг на друга не влияют. Привязку можно держать в нескольких контурах сразу: тогда они служат друг другу тенью для сравнения.
  • Секреты. Все новые переменные попадают в secrets логгера, номер счёта в логах маскируется.
  • Отдельный бот и два канала, «Песочница» и «Счёт»: завести бота, создать каналы, добавить бота администратором с правом публикации, вписать токен бота и id каналов в .env. Свой бот — это свои лимиты Telegram: сигналы эмуляции не задерживают сообщения о деньгах.

Эмуляция · состав по инструментам

  • 22 инструмента, у каждого все его стратегии из [strategies.*]
  • сигналы в канал «Сигналы», виртуальный initial_deposit
  • меняется командами /api/v1/emulation/instruments

Счёт · состав по привязкам

  • например, 5 инструментов и 1 стратегия: 5 id вида share-sber-macd-4h-triple
  • сигналы только этих привязок, в канал «Счёт», капитал со счёта
  • привязки переводятся на счёт по одной командой /api/v1/account/bindings, сначала пройдя песочницу
  • у контура «Песочница» такой же свой состав: /api/v1/sandbox/bindings
С2

«Песочница», только чтение. Контур читает виртуальный счёт: капитал, позиции, заявки, стоп-заявки, операции. Сверщик работает, ни одной заявки.ловит расхождения учёта до первой заявки · денег нет

С3–С7

«Песочница», заявки. Настоящий API и котировки, виртуальный счёт. Песочница исполняет и обычные заявки, и стоп-заявки. Здесь же ловятся ошибки построения заявки: лоты, шаг цены, коридор, ГО.заявка уходит в песочницу · денег нет

Р1

«Счёт», только чтение. Второй вид контура из того же кода, orders = false. «Песочница» продолжает работать рядом.ни одной заявки · сверка на настоящем счёте

Р2

«Счёт», заявки. orders = true. Исход решает брокер.заявка уходит на биржу · деньги настоящие

Что контур проверит до первого тика

  1. Отпечаток счёта в базе контура совпадает с текущим: вид брокера и хеш номера счёта. «Песочница» дополнительно находит или открывает свой счёт, «Счёт» проходит допуск из раздела «Переход». Иначе контур не стартует, без тихого отката.
  2. Бот и канал контура заданы. Сделки без уведомлений недопустимы.
  3. Капитал прочитан со счёта.
  4. Сверка счёта с журналом прошла. При расхождении контур стартует с замороженными входами.

Ярус 1 · управление

Команды контура «Счёт»

Ресурс /api/v1/account устроен как /api/v1/emulation после П8: то же желаемое состояние, те же коды ответов, те же ETag и номер ревизии. Отличие одно: всё, что может открыть или закрыть позицию, требует "confirm": "account". У контура «Песочница» тот же набор команд под /api/v1/sandbox, confirm там не нужен.

ЗапросЧто происходит
GET /api/v1/accountСостояние контура: брокер (песочница или счёт), режим чтения или заявок, капитал, состав, открытые позиции, последняя сверка.
PUT /api/v1/account/target
{"mode": "on", "bindings": [...], "confirm": "account"}		Запуск контура со стартовым составом привязок, он может быть пустым. Без confirm запрос отклоняется. Контур «Счёт» один: если он уже работает, состав меняется командами ниже.
POST /api/v1/account/bindings
{"bindings": [...], "confirm": "account"}		Перевести привязку на счёт. Она начинает торговать на ближайшей границе тика и делит капитал счёта с остальными. Неизвестный id отклоняется целиком, как неизвестный инструмент у эмуляции.
POST /api/v1/account/bindings/remove
{"bindings": [...], "mode": "no_entries"}		Снять привязку со счёта: неисполненные входы снимаются у брокера, открытые позиции ведутся до закрытия со стопом и целями у брокера.
POST /api/v1/account/bindings/remove
{"bindings": [...], "mode": "close_all", "confirm": "account"}		Снять привязку и закрыть её позиции по правилам «закрыть всё».
PUT /api/v1/account/target
{"mode": "no_entries"}		Остановить весь контур, больше не входить. Неисполненные лимитные входы снимаются у брокера. Открытые позиции сопровождаются, стоп и цели остаются у брокера. После последнего выхода контур завершается сам.
PUT /api/v1/account/target
{"mode": "close_all", "confirm": "account"}		Остановить весь контур и закрыть всё. Снять входы, выйти из каждой позиции, после выхода снять её стоп и цели. Пока позиция не закрыта, стоп у брокера остаётся.
GET /api/v1/account/bindingsСостав счёта и все привязки из конфига с отметкой, где каждая торгует: на счёте, в эмуляции, там и там. По этому списку удобно выбирать, что переводить дальше.
GET /api/v1/account/reconcileПоследний отчёт сверщика: что совпало, что расходится, какие инструменты заморожены.

Ручные действия в песочнице — пополнить счёт, купить или продать лоты «как человек», чтобы проверить сверщик, — делает не API робота, а команда песочницы из С1. В приложении Т-Инвест песочницы не видно.

Ярус 1 · деньги

Капитал контура берётся со счёта

Эмуляция остаётся на initial_deposit. В контуре «Счёт» капиталом для риска служат деньги на счёте робота, и учитываются только его сделки. Сигнал публикуется в канал до допуска, поэтому его видно, даже если денег на сделку не хватило.

  • Откуда число. Решено на С3: капитал песочницы — рубли на счёте из GetPositions. Песочница при покупке фьючерса списывает полную цену контракта, поэтому liquid_portfolio (1 023 916 ₽ при 1 000 000 ₽) больше денег на счёте; он показывается рядом в статусе и сообщении о старте. Для настоящего счёта поле выбираем заново на Р1 по цифре в приложении.
  • Хватает ли ГО. GetMaxLots для фьючерса бесполезен: без плеча 0 лотов, с плечом 1,28 млн. Допуск считает сам контур: ГО на контракт из GetFuturesMargin (NG: 6 228 ₽ на покупку) умножить на лоты и сравнить со свободными деньгами.
  • Когда обновляется. До первого тика, по стриму портфеля, после каждого своего исполнения и после клиринга.
  • Один снимок на тик. Кандидаты тика допускаются пакетом по приоритету и видят один и тот же капитал.
  • Счёт недоступен. Новые входы останавливаются, в канал уходит предупреждение. Стопы и цели уже стоят у брокера.
  • Пополнение или вывод. Новый размер сделок сразу, без правки конфига.

Деньги в журнале и на счёте до копейки сходиться не будут: брокер дважды в день начисляет вариационную маржу, а робот считает PnL по сделкам. Поэтому капитал всегда берётся у брокера, а PnL отдельной сделки считает журнал.

Ярус 2 · перезапуск

Рестарт: сначала счёт, потом всё остальное

Ядро поднимает контур «Счёт» первым, раньше песочницы и эмуляции. Пока робот был выключен, у брокера могли сработать стопы и цели, поэтому до первого тика контур читает счёт и приводит журнал в соответствие.

Если на шаге 5 сверщик находит расхождение, которое нельзя провести автоматически, контур поднимается с замороженными входами по этому инструменту, а в канал уходит тревога. Защита и выходы при этом работают.

Ярус 2 · внутри контура

Путь команды в контуре «Счёт»

Белые блоки уже есть в коде и одинаковы у эмуляции и счёта. При сборке контура «Счёт» на место симулятора встаёт адаптер счёта, а исполнения приходят из стрима в тот же consume.

Outbox — таблица исходящих команд в trades.sqlite3 контура. План и строка «отправить заявку» пишутся одной транзакцией, поэтому при падении команда не потеряется, а статус SENT не даст отправить её второй раз.

Шина получает событие в самом конце: consume сначала записывает результат в SQLite и только потом публикует событие для канала.

Ярус 2 · одна заявка

Жизнь заявки на счёте

Сегодня ExecutionStatus знает ACK, PARTIAL, FILL, REJECT и CANCEL. Для счёта нужны ещё три промежуточных состояния, их хранит outbox: «отправлена», «неизвестно» и «снимается». Главное из них «неизвестно»: ответ брокера потерялся, и повторять вслепую нельзя.

Как сделано на С3. Промежуточные состояния хранит не outbox, а журнал заявок брокера в broker.sqlite3 контура: outbox доставляет команду адаптеру, журнал ведёт жизнь заявки у брокера. У каждого факта один владелец, TradeManager и эмуляция не менялись. Ключ заявки — uuid5(command_id).

Ключ идемпотентности заявки в API (order_id в PostOrder и PostStopOrder) равен нашему command_id. Поэтому после обрыва робот спрашивает брокера по ключу (GetOrderState с типом номера ORDER_ID_TYPE_REQUEST) и только потом решает. Разведка С1: повтор того же ключа второй заявки не создаёт, но брокер отвечает ошибкой 30057, а не прежней заявкой, поэтому «повтор с тем же ключом» на схеме — только для заявки, которую поиск по ключу не нашёл. Стрим присылает сначала событие с временным номером заявки, поэтому исполнения сопоставляются по order_request_id, то есть по нашему ключу. Ветка «гонка» означает, что запрошенная отмена не гарантирует нулевого исполнения: reducer принимает fill и после неё.

Вход по шагам

Сплошная стрелка означает запрос, пунктир означает ответ или событие стрима. Между шагами 7 и 9 позиция живёт без стопа у брокера. Если стоп не принят за отведённое время, контур выходит по рынку и шлёт тревогу. Рыночная заявка от самого контура — только этот аварийный выход. Входа по рынку нет.

Ярус 3 · самое острое место

Стоп и цели у брокера

После исполнения входа контур выставляет у брокера заявки на цели (с С3 — обычные лимитные, дневные) и стоп-заявку (с С4) и хранит их номера в журнале заявок broker.sqlite3. Что для этого даёт API, проверено по SDK t-tech-investments 1.49.3 из .venv:

Своего стрима у стоп-заявок нетИх состояние видно только запросом GetStopOrders: активна, исполнена, снята, истекла.services.py: get_stop_orders
Срабатывание видно в стриме заявокСработавшая стоп-заявка порождает обычную биржевую заявку. Её исполнение приходит в OrderStateStream, а номер появляется в поле exchange_order_id стоп-заявки.schemas.py: StopOrder.exchange_order_id · подтверждено в песочнице
Связки OCO нетЦель и стоп ничего не знают друг о друге. Уменьшать стоп после цели должен контур. Ключ идемпотентности у стоп-заявок есть, но GetStopOrders его не возвращает: у StopOrder нет поля с нашим ключом. Потерянный ответ ищется по инструменту, стороне, объёму и цене.schemas.py: PostStopOrderRequest.order_id

В песочнице стоп-заявки исполняются. Разведка С1 29.10: STOP_LOSS на продажу 1 лота NG сработал, песочница сама выставила рыночную продажу (её номер — exchange_order_id стоп-заявки), стрим принёс «новая», затем «исполнена», а GetStopOrders показал «исполнена». Имитация срабатывания контуром не нужна: всё из этого раздела проверяется в песочнице по-настоящему.

Цель сработала: как контур это узнаёт

Шаги 4 и 5 делает контур, и только с С4: до него стопа у брокера нет. Если в момент срабатывания цели он не работает, стоп остаётся на прежний объём, и тогда получается вот что:

Стоп всегда на весь остатокПосле любого частичного выхода контур первым делом пересоздаёт стоп, потом делает всё остальное.
Перенос стопаИдёт как «снять старый, поставить новый» с проверкой остатка. Короткое окно без стопа лучше двух стопов на один объём.
Опрос стоп-заявокРаз стрима у них нет, сверщик опрашивает GetStopOrders при каждом незнакомом исполнении и по расписанию, не чаще 30 раз в минуту.
Срок жизниСтоп ставится с GOOD_TILL_CANCEL и переживает конец сессии и остановку робота (переживает ли ночь в песочнице — проверка П24). Цели — обычные лимитные заявки: брокер снимает их вечером, контур ставит заново после открытия торгов (так с С3, решено 08.11). Стоп снимает сам контур при выходе из сделки.
Старт после простояСверщик до первого тика сравнивает остаток с объёмом стопа и целей у брокера и срезает лишнее. Перезакрытие, которое уже случилось, он покажет тревогой.
Ярус 3 · остальные тонкие места

Нюансы и ответы на них

Неттинг позиции

С3

Счёт видит одну позицию на инструмент, у контура на нём может быть несколько сделок.

Каждая сделка ведёт свои заявки по своим ключам, исполнения разносятся по номеру заявки. Встречные сделки по семейству уже запрещены, и для счёта это обязательно.

Асинхронность

С3

Сегодня submit сразу возвращает итог исполнения.

Адаптер отдаёт только ACK или отказ. Исполнения кладёт в очередь поток стрима, а тик забирает их через существующий drain_addressed_events.

Лоты, шаг цены, коридор

С3

Цена фьючерса в пунктах, у каждой бумаги свой шаг и лот, биржа режет цены вне коридора.

Адаптер округляет до min_price_increment, переводит количество в лоты и проверяет коридор до отправки. Цены заявок и исполнений фьючерса брокер возвращает в рублях за контракт (NG: 23 960 ₽ при цене 2.962), а журнал ведёт пункты — адаптер переводит рубли в пункты через стоимость шага. Ошибки построения ловит песочница, денег они не стоят.

Стоп срабатывает иначе

С7

Брокер исполняет стоп по последней цене внутри минуты, симулятор по закрытым 1m-барам.

Результаты счёта и тени будут расходиться, и это нормально. Расхождение попадает в отчёт, а не в логику.

Клиринг, сессии биржи, экспирация

С3

Календарь уже не пускает входы, но брокер всё равно может отказать.

Отказ входа отменяет план и снимает резерв без повторов. Повторы только для выходов и защиты, после открытия торгов.

Окно без стопа

С4

Между исполнением входа и принятием стоп-заявки проходит время.

Срок на постановку стопа. Не успел или получил отказ: выход по рынку и тревога в канал.

Доборы и сокращения

С4

Каждый добор меняет объём, который должен закрывать стоп.

Добор считается завершённым только после того, как стоп пересоздан на новый остаток. До этого следующий добор не допускается.

Стоп у контура и у брокера

С4

На С3 условие стопа проверяет контур по закрытой минуте. Если оставить его рядом со стоп-заявкой, выйдут оба.

Пока стоп у брокера не принят, условие держит контур, как на С3. Принят — контур по минутам стоп не проверяет и только ведёт стоп-заявку.

Ядро на рестарте

С2

Обновление робота перезапускает ядро, и на это время контур остаётся без свечей.

Позиции в паузе защищают стопы у брокера. После старта контур «Счёт» поднимается первым и сверяется до первого тика. Ядро подхватывает живой процесс контура только той же версии.

Ярус 4 · переход

Переход от песочницы к счёту

Один контур с переключателем «песочница или счёт» опасен: журнал песочницы оказался бы на настоящем счёте, и сверщик принял бы её позиции за закрытые стопами. Поэтому счёт не заменяет песочницу, а поднимается рядом с ней вторым видом контура из того же кода, с чистым журналом. Песочница остаётся стендом: через неё проходит каждая привязка и каждая новая версия робота.

Отпечаток счёта. При первом старте контур записывает в свою базу вид брокера и хеш номера счёта. Если при следующем старте отпечаток другой, контур не стартует. Так журнал одного счёта не может продолжиться на другом.

Допуск контура «Счёт» к старту

  1. Токен видит ровно один счёт, это TINKOFF_ACCOUNT_ID, и у счёта access_level с полным доступом. Видит больше — контур не стартует.
  2. GetInfo подтверждает, что пользователю разрешены срочные контракты (qualified_for_work_with). В песочнице этого не увидеть, а без допуска брокер отказывает во входах по фьючерсам.
  3. Тариф прочитан через GetUserTariff, комиссии известны.
  4. Бот и канал «Счёт» заданы.
  5. На первом старте счёт пуст: нет позиций, заявок и стоп-заявок. Иначе тревога и заморозка входов: счётом владеет только робот.

Порядок перехода

  1. Песочница готова. Отчёт С7 за неделю без необъяснённых расхождений, хаос-сценарии С3–С4 пройдены, предохранители С6 срабатывают.
  2. Р1, счёт только на чтение. Открыть счёт робота, выпустить токен только на него, положить деньги. Контур «Счёт» стартует с orders = false. Сделка руками в приложении видна сверщику, капитал в API совпадает с приложением. Неделя без ложных тревог.
  3. Р2, первая привязка. Привязка, которая неделю торговала в песочнице без расхождений, переводится на счёт с confirm. Песочница продолжает торговать ею же, отчёт сравнивает три стороны: эмуляцию, песочницу и счёт.
  4. Дальше по одной. Каждая следующая привязка проходит путь эмуляция → песочница → счёт.

Откат. PUT /api/v1/account/target {"mode": "no_entries"} прекращает новые входы. Открытые позиции доживают со стопами у брокера, песочница и эмуляция работают дальше. Журнал счёта не трогается, повторный старт продолжает с того же места.

Ярус 4 · план работ

Этапы

Каждый этап — отдельный change в OpenSpec: спека, реализация, архив, ветка от origin/release/*. Код контура на брокере пишется на С2–С6 под видом «Песочница», а Р1 поднимает из него второй вид, «Счёт». Этап закончен, когда его можно проверить руками по колонке «Проверяю руками». Первые семь этапов идут в песочнице, настоящие деньги появляются только на Р2.

План С4: стоп у брокера

После С3 цели уже стоят у брокера, а стоп проверяет сам контур по закрытой минуте. Пока процесс контура не работает (убит, ядро обновляется, нет свечей), позицию защищают только цели. С4 переносит стоп к брокеру стоп-заявкой, и позиция защищена без контура. Change — add-broker-protection.

Работы по шагам

1. Разведка стоп-заявок

П19–П24

Разведка С1 проверила только STOP_LOSS на 1 лот в течение получаса.

Дополнить python -m src.sandbox probe. Нужно выяснить:

  • сколько ждёт рыночная заявка стопа и одна ли у неё сделка;
  • что стрим даёт по заявке, порождённой стопом: order_request_id, номер;
  • находит ли её GetOrderState с ORDER_ID_TYPE_EXCHANGE;
  • что отвечает повтор PostStopOrder тем же ключом;
  • что отвечает снятие уже исполненного стопа;
  • в чём цена стопа в GetStopOrders, в рублях или пунктах;
  • переживает ли GTC-стоп ночь (П24, руками утром).

2. Журнал стоп-заявок

broker.sqlite3

Без журнала стоп-заявку не найти после рестарта: нашего ключа в ней нет.

Стоп-заявка — строка журнала заявок вида stop: ключ uuid5(command_id), номер стоп-заявки, цена, объём, exchange_order_id. Состояния: отправлена, активна, снимается, снята, исполнена, истекла, неизвестно.

3. Постановка и пересоздание

ядро С4

Каждое изменение остатка меняет объём, который должен закрывать стоп.

Стоп ставится после исполнения входа и пересоздаётся после цели, добора, сокращения и MoveStop: снять старый, дождаться подтверждения, поставить новый. Частичный вход — стоп на исполненное. Следующий добор не допускается, пока стоп не пересоздан. Срок stop_place_secs: не принят — выход и тревога.

4. Срабатывание

стрим

Стрима у стоп-заявок нет, а заявка стопа приходит в стрим без нашего ключа.

Незнакомая заявка в стриме → GetStopOrders → совпал exchange_order_id → защитные исполнения сделки <trade>:pv:stop:<стоп-заявка>:<сделка биржи>, цели снимаются. Рыночная заявка стопа обычно исполняется сразу; если остаток не закрыт, дальше идёт цикл выхода С3. Опрос — при незнакомой заявке и на сверке, не чаще 30 раз в минуту.

5. Подъём после простоя

до первого тика

Пока контура не было, стоп мог сработать, а ответ на постановку мог потеряться.

Исполненные за простой стопы → сделки через GetOrderState по номеру биржи → факт выхода. Стоп с потерянным ответом ищется по инструменту, стороне, объёму и цене. Лишнее снимается, недостающее ставится. Только потом сверка и первый тик.

6. Сверщик

reconcile

Сейчас сверщик видит в любой стоп-заявке расхождение.

Стоп-заявки берутся из журнала. Нет стопа или объём не равен остатку — пересоздать сразу, без тревоги. Чужая стоп-заявка — тревога и заморозка входов по инструменту.

7. Остановка

бывший С5

close_all на С3 не знает про стоп у брокера.

close_all и снятие привязки с close_all: снять стоп и цели, потом выход. Сокращение сначала уменьшает стоп на свой объём. no_entries, Ctrl+C и kill: стоп остаётся у брокера, сообщение stopped называет число стопов у брокера.

8. Канал и API

2.8.0

Человек должен видеть, стоит ли стоп у брокера.

Строки карточки: «стоп у брокера 2.812 · 10 лотов, стоп-заявка …ab12», «стоп перенесён», «стоп пересоздан на остаток 5», «стоп сработал у брокера», «стоп не принят — выход». В GET /api/v1/sandbox и в позициях контура у сделки есть стоп у брокера: цена, лоты, состояние. OpenAPI 2.8.0. Показ в UI — отдельно, в репозитории UI.
