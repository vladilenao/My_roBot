# Архитектура My_roBot

Торговый робот, работающий с Tinkoff Invest API. Запускается из `run.py`, собирается в
один автономный бинарник через PyInstaller (`run.spec`, см. `README.txt`).

Ритм работы — **«один тик = закрытая свеча любого активного таймфрейма»**: итерация
выравнивается по ближайшей границе закрытия свечи среди ТФ привязок, решения
принимаются только по готовым (закрытым) барам; на тике обрабатываются привязки
тех ТФ, чья свеча закрылась. Помимо ТФ привязок всегда поддерживается базовый
поток **1m**: на нём симулируются защитные стопы/цели, а индикаторные решения
профиля — только на закрытии его собственного ТФ.

## Принципы модульности

- **Один пакет — одна сквозная ответственность.** Внутренности модулей не смешиваются;
  каждая папка в `src/` закрывает свою область.
- **Композиция через конструктор.** Зависимости собираются в `run.py` без DI-фреймворка.
  `TradingBot` не знает конкретных реализаций — получает интерфейсы (`execution`,
  `data_cache`, `context_cache`, `signal_filter`, `trade_manager`, `risk_manager`).
- **Стратегии — только вход.** Стратегия выдаёт детерминированное входное событие
  (направление, ориентир High/Low, время доступности), но не управляет позицией:
  доборы, выходы и стопы ведёт профиль управления сделкой. Имя стратегии → класс и
  конфиг; назначение «стратегия × инструмент» задаётся в конфиге `robot.toml`.
- **Один владелец фактического состояния.** SQLite-хранилище — единственный источник
  истины для планов, заявок, исполнений, целей, резервов, счёта и аудита. Пользовательские
  CSV (`journal.csv`/`positions.csv`) и файл аудита — автоматические проекции базы и
  никогда не читаются для восстановления.
- **Исполнение адресное и отделено от решений.** Команды несут
  `trade_id`/`command_id`/`state_revision`; брокер исполняет строго указанную сделку.
  В торговом режиме под портом — свечной симулятор на базе 1m-баров; в безопасном
  режиме — `NotifyOnlyExecutionPort` (только уведомления, без портфельных резервов).

## Модули и их ответственность

| Модуль | Файлы | Ответственность |
|---|---|---|
| `instruments` | `model.py`, `selector.py` | Тип `Instrument`, нормализация, выбор инструментов при старте. |
| `api` | `client.py`, `instruments.py`, `retry.py` | Обёртка над Tinkoff API (потоки свечей, ретраи, метаданные контрактов). |
| `data` | `cache.py`, `loader.py`, `htf_provider.py` | Кэш рыночных данных по парам и загрузка свечей (`load_candles`), провайдер старших ТФ для фильтров. |
| `market_context` | `context_cache.py`, `models.py`, `sr_levels.py`, `trend.py` | Рыночный контекст по парам: тренд, уровни поддержки/сопротивления. |
| `market_structure` | `swings.py`, `harmonic.py`, `fibonacci.py` | Структура рынка: свинг-детектор, формация AB=CD, уровни Фибо. |
| `strategies` | `*_strategy.py`, `base_strategy.py`, `registry.py`, `signals.py`, `contracts.py`, `names.py`, `indicators/` | Входные стратегии. `Decision` — входное событие (BUY/SELL/HOLD + ориентир входа и время доступности); контракты `Assignment` несут `id`/`management`/`priority`. |
| `trade_management` | `models.py`, `actions.py`, `manager.py`, `state.py`, `audit.py`, `profiles/`, `opposite_signals.py` | **Управление сделкой**: `TradePlan`/`TradeState`/`TargetPlan`, адресные команды, `TradeManager` (фазы, маршрутизация, допуск), чистые переходы фаз, `CalculationTrace`, четыре профиля (`levels_rr`, `atr_trend`, `ma_cloud`, `pattern_targets`). |
| `decision` | `filter.py`, `filters/` | Пост-фильтр **входных** кандидатов (`raw`, `basic_levels`, `triple_screen`); выходы и сокращения фильтр не проходят. |
| `portfolio` | `models.py`, `account.py`, `manager.py`, `risk.py` | Позиции/счёт/резервы и чистая математика портфельного риска: `PortfolioRiskManager` (лимиты сделки/инструмента/групп/портфеля, максимальный дополнительный объём, направленное SHORT-расстояние), `RiskLimits`, `RiskTrade`. |
| `broker` | `port.py`, `journal_broker.py` | Контракт `BrokerPort`/`ExecutionEvent` и адресный свечной симулятор (`fill`/`partial`/`ack`/`reject`/`cancel`, защита, перенос стопов, идемпотентность). |
| `trade_journal` | `schema.py`, `storage.py`, `reducer.py`, `export.py` | SQLite (`user_version`, FK, WAL, единый unit-of-work), транзакционный `ExecutionReducer` (позиции/счёт/резервы/цели/события), `CsvExporter` (атомарный экспорт двух CSV с `export_revision`) и `AuditExporter` (ротируемый `trade_audit.log`). |
| `notifier` | `base.py`, `console.py`, `telegram.py` | Доставка уведомлений (консоль / Telegram), формат плана и событий, короткие имена контрактов. |
| `scheduler` | `timing.py` | `MultiTimeframeScheduler` — координатор сеток активных ТФ (тик = ближайшая граница любого ТФ); `CandleScheduler` — математика одной сетки. |
| `config.py` | — | Параметры из `robot.toml` (внешнего или вшитого `default.toml`) и токены из `.env`. |
| `config_loader.py` | — | Загрузка и валидация TOML: приоритет внешний `robot.toml` → вшитый `default.toml` → дефолты; явные связки (`id`/`management`/`priority`), четыре профиля, лимиты, `database_file`/`audit_file`; неизвестные ключи/несовместимости → `ConfigError` с файлом и ключом. |
| `logging_setup.py` | — | Технический журнал (`bot_debug.log`, ротация, `service_uid`/`correlation_id`) и независимый аудит `trade_audit.log`. |
| `bot` | `trading_bot.py` | **Оркестратор**: сопровождение открытых сделок, сбор входных кандидатов всего тика, пакетный допуск. |

## Поток данных

```
run.py  (композиция зависимостей)
   │
   ├─ instruments.selector ───────────────► список инструментов
   ├─ scheduler.timing ───────────────────► ритм (CandleScheduler)
   ├─ data.cache ─┐                        (кэш)
   ├─ api.client ─┴─► data.loader ────────► свечи (включая 1m для защиты)
   │
   └─► TradingBot._loop()  (один тик = одна закрытая свеча)
          │ 1) защита на 1m: broker.track_bar → стопы/цели по закрытым барам
          │ 2) сопровождение: trade_manager.manage(...) на ТФ закрытой свечи
          │    ├─ профиль → команды (Close/Reduce/MoveStop/Add)
          │    ├─ AddToTrade проходит входной фильтр; остальные — напрямую
          │    └─ submit → broker → ExecutionEvent → reducer → SQLite
          │ 3) вход: strategies.compute/decide → Decision (входное событие)
          │    └─ кандидаты тика сортируются (−priority, id, контракт, signal_id)
          └─► trade_manager.actions_for_signal: профиль планирует → PortfolioRisk
              └─ резерв риска/ГО → outbox → broker → event → SQLite
                     │
              SQLite-транзакция (позиции/счёт/резервы/цели/событие/аудит)
                     │
              ┌──────┼─────────────┐
              v      v             v
      CsvExporter  AuditExporter  notifier (пользователю)
     journal.csv /  trade_audit.log
     positions.csv
```

Ключевые точки порядка на тике: защита на 1m всегда раньше новых входов с медленных
ТФ; сопровождение открытых сделок раньше оценки новых входных сигналов по той же
свече; кандидаты собираются по всем инструментам и только потом допускаются по
приоритету. Стоп имеет приоритет при неоднозначном касании стоп/цели на одном баре;
новые fill не получают ретроактивных тейков по уже достигнутым экстремумам.

## Стратегии

- Каждая стратегия — класс, построенный по `strategies/contracts.py` (`SignalType`,
  `Decision` как **входное событие** с ориентиром и `available_at`) и базовому классу
  `base_strategy.py`; индикаторы живут в `strategies/indicators/`.
- `registry.get_strategy(name)` мапит имя → класс/конфиг; `validate_assignments`
  сверяет назначения.
- Реализованные стратегии входа: `macd_rsi_stoch`, `flat_triangle`, `harmonic_abcd`,
  `ma_cloud_rsi_macd`. MA Cloud отдаёт входные события по трём подтверждениям
  (MA-облако, RSI 50, MACD 0) детерминированно — без ведения «виртуальной» позиции;
  её прежние доборы/выходы перенесены в профиль `ma_cloud`.

## Управление сделкой

- План (`TradePlan`) фиксирует `trade_id`, `assignment_id`, инструмент, сторону,
  исходный `signal_id`, `reference_entry`, стоп, цели, входной trigger/TTL и снимок
  профиля. Фазы: `PLANNED → ENTRY_PENDING → OPEN/BUILDING → REDUCING → CLOSED`;
  `CANCELLED` — только без исполненного объёма.
- Профиль **stateless**: получает immutable view плана/состояния/позиции/рынка и
  возвращает намерения (команды) и новое профильное состояние; объём и среднюю цену
  меняет только reducer в одной SQLite-транзакции.
- Портфельный риск возвращает разрешённый **дополнительный** объём (по итоговой
  позиции после добора) и резервирует риск/ГО незавершённых заявок; выхода и
  сокращения не блокируются лимитами новых входов. Подробные правила профилей и
  численные примеры — `docs/trade-management/profiles.md`.

## Хранение состояния и аудит

- `trades.sqlite3` (по умолчанию, ключ `[trading].database_file`) — единственный
  источник истины: планы, профильные снимки, заявки, fills, цели, резервы, счёт,
  события, обработанные сигналы, outbox и расчётные трассы. Один reducer пишет всё
  одной транзакцией; повтор события идемпотентен; восстановление — только из базы.
- После каждой транзакции и при старте `CsvExporter` атомарно пересоздаёт два
  пользовательских файла из одного снимка: `journal.csv` (лента событий с явным
  типом — ПЛАН/ЗАЯВКА/ВХОД/ДОБОР/ТЕЙК/ВЫХОД/СНИМОК/ОТМЕНА/СТОП/ОТКАЗ) и
  `positions.csv` (карточки: `position_id`= `trade_id`, профиль, фаза, остаток,
  валовой/чистый PnL и комиссии). Оба несут `export_revision`.
- Старые CSV при первом экспорте новой базы сохраняются как `.legacy.<timestamp>`
  без импорта; освобождённый/удалённый файл восстанавливается следующим экспортом.
  На Windows блокировка файла не останавливает торговлю: ревизия отстаёт, ошибка
  фиксируется, экспорт повторяется.
- `AuditExporter` выводит каждую трассу (`CalculationTrace`) ровно один раз в
  ротируемый `trade_audit.log` независимо от уровня `bot_debug.log`; индикаторные
  расчёты сохраняют seed и неизменное входное окно. Секреты не пишутся.

## Вспомогательное

- `tests/` — автотесты: `tests/unit/` (быстрые), `tests/integration/` (SQLite,
  автоэкспорт, outbox, резервы, жизненный цикл четырёх политик), `tests/snapshot/`
  (единый параметризованный раннер стратегий с эталонами в `tests/snapshot/data/`).
- `docs/trade-management/` — пользовательская документация: профили (с четырьмя
  SVG-графиками), хранилище/CSV/аудит.
- `tools/visualize_signals.py` — рендер SVG-картинок сигналов для спецификаций.
- `openspec/` — спецификации и исторические изменения (OpenSpec): каждая фича
  прорабатывается через proposal → design → specs → tasks, затем архивируется.
- Выпуск: версия живёт в `src/__init__.py` (`__version__`, SemVer), изменения — в
  `CHANGELOG.md`; сборка `run.spec` выдаёт `dist/robot-vX.Y.Z` рядом с `robot.toml`
  и `robot-vX.Y.Z.txt` (тезисы версии из CHANGELOG), токены — только в `.env`.
