# Сохранение и ручная переотправка уведомлений Telegram

**Статус: хранилище, команды и очистка реализованы.**
Изменение: [add-telegram-manual-delivery-recovery](../../openspec/changes/archive/2026-10-06-add-telegram-manual-delivery-recovery/proposal.md).

## Зачем сохранять уведомления

Если интернет или Telegram недоступны, торговля продолжается, но уведомление может
не прийти. Чтобы позже отправить именно ту карточку, которую подготовил робот,
сохраняются её текст, подпись, кнопки и готовая картинка. При переотправке цены и
график не рассчитываются заново: пользователь получает исходные сведения о сделке.

Всё находится в `<каталог состояния>/telegram_delivery.sqlite3`. Это отдельная
база уведомлений, а не торговый журнал `trades.sqlite3`.

Картинки хранятся **в отдельной таблице `telegram_files` внутри этой базы**, как
бинарные данные (BLOB). В ней также есть имя, тип файла, размер, контрольная сумма
и время создания. Уведомление ссылается на файл по ID. Постоянные PNG в отдельной
папке не создаются. Сохранение готовой карточки и её картинки происходит одной
транзакцией: для переноса или резервной копии не нужно собирать отдельные PNG.
При копировании работающей SQLite следует использовать корректную резервную
копию SQLite, учитывающую текущие записи, а не копировать только основной файл.

## Картинки хранятся семь дней

Отдельная задача `telegram-files-cleanup` удаляет файлы **старше семи суток с
момента сохранения**, независимо от того, пришло уведомление или нет. Повторная
отправка не начинает эти семь дней заново. Файл ровно семи суток ещё сохраняется.
Тексты, сведения о доставке и история попыток этой задачей не удаляются.

Поэтому переотправить исходную карточку с графиком нужно до удаления картинки.
После удаления список покажет: «Картинка удалена: срок хранения 7 дней». Робот не
будет придумывать новый график или молча заменять фотографию текстом. Уведомления,
которые изначально были только текстовыми, остаются доступными для повторной
доставки. Если удалена картинка недоставленной корневой карточки, её зависимые
этапы могут оказаться заблокированы — причина будет показана в отчёте.

Очистка запускается отдельно от отправки при старте Telegram-части робота и затем
раз в сутки. Если робот выключен, следующая очистка произойдёт при его запуске.
Для независимого ежедневного расписания системный планировщик сможет вызывать:

```sh
.venv/bin/python run.py --telegram-cleanup-files --state-dir data
```

Само внешнее расписание не создаётся. Очистка не отправляет сообщения и
не запускает торговлю; её можно выполнять при работающем роботе. Если картинка
уже считана отправляющим worker в память, текущая попытка заканчивается с этими
байтами; следующая ручная переотправка после очистки будет заблокирована.
Удаление освобождает место внутри SQLite для новых данных; размер
файла базы на диске не обязательно сразу уменьшится.

## Как запросить переотправку

Ниже — интерфейс для запуска из корня проекта. `data` замените на каталог
состояния нужного запуска. Для собранного приложения вместо `.venv/bin/python
run.py` используется путь к исполняемому файлу робота.

Сначала посмотреть список недоставленных уведомлений:

```sh
.venv/bin/python run.py --telegram-pending --state-dir data
```

Просмотр доступен и при работающем роботе. Он покажет ID уведомления, инструмент,
дату, результат попыток и наличие картинки. Например, если в списке нужное
уведомление имеет ID `42`, **запрос на его переотправку**:

```sh
.venv/bin/python run.py --telegram-retry --id 42 --state-dir data
```

ID `42` здесь учебный — нужно подставить ID из вашего списка. Для ручной доставки
робот должен быть остановлен: общий lock защищает от одновременной отправки
одной карточки двумя процессами. Команда запускает только доставку, без торговли.

Если предыдущая попытка завершилась таймаутом, результат неизвестен: Telegram
мог получить сообщение, хотя ответ не дошёл до робота. Для осознанного повтора
такого уведомления нужен дополнительный флаг:

```sh
.venv/bin/python run.py --telegram-retry --id 42 --include-uncertain --state-dir data
```

**Это может создать дубль в канале.** До отправки команда покажет предупреждение.
Без `--include-uncertain` такие попытки пропускаются. Подтверждённые доставки
повторно не отправляются даже с этим флагом.

### Если сообщение пришло, а кнопок нет

Та же команда умеет восстанавливать навигацию **уже доставленной** карточки.
Например, для операции №17, которая была успешно отправлена без кнопок:

```sh
.venv/bin/python run.py --telegram-retry --id 17 --state-dir data
```

Если №17 имеет статус `confirmed`, новая фотография не публикуется. Команда
регистрирует её как основную карточку сделки, восстанавливает кнопки `ЦЕЛЬ1`,
`ЦЕЛЬ2`, `СТОП`, `Итог` для подтверждённых этапов и добавляет «Открыть сделку»
к уже доставленным сообщениям этой же сделки. Недоставленные этапы не получают
ссылок. Отдельной кнопки для входа в текущем оформлении нет.

Восстановление меняет только клавиатуры существующих сообщений; их подписи,
финансовые факты и изображения остаются сохранёнными. Оно работает и после
семидневного удаления PNG, если само сообщение ранее было доставлено.
Повтор команды безопасен для подтверждённых публикаций: используются операции
редактирования кнопок. Флаг `--include-uncertain` нужен для повторной публикации
с неизвестным исходом, но не для восстановления кнопок confirmed карточки.

При сбое обновления кнопок или получения адреса канала команда сообщает ошибку
навигации и завершается с ненулевым кодом. Повторите ту же команду: доставленная
карточка не дублируется, а ссылки собираются заново из актуальных подтверждений.
История неудачных правок сохраняется; после успешного восстановления устаревшие
правки помечаются `superseded` и больше не показываются как недоставленные.

Новые операции сохраняют назначение карточки и её этапов отдельно от текста.
Для старой базы v2 поддерживается восстановление по известному формату ключа
сигнала и заголовкам прежних карточек. Если основную карточку распознать нельзя,
команда явно сообщает об этом и не придумывает ссылки. Другие сделки не меняются.

Пример запроса для всех подходящих уведомлений за день:

```sh
.venv/bin/python run.py --telegram-retry --from 2026-10-06 --to 2026-10-06 --state-dir data
```

Даты учитываются в настроенном часовом поясе, конечная дата включается целиком.
Неопределённые доставки в этом примере исключены. Команда без ID, сделки или
периода не запускает переотправку всего архива.

Если выбранному этапу нужна недоставленная корневая карточка, команда включит её
в список зависимостей и покажет это до отправки. Сначала отправляется корень,
затем этапы; кнопки получают подтверждённые ссылки. Неудача одной сделки не
мешает независимым сделкам. В конце выводится отчёт об успехах, отказах,
неопределённых результатах, пропусках и блокировках.

## Что не получится восстановить

Записи старой версии базы содержат только результаты попыток, без сохранённой
картинки и полного сообщения. Они останутся видны, но точная переотправка для
них недоступна. Это относится и к обсуждавшимся пропущенным сигналам LKOH/BR от
06.10.2026: новая функция не восстановит задним числом отсутствующие материалы.
Перезапуск робота сам по себе не рассылает старые сообщения. Сброс базы не нужен.
