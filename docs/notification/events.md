# События шины уведомлений

Шина разводит торговый контур и доставку уведомлений: контур публикует
типизированное событие, каналы решают, что показать пользователю.

## Правило одного направления

```
торговый контур  ──publish──▶  EventBus  ──▶  Channel (console, telegram)
                                    │
                                    └── подписчик фильтрует по supported_types
```

Контур не знает про каналы, Telegram и тексты. Канал получает торговые данные
только из `Event`; Telegram отдельно хранит receipts/ссылки доставки, не финансовую истину.

## Событие

```python
@dataclass(frozen=True)
class Event:
    type: EventType        # тип из закрытого каталога
    instrument: str = ""   # короткое имя контракта: NG-10.26, не тикер и не label
    bar_time: datetime | None = None
    timeframe: str = ""
    payload: Mapping[str, Any]   # неизменяемый mapping
```

`bar_time` — время закрытия бара, а не время публикации уведомления.
`payload` глубоко неизменяем: изменить вложенные коллекции на месте нельзя.
Необязательный `visual` содержит ограниченный самодостаточный снимок сделки/свечей.

## Каталог типов

| Тип | Что означает | Кто публикует |
|---|---|---|
| `decision` | Решение стратегии: покупка, продажа, отсутствие сигнала, отсев фильтром | `_publish_decision` на каждом тике |
| `signal` | Рекомендация: сделка допущена, заявка ждёт подтверждения | `_publish_signal` |
| `rejected` | Сделка не допущена, с указанием причины | `_publish_rejection` |
| `order_accepted` | Брокер принял заявку | брокер |
| `order_rejected` | Брокер отклонил заявку | брокер |
| `trade_opened` | Открытие позиции | брокер |
| `position_added` | Добор позиции | брокер |
| `stop_hit` | Сработал защитный стоп | брокер |
| `target_hit` | Достигнута цель | брокер |
| `trade_closed` | Позиция закрыта | брокер |
| `trade_cancelled` | Заявка отменена | брокер |
| `protection_armed` | Установлены стоп и ТП | брокер |
| `stop_moved` | Стоп перенесён | брокер |
| `risk_limit_hit` | Превышен общий бюджет или риск неизвестен | портфельный координатор |
| `clearing_done` | Снимок баланса и позиций | брокер |
| `reservation_changed` | Изменилась зарезервированная сумма | брокер |
| `heartbeat` | Тики работы и ошибки за период | торговый контур |
| `error` | Сбой робота, операция без технических деталей | торговый контур |
| `rate_limited` | Исчерпан лимит запросов к API | по необходимости |
| `tick_started` | Служебная граница начала обработки тика | торговый контур |
| `tick_finished` | Служебная граница завершения тика | торговый контур |

Список закрыт: новый тип — это изменение контракта, а не правка шаблона.

## Точки публикации

- `decision` — на каждом тике по каждой паре «инструмент × стратегия», из
  `_analyze`. Это самый частый поток: его почти всегда отфильтровывает
  конфигурация канала.
- `signal` — из `_publish_signal`, **после** допуска и построения плана,
  **до** постановки заявки. Смысл: «сделка в работе, ждёт подтверждения».
- `rejected` — из `_publish_rejection`, с причиной отказа.
- В адресном runtime финансовые события публикуются после применения execution
  редьюсером: цена/количество/комиссия — один fill, gross/net/накопленные расходы
  и остаток — подтверждённая карточка SQLite. Broker-конфигурационная оценка
  подписана отдельно от суммы брокера и исторической неизвестности. Повторный
  execution не публикует финансовый факт заново; сбой канала не откатывает fill.
- `risk_limit_hit` несёт общий процент/B/лимит/open risk/pending/free/excess либо
  unknown-state с причиной. Для портфельного сообщения отдельный trade_id не
  требуется. Legacy структурные BrokerEvent продолжают переводиться в Event.
- `heartbeat` и `error` — из торгового контура напрямую.
- `tick_started` и `tick_finished` — служебные границы одной обработки; консоль получает их независимо от своего списка пользовательских `events`, Telegram их не получает и отдельного текста для них нет.
- `stop_moved` — после действующего ACK переноса, не acceptance `next-bar`.
  Старый/новый подтверждённые уровни и effective time сохраняются в lifecycle-снимке.
  Отмена/отказ операции при открытой позиции не подменяют её состояние закрытым.

## События исполнителя: соответствие и текст

Брокер различает исходы, а не «семейство» операции: `fill` порождён четырьмя
разными типами, `order` — двумя. Тип передаётся значением каталога, а не
вычисляется по признаку.

| Место эмиссии | Исход | Тип события | Текст в консоли |
|---|---|---|---|
| приём заявки | заявка размещена | `order_accepted` | `📝 Ордер: Заявка BUY 4 NG-9.26 по 100 принята` |
| отклонение заявки | заявка отклонена | `order_rejected` | `📝 Ордер: Сделка BUY NG-9.26 отклонена (otherexisting)` |
| вход | исполнение входа | `trade_opened` | `💰 Сделка: Вход BUY 4 NG-9.26 по 100` |
| добор | исполнение добора | `position_added` | `➕ Добор: Добор BUY 2 NG-9.26 по 101` |
| цель | исполнение по цели | `target_hit` | `🎯 Цель: Цель 2 NG-9.26 по 104` |
| стоп | исполнение по стопу | `stop_hit` | `🛑 Стоп: Защитный стоп 4 NG-9.26 по 96` |
| закрытие | исполнение закрытия | `trade_closed` | `💰 Сделка: Закрытие 4 NG-9.26 по 110 (PnL 400)` |
| отмена | отмена заявки | `trade_cancelled` | `❌ Отмена: Заявка NG-9.26 отменена (ttl)` |
| истечение | заявка снята по TTL | `trade_cancelled` | `❌ Отмена: Заявка NG-9.26 истекла по TTL` |
| защита | стоп и ТП выставлены | `protection_armed` | `🛡 Защита: Защитный стоп 96 / ТП 104 установлен` |
| общий бюджет | превышение или unknown-state | `risk_limit_hit` | `⚠️ Риск: общий бюджет 2% … превышение 100 ₽; новые входы/доборы запрещены` |
| клиринг | снимок баланса | `clearing_done` | `🏛 Клиринг: снимок баланса 100000 руб, открыто позиций: 1` |

`trade_id` события нужен для корреляции и в текст не выводится: пользователь
видит смысл события, а не внутренний идентификатор. Идентификатор позиции в
уведомляющем событии отсутствует, потому что пользователю он ничего не
сообщает.

## Каналы

```python
class Channel(ABC):
    name: str
    supported_types: frozenset[EventType]

    def handle(self, event: Event) -> None: ...   # абстрактный
    def close(self) -> None: ...                 # по умолчанию ничего не делает
```

Канал сам фильтрует по `supported_types` и сам решает, что выводить:
шаблон принадлежит каналу, общего форматтера нет.

- **console** — источник истины. По умолчанию получает все пользовательские
  события и служебные границы тика, печать в `stdout` через `print`, без записи
  в логгер. Чистые HOLD не печатаются по одному: если за штатный тик не было
  другого вывода, печатается `● HH:MM ➜ ⏳ Нет сигналов (N пар: <инструменты>)`;
  время — фактическое московское время публикации. Явный список `events` не
  требует добавлять границы, но исключение `decision` отключает и эту сводку.
- **telegram** — по умолчанию `signal`, `trade_opened`, `position_added`, `stop_hit`,
  `target_hit`, `stop_moved`, `trade_closed`, `trade_cancelled`, `order_rejected`.
  `handle()` кладёт Event в `queue.Queue(maxsize=1000)`; один daemon-поток
  форматирует, рендерит и отправляет [визуальную историю](telegram-cards.md).

### Очередь Telegram

- Переполнение означает, что сеть не успевает: отбрасывается **самое старое**
  сообщение, чтобы свежие состояния сделки не терялись.
- Текст до 4096/подпись фото до 1024 после разбора HTML; подробности идут
  продолжениями, без разрыва HTML-тегов/сущностей.
- `429` и сетевые исключения пишутся в `bot_debug.log` и **не повторяются**.
- Без токена или `chat_id` канал не отправляет и не печатает ничего: в этом
  случае пользователь не увидел бы уведомление и не понял бы почему.
- `close(timeout=5.0)` завершает поток; на остановке робота очередь допускается
  не опустошиться полностью — лучше потерять хвост, чем зависнуть на выходе.

## Конфигурация

```toml
[notifier]
channels = ["console", "telegram"]   # порядок подписки

[notifier.console]
events = ["decision", "signal", "rejected", "heartbeat", "error"]

[notifier.telegram]
events = ["signal", "trade_opened", "position_added", "stop_hit", "target_hit",
          "stop_moved", "trade_closed", "trade_cancelled", "order_rejected"]
```

Старый ключ `channel = "telegram"` поддерживается и равносилен
`channels = ["telegram"]`; задавать оба в одном файле — ошибка конфигурации.
Неизвестный канал, неизвестный тип события, пустой список или повтор — тоже
ошибка загрузки, а не предупреждение в логе.

Секреты Telegram живут только в `.env` или переменных окружения, в `robot.toml`
их быть не должно.

## Формулировки

Консольные тексты собраны в `src/notifier/templates/`; HTML Telegram — в
`src/notifier/telegram_templates.py`. Шаблоны принадлежат своему каналу:

- `decision` — `● NG-10.26 (1h) 22:45 | macd [basic] ➜ 🟢 ПОКУПКА (BUY) — Цена: 1234.568`
- тихий тик — `● 10:15 ➜ ⏳ Нет сигналов (8 пар: NG-9.26, GAZP, Si, RTS)`
- `rejected` — `⛔ NG-10.26 ➜ Сделка не допущена: Размер ниже минимального`
- `signal` — план со статусом «в работе, ждёт подтверждения», валовым/чистым сценарием, оценкой расходов, выбранным объёмом/ограничением и общим бюджетом; неизвестный полный payoff не подменяется нулём.
- `error` — `❗ Сбой: анализ NG-10.26 (1h). Робот продолжает работу. Подробности — в bot_debug.log рядом с роботом.`

Технические дампы исключений в уведомления не попадают: они остаются в
`bot_debug.log` через `log.exception`.
